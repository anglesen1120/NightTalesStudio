# Local development setup

Daily development is native on macOS, without Docker (`plans/00-overview.md` §5.1, `DECISIONS.md` §10.13).

## Native stack (default)

One command starts the whole platform on this machine, every listener on `127.0.0.1` (11.1.1-T1, D14,
11 CR-16). Docker is never involved.

```bash
brew install postgresql@17 seaweedfs mailpit awscli ffmpeg   # awscli by tools/dev/storage-init.sh; ffmpeg by tools/mock-mpt
(umask 077; cp .env.example .env)                     # then set your own POSTGRES_PASSWORD
tools/dev/up.sh                                       # add --web for ng serve, --skip-storage-init to skip step 4
tools/dev/down.sh                                     # --services also stops postgresql@17, --volumes discards dev data
```

`ffmpeg` is the 11.1.2-T1 addition: `tools/mock-mpt` writes its two canned 10 s MP4s with `ffmpeg -f lavfi`
on the first native start (its image's media stage runs the same recipe), and `tests/NightTales.MockMpt.Tests`
runs it once too — hence the unit job below needs `ffmpeg` on the PATH as well.

`up.sh` is idempotent: a service that is already running is left alone, so running it twice changes
nothing. It verifies `.env` and the ports *before* it starts anything, then

1. builds `src/NightTales.Api`, `src/NightTales.Worker` and `tools/mock-mpt` once, sequentially, before
   anything starts — every host shares the same project outputs, so parallel `dotnet run`s race on them.
   The build passes `-p:OpenApiGenerateDocuments=false`, the flag both Dockerfiles use on publish: the
   Api's build-time OpenAPI generator boots the host without this script's start-up env and fails on a
   fresh clone, so the document is generated by CI instead (09.1.5-T1, which sets those values and never
   runs this script). A failed build exits 1 with the log path and starts nothing — no seaweedfs or
   mailpit process is left half-up;
2. starts the Homebrew `postgresql@17` service (only when `brew services list` says it is not started)
   and runs `tools/dev/db-init.sh` (role and database from `.env`, idempotent);
3. starts `seaweedfs` and `mailpit` as its own loopback processes — never `brew services`, whose stock
   definitions take no flags and bind every interface;
4. runs `tools/dev/storage-init.sh` when it exists (11.1.1-T2 creates the three dev buckets);
5. starts each host with `dotnet run --no-build` (the mock is skipped, with a warning, until 11.1.2-T1
   lands) and waits for every health endpoint (`DEV_HEALTH_TIMEOUT`, default 90 s; the build in step 1
   runs before this wait, so raise the row only if cold start-up is slow). It fails with exit 1 naming
   the service and its log file — loudly, never as a silent half-up stack. A host whose process has
   already exited is reported at once instead of waiting out the timeout, and the services that did come
   up are left running for inspection (`tools/dev/down.sh` stops them).

Exit codes are the 01 D9 convention: 0 ok, 1 a check failed, 2 usage or environment (an unknown flag,
a missing `.env`, a missing variable — named, with nothing started).

| Service | URL |
|---|---|
| Api | `http://127.0.0.1:5000` (`/health/live`) |
| Worker health | `http://127.0.0.1:8082/health/ready` |
| mock-mpt | `http://127.0.0.1:8090` (`/v1/health`, `x-api-key` header) |
| Mailpit UI | `http://127.0.0.1:8025` (SMTP `127.0.0.1:1025`) |
| Storage (S3) | `http://127.0.0.1:8333` (SeaweedFS; volume server 8084, off MPT's 8080) |
| Web (`--web`) | `http://127.0.0.1:4200` |
| PostgreSQL | `127.0.0.1:5432`, role and database from `.env` |

Runtime state lives in the git-ignored `.nts/dev/` (`NTS_HOME`, 01 DEC-5): `<service>.pid` plus
`<service>.identity` (the pid and the exact instance `up.sh` started — start time and command line),
`<service>.log`, `config/` (the throwaway Auth/DataProtection material `up.sh` generates once —
the Api and the Worker validate an ES256 signing key, `App:PublicOrigin` and the `DP_KEK` at
start-up, 09.3.2-T1/09.9.4-T1), `seaweedfs/` and `mailpit/`. `down.sh` only signals a process whose
identity still matches, so a pid recycled by another process is never killed, and `up.sh` refuses to
start (exit 2) when `DEV_KEK_PASSWORD` in `.env` no longer matches the password file the KEK PFX was
generated with (the secret is never printed). The ports are `.env` rows
(`DEV_API_PORT`, `MOCK_PORT`, `DEV_WORKER_HEALTH_PORT`, `DEV_WEB_PORT`, `DEV_STORAGE_PORT`,
`DEV_STORAGE_VOLUME_PORT`, `DEV_MAIL_SMTP_PORT`, `DEV_MAIL_UI_PORT`); each is validated as an integer
in 1–65535 during preflight (a malformed row exits 2 before anything is built or started), and `up.sh`
exits 1 naming a port that is already taken. The Api's internal 8081 listener (02 D10,
code-configured by 02.5.2-T2) has no row and is only checked for conflicts.

The default `DEV_API_PORT=5000` collides with the Mac's **AirPlay Receiver** (System Settings → General →
AirDrop & Handoff): when it is on, ControlCenter listens on `*:5000`, so `up.sh` exits 1 naming
`DEV_API_PORT` before starting anything. Put a free port in `.env` instead — `DEV_API_PORT=5100` is what
the owner's `.env` uses — and the URLs `up.sh` prints follow that row. This override is native-only: the
optional compose `api` service publishes a fixed `127.0.0.1:5000:8080`, so move its host side in a
git-ignored `docker-compose.override.yml` if 5000 is taken.

`tools/dev/down.sh` stops each service with `SIGTERM` and waits 15 s before `SIGKILL`. SeaweedFS is the
slow one: with `up.sh`'s command line, `weed server` needs 10–25 s for its own graceful shutdown
(measured on seaweedfs 4.48, 2026-10-02; `SIGINT`, a repeated `SIGINT` and `-master.peers=none` all give
the same or worse, so it is not a signal problem), and a `down.sh` run can therefore end with
`seaweedfs … SIGKILL`. That is safe: the `.nts/dev/seaweedfs` store is disposable and `--volumes` deletes
it outright. `--volumes` verifies first that the server on `127.0.0.1:5432` is the Homebrew
`postgresql@17` cluster whose data directory this machine owns (the same check `db-init.sh` runs) and
refuses any other cluster before it deletes a file or sends a `DROP`; the shared Homebrew data
directory (and the `NTS_TEST_PG` databases in it) is never touched.

`up.sh` does not apply migrations: run the command in the Migrations section below once against a
fresh database.

## .NET solution

- SDK 10.0.401 (`global.json`, `rollForward: latestPatch`).
- The two commands below are exactly what `.github/workflows/backend.yml` runs (`build-test`, then
  `integration`). The build-time OpenAPI generator boots the Api, so every build and test command needs
  the five values a deployment always provides: a parseable connection string, which it never uses to
  connect; an ES256 signing key for the start-up validation of 09.3.2-T1 (secret
  `nts/<env>/api/JWT_SIGNING_KEY`); a valid `App:PublicOrigin` for the validation of 09.9.4-T1 (BD12) —
  the base `appsettings.json` carries the Development value `http://localhost:4200`, which is rejected
  outside Development; the `DP_KEK` PFX of the Data Protection key ring (09.9.4-T1, WF15, secret
  `nts/<env>/shared/DP_KEK`); and a non-default `Email:AddressHashPepper` (09.2.6-T3, BD16) — the base
  `appsettings.json` carries the Development pepper, which the e-mail validator rejects outside
  Development. Generate throwaway values for all of them — CI does the same with `openssl` and fixed
  placeholders, so no private key or certificate is ever committed.

```bash
export ConnectionStrings__Postgres='Host=127.0.0.1;Database=nighttales;Username=nighttales;Password=ci-openapi-document-generation-placeholder'
export Auth__Jwt__SigningKey="$(openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256)"
export App__PublicOrigin='https://localhost:4200'   # any valid https origin; never a real deployment one
export Email__AddressHashPepper='ci-openapi-document-generation-placeholder'   # non-secret; same as CI
# A throwaway DP_KEK: an RSA self-signed PFX (RSA because the ring is encrypted with EncryptedXml,
# which accepts RSA only) in a temporary directory, generated once per shell.
export KEK_PASSWORD="$(openssl rand -hex 24)"
openssl req -x509 -newkey rsa:2048 -nodes -days 1 -subj '/CN=nts-dev-dp-kek' \
  -keyout "${TMPDIR:-/tmp}/dp-kek.key" -out "${TMPDIR:-/tmp}/dp-kek.crt"
openssl pkcs12 -export -out "${TMPDIR:-/tmp}/dp-kek.pfx" \
  -inkey "${TMPDIR:-/tmp}/dp-kek.key" -in "${TMPDIR:-/tmp}/dp-kek.crt" -passout env:KEK_PASSWORD
export DataProtection__KekPfxPath="${TMPDIR:-/tmp}/dp-kek.pfx"
export DataProtection__KekPfxPassword="$KEK_PASSWORD"
dotnet restore NightTales.ci.slnf --locked-mode
dotnet build   NightTales.ci.slnf -c Release --no-restore   # writes src/NightTales.Api/openapi.json (git-ignored)
dotnet format  NightTales.ci.slnf --verify-no-changes --no-restore
```

```bash
# Unit job (no database). The count grows with every feature (98 on the 2026-09-29 wave-2
# tree, 35 when this block was written). `--minimum-expected-tests 1` is the guard that makes a
# zero-match filter red instead of silently green (see the note below). `--no-build` reuses the
# Release build from the block above, so that block (with its ConnectionStrings__Postgres export)
```

```bash
# Integration job (needs the server from the Database section below). The count grows with every
# feature (56 on the 2026-09-29 wave-2 tree, 23 when this block was written). Self-contained: the
# build-time values from the block above plus NTS_TEST_PG are exported here (the same five values the
# first block exports, so re-run that block or export them again). `ConnectionStrings__Postgres`,
# `Auth__Jwt__SigningKey`, `App__PublicOrigin`, `Email__AddressHashPepper` and the `DP_KEK` pair are required by the build-time
# OpenAPI generator, which boots the Api and runs its start-up validation — not by the tests, which
# read NTS_TEST_PG. Without the connection string a build fails inside the generator: MSB3073 from the

# nts/<env>/api/JWT_SIGNING_KEY) must be the PEM of a P-256 EC private key`, and without the KEK or the
# origin with the fixed `'DataProtection:KekPfxPath' is required` / `'App:PublicOrigin' is required and

export ConnectionStrings__Postgres='Host=127.0.0.1;Database=nighttales;Username=nighttales;Password=ci-openapi-document-generation-placeholder'
export Auth__Jwt__SigningKey="$(openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256)"
export App__PublicOrigin='https://localhost:4200'
export Email__AddressHashPepper='ci-openapi-document-generation-placeholder'
export KEK_PASSWORD="$(openssl rand -hex 24)"
openssl req -x509 -newkey rsa:2048 -nodes -days 1 -subj '/CN=nts-dev-dp-kek' \
  -keyout "${TMPDIR:-/tmp}/dp-kek.key" -out "${TMPDIR:-/tmp}/dp-kek.crt"
openssl pkcs12 -export -out "${TMPDIR:-/tmp}/dp-kek.pfx" \
  -inkey "${TMPDIR:-/tmp}/dp-kek.key" -in "${TMPDIR:-/tmp}/dp-kek.crt" -passout env:KEK_PASSWORD
export DataProtection__KekPfxPath="${TMPDIR:-/tmp}/dp-kek.pfx"
export DataProtection__KekPfxPassword="$KEK_PASSWORD"
export NTS_TEST_PG="Host=127.0.0.1;Port=5432;Database=${POSTGRES_DB:-nighttales};Username=${POSTGRES_USER:-nighttales};Password=<POSTGRES_PASSWORD from .env>"
dotnet restore NightTales.ci.slnf --locked-mode
dotnet build   NightTales.ci.slnf -c Release --no-restore
dotnet test    NightTales.ci.slnf -c Release --no-build \
```

- Tests run on Microsoft.Testing.Platform (`global.json` `test.runner`; xunit.v3 4.x no longer supports VSTest on the .NET 10 SDK). Test projects pass `--ignore-exit-code 8` (`tests/Directory.Build.props`), so a run with **zero** tests prints `total: 0` and still exits 0 — a filter typo would pass vacuously. Both commands above therefore pass `--minimum-expected-tests 1`, which fails such a run with `Minimum expected tests policy violation, tests ran 0, minimum expected 1` and exit code 9 (8 would be ignored). Do not add `--logger trx` / `--report-trx`: under this xunit.v3/MTP setup they turn the run into `Zero tests ran` with exit code 5 (verified 2026-09-29); CI uploads the console log instead.
- The Api listens on `http://127.0.0.1:5000` (`src/NightTales.Api/Properties/launchSettings.json`). Use `127.0.0.1`, not `localhost`: macOS AirPlay Receiver (ControlCenter) listens on `*:5000`, and `localhost` can resolve to it. The **Native stack** section above covers the same collision for `up.sh` and how to move the native Api port with `DEV_API_PORT`.

## Host boot contexts

The Api and the Worker have several boot contexts beyond `dotnet run`. A host that is started runs its
registered `ValidateOnStart` checks and hosted services, but TestKit harnesses and CLI modes do not
execute every normal entry-point step or background service. Code that works under `dotnet run` can
still fail the build or the gate in another context.

|Context|Environment|Database|Configuration comes from|
|---|---|---|---|
|`dotnet run` / `tools/dev/up.sh`|Development|local PostgreSQL 17, migrated|`appsettings*.json` + the env exports above|
|`nts-migrate` (EF migration bundle)|No Api/Worker host environment or startup services|target PostgreSQL database; applies migrations|`AppDbContextDesignFactory` reads `ConnectionStrings__Postgres` / `ConnectionStrings:Postgres`; the bundle can override the connection with `--connection`. Factory construction needs no Api/Worker secrets.|
|`nts-seed` / Api or Worker `--seed`|Environment of the invoking host/process|target PostgreSQL database, already migrated|Same configuration sources and eager composition checks as the invoking Api/Worker. The host is built, then `SeedCommand.Run` executes `SeedRunner` and exits without starting listeners or hosted services; host-start `ValidateOnStart` checks are not automatically run.|
|`ApiFactory` (TestKit)|Development (WebApplicationFactory)|per-class test database|`ApiFactory.ApplyRequiredStartupSettings` (`tests/NightTales.TestKit/Api/ApiFactory.cs`)|
|`ApiFactory.ProductionHost` (TestKit)|Development by default (WebApplicationFactory); the callback may select Production with `UseEnvironment`|per-class test database|`appsettings*.json` + process configuration, overridden by `ApplyRequiredStartupSettings`, the connection string and the caller's callback; production registrations, without the test authentication scheme or fake clock|
|`WorkerHost` (TestKit)|Process-selected Generic Host environment; not explicitly forced to Development|per-class test database|`WorkerHost.HarnessSettings` + `EmailTestSettings`; default configuration sources are cleared. Telemetry is opt-in and `WithTelemetry()` supplies `Logging:UserHashSalt`; the harness removes the outbox and node-health loops, defaults to inline jobs and does not run entry-point node registration.|
|`NightTales.MptAdapter` executable (`AdapterHost.RunAsync`)|Process-selected WebApplication environment; Development affects allowed listen addresses|local SQLite under `Adapter:DataDir`, migrated before listening|Default WebApplication configuration providers plus `Adapter` and `RenderNodeServer` option defaults. `RenderNodeServer:ApiKey` is required, with `ADAPTER_API_KEY` as fallback; the optional next key has the analogous `ADAPTER_API_KEY_NEXT` fallback. Startup checks key separation, `Adapter:ListenAddress`, valid `Adapter:CertPath` / `Adapter:KeyPath` files and writable `Adapter:DataDir`; options are validated on start.|
|**Build-time OpenAPI generator** (every `dotnet build` of the Api, `OpenApiGenerateDocuments=true` in `NightTales.Api.csproj`)|Production|**none you can rely on**: CI passes a placeholder connection string; the local gate script points at the shared server, whose database may lack the newest tables|`appsettings.json` (Development defaults, some refused outside Development) overridden by process env: the `env:` block of `.github/workflows/backend.yml`, the local gate script, the build-time blocks in [.NET solution](#net-solution)|
|Docker image publish (`src/NightTales.Api/Dockerfile`)|n/a|n/a|the generator is off (`-p:OpenApiGenerateDocuments=false`); `tools/dev/up.sh` turns it off the same way|

TestKit also applies a process-wide host default before its factories run: `TestHostDefaults` sets
`DOTNET_hostBuilder__reloadConfigOnChange=false` when that environment variable is absent, disabling
appsettings reload watchers. An explicit environment value is preserved. This is a test-host default,
not an application-required configuration key.

Rules for any change that runs at start-up:

- It must succeed in every row above. Data seeding at start-up runs only in Development:
  `SeedHostedService.StartAsync` returns early outside Development, and other environments seed
  explicitly with `nts-seed`, the host's `--seed` switch (09.2.5 plan §2). Start-up code in the
  **Api** must not need a migrated database, because the build-time generator boots the Api without
  one: a hosted service that queries a table fails the build with `42P01` (02.2.4-T1). The Worker is
  not booted by the generator; its start-up database work (e.g. node registration) runs against a
  migrated database.
- A new configuration key that the host refuses to start without outside Development needs a
  non-secret placeholder in every Production-like row: the `env:` block of
  `.github/workflows/backend.yml`, the local gate script, both build-time blocks in
  [.NET solution](#net-solution), `ApiFactory.ApplyRequiredStartupSettings`, and `WorkerHost.HarnessSettings` /
  `EmailTestSettings` when the Worker binds it. Precedent: `Email__AddressHashPepper` (09.2.6-T3).
  The generator reports a missing key as `MSB3073` from `dotnet-getdocument` with a long hosting stack
  (see the build-time block), so check this list before hunting.
- A new way of starting a host adds a row to this table.
- The MptAdapter is a separate executable: its API keys, TLS files, listen-address rules and writable
  SQLite data directory must remain valid when changing startup configuration; Api/Worker build-time
  placeholders do not satisfy these checks.

## Database

Native PostgreSQL 17 from Homebrew on `127.0.0.1:5432` (loopback only).

```bash
(umask 077; cp .env.example .env)        # then set your own POSTGRES_PASSWORD (unquoted)
brew install postgresql@17
brew services start postgresql@17
tools/dev/db-init.sh                      # role + database from .env; safe to re-run
export PATH="$(brew --prefix postgresql@17)/bin:$PATH"   # psql / pg_isready (keg-only formula)
```

`db-init.sh` first checks (and re-checks after its own restart) that the server on `127.0.0.1:5432` is Homebrew `postgresql@17` (`server_version_num` 17.x, `data_directory` = `$(brew --prefix)/var/postgresql@17`); otherwise it exits 1 without changing anything. It then sets `listen_addresses = '127.0.0.1'` (restarting the service once if it differs), creates the `.env` role with `LOGIN CREATEDB` and its database, and converges the password and the database owner on re-runs. It refuses `postgres`/`pg_*` and any existing role with SUPERUSER, CREATEROLE, REPLICATION or BYPASSRLS, the system databases, a missing `.env` password and the `.env.example` password. `CREATEDB` is needed by the test fixture, which creates one database per test class. Homebrew's default `pg_hba.conf` trusts `127.0.0.1`, so locally the password is not enforced; it matters for the compose path and for any `scram-sha-256` setup.

Connection string for the Api and the Worker, never in `appsettings*.json`. `db-init.sh --user-secrets` stores it with `dotnet user-secrets` for both projects, built from the same parsed `.env` values and piped as JSON on stdin, so the password never appears in argv or shell history:

```bash
tools/dev/db-init.sh --user-secrets
```

The environment variable `ConnectionStrings__Postgres` works as well. Integration tests read `NTS_TEST_PG`, which points at this same server; export it (or set it in the shell that runs `dotnet test`) with the same `.env` values and a database the role can connect to, because each test class creates and drops its own database next to it:

```bash
export NTS_TEST_PG="Host=127.0.0.1;Port=5432;Database=${POSTGRES_DB:-nighttales};Username=${POSTGRES_USER:-nighttales};Password=<POSTGRES_PASSWORD from .env>"
```

The `Database=` value is only where the fixture runs its own DDL — `CREATE DATABASE`, `DROP DATABASE` and the catalog queries. No test ever writes into it: every test class gets its own fresh `nts_t_<uuid>` database copied from the template, so the value carries no state and **any database the role can connect to works**. The dev value above is `nighttales` (the `.env` database made connectable by `tools/dev/db-init.sh`); the CI integration job points `NTS_TEST_PG` at its `postgres:17` service container, which it reaches at `127.0.0.1` — a loopback host, so CI needs no override.

A missing or blank `NTS_TEST_PG` fails the test fixture with a named error; it never skips silently. The fixture checks the server once per run (`tests/NightTales.TestKit/Database/PostgresFixture.cs`):

| Fact | Behaviour |
|---|---|
| Server major | must be PostgreSQL **17** (`server_version_num / 10000`); anything else fails with `NTS_TEST_PG must point at PostgreSQL 17 (found …)` before a database is created |
| Role privileges | the role needs `CREATEDB` and must own the databases the harness manages: `PostgresFixture` drops and rebuilds the template database `nts_template` once per run and each test class gets `CREATE DATABASE … TEMPLATE nts_template`, dropped with `FORCE` when the class is over. SQLSTATE `42501` (for example `must be owner of database nts_template` or `permission denied to create database`) becomes an `InvalidOperationException` that names the failing statement and points at `tools/dev/db-init.sh`; every other SQLSTATE keeps its original `PostgresException` |
| Managed database names | every database the fixture creates or drops must start with the reserved prefix `nts_` — the template name is checked when the fixture is constructed, and the DDL renderer refuses any other name, so a typo or a stray name can never reach a shared database |
| DDL target host | the server must be **loopback** (`127.0.0.0/8`, `::1`, `localhost` or a Unix-socket path). A remote host is refused with `NTS_TEST_PG points at '<host>', which is not a loopback host …` unless `NTS_TEST_PG_ALLOW_REMOTE_DDL=1` is set explicitly; the fixture **drops and creates databases**, so that override must never target a shared or production cluster — only a disposable test server. CI needs no override: the `postgres:17` service container is reached at `127.0.0.1` (loopback) |
| Missing, blank or unparsable value | `InvalidOperationException` naming `NTS_TEST_PG`, with the connection string masked (`Password=***`); never a skip |
| Unit job | needs no `NTS_TEST_PG`: `dotnet test … --filter "Category!=Integration" --minimum-expected-tests 1` leaves out every class tagged `Category=Integration` — every class deriving from `NightTales.TestKit.IntegrationTest` plus the DB-dependent `NightTales.Infrastructure.UnitTests/Persistence` classes |

Each class database's Npgsql pool is cleared before the `DROP DATABASE … WITH (FORCE)`, so the drop does not wait for PostgreSQL to terminate idle pooled backends; that is why a class teardown costs about 10 ms instead of a few hundred.

**Optional compose path (e2e / image smoke only).** `docker-compose.yml` defines a `postgres` service (`postgres:17-alpine`, `127.0.0.1:5432`, healthcheck: a password login with `psql -h 127.0.0.1 ... SELECT 1`). Daily development never starts it. It binds the same port as the native server, so stop one before starting the other, or move the host port in a git-ignored `docker-compose.override.yml`. Its data volume is disposable: `docker compose down -v`. The image applies `POSTGRES_*` only when the volume is first created; after changing them, recreate the volume or the healthcheck stays unhealthy.

`docker-compose.yml` is one file with one `name: nighttales`: `postgres` (09.1.1-T2), `api`, `worker`
and `web` (11.1.1-T1), plus `storage` (SeaweedFS) and `mail` (Mailpit) (11.1.1-T2). Every published
port is `127.0.0.1:<host>:<container>`, every service has a healthcheck, and every value comes from
`.env` (the file has `${VAR:?…}` guards, so no credential is committed).

```bash
docker compose config --quiet                          # validates the merged file (fails without POSTGRES_PASSWORD).
                                                       # Never print the resolved file: it interpolates secrets.
docker compose up -d --wait                            # postgres, api, worker, storage and mail all healthy
docker compose --profile web up -d --wait              # adds web; 10.1.1-T2 owns that image
docker compose ps --format '{{.Service}} {{.Ports}}'   # every published port starts with 127.0.0.1:
docker compose down                                    # or: down -v to discard the pgdata and seaweedfs volumes
```

- The Api and the Worker build from `src/NightTales.Api/Dockerfile` and
  `src/NightTales.Worker/Dockerfile` (multi-stage, non-root, base images pinned by digest; both are
  `aspnet:10.0` because the Worker hosts a Kestrel health listener, 09 W3 CR-42).
- Both need the dev-only Auth/DataProtection material the native stack uses. Run `tools/dev/up.sh`
  once: it writes the throwaway ES256 signing key and the `DP_KEK` PFX into `.nts/dev/config`
  (git-ignored). The **Api only** loads the signing key, from `.nts/dev/config/compose.env` (the
  Worker never composes the auth services, 09.3.2-T1, so it must not hold it); both services get the
  PFX through a single read-only bind mount of that one file (`NTS_DEV_CONFIG_DIR` moves the host side
  when `NTS_HOME` points at another checkout) — read-only config, never container state, and nothing
  is committed.
- The DP_KEK PFX stays **owner-only** (`up.sh` runs with `umask 077`, mode `0600`) and a bind mount
  keeps the host ownership, so the containers run as the UID that owns the checkout instead of the
  image's `APP_UID` (1654). Put the numbers from `id -u` / `id -g` into `.env` as
  `NTS_COMPOSE_UID` / `NTS_COMPOSE_GID` — on a workstation and on a CI runner alike (the rows are
  commented out in `.env.example`). Leaving them unset keeps the image user, which is only correct
  for a service that does not need the key. The key's mode is never relaxed to make this work.
- The Worker's health listener binds `Worker:HealthAddress` — `127.0.0.1` by default (the native
  default, and `up.sh` pins it), and the compose service sets `0.0.0.0` so the published host port
  `127.0.0.1:8082` can reach it across the container's network namespace. The host side is never
  wider than `127.0.0.1`.

- Do not run both paths at once: `5432`, `8333` and `1025` collide. The override file can move the
  host side of a published port.
- `web` is behind the `web` profile and its image is 10.1.1-T2's, so `docker compose config --quiet`
  validates the definition long before the image exists.
- `storage` and `mail` are digest-pinned (`chrislusf/seaweedfs` 4.48, `axllent/mailpit` v1.31.3; D14;
  a bump is a hand edit, T12) and publish only `127.0.0.1:8333`, `127.0.0.1:1025` and
  `127.0.0.1:8025`. SeaweedFS's master (9333), filer (8888) and volume server (8084) stay on the
  compose network — 8084 keeps MPT's 8080 free — and its store lives in the `seaweedfs` volume, so
  `down -v` discards it. Both services carry the healthchecks `up.sh` waits on natively
  (`/cluster/status`, `/api/v1/info`). The Api and the Worker reach them by service name
  (`http://storage:8333`, `mail:1025`; T41); `tools/dev/storage-init.sh` still uses the published
  loopback endpoint, so one command serves both paths.
- After `up`, run `tools/dev/storage-init.sh` once to create the three dev buckets (D14/D15); after
  `docker compose down -v` it creates them again (dev data is disposable). SeaweedFS in the compose
  service also runs with `-master.volumeSizeLimitMB=64`, for the same reason as the native command
  line above: the 30 GB default leaves no free volume slot for a new bucket.

## Local object storage (SeaweedFS)

Development speaks S3 to a local **SeaweedFS** gateway, started by `tools/dev/up.sh` as its own
process (11.1.1-T2, D14; Apache-2.0, E11) — never `brew services`, whose stock definition takes no
flags, binds every interface and would put the volume server on 8080 (MPT, 01 D4). The dev buckets
are created by `tools/dev/storage-init.sh`.

| Piece | Value |
|---|---|
| S3 API | `http://127.0.0.1:8333` (`STORAGE_ENDPOINT`) |
| master status API | `http://127.0.0.1:9333/cluster/status` (the readiness probe `up.sh` waits on) |
| volume server | `127.0.0.1:8084` (moved off MPT's 8080) |
| filer | `127.0.0.1:8888` (unused in dev) |
| data directory | `.nts/dev/seaweedfs` (git-ignored; `down.sh --volumes` deletes it) |
| formula | `seaweedfs` 4.48 (Homebrew; `brew install seaweedfs`) |

The exact command line `up.sh` runs (the credentials come from the environment, never argv):

```bash
AWS_ACCESS_KEY_ID="$STORAGE_ACCESS_KEY" AWS_SECRET_ACCESS_KEY="$STORAGE_SECRET_KEY" \
  weed server -ip=127.0.0.1 -ip.bind=127.0.0.1 -dir=.nts/dev/seaweedfs \
    -volume.port=8084 -master.volumeSizeLimitMB=64 -s3 -s3.port=8333
```

`-master.volumeSizeLimitMB=64` is not optional: SeaweedFS's 30 GB default leaves no free volume slot
for a new bucket, so the second `create-bucket` fails with `No writable volumes` (04.2.3-T1
rehearsal). `-s3` reads `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, which `up.sh` exports from the
`STORAGE_ACCESS_KEY`/`STORAGE_SECRET_KEY` rows in `.env`, so the server and every client agree.

**Buckets (D15, `<env> = dev`).** `nt-media-dev`, `nt-public-dev` and `nt-music-dev`, plus the
`music/` and `music-evidence/` prefix markers inside the music bucket. `tools/dev/storage-init.sh`
creates them idempotently and never deletes; it exits 0 ok / 1 a check failed / 2 usage or
environment, waits up to `STORAGE_WAIT_SECONDS` (default 60) for the gateway, and uses the host `aws`
CLI first, `uvx --from awscli aws` next, then the pinned `amazon/aws-cli` container (11 CR-16, T11).
The container branch is the one client that cannot reach a loopback endpoint: the default
`STORAGE_ENDPOINT=http://127.0.0.1:8333` would be the helper container's own namespace, so for that
branch alone a loopback endpoint is rewritten to `host.docker.internal` (macOS Docker/colima resolve
it to the host). The host clients and the readiness probe keep the endpoint as written.

```bash
tools/dev/storage-init.sh                                         # run by up.sh (skip with --skip-storage-init)
aws --endpoint-url http://127.0.0.1:8333 s3api list-buckets       # the three names, again after a re-run
aws --endpoint-url http://127.0.0.1:8333 s3 ls s3://nt-music-dev/ # PRE music/  PRE music-evidence/
tools/dev/down.sh --volumes                                       # discard .nts/dev/seaweedfs (dev data is disposable)
```

**Wiring.** `up.sh` exports the `.env` rows to the Api and the Worker under the canonical
double-underscore configuration names of each settings type: the flat storage rows are shell input
only, mapped to the `StorageSettings` property names — `STORAGE_ENDPOINT` → `Storage__ServiceUrl`,
`STORAGE_ACCESS_KEY` → `Storage__AccessKey`, `STORAGE_SECRET_KEY` → `Storage__SecretKey`,
`STORAGE_REGION` → `Storage__Region` and `STORAGE_BUCKET_MEDIA`/`__PUBLIC`/`__MUSIC` →
`Storage__Buckets__Media`/`__Public`/`__Music` (the spelling matters: `Storage__BUCKET_MEDIA` binds as
`Storage:BucketMedia`, which matches no property; only `ServiceUrl` has a `Storage:Endpoint` alias),
all loopback; the mail rows keep their flat `SMTP_*` names in `.env` but are exported as the canonical
`Email__Smtp__Host`/`__Port`/`__Username`/`__Password` and `Email__From__Address`. The optional compose
services override the storage host part to the service names (`http://storage:8333`; T41) and the mail
host to `mail:1025`. Nothing but the emulator's own store lives here; the real client (`AmazonS3Client`)
arrives with 09.7.2-T1.

## Local mail (Mailpit)

Development sends every e-mail through a local SMTP sink: **Mailpit**, started by `tools/dev/up.sh`
(11.1.1-T2) on `127.0.0.1:1025`, with its UI and its API at <http://127.0.0.1:8025> (09.2.6-T3).
MIT-licensed (E11); Homebrew `mailpit` 1.31.3.

```bash
mailpit -q --disable-version-check --smtp 127.0.0.1:1025 --listen 127.0.0.1:8025 \
  --database .nts/dev/mailpit/mailpit.db --smtp-auth-accept-any --smtp-auth-allow-insecure
```

`--smtp-auth-accept-any`/`--smtp-auth-allow-insecure` are the native twins of the compose service's
`MP_SMTP_AUTH_ACCEPT_ANY`/`MP_SMTP_AUTH_ALLOW_INSECURE`, so the `SMTP_USER`/`SMTP_PASSWORD` rows in
`.env` are accepted. The store is `.nts/dev/mailpit` (git-ignored; `down.sh --volumes` deletes it).
A version bump is a hand edit of the formula and of the digest in `docker-compose.yml` (T12).

```bash
nc -z 127.0.0.1 1025                            # the SMTP sink every host dials
curl -fsS http://127.0.0.1:8025/api/v1/info     # Mailpit is up; its UI is at the same base URL
```

A message the Api queues is rendered and sent by the Worker's `SendEmailJob` and appears in that UI;
`EmailEndToEndTests` asserts exactly that, and skips itself when the sink is not part of the run. The test
reads two environment variables, which the developer exports before running it (`up.sh` starts the sink; it
does not export them):

```bash
export NTS_MAILPIT_URL=http://127.0.0.1:8025   # the Mailpit API and UI base URL; absent → the test skips
export NTS_SMTP_PORT=1025                     # only when the sink does not listen on the default port
```

Both hosts read the pipeline's configuration from `Email:*`, with the loopback defaults committed in
`appsettings.json`: `Email:Smtp:Host` `127.0.0.1`, `Email:Smtp:Port` `1025`, `Email:Smtp:Security` `None`
(plaintext is accepted only towards a loopback endpoint, in any environment) and `Email:From:Address`
`no-reply@nighttales.local`. `up.sh` therefore exports the `.env` `SMTP_*` rows as the canonical
`Email__Smtp__Host`/`__Port`/`__Username`/`__Password` and `Email__From__Address`; the flat
`SMTP__HOST`/`SMTP__PORT`/`SMTP__USER`/`SMTP__PASSWORD` spelling remains readable as an alias of
`Email:Smtp:*`, but an explicit `Email:Smtp:*`/`Email:From:*` value (such as the committed
`appsettings.json`) wins over it, so the alias cannot override those defaults. A deployment overrides the
canonical names `Email__Smtp__Host`, `Email__Smtp__Security` (`StartTls`), `Email__Smtp__Username`,
`Email__Smtp__Password` and its own `Email__AddressHashPepper` — the host refuses to start when the
transport is plaintext towards a remote server or the address pepper is blank (09 README BD9/BD16).

## Migrations

`InitialCore` (09.2.2-T2) is the schema every later migration builds on; it is never edited again. A schema
change is an expand-only migration (`NFR-09-6`: expand → migrate → contract) named
`<yyyyMMddHHmm>_<Owner>_<What>`, for example `202610051200_02_SourcesAndFetchTasks` (`InitialCore` itself
keeps EF's timestamp prefix).

```bash
# The tools read the connection string from the environment, never from argv (11 CR-14): a connection
# string in argv is visible to every process on the machine. The design-time factory
# (src/NightTales.Infrastructure/Persistence/AppDbContextDesignFactory.cs) builds the model itself, so the
# Api host is not started and `--startup-project` is not needed (it would need EF's Design package there).
# With the variable unset the factory does not fail: it falls back to the non-secret placeholder
# `Host=invalid.localhost;Database=nts_design_time`, which is never contacted (the factory only builds the
# model). The bundled `nts-migrate` runner takes its own `--connection "<db>"`, applied after the context is
# built, so it runs without this export.
export ConnectionStrings__Postgres="Host=127.0.0.1;Port=5432;Database=${POSTGRES_DB:-nighttales};Username=${POSTGRES_USER:-nighttales};Password=<POSTGRES_PASSWORD from .env>"

dotnet ef migrations add 202610051200_02_SourcesAndFetchTasks \
  --project src/NightTales.Infrastructure --context AppDbContext --output-dir Persistence/Migrations
dotnet ef migrations has-pending-model-changes --project src/NightTales.Infrastructure --context AppDbContext
dotnet ef migrations script --idempotent --project src/NightTales.Infrastructure --context AppDbContext   # read it before the PR
dotnet ef database update --project src/NightTales.Infrastructure --context AppDbContext                 # the local dev database
```

- **Never edit a generated file by hand** except inside `Up`/`Down` of the migration class. The snapshot and the
  Designer are rendered by the generator; `.editorconfig` exempts `Persistence/Migrations/[0-9]*.cs` and
  `AppDbContextModelSnapshot.cs` from the house style rules (their block-scoped namespace, BOM and constant
  array literals are the generator's), so a fresh `migrations add` compiles and formats as it comes out.
- **Two branches that add a migration in parallel** both touch `AppDbContextModelSnapshot.cs` and the Designer of
  the last migration, so the merge conflicts. Do not resolve that conflict by hand: the branch that merges
  **second** removes its own migration (`dotnet ef migrations remove`), merges the other one, and regenerates
  on top. The published migration id of the first branch never changes.
- **A migration that adds a table extends** `tests/NightTales.Api.IntegrationTests/Migrations/SeedPrevious.cs`
  with a row of that table, so the *next* migration is exercised over data, not only over an empty schema.
- **A destructive step** (drop a table/column, narrow a column) needs `[ContractMigration("why the previous
  release is over")]` on the migration class; without it `Migrations_ContainNoDestructiveOperations` fails the
  build, in the unit job and in the `migrations` job. The review checklist is in
  `.github/pull_request_template.md` § Migration.
- The bundle is a build artifact: `dotnet ef migrations bundle --self-contained -r linux-x64 -o
  artifacts/nts-migrate --project src/NightTales.Infrastructure` (`artifacts/` is git-ignored; 11.5.1 builds it
  in the pipeline and runs it as a one-shot job before rollout). Locally it takes the connection string with
  `--connection "<local dev db>"` — applied after the design-time context is built, so the run does not need
  `ConnectionStrings__Postgres` set; in CI and in the cloud the value comes from that variable
  (masked with `::add-mask::`), never from argv.
