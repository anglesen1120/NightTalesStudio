## Goal

`POST /api/v1/episodes/{id}/story/generate` accepts a request with an `Idempotency-Key`, and in **one transaction** it takes the episode row lock, checks the rolling-24 h limit, checks the platform spend cap, reserves through the metering-only ledger, inserts the `queued` `generation_runs` row and moves the episode to `story_generating` with the `StoryGenerationRequested` outbox row — returning `202` + `Location`. Replaying the same key returns the original body and creates nothing.

## Design

### Command and endpoint

```csharp
// src/NightTales.Application/Features/Stories/Commands/GenerateStory/GenerateStoryCommand.cs
public sealed record GenerateStoryCommand(Guid EpisodeId, GenerationTrigger Trigger = GenerationTrigger.User, string? IdempotencyKey = null)
    : ICommand<ErrorOr<GenerateStoryAccepted>>, IIdempotentCommand, IIdempotencyKeySource;
public sealed record GenerateStoryAccepted(Guid GenerationRunId, string Status, string Stage);
```

No request body; `lengthTier` and `brief` are episode columns (09.5.1). The 09 §5.1 example's `string? ETag` parameter is **dropped** (D9 does not list generate; §10 item 2). Endpoint in `src/NightTales.Api/Endpoints/StoryEndpoints.cs`, `MapPost("/api/v1/episodes/{id:guid}/story/generate")`, `[Audited("episode.story_generation_requested", Category.Episodes, Visibility.User)]` with `data = { episodeId, generationRunId, trigger, tier, worstCaseUsd }` (ids/numbers only). `Idempotency-Key` header is **required** (max 128 chars); missing → 400 `idempotency_key_required` (TL T18).

Handler order (inside `Logging → Authorization → Validation → UnitOfWork → Idempotency → Audit`, 09 README D5/D6 (09 CR-12): UnitOfWork opens the transaction first, and Idempotency claims its key in that transaction, so the stored response commits or rolls back together with the command):

| Step | Action | Failure |
|---|---|---|
| 1 | `LockEpisodeForUpdateAsync(episode.Id)` (T1) then load; missing / not the caller's → 404 (never 403) | `episode_not_found` 404 |
| 2 | `Trigger != User` requires `SystemContext`; a user passing `autopilot` is rejected | `forbidden` 403 |
| 3 | `episode.Status ∈ {draft, story_review}`; `story_generating` → its own code (02 CR-30) | 409 `story_generation_in_progress` for `story_generating`; 409 `episode_invalid_state` for every other status |
| 4 | `IFactSheetGuard.EnsureApprovedAsync(episode.Id, series.Topic, ct)`; store `ApprovedFactSheet.FactSheetId` as `input_fact_sheet_id` (null for non-true-crime without a sheet) | 409 `fact_sheet_required` |
| 5 | rolling-24 h limit (**02.4.2-T1**) | 429 `story_generation_limit` + `Retry-After` |
| 6 | active-run check (explicit query for the fastest error; the index is the guarantee) | 409 `story_generation_in_progress` |
| 7 | `usageBound = await storyCostEstimator.WorstCaseAsync(episode.LengthTier, series.Language, ct)` | — |
| 8 | `IBudgetGuard.CheckAsync(usageBound.Cost, ct)` | 429 `spend_cap_reached` |
| 9 | `reservationId = await creditLedger.ReserveAsync(userId, CreditOperation.StoryGenerate, episode.Id, usageBound, ct)` | P never fails; a future ledger's own `insufficient_credits` |
| 10 | insert `generation_runs`: `kind=story`, `status=queued`, `stage=queued`, `previous_episode_status=episode.Status`, `counts_toward_limit=true`, `worst_case_usd=usageBound.Cost.Usd`, `input_fact_sheet_id`, `idempotency_key`, `queued_at=clock.UtcNow` | — |
| 11 | `episode.RequestStoryGeneration(run.Id, Trigger, now)` (T1/T2 of T1's table) → outbox row in the same tx | — |
| 12 | return `GenerateStoryAccepted(run.Id, "queued", "queued")` → endpoint maps to `202` + `Location: /api/v1/episodes/{id}` | — |

Steps 5–10 share the transaction and the episode row lock so the count, the limit check and the insert cannot interleave; no serialisable isolation is needed. `[Audited]` per D13.

Autopilot path: `AutopilotPlanJob` (02.8.3-T1) sends the same command with `Trigger = Autopilot` and `IdempotencyKey = $"autopilot:{seriesId}:{slotAt:O}:story"` under `SystemContext(ownerId)`; no FR-02-7 counting (D2).

### `ICreditLedger` + `MeteringOnlyCreditLedger`

```csharp
// src/NightTales.Application/Abstractions/Money/ICreditLedger.cs
public interface ICreditLedger
{
    ValueTask<ErrorOr<ReservationId>> ReserveAsync(Guid userId, CreditOperation op, Guid referenceId, UsageBound bound, CancellationToken ct);
    ValueTask<ErrorOr<Success>> SettleAsync(ReservationId reservationId, CancellationToken ct);   // cost read from usage_records by reservation
    ValueTask<ErrorOr<Success>> RefundAsync(ReservationId reservationId, string reason, CancellationToken ct);
}
```

`MeteringOnlyCreditLedger` (Infrastructure/Money, P): `ReserveAsync` → fresh `ReservationId` (UUIDv7), never rejects, writes nothing; `SettleAsync`/`RefundAsync` → `Result.Success`, no `credit_ledger`/`credit_lots` rows, `RefundAsync` idempotent by `reservationId`. 12.1.2 replaces the DI registration at M2 (CR-2). `CreditOperation` values: `story_generate`, `fact_sheet`, `bible_proposal`, `idea`, `source_find`.

### `IBudgetGuard` + `UsageBudgetGuard`

```csharp
// src/NightTales.Application/Abstractions/Pricing/IBudgetGuard.cs
public interface IBudgetGuard { ValueTask<ErrorOr<Success>> CheckAsync(CostBound worstCaseUsd, CancellationToken ct); }
// src/NightTales.Infrastructure/Pricing/UsageBudgetGuard.cs
internal sealed class UsageBudgetGuard(IReadDb readDb, IOpenBoundsReader openBounds, BudgetOptions options, IClock clock) : IBudgetGuard;
```

Deny when `spent(today UTC) + openBounds + worstCaseUsd > Budget:MaxPlatformCostUsdPerDay`; same rule per calendar month against `…PerMonth` → 429 `spend_cap_reached`. `spent` and the open bounds are read through `IReadDb` (own transaction, D14):

```sql
SELECT COALESCE(SUM(cost_usd), 0) FROM usage_records WHERE created_at >= @dayStartUtc;    -- day
SELECT COALESCE(SUM(cost_usd), 0) FROM usage_records WHERE created_at >= @monthStartUtc;  -- month
SELECT COALESCE(SUM(worst_case_usd), 0) FROM generation_runs WHERE status IN ('queued','running'); -- IOpenBoundsReader
```

**Concurrency (TL review 2026-09-24, T61):** the episode row lock does not serialise two *different* episodes, so two commands could both pass the check and together exceed the cap. When called from a command, `CheckAsync` therefore runs inside the command transaction after `SELECT pg_advisory_xact_lock(hashtext('budget_guard'))`. The lock is held until the `generation_runs` insert commits, so the next check sees the new open bound. Its cost is one short, platform-wide serialisation per paid command (≤ a few per minute in P). Dispatch-time checks inside jobs take the same lock. Test: `BudgetGuard_TwoEpisodesConcurrently_SecondSeesFirstOpenBound`.

`IOpenBoundsReader` is the single extension point so 05/12 can add render reservations later without touching the guard (§10 item 9). `Budget:Enabled` (default true) is a test-only kill-switch.

| Config key | Default |
|---|---|
| `Budget:Enabled` | `true` |
| `Budget:MaxPlatformCostUsdPerDay` | `3` |
| `Budget:MaxPlatformCostUsdPerMonth` | `40` |

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two concurrent calls for one episode | the `FOR UPDATE` row lock serialises them; the loser fails step 6 `story_generation_in_progress`; the partial unique index is the second backstop |
| Idempotency replay after the run finished | the stored response is returned; no new run, no second reservation |
| `IFactSheetGuard` missing vs unapproved sheet | both → 409 `fact_sheet_required` (the handler only needs the verdict) |
| Budget cap reached | 429 `spend_cap_reached`; nothing is inserted, so the cap cannot be breached by a retry storm |
| `provider_funds_exhausted` at command time | **not** checked here — 12.8.3 requires 202 + a `queued` run so the UI can say "reserved, not charged yet" |
| Transaction rollback (any step fails) | the row lock, the run row, the reservation and the outbox row all roll back together |
| Rollback of the feature | no migration; revert DI + endpoint |
