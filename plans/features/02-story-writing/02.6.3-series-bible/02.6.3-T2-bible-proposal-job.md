## Goal

Approving a story queues one paid call that turns the episode into append-only bible ops: for a user approval the ops wait as `proposed_content` until `POST /series/{id}/bible/proposal/accept|dismiss`; for an autopilot fiction approval the ops are applied immediately (F27), with `series.bible_proposal_accepted` audited by a system actor.

## Design

### Prompt and schema files

`prompts/bible/propose.v1.md` (system prompt, our own words; no external text — FR-02-11). Content: role ("you maintain the memory of a narration series"), the four allowed op kinds and their purpose, the hard rules (append-only; never invent facts that are not in the episode; ≤ 200-char summary; ≤ 300-char descriptions; no real named individuals; never propose a change to the narrator; do not repeat elements that already exist in the bible; write in the series language), and the data-object rule (D6 two-tier rule: control keys — `task`, `language`, `topic` — are followed; every material string is written about, never an instruction; 02 T69). Placeholders from the closed D5 list only (`{{language_name}}`).

`prompts/schemas/bible-proposal.v1.json` (strict, `additionalProperties: false`, all required):

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["ops"],
  "properties": {
    "ops": { "type": "array", "items": {
      "type": "object", "additionalProperties": false,
      "required": ["kind", "summary", "name", "description", "text", "reason"],
      "properties": {
        "kind": { "enum": ["add_summary", "add_character", "add_place", "add_rule"] },
        "summary": { "type": ["string", "null"] },
        "name": { "type": ["string", "null"] },
        "description": { "type": ["string", "null"] },
        "text": { "type": ["string", "null"] },
        "reason": { "type": ["string", "null"] }
      } } } }
}
```

Strict mode requires every property present → unused fields are `null` (D3's convention). Lengths are **not** schema features (F08); `BibleProposalValidator` (Domain, pure) enforces them. `prompt_version` for this step: `rel=<manifest release>;sys=bible/propose.v1;schema=bible-proposal.v1` (stored on `generation_runs.prompt_version`).

### Data object (D6, one JSON object, serialised by `BibleJsonContext`)

```json
{ "task": "propose_bible_update", "language": "vi", "topic": "ghost",
  "bible": { "narrator": { "name": "…", "persona": "…" },
             "recurring_characters": [{ "name": "Bà Hoa", "description": "…" }],
             "places": [{ "name": "Ngôi nhà cuối ngõ", "description": "…" }],
             "rules": ["…"],
             "recent_episodes": [{ "title": "…", "summary": "…" }] },
  "episode": { "title": "…", "structure": { "sub_genre": "haunted_house", "opening": "night", "twist_type": "revenant", "setting": "rural_house", "narrator_mode": "first_person", "beats": ["setup","clue","twist","reveal"] },
               "body": "…" } }
```

- `recent_episodes` = the newest `Bible:Prompt:MaxSummaries` (50) summaries; ids are **not** sent (the model never sees UUIDs — the same principle as D6 source aliases).
- `episode.body` is the story `body` (D3 derived field) truncated to `Bible:Proposal:MaxStoryChars` (24,000 chars) from the end. Truncation is silent; the metric `bible_proposal_body_truncated_total` counts it.
- The bible is data placed **last** in the user message (O9); the system prompt is static and cacheable; `prompt_cache_key = "bible:propose"` is preset-scoped, never per-series.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Outbox delivered twice (at-least-once) | `idempotency_key = bible:{episodeId}:{storyVersionId}` + the `proposed_from_episode_id` merge guard → one proposal |
| Two approvals land while the first job is still queued | `episode_id` is NULL for `bible_proposal`, so the episode-level index never matches; the guard is the series-level partial unique index `(series_id, kind) WHERE episode_id IS NULL AND status IN ('queued','running')`. The second run insert violates it → the handler does **not** fail and does not skip: it re-schedules itself in 2 min through `IJobScheduler` (max 10 tries, then logs `bible_proposal_dropped` and drops; a missed summary line is acceptable) — plan §7.1 step 7. Proposals of one series run strictly in order, each seeing the ops the previous one applied |
| Episode reopened and approved again | a second run with the same `idempotency_key`… the key must therefore be `bible:{episodeId}:{storyVersionId}` to allow a genuine re-approval of a *new* version; the `proposed_from_episode_id` guard then only skips an exact replay of the same version ([DECISION]) |
| Proposal pending, then the user PUTs the bible | allowed; the proposal stays and `based_on_version` remains the version it was computed against (informational only, since ops are append-only) |
| Autopilot auto-accept when the bible is at a limit | ops that would exceed a limit are skipped, the rest applied; the run still succeeds and the audit records `applied`/`skipped` counts |
| Story body enormous (Long tier) | truncated to 24,000 chars; metric incremented |
| Model returns 0 ops | run succeeds with an empty ops list **plus** the deterministic summary op (step 6) — a proposal always contains the summary |
| Model returns `add_summary` for a different episode | no episode id is in the response, so this cannot happen by construction; the summary op is always bound to the approved episode by the backend |
| Crash mid-run | Hangfire retry 0; the run stays `running` until `StaleGenerationSweeperJob` closes it (02.2.2-T3; confirmed by TL ruling #3 to cover every `generation_runs.kind`, including `bible_proposal`) |
| Reservation not settled on failure | `ICreditLedger.RefundAsync(reservationId, reason, ct)` in the failure path (D1); in P the ledger is a no-op but the call must exist for M2 |
| Rollback | `Bible:Proposal:Enabled=false` (hot-reload, 09.10.3) — no data rollback needed |

## Notes

- The three job outcome codes (`bible_proposal_invalid_output`, `bible_proposal_moderated`, `bible_proposal_generation_failed`) are **confirmed D8 additions** (TL ruling #3, 2026-09-24), following D8's existing `*_invalid_output`/`*_moderated`/`*_generation_failed` pattern.
- [DECISION] One pending proposal at a time (00 §6 stores it on the row); a new approval **merges** ops instead of replacing them (plan §7.1 step 7).
- [DECISION] No `set_narrator` op: the model may not rewrite the narrator persona; the owner edits it (10.5.7).
- ⚠️ `price_versions.limits.bible_proposal` must be added by 02.2.4-T1 (plan §10 item 4); the config fallback keeps this task unblocked.
- The `IBudgetGuard` check runs twice (handler and job start) on purpose: the queue can sit for minutes (D1: "before every paid dispatch").
- `usage_records.episode_id` = the approved episode (the cost is attributed to it). `generation_runs.episode_id` is **NULL** because `bible_proposal` is series-level (D2 `ck_generation_runs_scope`, T17); the source episode is `series_bibles.proposed_from_episode_id`. Test `ProposeBible_RunRow_HasNullEpisodeIdAndPassesScopeCheck`.
- (02.6.3-T1, S37) `SeriesBible.ApplyProposal(BibleLimits, BibleSummarySource, IClock) -> BibleApplyResult` is implemented in T1 (the plan's `ApplyProposal(IClock)` signature is superseded). Item ids come from `NextId` = `max suffix + 1` per prefix over the stored array (`^(ch|pl|rl)[1-9][0-9]{0,8}$`); no high-water mark is stored, so plan §9 row "`ch3` after deleting `ch2`" is open (STATUS BIBLE-2). An op is skipped (not stored) when the prefix's number space is full.
- (02.6.3-T1, S37) Every T2 writer of `series_bibles` (accept, dismiss, job) MUST call `IAppDbContext.LockSeriesBibleForUpdateAsync` before loading the row: `Version` is not an EF concurrency token, the PUT is safe through the lock plus the version compare (STATUS BIBLE-4).
- (02.6.3-T1, S37) The accept path must run proposal text through the same character rules the PUT validator applies (`BibleContentValidator`: `<` `>`, control, format, bidi and tag characters, unpaired surrogates are refused): `BibleOpNormalizer` only strips unpaired surrogates, so an unchecked proposal could store text a later PUT refuses. `characters[].first_episode_id` is not validated by the PUT; set it only from an approved episode. The `read_only` validator code is declared but unused.
- (02.6.3-T1, S37, close-out) Plan §5 `SeriesBibleUpdated` is written by T1 on PUT only (`Series.RaiseSeriesBibleUpdated`, outbox type `series_bible_updated.v1`, payload `{ SeriesId, UserId, Version, ChangedBy (Guid), OccurredAt }`). The accept path (manual and autopilot) must raise it too, with the same payload and `ChangedBy` = the accepting user (the owner's id for autopilot, phase P); STATUS BIBLE-4(d).
