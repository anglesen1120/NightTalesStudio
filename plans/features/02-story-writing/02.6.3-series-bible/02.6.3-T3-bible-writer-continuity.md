| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

The writer receives a bounded `BibleSnapshot` plus an `avoid_plots` list inside the D6 data object, and the self-review receives the same bible so it can raise `bible_contradiction` issues — with a documented truncation order so the data object never exceeds the prompt budget.

## Inputs

- Contract: README D4 (token rule; token counts), D5 (prompt order for caching, O9: static first, data last), D6 (`bible` and `avoid_plots` keys; untrusted data as one JSON object), D21 (`StoryWriteRequest(..., BibleSnapshot? bible, IReadOnlyList<string> avoidPlots)`; `RunContext`), D22 (`audit.v1`; `segment` addressing), D19 (never log content), F21 (injection), F27 (last 50 summaries, ≤ 200 chars).
- Story 02.6.3: "the writer receives the bible and must not repeat a plot listed in `episode_summaries`; the self-review checks continuity against it"; 02.6.1: "continuity with the series bible" is a review check.
- CheckpointSimilarityPlan (TL ruling): `TextNormalizer.Normalize(string, Language)` / `Shingler` are **not** needed here (no scoring) — the bible snapshot is plain text shaping.
- FactSheetReviewPlan: the review data object gets the same `bible` key; `avoid_plots` is **not** sent to the review; the review rule name is `bible_contradiction` with severity blocking only for a narrator/narrator-mode contradiction.
- StoryWriterPlan: data object ≤ `Story:Prompt:MaxDataObjectBytes` (65,536 UTF-8 bytes); over budget the assembler drops `avoid_plots` oldest-first then fails `PromptTooLarge`; `EpisodeSnapshot(..., StructurePlan? Structure)`; `BibleSnapshot` must stay a plain record with no behaviour-only members.
- Plan `../plan.md` §3.1, §4 (U5 note), §8 (injection), §10 items 6/7.

## Design

### Domain types (`src/NightTales.Domain/Series/Bible/`)

```csharp
public sealed record BibleSnapshot(
    int Version,
    BibleNarratorSnapshot? Narrator,
    IReadOnlyList<BibleCharacterSnapshot> RecurringCharacters,
    IReadOnlyList<BiblePlaceSnapshot> Places,
    IReadOnlyList<string> Rules,
    IReadOnlyList<BibleEpisodeSummarySnapshot> EpisodeSummaries,
    bool Truncated);                       // true when the budget step dropped anything

public sealed record BibleNarratorSnapshot(string? Name, string Persona, string? VoiceNotes);
public sealed record BibleCharacterSnapshot(string Name, string Description, Guid? FirstEpisodeId);
public sealed record BiblePlaceSnapshot(string Name, string Description);
public sealed record BibleEpisodeSummarySnapshot(string Title, string? Summary, StoryStructureTags? Structure, DateOnly? ApprovedOn);
```

No ids in the snapshot for characters/places/rules (the model has no use for them and D6 keeps identifiers out of the data object; `FirstEpisodeId` is kept only for the *review* variant, which is not serialised to the model — see "review input" below). Keep the writer variant id-free.

### `BibleSnapshotBuilder` (Domain, pure) — the budget

```csharp
public static BibleSnapshot Build(SeriesBibleContent content, BibleSnapshotLimits limits);
public sealed record BibleSnapshotLimits(int MaxSummaries, int MaxChars, int MaxDescriptionChars,
                                         int MaxVoiceNotesChars, int KeepFullSummaryCount, int MaxArrayEntries);
```

Steps, applied **in order**, each step only if the serialised size is still over `MaxChars` (default **24,000** chars, counted as UTF-8 bytes of the serialised `bible` object, values **and** JSON structure — keys/quotes/commas/brackets — after `System.Text.Json` serialisation with `BibleJsonContext`):

| # | Step | Drops |
|---|---|---|
| S0 | newest `MaxSummaries` (50) by `approved_at` desc | older summaries entirely |
| S1 | truncate `narrator.voice_notes` to `MaxVoiceNotesChars` (500) | tail of the voice notes |
| S2 | truncate every character/place `description` to `MaxDescriptionChars` (150) | description tails |
| S3 | keep the full `summary` text only for the newest `KeepFullSummaryCount` (25); older ones become `Summary = null` (title only) | summary texts |
| S4 | keep the first `MaxArrayEntries` (15) rules | later rules |
| S5 | keep the first `MaxArrayEntries` (15) places | later places |
| S6 | keep the first `MaxArrayEntries` (15) characters | later characters |
| S7 | drop all rules | rules |
| — | still over → throw `BibleSnapshotTooLargeException` | the job fails `story_generation_failed` with `error_detail = bible_too_large`, not counted (D2) |

**Convergence proof [DECISION].** The 02.6.3-T1 limits now cap every field that feeds the snapshot, including character/place **`name` ≤ `Bible:Limits:NameChars` (60 chars, new T1 limit)** — without that cap this budget cannot be proven to converge. With every T1 limit at its maximum (30 characters, 30 places, 30 rules, 50 summaries, narrator persona 1,000) and every truncation step S1–S7 applied, the worst-case **value** bytes are: narrator `80 + 1,000 + 500 = 1,580`; characters `15 × (60 + 150) = 3,150`; places `15 × (60 + 150) = 3,150`; rules `0` (S7); summaries `25 × (100 + 200) + 25 × 100 = 10,000` (S3) — **total 17,880**, plus ≈ 2,000–2,500 bytes of JSON structure for ~115 array items (field names, quotes, commas) ≈ **20,000–20,400 bytes**, safely under the 24,000 budget with ≈ 3,600–4,000 bytes of margin. `MaxSummaries = 50` (F27's explicit "last 50 summaries") is therefore always reachable by S0 alone for a realistic bible, and the pathological maximal-limits case still converges without ever reaching the exception — `BibleSnapshotTooLargeException` is unreachable in practice and exists only as a defensive backstop against a future limits change that breaks this arithmetic (re-run this proof if any 02.6.3-T1 limit changes).

The narrator is **never** dropped (a series without its narrator is a different series); `Truncated = true` when any step after S0 dropped something; the job logs it (ids/counts only) and increments `bible_snapshot_truncated_total`.

### `AvoidPlotsBuilder` (Domain, pure)

```csharp
public static IReadOnlyList<string> Build(IReadOnlyList<BibleEpisodeSummarySnapshot> summaries, int max = 25, int maxCharsPerEntry = 120);
```

Called as `AvoidPlotsBuilder.Build(snapshot.EpisodeSummaries, …)` — **on the already-truncated `BibleSnapshot`**, never on the raw `SeriesBibleContent` (so `avoid_plots` and `bible.recent_episodes` always agree on which episodes survived truncation and the two builders cannot diverge). Newest first, `Summary` only (skip the title-only entries left by S3), first sentence (split on `.`/`!`/`?`/`…`), trimmed to ≤ 120 chars on a word boundary, deduped by `BibleOpNormalizer.Normalize`, at most 25 entries. The result is the `avoid_plots` list of D21/D6. **Why not the full summaries:** `avoid_plots` is a prohibition list — short and imperative beats a paragraph; the full summaries are already in `bible.recent_episodes` for continuity. The small duplication (≤ 25 × 120 = 3,000 bytes) is deliberate, additive to the 24,000-byte bible budget, and already covered by the convergence proof's margin (≈ 3,600–4,000 bytes headroom ≥ 3,000).

### `IBibleSnapshotProvider` (Application `Features/SeriesBible/Abstractions`)

```csharp
public interface IBibleSnapshotProvider
{
    ValueTask<BibleForWriter> GetForWriterAsync(Guid seriesId, CancellationToken ct);
}
public sealed record BibleForWriter(BibleSnapshot? Bible, IReadOnlyList<string> AvoidPlots, int Version);
```

- `Bible` is `null` when the bible is empty (no narrator persona, no arrays) so the assembler omits the key entirely; `Version` is `0` then.
- Implementation `Infrastructure/SeriesBible/BibleSnapshotProvider.cs`: one no-tracking read of `series_bibles` by `series_id` (tenant filter on) → `BibleSnapshotBuilder.Build` + `AvoidPlotsBuilder.Build`. No caching (a bible read is one row; the job reads it once per generation).
- Called by `StoryWriteRequestAssembler` (02.2.2-T3, cross-feature: they call it) and by the review request assembly.

### Review input (02.6.1 / 02.6.2)

- `StoryReviewRequest` (owned by FactSheetReviewPlan) gains `BibleSnapshot? Bible` (serialised under the `bible` key). `avoid_plots` is not sent to the review (confirmed by FactSheetReviewPlan).
- Review rule: **`bible_contradiction`** — a closed-list value of `review.v1.issues[].rule`, `kind = objective`, `severity = blocking` **only** for a narrator/narrator-mode contradiction (the server downgrades any other `bible_contradiction` to `advisory` unless its `evidence` cites the narrator). `segment` uses the D22 addressing (`hook`, `p:3`, `ending`, `meta`).
- The review variant of the snapshot keeps `first_episode_id`? No: the review compares story text with bible facts; the writer variant is sufficient. Use one type; do not add a second.
- `audit.v1` gets no new field: a `bible_contradiction` issue lands in `model_review.issues[]` like any other (D22). The `local.issues[]` list is unaffected (no new local rule; the bible has no objective local check — length/hook/keywords are 02.3.4's).

### Cache friendliness (O9)

The bible is **data**: it is appended to the user message **after** the system prompt, preset and shared rules, and it is the last dynamic block. Consequences to preserve:
- `prompt_cache_key` stays `<step>:<preset>` (e.g. `write:ghost.vi`) — **never** include `seriesId` or a bible version, or every series loses cache sharing.
- No bible text is ever substituted into a template placeholder (D5's closed placeholder list does not include it).
- `prompt_version` does **not** change when the bible changes (the bible is not a prompt file, NFR-02-2). Only `prompts/manifest.json` changes it.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Bible larger than the budget even after S7 | job fails `story_generation_failed` + `error_detail = bible_too_large`, `counts_toward_limit = false` (D2), episode returns to the previous status (00 §7 / P3) |
| `avoid_plots` alone exceeds the assembler's data-object budget | the assembler drops `avoid_plots` oldest-first (StoryWriterPlan's rule) and then fails `PromptTooLarge`; our 25×120 cap makes this unreachable in practice (asserted by the boundary test) |
| Bible edited between the job start and the writer call | the snapshot is built once per generation; a mid-run PUT affects the *next* generation (the current one is consistent) |
| Series deleted mid-run | the read returns nothing → `Bible == null` (no failure); the retention sweep deletes the row (D19) |
| Summary text contains a newline or quotes | serialised by `System.Text.Json` inside the one data object (D6) — no break-out |
| `first_episode_id` points at a deleted episode | not sent to the model; harmless in the snapshot |
| Episode summaries list contains the current episode (regenerate) | `avoid_plots` includes the previous version's plot; that is intended for a regenerate (a new angle), and the review flags an exact repeat |
| Rollback | none needed: without the provider the request assembles without `bible` (nullable, D21) |

## Notes

- [DECISION] `avoid_plots` = newest 25 summaries reduced to their first sentence (≤ 120 chars); `bible.recent_episodes` = newest 50 summaries. Rationale in the Design section.
- [DECISION] The narrator is never truncated away; an over-budget bible fails loudly.
- ⚠️ The budget constants (24,000 chars, 25/15/500/150) are first guesses **grounded in a worst-case proof** (Design section) against the 02.6.3-T1 limits; measure with real bibles in M1 and adjust the config (no code change). Re-run the proof if any T1 limit changes.
- `bible_contradiction` is owned by 02.6.1's rule list (FactSheetReviewPlan confirmed it is in the closed list and that only a narrator contradiction may be `blocking`). Do not add a second rule name.
- Do not log bible content or summaries (D19). The truncation log line carries counts only.
- The review must not receive `avoid_plots` (confirmed) — sending it would duplicate the summaries and cost tokens for no benefit.
- (02.6.3-T1, S37) A fresh bible (backfilled or created with the series) has `narrator.persona = ""` and empty arrays (STATUS BIBLE-3); the writer snapshot must treat an empty persona as "no narrator voice", not as an error. Stored text is validated against `<` `>`/control/format/bidi characters on the PUT path only (T1), item ids against `^(ch|pl|rl)[1-9][0-9]{0,8}$`.
