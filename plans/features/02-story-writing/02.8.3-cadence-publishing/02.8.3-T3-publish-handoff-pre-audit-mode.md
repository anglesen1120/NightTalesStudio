## Goal

A run whose video gate passed creates the publication through the existing 06.2.1 command with the story's metadata, the owner's privacy setting, `publish_at = slot_at` and `contains_synthetic_media = true`; the veto window is honoured (never shorter than `MinVetoWindowHours`), and while `youtube_audit_status = pending` the publication is created **private with no `publishAt`**, the go-live check is skipped, and the run ends `published_private_locked`.

## Design

### The publication request (the hand-off)

`CreatePublicationStep` (Application `Features/Autopilot/Orchestration/AutopilotStepHandlers/CreatePublicationStep.cs`) sends 06.2.1's command under `SystemContext(run.UserId)`:

```csharp
var story = episode.CurrentStory;                       // story.v1 content
var publication = await sender.Send(new CreatePublicationCommand(
    EpisodeId: run.EpisodeId,
    ChannelConnectionId: authorization.ChannelConnectionId,   // the channel the owner authorized, not series.default_channel_id
    Title: story.Title,                                       // ≤ 100 chars, no < >
    Description: story.Description,                           // ≤ 1,000 chars (D3) < 06.2.1's 5,000 ⚠️
    Tags: story.Tags,                                         // ≤ 15 × ≤ 30 chars, ≤ 400 total (F36)
    Privacy: settings.Privacy,                                // public | unlisted | private
    PublishAt: run.SlotAt,                                     // always the slot; 06.2.4-T1 omits publishAt from the upload request in pre-audit (06 YR2 / CR-4)
    ContainsSyntheticMedia: true,                             // always (06 FR-06-3, Y4)
    AutopilotAuthorizationId: authorization.Id,
    IdempotencyKey: $"autopilot:{seriesId}:{slotAt:O}:publication"), ct);
```

- `EpisodeId` comes from the run, never from a request body (09.2.3).
- The command validates the metadata against the 06.2.1 limits; a validation failure ends the run `failed` with `pause_reason = publication_create_failed` and notifies the owner. The D3 validator already enforces the same limits (F36), so a mismatch means a 06-side change — the test `CreatePublication_StoryMetadataWithin06Limits` guards it.
- The publication is created in `awaiting_consent` (00 §7). **No `consent_at` is written here** — 06.2.2-T3 writes it after the veto window from `series_autopilot_authorizations` (this run's `authorization_id`). The hand-off therefore never touches consent.
- On success the step reads `publication_id` from `CreatePublicationCommand`'s synchronous response (no outbox round trip needed for this) and advances the run to `publication_created`; from there `PublicationUpdated` (00 §8, real contract event) drives the rest.
- `ready → scheduled` on the **episode** is a consequence of the publication reaching `scheduled` (00 §7), not something this step sets.

### Veto-window timing

- Guard (evaluated on every tick once the video is approved): let `cutoff = upload_at − MinVetoWindowHours`.
  - `now ≥ cutoff` → the slot is **missed**, checked first: the run ends `failed` with `pause_reason = slot_missed` and the owner is notified (T4 trigger 13 counts two in a row). Nothing is created. **The veto window is never shortened below `MinVetoWindowHours` (2 h)**. It is the mechanism that makes autonomous publishing acceptable.
  - `publication_create_at ≤ now < cutoff` → create the publication now. This is the normal case, or a late video with a shortened but ≥ 2 h veto window.
  - `now < publication_create_at` → wait. The run stays in `video_gate` (gate passed) and the next 15-min tick re-evaluates. A publication is never created before `publication_create_at`, so the veto window is exactly the configured one in the buffer case.
- Test `PublishStep_AtOrAfterCutoff_EndsSlotMissed_CreatesNothing`, `PublishStep_BetweenCreateAtAndCutoff_Creates`, `PublishStep_BeforeCreateAt_Waits` pin the three branches (boundary `now == cutoff` → missed).
- 06.2.2-T2 sends the veto notice (in-app + e-mail with the preview and the edit/cancel links). The run moves `publication_created → veto_window` when `veto_notice_sent_at` is set, and `→ paused` (`veto_notice_undelivered`, T4 trigger 11) when it is still empty 30 min after creation.
- An owner `PATCH /publications/{id}` during the window is 06's path (it re-runs metadata validation and the 02.8.2 moderation gate, then counts as user consent); the run observes `PublicationUpdated` and ends `scheduled` on consent. An owner `StoryReopened`/`VideoRejected` cancels the pending publication → the run ends `cancelled_by_owner`.

### Pre-audit mode

```csharp
var auditStatus = await settingsProvider.GetAsync<string>("youtube", "audit_status", ct);  // pending | approved | rejected
var preAudit = auditStatus is "pending" or "rejected";
```

| Audit status | `pre_audit_mode` | Publication request | 06.2.5 go-live | Run outcome |
|---|---|---|---|---|
| `pending` | `keep_cadence_private` (default) | `privacy = private`, **`publishAt = null`** | skipped (no `PublicationGoLiveJob` scheduled) | `published_private_locked` when 06 reports the video processed |
| `pending` | `pause_after_n_private` | same | skipped | same, and T4 trigger 14 pauses the series once the series has `pre_audit_pause_after` locked videos |
| `approved` | either | `privacy` from settings, `publishAt = slot_at` | normal | `published` |
| `rejected` | either | treated as `pending` + a UI banner; the owner decides (re-file or keep private) | skipped | `published_private_locked` |

- **Why `publishAt = null`:** with `privacy = private` and a future `publishAt`, YouTube itself makes the video public at that time — a bug in our go-live skip would then publish unaudited content. Withholding `publishAt` makes the private lock structural rather than procedural. This is a **CR to 06.2.4-T1** (plan §10 open item 6): the upload job must omit `publishAt` when the project is in pre-audit mode (or when the publication's `publish_at` is flagged pre-audit — the cleanest carrier is a boolean on the publication; ✅ ruled (06 YR2/YR20): the publication keeps `publish_at = slot`; 06.2.1-T1 stamps `platform_payload.preAudit` at creation and 06.2.4-T1 omits `publishAt` from the upload request.
- **Why the go-live check is skipped:** 06.2.5's `PublicationGoLiveJob` asserts `privacyStatus` changed to public. In pre-audit mode there is nothing to assert; the run instead ends `published_private_locked` when `PublicationUpdated` reports `processing → processed`. The `published_private_locked` outcome is the audit trail that this video is intentionally private (and the evidence 06.5.1 shows).
- **Why the cadence is kept:** the alternative (pause everything until the audit passes, months ⚠️) would leave the channel empty; the audit needs real-use evidence (02 §4 "this also provides real-use evidence for the audit"), and private uploads are exactly that.
- The setting is read **once per run step** (not cached across runs) so flipping it mid-day takes effect on the next creation; it is read through `DbSettingsProvider` (09.10.3-T1) and is a **non-secret** `system_settings` value (09.10.1), so it can be edited in the admin UI.
- The key `youtube.audit_status` is added to 09 §5.6's catalogue by this task (plan §10 open item 5) with values `pending|approved|rejected`, default `pending` (fail safe: an unset value means private).

### Episode/run state after publishing

| 06 event | Run | Episode |
|---|---|---|
| publication `scheduled` (consent written) | `scheduled` | `scheduled` (00 §7 `ready → scheduled`) |
| publication `published` | `published`, `finished_at` set | `published` |
| publication processed while pre-audit | `published_private_locked`, `finished_at` set | stays `scheduled` in YouTube terms; our episode shows "uploaded (private)" [INFERENCE: the UI copy is 10.4.3's] |
| publication `failed` | `failed` + T4 trigger 8/9/10 | unchanged |

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| No active channel connection at creation | the run was already paused by T4 trigger 6; if the connection drops between the gate and the creation, 06.2.1 fails → run `failed` (`publication_create_failed`) + alert |
| 06.2.1 rejects the metadata | run `failed`; the owner sees the field errors in the alert and in the run log |
| Quota exhausted at upload (06.2.3-T2) | publication back to `scheduled` (`next_attempt_at` = next PT midnight, code `youtube_quota_exhausted`) → T4 trigger 8 pauses the series (06 CR-4) |
| Owner cancels the publication during the veto | run `cancelled_by_owner` (not a pause, no alert beyond the normal `PublicationUpdated`) |
| Owner edits the publication during the veto | 06 re-validates and records user consent; the run → `scheduled` |
| Pre-audit mode with `privacy = public` in settings | the publication is still created `private` (the pre-audit branch overrides the setting) and the UI shows why — [DECISION] the setting is not changed, so leaving pre-audit restores the owner's choice automatically |
| `youtube.audit_status` flips to `approved` between creation and go-live | the already-created private publication stays private for that slot (its `publishAt` is null); the next run is live. The run still ends `published_private_locked` — correct, because the video is private |
| Setting read fails (DB error) | treated as `pending` (fail safe) and logged; never treated as approved |
| Rollback | set `youtube.audit_status = pending` (everything private) or disable the series (T2); no migration involved |
