## Goal

Every condition that makes autonomous publishing unsafe stops the series instead of retrying: the trigger fires from its detection source, `series.autopilot_pause_reason` + `autopilot_paused_at` are set, no new idea/story/render job is created, and the owner gets one outbox e-mail naming the reason and listing the videos already scheduled on YouTube with Studio links. Resume re-checks every trigger and refuses while the reason still holds; a content report pauses the series and hands over to the 08.4.4 runbook.

### The pause operation (one code path)

```csharp
// src/NightTales.Application/Features/Autopilot/Commands/PauseAutopilot/{PauseAutopilotCommand,PauseAutopilotHandler}.cs
public sealed record PauseAutopilotCommand(Guid SeriesId, AutopilotPauseReason Reason, string? Note,
    Guid? RunId, Guid? PublicationId, string? TechnicalDetail);

public async Task<ErrorOr<Success>> PauseAsync(PauseAutopilotCommand cmd, CancellationToken ct)
{
    // 1. load the series (tenant filter on), already paused → no-op (idempotent)
    // 2. series.Pause(cmd.Reason, now)                      → autopilot_paused_at, autopilot_pause_reason
    // 3. non-terminal runs of the series → AutopilotRun.Pause(reason, now)   (one transaction)
    // 4. audit autopilot.paused { seriesId, pauseReason, runId, publicationId }   (D13)
    // 5. outbox AutopilotOwnerAlert { … } unless Reason == OwnerPaused         (T2's route sends no e-mail)
    // 6. log + metric autopilot_pause_total{reason}
}
```

- **Idempotent**: a second trigger for the same reason is a no-op (no second e-mail). A **different** reason while already paused updates `pause_reason` and sends one more e-mail only if the new reason is more severe than the stored one (`severity` order: spend/funds > channel/incident > upload/rejected/quota > gate/run/slot > owner). [DECISION] Severity ordering prevents an alert storm while keeping the most actionable reason visible.
- **What stops:** the planner skips paused series (`PlanAsync`), so no new run is created; existing non-terminal runs go to `paused` and are not advanced by the tick. Already-created publications are **not** touched — they continue through 06 unless the owner cancels them, which is exactly why the alert lists them.
- The manual pause (`OwnerPaused`) sends no e-mail (the owner did it) but still writes the audit row.
- Pausing does not revoke the authorization: resuming does not require a new acceptance unless a covered field changed.

### Spend caps

- Platform: unchanged from D1 — `IBudgetGuard.CheckAsync(worstCaseUsd, ct)` before every paid dispatch (02.8.1/02.2.2/02.5.3 already do this); this task only maps the 429/refusal to a pause.
- `AutopilotCostGuard` (Application `Features/Autopilot/Spend/`):

```csharp
public interface IAutopilotCostGuard
{
    ValueTask<ErrorOr<Success>> CheckRunAsync(Guid runId, decimal nextStepWorstCaseUsd, CancellationToken ct);
    ValueTask<ErrorOr<Success>> CheckDayAsync(Guid seriesId, decimal nextStepWorstCaseUsd, CancellationToken ct);
}
```

  - run cost = `SUM(usage_records.cost_usd)` joined to the run's `generation_runs` via `reservation_id` (both written from the same `RunContext`, D14/D21), compared against `Autopilot:MaxCostUsdPerRun` (1.50);
  - day cost = the same sum for the series' runs whose `slot_at`'s local date is today, against `Autopilot:MaxCostUsdPerDay` (3.00);
  - a refusal returns `Error.Validation("autopilot_run_cost_cap")` → the step ends `failed` and the pause fires (trigger 4). A refusal never retries.
- Config validation: `Autopilot:MaxCostUsdPerDay ≤ Budget:MaxPlatformCostUsdPerDay` (a larger autopilot cap is dead config and a sign of a mistake) → start-up error.

### Alert e-mail

Outbox event `AutopilotOwnerAlert { UserId, SeriesId, RunId?, PublicationId?, Reason, CopyKey, Locale, ScheduledPublications[] }`, rendered by the e-mail template `autopilot_alert.{vi|en}.html` (plan §3.6 layout) and sent by `SendEmailJob` (09.2.6, 5 retries, idempotent by message id):

- subject: `[NightTales] Autopilot paused — <series title>`;
- reason line from `CopyKey` in the owner's `ui_locale`;
- the scheduled list: `publications` of the series with `status ∈ {scheduled, uploading, processing}` and `external_post_id IS NOT NULL`, ordered by `publish_at`, cap 20, each `"<title> — <publish_at local> — https://studio.youtube.com/video/<external_post_id>/edit"` ⚠️ URL shape (plan §1), fallback `https://studio.youtube.com/channel/<external_account_id>/videos/upload` when the id is missing;
- one "fix" sentence per reason (e.g. `spend_cap_reached` → "Top up the OpenAI project limit or wait for the next day; the cap is $3/day");
- a deep link to the run log (`<public app URL>/series/<id>?tab=autopilot`) and the Resume instructions;
- **never** any story/brief/fact/source text (D19); only our own publication titles, times and links.

The in-app side is the SignalR `AutopilotRunUpdated`/`EpisodeUpdated` events plus the paused banner from T2's GET (10.4.3).

### Resume

`ResumeAutopilotCommand` (T2's route, rules owned here):

1. owner-scoped load; 404 otherwise;
2. **re-check every trigger**: `IAutopilotPauseRechecker.EvaluateAsync(seriesId, ct)` returns the reasons that still hold (channel not active, platform/autopilot cap still over, quota day not rolled over, `youtube_audit_status = rejected` with `pause_after_n_private` reached, open content report). Non-empty → 409 `autopilot_pause_reason_active` with `errors.reasons = [...]` (plan §10 open item 4);
3. require a valid, current authorization for the stored settings (else 409 `autopilot_authorization_required`) and an `active` channel connection (else 409 `channel_reauth_required`);
4. clear `series.autopilot_paused_at`/`pause_reason`; set the paused runs back to their previous state (`paused_from_state` stored in memory? No: [DECISION] a resumed run goes back to the state it was paused from, which is recoverable from `step` — the step name maps 1:1 to a state: `idea → planned`, `story*`/`story_gate → story_gate`, `render`/`video_gate → video_gate`, `publication`/`consent`/`go_live → publication_created`. Stored as `paused_from_state` (one more column ⚠️ or derived — derived is preferred, no CR);
5. audit `autopilot.resumed { seriesId, previousPauseReason }`; no e-mail.
6. If the slot of a resumed run is already past its `start_at`, the next tick catches it up; if the slot is unrecoverable (`now > upload_at`), the run ends `failed` with `slot_missed` (trigger 13 counts it).

### Takedown hook (08.4.4-T1)

- `ReportCreated` (13.3.4) → resolve the report's target to an episode/publication → find the series → `PauseAsync(ContentReported)` + the alert e-mail with an extra line: "A report was filed on <episode title>; follow the takedown runbook: make the video private or remove it in YouTube Studio within 24 h and record the cause."
- The runbook itself (08.4.4-T1) owns the human steps; this task supplies the pause, the e-mail and the `audit_logs` row (`autopilot.paused` with `pauseReason = content_reported` and the report id in `data`).
- The platform does **not** delete or private the video through the API in the MVP (06.2.6: we do not delete videos on the user's channel); the alert carries the Studio link so the owner can act within 24 h.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two triggers at once (e.g. quota + upload failure) | the more severe reason wins; one e-mail |
| Pause while a publication is `uploading` | nothing is cancelled; 06 finishes or fails the upload; the alert lists it so the owner can act in Studio |
| Pause during the veto window | the publication stays `awaiting_consent` and 06.2.2-T3 writes no consent while the series is paused ([DECISION] the consent job checks the series pause state; CR to 06.2.2-T3) — otherwise a paused series could still upload |
| Resume when the platform cap is still over | blocked; the owner must top up or wait for the daily reset (the rechecker reads the live cap) |
| Resume after the slot passed | the run fails with `slot_missed`; the next slot is planned normally |
| `provider_funds_exhausted` (12.8.3) | pause with the same reason; the resume requires the provider balance to be restored (the rechecker queries the latest `provider_balance_snapshots` when available, else allows the resume and lets the next dispatch decide) ⚠️ |
| Incident cleared (OAuth client fixed) | the `PlatformIncidentCleared` event makes the rechecker stop blocking; the owner still presses Resume (no auto-resume) |
| The alert e-mail cannot be sent | `SendEmailJob` retries 5×; if it still fails, the pause stands (the state is in the DB and the UI banner shows it) — the e-mail is a notification, not the mechanism |
| Series already paused when the tick runs | no new runs; the tick still evaluates the veto/quota/pre-audit checks so a cleared condition is visible in the rechecker |
| Rollback | disable the series (T2) or resume manually; pausing is pure state, no data is destroyed |
