## Goal

The same linter result shows up in three places: as a hint while editing, as a blocker at approve, and as a blocker at render (because the fact sheet can change between the two). All three use one error shape the UI can map to a chip.

## Inputs

- README **D10** (`keywords_flagged` 409 + `errors[]`), **D11**; `plan.md` §4 (use-case table), §6 (copy keys).
- 02.3.4-T1: `StoryQualityChecker.Check(StoryContentV1, StoryCheckContext) → QualityReport`; objective blocking issues block approve.
- 02.3.2-T1 approve precondition order (If-Match → state → true-crime guard → similarity → …).
- 09.6.1 render command (`story_approved`, Idempotency-Key, reserve, outbox `RenderRequested`).
- CR-13: `StoryRenderInput` gains `Segments` (`SegmentKeywords` list).

## Design

1. **Checker (02.3.4-T1):** `StoryCheckContext` gains `NameCorpus Names` (loaded by the caller through `INameCorpusProvider`) and `RenderImagePlan? Plan`. The checker appends `RenderKeywordLinter.Lint(...)` issues and the plan's hint codes (`scenes_trimmed`, `scenes_sparse`) as advisory issues with segment `meta`. No new stored field: the issues live in `audit_report.local.issues` (02 D22).
2. **Approve (02.3.2-T1):** after the existing guards and before the state change, run the linter on the version being approved; blocking issues → `Error.Conflict("keywords_flagged")` with metadata `errors = [{ segment, index, rule }]`.
3. **Render (09.6.1-T1):** first step after the state check: load `StoryRenderInput` (approved version), `NameCorpus`, run the linter; blocking → 409 `keywords_flagged`. Zero planned terms → 409 `keywords_flagged` with rule `no_scenes`. Then the plan, worst case and budget (03.2.1-T1).
4. **ProblemDetails:** 09.1.4 maps `keywords_flagged` to 409 with an `errors` extension array (same mechanism as `story_invalid_content` field errors).

Error body:

```json
{ "type": "https://nighttales.app/errors/keywords_flagged", "title": "Some scenes must be changed", "status": 409,
  "code": "keywords_flagged",
  "errors": [ { "segment": "p:3", "index": 1, "rule": "keyword_name_detected" },
              { "segment": "hook", "index": 0, "rule": "keyword_invalid" } ] }
```

## Steps

4. Add the i18n keys from `plan.md` §6 to the web bundles hand-over list (CR-7).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Name corpus load fails (DB error) | approve/render return 503 via the normal pipeline; never skip the check silently |
| Autopilot approve hits `keywords_flagged` | the same command fails → 02.8.3 run goes to `waiting_owner` with reason `keywords_flagged` (02.8.3-T1 already maps command errors to owner action) |
| The user edits a keyword to fix it | `PUT /story` recomputes the checker; the chip turns normal; approve passes |
| Rollback | remove the linter step from the two handlers; the checker hint stays harmless |

## Notes

- Keep the linter step **after** the If-Match/state checks so a stale tab gets 412, not 409 (02.3.2-T1 order).
- Links: D10 · D11 · CR-7 · CR-9 · CR-13 · 02.3.2-T1 · 02.3.4-T1 · 09.6.1-T1 · 09.1.4.
- **Hand-over from 03.2.2-T1 (PR #203):** map a linter issue back to the segment keyword with `RenderKeywordLinter.TryGetKeywordIndex(issue, out int index)` (03 CR-18 b): the Evidence of both issue kinds ends in `;index:<i>`, and a name-rule Evidence is `run:<n>;index:<i>`; never put keyword or name text into `errors[].detail` or logs. The corpus check is skipped for a keyword that already fails R2 (it is re-linted after the rewrite).
- **Delivery (Session 53).** Path drift: the Outputs name `ApproveStoryHandler.cs`, `RenderEpisodeHandler.cs` and `ErrorCatalogue.cs`; the real files are `ApproveStoryCommandHandler.cs`, `RenderEpisodeCommandHandler.cs` and `Errors.cs` / `ErrorCatalogue.cs`, whose `keywords_flagged` / `no_scenes` entries and `ProblemBody.Errors` pre-existed (09.6.1-T1, OPEN-5). The render handler already linted after the state and If-Match checks, so this task wired the checker and approve and moved the keyword mapping into `KeywordLintMapping` (render behaviour unchanged).
- **Checker.** `StoryCheckContext.Names` is required (no default), `Plan` is fed by `StoryCheckInputs.PlanFor` from Edit and the generation pipeline. Only `keyword_name_detected` (Q-KW-05, blocking objective) is emitted from the linter (plan.md §4 names only that rule); `keyword_invalid` stays the Q-KW-03 advisory, so the chip is one severity step softer than approve/render, which return `keyword_invalid` rows too (the validator blocks the same condition at save). The pipeline reads the corpus once, before the first paid call; Edit reads it once per save; a load failure is never caught (503).
- **Approve.** The lint sits after the gate stages and before the moderation refresh and `ApproveStory`; 412/428 and the idempotent already-approved reply come first. Unreadable stored content returns 503 `service_unavailable` (fail-closed; the condition is permanent, so a client retrying on 503 will keep failing until the content is fixed). No OpenAPI change: approve already declares 409 and `errors[]` is the existing `ProblemBody.Errors`, so no web re-pin hand-over is needed. The approve 503 is not declared in `web/openapi.json` (same as every handler that can hit a transient DB error).
- **i18n.** The key `quality.keyword_name_detected` is added to the web quality bundles (en, vi) because `QualityHints_AllMessageKeysExistInBothLanguages` requires parity; the web lane (10.5.10-T1 / 10.6.1-T2) only has to render it.
- **Test fixtures.** Existing approve fixtures (`ApproveStoryEndpointTests`, `RealGuardApprovalTests`, `StoryApprovalRouteInputTests`, `ApproveReopenQaTests`) seeded two-word keywords that fail `KeywordRules`; they now seed valid phrases (the rule was not weakened).
- **Open.** (1) `StoryRenderInputProvider` throws `InvalidOperationException` on unreadable stored content, so render answers 500 where approve answers 503 (pre-existing, owner TL). (2) No test asserts the log channel is free of keyword text (code evidence only). (3) The D22 segment list is built in four places (approve, `StoryCheckInputs`, the checker, `StoryRenderInputProvider`); a shared Domain helper is a later cleanup. (4) `Checker_NameDetected_BlocksApproveInUi` is the plan 10 component test; the web `canApprove` rule already exists.
