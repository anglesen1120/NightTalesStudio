## Goal

The same linter result shows up in three places: as a hint while editing, as a blocker at approve, and as a blocker at render (because the fact sheet can change between the two). All three use one error shape the UI can map to a chip.

## Inputs

- README **D10** (`keywords_flagged` 409 + `errors[]`), **D11**; `plan.md` §4 (use-case table), §6 (copy keys).
- 02.3.4-T1: `StoryQualityChecker.Check(StoryContentV1, StoryCheckContext) → QualityReport`; objective blocking issues block approve.
- 02.3.2-T1 approve precondition order (If-Match → state → true-crime guard → similarity → …).
- 09.6.1 render command (`story_approved`, Idempotency-Key, reserve, outbox `RenderRequested`).
- CR-13: `StoryRenderInput` gains `Segments` (`SegmentKeywords` list).

## Design

1. **Checker (02.3.4-T1):** `StoryCheckContext` gains `NameCorpus Names` (loaded by the caller through `INameCorpusProvider`) and `RenderImagePlan? Plan`. The checker appends `RenderKeywordLinter.Lint(...)` issues and the plan's hint codes (`scenes_trimmed`, `scenes_sparse`) as advisory issues with segment `meta`. No new stored field: the issues live in `audit_report.local.issues` (02 D22).
2. **Approve (02.3.2-T1):** after the existing guards and before the state change, run the linter on the version being approved; blocking issues → `Error.Conflict("keywords_flagged")` with metadata `errors = [{ segment, index, rule }]`.
3. **Render (09.6.1-T1):** first step after the state check: load `StoryRenderInput` (approved version), `NameCorpus`, run the linter; blocking → 409 `keywords_flagged`. Zero planned terms → 409 `keywords_flagged` with rule `no_scenes`. Then the plan, worst case and budget (03.2.1-T1).
4. **ProblemDetails:** 09.1.4 maps `keywords_flagged` to 409 with an `errors` extension array (same mechanism as `story_invalid_content` field errors).

Error body:

```json
{ "type": "https://nighttales.app/errors/keywords_flagged", "title": "Some scenes must be changed", "status": 409,
  "code": "keywords_flagged",
  "errors": [ { "segment": "p:3", "index": 1, "rule": "keyword_name_detected" },
              { "segment": "hook", "index": 0, "rule": "keyword_invalid" } ] }
```

## Steps

1. Extend `StoryCheckContext` and `StoryQualityChecker` (02.3.4-T1 files) as in Design 1.
2. Add the linter step to `ApproveStoryHandler` (02.3.2-T1) and to `RenderEpisodeHandler` (09.6.1-T1).
3. Add `keywords_flagged` to the error catalogue and the ProblemDetails mapper (CR-9).
4. Add the i18n keys from `plan.md` §6 to the web bundles hand-over list (CR-7).
5. Integration tests for approve and render.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Name corpus load fails (DB error) | approve/render return 503 via the normal pipeline; never skip the check silently |
| Autopilot approve hits `keywords_flagged` | the same command fails → 02.8.3 run goes to `waiting_owner` with reason `keywords_flagged` (02.8.3-T1 already maps command errors to owner action) |
| The user edits a keyword to fix it | `PUT /story` recomputes the checker; the chip turns normal; approve passes |
| Rollback | remove the linter step from the two handlers; the checker hint stays harmless |
