## Goal

## Design

Console work plus two repo artifacts; no product code, no migration, no route.

**Record document `docs/ops/youtube-oauth-setup.md`** — one section per environment, each holding a table with the values 06.1.2-T1/T2 need at runtime and 13.4.2-T1 needs for the audit:

| Field | staging | prod |
|---|---|---|
| Google Cloud project id / number | `nts-youtube-staging` (record the number) | `nts-youtube-prod` |
| OAuth client type / name | Web application `nts-web-staging` | Web application `nts-web-prod` |
| Client id (public) | `….apps.googleusercontent.com` (recorded) | recorded |
| Secret location | `nts/staging/api/YOUTUBE_CLIENT_SECRET` | `nts/prod/api/YOUTUBE_CLIENT_SECRET` |
| Redirect URI | `https://<staging origin>/api/v1/channels/youtube/callback` | `https://<prod origin>/api/v1/channels/youtube/callback` |
| Authorised JavaScript origins | none (server-side flow only) | none |
| Scopes | `https://www.googleapis.com/auth/youtube.upload`, `https://www.googleapis.com/auth/youtube.readonly` | same |
| Publishing status | Testing | In production (unverified) |
| Test users | the owner's Google account only | n/a |
| `YouTube:AuditStatus` | `pending` | `pending` until 13.4.2-T1 |

Extra redirect URIs on **staging only**, temporarily, for the check script: `http://127.0.0.1:8765/` — removed again after the check (a stray loopback URI on prod is rejected by policy: the doc records "prod has exactly one redirect URI").

**Check script `tools/ops/youtube-oauth-check.py`** (stdlib only, Python 3.12, no third-party import):

```
python3 tools/ops/youtube-oauth-check.py --env staging [--redirect-uri <uri>] [--keep-token]
```
1. reads `YOUTUBE_CLIENT_ID` / `YOUTUBE_CLIENT_SECRET` from the environment (never argv, never a file; the doc says how to export them from the secret manager);
2. prints the authorization URL, runs a loopback listener on `127.0.0.1:8765`, exchanges the code at `https://oauth2.googleapis.com/token`, and asserts: a `refresh_token` is present, `scope` equals the two scopes (order-insensitive), `expires_in` > 0;
3. calls `channels.list?part=snippet&mine=true` with the access token and asserts exactly one channel with a non-empty id;
4. calls `POST https://oauth2.googleapis.com/revoke?token=<access_token>` and asserts 200, then re-calls `channels.list` and asserts HTTP 401;
5. with `--redirect-uri <other>`, stops after step 2 and asserts the token endpoint answers `redirect_uri_mismatch` (exit code 2);
6. prints one summary line and exits 0/1/2; it never prints the secret, the refresh token or the access token (only `refresh_token=yes|no`, the scope set and the channel id).

### Performance

No runtime path is added by this task (console + two files), so the performance commitments are all about not putting a call in the hot path later: exactly one redirect URI and exactly two scopes per client (the token response and the consent screen stay minimal), no JavaScript origins (nothing browser-side calls Google), the check script makes three HTTPS calls total (authorize → exchange → `channels.list`) plus one revoke and never retries, and the record document carries the values 06.1.2-T1/T2 read from configuration so no runtime lookup of the console is ever needed. Nothing in this task adds a per-request external call, a new job or a new table.

## Steps

1. Create the two projects (`nts-youtube-staging`, `nts-youtube-prod`); enable **YouTube Data API v3** in both; record ids and numbers.
2. Configure each OAuth consent screen: app name `Night Tales`, the owner's support e-mail, authorised domain `<origin host>`, the privacy-policy URL and the terms URL from the 13.1.1-T1/13.1.2-T1 versions as rendered by 10.3.1-T1 (soft — if the pages are not live yet, register the intended URLs and re-verify before the 06.1.2-T1 acceptance run), and only the two scopes.
3. Create the Web-application OAuth client per project; set exactly the one redirect URI per env (plus the temporary loopback URI on staging); store each secret in the secret manager as `nts/<env>/api/YOUTUBE_CLIENT_SECRET`; remove anything that landed in a shell history file, a notes file or the repo.
4. staging: set Publishing status = Testing and add the owner's Google account to Test users (G10: ≤ 100 test users, refresh tokens expire after 7 days). prod: set Publishing status = In production; do **not** submit the verification form (13.4.2-T1 files the audit; until then uploads are `private`, G2).
5. Write `docs/ops/youtube-oauth-setup.md` with the record tables, the staging-7-day note and the re-check command a later operator runs after any client change.
6. Write `tools/ops/youtube-oauth-check.py` and run it against staging with the owner's account; run the negative case; record both outputs (command + summary line) in the doc.
7. Hand the recorded `Client id`s to 06.1.2-T1/T2 as the values of `YouTube:ActiveClientId` and `YouTube:Clients:<clientId>:SecretRef` (staging and prod differ).

## Tests

No product code exists in this task, so no xunit test is added; the executable verification is the script plus the staging authorize round-trip, and the summary line is the evidence.

| Check | Kind | Assertion |
|---|---|---|

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Consent screen lacks a privacy-policy/terms URL (13.1.x not published yet) | Google refuses to save; the soft dependency means the task can start, but the 06.1.2-T1 acceptance run and the staging smoke (plan §11 step 4) must not run before both URLs are live |
| Wrong client type (Desktop instead of Web application) | no `client_secret` in the exchange; recreate the client as Web application and re-store the secret |
| Client secret leaked (pasted into a ticket/chat) | rotate in the console, write the new value to the secret manager, `nts-node sync-env`/deploy per 11 D15 H8; the doc records the rotation date |
| Client deleted or recreated | a new client id orphan an existing connection's pinned `oauth_client_id` (D5) → the connection fails with `invalid_client` and 06.2.3-T3 raises a platform incident; reconnect after `YouTube:ActiveClientId` is updated |
| Test-user cap / unverified-app user cap (100 new users, G10) | P has one user; the doc records the cap so a rollout never discovers it in production (phase S dropped, DEC 10.14) |
| Staging refresh token expires after 7 days | expected: 06.4.2-T1 marks the connection `expired` and raises the deletion duty; re-connect weekly during development |
| Accidental second redirect URI (loopback) left on prod | rejected by the acceptance check; remove it and re-run the check |
| The `YouTube:AuditStatus` value drifts from the console state | both are config/console facts; 13.4.2-T1's checklist compares them once, and 06.2.4-T1 reads the option, so a drift shows as an upload staying `private` (safe direction) |

## Notes

- The scope choice is ruled (D2/F11/G12): `youtube.upload` alone may not authorize `channels.list?mine=true`, and `youtube.readonly` is the documented scope for reading the account — the extra scope is the least-privileged pair that makes the connect flow's channel fetch work.
- Store the client id (public) in the doc; store the secret nowhere but the secret manager. `docs/ops/` is a plain doc, deliberately not an `.env.example` (11.1.1-T2 owns that file) and not a config file.
- The exact contract for reading a secret at runtime in P (`YouTube:Clients:<clientId>:SecretRef`) is 06.1.2-T1's; it is recorded here so the two tasks hand over a stable name.
