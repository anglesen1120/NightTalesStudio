## Goal

A successful callback leaves exactly one owned, publishable row: `ChannelConnection` stores the channel identity and both tokens as `ITokenProtector` ciphertext under the **per-connection** purpose `tokens.v1/{connectionId}`, pins the `oauth_client_id` that minted the code, is never duplicated for the same Google channel, and is the single source `GET /channels` reads; the user gets the `channel_connected` e-mail through 09.2.6-T3's queue (never inline).

## Design

### Domain — `src/NightTales.Domain/Publishing/ChannelConnection.cs`

Exactly the aggregate in `06.1-connect/plan.md` §3.1: `Connect(...)` (generates `Guid.CreateVersion7()` **before** encryption), `Reconnect(displayName, accessTokenEnc, refreshTokenEnc, tokenExpiresAt, scope, oauthClientId, now)` (same row, `oauth_client_id` re-pinned to the state's client per YR11, `Status = Active`, `RevokedAt = null`, `LastVerifiedAt = now`), `MarkExpired(now)`, `MarkError(now)`, `Revoke(now)` (nulls both token columns, `TokenExpiresAt = now`, `RevokedAt = now`); the domain **declaration** of `MarkRefreshed(accessTokenEnc, refreshTokenEnc, tokenExpiresAt, now)`, `RefreshFromApi(displayName, now)` and `PurgeYouTubeData(now)` (nulls tokens, `ExternalAccountId`, `DisplayName`; requires `Status == Revoked`) also lives in this file (06.4-revocation CRs accepted, `plan.md` §3.1) — this task ships the declarations and their domain tests; 06.4.2-T1's and 06.4.3-T1's commits land the callers. `ExternalAccountId`/`DisplayName` are `string?` for that reason. Enum `ChannelConnectionStatus { Active, Revoked, Expired, Error }` (lower-case wire values). `Platform` and its wire mapping come from 06.1.2-T1 — no second enum.

All setters are private (`OAuthClientId` is `private set` so `Reconnect` can re-pin it per YR11; the fields no method writes stay `private init`); the only mutation paths are the seven methods above, so "no upload without an `active` connection" (06 README NFR-06-1's sibling rule) is a domain fact, not a guard the upload job must remember.

### Token access — `ITokenService` (Application/Infrastructure, declared here)

`06.2.3-T2` and `06.4.2-T1` both need "the current access token, refreshed under lock" for this aggregate; since the lock and the re-read are against `channel_connections`, this task is the single declaring/implementing owner (README D9 names the member without pinning a task; accepted here per `plan.md` §3.1, closing 06.4-revocation §10.1 item 1):
```csharp
// Application/Abstractions/Publishing/ITokenService.cs
public sealed record ChannelAccessToken(string AccessToken, DateTimeOffset ExpiresAt);
public interface ITokenService
{ Task<ErrorOr<ChannelAccessToken>> GetAccessTokenAsync(Guid connectionId, CancellationToken ct); }
```
`TokenService` (`src/NightTales.Infrastructure/Publishing/TokenService.cs`, Scoped): `SELECT … FOR UPDATE` on the `channel_connections` row, **re-read after the lock** (F21); `revoked`/missing → `Error.NotFound("channel_reauth_required")`-class failure (the caller maps it); `TokenExpiresAt` ≥ now + 5 min → unprotect and return the current access token; otherwise `IYouTubeClient.RefreshAsync` (06.1.2-T1's port) with the client from `IOAuthClientResolver.ResolveAsync(connection.OAuthClientId)` (the connection's **pinned** client, D5) → on success, `connection.MarkRefreshed(...)`, `SaveChangesAsync` (still inside the row lock), return the new token; `invalid_grant` → propagate as a typed failure so the caller (06.2.3-T2 / 06.4.2-T1) applies its own connection-expiry handling — this port never mutates `Status` on failure, only `MarkRefreshed` on success. One implementation, no direct `SELECT … FOR UPDATE` anywhere else in the codebase.

**`ConnectChannelConnectionHandler`** (also the `IConnectChannelConnection` implementation; no `SaveChanges` of its own — it joins the caller's `IUnitOfWork`, or creates one when invoked from anywhere else):
1. Load the existing row for `(platform, external_account_id)` **without** `IgnoreQueryFilters`, **`FOR UPDATE`** (YR11 — the lock is taken before any token is written, so two concurrent connects for the same channel serialise here and the re-pin cannot interleave with an upload's token read):
   - a live row of the same user → `Reconnect(...)`: tokens replaced under the **existing** connection id, `oauth_client_id` **re-pinned** to the state's client, status `active`;
   - no visible row → insert a new row (a conflict at the DB level means another user owns a live row → `23505` on `ux_channel_connections_account`).
   The lookup is a single `SELECT … WHERE platform = @p AND external_account_id = @a AND status <> 'revoked' FOR UPDATE` read through the tenant-filtered context; the *authoritative* one-owner rule is the index — the read is an optimisation, never the guard (so a race cannot create two owners).
2. `connectionId = existing?.Id ?? Guid.CreateVersion7()`; protect both tokens for it: `_protector.Protect(connectionId.ToString(), accessToken)` → purpose `tokens.v1/{connectionId}` (D4) — on a reconnect this is the **existing** id, never a fresh one (YR11), so already-stored ciphertext of that connection keeps its purpose and an in-flight reader never sees a re-keyed row. The refresh token uses the same purpose; a `null` refresh token is rejected before this point by 06.1.2-T1 (D2 requires offline access) — the column stays `NULL`-able only for the revoked state.
3. `IEmailSender.QueueAsync(new EmailMessage(userId, "channel_connected", uiLocale, params), ct)` with `params = { displayName = user display name, channelTitle, occurredAt = ISO-8601 of now, device = RequestInfo.UserAgent summary, securityLink = "/account/security" }`. Queue only (A8) — this task never calls SMTP; the address is resolved from `users.email` by `SendEmailJob`.
4. `23505` on `ux_channel_connections_account` → `Error.Conflict("channel_already_connected")`; any other `DbUpdateException` propagates (500) rather than being swallowed.
5. `uiLocale` comes from the user row (`Language { Vi, En }` reused, 09 D16 — no second locale enum).

**`ListChannelsHandler`** — one query, projection straight to `ChannelConnectionDto` (`.Select(...)`, no `Include`, no navigation), `ORDER BY connected_at DESC`, tenant filter from `IUserOwned`. No token column and no `oauth_client_id` in the projection (the client id is an internal pinning detail; the S-phase admin view is 06.1.2-T3's). No per-row follow-up query (a test asserts one SQL command for the list).

### Performance (README D18)

- **Upsert**: one targeted read `WHERE platform = @p AND external_account_id = @a AND status <> 'revoked'` on `ux_channel_connections_account` plus one INSERT or one UPDATE — never a scan, never `IgnoreQueryFilters`, never a per-channel loop. The read exists only to decide insert-vs-update; the index is the authority.
- **List**: one statement, `.Select(...)` straight to the DTO, ordered by `connected_at DESC`, served by `ix_channel_connections_user_id` combined with the tenant filter — no `Include`, no navigation, no per-row token decrypt (the DTO carries no token), no count query, no paging (a user has a handful of connections).
- **Tokens are never read for a list or a DTO**: decryption happens only where a Google call needs a live token (06.2.3-T2), so the protector is off the list path entirely.
- **E-mail**: one `email_messages` insert (with its `email_requested.v1` outbox row in the same transaction) — the queue is the only write, no SMTP call, no render, so the callback's latency does not include mail.
- The batched `videos.list`/`channels.list` refresh over many connections is **06.4.2-T1's** (≤ 50 ids per call, ≤ 500 connections per run) — this task must not grow a loop over connections.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Another user owns a live row for the channel | `23505` on `ux_channel_connections_account` → 409/redirect `channel_already_connected`; the losing transaction writes nothing (no audit, no e-mail, no outbox) |
| The losing transaction already queued the e-mail | impossible by order: the upsert runs before `QueueAsync` and both commit together, so a rolled-back connect sends nothing |
| The user's row is `expired`/`error` and they reconnect | `Reconnect` on the same row, `status = active`, `revoked_at = null`; the token columns are overwritten (the old ciphertext is not kept — history lives in the audit row) |
| Revoked row for the same channel, same user, reconnects | `status <> 'revoked'` excludes it from the unique index, so this is a **new** row (the revoke is the end of that connection's life); the partial index allows it |
| Token table columns after `Revoke` | `NULL`; a `ChannelConnectionDto` read of a revoked row still works (the list shows the historical row with `status = revoked`) |
| `display_name` differs from the earlier row (channel renamed) | `Reconnect` overwrites it; the e-mail reports the value fetched by `channels.list` |
| A refresh token missing from the token response | 06.1.2-T1 rejects before this handler runs; if it ever arrives, the handler fails with `oauth_exchange_failed` rather than storing a `NULL` refresh token on an `active` row |
| The e-mail locale is not set on the user row | `Language.En` is the documented fallback (09 D16); the tests pin the vi case |
| Very long channel title (> 200 chars) | Google's own limit is smaller, but the column width is enforced; an over-long title fails the insert loudly rather than truncating silently (a truncated title in the security e-mail would be misleading) |
| `channel_connections` row whose user was deleted | no FK, row survives (13 §5.4); `GET /channels` is unreachable without the user, and 13.3.1-T1's `channel` scope handler (06.4.3-T1) calls `PurgeYouTubeData` — tokens, `ExternalAccountId` and `DisplayName` all become `null` |

## Notes

- **YR11 (reconnect).** The reconnect is a locked read-then-write on the **same** row: `FOR UPDATE` → protect under the existing id → `Reconnect(..., oauthClientId: state.oauth_client_id, now)`. Consequences: the connection follows the client that actually minted the new code (so retiring an OAuth client in the S-phase settings never needs a reconnect per client), and `Revoke`/disconnect (06.4.1-T1) takes the same row lock — the two paths cannot interleave with an upload's `ITokenService` read.
- **The purpose string is internal now**: `tokens.v1/{connectionId}` is used only inside this file — `ConnectChannelConnectionHandler.ConnectAsync` protects with it, `TokenService.GetAccessTokenAsync` unprotects with it (`ConnectionId.ToString()`, the lower-case dashed UUID form) — so there is no cross-file string to keep in sync; the unit test `Tokens_DoNotDecryptUnderAnotherPurpose` still pins the exact suffix.
