## Goal

`POST /publications/{id}/consent` turns an `awaiting_consent` publication into `scheduled` only when the client echoes the consent text version that was actually shown (`pc.v1`) and the row's current ETag. Consent records the four evidence fields (`consent_at`, `consent_text_version`, `consent_source = user`, audit row), moves the episode to `scheduled` in the same transaction and enqueues the upload job at the computed queue time. The domain refuses to start an upload for any publication without `consent_at`, so no later stage can bypass consent.

## Design

```csharp
// src/NightTales.Application/Features/Publishing/Commands/ConsentPublication/
public sealed record ConsentPublicationCommand(Guid PublicationId, string ConsentTextVersion,
    string IfMatch) : ICommand<ErrorOr<PublicationDto>>;
// IfMatch is bound from the header by the endpoint filter; the handler compares it (09.1.4-T1 pattern:
// handlers compare after load, so the 412 carries the current ETag and no row is locked on a stale value).

public sealed class ConsentPublicationHandler : IRequestHandler<ConsentPublicationCommand, ErrorOr<PublicationDto>>
{
    public async Task<ErrorOr<PublicationDto>> Handle(ConsentPublicationCommand cmd, CancellationToken ct)
    {
        var publication = await db.Query<Publication>()                 // tenant filter → 404 for others
            .Where(p => p.Id == cmd.PublicationId).SingleOrDefaultAsync(ct);
        if (publication is null) return Error.NotFound(ErrorCodes.NotFound, "publication_not_found");
        if (!ETags.Matches(cmd.IfMatch, ETags.Publication(publication.Xmin)))
            return Error.PreconditionFailed(ErrorCodes.PublicationConflict);
        var textVersion = options.CurrentValue.ConsentTextVersion;      // pc.v1 (IOptionsMonitor)
        var consented = publication.Consent(cmd.ConsentTextVersion, textVersion, clock.UtcNow);
        // Consent(...) raises PublicationUpdated (D13's existing shape, unchanged) on success. This handler
        // NEVER calls IJobScheduler: the Api's registration of it throws by design (09-backend-api README:288
        // [DECISION]); a Worker-side subscriber to publication_updated.v1 does the scheduling (YR3).
        if (consented.IsError) return consented.Errors;                 // consent_text_outdated | publication_invalid_state
        var episode = await db.Episodes.SingleAsync(e => e.Id == publication.EpisodeId, ct);
        if (episode.MarkScheduled(clock.UtcNow).IsError) return /* episode_invalid_state */;
        await db.SaveChangesAsync(ct);          // ONE UnitOfWork transaction: publication row + outbox row
        return mapper.ToDto(publication);
    }
}
```

**YR3 (consent → upload scheduling).** `publication_updated.v1` keeps its D13 shape unchanged (`{ publicationId, episodeId, userId, status, errorCode? }`); this handler never calls `IJobScheduler`/`IPublishScheduler`. The Worker-side subscriber is **implemented, not `[OPEN]`**: `06.2.3-T2`'s `PublicationScheduledForUploadHandler` reacts to `publication_updated.v1` on `status == "scheduled"`, re-reads the row and computes `queueAt = row.NextAttemptAt ?? PublicationQueueTime.For(row.PublishAt, options.PublishLeadMinutes, clock.UtcNow)` — the same D12 formula this folder would have used, independently derived (confirmed via IRC with `Y06Upload` 2026-09-25) — then calls its own named port `IPublishScheduler.EnqueueAtAsync(publicationId, when, ct)` (not a bare `IJobScheduler.Schedule<PublishYouTubeJob>` call; `06.2.3-T2` owns that seam). It also guards against a hot loop on an incident-held row (`ErrorCode == "platform_incident"`, `NextAttemptAt = null`), which `06.2.3-T2` caught independently.

This handler's own contract is unchanged by any of that: after `Consent(...)` succeeds it only leaves the row `scheduled` (with `PublishAt`/`NextAttemptAt` correct) and lets the standard outbox interceptor raise `publication_updated.v1` — confirmed with `Y06Upload` that nothing else is required on this side.

**Flagged to `Y06Upload`, not resolved here (their mechanism, not this folder's):** D9's order is lock → `external_post_id` check → **reserve quota (D10)** → token → session, and the session URI is committed *before* the first byte, releasing the row lock during streaming. At-least-once delivery could call `EnqueueAtAsync` twice for the same attempt (same `queueAt`); if `PublicationScheduledForUploadHandler` has no per-attempt dedup, a second concurrent `PublishYouTubeJob` run could reserve a second quota unit before the first sets `external_post_id`, and could probe/resume the same session while the first is still streaming. A per-attempt guard (skip when the row already has an enqueue recorded for the *same* `queueAt`; a *different* `queueAt` — a genuine retry — must still pass) closes this without blocking `quotaExceeded`'s or an incident-clear's legitimate re-schedule. Separately: the `NextAttemptAt ?? …` fallback must not fire while a `platform_incidents` row is open for the connection's client (D14, `../README.md:132` — a held row can carry `next_attempt_at = NULL`, which would otherwise read as "ready, derive from `PublishAt`" and re-enqueue into a still-broken client); the subscriber needs the same incident check `PublishYouTubeJob` itself does before scheduling. Both left to `06.2.3-T2`'s implementation, not specified further here.

Domain guard (owned by `06.2.1-T1`, called here) — `Publication.Consent(string textVersion, string currentTextVersion, DateTimeOffset now)`:

- rejects any state other than `AwaitingConsent` → `publication_invalid_state` (409);
- `textVersion != currentTextVersion` → `consent_text_outdated` (400, D7) — the client refetches the text and re-shows it;
- writes `ConsentAt = now`, `ConsentTextVersion`, `ConsentSource = "user"`, `Status = Scheduled`, raises `PublicationUpdated` (D13's existing shape, no `queueAt` — YR3).

`Publication.ConsentFromAuthorization(...)` stays the single entry point for `AutopilotConsentJob` (06.2.2-T3, D8) so the two consent paths cannot drift; the audit action differs (`publishing.consented` vs `publishing.consent_autopilot`, D17).

`PublicationQueueTime.For(DateTimeOffset? publishAt, int leadMinutes, DateTimeOffset now) → DateTimeOffset` (YR3, `src/NightTales.Domain/Channels/PublicationQueueTime.cs`, declared by this task): pure function, `publish_at − leadMinutes` when set, else `now` (D12), clamped `Math.Max(now, …)`. This handler does **not** call it — it plays no role in the consent command; `06.2.3-T2`'s `PublicationScheduledForUploadHandler` calls this same function with the row's fresh values (`NextAttemptAt ?? PublicationQueueTime.For(PublishAt, PublishLeadMinutes, now)`) when it acts on `publication_updated.v1`. Declaring it here (not duplicating the formula in the Worker subscriber) is the single-owner fix YR3 requires. This handler's only remaining job after `Consent(...)` succeeds is to move the episode and save.

Pre-audit visibility (D12/C4) is **not** this handler's concern: `06.2.1-T1` stamps `platform_payload.preAudit`/`requestedPrivacy` and the effective `privacy` at **create** time, once, permanently — `06.2.4-T1`'s planner and `PublishYouTubeJob` only ever *read* those fields (confirmed with `Y06Status` 2026-09-25, reversing an earlier proposal for a queue-time correction: per `02.8.3-T3:156` a pre-audit slot stays private for that publication forever, only the next autopilot run goes public). This handler never reads or writes `privacy`, `preAudit` or `requestedPrivacy`.

Endpoint (in `PublishingEndpoints`, 06.2.1-T1's file):

```csharp
group.MapPost("/publications/{id:guid}/consent", ConsentPublication)
     .RequireAuthorization().RequireFeature("youtube_publish").RequireIfMatch().RequireRateLimiting("auth")
     .Produces<PublicationDto>(200).ProducesProblem(400).ProducesProblem(404).ProducesProblem(409)
     .ProducesProblem(412).ProducesProblem(428);
```

Request body `{ consentTextVersion }`. Response: `200` + `ETag: "pu-<xmin>"` read **after** commit (09.1.4-T1's `ToCreatedResult` etag callback pattern) so the client can immediately PATCH/cancel with the fresh value. Error codes: 400 `consent_text_outdated`, 404 `not_found`/`feature_disabled`, 409 `publication_invalid_state`, 412 `publication_conflict`, 428 `if_match_required`.

Idempotency: consenting an already-`scheduled` row whose `consent_source` is `user` is a **success no-op** returning the same DTO/ETag and writing no second audit/outbox row (a retried request after a lost response must not fail); the domain method is the arbiter, the handler does not special-case it. A repeat for an `autopilot` row is a `publication_invalid_state` (the user's explicit consent on top of a machine consent is not silently merged; "approve now" 06.2.2-T4 uses the same route and is documented there).

Audit/outbox: `[Audited("publishing.consented", data: { publicationId, episodeId, consentTextVersion, source: "user" })]` — ids and the text version only, never the title or channel name (D17). Outbox `publication_updated.v1 { publicationId, episodeId, userId, status: "scheduled" }` (D13, unchanged shape); the SignalR fan-out keeps `{ publicationId, episodeId }` with no `RealtimeData` (WT54).

Codes: `publication_invalid_state` (409) and `publication_conflict` (412) are `06 CR-9` (YR5 — not CR-2; 09 §5.4 gains them alongside `publication_privacy_locked` 409 and `channel_not_active` 409), patterned on the 09 pair `episode_invalid_state` 409 / `episode_conflict` 412 (`09-backend-api/README.md:360`); `consent_text_outdated` is mandated by D7.

## Failure handling and edge cases

- Consent text version drift (the client rendered an older `pc.v1` revision while `YouTube:ConsentTextVersion` was bumped): 400 `consent_text_outdated`; the client refetches the text and re-shows the dialogue. `pc.v1` is a single immutable version string, so the same file revision is re-rendered, not translated into a second string.
- `publish_at` already past when consent arrives (e.g. a manual publication created hours ago): the effective queue time (computed by the Worker-side subscriber, not this handler) is `now` (never a negative delay — the subscriber clamps with `Math.Max(now, publishAt − lead)`).
- The Worker-side subscriber's scheduling failure and its recovery path (retries, `next_attempt_at`, 02's fallback tick) belong to that subscriber's own task (06.2.3-T2), not to this one; this handler's only failure surface ends at its own `SaveChangesAsync`. `06.2.2-T2`'s notice call runs inside the same transaction as this handler's write (see 06.2.2-T2 §Design), so a failed notice queue now fails the whole consent command too — it does not "not roll back," it *is* the rollback boundary.
- Concurrent consent + cancel: both load the row through `db.Query<Publication>()`; the optimistic `xmin` concurrency token makes the loser throw `DbUpdateConcurrencyException`, mapped by the UnitOfWork to 409 `concurrency_conflict`, and no half-applied episode transition survives.
- A publication deleted between the read and the save (account deletion cascade): 404 `not_found` from the FK/row-count check, never a 500.
- Enrolling "approve now" (06.2.2-T4) on an already-expired veto window: `AutopilotConsentJob` may have consented a moment earlier → this route then answers 409 `publication_invalid_state`; T4 documents the client handling (refetch, if already `scheduled` treat as success).
- No quota interaction here: the unit is reserved by `PublishYouTubeJob` at the PT day of upload (D10), so consent never consumes quota.
