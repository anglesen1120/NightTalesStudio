## Goal

Every consent sends the owner an e-mail (`publication_consented`), and every autopilot publication sends the veto notice (`publication_veto_notice`) with a preview, an edit/approve link and a **single-use cancel link** that is minted at send time, stored only as a hash, and carried in the URL fragment. `POST /publications/cancel-by-link` cancels exactly one publication from that link, anonymously, behind the `auth` rate policy. This is the only sanction against a stolen session publishing silently and the only channel for the veto window (D7).

## Design

### Two templates, registered in 09.2.6-T3's catalog (06 CR-6)

`Templates/Email/publication_consented.<locale>.{txt,html}` — allow-listed params (unknown key is a startup error, `09-backend-api/README.md:688`):
`displayName`, `channelTitle`, `videoTitle`, `privacy`, `privacyNote`, `scheduledAt`, `publicationUrl`, `approvalLine`, `consentSource` (`"user"` | `"autopilot"`, producer key — kept for the payload/audit trail per Main's request, but **not itself rendered**: BD9's renderer only does flat `{{key}}` substitution with no conditionals, `09-backend-api/README.md:688`, the same fact `privacyNote` below already relies on).
Sent on **every** consent, both user and autopilot (D7, YR9): channel title, video title, privacy, scheduled time, and a link to the publication page where it can still be cancelled before upload (06.2.6). `scheduledAt` is ISO-8601 **UTC** and the template appends the literal `UTC`; there is no user timezone column in 00 §6 `users` `[OPEN: if 13/10 later add one, the param is rendered locally]`. Not token-bearing → no minter. `approvalLine` is a **code-built, localized string** (not template branching) — `PublicationNotices` selects the vi/en copy for `source == User` ("you approved this upload") or `source == Autopilot` ("approved automatically after the veto window", YR9's exact wording) and passes the already-rendered line as one flat param.

`Templates/Email/publication_veto_notice.<locale>.{txt,html}` — params: `displayName`, `channelTitle`, `videoTitle`, `description`, `tags`, `privacy`, `privacyNote`, `scheduledAt`, `vetoEndsAt`, `publicationUrl`, `publicationId` (producer key, consumed only by the minter to build the link — never rendered), `cancelUrl` (minter output). Content: the preview (title, description, tags, privacy, time), the veto deadline, an edit/approve link and the cancel link (`../../06-youtube-posting.md:68-70`). Token-bearing → `PublicationCancelTokenMinter`.

`privacy`/`privacyNote` (advisor-fixed 2026-09-25, closes the notice-vs-row drift; permanence wording fixed 2026-09-25): `privacy` is always the row's **effective** value (`platform_payload.preAudit ? "private" : the owner's submission` — already correct because 06.2.1-T1 stamps it at create, before either notice is queued, D12/C4, YR20). `privacyNote` is a single string **built in C#** by `PublicationNotices` (not a `{{…}}` placeholder embedded inside a param value — `requestedPrivacy` is not itself an allow-listed key, and `{{key}}` is the renderer's own substitution syntax, BD9), empty when `preAudit` is absent, else `$"(will be published as Private because the project has not passed Google's audit; you selected {requestedPrivacy})"` — **permanent**, not "until", matching YR20's "that slot stays private" (a pre-audit publication never later becomes public; only the next autopilot run does). Both templates carry it so a manual consent on a pre-audit-locked row is explained the same way as an autopilot notice.

Locale comes from `users.ui_locale` through the existing `Language { Vi, En }` enum (09 README:319, D16 — no second enum). Both e-mails are queued with `IEmailSender.QueueAsync(new EmailMessage(userId, template, locale, params))` and the returned `email_messages.id` is the only handle we keep; a queue failure is returned to the handler and logged with the template name and a user-id hash (never an address, never a token).

### Minter, link shape and token lifetime (WT17)

```csharp
// src/NightTales.Application/Features/Email/TokenMinters/PublicationCancelTokenMinter.cs
public sealed class PublicationCancelTokenMinter : IEmailTokenMinter
{
    public async Task<ErrorOr<IReadOnlyDictionary<string, string>>> MintAsync(Guid userId, string template,
        IReadOnlyDictionary<string, string> parameters, CancellationToken ct)
    {
        if (template != EmailTemplates.PublicationVetoNotice) return new Dictionary<string, string>();
        var publicationId = Guid.Parse(parameters["publicationId"]);
        var vetoEndsAt = DateTimeOffset.Parse(parameters["vetoEndsAt"]);
        var expiresAt = new[] { vetoEndsAt, clock.UtcNow.AddHours(48) }.Min();   // YR8: min(veto_ends_at, now + 48 h)
        var token = await tokenService.IssueAsync(userId, UserActionKind.PublicationCancel,
            subjectId: publicationId, expiresAt, RequestInfo.System, ct);         // YR8 overload
        if (token.IsError) return token.Errors;
        return new Dictionary<string, string> { ["cancelUrl"] = AuthLinks.PublicationCancel(origin, publicationId, token.Value) };
    }
}
```

- `AuthLinks` gains one member (06 CR-6), patterned exactly on the existing two:
  `PublicationCancel(Uri origin, Guid publicationId, string token) => $"{origin.GetLeftPart(UriPartial.Authority)}/publications/cancel#p={publicationId}&t={token}"` — token **after** the `#` (the invariant `AuthLinksTests.Links_PutTheTokenAfterTheHash` already pins for reset/verify, `09.3.3-T1:173`). [INFERENCE on the exact member name/signature; the pattern and the fragment rule are verified.]
- Origin: **no new config key** ✅ — `09.2.6-T3:109` pins it: "Links are built at send time from `App:PublicOrigin` by the minter" ([RULED — README §B10 WT17]), so this minter takes the same `Uri origin` as its `PasswordReset` sibling and 06 declares no key. `{{approve_url}}` (06.2.2-T4) uses the same origin.
- **TTL and scoping, settled by YR8 (closes the earlier `[OPEN]`):** `IUserActionTokenService` gains an `IssueAsync(Guid userId, UserActionKind kind, Guid subjectId, DateTimeOffset expiresAt, RequestInfo info, ct)` overload (09.3.3-T1's, a 06 CR-6 extension); the per-kind invalidation that used to kill every other unused token of the same `(user, kind)` is now scoped to `(user, kind, subjectId)` — minting a cancel link for publication B no longer kills publication A's still-live link, closing the earlier per-user cross-object-kill bug this folder had flagged. Expiry is `min(veto_ends_at, now + 48 h)`, computed here from the `vetoEndsAt` param already on hand (no extra query).
- Consequences honoured: no token in `email_messages.params`, none in the outbox payload, none in logs; `params` is nulled once `sent` (09.2.6-T3:168). The veto notice is queued **before** `veto_ends_at` (the publication is created with the window already set, YR1), so the deadline is never in the past when the owner reads it.

### Where the two calls live

This task inserts the two notice calls into the handlers 06.2.1-T1/06.2.2-T1 own, **before** each handler's single `SaveChangesAsync` — not after commit (advisor-fixed 2026-09-25: a post-commit second update was the original draft and it broke three things at once — `06.2.1-T1`'s "exactly one `publication_updated.v1` per create" acceptance check if the second save re-raised a domain event, the `201` response's `ETag: "pu-<xmin>"` since `xmin` bumps again after the value the response already captured, and the "queueing fails, the command still commits" line in `plan.md` §7, which only makes sense if queueing is inside the same atomic unit).

**Mechanism confirmed against the port's actual contract (advisor-fixed 2026-09-25, second pass):** these calls go through `IEmailSender.QueueAsync` — the standard port (C6, `09.2.6-T3:23-24`) — **not** a bypass that touches `db.EmailMessages.Add` directly. `09.2.6-T3:39` settles the commit boundary explicitly: `QueueAsync`'s Application-layer implementation resolves the template, validates the param allow-list, computes the address hash, then "add[s] the aggregate — the outbox interceptor (D11) writes `email_requested.v1` in the same `SaveChanges`. **All producers are command or outbox handlers, so it always joins an existing UnitOfWork.**" So calling `IEmailSender.QueueAsync` from inside `CreatePublicationHandler`/`ConsentPublicationHandler`, before their own `SaveChangesAsync`, is not a workaround — it is the port's documented behaviour: it never commits on its own, and the outbox interceptor is exactly what raises `email_requested.v1` (the standard domain-event-to-outbox path, the same mechanism that turns `Publication`'s own domain events into `outbox_messages` rows) — one `SaveChangesAsync` covers the `Publication`/`Episode` write and the `EmailMessage` row together, with no second enqueue path invented by this folder (BD9 stays the single owner of "how an e-mail gets queued").

- `CreatePublicationHandler`: after `Publication.Create(...)` succeeds and before `db.SaveChangesAsync`, when `AutopilotAuthorizationId is not null` → `notices.QueueVetoNoticeAsync(publication, channelDisplayName, ownerDisplayName, locale, ct)` builds the `EmailMessage` and params, calls `IEmailSender.QueueAsync` (returns the pre-generated `email_messages.id`, a client-side UUIDv7 — no DB round trip needed to know it, `09.2.6-T3:52`'s `EmailMessage.Queue` factory), then passes that id to `publication.SetVetoNoticeEmailId(id)` (a new domain method, writes `platform_payload.vetoNoticeEmailId`) on the *same tracked, unsaved* `Publication` instance — no second query, no second update statement.
- `ConsentPublicationHandler`: after `Publication.Consent(...)` succeeds and before `db.SaveChangesAsync` → `notices.QueueConsentedAsync(publication, ConsentSource.User, ct)` → `IEmailSender.QueueAsync`, same in-memory-then-save pattern, always (D7/YR9: every consent).

Application port owned here (a thin adapter over `IEmailSender`, not a second enqueue mechanism). `QueueVetoNoticeAsync` keeps its original shape — the in-memory entity plus the denormalized fields the handler already has from its own earlier queries (steps 1–4 of `06.2.1-T1`'s handler), so no re-query is needed for a not-yet-saved `Publication`. `QueueConsentedAsync` (Main's exact signature) is different: it takes only the entity and a `ConsentSource`, so `PublicationNotices` resolves the channel display name and the owner's `DisplayName`/`UiLocale` itself, through the tenant-filtered `IAppDbContext` — two no-tracking projections by `publication.ChannelConnectionId` and `publication.UserId` (related rows, never re-reading the `Publication` itself, which is unsaved on this path):

```csharp
// src/NightTales.Application/Abstractions/Publishing/IPublicationNotices.cs
public interface IPublicationNotices
{
    Task<ErrorOr<Guid>> QueueVetoNoticeAsync(Publication publication, string channelDisplayName,
        string ownerDisplayName, Language locale, CancellationToken ct);
    Task<ErrorOr<Unit>> QueueConsentedAsync(Publication publication, ConsentSource source, CancellationToken ct);
    // renamed from QueueConsentNoticeAsync (Main's exact signature, 2026-09-25): resolves channelDisplayName,
    // ownerDisplayName and locale internally instead of taking them as parameters — this method now has three
    // callers (06.2.2-T1's consent, 06.2.2-T3's AutopilotConsentJob, 06.2.2-T4's approve-now) and repeating the
    // lookup at every call site was worse than doing it once here; QueueVetoNoticeAsync is unchanged.
}

// src/NightTales.Infrastructure/Publishing/PublicationNotices.cs
public sealed class PublicationNotices(IEmailSender emailSender, IAppDbContext db) : IPublicationNotices
{
    public Task<ErrorOr<Guid>> QueueVetoNoticeAsync(Publication publication, string channelDisplayName,
        string ownerDisplayName, Language locale, CancellationToken ct)
        => emailSender.QueueAsync(new EmailMessage(publication.UserId, EmailTemplates.PublicationVetoNotice,
            locale, VetoNoticeParams(publication, channelDisplayName, ownerDisplayName)), ct);

    public async Task<ErrorOr<Unit>> QueueConsentedAsync(Publication publication, ConsentSource source, CancellationToken ct)
    {
        var channelDisplayName = await db.Query<ChannelConnection>().Where(c => c.Id == publication.ChannelConnectionId)
            .Select(c => c.DisplayName).SingleAsync(ct);                          // tenant-filtered, no-tracking
        var owner = await db.Query<User>().Where(u => u.Id == publication.UserId)
            .Select(u => new { u.DisplayName, u.UiLocale }).SingleAsync(ct);
        var locale = owner.UiLocale;
        var approvalLine = ApprovalLine.For(source, locale);        // code-built localized string, vi/en;
            // NOT a template-conditional — BD9's renderer does flat {{key}} substitution only (09-backend-api
            // README:688), the same reason privacyNote is computed in code below, not branched in the template
        var consentSource = source == ConsentSource.Autopilot ? "autopilot" : "user";   // producer key, unrendered
        var @params = ConsentedParams(publication, channelDisplayName, owner.DisplayName, approvalLine, consentSource);
        return (await emailSender.QueueAsync(new EmailMessage(publication.UserId,
            EmailTemplates.PublicationConsented, locale, @params), ct)).Then(_ => Unit.Value);
    }

    // Two explicit builders, one per template — a shared `BuildParams` cannot exist: the templates have
    // different allow-lists (`:26` vs `:29`) and `QueueAsync` rejects any key outside a template's own list
    // (09.2.6-T3:39), so a merged builder would fail every consent the moment it emitted a veto-only key.
    private static IReadOnlyDictionary<string, string> VetoNoticeParams(Publication p, string channelDisplayName,
        string ownerDisplayName) => new Dictionary<string, string>
    {
        ["displayName"] = ownerDisplayName, ["channelTitle"] = channelDisplayName, ["videoTitle"] = p.Title,
        ["description"] = p.Description, ["tags"] = string.Join(", ", p.Tags),
        ["privacy"] = p.Privacy, ["privacyNote"] = BuildPrivacyNote(p),
        ["scheduledAt"] = p.PublishAt?.ToString("O") ?? "", ["vetoEndsAt"] = p.VetoEndsAt!.Value.ToString("O"),
        ["publicationUrl"] = PublicationUrl(p), ["publicationId"] = p.Id.ToString(),
    };   // "cancelUrl" is minter output, not a producer key — never set here (WT17)

    private static IReadOnlyDictionary<string, string> ConsentedParams(Publication p, string channelDisplayName,
        string ownerDisplayName, string approvalLine, string consentSource) => new Dictionary<string, string>
    {
        ["displayName"] = ownerDisplayName, ["channelTitle"] = channelDisplayName, ["videoTitle"] = p.Title,
        ["privacy"] = p.Privacy, ["privacyNote"] = BuildPrivacyNote(p),
        ["scheduledAt"] = p.PublishAt?.ToString("O") ?? "", ["publicationUrl"] = PublicationUrl(p),
        ["approvalLine"] = approvalLine, ["consentSource"] = consentSource,
    };   // no description/tags/vetoEndsAt/publicationId — publication_consented's allow-list (:26) has none of them
}
```

`ApprovalLine.For(ConsentSource, Language) → string` (this task, alongside `PublicationNotices`): a small static lookup — `User` → `"You approved this upload." / "Bạn đã duyệt video này."`; `Autopilot` → `"Approved automatically after the veto window." / "Đã tự động duyệt sau thời gian phủ quyết."` (YR9's exact English wording, vi is this task's translation). No conditional logic reaches the template file itself.

`IEmailSender.QueueAsync` itself never calls `SaveChangesAsync` (confirmed above), so the calling handler's own single save covers everything. A queueing failure (unknown template, a param key outside the template's allow-list, `09.2.6-T3:39`'s validation) is returned as an `ErrorOr` error and the **whole** command fails — including the `Publication`/`Episode` writes, which is correct once queueing is inside the same atomic transaction. This supersedes `plan.md` §7's older "queueing fails, the command still commits" line, which only made sense back when queueing was outside the transaction (YR9 now mandates in-transaction queueing for every consent path, see plan.md).

### Cancel-by-link

```csharp
public sealed record CancelPublicationByLinkCommand(Guid PublicationId, string Token) : ICommand<ErrorOr<Success>>;
```

Handler (YR8): `tokenService.ConsumeAsync(token, UserActionKind.PublicationCancel, ct)` — one atomic `UPDATE … SET used_at = now() WHERE token_hash = @h AND used_at IS NULL AND expires_at > now()` inside the port, constant-time compare, single use; it returns `(userId, subjectId)` (or 400 `cancel_token_invalid`). The handler requires `subjectId == cmd.PublicationId` — a token minted for a different publication answers the same generic 400, never a cross-object cancel. Then load by `(publicationId, userId, status = AwaitingConsent)` and `Publication.Cancel(now)`; queue nothing; emit `publication_updated.v1` (D13); audit `publishing.cancelled` with `actor = system:link`. A missing publication, a foreign publication, a used/expired token or a publication past `awaiting_consent` all answer the **same** 400 `cancel_token_invalid` (no state leak, no enumeration). `ForUpdate` ordering makes it race-free against both the upload job and `AutopilotConsentJob` (the loser sees the new status and answers the generic 400).

Endpoint: anonymous (`IAllowAnonymousRequest`, the 09.3.3-T1 pattern), `.RequireRateLimiting("auth")`, `.RequireFeature("youtube_publish")` (D1), response `204`; the response sets `Referrer-Policy: no-referrer` and `Cache-Control: no-store` (D3's callback pattern) so the fragment is never leaked through a Referer or a shared cache.

## Failure handling and edge cases

- `IEmailSender.QueueAsync` failure on the veto-notice path (unknown template, param outside the allow-list — a code bug, not an operational fault): the **whole** `CreatePublicationCommand` fails and rolls back, since queueing now runs inside the same `SaveChangesAsync` as `Publication.Create` (§Design) — no publication row, no `veto_ends_at`, nothing half-created. This is different from an SMTP-level delivery failure (next bullet), which happens after the row is safely committed and is 06.2.2-T3's concern via `veto_notice_sent_at`.
- Notice queued but SMTP delivery fails: `SendEmailJob` retries 5× (`09 §5.3`); the token row minted on the first send attempt is single-use per attempt, so a retry mints a second row [INFERENCE: `SendEmailJob`'s idempotency guard is the message id, per `09.2.6-T3:107`, so a retry of the same message re-renders; a previously minted, unsent row simply expires unused]. Both rows are inert without the body.
- Veto window shorter than one `SendEmailJob` retry cycle (~minutes): the deadline may pass before delivery; the token then fails expiry and the publication falls to the autopilot consent path — the owner still received (or will receive) the preview with `vetoEndsAt` in the past `[OPEN: 06.2.2-T3 may re-queue the notice or pause the series; owner decision]`.
- A user clicks the cancel link after the upload started: the status guard answers 400 `cancel_token_invalid` and the page instructs the user to YouTube Studio (06.2.6's rule).
- Duplicate clicks on the link (double POST from the SPA): the first consumes the token, the second gets the generic 400; the obvious UI treatment (already-cancelled page) is 10 wave 2's.
- Token brute force / enumeration: 32 random bytes, hashed lookup, constant-time compare, one generic code, `auth` rate policy.
- A publication whose owner's account was deleted (cascade removes the token row): the link answers the generic 400.
- The veto notice for a publication cancelled before delivery: the token row remains until `expires_at` and the route refuses with the generic 400 — no cleanup job needed (the row dies with the user, and `used_at`/`expires_at` make it inert).
- Locale not `vi`/`en` (a future locale): `Language` has two members (09 README:319) — the mapper falls back to `Vi` and the template pair always exists at startup (the catalog validates both keys, `09-backend-api/README.md:688`).
