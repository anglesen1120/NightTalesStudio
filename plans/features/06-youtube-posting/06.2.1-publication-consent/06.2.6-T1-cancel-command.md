## Goal

The owner can cancel a publication that has not started uploading, from the app or from the veto-list row: `DELETE /publications/{id}` moves `awaiting_consent|scheduled → cancelled`, releases any quota unit reserved for it, stops the pending upload, and records the audit row. After the upload has started the answer is a 409 that points the UI at YouTube Studio — we never delete videos on the user's channel in MVP (`../../06-youtube-posting.md:87`).

## Design

```csharp
// src/NightTales.Application/Features/Publishing/Commands/CancelPublication/
public sealed record CancelPublicationCommand(Guid PublicationId, string IfMatch) : ICommand<ErrorOr<Deleted>>;
```

Handler:

1. Load owner-scoped: `db.Query<Publication>().Where(p => p.Id == cmd.PublicationId).ForUpdate()` — the row lock is what makes cancel and the upload job mutually exclusive. Absent → 404 `not_found`.
2. `ETags.Matches(cmd.IfMatch, ETags.Publication(xmin))` → else 412 `publication_conflict` (with the current ETag in the response).
3. Already `cancelled` → **204** (idempotent repeat; no second audit/outbox row, no second release).
4. `Publication.Cancel(clock.UtcNow)` — accepts `awaiting_consent` and `scheduled`; `uploading|processing|published|failed` → 409 `publication_invalid_state` (the client shows the copy key `publication.cancel.uploaded_use_studio`).
5. Quota release: read `platform_payload.quotaReservedDay`; when present, `IQuotaLedger.ReleaseAsync(new QuotaReservation(day))` (D10 — release only for a unit YouTube never received; the key is written by `06.2.3-T2` when it reserves and cleared by it on success/failure, so its presence at this point means the reserve is outstanding). When absent there is nothing to release: a row in `awaiting_consent|scheduled` has not passed the upload job's reserve step.
6. Mark the publication's cancel token inert if one is outstanding — not by a new column: the token row's own `used_at` is set by the link path, and this path relies on the status guard the link route already applies (`awaiting_consent` only), so an outstanding token for a cancelled row answers the generic 400 (`06.2.2-T2`).
7. Save (UnitOfWork transaction) — the outbox interceptor writes `publication_updated.v1 { publicationId, episodeId, userId, status: "cancelled" }` (D13); `06.2.2-T3`/02 see the change and stop any pending work. No e-mail is sent on cancel (D7 lists only consent and veto notices).
8. `[Audited("publishing.cancelled", data: { publicationId, episodeId, previousStatus, actor: "user" })]`.

Endpoint (in `PublishingEndpoints`):

```csharp
group.MapDelete("/publications/{id:guid}", CancelPublication)
     .RequireAuthorization().RequireFeature("youtube_publish").RequireIfMatch()
     .Produces(204).ProducesProblem(404).ProducesProblem(409).ProducesProblem(412).ProducesProblem(428);
```

`DELETE` answers 204 (no body, so no DTO/ETag to return). Errors: 404 `not_found`/`feature_disabled`; 409 `publication_invalid_state`; 412 `publication_conflict`; 428 `if_match_required`; 409 `concurrency_conflict` if the `xmin` token loses a race that `If-Match` did not cover (09 UnitOfWork mapping).

Why not a `status = cancelled` special case for the pending Hangfire job: `PublishYouTubeJob` is enqueued with a delay and cannot be un-scheduled reliably; it re-reads the row under lock and refuses to upload anything not `scheduled` with `consent_at` set (`Publication.StartUpload`), so a cancelled publication is skipped by the job — the job is never the source of truth, the row is.

Performance: one row lock, one read, one update, one optional ledger update (`platform_quota_usage` touched by primary key `(platform, quota_day)`); no scan, no N+1, no external call, no Google traffic. Index use: PK lookup + `ix_publications_status_next_attempt_at` untouched by this path.

Security: owner-only through the tenant filter (a foreign publication is a 404, never a 409); the flag gate; `If-Match` prevents cancelling a row the user has not seen the current state of; the audit row holds ids and statuses only; nothing about the publication is logged except its id and previous status.

## Failure handling and edge cases

- Cancel racing the upload job's first step: both take the publication row `FOR UPDATE`. If the job wins, the row is `uploading` and cancel answers 409 (the user is told to use YouTube Studio); if cancel wins, the job re-reads `cancelled` and refuses via `Publication.StartUpload`. No lost-response window creates a second video.
- Cancel racing `AutopilotConsentJob`: the job's claim query requires `status = awaiting_consent` and `veto_ends_at <= now` (`FOR UPDATE SKIP LOCKED`, D8); a cancelled row is not claimed. A job that already claimed the row blocks cancel until it commits, after which cancel sees `scheduled` and still succeeds (the veto's intent is honoured, and the user's cancel wins because it happens later).
- Ledger row missing for the day (the day rolled over between reserve and cancel, i.e. a PT-midnight boundary): `ReleaseAsync` is a no-op and the discrepancy is left to the day rollover — the ledger is a daily counter, not an accounting record; the task must not insert a row for a past day.
- `units_used` already 0 when a release arrives (double release after a crash between the ledger update and the commit): guard the update with `units_used > 0`; the ledger must never go negative.
- `platform_payload` malformed (a hand-edited row or a format change by 06.2.3-T2): treat an unparseable `quotaReservedDay` as absent, log the publication id, and skip the release — never fail the cancel because of a payload parse error.
- Cancel while an open `platform_incidents` row holds the client (D14): allowed; the publication was never uploaded, so no incident interaction exists.
- Cancel after the owner disconnected the channel: the disconnect path (06.4.1-T1) already cancelled the row; this route answers 204 idempotently.
- Cancel of a publication whose episode was deleted (cascade): 404 `not_found`.
- `DELETE` retried after a lost response: 204 both times, exactly one audit and one outbox row.

## Notes

- `[OPEN]` for the TL: `platform_payload.quotaReservedDay` as the second `platform_payload` key (owned by `06.2.3-T2`), versus an `IQuotaLedger.TryReleaseForPublicationAsync(publicationId, ct)` on the ledger side. The first keeps the ledger dumb (D10's stated API) and needs no signature change; the second needs a new ledger column/row mapping and touches `06.3.1-T1`.
- This task is the only cancel implementation: 06.4.1-T1 (disconnect) and 06.2.2-T2 (cancel-by-link) reach the same `Publication.Cancel` domain method; only the caller identity in the audit row differs (`user`, `system:disconnect`, `system:link`).
- No episode status change on cancel: the episode returns to its pre-publication state only through 02's own flow (`Episode.MarkScheduled` is the D12 call, and its reversal is 02's, not ours) — recorded here so 02's fallback tick owns the retry decision after a cancel.
