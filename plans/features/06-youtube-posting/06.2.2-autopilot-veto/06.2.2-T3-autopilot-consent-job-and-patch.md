## Goal

When an autopilot publication's veto window ends and the owner did not object, the platform records the consent that authorizes the upload — but only if the owner actually received the notice, the series is not paused, the authorization is current and the channel is connected. In the same window the owner can still edit the post; a passing edit is itself the owner's consent. Both paths are owner-only, ETag-guarded, idempotent and audited with ids only.

Deliverables: the recurring `AutopilotConsentJob` + its Application handler, `PATCH /publications/{id}` with full metadata re-validation and the moderation gate, two `Publication` domain behaviours, one narrow reader port, and one expand-only index migration.

## Design

### Domain (`src/NightTales.Domain/Publishing/`)

`ConsentFromAuthorization(string textVersion, Guid authorizationId, DateTimeOffset now)` is **already declared and implemented by 06.2.1-T1** (`06.2.1-T1-publication-aggregate.md:59`; reused verbatim by `AutopilotConsentJob` per that file's own text, `plan.md:251`) — **this task calls it, it does not redeclare it**, and uses its real argument order (`textVersion` first). It does not touch `next_attempt_at`, so 06.2.3-T2's handler falls back to `QueueTime` exactly like the manual-consent path — no separate fix needed here since this task adds no such effect.

```csharp
// Publication.cs — added here; veto_ends_at has no mutator (immutable after create); instance methods,
// same shape as the aggregate's existing Cancel(now) (06.2.1-publication-consent/plan.md:81).
// PreAudit (bool) is 06.2.1-T1's own read-only property, set once at create (F-21) — this task reads it,
// never writes platform_payload.preAudit/requestedPrivacy directly.
public ErrorOr<Success> MarkNoticeDelivered(DateTimeOffset now);                              // UC-1a

public ErrorOr<Success> ApplyOwnerEdit(
    PublicationMetadata metadata, string consentTextVersion, DateTimeOffset now, bool implicitConsent); // UC-2
// Privacy is permanently frozen while PreAudit (F-21, plan §3.1 I9, confirmed permanent 2026-09-25):
//   PreAudit && metadata.Privacy != "private" -> refuses the WHOLE edit, PublicationPrivacyLocked (O-2)
//   PreAudit && metadata.Privacy == "private" -> proceeds; Privacy is a no-op
//   !PreAudit                                 -> publications.privacy = metadata.Privacy
// Never writes platform_payload.preAudit or .requestedPrivacy (06.2.1-T1 owns both).
```

**Aggregate ownership, pinned with 06.2.1-T1 (2026-09-25):** `Publication.cs` has one writer per method; `06.2.1-publication-consent/plan.md:283` only asserts that `ConsentFromAuthorization` writes `consent_source = autopilot`, it does not declare the method, so this task adds all three methods above.

`MarkNoticeDelivered` refuses when `veto_notice_sent_at is not null` (idempotent) or `status != AwaitingConsent`; effect: `veto_notice_sent_at = now`, no status change, no domain event (it is not a consent). The handler checks `veto_notice_sent_at is not null` and `authorizationId == publication.AutopilotAuthorizationId` **before** calling 06.2.1-T1's `ConsentFromAuthorization` (that method has no notice-delivery concept of its own, I2). `ApplyOwnerEdit` refuses outside `{AwaitingConsent, Scheduled}`, refuses when `external_post_id is not null`, refuses the **whole** edit with `PublicationPrivacyLocked` when `PreAudit && metadata.Privacy != "private"` (permanent freeze, F-21, I9 — no partial write, not even to title/description/tags), never writes `veto_ends_at`, and when `implicitConsent && status == AwaitingConsent` writes `consent_at/consent_text_version/consent_source = "user"` and moves to `Scheduled`. New domain events (only from the latter two): `PublicationConsented(PublicationId, EpisodeId, UserId, Source)`, `PublicationEdited(PublicationId, EpisodeId, UserId, Status)` → 09.1.2's interceptor puts `publication_updated.v1` on the outbox.

### Application

**No new port.** Both claims reuse 09's pinned cross-tenant bypass `ISystemWorkQuery.PendingAsync<Publication>(predicate, batch, ct)` (`Application/Abstractions/ISystemWorkQuery.cs`, impl `Infrastructure/Persistence/Queries/SystemWorkQuery.cs`; wave-1 member at `09.2.3-T1:36`, "no port widening" at `09.2.6-T3:107`); it takes no `ORDER BY` and no lock hint ([OPEN] plan §10 O-12, a wording gap in README D8). Per-row work reloads through 09's `IAppDbContext` (`db.Query<Publication>()`, tenant filter for free, `09.4.2-5.3/plan.md:196`) inside the owner's `SystemContext`, where `FOR UPDATE` plus the `xmin` token decide any race.

`src/NightTales.Application/Features/Publishing/Commands/StampDueNoticeDelivery/{StampDueNoticeDeliveryCommand.cs,StampDueNoticeDeliveryHandler.cs}` (UC-1a, F-2a — **must run before UC-1b in every tick**, see Job below):

Claim predicate — deliberately **no `veto_ends_at`**, only "not yet stamped": `p => p.Status == PublicationStatus.AwaitingConsent && p.VetoNoticeSentAt == null && p.PlatformPayload.VetoNoticeEmailId != null`. `src/NightTales.Application/Features/Publishing/Commands/ConsentDueAutopilotPublications/{ConsentDueAutopilotPublicationsCommand.cs,ConsentDueAutopilotPublicationsHandler.cs}` (UC-1b, §4 of the plan for the record shapes) — claim predicate `p => p.Status == AwaitingConsent && p.AutopilotAuthorizationId != null && p.VetoEndsAt <= now`; per row, after the reload: five checks (status still `awaiting_consent`, `veto_notice_sent_at is not null` — normally already true from UC-1a, series not paused, authorization current, connection active) → `ConsentFromAuthorization` → audit → outbox.

`src/NightTales.Application/Features/Publishing/Jobs/AutopilotConsentJob.cs` (F-22 convention): runs both commands in order every tick; see Job below.

`src/NightTales.Application/Features/Publishing/Commands/EditPublication/{EditPublicationCommand.cs,EditPublicationHandler.cs,EditPublicationValidator.cs}` (UC-2) — record + handler + FluentValidation validator, using 02.4.1-T1's `IContentModerator.CheckAsync(IReadOnlyList<string> texts, ModerationStage stage, ct)` (`02.8.2-T2:60`) with `ModerationStage.AutopilotGate` over `[title, description, ...tags]`. **There is no publication-gate method**: `IAutoApprovalGate` exposes only `EvaluateStoryAsync`/`EvaluateVideoAsync` (`02.8.2-T1:48-49`), and `02.8.2/plan.md:15` puts publication/consent explicitly out of that feature's scope — 06 owns the *call*, 02 owns the moderator and its verdict.

### Job (Worker)

```csharp
[JobPolicy(Queue = JobQueue.Publish, Retries = 3)]   // "publish" per D8; JobQueue member name is 09's
public sealed class AutopilotConsentJob(ISender sender)
{
    public async Task RunAsync(CancellationToken ct)

        await sender.Send(new StampDueNoticeDeliveryCommand(), ct);          // UC-1a first, every tick
```

### Infrastructure

### Authorisation, idempotency, audit

Owner-only load (`WHERE id = @id AND user_id = @currentUser`; a miss is a uniform 404). Feature flag on both the route and the registration. `If-Match` mandatory (428) and compared with `ETags.Matches` (strong, exact); stale → 412 `publication_conflict` ([OPEN] O-2), `xmin` race → 409 `concurrency_conflict` (09 D5). Consent is idempotent by the `consent_at is null` guard plus the conditional `status = 'awaiting_consent'` write; `MarkNoticeDelivered` is idempotent by its own `veto_notice_sent_at is not null` guard; a lost update is caught as `DbUpdateConcurrencyException` and counted as a skip, never as an error. Audit: `publishing.consent_autopilot` (job) and `publishing.consented` (implicit edit consent) with `{ publicationId, authorizationId, consentTextVersion }`; a post-consent metadata edit uses the action of O-1. `MarkNoticeDelivered` writes **no** audit row — it is not a consent. Logs carry ids and the skip reason only.

## Acceptance checks

- [ ] With the flag off: `PATCH /api/v1/publications/{id}` → 404 `feature_disabled` and `autopilot-consent` is absent from the recurring-job set.
- [ ] A due publication (`status = awaiting_consent`, `veto_ends_at <= now`) whose notice is `EmailStatus.Sent` → after one job run: `status = scheduled`, `consent_at` set, `consent_text_version = YouTubeOptions.ConsentTextVersion`, `consent_source = autopilot`, `veto_notice_sent_at` set, one `publishing.consent_autopilot` audit row and one `publication_updated.v1` outbox row `{ publicationId, episodeId, userId, status = "scheduled", errorCode = null }` (agreed with 06.2.1-T1's consent handler 2026-09-25; no title, no channel name).
- [ ] The same row with `EmailStatus.Queued` (or no `victoNoticeEmailId`) → unchanged after the run (`status`, `consent_at` still null), skip counter `notice_undelivered` incremented, **no audit and no outbox row**.
- [ ] `series.autopilot_paused_at IS NOT NULL` → unchanged, skip counter `series_paused` (02.8.3-T4's CR is satisfied).
- [ ] `series.current_autopilot_authorization_id != publication.autopilot_authorization_id`, or `revoked_at IS NOT NULL` → unchanged, skip counter `authorization`.
- [ ] Connection not `active` → unchanged, skip counter `connection`.
- [ ] Running the job twice back-to-back consents each row exactly once (second run: `SkippedCandidates` counts it, no second audit row, no second outbox row).
- [ ] 120 due rows → first run consents 50, second run 50, third run 20 (batch cap observable in the counters).
- [ ] `PATCH` a `awaiting_consent` row with a valid body and the current `ETag` → 200, fields persisted, `status = scheduled`, `consent_at` = the edit time, `consent_source = user`, new `ETag` in the response header; the same request replayed with the **old** `ETag` → 412 `publication_conflict`.
- [ ] `PATCH` without `If-Match` → 428 `if_match_required`; `PATCH` on another user's publication id, and on a non-existent id, both → 404 with the same body shape.
- [ ] `PATCH` on a `preAudit`-locked row (`platform_payload.preAudit = true`) requesting a `privacy` other than `"private"` → 409 `publication_privacy_locked` (O-2), **no** field written at all (title/description/tags/publishAt included), `platform_payload.requestedPrivacy` untouched.
- [ ] `PATCH` on the same `preAudit`-locked row submitting `privacy = "private"` (no real change) → 200, every other field (title/description/tags/publishAt) updates normally.
- [ ] `PATCH` on a `uploading`/`processing`/`published` row, or on a `scheduled` row with `external_post_id` set → 409 `publication_invalid_state` ([OPEN] O-5) and **no** field change.
- [ ] `PATCH` with title 101 chars, a `<` in the description, a description of 4,999 bytes + attribution pushing it over 5,000, or tags over the G4 count → 400 `validation_failed` with `errors` keys `title`/`description`/`tags`; nothing persisted.
- [ ] `PATCH` moving `publish_at` earlier so that `min(now + veto_window_hours, publishAt − PublishLeadMinutes) − now < MinVetoWindowHours` → 400 `validation_failed`, `errors.publishAt`, `veto_ends_at` unchanged (YR1 corollary).
- [ ] `PATCH` whose body passes metadata but `IContentModerator.CheckAsync(…, ModerationStage.AutopilotGate, …)` returns a blocking category → 400 `validation_failed` with `errors.moderation` listing the categories (O-11); publication unchanged.
- [ ] `EXPLAIN` on UC-1b's claim (`PendingAsync<Publication>` over the due-consent predicate) shows `Index Scan using ix_publications_veto_scan`; `EXPLAIN` on UC-1a's claim shows `Index Scan using ix_publications_veto_notice_pending`; a 1,000-row fixture run issues no per-row series/connection query outside the context load.
- [ ] A publication created with `veto_window_hours = 12` whose notice becomes `EmailStatus.Sent` gets `veto_notice_sent_at` stamped within one job tick — **not** 12 hours later — and never trips 02.8.3-T4's 30-minute pause trigger (`_VetoNoticeUndelivered`) in a run that advances `FakeClock` past 30 minutes with the notice delivered early.
- [ ] A publication whose notice is still `EmailStatus.Queued` at the 30-minute mark is left untouched by both passes (no stamp, no consent, no cancel); 02's own pause logic is exercised in 02.8.3-T4's suite, not duplicated here.
- [ ] No log line, audit row or exception message produced by these paths contains a title, a description, a tag or an e-mail address.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Notice `Queued`/`Sending`/`Failed` | skip, no write, retried next minute; the row stays `awaiting_consent` (never a silent upload) |
| Notice delivered but the job crashes before commit | nothing was written (one transaction per user); the next tick re-reads and consents |
| Two job instances at once | the orchestrator's claim (`ISystemWorkQuery.PendingAsync`) holds no lock; each per-row command (`ConsentAutopilotPublicationCommand`/`StampNoticeDeliveredCommand`) reloads `FOR UPDATE` and relies on the `xmin` concurrency token → one winner, the other counts a skip (O-9) |
| Owner PATCH/consent in the same second as the job | phase B's `FOR UPDATE` + status re-check sees the new status → skip |
| Series paused mid-batch | rows after the pause are skipped in the same run (the state is read per row) |
| Publication already `cancelled` (06.2.6-T1 or 06.4.1-T1) | status re-check → skip; no consent on a cancelled row |
| Authorization revoked between claim and write | the per-row reload (`db.Query<Publication>()` joined with the series/authorization/connection state) reads it in the same transaction as the write → skip |
| `EmailDeliveryStatus` read fails (DB error) | the whole per-user transaction fails → Hangfire retry; no partial consent |
| Row stuck due for weeks (`notice_undelivered`) | the job keeps skipping; the alert of [OPEN] O-4 (`YouTube:Veto:MaxHoldDays`) fires; the job never cancels on its own |
| `PATCH` on a row whose episode was reopened/story changed (02.8.3 cancels it) | 409 invalid state after the cancel; the client refetches |
| `PATCH` with an `ETag` from a `GET` of a different publication | `ETags.Matches` compares the value, not the row → the `xmin` compare on write fails → 412/409, never a wrong-row write |
| Clock skew between Worker hosts | `now` always comes from the injected `IClock`, never `DateTimeOffset.UtcNow`; `veto_ends_at <= now` uses the DB clock in the claim query (`now()`), so a skewed host cannot consent early |
| Migration fails on `CONCURRENTLY` (inside a transaction) | startup fails loudly; the migration is marked `suppressTransaction` and the rollout note in the plan tells the operator to drop an invalid index (`DROP INDEX CONCURRENTLY`) and redeploy |
