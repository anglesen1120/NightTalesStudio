## Goal

The owner must be able to authorize an upload with one tap from the veto notice itself, without hunting for the Studio. This task adds the deterministic approve deep link, the notice's "Approve now" call to action and the proof that the path works **independently of series-level authorization** — the owner's accepted fallback (README §10 O3) when the audit does not accept one authorization covering many videos.

Deliverables: the `AuthLinks.PublicationApprove` helper (under the already-open 06 CR-6 to 09.3.3-T1), the `{{approve_url}}` catalog key filled at send time by 06.2.2-T2's notice minter, the notification's deep link, the page contract handed to plan 10, and the end-to-end + fallback tests.

## Design

### The link (one helper member, no new port, no new key)

```csharp
// src/NightTales.Application/Features/Auth/Password/AuthLinks.cs — added under 06 CR-6,
// next to T2's PublicationCancel; same shape as the existing PasswordReset/VerifyEmail members.
public static string PublicationApprove(Uri origin, Guid publicationId, Guid episodeId) =>
    $"{origin.GetLeftPart(UriPartial.Authority)}/publications/approve#p={publicationId:D}&e={episodeId:D}";
```

- Origin: the existing 09-owned `App:PublicOrigin`, already supplied to minters at send time (`09.2.6-T3:109`). **No new configuration key**, no 06-local options object, no DI port — the helper is a pure static like its siblings, so Api and Worker share one implementation.
- `GetLeftPart(UriPartial.Authority)` normalises any configured origin form (trailing slash, path, port) into the same absolute prefix, exactly as `PasswordReset` does.
- The two ids live **in the fragment**, after `#`, like the token of the reset/cancel links: a fragment is never sent to a server, never reaches an access log and never becomes a `Referer`. No token is minted: the cancel link is plan 06's only capability URL (D7), and an approve action is safe behind the owner's own bearer session. `#p=` (publication) and `#e=` (episode) — the page needs the episode because the only read route is episode-scoped (00 §8:362).

### Notice template and send-time rendering

- The `publication_veto_notice` catalog entry (owned by 06.2.2-T2) gains **one** placeholder, `{{approve_url}}`, in its `Keys` set and in all four embedded files (`vi`/`en` × `txt`/`html`), rendered as a primary button above the cancel link. `EmailTemplateProvider.ValidateOrThrow()` (09.2.6-T3:95) fails the boot if the key or a file is missing, so the change cannot ship half-applied.
- The value is filled **at send time by the same minter** that produces the cancel link, from `App:PublicOrigin` (WT17) and the message's ids. `approve_url` is token-free; it therefore never enters `email_messages.params` or the outbox payload, whose allow-list stays exactly as WT30 pinned it (no new allow-list key, no new minter class).
- 06.2.2-T2's queueing decision is unchanged; this task states the requirement it relies on: the notice is queued whenever `veto_ends_at` is set, **also in per-video fallback mode** (where `autopilot_authorization_id` is null), because that row is exactly the one the owner must approve in the O3 fallback.
- The in-app notification (`PublicationVetoNotice`, 10.7.1) carries the same URL from the same helper, so both channels lead to the same action.

### Approve page contract (handed to plan 10, not implemented here)

`{App:PublicOrigin}/publications/approve#p={publicationId}&e={episodeId}` — the page is plan 10 wave 2's ([OPEN] O-3 records the CR, because plan 10 owns web routes):

1. Requires a session; a signed-out visitor goes to sign-in and returns to the full link (the client preserves the fragment).
2. Resolves the row from `e` through `GET /api/v1/episodes/{e}/publications` (D6 contract; 404 `feature_disabled` hides the action).
3. Reads `p` from the fragment; unknown or absent id → the `publication.approve.expired` copy, no request.
4. `POST /api/v1/publications/{p}/consent { consentTextVersion }` with `If-Match: <row.etag>`; 200 → `publication.approve.done`; 400 `consent_text_outdated` → refetch and retry once with the current text version; 409 → refetch and show the state message; 412 → `ConflictDialog`.
5. The action is idempotent server-side, so a double tap, a back-then-forward or a restored tab never produces a second consent.

### Fallback semantics (O3) — the acceptance of this task

`POST /publications/{id}/consent` is guarded by the publication's status and the consent text version only; it does **not** consult `series.current_autopilot_authorization_id`. Therefore:

- a series whose authorization was revoked, or for which the audit will not accept series-level authorization, still ships per-video notices with a working Approve now (the owner taps once per video);
- `AutopilotConsentJob` (06.2.2-T3) skips those rows (no current authorization ⇒ no automatic consent), so the two paths can never both fire;
- the approve path also works **after** `veto_ends_at` while the row is still `awaiting_consent` (a notice that was never delivered, plan [OPEN] O-4), so the owner is never locked out of their own publication.

## Acceptance checks

- [ ] `AuthLinks.PublicationApprove(new Uri("https://app.example/"), p, e)` returns exactly `https://app.example/publications/approve#p=<p:D>&e=<e:D>`; the same result for `https://app.example`, `https://app.example/` and `https://app.example/anything` (authority-only prefix, no double slash, no path).
- [ ] The returned string contains no query string, no token and no title; both ids are after the `#`.
- [ ] The link is invariant across cultures (invariant GUID formatting) and identical for `vi` and `en` renderings of the same message.
- [ ] Changing `App:PublicOrigin` changes the approve link, the cancel link and the reset link together; one notice never mixes two origins.
- [ ] `EmailTemplateProvider.ValidateOrThrow()` passes with the notice catalog entry: `approve_url` is in `Keys` and all four files exist; removing the key from `Keys` or deleting one file fails the boot (proved by the test).
- [ ] `email_messages.params` for a queued notice contains no approve/cancel URL and no token (WT30), and the notice row still renders both links.
- [ ] End-to-end from the built link: `GET /api/v1/episodes/{e}/publications` → the row is `awaiting_consent` → `POST /api/v1/publications/{p}/consent { consentTextVersion }` with `If-Match: row.etag` → 200, `status = scheduled`, `consent_at` set, `consent_source = user`, one `publishing.consented` audit row, one `publication_updated.v1` outbox row, the `publication_consented` e-mail queued, and the response `ETag` advanced.
- [ ] Repeating that POST (double tap) → 200 no-op; still exactly one audit row and one outbox row.
- [ ] **Fallback:** a publication with `autopilot_authorization_id IS NULL` (per-video mode, O3) in `awaiting_consent` with a sent veto notice → the approve flow consents it (`consent_source = user`), and a later `AutopilotConsentJob` run leaves it alone (already `scheduled`, no `consent_autopilot` audit row).
- [ ] **Late approval:** a row still `awaiting_consent` whose `veto_ends_at` is in the past (undelivered notice) → approve succeeds and the row becomes `scheduled`.
- [ ] A stale `consentTextVersion` → 400 `consent_text_outdated`; a foreign or nonexistent publication id → 404; the flag off → the notice is never queued and `POST …/consent` → 404 `feature_disabled`.
- [ ] The approve request's log line and its audit row carry ids and codes only — no fragment, no title, no e-mail address.
- [ ] The `PublicationVetoNotice` notification payload carries the identical URL the e-mail carries.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Link opened while signed out | sign-in first, then the same link (fragment preserved); nothing is consented before a session exists |
| Mail client prefetches the URL | harmless: the fragment is never sent, so the prefetch reaches only the page shell and triggers no action |
| The job consented a second earlier | the page finds `scheduled` + the same text version + `consent_source = autopilot`; per 06.2.2-T1 this is not the user path, so the page refetches and shows the state message — no duplicate consent, no error storm (`errors.publication_invalid_state`) |
| Publication cancelled (owner, 06.2.6-T1, or disconnect 06.4.1-T1) | 409 → refetch; the row is gone from the veto list |
| `p` and `e` from different episodes (hand-edited link) | the row lookup by `p` inside the episode's list fails → unknown id ⇒ `publication.approve.expired`; the API never consents a row the episode did not return |
| Consent text version changed while the mail sat in the inbox | 400 `consent_text_outdated`; the page refetches, shows the current text version and retries once |
| `App:PublicOrigin` misconfigured | it is already required by the e-mail minter (`09.2.6-T3:109`) and CORS (09 BD12), so a bad value fails the boot / the send, never a relative link |
| Notice queued but never delivered (O-4) | the owner can still approve late from the Studio row (10.4.3-T2) or from the mail once it arrives; this task adds no re-send and no reminder |
| Flag off mid-session | the page hides the action and refetches `/me` (10.4.3-T2 pattern); the link then answers 404 `feature_disabled` |
| Template key added but a locale file missed | `EmailTemplateProvider.ValidateOrThrow()` stops the boot (all four files are checked) — the change cannot ship half-applied |

## Notes

- **No new route, no new port, no new configuration key.** Everything runs through `POST /publications/{id}/consent` (00 §8:362); this task adds one static helper member, one catalog key with its send-time value, and the fallback proof — which is why it is XS. It deliberately does **not** introduce an `IPublicationApproveLinkBuilder` or an Infrastructure class: `AuthLinks` is the established link-shape home (`09.3.3-T1:76`) and the 06 CR-6 already opens it for 06's publication links.
- **[OPEN] O-3 (CR to plan 10):** the page route `/publications/approve` and its two copy keys (`publication.approve.done`, `publication.approve.expired`) belong to plan 10 wave 2. Until they exist, the notice's approve link is still satisfiable through the veto list of 10.4.3-T2 (same publication id, same action), and 06.5.1-T1's evidence pack records the received mail plus the row action. The origin needs no decision: it is `App:PublicOrigin` ✅ (`09.2.6-T3:109`).
- Do not add an approve token (D7 keeps the cancel link as the only capability URL) and do not add an allow-listed `approve_url` param: both links are produced at send time by the notice minter, which keeps `email_messages.params` token-free (WT30).
- The `{{approve_url}}` addition must keep the catalog `Keys` and the renderer's values in sync; `NoticeTemplate_ApprovePlaceholder_InKeys_AllFourFiles_Vi_And_En` is the guard, and it is the same class of check the W2 CR-6 lesson (every `{{key}}` supplied) demands.
