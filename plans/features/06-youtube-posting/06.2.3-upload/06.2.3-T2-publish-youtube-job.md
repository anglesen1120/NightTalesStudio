## Goal

A publication that has consent and `status = scheduled` becomes a YouTube video, exactly once, even when the network dies after the last chunk. `PublishYouTubeJob` (queue `publish`, 5 retries) locks the row, reconciles instead of re-uploading when `external_post_id` is already set, refuses any upload without `consent_at`, holds when an OAuth incident is open, reserves one quota unit, refreshes the access token under a row lock, persists the **encrypted** session URI before the first byte, streams the MP4 from object storage, and maps every Google failure to a publication transition, an `error_code`, a `next_attempt_at` and an outbox event (plan §7).

## Design

### Job and command

```csharp
// src/NightTales.Application/Features/Publishing/Jobs/PublishYouTubeJob.cs
[JobPolicy(Queue = JobQueue.Publish, Retries = 5)]
public sealed class PublishYouTubeJob(ISender sender, ILogger<PublishYouTubeJob> log) : IBackgroundJob
{
    public async Task RunAsync(Guid publicationId, CancellationToken ct);   // ids only (arch rule Jobs_TakeIdsOnly)
}

// src/NightTales.Application/Features/Publishing/Upload/PublishYouTubeCommand.cs
public sealed record PublishYouTubeCommand(Guid PublicationId) : IRequest<ErrorOr<UploadOutcome>>;
public enum UploadOutcome { Processing, Rescheduled, HeldByIncident, ReauthRequired, Failed, Reconciled }
```

`PublishYouTubeJob.RunAsync` sends the command and logs the returned `UploadOutcome`; a domain-level error (`not_found`, `validation_failed`, `feature_disabled`) is logged and swallowed (a deleted or flag-disabled row must never retry 5×); a thrown transport exception propagates so Hangfire's attempt counter applies.

### Handler (plan §4 UC1, in order)

```csharp
// src/NightTales.Application/Features/Publishing/Upload/PublishYouTubeHandler.cs
public sealed class PublishYouTubeHandler(
    IAppDbContext db, ITokenService tokens, IYouTubeClient youtube, IBlobStore blobs,
    IQuotaLedger quota, IPlatformIncidentStore incidents, IFeatureFlags flags, IClock clock,
    IUnitOfWork uow, ILogger<PublishYouTubeHandler> log) : IRequestHandler<PublishYouTubeCommand, ErrorOr<UploadOutcome>>;
```

1. flag (`IFeatureFlags`, key `youtube_publish`) → `NotFound(ErrorCodes.FeatureDisabled)`;
2. `ISystemWorkQuery` (the wave-1 pinned member) resolves `(id, user_id)`; `db.Publications` (`IAppDbContext`) reads the row with `SELECT … FOR UPDATE` and loads its `Episode` (title) + the `final_video` asset (`storage_key`, `size_bytes`); missing → `NotFound(ErrorCodes.PublicationNotFound)`. **No `IPublicationRepository` port exists**: 06.2.1-T1 persists through `AppDbContext`/`DbSet<Publication>` (`06.2.1-T1-publication-aggregate.md:202-203`), so this task uses the same seam (CR-20);
3. `external_post_id IS NOT NULL` → `youtube.GetVideosAsync` → `MarkUploadedExternal`/terminal mapping (no second upload, F02); otherwise **YR27-1 early-run guard**: `next_attempt_at IS NOT NULL AND next_attempt_at > clock.UtcNow` → return `Rescheduled` as a no-op, no quota/state touch (guards a duplicate or early outbox redelivery);
4. `Publication.StartUpload(now)` (refuses without `consent_at`; `scheduled` → `uploading`; `uploading` → no-op "resume" so a retry after a lost response reaches step 8's probe/resume (YR18); a `processing`/`failed`/`published`/`cancelled` row returns the current outcome as a no-op);
5. `var openIncidentId = await incidents.HasOpenIncidentAsync("youtube", connection.OAuthClientId, ct)`; non-null → `Publication.HoldForIncident(openIncidentId.Value, clock.UtcNow + TimeSpan.FromSeconds(5 * options.Poll.IntervalSeconds))` (YR24: deferred, never `null`) (no Google call, no quota);
6. **YR27-2**: `platform_payload.quotaReservedDay` already set (a resume) → skip straight to **step 7** (the token is still needed before step 8 builds the request), no reserve. First `userQuota.TryReserveAsync(publication.UserId, clock.UtcNow, ct)` (**ST1: the per-user slot is taken before the global unit**); `user_upload_limit_reached` → `RescheduleUpload(PublicationErrorCodes.UserUploadLimitReached, NextPtMidnight(clock) + jitter(≤ 10 min))` and **no** global reserve in this run; on success set `reservedUserThisRun = true`, then otherwise `quota.TryReserveAsync("youtube", clock.UtcNow, ct)`, and on success set `reservedThisRun = true`; `youtube_quota_exhausted` → `RescheduleUpload(PublicationErrorCodes.QuotaExhausted, NextPtMidnight(clock) + jitter(≤ 10 min))`; (06 CR-13)
7. `ITokenService.GetAccessTokenAsync(connectionId, ct)` (the one shared refresh path, F12; row-locked, below);
8. `VideoInsertRequest` from **`platform_payload.upload` verbatim** (F13: `privacyStatus`, `publishAt?`, `preAudit`; never from live `YouTubeOptions.AuditStatus`), `length = assets.size_bytes` with the nullable `BlobObject.Length` only cross-checked (F14/CR-18 — a disagreement fails before any Google call); session: `platform_payload.uploadSessionEnc` → `Unprotect` + `ProbeUploadAsync` (`Complete` → step 10; `Partial(n)` → `UploadStreamPositioning.EnsureAtAsync(stream, n, ct)` then `ResumeUploadAsync` (the client reads from the stream's current position and starts the first `Content-Range` there); `Expired` → **YR27-3: reserve a fresh unit first** (`quota.TryReserveAsync` again — a restart is a new `videos.insert`, even if step 6 skipped the reserve under YR27-2; on success here set `reservedThisRun = true`) — a reserve failure here goes to the same `youtube_quota_exhausted` branch as step 6; on success `StartUploadAsync` opens the new session and overwrites `platform_payload.quotaReservedDay`) → step 9; absent → `StartUploadAsync(token, request, length)`, persist the protected session URI and commit before the first byte (`AttachUploadSession` + `CommitAsync`);
9. `blobs.OpenReadAsync(StorageBuckets.Media, asset.StorageKey, ct)` → `ResumeUploadAsync`; the stream is disposed in `finally`;
10. `MarkProcessing(videoId)` — writes `platform_payload.processing { startedAt = now, deadlineAt = now + Poll:MaxMinutes, polls = 0 }` for 06.2.5-T1's poller and clears `platform_payload.quotaReservedDay` — → `ErrorOr` `Processing`; `uow.CommitAsync()` once.

**Release semantics (YR19, corrected).** The quota reservation is released in `finally` **only** when `reservedThisRun == true` **and** either `sessionCreateSent == false` (no session-create call was issued *in this run* — the flag is set the instant `StartUploadAsync` is issued, not when it succeeds, so a rejected session-create still counts as "sent") **or** the classification is `quotaExceeded`/`uploadLimitExceeded`. `reservedThisRun` is set only where step 6 or step 8's restart actually calls `TryReserveAsync` — a resume that skipped step 6 under YR27-2 leaves it `false`, so a probe/resume failure in that run can never release a unit an *earlier* run already consumed (the original YR19 text checked `sessionCreateSent` alone, which had that bug). The step-5 incident gate is separate: it short-circuits before step 6 reserves anything, so nothing is released there — `HoldForIncident` never touches the ledger. The **per-user** reservation is released on exactly the same branch and conditions (`reservedUserThisRun == true` and the same predicate), so the per-user counter and the global unit move together (**ST2**, F25); step 8's session-404 restart also re-reserves both. (06 CR-13b)

### Token refresh under lock

**One refresh path, owned by 06.1.2-T2.** D9 names `ITokenService.GetAccessTokenAsync(connectionId)` (`../README.md:120`), and 06.1.2-T2 already declares and ships it — "the token columns through `ITokenService.GetAccessTokenAsync(connectionId)`", "the purpose string is the contract" (`06.1-connect/06.1.2-T2-channel-connection.md:110, 183`); 06.2.5-T1 and 06.4.1-T1/06.4.2-T1 consume the same member. 06.4.2's plan §10.1 still records the declaring task as an [OPEN] — stale, closed by CR-19 against this evidence. This task **consumes** it and declares no parallel port:

```csharp
// consumed, not declared here — implemented by 06.1.2-T2:
//   Task<ErrorOr<ChannelAccessToken>> ITokenService.GetAccessTokenAsync(Guid connectionId, CancellationToken ct)
//   ChannelAccessToken(string AccessToken, DateTimeOffset ExpiresAt)
```

06.1.2-T2's implementation: `SELECT … FOR UPDATE` on the `channel_connections` row, **re-read after the lock** (F21) → if `token_expires_at - clock.UtcNow < 5 min`, `IOAuthClientResolver.ResolveAsync(oauth_client_id, ct)` → `IYouTubeClient.RefreshAsync(refresh_token, client, ct)` → persist `access_token_enc`/`token_expires_at` (and the rotated `refresh_token_enc` when the response carries one) → commit. The loser of the lock re-reads the fresh token and issues **no** second refresh grant, so a refresh token is never presented twice (F21 → Google revocation). `invalid_grant` → connection `expired` + `channel_connection_changed.v1`; `invalid_client`/`unauthorized_client` → incident (via the store, this task's `IPlatformIncidentStore`).

### Aggregate transitions (seven additions to 06.2.1-T1's `Publication`)

06.2.1-T1 **already declares** `Publication.StartUpload(DateTimeOffset now)` (`06.2.1-T1-publication-aggregate.md:58`): rely on it, do not redeclare it. This task adds `AttachUploadSession`, `MarkProcessing`, `MarkUploadedExternal`, `RescheduleUpload`, `FailUpload`, `HoldForIncident`, `ReleaseHold` (**seven** additions — YR27-4 adds `ReleaseHold`) with the preconditions of `plan.md` §3.1 (CR-20: 06.2.1-T1 owns the aggregate; if it prefers to own all of them, this task calls its members and adds nothing); each raising a `[OutboxEvent("publication_updated.v1")]` `PublicationUpdated { PublicationId, EpisodeId, UserId, Status, ErrorCode? }` domain event (D13, unchanged shape) so the interceptor writes the outbox row in the same transaction. `RescheduleUpload` sets `next_attempt_at` (the quota-reschedule case, UC1 step 6) so `PublicationScheduledForUploadHandler` (below) re-enqueues the job — a reschedule with no re-enqueue path would strand the row `scheduled` with nothing to wake it (TL-flagged 2026-09-25); `HoldForIncident(Guid incidentId, DateTimeOffset nextAttemptAt)` sets a **deferred** `next_attempt_at` (YR24: `now + 5 × Poll:IntervalSeconds`, never `null`) and `platform_payload.heldByIncidentId = incidentId`, which is what makes the hold self-checking rather than a hot loop (plan.md UC4). `Publication.Published`/`Cancelled` from 06.2.2 remain untouched. `platform_payload` is mutated through a typed helper (`PublicationPayload.With(...)`) rather than string JSON in the handler, so the keys of `plan.md` §3.2 are written in one place. Error codes are `PublicationErrorCodes` constants (`src/NightTales.Domain/Publishing/PublicationErrorCodes.cs`, YR27-6) — `QuotaExhausted`, `ChannelReauthRequired`, `PlatformIncident`, `UploadFailed`, `Rejected` — used everywhere in this folder instead of raw string literals.

### Incidents (table + port, CR-22)

`Domain/Publishing/PlatformIncident.cs`, `Infrastructure/Persistence/Configurations/PlatformIncidentConfiguration.cs` (partial unique `(platform, oauth_client_id) WHERE cleared_at IS NULL`), migration `…_06_PlatformIncidents.cs` (DDL exactly as `plan.md` §3.3), and:

```csharp
// src/NightTales.Application/Abstractions/Publishing/IPlatformIncidentStore.cs
public sealed record PlatformIncidentRaiseResult(Guid IncidentId, bool IsNew, int AffectedConnections);
public sealed record PlatformIncidentClearResult(Guid IncidentId, bool AlreadyCleared, int PublicationsRescheduled, bool Remaining = false);   // Remaining = true: MaxBatches hit or a batch failed — the incident is intentionally left open (06.2.3-T3)

public interface IPlatformIncidentStore
{
    Task<ErrorOr<PlatformIncidentRaiseResult>> RaiseAsync(string platform, string oauthClientId, string errorCode, DateTimeOffset now, CancellationToken ct);
    Task<ErrorOr<Guid?>> HasOpenIncidentAsync(string platform, string oauthClientId, CancellationToken ct);   // null = no open incident; non-null is that incident's id, needed by HoldForIncident
    Task<ErrorOr<PlatformIncidentClearResult>> ClearAsync(Guid incidentId, string @operator, string note, DateTimeOffset now, CancellationToken ct);   // YR16: cleared_by = @operator
}
```

`RaiseAsync` is idempotent (`INSERT … ON CONFLICT DO NOTHING RETURNING id`, then re-read → `IsNew = false`) and, when `IsNew`, itself writes **both** the outbox `platform_incident_raised.v1` (`[OutboxEvent("platform_incident_raised.v1")] [PlatformEvent]` — an incident has no user root) **and** the audit row `publishing.incident_raised` (category `support`, visibility `internal`, `subject_user_id = null` — an internal-visibility row is exempt from `ck_audit_logs_user_visible_has_subject`, which only constrains `visibility = user` rows). **`RaiseAsync` opens no transaction of its own**: it enlists the incident insert, the outbox row and the audit row in the **caller's ambient `IUnitOfWork`** (`PublishYouTubeHandler`'s transaction for the upload path, 06.4.2-T2's for the token-health path) — in `PublishYouTubeHandler` specifically, this means `Publication.HoldForIncident` commits together with the raise in that same commit, so a crash can never leave a publication held without its incident row, or an incident row without its audit/outbox pair (06.4.2-T2 never calls `HoldForIncident`, R18: its raise stands alone). `IAuditWriter.WriteAsync` joins the ambient transaction and throws without one, which is exactly the guard that enforces this — **YR25: the store is the single writer; callers never write either**. **YR24: holds are lazy and per row, no raise-time batch sweep** — `Publication.HoldForIncident(incidentId, now + TimeSpan.FromSeconds(5 * options.Poll.IntervalSeconds))` (`incidentId` from this same `RaiseAsync` call's result) sets `heldByIncidentId` and a **deferred** `next_attempt_at` (never `null`) only on the one row the caller is already holding a lock on; any other publication of that client is held independently, the next time its own job/poll/go-live run finds the same open incident via `HasOpenIncidentAsync`. The clear command (06.2.3-T3) can wake a row immediately; absent a clear, the deferred `next_attempt_at` makes the row re-check on its own (the "lazy" part of YR24).

### Error mapping

Rules (plan §7): `youtube_quota_exceeded` → release + `scheduled`/`youtube_quota_exhausted`/next PT midnight + jitter; `youtube_reauth_required` → `failed`/`channel_reauth_required`; `youtube_client_broken` → hold + incident (connection unchanged); `youtube_upload_failed` → `failed`/`youtube_upload_failed` (raw reason into `platform_payload.lastGoogleReason`); `youtube_rejected` → `failed`/`youtube_rejected`; `youtube_transport`/`youtube_session_expired` → stay `uploading`, let Hangfire retry with resume; attempts exhausted → `failed`/`youtube_upload_failed`.

### PT day

`NextPtMidnight(IClock clock, DateTimeOffset now)`: `TimeZoneInfo.FindSystemTimeZoneById("America/Los_Angeles")` (ICU, same rule as 02 T7) → next local midnight → `DateTimeOffset` with the offset that applies **at that instant** (DST-safe: a spring-forward midnight is `00:00` local; a fall-back day uses the offset in force at the target time, not `now`'s). Jitter 0–10 min from `Random.Shared`; the value is persisted in `next_attempt_at` so a retry does not re-jitter into a different slot.

### Schedule/re-enqueue subscriber (YR3, README §10; supersedes CR-10's `IPublishScheduler`)

```csharp
// src/NightTales.Application/Features/Publishing/Events/PublicationScheduledForUploadHandler.cs
public sealed class PublicationScheduledForUploadHandler(
    IAppDbContext db, IJobScheduler jobs, IOptions<YouTubeOptions> options, IClock clock) : IOutboxHandler<PublicationUpdated>
{
    public async Task HandleAsync(PublicationUpdated e, CancellationToken ct)
    {
        if (e.Status != "scheduled") return;
        var row = await db.Publications.AsNoTracking().SingleOrDefaultAsync(p => p.Id == e.PublicationId, ct);
        if (row is null) return;                                                          // gone by the time this ran
        if (row.Status != PublicationStatus.Scheduled) return;                            // re-check current state, not the event's snapshot
        if (row.ExternalPostId is not null) return;                                       // already has a video; the job's own reconcile handles it
        var queueAt = row.NextAttemptAt                                                   // quota reschedule, incident hold, or incident clear already computed this
            ?? PublicationQueueTime.For(row.PublishAt, options.Value.PublishLeadMinutes, clock.UtcNow);   // D12 (pure, Domain, declared by 06.2.2-T1); publish_at − lead time, or now — fresh-consent case only
        var delay = queueAt - clock.UtcNow;
        if (delay <= TimeSpan.Zero) jobs.Enqueue<PublishYouTubeJob>((j, jobCt) => j.RunAsync(e.PublicationId, jobCt));
        else jobs.Schedule<PublishYouTubeJob>((j, jobCt) => j.RunAsync(e.PublicationId, jobCt), delay);
    }
}
```

**The outbox payload is unchanged from D13** — `publication_updated.v1 { publicationId, episodeId, userId, status, errorCode? }`, no added field — so the handler re-reads `Publications` for `next_attempt_at`/`publish_at` instead of receiving a `queueAt`. **No held-guard needed (YR24, revised).** An earlier draft special-cased `error_code == "platform_incident"` because `HoldForIncident` used to set `next_attempt_at = NULL`, which the fallback misread as a fresh consent and scheduled for roughly `now` — a hold → event → enqueue → hold loop. YR24 fixes the root cause: `HoldForIncident` now always sets a real **deferred** `next_attempt_at` (`now + 5 × Poll:IntervalSeconds`), so the fallback path is never taken for a held row — the handler schedules the next check at that deferred instant through the same branch every reschedule uses, which **is** the "lazy" re-check YR24 asks for: `PublishYouTubeHandler`'s incident gate (UC1 step 5) either finds the incident cleared and proceeds, or holds again with a fresh deferred instant. 06.2.3-T3's clear command additionally wakes the row immediately by writing a `next_attempt_at` of `now` before the same event fires.

### Performance

One publication per run; the row lock is a single-row `FOR UPDATE`; `SaveChanges` twice at most (session-URI commit + terminal commit); the stream is never buffered (T1 guarantees the chunk-sized reads); `OpenReadAsync` of a 2 GB asset holds one chunk buffer plus the SDK's internal buffer — the only allocation per run. Parallelism of queue `publish` = 2 (D9/09.2.6-T1 `Jobs:Workers:publish`).

## Failure handling and edge cases

- **Lost response after the last chunk** (the reason this task exists): the session URI is committed before the first byte, so the next run probes → `Complete(videoId)` → `MarkUploadedExternal`. A probe answers `Partial(n)` → the stream is read from `n` (`Stream.Seek` on the blob stream; `IBlobStore.OpenReadAsync` returns a seekable `ResponseStream` for S3 — if it ever is not seekable, the handler drains `n` bytes instead, which is still O(n) reads and no full buffer).
- **Row disappears mid-run** (user deletes the episode): the blob open throws `not_found`; the handler cleans up (`Release`, no incident), logs `publication_gone` and returns; no retry storm.
- **Quota exhausted with a session already open**: the unit was consumed; the row goes back to `scheduled` **without** clearing `uploadSessionEnc`, so the retry at the next PT midnight resumes instead of re-uploading.
- **Held by incident while a session exists**: same — the session survives the hold; after `incident clear` the resumed run continues from `n`.
- **`invalid_client` from a *user-specific* problem** (e.g. a deleted Google Cloud project): the incident is platform-wide by design (D14); the operator clears it after fixing the client. Until then all publications of that client are held, not failed — this is the deliberate difference from `invalid_grant`.
- **Two runs for one publication** (a duplicate enqueue): the row lock serialises them; the second sees `processing` and returns a no-op.
- **Clock skew / expiry**: the token's validity is compared against `IClock.UtcNow` inside the same lock as the refresh.
- **Shutdown mid-upload**: `ct` cancels the chunk PUT; Hangfire requeues; the session URI makes the requeued run resume (no duplicate).
- **`SaveChanges` fails at the session-URI commit**: the handler aborts before the first byte, releases the unit and lets Hangfire retry — the safe direction.
- **Rollback**: flag off, then drain the `publish` queue; publications left `uploading` resume when re-enabled because the session URI is persisted and the session lives a week (G7).
