## Goal

One pure function turns a Google failure into one of five outcomes, and one operator verb clears the state that a broken OAuth client puts the platform in. `OAuthErrorClassifier.Classify(YouTubeFailure)` becomes the **single** mapping used by the upload job and by `TokenHealthJob`; an `invalid_client`/`unauthorized_client` answer holds **the one failing publication** lazily and per row (YR24: `status` unchanged, a **deferred** `next_attempt_at`, `error_code = platform_incident`, `platform_payload.heldByIncidentId` set — other publications of the same client are held only when their own job next runs), raises exactly one `platform_incidents` row, emits `platform_incident_raised.v1` and pages the operator; `nts-worker incident clear <id> --operator <name> --note "…"` closes the row, re-schedules every held publication of that incident id (across users, YR27-4) with jitter for `scheduled` rows and immediately for `processing` rows, emits `platform_incident_cleared.v1` and audits the action.

## Design

### Classifier (pure, no Google type)

```csharp
// src/NightTales.Application/Features/Publishing/Incidents/OAuthErrorClassifier.cs
public enum OAuthErrorOutcome { Transient, TokenRevoked, PlatformIncident, Quota, Validation }
public sealed record OAuthErrorClassification(OAuthErrorOutcome Outcome, string ErrorCode, string? GoogleReason);

public static class OAuthErrorClassifier
{
    public static OAuthErrorClassification Classify(YouTubeFailure failure);
}
```

| Input (`YouTubeFailure(GoogleReason, HttpStatus, IsTransport)`) | Outcome | `ErrorCode` |
|---|---|---|
| `invalid_grant`; HTTP 401 with reason `unauthorized` | `TokenRevoked` | `youtube_reauth_required` |
| `invalid_client`, `unauthorized_client` | `PlatformIncident` | `youtube_client_broken` |
| `quotaExceeded`, `uploadLimitExceeded`; HTTP 403 with either | `Quota` | `youtube_quota_exceeded` |
| `invalidPublishAt`, `invalidTitle`, `invalidDescription`, `invalidValue`, any other 4xx with a reason | `Validation` | `youtube_upload_failed` |
| `IsTransport` (5xx, timeout, `HttpRequestException`, no reason) | `Transient` | `youtube_transport` |
| `uploadAborted`, `codec`, `emptyFile`, `invalidFile`, `tooSmall` (a `failed` `videos.list` status) | `Validation` | `youtube_upload_failed` |
| `claim`, `copyright`, `duplicate`, `inappropriate`, `legal`, `length`, `termsOfUse`, `trademark`, `uploaderAccountClosed`, `uploaderAccountSuspended` (a `rejected` status) | `Validation` | `youtube_rejected` |

Ordering is deliberate and tested: `invalid_client` is checked **before** `invalid_grant` (a client-side rejection must not expire a user's grant), and `IsTransport` never wins over a present `GoogleReason` (a 5xx body that carries a reason is still classified by the reason). No state, no clock, no logging (the caller logs); `YouTubeFailure` is built in `GoogleYouTubeClient` (T1), so Application stays free of `Google.Apis.*` (architecture rule `InfrastructureOnly_GoogleApis`).

**Cutover (mandatory).** `UploadFailureMap` (06.2.3-T2) becomes a thin adapter over `Classify` — one mapping table, one adapter per caller:

```csharp
public static (UploadOutcome Outcome, string? ErrorCode, bool RaiseIncident) Map(ErrorOr<UploadResult> failure);   // now: Classify(...) → outcome
```

`TokenHealthJob` (06.4.2-T1) consumes `Classify` directly for its refresh branch. No second switch over Google reasons may exist after this task (a grep for `invalid_client` outside `OAuthErrorClassifier` must return only the fake and the tests).

### Incident writes (raise from the upload path, clear from the CLI)

- **Raise (upload).** `PublishYouTubeHandler`, on `PlatformIncident`, calls `var raise = await IPlatformIncidentStore.RaiseAsync("youtube", connection.OAuthClientId, ErrorCode, clock.UtcNow, ct)` (a `PlatformIncidentRaiseResult { IncidentId, IsNew }`), then `Publication.HoldForIncident(raise.IncidentId, clock.UtcNow + TimeSpan.FromSeconds(5 * options.Poll.IntervalSeconds))` (sets `error_code = PublicationErrorCodes.PlatformIncident`, a **deferred** `next_attempt_at` — YR24, never `NULL` — reusing YR17's `5 × Poll:IntervalSeconds` key, `platform_payload.heldByIncidentId = raise.IncidentId`) — all in ONE transaction, so a crash can never hold a publication without its incident row. **Quota (YR19, corrected):** the unit is released only when `reservedThisRun == true` and the failure hit during token refresh (step 7, before `StartUploadAsync` was ever issued this run); if `invalid_client`/`unauthorized_client` instead comes back **as the session-create response itself** (the request was sent), the unit is consumed. `raise.IsNew` decides the alert and the outbox event.
- **Clear (operator).** `ClearPlatformIncidentCommand(Guid IncidentId, string Operator, string Note)` (plan §4 UC2) → `ClearAsync(incidentId, @operator, note, now, ct)`. **`publications`/`channel_connections` are `IUserOwned` and tenant-filtered (D10); the CLI runs as `system:operator` with no ambient user, so the sweep cannot use a plain `db.Publications` read — it goes through the pinned wave-1 `ISystemWorkQuery.PendingAsync<T>` (09.2.3-T1:36, one signed member, no extension) exactly the way `PublishYouTubeHandler`'s own row lookup does (06.2.3-T2 step 2).** `cleared_at` is set only **after** the sweep finds zero remaining held rows, so a crash mid-sweep leaves the incident open and a re-run of the same CLI command resumes and finishes it — never a partial "cleared but still held" state:

```csharp
// The advisory lock is session-scoped in Postgres: it belongs to one physical connection, not to a
// pooled DbContext (EF returns each command's connection to the pool). Open ONE connection explicitly
// and hold it for lock → cleared-check → sweep completion → final commit → unlock, or the unlock in
// `finally` can run on a different connection and leak the lock, hanging every future `incident clear`
// for this id. Use pg_try_advisory_lock (non-blocking, same as 09.7.3-T1's retention sweep), not the
// blocking pg_advisory_lock: a stuck sweep must fail one CLI invocation, never hang a second one.
await using var lockConn = dataSource.CreateConnection();
await lockConn.OpenAsync(ct);
var lockKey = HashLockKey(incidentId);   // e.g. hashtext("incident_clear:" + incidentId)
var acquired = await lockConn.ExecuteScalarAsync<bool>("SELECT pg_try_advisory_lock(@key)", new { key = lockKey });
if (!acquired) return Error.Conflict(code: "incident_clear_busy");   // CLI prints "busy", exits non-zero — never blocks
try
{
    var alreadyCleared = await lockConn.ExecuteScalarAsync<bool>(
        "SELECT cleared_at IS NOT NULL FROM platform_incidents WHERE id = @id", new { id = incidentId });
    if (alreadyCleared) return new PlatformIncidentClearResult(incidentId, AlreadyCleared: true, PublicationsRescheduled: 0);

    // Step 1: resolve the client's connections cross-tenant (bounded set, same pinned port, ChannelConnection
    // is IUserOwned too) — narrows the sweep to this client instead of a full-table scan.
    var connIds = await systemWork.PendingAsync<ChannelConnection>(c => c.OAuthClientId == oauthClientId, batch: 10_000, ct)
        .Select(c => c.Id).ToListAsync(ct);

    // Step 2: bounded sweep loop — MaxBatches + a run-local failedIds set guarantee progress even if a
    // batch's SaveChangesAsync keeps failing for the same rows (09.7.3-T1's exact guard, plan.md:163/218).
    int rescheduled = 0, batches = 0;
    var failedIds = new HashSet<Guid>();
    var drained = false;   // true only if the loop's last query returned zero candidates (nothing left to reschedule)
    while (batches++ < IncidentClearOptions.MaxBatches)   // e.g. 50 batches × 200 = 10,000 rows, ample for P
    {
        var candidates = await systemWork.PendingAsync<Publication>(
            p => connIds.Contains(p.ChannelConnectionId) && !failedIds.Contains(p.Id)
              && (p.Status == PublicationStatus.Scheduled || p.Status == PublicationStatus.Processing)
              // [OPEN/INFERENCE] EF.Functions.JsonExtractPathText translation against this jsonb mapping is
              // unconfirmed at plan time; if it does not translate inside PendingAsync<T>'s Expression<Func<T,bool>>,
              // fall back to filtering on connIds+status here and re-checking heldByIncidentId per row inside
              // the tenant-scoped `scopedDb` query below (an ordinary LINQ jsonb predicate under ISystemContext.For,
              // not a new port) before calling ReleaseHold.
              && EF.Functions.JsonExtractPathText(p.PlatformPayloadJson, "heldByIncidentId") == incidentId.ToString(),
            batch: 200, ct).ToListAsync(ct);   // (Id, UserId) pairs only — no row data crosses the tenant boundary here
        if (candidates.Count == 0) { drained = true; break; }
        foreach (var group in candidates.GroupBy(c => c.UserId))   // an incident can span many users' connections
        {
            using var scope = scopeFactory.CreateScope();
            using var system = scope.ServiceProvider.GetRequiredService<ISystemContext>().For(group.Key);
            var scopedDb = scope.ServiceProvider.GetRequiredService<IAppDbContext>();
            var ids = group.Select(c => c.Id).ToList();
            var held = await scopedDb.Publications.Where(p => ids.Contains(p.Id)).ToListAsync(ct);   // tenant filter now matches (For(userId) is set)
            try
            {
                foreach (var p in held)
                {
                    var nextAttemptAt = p.Status == PublicationStatus.Processing ? now : now + Jitter(0, 60);   // YR17: processing keeps `now`, no jitter
                    p.ReleaseHold(nextAttemptAt, now);   // raises PublicationUpdated { Status = <current> } (D13 unchanged shape); no-op on a terminal status (T2 domain test)
                }
                await scopedDb.SaveChangesAsync(ct);   // one interceptor pass per user-group batch writes one outbox row per touched publication
                rescheduled += held.Count;
            }
            catch (DbUpdateException)
            {
                foreach (var id in ids) failedIds.Add(id);   // exclude from the next query so a stuck batch never repeats forever
            }
        }
    }

    // Gate the final commit: the incident is cleared ONLY when the sweep actually finished — every batch
    // drained and none failed. `MaxBatches` exhausted, or any `failedIds`, leaves the incident open on
    // purpose (see "The final commit" below) so a re-run of the same CLI command continues the work,
    // instead of silently under-reporting a clear that did not finish.
    if (!drained || failedIds.Count > 0)
        return new PlatformIncidentClearResult(incidentId, AlreadyCleared: false, PublicationsRescheduled: rescheduled, Remaining: true);

    // Only now, on the SAME lockConn-guarded critical section: commit the incident row itself.
    await using var incidentScope = scopeFactory.CreateScope();
    var incidentDb = incidentScope.ServiceProvider.GetRequiredService<IAppDbContext>();
    var incident = await incidentDb.PlatformIncidents.SingleAsync(i => i.Id == incidentId, ct);
    incident.Clear(now, @operator, note);   // cleared_at, cleared_by, note — raises platform_incident_cleared.v1 + writes the audit row (D17)
    await incidentDb.SaveChangesAsync(ct);
    return new PlatformIncidentClearResult(incidentId, AlreadyCleared: false, PublicationsRescheduled: rescheduled);
}
finally
{
    await lockConn.ExecuteScalarAsync<bool>("SELECT pg_advisory_unlock(@key)", new { key = lockKey });   // same connection that acquired it
}
```

**The final commit.** `cleared_at = now`, `cleared_by = @operator` (YR16: the operator's name, not a fixed string), `note`, plus the outbox `platform_incident_cleared.v1` and the audit row `publishing.incident_cleared` (category `support`, visibility `internal`, actor `system:operator`, `ActorLabel = @operator`, `data = { incidentId, platform, oauthClientId, rescheduled }` — ids, counts and the operator's name only, D17) run **only when the sweep drained with zero `failedIds`** (`ClearAsync`'s `!drained || failedIds.Count > 0` gate). Each `publication_updated.v1` (D13 unchanged shape — no `queueAt` field; 06.2.3-T2's `PublicationScheduledForUploadHandler` re-reads `next_attempt_at` off the `scheduled` rows itself; the `processing` rows fall outside that handler's `status == "scheduled"` filter and are 06.2.5-T1's poller's concern) was already committed per user-group batch during the loop, so by the time this final commit lands every held publication the incident owned is already rescheduled. If the loop instead hits `MaxBatches` or leaves any row in `failedIds`, `ClearAsync` returns early with `Remaining: true` and a partial `PublicationsRescheduled` count, **without** touching `cleared_at` — the CLI prints the partial count and a `remaining=true` marker and exits non-zero, and the operator re-runs the same command to finish the rest (a stuck row is never silently reported as cleared).
- **Serialize the clear.** The whole operation — lock, cleared-check, sweep, final commit — runs on one explicitly-held connection guarded by `pg_try_advisory_lock` (non-blocking; a second concurrent operator or an overlapping retry gets `incident_clear_busy` immediately instead of blocking or racing the sweep) and is released via `pg_advisory_unlock` on that same connection in `finally`. This is 09.7.3-T1's exact lock pattern (`plan.md:77`), adapted from try-then-skip to try-then-error since a clear is an operator-invoked command, not a silent recurring job.

### CLI verb

```csharp
// src/NightTales.Worker/Cli/IncidentCommands.cs        (registered in the Worker's command tree, no web listener)
// nts-worker incident clear <id> --operator <name> --note "<text>"
```

- `<id>` parsed as `Guid`; `--operator` and `--note` both required (YR16: `--operator` 1–100 chars, `--note` 1–500 chars); usage error → exit 1 with the usage line, no side effect.
- Output (stdout, one line): `id=<guid> alreadyCleared=<true|false> rescheduled=<n> remaining=<true|false>`; `remaining=true` → exit 3 (the sweep did not finish — `MaxBatches` hit or a batch failed — re-run the same command); not-found → `id=<guid> notFound` and exit 2 (a tool must not report success for a typo).
- The verb resolves the command through `ISender` (the Worker's mediator), so the same code path is used by tests; the CLI contains no business logic beyond parsing and printing.
- No HTTP route: `incident clear` is host-only, so an admin *session* is neither necessary nor sufficient (plan §8).

### Alert (P1, soft dependency on 11.6.2-T1)

- **This task defines the names it emits** — nothing today covers a platform incident: 11.6.2-T1's set is a closed 15 rules whose only YouTube rule is #10 (quota > 80 %) and 09.9.3's custom metrics add only `youtube_quota_used`. Gauge `platform_incident_open{platform,oauth_client_id}` (number of open rows; cardinality bounded by the number of OAuth clients) and counter `platform_incident_cleared_total`. Until CR-12 is applied the metric is emitted and read by hand, and the `Warning` log line below is the alert: **no page is claimed**.
- The alert rule ships as a repository file next to 11.6.2-T1's rules: `condition: platform_incident_open > 0`, `for: 5m`, `severity: page`, `summary: "YouTube OAuth client %s is rejected by Google"`, annotation carrying the `oauth_client_id` label only. **CR-12** asks 11.6.2-T1 to load it as a 16th rule and to add it to the threshold assertion (the rule set is otherwise asserted as exactly 15, so the two tasks must land together or the assertion must move).
- Until the rule file is loaded (the soft part), the operator still learns of the incident: the raised outbox event is a log record (`platform_incident_raised`, `Warning`, ids only), and the publication rows carry `platform_incident`. No second notification mechanism (no e-mail to the owner — D14 says the *user* sees the neutral "temporarily unavailable" copy, and 02.8.3-T4's own alert e-mail carries `oauth_client_incident` to the series owner).

## Failure handling and edge cases

- **`invalid_client` while a session is open** → hold keeps `uploadSessionEnc`, so the resumed run after the clear continues from the stored offset instead of re-uploading.
- **The client is fixed but the incident is not cleared** → publications stay held, each with its own **deferred** `next_attempt_at` (YR24: `now + 5 × Poll:IntervalSeconds`, never `null`) that only causes a bounded lazy re-check, not a retry storm; no quota is consumed on that re-check while the incident is still open, and the alert stays open. This is intended: an unbounded retry would burn 100 units a day on a broken client.
- **The client is deleted permanently** → the operator clears the incident after reconnecting the affected channels (06.1.2 flow); the next run answers `invalid_grant` → `channel_reauth_required`, which is the honest terminal state for the user.
- **Two incidents in sequence** (clear, then break again) → a new row (the partial unique only covers open rows); the sweep matches `heldByIncidentId`, so the second hold is attributable and the first clear cannot reschedule rows it never held.
- **A publication held by an incident is cancelled by the user** → the row leaves `scheduled`/`processing`; the sweep's `ISystemWorkQuery.PendingAsync` predicate (`status IN (Scheduled, Processing)`) excludes it; no `ReleaseHold` call and no outbox event for it.
- **`ClearAsync` crashes mid-sweep** → `cleared_at` is set only after the loop finds zero remaining held rows (see "The final commit" above), so a crash between batches leaves the incident open with some publications already rescheduled and some still held; a re-run of the same CLI command resumes from wherever the query now finds work and finishes it — never a permanently stuck "cleared but still held" row.
- **Alert rule not yet loaded** (11.6.2-T1 is a soft dependency) → the incident still exists, holds and clears correctly; only the page is missing. The drill (11.6.2-T1's acceptance) is the gate that proves the route end to end.
- **CLI run against a non-production host** → the verb is host-only; there is no HTTP surface, so no CORS/CSRF concern exists; the audit row records the operator as `system:operator`.
- **Rollback** → the classifier is pure and the verb is additive; disabling the flag stops the raise path (no uploads start), leaving existing incidents clearable. No data change.
