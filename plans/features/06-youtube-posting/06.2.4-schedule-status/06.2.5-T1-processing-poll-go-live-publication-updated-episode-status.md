## Goal

Close the publishing loop after the upload job stored `external_post_id`: poll YouTube until the video is processed (60 s, ≤ 120 min), map `uploadStatus`/`failureReason`/`rejectionReason`/`privacyStatus` ✅ G6 to the publication status, confirm the go-live of a scheduled slot (`publishAt + 5 min`, retried every 15 min for 120 min) ✅ D12/C5, move the episode `ready → scheduled → published` in the **same transaction**, and emit `publication_updated.v1` → SignalR `PublicationUpdated` with ids only ✅ D13 + `09.8.1-T1:114-129`.

## Design

**1. Domain: one mapping, one transition table.**
`src/NightTales.Domain/Publishing/Publication.Processing.cs` (partial; `Publication.cs` is 06.2.1-T1's) and `src/NightTales.Domain/Episodes/Episode.Publishing.cs` (the 09 convention: `Episode.cs` is 09.5.1's, feature methods live in partial files ✅ `09-backend-api/README.md:339`).

```csharp
// MarkProcessed takes primitives, never YouTubeVideoStatus: that record lives beside IYouTubeClient
// in the Application layer (06.2.3-T1:58) and Domain must not reference an Application type — the
// command handler (Application) maps YouTubeVideoStatus onto these parameters before calling in.
public ErrorOr<PublicationProcessingOutcome> MarkProcessed(string uploadStatus, string? failureReason,
        string? rejectionReason, string? privacyStatus, DateTimeOffset now);
public sealed record PublicationProcessingOutcome(bool Live, bool AwaitGoLive, DateTimeOffset? GoLiveAt);

public ErrorOr<Success> MarkRejected(RejectionReason reason, DateTimeOffset now);      // -> failed + youtube_rejected
public ErrorOr<Success> MarkProcessingFailed(string errorCode, DateTimeOffset now);    // -> failed (processing -> failed)
public ErrorOr<Success> MarkLive(DateTimeOffset now);                                  // scheduled -> published
public ErrorOr<Success> MarkGoLiveUnconfirmed(DateTimeOffset now);                     // failed + youtube_go_live_unconfirmed
// NOTE: no MarkProcessing(startedAt, deadlineAt, now) here — that overload is 06.2.3-T2's
// (`Publication.MarkProcessing(videoId)`, uploading -> processing), which already writes
// platform_payload.processing { startedAt, deadlineAt = startedAt + Poll:MaxMinutes, polls = 0 }
// at upload completion (06.2.3-T2 step 10). This task only increments `polls` and advances
// `next_attempt_at` on each re-claim (§Design 2) — a second MarkProcessing signature would collide.

// Episode.Publishing.cs
public ErrorOr<Success> MarkScheduled(Guid publicationId, DateTimeOffset now);   // ready -> scheduled (idempotent)
public ErrorOr<Success> MarkPublished(Guid publicationId, DateTimeOffset now);   // scheduled -> published
// No Episode.MarkPublicationFailed: 00-overview.md:336 has no scheduled -> ready edge and
// 02.8.3-T3:83 treats a publication failure as episode-unchanged (§Notes, retracted design).
```

Every transition is a CAS on the current status (`WHERE id = @id AND status = @expected`): a replayed job or outbox message is a no-op returning `Success` with no side effect (O1). Terminal `published|failed|cancelled` are absorbing; a late snapshot for a `cancelled` publication is dropped and counted.

| `uploadStatus` (G6) | Condition | Publication | `error_code` | `next_attempt_at` |
|---|---|---|---|---|
| `processed` | `platform_payload.upload.publishAt` is `null` (pre-audit, owner-private, or catch-up — 06.2.4-T1 invariant 1) | `published` (row keeps whatever `Privacy` 06.2.1-T1 stamped) | null | null |
| `processed` | `platform_payload.upload.publishAt` was sent and is in the future (only possible when `Privacy == "public"`, not pre-audit) | `scheduled` | null | `publish_at + GoLive:DelayMinutes` |
| `processed` | `upload.publishAt` was sent but is already in the past | `published` | null | null |
| `rejected` | `rejectionReason` present | `failed` | `youtube_rejected` | null |
| `failed` | `failureReason` present | `failed` | `youtube_upload_failed` | null |
| `uploaded`/`deleted` | past `processing.deadlineAt` | `failed` | `youtube_upload_failed` | null |

`platform_payload.upload.publishAt` (06.2.4-T1's write) decides the `AwaitGoLive` branch, not the raw row `publish_at`: only a `Privacy == "public"`, non-pre-audit row ever has `upload.publishAt` set. `preAudit`/`Privacy` themselves are read from **06.2.1-T1's create-time stamp** (`06.2.1-T1-publication-aggregate.md:264,267`), never from the live `YouTubeOptions.AuditStatus` and never written by this task: a pre-audit or owner-private slot stays that way permanently, even if the audit is approved later (`02.8.3-T3:156`, YR20).

**2. `PollYouTubeProcessingJob`** — `src/NightTales.Application/Features/Publishing/Jobs/PollYouTubeProcessingJob.cs`, `sealed`, `IBackgroundJob`, `[JobPolicy(Queue = JobQueue.Publish, Retries = 3)]` (transport errors only; the 60 s cadence is the real retry).

```csharp
public Task RunTickAsync(CancellationToken ct);                       // recurring entry (ids-only rule: only ct)
public Task RunAsync(Guid publicationId, CancellationToken ct);       // one publication, ids only (arch test)
```

- Recurring registration in `src/NightTales.Worker/Jobs/PublishingRecurringRegistrations.cs` (`IRecurringJobRegistration`, stable id `publishing-poll-processing`, cron from `YouTube:Poll:IntervalSeconds` = 60) **only while `youtube_publish` is on**, removed with `RemoveRecurringIfExists` otherwise (D1, O2).
- `RunTickAsync` claims ≤ 50 rows in one short transaction:

```sql
-- NULL next_attempt_at is included: 06.2.3-T2's MarkProcessing(videoId) CLEARS it at upload
-- completion (uploading -> processing), so the very first poll of a freshly-uploaded row must
-- still be claimable; every re-claim after that sets a concrete next_attempt_at (below).
SELECT id FROM publications
 WHERE status = 'processing' AND (next_attempt_at IS NULL OR next_attempt_at <= now())
 ORDER BY channel_connection_id, next_attempt_at NULLS FIRST   -- one videos.list call per 50 ids of one connection
 LIMIT 50 FOR UPDATE SKIP LOCKED;
```

(Uses D18's partial index `(status, next_attempt_at) WHERE status IN (…,'processing')`; no sequential scan, no N+1: at most one `videos.list` per connection per tick.)
- Token: `ITokenService.GetAccessTokenAsync(connectionId)` (06.2.3-T2, refresh under `FOR UPDATE` on the connection row, D9/F21). A 401/`invalid_grant` is 06.2.3-T3's classifier path (connection `expired` + outbox) and leaves the row's status unchanged with `next_attempt_at = now + IntervalSeconds`.
- `videos.list` per group with ≤ 50 ids = 1 unit from the 10,000-unit bucket (G1) — **`IQuotaLedger` is not touched** (D10's ledger counts uploads only).
- Each snapshot is applied through `ISender` → `RecordPublicationProcessingStatusCommand(PublicationId, Snapshot)` so the pipeline/UnitOfWork/outbox apply (O1). `startedAt`/`deadlineAt` are already set by 06.2.3-T2's `MarkProcessing(videoId)` (upload completion) — this job only increments `platform_payload.processing.polls` and sets `next_attempt_at = now + IntervalSeconds` on every non-terminal re-claim; it never re-derives `deadlineAt`.
- A `processing` row without `external_post_id` is failed with `youtube_upload_failed` + a warning (never a null `videos.list` id).
- Rows whose connection's client has an **open `platform_incidents`** row are held: `next_attempt_at = now + 5 × Poll:IntervalSeconds` (never `null` — YR17) and `platform_payload.heldByIncidentId` is set; `06.2.3-T3`'s clear command re-schedules `processing` rows with `next_attempt_at = now` in addition to the `scheduled` rows it already reschedules (coordination note for `06.2.3-T3`, §Notes).

**3. `PublicationGoLiveJob`** — `…/Jobs/PublicationGoLiveJob.cs`, `[JobPolicy(Queue = JobQueue.Publish, Retries = 3)]`, `RunAsync(Guid publicationId, CancellationToken ct)`.

- Scheduled by the poller when `MarkProcessed` reports `AwaitGoLive`: `IJobScheduler.Schedule<PublicationGoLiveJob>((j, ct) => j.RunAsync(id, ct), goLiveAt − now)` with `goLiveAt = publish_at + GoLive:DelayMinutes` (5 min, D12/C5). **Never scheduled when `platform_payload.upload.publishAt` is `null`** — pre-audit, owner-`private`, or catch-up rows all have it null (06.2.4-T1 invariant 1); only a `Privacy == "public"` row that actually received a future `publishAt` reaches this branch.
- Each run: `videos.list(part=status)` for `external_post_id` → `privacyStatus = public` ⇒ `ConfirmPublicationLiveCommand` (`MarkLive` + `Episode.MarkPublished` + `publication_updated.v1`, one transaction); `private`/`unlisted` ⇒ `platform_payload.goLive.attempts++` and `Schedule(now + GoLive:RetryMinutes)` until `attempts × RetryMinutes ≥ GoLive:MaxMinutes` (120 min) → `failed` `youtube_go_live_unconfirmed` + P1 alert (D12).
- It is the **only** writer of the go-live transition; 02.8.3's `publish_at + 10 min` fallback only reads `PublicationUpdated` (P2). Open incident ⇒ hold with `next_attempt_at = now + 5 × Poll:IntervalSeconds` + `platform_payload.heldByIncidentId` (YR17, same as the poller).
- Go-live claim query (D18's index covers `scheduled`; `external_post_id IS NOT NULL` excludes quota-deferred rows — D10's ledger returns them to `scheduled` with `next_attempt_at` = next PT midnight but no `external_post_id` yet, O8 — which would otherwise be "confirmed" against a null video id and wrongly failed; the `preAudit` predicate keeps pre-audit rows out of the candidate set even if one somehow carries a `next_attempt_at`). **`IS DISTINCT FROM 'true'`, not `= 'false'`**: 06.2.1-T1 writes no `preAudit` key at all on an approved row (`06.2.1-T1-publication-aggregate.md:167,220`), so `platform_payload->>'preAudit'` is `NULL` for every normal, approved slot — `= 'false'` would filter out every row that should go live; `IS DISTINCT FROM 'true'` treats `NULL` and `'false'` the same, correctly:

```sql
SELECT id FROM publications
 WHERE status = 'scheduled' AND next_attempt_at <= now()
   AND external_post_id IS NOT NULL
   AND (platform_payload->>'preAudit') IS DISTINCT FROM 'true'
 ORDER BY channel_connection_id, next_attempt_at
 LIMIT 50 FOR UPDATE SKIP LOCKED;
```

**4. Event and realtime.**
`src/NightTales.Application/Features/Publishing/Events/PublicationUpdatedEvent.cs`:

Written by `OutboxSaveChangesInterceptor` in the same `SaveChanges` as the status write (`user_id` from the aggregate's `IUserOwned.UserId`, O1). `src/NightTales.Application/Features/Publishing/Handlers/PublicationUpdatedRealtimeHandler.cs`:

```csharp
public sealed class PublicationUpdatedRealtimeHandler(IRealtimeNotifier notifier) : IOutboxHandler<PublicationUpdatedEvent>
{
    public ValueTask HandleAsync(PublicationUpdatedEvent e, OutboxContext ctx, CancellationToken ct)
        => new(notifier.NotifyAsync(e.UserId,
               new RealtimeEvent(RealtimeEventName.PublicationUpdated,
                                 new RealtimeIds(PublicationId: e.PublicationId, EpisodeId: e.EpisodeId), Data: null), ct));

```

- `Data = null` — WT54 allows data only for `RenderProgress`; ids only, ≤ 8 KB; `pg_notify` runs inside the handler's transaction (R1), so a rolled-back status never notifies; the client refetches `GET /episodes/{id}`.
- 02's own handler consumes the same type (D13); the event is emitted **once per transition** (`processing`, `published`, `failed`, `scheduled`), never for a no-op CAS replay.

**5. Episode status in the same transaction (D12/F15, `00-overview.md:336`).** `RecordPublicationProcessingStatusCommand` and `ConfirmPublicationLiveCommand` load the episode in the same `SaveChanges`: `MarkPublished` on the terminal-success path, `MarkScheduled` (idempotent safety net — 06.2.2-T1 is the primary caller) while waiting for go-live. An `episode_invalid_state` from the episode is logged and swallowed: the publication status is the source of truth and must not depend on the episode's state.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `videos.list` 5xx/timeout | row unchanged, `next_attempt_at = now + 60 s` (job `Retries = 3` covers the immediate transport retry); the poll deadline still bounds the total |
| 401/`invalid_grant` on the access token | 06.2.3-T3: connection `expired` + `channel_connection_changed.v1` via outbox; this job only reschedules the row and logs ids |
| `invalid_client`/`unauthorized_client` | 06.2.3-T3 raises `platform_incidents` (D14); this job holds affected rows at `next_attempt_at = now + 5 × Poll:IntervalSeconds` + `platform_payload.heldByIncidentId` (YR17, never `null`) and never alerts twice — the row keeps being re-claimed and re-skipped, not left forever unclaimable |
| video missing from the `videos.list` answer (`deleted`) | `MarkProcessingFailed("youtube_upload_failed")` + warning (the uploader deleted it or the API lost it) |
| `external_post_id` null on a `processing` row | failed with `youtube_upload_failed` (`MarkProcessingFailed`), warning, no null id sent to Google |
| publication cancelled mid-poll | CAS fails → no-op, no event, row stays `cancelled`; a metric counts the dropped snapshot |
| `publishAt` in the past already at processing time | `published` directly, no go-live job (matches 06.2.4-T1's catch-up rule) |
| go-live check answered `unlisted` | retried as not-yet-live (G6 `privacyStatus`), inside the same 120-min budget |
| clock/`next_attempt_at` in the future | claim query simply skips it; no busy loop (index on `(status, next_attempt_at)`) |
| duplicate tick (two Worker instances) | `FOR UPDATE SKIP LOCKED` + CAS ⇒ one winner; the loser no-ops |
| 02's fallback at `publish_at + 10 min` fires first | it only reads `PublicationUpdated` (P2); a second writer would break the CAS — coordination note §Notes 1 |
| very large batch of overdue rows | ≤ 50 rows/tick, ordered by connection so the `videos.list` unit cost stays ⌈rows/50⌉ (G1) |
| row held by an open incident, past its poll deadline | the deadline check only fires on a *processed* run; a held row is re-claimed every `5 × Poll:IntervalSeconds` (YR17) but stays held (skipped) until 06.2.3-T3's clear command resets `next_attempt_at = now` for it |
