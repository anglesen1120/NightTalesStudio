## Goal

A complete, clause-mapped, reproducible evidence pack for the YouTube API audit (extension) is on disk and verified, so that `13.4.2-T1` can file it on the first attempt. The pack proves that the studio's behaviour matches every III.x clause and every sentence of the privacy policy and ToS **at the filed versions**, and it carries the quota justification for M1 (the owner's cadence and the daily cap). Deliverable = documents, checklists and review steps; the task writes no code and changes no schema.

## Design

**Deliverable layout** (repo copy = text only, 13 README D5):

```
docs/compliance/audit-pack/<yyyy-mm-dd>/

  01-walkthrough-checklist.md # the 13-step behaviour walkthrough, one row per step, mapped to clause ids
  02-policy-clause-map.md     # every III.x clause and policy sentence → the test/screenshot/query that proves it
  03-retention-deletion.md    # the 7/30/30 duties, their job, their alert, their proof query
  04-quota-justification.md   # M1: owner cadence, 100 units/day, the ledger, the > 80 % alert
  05-consent-model.md         # pc.v1, series authorization version, veto window, approve-now, III.C.3 justification
  06-artefacts.md             # links/locations + SHA-256 of every external artefact (no binary in the repo)
```

**Manifest rules** (`index.md`). One row per artefact, columns `# | Artefact | Source of truth (table/route/screen + owner task) | Collected at (date, env) | How to reproduce | Verifier | Redaction applied`. Every row must satisfy: (a) the source is a named table, route or screen with its owner task id; (b) reproduction is a single command, query or click path written down; (c) the collected date and the environment (`prod-api staging`, owner channel) are recorded; (d) a second person reproduced it; (e) the redaction applied to the repo copy is stated (channel name/video id/e-mail replaced or hashed).

**Walkthrough checklist** (`01-walkthrough-checklist.md`) — the 13 steps of 06 README F16 / high-level `06-youtube-posting.md:117`, each with: precondition, action, expected observable, screenshot/cast timestamp, clause ids, pass/fail, verifier initials:
1. policy acceptance (legal dialog) → 2. connect (re-auth + consent) → 3. channels page shows the connection → 4. publish form filled (title/description/tags/privacy/schedule) → 5. per-video consent (`pc.v1` shown, version recorded) → 6. upload → private → 7. processing → published → 8. disconnect (Google revoke + 7-day request) → 9. autopilot on (series authorization text + version) → 10. veto-window notice arrives with edit/cancel/approve-now → 11. consent row written by the scheduler/authorization → 12. upload of the autopilot publication → 13. quota wait + ETA shown when the day is full.

**Clause map** (`02-policy-clause-map.md`) — one row per clause/sentence: `Clause | Policy text (quoted) | Our behaviour | Proof (artefact id / test id / screenshot) | Verdict`. Mandatory rows: III.A.1 (ToS link + binding clause), III.A.2 (privacy policy before features, "uses YouTube API Services", Google Privacy Policy link, revocation link, contact), III.C.3 (the consent-model justification: explicit per-video consent, veto window, one-tap approve-now fallback — owner decision O3), III.D.2 (7 days after in-app revoke / 30 days after Google-page revoke / periodic reconfirm), III.E.4 (reconfirm or refresh/delete stored data every 30 days; user deletion ≤ 7 days). A row with `Verdict = gap` blocks the handoff.

**Retention/deletion table** (`03-retention-deletion.md`): row per data class — tokens (`channel_connections.*_enc`, deleted/null on revoke), channel metadata (`display_name`, `external_account_id`), YouTube-derived fields (`external_post_id`, `platform_payload`), publications (kept as our record, YouTube-derived fields nulled), `data_deletion_requests` (kept as the audit trail), blobs/video assets (09.7.2-T1 prefix delete, episode scope), with `duty | deadline | job | alert | proof query`.

**Quota justification** (`04-quota-justification.md`): M1 numbers only — owner cadence (posts/day from the series settings), one unit per upload against the 100-unit upload bucket, `units_limit` from `YouTube:Quota:UnitsPerDay`, the ledger row shape, the ETA endpoint and the > 80 % alert; plus the M2 re-filing note (beta data) as the high-level plan requires. No fabricated volume numbers: the cadence value is read from the owner's series settings at pack time and cited.

**Consent model** (`05-consent-model.md`): per-video consent with the text version, autopilot series authorization with its version, the veto window (≥ `MinVetoWindowHours`, default 12), the cancel link, approve-now, and the III.C.3 justification; each statement points at the artifact/screen that shows it.

**Evidence-quality rules (apply to every row).** Reproducible from the repo copy alone (13 README D5); no secret, token, cookie, e-mail, IP or raw API payload in the repo copy — the repo holds redacted values, the external artefact holds the raw form with its SHA-256 recorded; every screenshot has a clause id and a timestamp; every database evidence item is a read-only query whose SQL is written in the pack; the walkthrough runs on the **production API project** (the one being audited) with the owner's channel (high-level F16) — staging-only artefacts are marked as such and cannot substitute for a production step.

**Review steps.** (1) Author self-review against the clause map (every mandatory row has a proof). (2) Second-person reproduction: a different person (owner) re-runs three randomly chosen manifest rows and signs. (3) Redaction pass (`grep` for token/e-mail/id patterns over the repo copy). (4) Legal-text version check: every version quoted equals `manifest.json` and `LegalDocuments:Current:*` (13 README K1/D1). (5) Handoff: pack index + the clause map go to `13.4.2-T1`, which drafts the form answers and files; the pack id is recorded in the filing note.

**Performance and reuse constraints.** Pack assembly uses read-only SQL on existing indexes (`platform_quota_usage` PK `(platform, quota_day)`, `data_deletion_requests` by `completed_at`, `audit_logs` `(subject_user_id, created_at DESC)`, `publications` by `(status, next_attempt_at)`) and existing routes/screens — no new export endpoint, no new e-mail, no new flag, no new audit mechanism, no CSV written by a script that bypasses the API (`09.2.2-T1` conventions; 06 README D1/D17). The pack is text ≤ a few hundred KB; screencasts are external.

## Steps

1. Freeze the pack date and the audit window; create `docs/compliance/audit-pack/<date>/`.
2. Collect A1–A16 row by row, writing each reproduction into `index.md` as you go (never collect first and document later).
3. Run the 13-step walkthrough on the production API project with the owner's channel; record it; map each step to its clause ids; keep the cast file outside the repo and record its SHA-256.
4. Write the clause map (`02`) against the live policy texts (06 README G13); mark every row `proven` / `gap`; fix or escalate gaps (a gap is a plan §11 blocker, not a footnote).
5. Write the retention/deletion table (`03`) and prove each row with A5–A7 and A16.
6. Write the quota justification (`04`) with the M1 numbers read from the owner's settings at pack time; include the ETA/alert evidence.
7. Write the consent model (`05`) with the four publication/authorization rows and the two screens.
8. Redaction pass over the whole pack (grep for token/e-mail/IP/id patterns); record the redaction per row.
9. Second-person reproduction of three random rows; sign in the manifest.
10. Hand the pack index + clause map to `13.4.2-T1`; record the handoff date in the pack and in the 06 README §7 gate evidence.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| A producer artefact is not live yet (e.g. `06.4.3-T1` not merged) | the pack stops at that row; the gap is recorded with the blocking task id and the handoff to `13.4.2-T1` does not happen (gate 06-audit-ready fails) |
| 10 wave-2 screens (`10.7.1/2/4-T1`) not detailed when the pack starts | the walkthrough still runs against whatever UI exists; rows cite the task ids and the copy is captured from the shipped UI; plan §2 [OPEN] tracks the wave-2 dependency |
| The audit rejects series-level authorization | the pack keeps the per-video consent + approve-now evidence (owner decision O3 in 06 README §10); the walkthrough step 10/11 evidence is re-shot for per-video authorization and the clause map row is re-verdict |
| A policy text changes after collection | the pack is invalidated for the changed sentence: re-collect that artefact and re-run the clause row; the pack date stays, a revision note is added |
| A version drift between `manifest.json`, the API config and the quoted text | blocked: `VP4` fails, the version is fixed first (13 README D1 owns the check) |
| The owner's channel shows identifying data in a screenshot | redact the channel/video names, keep the raw file outside the repo with its SHA-256, record the redaction |
| A quota/retention number in the pack cannot be reproduced | it is removed, not approximated; the justification uses only numbers read at pack time |
| The audit form asks a question the pack does not answer | the row is added to the clause map (form answers are `13.4.2-T1`'s) and, if behaviour-backed, needs new evidence before filing |
| A deletion request completed after the backup PITR point during the audit window | the pack cites the restore re-apply rule (11.6.1-T1, 13 README K5) and the `completed_at` timeline |
