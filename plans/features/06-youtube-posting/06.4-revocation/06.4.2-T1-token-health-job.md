# 06.4.2-T1 — `TokenHealthJob`: refresh check, Google-page revoke, 30-day data refresh

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

The daily allow-listed system job that keeps the platform inside the Google policy timers: a refresh failure classified `TokenRevoked` (the user revoked us on the Google security page) moves the connection to `revoked`, wipes the tokens and opens the **30-day** deletion request; a failure classified `PlatformIncident` changes nothing and hands off to 06.4.2-T2; and every connection whose stored Authorized Data is older than 25 days is re-verified (channel title refreshed, video ids/status refreshed or the vanished ids dropped) so the 30-day re-verification duty is met with margin (README D16, F16; G13).

## Inputs

- Contract: `../README.md` D16 (job behaviour, `MaxConnectionsPerRun` 500, 25-day trigger, batches of 50), D13 (outbox), D17 (logs/audit), D19 (`FakeGoogleServer`, `FakeClock`), R2/R4 (30 days, `google_revoke`), R12 (`ISystemWorkQuery` + `ISystemContext.For`, already used the same way by `PublishYouTubeHandler`), R14 (`videos.list` quota + `uploadStatus`), R15 (staging Testing project).
- **`ITokenService.GetAccessTokenAsync(Guid connectionId, ct) → ErrorOr<ChannelAccessToken(AccessToken, ExpiresAt)>` — consumed, not declared here.** Declared and implemented by **06.1.2-T2** (`src/NightTales.Infrastructure/Publishing/TokenService.cs`, Scoped, registered in both Api and Worker roots): `SELECT … FOR UPDATE` + re-read after the lock; `token_expires_at ≥ now + 5 min` → returns the current token with **no** Google call; otherwise refreshes and, on success, **calls `connection.MarkRefreshed(...)` itself** — this job never calls `MarkRefreshed` directly. On failure the error propagates so this job can classify it. Given a daily cadence against ~1-hour access tokens, a genuine refresh attempt happens on effectively every run for an active connection.

GoogleReason)`, `enum OAuthErrorOutcome { Transient, TokenRevoked, PlatformIncident, Quota, Validation }`. This is the **single** mapping shared with the upload path (`PublishYouTubeHandler`) — no second switch over Google reasons may exist in this job.
- Consumed, not declared: `IYouTubeClient.GetMyChannelAsync`/`GetVideosAsync` (06.2.3-T1's port half), `IDeletionRequests.CreateAsync` (13.3.1-T1), `ISystemContext.For` + `ISystemWorkQuery` (09 README:250-256), `IBackgroundJob` + `IRecurringJobRegistration` (09 README:287-289), `IUnitOfWork` (09.1.3-T1).
- Explicit non-goal: no incident row is written here (06.4.2-T2 owns the `RaiseAsync` call), and no hold sweep over publications — **YR24** makes the hold lazy and per row, applied by *any* job that owns the row and holds its lock (upload, poll, go-live), never by `TokenHealthJob` and never as a batch (plan §4 UC2/UC3, R18).

## Design

**Options** — new `src/NightTales.Application/Features/Publishing/TokenHealth/TokenHealthOptions.cs` (section `TokenHealth`) [INFERENCE names; CR request to README D11's key list]:

```csharp
public sealed class TokenHealthOptions
{
    public const string SectionName = "TokenHealth";
    public string RunAtUtc { get; init; } = "03:00";          // cron source for the recurring registration
    public int MaxConnectionsPerRun { get; init; } = 500;      // D16
    public int DataRefreshAfterDays { get; init; } = 25;       // D16 (30-day duty, 5-day margin)
    public int VideoBatchSize { get; init; } = 50;             // G1/R14
}
```

**Sweep read — extends the already-existing `ISystemWorkQuery`, no new port, no allow-list CR.** `PublishYouTubeHandler` (06.2.3-T2) already resolves `(id, user_id)` cross-user through `ISystemWorkQuery` (R12) — this task adds one member to the **same** interface:

```csharp
Task<IReadOnlyList<YouTubeHealthCandidate>> GetYouTubeConnectionsForHealthAsync(int limit, CancellationToken ct);
// YouTubeHealthCandidate(Guid Id, Guid UserId, string OAuthClientId)
```
`WHERE platform = 'youtube' AND status IN ('active','expired') ORDER BY last_verified_at NULLS FIRST LIMIT @limit`. The `expired` rows are included deliberately: an upload-side 401 sets `expired` (06.2.3-T2), and excluding them would leave a connection's 30-day duty unmet forever if nobody retries it manually.

Every other read this job performs — the connection's own publications for the video-id refresh, `LastVerifiedAt` for the 25-day trigger — happens **after** `ISystemContext.For(userId)` is set for that row, so it is an ordinary tenant-filtered `IAppDbContext` query. **No second cross-user port and no `IgnoreQueryFilters` anywhere else in this job.**

**Job** — `src/NightTales.Application/Features/Publishing/TokenHealth/TokenHealthJob.cs`:

```csharp
[JobPolicy(Retries = 2)]
public sealed class TokenHealthJob : IBackgroundJob          // no domain parameter (09 README:287)
{
    public Task RunAsync(CancellationToken ct);                // delegates to TokenHealthRunner
}
```

Registration — `src/NightTales.Worker/Jobs/Publishing/TokenHealthRecurringRegistration.cs` implementing `IRecurringJobRegistration`: stable id `token-health`, cron from `TokenHealth:RunAtUtc`, queue `publish`, registered **only while `youtube_publish` is on** (README D1; the 02.8.3-T1 pattern).

**Runner** — `src/NightTales.Application/Features/Publishing/TokenHealth/TokenHealthRunner.cs`:

```csharp
var candidates = await _systemWorkQuery.GetYouTubeConnectionsForHealthAsync(o.MaxConnectionsPerRun, ct);
foreach (var group in candidates.GroupBy(c => c.OAuthClientId))
{
    if (await ShouldSkipClientAsync(group.Key, ct)) continue;   // 06.4.2-T2's pre-check; see that task
    foreach (var row in group)
    {
        using var scope = _scopeFactory.CreateScope();
        using var system = scope.ServiceProvider.GetRequiredService<ISystemContext>().For(row.UserId);
        await ProcessRowAsync(scope.ServiceProvider, row, ct);      // own transaction per row
    }
}
```

`ProcessRowAsync`:

1. `ITokenService.GetAccessTokenAsync(connectionId, ct)`. Success ⇒ proceed to the data refresh (step 3) — **this job does not call `MarkRefreshed`**; `ITokenService` already did, when it rotated the tokens.
2. Failure ⇒ obtain a `YouTubeFailure` from the error (see the [OPEN] item above) and call `OAuthErrorClassifier.Classify(failure)`:
   - `Outcome == TokenRevoked` ⇒ `connection.Revoke(now)` + `IDeletionRequests.CreateAsync(userId, DeletionScope.Channel, targetId: connectionId, DeletionReason.GoogleRevoke, ct)` (`due_at = now + 30 d`, the engine computes it) + outbox `channel_connection_changed.v1 { connectionId, userId, status: "revoked" }` + audit `publishing.channel_revoked_google` (**README §10 YR21** confirms this action is now in D17's list — no longer an open CR) + metric `youtube_token_health_rows_total{outcome="revoked"}`; **no** data refresh for this row this run;
   - `Outcome == PlatformIncident` ⇒ **06.4.2-T2's branch entirely** (that task's file): call `RaiseAsync` and skip the rest of the client group; this job's own code does nothing else for this outcome (no status change, no request, no hold — R18);
   - any other outcome / a transport failure ⇒ leave the row untouched, count `youtube_token_health_rows_total{outcome="failed"}`, tomorrow's run retries it.
3. `RefreshStoredDataAsync(connection)` — only when `LastVerifiedAt < now − TokenHealth:DataRefreshAfterDays` (25 days):

```csharp
var channel = await _youTube.GetMyChannelAsync(token, ct);            // 1 unit, general bucket (R14)
if (channel.ExternalAccountId != connection.ExternalAccountId) { connection.MarkError(now); return; }  // [INFERENCE]
connection.RefreshFromApi(channel.Title, now);                         // sets last_verified_at too (no second setter)
var ids = await _db.Publications                                       // ordinary tenant-scoped query — no special port
    .Where(p => p.ChannelConnectionId == connection.Id && p.ExternalPostId != null)
    .Select(p => new { p.Id, p.ExternalPostId }).ToListAsync(ct);
foreach (var batch in ids.Chunk(o.VideoBatchSize))                     // ≤ 50 ids, G1/R14
{
    var videos = await _youTube.GetVideosAsync(token, batch.Select(x => x.ExternalPostId!).ToArray(), ct);  // 1 unit
    foreach (var v in batch)
        if (videos.All(x => x.Id != v.ExternalPostId) || videos.Single(x => x.Id == v.ExternalPostId).UploadStatus == "deleted")  // G6
            await _db.Publications.Where(p => p.Id == v.Id).ExecuteUpdateAsync(s => s.SetProperty(p => p.ExternalPostId, (string?)null), ct);
        else
            await _db.Publications.Where(p => p.Id == v.Id).ExecuteUpdateAsync(s => s.SetProperty(p => p.PlatformPayload, /* merge videoStatus */ default!), ct);
}
```

Quota: these two calls use the **general** 10,000-unit bucket (R14) and never `IQuotaLedger`, which counts the 100/day **insert** bucket (D10/R16). A 429/`quotaExceeded`, a 5xx after retries, or a `403` on either call skips the connection's refresh, nulls **nothing**, counts a metric, and retries tomorrow.

Run summary: one log line + one counter series per run (`considered / refreshed / revoked / skipped-by-incident / failed`), ids and counts only.

`MarkError(now)` is used for the channel-id-mismatch condition above so the row stops being attempted every day [INFERENCE].

`platform_incident_cleared.v1` needs no handler in this folder: exclusion of a broken client is derived **live**, every run, from `HasOpenIncidentAsync` (06.4.2-T2's pre-check) — there is no persisted skip-state anywhere in this job for a clear event to invalidate. 02.8.3-T4 already owns the series-unpause consumer of that event (`../02-story-writing/02.8.3-cadence-publishing/02.8.3-T4-…:29`). `../06.2.3-upload/plan.md:214`'s note that "06.4.2-T1 resumes the client" describes this implicit, stateless resume — not a registered handler — and is recorded here as a CR to clarify that line's wording, not as a requirement to build one.

## Acceptance checks

- [ ] With a refresh failure classified `TokenRevoked` the connection is `revoked`, both ciphertexts are `NULL`, one `data_deletion_requests` row exists with `scope = channel`, `target_id = connectionId`, `reason = google_revoke`, `due_at ≈ now + 30 d`, and one `channel_connection_changed.v1` outbox row carries `{ connectionId, userId, status: "revoked" }`.
- [ ] With a refresh failure classified `PlatformIncident` no connection changes status, no `data_deletion_requests` row is created, and the row's own handling is entirely 06.4.2-T2's — this job's `ProcessRowAsync` performs no further action on that outcome.
- [ ] A `TokenRevoked` failure on one row does not stop the run: the following row of a *different* client is still processed.
- [ ] An `expired` row whose refresh succeeds becomes `active` with rotated ciphertext that unprotects, `last_verified_at` advanced, and no deletion request created (`ITokenService` performs the transition internally).
- [ ] With `FakeClock` at +26 days since `last_verified_at`, the channel title is refreshed and a video id absent from `videos.list` (or `uploadStatus = deleted`) becomes `NULL` **while the publication row stays**; a present id keeps its id.
- [ ] With `videos.list` answering `429`, neither the title nor any `external_post_id` changes and `platform_quota_usage` is untouched.
- [ ] The sweep processes at most `TokenHealth:MaxConnectionsPerRun` rows (config 2 with 3 candidates ⇒ one deferred).
- [ ] A transport failure on one row leaves it untouched, counts a failure, and does not fail the job.
- [ ] The recurring registration is absent while `youtube_publish` is off and present (stable id `token-health`) when it is on.
- [ ] A `platform_incident_cleared.v1` event requires no consumer in this folder: the very next scheduled run for that client refreshes normally purely because `HasOpenIncidentAsync` now returns `null` (no open incident).
- [ ] The run summary and every log line contain ids, statuses and counts only — no channel title, no video title, no token.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `TokenRevoked` (Google-page revoke, expiry) | revoke + 30-day request + outbox, no data refresh |
| `PlatformIncident` | nothing changes here; 06.4.2-T2 raises the incident and the client is skipped for the rest of the run |
| transport / 5xx / unmapped 4xx on refresh | row untouched, retried tomorrow |
| `channels.list` returns a different channel id | row → `error`, refresh skipped (no silent data mix-up) [INFERENCE] |
| `videos.list` returns an empty `items` or `uploadStatus = deleted` | `external_post_id = NULL`, publication row kept |
| `videos.list` 429 / 403 quota | skip the refresh, null nothing, metric, retry tomorrow; never debit the upload ledger |
| More candidates than `MaxConnectionsPerRun` | the oldest `last_verified_at` rows go first; the rest wait for tomorrow |
| A row is deleted between the sweep and the row's scope | the row is skipped with a debug log; the run continues |
| Job crashes mid-run | rows already committed keep their new state; the next run re-derives everything from the DB |
| Staging Testing project (7-day refresh tokens) | weekly `TokenRevoked` → revoke + 30-day request — expected (R15), not a bug |
| `ITokenService`'s internal refresh races with `PublishYouTubeJob`'s own call | both go through the same `FOR UPDATE` lock inside `ITokenService`/`TokenService` — this job never opens a second lock path |
