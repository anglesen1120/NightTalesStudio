## Goal

Turn `TokenHealthJob`'s `PlatformIncident` classification into a pre-check plus a raise call against 06.2.3-T2's already-shipped incident store. Every other effect — the DB row, the idempotency, the outbox event, the audit row, the hold, the alert — is entirely 06.2.3-T2/T3's already-built mechanism (**README §10 YR24/YR25**). This task adds no store, no table, no classifier, no hold sweep, no outbox event and no audit row of its own (README D14, D16; high-level §8 risk row).

## Design

**Edit `src/NightTales.Application/Features/Publishing/TokenHealth/TokenHealthRunner.cs`:**

```csharp
private async Task<bool> ShouldSkipClientAsync(string oauthClientId, CancellationToken ct)
{
    var open = await _incidents.HasOpenIncidentAsync("youtube", oauthClientId, ct);   // ErrorOr<Guid?>
    // fail OPEN on a store error: a store outage must not silently stop the 30-day duty for every
    // connection of an otherwise-healthy client — log + count, then proceed as if no incident is open.
    if (open.IsError) { _logger.LogWarning("HasOpenIncidentAsync failed for {ClientId}", oauthClientId); return false; }
    return open.Value is not null;   // Guid?: non-null = the open incident's id, null = no open incident (shipped 06.2.3-T2 signature)
}
```

Wired into the group loop (06.4.2-T1's runner): before the first row of each `oauthClientId` group, `ShouldSkipClientAsync` → `true` abandons the whole group and counts `youtube_token_health_skipped_incident_total{oauth_client_id}`.

Inside `ProcessRowAsync`, the `PlatformIncident` branch — **the entire footprint of this task**:

```csharp
if (classification.Outcome == OAuthErrorOutcome.PlatformIncident)
{
    var raised = await _incidents.RaiseAsync("youtube", row.OAuthClientId, classification.ErrorCode, _clock.UtcNow, ct);
    if (raised.IsError) _logger.LogWarning("RaiseAsync failed for {ClientId}", row.OAuthClientId);
    // that's it: RaiseAsync itself decides idempotency (IsNew) and writes both the audit row and the
    // outbox event when new (YR25) — this task adds no audit call, no outbox call, no metric of its own
    // beyond the diagnostic skip counter.
    _skippedThisRun.Add(row.OAuthClientId);   // the remainder of the group is abandoned by the outer loop
    return;
}
```

Connections/tokens/`revoked_at` are left **untouched** on this path (invariant 6); no `IDeletionRequests` call; no `publications` write of any kind (the hold, if it applies at all to any of this client's rows, happens lazily inside whichever job later touches that specific publication — YR24, not here).

- [ ] With an open `platform_incidents` row for the client, a run refreshes **no** connection of that client, and calls `RaiseAsync` **zero** times.
- [ ] With `invalid_client` on two connections of one client: `RaiseAsync` is called at most once per client per run; both connections stay `active` with their tokens and `revoked_at IS NULL`.
- [ ] Exactly one `platform_incidents` row and one `publishing.incident_raised` audit row exist after the run — both written by `RaiseAsync` itself (**YR25**), asserted by `TokenHealth_InvalidClient_WritesOneAuditRowOnlyWhenNew`.
- [ ] **No** `data_deletion_requests` row is created on any `PlatformIncident` path (asserted by count, after a run that also produces a legitimate `TokenRevoked` request for a different client).
- [ ] This task's code makes **zero** writes to `publications` (no hold sweep, YR24) — a `scheduled` row of the affected client is untouched by `TokenHealthJob`/06.4.2-T2 itself.
- [ ] A store outage (`HasOpenIncidentAsync` returns an error) neither stops the run nor silently skips the client forever; the failure is logged and counted, and the group is treated as healthy for that run.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two rows of one client fail in the same run | at most one extra `RaiseAsync` call per client, since the group is abandoned after the first `PlatformIncident` hit |
| The incident is cleared (06.2.3-T3's CLI) while this run is mid-group | this run still skips the group (checked once per group, before the first row); the *next* run refreshes normally because `HasOpenIncidentAsync` now returns `null` (no open incident) |
| Store outage on `RaiseAsync` itself (not just `HasOpenIncidentAsync`) | logged and counted; the row's transaction leaves the row untouched (same as a transport failure) rather than silently dropping the incident signal, since the next run's classifier hit retries the raise |
| Both `PublishYouTubeHandler` and `TokenHealthJob` raise for the same client near-simultaneously | the store's partial-unique index resolves it to one row; `RaiseAsync` itself decides which caller sees `IsNew == true` and writes the one audit row + one outbox event (YR25) — neither caller needs its own guard |
| A `Transient`/`Quota`/`Validation`/`TokenRevoked` outcome reaches this branch | never happens — this branch is entered only for `Outcome == PlatformIncident`; the other outcomes are 06.4.2-T1's own branches |
| Publications of the affected connections are never immediately held | expected by design (YR24: lazy per-row, no raise-time sweep) — each publication is held only when its own job next touches it |
