# 06.4.3-T1 — YouTube channel-scope deletion handler + due-date alert

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 06.4.3 | S (0.5) | BE | 06.4.1-T1, 13.3.1-T1 | 06.5.1-T1 | P · M1 |

## Goal

Make the 7/30-day promise real: implement `IDeletionScopeHandler` for `scope = channel` so 13.3.1-T1's `DataDeletionJob` can delete everything YouTube-derived for a disconnected channel — tokens, channel identity, `external_post_id`, `platform_payload` — while keeping the publication rows that carry our own consent/audit record; and prove that a channel-scope request participates correctly in the engine's due-date tracking so its ≤24 h alert covers it (README D15, D16; 13 README D4/F4).

## Inputs

- Engine contract (13 README D4:48, R5/R6): `IDeletionScopeHandler { DeletionScope Scope; Task<ErrorOr<DeletionResult>> ExecuteAsync(DeletionRequest r, ct) }`, registered by the owning plan; `DataDeletionJob` hourly, allow-listed system job, batch ≤ 20, `FOR UPDATE SKIP LOCKED`, per-row `ISystemContext.For(r.UserId)`; on success the engine sets `completed_at`, writes audit `account.data_deleted` (`support`, `user`), and updates metrics `deletion_requests_open` / `deletion_request_overdue_total`; it alerts when any open request has `due_at − now < 24 h` (an 11.6.2-T1 rule). Restore re-apply: `nts-worker deletions reapply --since <PITR timestamp>` replays **completed and still-open** requests (**YR12**).
- **YR7 (TL ruling, README §10): the return shape is 13.3.1-T1's, not this task's.** `IDeletionScopeHandler.ExecuteAsync(DeletionRequest r, ct) → ErrorOr<DeletionResult(int ObjectsDeleted, int RowsAffected)>`; failures are plain `Error`s, never a `DeletionResult` variant. This task adapts to that shape; it does not invent `Completed`/`Failed` factory methods.
- **YR12 (TL ruling): restore re-apply on a row a PITR restore returned to `active`.** The channel handler must revoke first (tokens nulled, status `revoked`) **then** purge — idempotent either way (whether the row was already `revoked` or is a restored `active` row predating the disconnect).
- **YR14 (TL ruling): distinguish "gone" from "not visible".** A `target_id` this handler cannot see under the tenant filter must be resolved with an **allow-listed existence check** before deciding the outcome: truly gone (hard-deleted) → a normal completion with zero counts; exists but belongs to another user (**not visible**, a corrupted/foreign request row) → an `Error` (the engine keeps the request open and alerts), never silently reported as done.
- Request shape: `data_deletion_requests(user_id, scope, target_id, reason, requested_at, due_at, completed_at)` with `target_id` = the connection id (13 README K4 + D4, `13 CR-1`).
- `../README.md` D15 (the exact scrub list), D18 (`publications (channel_connection_id)` index), §5.4 (timers).
- **`ChannelConnection.Revoke(now)` and `PurgeYouTubeData(now)` are declared and domain-tested by 06.1.2-T2** (`agent://Y06Connect`, confirmed 2026-09-25): `PurgeYouTubeData` requires `Status == Revoked` (throws otherwise) and nulls `AccessTokenEnc`, `RefreshTokenEnc`, `ExternalAccountId`, `DisplayName` (both identity columns `text NULL`, no placeholder). This task consumes both methods; it declares neither and writes no domain test for either.
- **Cross-user existence check (YR14) — extends the already-allow-listed `ISystemWorkQuery`** (same pattern 06.4.2-T1 uses for its sweep, R12): `Task<bool> ChannelConnectionExistsAsync(Guid id, CancellationToken ct)` [INFERENCE member name] — a plain existence probe, no row data returned, so it cannot leak another user's channel details even though it bypasses the tenant filter.
- Produced by 06.4.1-T1: the `channel` requests this handler executes (`scope = channel`, `reason = in_app_revoke`, `due_at = now + 7 d`) and by 06.4.2-T1: `google_revoke` rows at 30 d.

## Design

**`src/NightTales.Application/Features/Publishing/Deletion/ChannelDeletionScopeHandler.cs`**

```csharp
public sealed class ChannelDeletionScopeHandler : IDeletionScopeHandler
{
    public DeletionScope Scope => DeletionScope.Channel;

    public async Task<ErrorOr<DeletionResult>> ExecuteAsync(DeletionRequest r, CancellationToken ct)
    {
        if (r.TargetId is not { } connectionId) return Error.Failure("channel_target_missing");   // YR7: failures are Errors

        var connection = await _db.ChannelConnections.FirstOrDefaultAsync(c => c.Id == connectionId, ct);   // tenant-scoped
        if (connection is null)
        {
            // YR14: "gone" (hard-deleted) vs "not visible" (exists, foreign) — never conflate the two
            var exists = await _systemWorkQuery.ChannelConnectionExistsAsync(connectionId, ct);   // allow-listed, no tenant filter
            return exists
                ? Error.Failure("channel_target_not_visible")               // keeps the request open, the engine alerts
                : new DeletionResult(ObjectsDeleted: 0, RowsAffected: 0);   // truly gone: idempotent no-op

        }

        // YR12: a restore re-apply can replay this request against a row a PITR restore brought back to
        // `active` (predating the disconnect that created the request). Revoke first, then purge — the
        // sequence is idempotent whether the row was already `revoked` or needs revoking now.
        if (connection.Status != ChannelConnectionStatus.Revoked)
            connection.Revoke(_clock.UtcNow);

        connection.PurgeYouTubeData(_clock.UtcNow);          // consumed, not declared here (06.1.2-T2)
        var scrubbed = await _db.Publications
            .Where(p => p.ChannelConnectionId == connectionId)
            .ExecuteUpdateAsync(s => s                                      // one batched statement, no per-row loop
                .SetProperty(p => p.ExternalPostId, (string?)null)
                .SetProperty(p => p.PlatformPayload, (JsonDocument?)null), ct);

        _logger.LogInformation("channel deletion scope executed {ConnectionId} {Publications}",
                               connectionId, scrubbed);                     // ids and counts only
        return new DeletionResult(ObjectsDeleted: 0, RowsAffected: 1 + scrubbed);   // [INFERENCE mapping, see Notes
    }                                                                               // — channel scope deletes no blob/object
}
```

- **`DeletionResult(ObjectsDeleted, RowsAffected)` mapping [INFERENCE, YR7 fixes the type, not the channel-scope semantics]:** `ObjectsDeleted = 0` always (this scope deletes no S3/blob objects — unlike the `episode` handler, which composes 09.7.3-T1's asset delete); `RowsAffected = 1 (connection) + scrubbed publications`. Recorded as an assumption to confirm against 13.3.1-T1's own usage of the two fields.
- **What is deliberately kept** (and why): `publications.title`, `description`, `tags`, `privacy`, `consent_at`, `consent_text_version`, `consent_source`, `autopilot_authorization_id`, `veto_notice_sent_at`, `status` — the user typed them into our form and they are our consent/audit record (13 §5.4 "keeps publication rows"; 06 README D15 lists only YouTube-derived fields). The connection row itself is kept `revoked` as proof of the revocation event.
- **`ExecuteUpdateAsync`** (EF Core bulk update, no tracking, no `SaveChanges` per row) keeps the statement count bounded regardless of connection size; `IUnitOfWork` commits once (the engine's row transaction).
- **Registration** — add the handler to the Worker composition root's `IDeletionScopeHandler` collection (13 D4); the Worker must fail fast on a duplicated or missing `Channel` handler.
- **`IgnoreQueryFilters` used exactly once, narrowly**: the YR14 existence check goes through `ISystemWorkQuery` (already allow-listed, R12) and returns a `bool` only — no row data crosses the tenant boundary. Every other query in this handler stays tenant-filtered.

**Due-date alert — engine's mechanism, this task's evidence.** 13.3.1-T1's `DataDeletionJob` maintains `deletion_requests_open` (gauge) and `deletion_request_overdue_total` (counter); an 11.6.2-T1 rule fires on "any open request has `due_at − now < 24 h`", evaluated and de-duplicated by the alerting backend (the same shape as 06.2.3-T3's `platform_incident_open > 0 for 5m` rule — no `alerted_at` column anywhere). This task builds no alert rule and no metric of its own, but it **does** prove the channel-scope input to that mechanism is correct: a channel request the engine has not yet completed, with `due_at` inside the 24-h window, must still read as open (`completed_at IS NULL`) at the point the alert rule would evaluate it, and a request this handler completes must stop being counted as open on the very next evaluation.

## Steps

1. Write `ChannelDeletionScopeHandler` per YR7/YR12/YR14 above.
2. Extend `ISystemWorkQuery` with `ChannelConnectionExistsAsync` (additive member, same interface 06.4.2-T1 already extends — no second cross-user port).
3. Register the handler in the Worker composition root; extend the composition test that asserts one handler per `DeletionScope`.
4. Integration tests: run the real `DataDeletionJob` over a channel request (Testcontainers PostgreSQL) rather than calling the handler directly, so the engine's `SystemContext`, `completed_at`, the audit `account.data_deleted` and the open/overdue metric state are all exercised.
5. Add the restore-re-apply case (a request replayed against a restored `active` row) and the gone-vs-foreign case explicitly, per YR12/YR14.

## Acceptance checks

- [ ] Driving the engine with a channel request whose connection is already `revoked` leaves both token ciphertexts `NULL`, `external_account_id IS NULL`, `display_name IS NULL`, status stays `revoked`, and the return is `DeletionResult(ObjectsDeleted: 0, RowsAffected: 1 + publicationCount)`.
- [ ] Driving the engine with a channel request whose connection was restored to `active` by a PITR restore (YR12) revokes the row (tokens nulled, status `revoked`) and then purges it in the same call — one pass, no partial state, re-running it a second time changes nothing further.
- [ ] Every publication of that connection has `external_post_id IS NULL` and `platform_payload IS NULL`, and **all** rows still exist with `title`, `description`, `tags`, `consent_at`, `consent_text_version`, `status` unchanged.
- [ ] A request whose connection row was hard-deleted (the existence check also finds nothing) completes with `DeletionResult(0, 0)` and does not fail the job (YR14, the "gone" branch).
- [ ] A request whose `target_id` exists but belongs to another user (the existence check finds it, the tenant-filtered read does not) returns an `Error` — the engine keeps the request open and alerts; nothing is written for it (YR14, the "not visible" branch — distinct from the "gone" branch above).
- [ ] The engine sets `completed_at` before `due_at` for a 7-day channel request in the test; one audit row `account.data_deleted` exists (the engine's own audit, not written by this handler).
- [ ] A channel-scope request with `due_at = now + 23 h` and `completed_at IS NULL` still reads as open (counted by `deletion_requests_open`) at that point, so the engine's ≤24 h alert rule has a true condition to fire on; the same request, once this handler completes it, no longer reads as open on the next evaluation.
- [ ] The handler's log line contains the connection id and counts only — no title, no token, no channel name.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Connection row hard-deleted (truly gone) | `DeletionResult(0, 0)` — the request is done, not failed (YR14 "gone" branch) |
| `target_id` exists but belongs to another user | `Error` → the engine keeps the request open and alerts; nothing is written (YR14 "not visible" branch) |
| Connection restored `active` by a PITR restore, request replayed | revoke then purge in one call (YR12) — never throws on the precondition, because this handler revokes first when needed |
| A publication is being processed by another transaction | the batched update waits on the row lock — bounded by the engine's hourly batch of 20 |
| Handler throws (DB error) | the request stays open, the engine's retry/alert path applies; no partial commit (one transaction) |
| Duplicate `Channel` handler registered | Worker startup fails fast (composition test) — a second handler would silently double-scrub |
| A channel-scope request exists while `youtube_publish` is off | the engine still runs it (plan §11): deletion is a policy duty, not a feature |
| The user reconnects the same channel after deletion | a **new** connection row is created by 06.1.2-T2; the purged row's `external_account_id` is `NULL`, so it can never collide with the partial unique index (which only excludes `revoked` rows anyway); the old row stays as the deletion record |
