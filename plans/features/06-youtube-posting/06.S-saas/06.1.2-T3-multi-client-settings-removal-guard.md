## Goal

The operator can run more than one Google OAuth client (for example a production client and a staging/verification client) from `system_settings` — no config edit, no restart — and cannot delete a client id that live `channel_connections` rows are pinned to. Admins can see how many connections each client carries. The connect e-mail, re-auth and single-client pinning are **already P** (`06.1.2-T1`/`06.1.2-T2`, Part A F19/CR-7) and are not touched here.

## Design

**Settings model (integration `youtube`).**

| Key | `value jsonb` | Notes |
|---|---|---|
| `oauth.active_client_id` | `"<clientId>"` (JSON string) | must exist in `oauth.clients`; a value not in the map → `oauth_client_unknown` |
| `oauth.clients` | `{ "<clientId>": { "displayName": "NightTales prod", "clientSecretKey": "YOUTUBE_CLIENT_SECRET", "createdAt": "2026-09-25T00:00:00Z" } }` | **no secret material** (F27): `clientSecretKey` names a secret resolved through the P path (Part A C12); if the row is created as a secret (`is_secret = true`) 09.10.1's Data Protection purpose `settings.v1/youtube/<key>` covers it — this task adds no purpose |

`YouTubeClientSettings` (Application record: `ActiveClientId`, `IReadOnlyDictionary<string, YouTubeClientEntry>`) + `IYouTubeClientSettingsReader` (Application port) with the Infrastructure implementation `SystemSettingsYouTubeClientReader` (`IAppDbContext`, `IMemoryCache` 30 s keyed `youtube.client_settings`, `ILogger`). No row → `null` (the fallback signal); a malformed `value jsonb` → `Error.Failure("settings_malformed")` logged once per cache window and treated as `null` (safe: P behaviour).

**Resolver.** `SettingsOAuthClientResolver : IOAuthClientResolver` (Infrastructure/Publishing): `ActiveClientId` → from the settings (fallback → the config resolver); `ResolveAsync(oauthClientId, ct)` → settings entry → secret via the P secret accessor; no entry, or `clientSecretKey` resolves to nothing → `Error.NotFound("oauth_client_unknown")`. Secrets are never cached in the settings model (only the resolved secret, inside the token exchange path, as in P). Registration: a small `CompositeOAuthClientResolver` (or a factory delegate) picks the settings resolver when `IYouTubeClientSettingsReader.ReadAsync()` is non-null and the config resolver otherwise — the choice is evaluated per call, so a row added at runtime takes effect without a restart (O7). The decision helper is unit-tested; the composition root registers both.

**Removal guard.** `IYouTubeClientRemovalGuard.EnsureRemovableAsync(IReadOnlyCollection<string> proposedClientIds, CancellationToken ct) → ErrorOr<Success>` — Application port, Infrastructure implementation `YouTubeClientRemovalGuard`:
1. `proposedClientIds` must contain the current `ActiveClientId` → else `Error.Conflict("oauth_client_in_use")` with `{ clientId = activeId }`.
2. For every id currently in `oauth.clients` but not in `proposedClientIds`: `SELECT oauth_client_id, COUNT(*) FROM channel_connections WHERE oauth_client_id = ANY(@removed) GROUP BY 1`; any count > 0 → `Error.Conflict("oauth_client_in_use")` with metadata `{ clientId, connections }` (first offender, deterministic by id).
3. Read-only check; the caller (`PUT /admin/settings/{integration}`, 09.10.1-T1) invokes it inside its transaction before persisting (CR-17), so a connect that commits between check and write cannot be missed — the same transaction's row lock on the settings row serialises concurrent writers.
The count query is cross-tenant (`channel_connections` is `IUserOwned`), so the guard lives in `src/NightTales.Api/Features/Admin/YouTube/` per `plans/09-backend-api.md:94` (it returns only counts, never channel rows).

**Admin counts.** `GetYouTubeClientSettingsQuery() : IQuery<YouTubeClientSettingsDto>` (`[NotAudited]`; reads are not audited — if the 09.3.6-T1 arch test demands one of the three attributes on the query type, this is it) in `Features/Admin/YouTube/`. One grouped statement over `channel_connections` (`AsNoTracking`, `IgnoreQueryFilters`) joined in memory to the settings map:

```csharp
public sealed record YouTubeClientSettingsDto(string ActiveClientId, IReadOnlyList<YouTubeClientDto> Clients);
public sealed record YouTubeClientDto(string ClientId, string DisplayName, bool Active, int Connections,
    int ActiveConnections, DateTimeOffset? LastConnectedAt, bool InUse);
```

Route `GET /api/v1/admin/youtube/clients` (admin/owner policy + MFA), placed in `src/NightTales.Api/Endpoints/Admin/YouTubeClientEndpoints.cs`; also behind `RequireFeature("youtube_publish")` (Part A D1). No token column, no channel name, no e-mail in the projection.

**Error codes (09 §5.4 catalogue via CR-17):** `oauth_client_in_use` (409), `oauth_client_unknown` (404).

## Acceptance checks

- [ ] With no `youtube` row in `system_settings`, `IOAuthClientResolver` behaves exactly as P (the config resolver answers) and `GET /channels` still works — the O7 fallback holds.
- [ ] Adding the two keys with a second client id and pointing `oauth.active_client_id` at it changes the client used by a **new** connect without a restart; an existing connection keeps its pinned id.
- [ ] `ResolveAsync` for an id missing from the map returns `oauth_client_unknown` (404) and never falls back to the active client.
- [ ] No secret-shaped value exists in `system_settings.value jsonb` for `youtube` and none appears in the log sink (scan test).
- [ ] Removing a client id pinned by ≥ 1 `channel_connections` row → 409 `oauth_client_in_use` with the count; the settings row is unchanged (no partial write).
- [ ] A proposal that drops the active client id → 409 `oauth_client_in_use` even when no connection is pinned.
- [ ] `GET /api/v1/admin/youtube/clients` returns one entry per `oauth.clients` id with `connections`/`activeConnections`/`lastConnectedAt`/`inUse` matching a manual SQL count.
- [ ] The payload contains no access/refresh token, no channel name, no e-mail, no `oauth_client_id` of a connection.
- [ ] A `user`-role token gets 404 on the route; an admin without a fresh MFA step is refused.
- [ ] With `youtube_publish` off, the route answers 404 `feature_disabled`.
- [ ] The grouped count query is the only `channel_connections` statement in the handler (no N+1) and it uses `IgnoreQueryFilters` only in `Features/Admin`.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| No `youtube` row in `system_settings` | P config resolver answers (O7); no error, no log noise beyond a debug line |
| `oauth.clients` present but empty, or missing `oauth.active_client_id` | `settings_malformed` logged once per cache window; treated as "no settings" → config fallback (safe) |
| A client id removed from `oauth.clients` while a connection is pinned | refused (409 `oauth_client_in_use`); if it happened out of band, the connection fails with `invalid_client` → `platform_incidents` hold and the operator re-points `oauth.active_client_id` (F17) |
| Two operators write settings concurrently | 09.10.1's settings transaction serialises them; the guard runs inside it (CR-17) |
| `clientSecretKey` names a secret that does not resolve | `oauth_client_unknown` (404); never a null secret passed to the exchange |
| Cache 30 s stale after a settings change | a new connect uses the previous client for ≤ 30 s; documented, accepted (no eviction event exists on `system_settings` in this task) |
| Worker and Api caches disagree | both read the same row; each resolves per call after its own TTL — the pinned id on the connection keeps the exchange correct |
