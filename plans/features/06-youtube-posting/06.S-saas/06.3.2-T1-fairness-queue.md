## Goal

One heavy user cannot consume the whole daily YouTube upload budget of the platform. At most `YouTube:Quota:UploadsPerUserPerDay` (3 in beta) publications per user per Pacific day reach Google; the queue order stays global FIFO by `consent_at`; a capped publication is deferred to the next PT midnight instead of failing; an admin can raise or remove the cap for one user.

## Design

**Schema (this task's expand-only migration `<yyyyMMddHHmm>_06_UserQuotaUsage`)** — spec in `plan.md` §3 (verbatim DDL, both tables). Entities `PlatformUserQuotaUsage` / `PlatformUserQuotaLimit`, configurations `PlatformUserQuotaUsageConfiguration` / `PlatformUserQuotaLimitConfiguration`, DbSets on `IAppDbContext`/`AppDbContext`. Both are **platform tables**: no `id`, no `xmin`, no `HasQueryFilter`, not `IUserOwned` (the 09.2.3-T2 allow-list line is CR-17).

**Ports and implementation.**

```csharp
public interface IUserQuotaLedger
{
    Task<ErrorOr<UserQuotaReservation>> TryReserveAsync(Guid userId, DateTimeOffset now, CancellationToken ct = default);
    Task<ErrorOr<Success>> ReleaseAsync(UserQuotaReservation reservation, CancellationToken ct = default);
}
public readonly record struct UserQuotaReservation(string Platform, Guid UserId, DateOnly Day);
```

`UserQuotaLedger` (Infrastructure/Publishing, **scoped**, `IAppDbContext` + `IOptionsMonitor<YouTubeOptions>` + `NightTalesMetrics`): `TryReserveAsync` is the single `INSERT … ON CONFLICT … WHERE uploads_used < COALESCE((SELECT uploads_per_day FROM platform_user_quota_limits …), @default) RETURNING` statement of `plan.md` §3 — 0 rows → `Error.Conflict("user_upload_limit_reached")` (429), 1 row → `new UserQuotaReservation("youtube", userId, PacificQuotaDay.Day(now))`. `ReleaseAsync` is the single `GREATEST`-guarded `UPDATE` from `plan.md` §3, always success. `PacificQuotaDay` and `IQuotaLedger` are **not** modified (ST8).

**Call site — CR-13 / CR-13b (the only P-side change; applied by this task).** In `PublishYouTubeJob` step 6 and in step 8's session-404 restart: `userQuota.TryReserveAsync(publication.UserId, clock.UtcNow, ct)` **before** `quota.TryReserveAsync("youtube", …)`; `user_upload_limit_reached` → `RescheduleUpload(PublicationErrorCodes.UserUploadLimitReached, NextPtMidnight(clock) + jitter(≤ 10 min))` with **no** global reserve in that run (ST1). The `finally` release mirrors YR19 with the new local flag `reservedUserThisRun` (ST2). `PublicationErrorCodes` gains `UserUploadLimitReached = "user_upload_limit_reached"` (YR27-6: declared once in Domain).

**Queue semantics [DECISION].** The claim query, `PublicationQueueTime` and `PublicationScheduledForUploadHandler` are untouched: a deferred row is skipped by the existing `next_attempt_at` predicate on the P index `(status, next_attempt_at)` (`06.2.5-T1:197`), so a capped user's next row cannot head-block the FIFO order. Cost: one extra conditional `UPDATE` per capped row per day (≤ 1 per user per tick, bounded by the day-long deferral).

**Admin override.** `SetUserQuotaLimitCommand(Guid userId, int uploadsPerDay, string reason)` / `ClearUserQuotaLimitCommand(Guid userId)` (`[Audited]`, `category = publishing`, `visibility = internal`, actions `publishing.user_quota_limit_changed` / `publishing.user_quota_limit_cleared`, `data = { uploadsPerDay, reason }`, `subject_user_id = userId`): upsert/delete `platform_user_quota_limits` with `updated_by` = actor; the effective limit is `COALESCE(override, YouTubeOptions.Quota.UploadsPerUserPerDay)`. Routes `PUT|DELETE /api/v1/admin/users/{userId}/quota-limit` in `Features/Admin/YouTube/` (the only allow-listed `IgnoreQueryFilters` site). Validation: 1–100, reason 3–500 chars, target user exists and is not deleted.

**Options/metrics.** `YouTubeOptions.Quota.UploadsPerUserPerDay = 3` (`YouTube:Quota:UploadsPerUserPerDay`, validated 1–100). `NightTalesMetrics.youtube_user_quota_deferred_total` counter [INFERENCE name].

## Acceptance checks

- [ ] With `UploadsPerUserPerDay = 2`, two concurrent `TryReserveAsync` for one user succeed and the third returns `user_upload_limit_reached`; the row shows `uploads_used = 2`, `uploads_limit = 2`.
- [ ] 20 parallel reserves for one user with limit 3 leave exactly 3 successes (no over-reservation under concurrency).
- [ ] `PUT …/quota-limit { uploadsPerDay: 5 }` lets a fourth reserve succeed immediately (the live `COALESCE`); `DELETE` restores 2 and a further reserve fails.
- [ ] A publication deferred by the cap is `scheduled` with `error_code = user_upload_limit_reached` and `next_attempt_at` = next PT midnight ± 10 min jitter; it is not picked up before that instant.
- [ ] After the resume sequence, the 404-restart sequence and a failed session-create, `platform_user_quota_usage.units_used` for that user equals the day's `platform_quota_usage.units_used` delta attributable to that user's reservations (the two counters never drift; `platform_quota_usage` itself has no user column, so the test attributes via the reservation log) (06 CR-21)
- [ ] A resume that skipped step 6 under YR27-2 does not increment `uploads_used` in that run.
- [ ] `ReleaseAsync` on a missing row / at 0 is a success and leaves `uploads_used`/`units_used` unchanged (idempotent, floor 0).
- [ ] `uploads_used` can never exceed the effective limit (invariant; asserted after the concurrency test).
- [ ] Both override routes write exactly one `audit_logs` row with the actor and the reason; 400 on `uploadsPerDay = 0`/`101` and on a 2-char reason; 404 for an unknown/deleted user; 403 for a `user` role.
- [ ] `platform_user_quota_usage`/`platform_user_quota_limits` have no `IUserOwned` behaviour: a non-admin authenticated read of them returns 0 rows (they are reachable only through the admin folder).
- [ ] The migration is applied by the deploy bundle before the Worker starts (`plan.md` §11); a reserve against a database without the table fails loudly (no silent degradation path exists).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Migration not yet applied (misconfigured deploy) | the reserve fails and the job retries — the deploy order (`plan.md` §11) prevents this; no code path hides it |
| Two Workers reserve the same user's slot simultaneously | the conditional `UPDATE` serialises them; exactly one wins the last slot |
| Override lowered below today's `uploads_used` | no retro effect: today's row already exceeds the new limit and simply refuses further reserves until the next PT day |
| User deleted while a reservation is open | FK keeps the row; the release still works (no user join in the release statement) |
| Clock at the PT midnight boundary | `PacificQuotaDay.Day(now)` decides the row; a reserve at 00:00:00 PT addresses the new day and succeeds even if the previous day was full (the P UC4 semantics) |
| Counter drift found by an operator | the day row is fixed by an operator `UPDATE` (`06.3.1-T1` runbook); the admin view (06.3.3-T1) makes the drift visible |
| Publication cancelled while deferred | no release: it never reserved in this run, and `06.4.1-T1`'s release is gated on `quotaReservedDay` (`06.4.1-T1:49`) — the per-user counter follows the same gate |
