## Goal

The operator launches multi-user publishing gradually — `off` → `admins` → a named beta list → a percentage → `all` — by writing `feature_flags.rules`, with no deploy and no restart, and without ever disturbing work that is already consented, scheduled or uploading.

## Design

**Rules schema for `youtube_publish` (pinned):**

```json
{ "rollout": "off" | "admins" | "list" | "percent" | "all",
  "userIds": ["<guid>"], "percentage": 0, "since": "<ISO-8601>", "note": "beta wave 1" }
```

Unknown keys are ignored (forward compatible); an unknown/absent `rollout` means "no rule" (ST4). `rules` is never interpreted for other flag keys (`tiktok_publish` keeps the P semantics until 07's own slice).

**Evaluator (pure, no I/O).** `RolloutRuleEvaluator.IsEnabled(string key, bool enabled, string? rulesJson, FeatureFlagSubject subject) → bool` in `src/NightTales.Infrastructure/Features/RolloutRuleEvaluator.cs`:

1. `enabled == false` → `false` (P semantics first).
2. `rulesJson` null/empty/unparsable, or `rollout` missing/unknown → `enabled` (fail-safe to P, never fail-open beyond it — ST4).
3. `off` → `false`; `admins` → `subject.IsAdmin`; `list` → `subject.UserId is Guid id && userIds.Contains(id)`; `percent` → `subject.UserId is Guid id && Bucket(key, id) < percentage`; `all` → `true`.
4. A null subject (`UserId == null, IsAdmin == false`) is false for `off`/`admins`/`list`/`percent` and true only for `all`.

`Bucket(key, userId)` = SHA-256 of `Encoding.UTF8.GetBytes($"{key}:{userId}")`, first 4 bytes big-endian as `uint`, `% 100` (ST5) — deterministic per (key, user), BCL only, no new package (F32).

**Surfaces (CR-14/CR-15).**

- `IFeatureFlags` gains `Task<bool> IsEnabledForAsync(string key, FeatureFlagSubject subject, CancellationToken ct = default)`; `IsEnabledAsync(key, ct)` keeps the P meaning (`enabled` only) so system paths, jobs and the CLI are unchanged.
- `public readonly record struct FeatureFlagSubject(Guid? UserId, bool IsAdmin)` in Application/Abstractions/Flags.
- `RequireFeature("youtube_publish")` builds the subject from `ClaimsPrincipal` (`NameIdentifier` + role claim, **no DB read**) and calls the scoped overload; a user outside the rollout gets the same 404 `feature_disabled` body as a disabled flag (BD13: no existence leak).
- The 30 s row cache and `feature_flags_changed.v1` eviction are reused for rules as well (the eviction handler reloads the row; the payload does not change).
- `PATCH /api/v1/admin/feature-flags/{key}` (09.9.1-T1, S) accepts `{ "enabled": bool, "rules": { … } | null }`, validates (unknown `rollout` → 400 `validation_failed`; `percent` ⇒ 0–100; `list` ⇒ 1–500 ids; each id a parseable GUID; `note` ≤ 200 chars), writes the row, audits `feature_flag_changed` and raises the existing event.
- CLI: `nts-worker flags set youtube_publish on --rules '<json>'` / `--rules clear`; `flags list` prints `rollout=<value> users=<n> pct=<n>`.

**Gate scope (O6 / ST6).** The rollout gates **new work only**: route access (via `RequireFeature`), autopilot series planning (one per-run check in 02.8.3's job — CR-16) and publication creation. No rollout value cancels, defers, holds or re-queues an existing `awaiting_consent`/`scheduled`/`uploading` row: `PublishYouTubeJob`, the claim query, `PublicationQueueTime` and the incident sweeps are untouched (ST8).

**Observability.** `feature_flag_evaluations_total{key, result}` counter [INFERENCE name] on the 09.9.3 metric holder, incremented by `IsEnabledForAsync` only (the system overload is deliberately not counted, to keep the series about the user-facing gate).

## Acceptance checks

- [ ] `{"rollout":"off"}` with `enabled = true` → every subject is refused (404 `feature_disabled`), including an admin.
- [ ] `{"rollout":"admins"}` → an `admin`/`owner` token gets 200 on `GET /channels`; a `user` token gets 404 `feature_disabled` with the standard 09.1.4-T1 body.
- [ ] `{"rollout":"list","userIds":[A]}` → A gets 200, B gets 404; A's answer is unchanged after the 30 s cache window.
- [ ] `{"rollout":"percent","percentage":50}` → the same user gets the same answer across ≥ 3 cache windows and across a process restart (sticky bucket); over 10 000 synthetic ids the enabled share is 50 % ± 2 pp.
- [ ] `{"rollout":"bogus"}` → 400 `validation_failed` on the `PATCH`, and a pre-seeded `bogus` value answers like P (the `enabled` value), never an error (ST4).
- [ ] A publication created **before** the rollout was narrowed still uploads (the gate is on new work only): with the user moved to `off`, the existing `scheduled` row reaches Google and the API's create route returns 404.
- [ ] `nts-worker flags set youtube_publish on --rules '{"rollout":"list","userIds":["<a guid>"]}'` writes the row, appends one `audit_logs` row (`feature_flag_changed`, `support`/`internal`) and evicts within the cache TTL (the next request sees the new value in < 1 s when the event lands); `--rules clear` sets `rules = null`; an invalid JSON or schema exits 1 without writing.
- [ ] `flags list` prints `rollout`, `users` count and `pct` and never prints user data beyond the count.
- [ ] An unauthenticated request to a gated route is 401 (auth first), never 404 — the subject build only runs for an authenticated principal.
- [ ] `feature_flag_evaluations_total` increments only on `IsEnabledForAsync` calls (the CLI/system path leaves it flat).

## Tests

- **Unit:** the evaluator's full decision table (each `rollout`, null subject, null/empty/malformed rules, unknown key, extra keys ignored); `Bucket` stability across calls/processes and its distribution; validation rules (percentage ranges, list size, guid parse, note length).
- **Integration:** `RequireFeature` endpoint test with three seeded identities (admin, listed user, unlisted user) × the four `rollout` values; cache behaviour (value change visible after eviction and after 30 s); the `feature_flags`-row round-trip through the `PATCH` handler (audit row + event row).
- **CLI:** the three flag interactions above with a stubbed DB failure (exit 2) and an invalid schema (exit 1).
- **Not tested:** Hangfire registration changes (there are none — ST8), Google (staging gate), the P `enabled`-only path beyond a regression test.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `rules` malformed or a value seeded by hand | treated as "no rule" → the `enabled` answer (ST4); one debug log per cache window |
| `percentage` changed between two requests | already-evaluated subjects may flip (the operator's intent); a subject's answer is stable for a fixed `rules` snapshot |
| `list` with 500+ ids | 400 at write time; the read path additionally ignores ids that do not parse |
| User deleted while listed | the subject id no longer authenticates, so the entry is inert |
| Rollout narrowed during an autopilot run | the per-run check (CR-16) applies from the next series; the current series finishes its planning step; no publication is cancelled |
| Two instances with different cache state | ≤ 30 s divergence, bounded by the TTL; the eviction event closes it faster |
| `enabled = false` and `rules = {"rollout":"all"}` | refused: `enabled` is checked first (P semantics, F13) |
| An admin token with no `nameidentifier` claim | subject = `(null, IsAdmin: true)` → `admins`/`all` true, `list`/`percent` false (documented; the claim is always present for a real token) |
