# 07.1.2-T2 — Re-auth surface, refresh rotation, client pinning and the TikTok token-error classifier

| Story | Size | Area | Depends on | Blocks | Phase / flag |

| 07.1.2 | S (0.5) | BE + Security | 07.1.2-T1, 06.1.2-T2, 09.2.6-T3 | 07.2.1-T1, 10.7.3-T1 (soft) | S · R2 · flag `tiktok_publish` |

## Goal

A TikTok connection never dies silently and a broken **client** never takes every connection down: refreshing writes the returned pair (rotated or unchanged) into the connection row under `FOR UPDATE` in the same transaction that read it; a **named** grant/token error marks that one connection `expired` and surfaces `tiktok_reauth_required` with a re-consent affordance on the existing connect route (`disable_auto_auth=1`); **any** unknown or ambiguous token-endpoint error raises a client-level `platform_incidents` row instead (TT4), which holds that client's work until an operator clears it; every outbound call uses the connection's **pinned** `oauth_client_id`; the `channel_connected` e-mail is queued for a first connect and a reconnect alike.

## Design

**Ports.**
- `ITikTokApiClient.RefreshAsync(string clientKey, string clientSecret, string refreshToken, CancellationToken ct) → ErrorOr<TikTokTokenResponse>` (extends the client 07.1.2-T1 declared; `RefreshToken` is nullable there because rotation is optional, K13).
- `ITikTokOAuthErrorClassifier.Classify(TikTokOAuthFailure(string? Error, string? ErrorDescription, int HttpStatus)) → TikTokOAuthFailureKind { NamedGrantOrToken, ClientLevel, Transient }` (Application, pure, table-driven).

| Evidence | Kind | Effect |
|---|---|---|
| named grant/token error naming the grant or the token (07.1.1-T1's recorded strings, ⚠️) | `NamedGrantOrToken` | connection `expired`; no incident |
| 5xx / transport / timeout | `Transient` | one retry inside the command; then no state change |
| anything else — unknown `error`, unparseable body, ambiguous description | `ClientLevel` | `IPlatformIncidentStore.RaiseAsync(platform: "tiktok", oauthClientId, errorCode)`; the connection is untouched |

**`RefreshTikTokTokenCommand(Guid ConnectionId)`** — `[NotAudited]` (state-only), dispatched by 06.4.2's job, one per row:
1. Re-read the row by id (ids-only job).
2. `SELECT * FROM channel_connections WHERE id = @id AND platform = 'tiktok' FOR UPDATE;` — skip when `status <> 'active'` or when an open incident exists for its client (06 D14).
3. Decrypt both tokens; `ResolveAsync(connection.OAuthClientId)` (pin, never `ActiveClientId`); `RefreshAsync` under the `token` bucket (D6) — a denied acquire ends the command with no state change.
4. On success, same transaction: `UPDATE channel_connections SET access_token_enc = @a, refresh_token_enc = @r, token_expires_at = now + @expiresIn, last_verified_at = now WHERE id = @id AND xmin = @xmin;` — `@r` is the returned refresh token **when present**, else the previous ciphertext (never NULL, D13); 0 rows ⇒ retry once (a concurrent re-auth won).
5. `NamedGrantOrToken` ⇒ `status = 'expired'` + outbox + log `tiktok.token.refresh_failed` (`channelConnectionId`, `oauthClientId`, `errorCode`, `log_id` — never the token or `open_id`).
6. `ClientLevel` ⇒ `RaiseAsync` only (it writes its own audit/outbox, YR25); `Transient` ⇒ one retry, then leave it to the next daily run.
7. Escalation (D10): before raising, count distinct recently-expired connections of the same client — `SELECT count(*) FROM channel_connections WHERE platform = 'tiktok' AND oauth_client_id = @c AND status = 'expired' AND last_verified_at > now() - interval '1 hour'` — ≥ 2 is logged `tiktok.oauth.escalated` and folded into the incident note; never a second incident row (partial unique allows one open row per client).

**`TokenHealthJob` branch.** No new job: 07 contributes the TikTok branch to 06.4.2's shared daily job through the same platform seam 06 used for YouTube ⚠️ (exact seam name is 06.4.2-T2's — extend it, never add a scheduler): ids only, ≤ 500 `active` TikTok connections whose client has no open incident, ordered `last_verified_at NULLS FIRST`, one `RefreshTikTokTokenCommand` per row so one bad row never rolls back the batch (06 YR26). `platform_quota_usage` is **not** involved (TT12).

**Re-auth surface.** No new route: the screen's reconnect action calls `POST /channels/tiktok/connect` again with `disable_auto_auth=1` (TikTok shows its consent screen) and the callback returns the **same** row to `active`, re-pinning the client (YR11). This task adds the `expired → active` outbox/audit consistency, exposes `status = 'expired'` through `GET /channels`, and fixes the copy key `errors.tiktok.reauthRequired` (vi+en) that 10.7.1/10.7.3 render. A publication that failed through the D10 ladder carries `tiktok_reauth_required` (declared once in Domain `PublicationErrorCodes`, TT3) with the same key.

**E-mail.** Both first connect and reconnect queue `channel_connected` (06.1.2-T2's catalog entry, `Templates/Email/channel_connected.<locale>.{txt,html}`, vi+en) through `IEmailSender.QueueAsync` inside the upsert transaction; **no new template name**; the body carries the nickname only, never tokens or `open_id`.

**Observability.** Logs `tiktok.token.refresh_failed|rotated`, `tiktok.incident.classified`, `tiktok.oauth.escalated` (ids/codes + `log_id` only). Metrics: `tiktok_token_refresh_total{outcome}` and `tiktok_oauth_errors_total{endpoint,kind}` (D18) plus the reused `tiktok_rate_limit_backoff_total{endpoint}`. Alerts: existing 11.6.2-T1 rules only (`platform_incident_open > 0`, P1).

## Acceptance checks

- Given an `active` connection whose refresh returns a **different** refresh token, Then both ciphertexts change, `token_expires_at = now + expires_in`, `status` stays `active`, `last_verified_at` advances, and no audit/outbox row is added by the refresh itself.
- Given the refresh response omits `refresh_token`, Then `refresh_token_enc` still decrypts to the previous value (never NULL, D13).
- Given a named grant/token error, Then that connection alone becomes `expired`, `channel_connection_changed.v1` is outboxed, `tiktok.token.refresh_failed` is logged with `log_id`, and **no** `platform_incidents` row exists.
- Given an unknown error or an unparseable body, Then no connection row changes and exactly one open incident exists for that `oauth_client_id`; a second identical failure raises nothing new (partial unique + `IsNew`, 06 YR25).
- Given a client with an open incident, Then the job refreshes none of its connections; after `nts-worker incident clear` the next run does.
- Given 501 eligible rows, Then at most 500 are claimed, ordered `last_verified_at NULLS FIRST`, one command per row, and a failing row leaves the others' writes committed.
- Given `ActiveClientId` changes in settings, Then an existing connection's refresh/revoke still calls its pinned `oauth_client_id` (fixture: pinned A, active B ⇒ calls hit A).
- Given an `expired` connection, Then `GET /channels` reports `status = "expired"` (06 D4 shape) and a fresh connect → callback returns the **same** id to `active`.
- Given an unverified taxonomy row, Then it classifies `ClientLevel` and DoR condition (1) stays open.
- Given a rate-limiter denial or a non-`active` row, Then the command ends with no state change and no incident.

## Failure handling and edge cases

| Situation | Handling |
|---|---|
| Refresh succeeds, DB write fails | transaction rolls back; the old ciphertexts stay valid until `token_expires_at`; next run retries |
| Concurrent re-auth replaces the tokens | `WHERE xmin = @xmin` matches 0 rows ⇒ retry once and refresh the new pair (never write a stale one) |
| Refresh token already rotated elsewhere | classified `NamedGrantOrToken` ⇒ `expired` + re-auth prompt; the user's next connect fixes it |
| `expires_in` far larger than 24 h | stored as returned; the D13 cadence is a floor, not a clamp |
| Routine 24 h expiry vs a broken client | only a **token-endpoint** failure, or ≥ 2 distinct connections of one client within 1 h, raises an incident (F24) — a routine expiry must never hold a whole client |
| Incident raised while publications are `scheduled` | they hold (not failed) and resume after `nts-worker incident clear`; the screen shows `errors.publishing.unavailable` |
| E-mail queueing fails on reconnect | the reconnect command fails (06 D3); the row stays `expired` and the user retries |
| Limiter denies the refresh | no state change; logged `kind=rate_limited`; the next daily run retries (no spin, D6) |
| A taxonomy row is missing/unverified | `ClientLevel` + ⚠️ in the DoR list; never guess a name into the table |
