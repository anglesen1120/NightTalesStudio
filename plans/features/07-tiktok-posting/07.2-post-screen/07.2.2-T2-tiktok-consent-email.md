# 07.2.2-T2 — TikTok consent e-mail (variant copy, vi/en)

## Goal

Every TikTok publication consent sends exactly one `publication_consented` e-mail that states what the user just agreed to on TikTok: the declaration variant their disclosure selection implies (Music Usage Confirmation, or Branded Content Policy + Music Usage Confirmation), the account, the caption and the chosen privacy — in the user's locale, in the same transaction as the consent so a lost mail can never follow a committed consent.

## Inputs

- `../README.md` §3 **D5** (variant ids `tt.v1.music` / `tt.v1.branded`, texts are embedded and rendered by 10.7.3), **D15** (reuse `IEmailSender` + the template catalog; **no** veto-window machinery, **no** cancel-by-link), §1 **C7** (e-mail `publication_consented` per consent), §1.3 **U9** (what each variant declares), §10 **TT10** (no cancel link for TikTok), §1 **K3/K17** (no promotional text is added by the server).

## Design

**Template.** One catalog entry, the existing `publication_consented` (06.2.2-T2's), with TikTok bodies per variant and locale — the payload carries a `variant` key so the renderer picks the body (`tt.v1.music` or `tt.v1.branded`), matching the stored `publications.consent_text_version`. Keys are registered in the entry's `Keys` allow-list so `ValidateOrThrow()` passes at boot; a body using an unregistered `{{key}}` (or a missing variant × locale file) fails the boot, never a runtime 500.

**Params (allow-listed [INFERENCE] set; confirmed against 06.2.2-T2's catalog entry at implementation, WT30).** `displayName`, `channelTitle` (= `channel_connections.display_name`, the creator nickname), `caption` (= `publications.title`), `privacy` (the wire enum as displayed), `platform` ("TikTok"), `variant` (`tt.v1.music` / `tt.v1.branded`), `scheduledAt` (= `consent_at`), `publicationUrl`. **No** `cancelUrl`, no veto fields, no token of any kind (TT10, WT30) — TikTok has no veto window (D15).

**Copy per variant (U9).** `music`: "By posting, you agree to TikTok's Music Usage Confirmation." `branded`: adds "…and to TikTok's Branded Content Policy." Both versions repeat the privacy the row was created with and note that the content may take a few minutes to be visible (the U11 wording belongs to 10.7.4's screen, but the mail carries the same expectation).

**Insertion point.** The TikTok branch of 07.2.2-T1's consent handler calls `IEmailSender.QueueAsync` **before** its single `SaveChangesAsync`, after the domain consent write and the outbox/audit work are staged. A failed queue therefore fails the whole consent request (06.2.2-T2:66's rollback boundary) — never a committed consent with no evidence mail. The handler stays the only caller; this task adds no route, no job, no event.

**Idempotency.** A repeat consent is 409 `publication_invalid_state` (07.2.2-T1) and therefore queues nothing; a concurrent loser (409 `concurrency_conflict`) queues nothing. The mail is thus at-most-one per `(publicationId, consent_text_version)`.

## Steps

1. Extend the `publication_consented` catalog entry: the TikTok bodies for `tt.v1.music` and `tt.v1.branded` in vi and en, with every `{{key}}` registered in `Keys`.
2. Write the vi and en copy (module: no promotional watermark or preset text is added — K17; the text states the declaration's legal reference per U9).
3. Add the queue call to 07.2.2-T1's TikTok consent branch, before the handler's single `SaveChangesAsync`.
4. Add the locale fallback (`en` + `event = publication_consent_email_locale_fallback`) for a user locale without a body.
5. Tests of §Tests; no schema and no job change.

## Acceptance checks

- **Given** a consent with `variant = tt.v1.music` **when** the request commits **then** exactly one `email_messages` row exists for that user with the Music Usage Confirmation wording, and one `send_email` job is enqueued (queue `email`).
- **Given** `variant = tt.v1.branded` **then** the row's body cites the Branded Content Policy **and** the Music Usage Confirmation (U9) — the two variants are byte-different.
- **Given** a vi user **when** the mail renders **then** the body is the vi text; an en user gets the en text; an unknown locale falls back to `en` and logs the fallback event (i18n).
- **Given** the params **then** they are exactly the allow-listed set: no token, no `cancelUrl`, no veto field, and the body contains no promotional text added by the server (K17, TT10, WT30).
- **Given** the queue fails (fake sender returns an error) **when** consent runs **then** the whole transaction rolls back — no `scheduled` publication, no `publication_updated.v1`, no audit row (06.2.2-T2:66's boundary).
- **Given** a repeat consent **then** 409 `publication_invalid_state` and **no** second `email_messages` row (at-most-one per publication + variant).
- **Given** a body edited to use an unregistered `{{key}}` **then** `EmailTemplateProvider.ValidateOrThrow()` fails the boot (test-time assertion on the catalog), so the regression cannot ship.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Queue throws / the fake returns an error | The consent request fails as a whole; the user retries from the screen (no partial state). |
| User has no locale set | `en` body + fallback log line; never an empty body. |
| `channelTitle` (nickname) absent on the connection | The param is sent empty and the template renders the platform name only — never a `{{channelTitle}}` leak. Caption is truncated by the template, never by the sender, and the full caption stays in `publications.title`. |
| The user revoked the connection between consent and send | `SendEmailJob` is unaffected (the mail carries no token and performs no platform call); the publication's own state is 07.3's concern. |
| Two consents for two publications of the same episode | Two mails, one per publication — the idempotency key is the publication, not the episode. |
| Body changed in `Templates/` after approval | The mail is evidence-adjacent: the change is a reviewed diff and 07.4.1-T1's evidence pack captures the rendered bodies (U9). |

## Notes

- **Security/privacy.** No token, no cancel link, no `open_id`, no presigned URL in the mail (TT10, WT30); the recipient address is hashed by the pipeline (`09.2.6-T3`), never logged; the params carry only the display values the user already saw on the screen.
- **Performance.** One templated insert inside an existing transaction; no extra query beyond the connection/episode rows the consent handler already loaded; the mail is delivered by the shared `SendEmailJob` (queue `email`, 5 retries) — this task adds no scheduling.
- **Observability.** The consent success log line (07.2.2-T1) carries `publicationId` + variant; a queue failure surfaces as the consent request's error, and `SendEmailJob`'s own failure metrics cover delivery. No new instrument.
- **i18n.** vi + en bodies per variant; the variant is chosen from the stored `consent_text_version`, so the mail and the row can never disagree.
- **[OPEN]** O-5 (`../plan.md` §11): the exact param allow-list is confirmed against 06.2.2-T2's catalog entry at implementation; this task never invents a second template or a second sender.
