# 07.3.1-T1 — `PublishTikTokJob` (init via `PULL_FROM_URL`) + per-endpoint rate limiter

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

A consented TikTok publication becomes **exactly one** TikTok post task: the job presigns the render artifact (CR-4), calls `POST /v2/post/publish/video/init/` once with `source_info.source = PULL_FROM_URL`, commits `publishId` + `status = uploading` **before** anything can poll, and never re-initialises a non-terminal row. Every outbound call passes the per-endpoint, per-connection limiter (init 6, creator-info 20, status 30, token 10, revoke 10 per minute); a denied acquire defers the job with jitter instead of failing the publication.

## Design

Interfaces (Application/Abstractions/TikTok — no Domain dependency on HTTP):

```csharp
public enum TikTokEndpoint { Init, CreatorInfo, Status, Token, Revoke }

public interface ITikTokRateLimiter
{
    // Success(TimeSpan.Zero) = granted; Errors.TooManyRequests(retryAfter) = denied (D6).
    ValueTask<ErrorOr<TimeSpan>> TryAcquireAsync(Guid connectionId, TikTokEndpoint endpoint, CancellationToken ct);
}

public interface ITikTokApiClient
{
    Task<ErrorOr<TikTokInitResult>> InitAsync(TikTokInitRequest request, CancellationToken ct);
    Task<ErrorOr<TikTokStatusResult>> FetchStatusAsync(string publishId, CancellationToken ct);   // 07.3.2-T1
    Task<ErrorOr<TikTokCreatorInfo>> GetCreatorInfoAsync(CancellationToken ct);                    // 07.2.1-T1
}

public sealed record TikTokInitRequest(string AccessToken, string VideoUrl, string PrivacyLevel, string Caption,
    bool DisableComment, bool DisableDuet, bool DisableStitch, bool BrandContentToggle, bool BrandOrganicToggle, bool IsAigc);
public sealed record TikTokInitResult(string PublishId);
public sealed record TikTokFailure(string Code, int HttpStatus, TikTokFailureKind Kind, string? LogId);   // Kind: Retryable | Terminal | PlatformIncident | RateLimited | Auth
```

- `TikTokApiClient` (Infrastructure/TikTok): typed `HttpClient`, base address from `TikTokOptions` (`https://open.tiktokapis.com/v2/` per K1/K7 ✅; the exact host is 07.1.1-T1's record), `System.Text.Json` source generation, every vendor error body mapped to `TikTokFailure` (K1's codes → 07.3.3-T1's D10 table), never a vendor exception in Application.
- Job body (K3 ✅): `post_info.privacy_level`, `post_info.title`, `disable_duet`, `disable_stitch`, `disable_comment`, `brand_content_toggle` (**always sent**, `false` when the disclosure toggle is off), `brand_organic_toggle`, `is_aigc = true`, and `source_info = { source: "PULL_FROM_URL", video_url }`. No `upload_url`, no chunks (D2/F01).
- `InMemoryTikTokRateLimiter`: `ConcurrentDictionary<(Guid, TikTokEndpoint), FixedWindow>` driven by `TimeProvider`, sizes from `TikTokOptions.RateLimits`; keys `tt:rl:{connectionId}:{endpoint}`; never throws. One `SemaphoreSlim(1,1)` per connection id in `TikTokApiClient` so sequential `PULL_FROM_URL` tasks never interleave (D6); released in `finally`.
- Domain: `Publication.StartTikTokUpload(DateTimeOffset now)` (D7 ✅) — refuses without `ConsentAt` (defence in depth), `scheduled → uploading`, resume no-op in `uploading`, sets `platform_payload.tiktok` (D8's key set + `initAt` from the declared extension in `plan.md` §3, set once on the first attempt) + `next_attempt_at = now + Poll:IntervalSeconds`. If 06.2.1-T1's generic `StartUpload(now)` already satisfies these preconditions, extend it instead of adding a parallel member (TT11 anti-duplication rule) — record the choice in Notes when it lands.
- **TX-A, before the HTTP call (the only thing between the `07-post-private` gate and a duplicate post)**: `For(userId)` → tracked row → `StartTikTokUpload(now)` **plus** `platform_payload.tiktok.initAttempt = { n = previous + 1, startedAtUtc = now, lastDisposition = null }` → commit. The marker is what makes D7's "never re-init while non-terminal" survive a crash: `n` counts real POST attempts, and the re-entry predicate is `initAttempt != null && publishId == null && n >= 1`.
- **Re-entry rule (D7/D16/F04)**: a re-entry (Hangfire retry or restart) evaluates `lastDisposition` — `null` (the process died while the POST was in flight or the socket timed out with no response) or `sent` ⇒ **never call `init` again**: the row goes `failed` `tiktok_upload_failed` (`platform_incident` instead when the failure class is client-level), and the user-visible recovery is a **new publication row**. `retryableResponse` (TikTok answered 429/5xx, which K1 classifies retryable) ⇒ re-init is allowed and `n` increments.
- **TX-B, after a 2xx init**: `platform_payload.tiktok.publishId` + `initAt = now` (once) + `next_attempt_at = now + Poll:IntervalSeconds` + outbox `publication_updated.v1 { status: "uploading" }` + realtime `PublicationUpdated` (ids only) in one `SaveChanges` (09.2.4-T1 interceptor).

## Steps

1. Confirm 06 D18's partial claim index predicate covers `'uploading'` (TikTok's candidate set is `uploading|processing`); if not, extend it in **07's own** migration (append-only, never edit the `_06_` migrations). `platform` is filtered inside the port call; verify the plan with `EXPLAIN`.
2. Add `TikTokEndpoint`, `ITikTokRateLimiter`, `InMemoryTikTokRateLimiter` with D6's sizes read from `TikTokOptions` (no hard-coded numbers).
3. Add `ITikTokApiClient`/`TikTokApiClient` with `InitAsync` only (the status/creator-info members land with 07.3.2-T1/07.2.1-T1 in the same interface).
4. Extend `PublicationScheduledForUploadHandler` (06.2.3-T2) with the `platform == "tiktok"` branch: `IJobScheduler.Enqueue(j => j.RunAsync(publicationId, ct))` — immediate, no `publishAt` (TT1/TT6, `(j, ct)` lambda shape `09.2.6-T1:25-26`). The Api still never enqueues (C9).
5. `PublishTikTokJob.RunAsync(Guid publicationId, CancellationToken ct)` (`[JobPolicy(Queue = JobQueue.Publish, Retries = 3)]`, `Application/Features/Publishing/Jobs/`):
   1. resolve `userId` (id-only job), load the row inside `ISystemContext.For(userId)`; `next_attempt_at > now` → no-op (TT2); terminal status → no-op.
   2. `publishId` present and status non-terminal → no-op + `tiktok_publish_attempts_total{outcome="skipped"}` (D7).
   3. `initAttempt != null && publishId == null && initAttempt.lastDisposition != "retryableResponse"` → **finalise, never re-init**: `failed` `tiktok_upload_failed` (or the D10 client-level incident code), one warning with ids only, metric `outcome="failed"` (UC-8/D7/F04).
   4. `HasOpenIncidentAsync("tiktok", connection.OAuthClientId)` → `Publication.HoldForIncident(incidentId, now + 5 × Poll:IntervalSeconds)`, no HTTP call (06.2.3-T3, never `NULL`).
   5. fail-closed audit gate: `TikTokOptions.AuditStatus != approved && privacyLevel != "SELF_ONLY"` → `failed` `tiktok_invalid_post_settings`, **no** HTTP call (UC-9/D4).
   6. `ITokenService.GetAccessTokenAsync(connectionId)`; 401 → 07.3.3-T1's ladder (refresh once, retry once).
   7. **Account-privacy gate (07 CR-14, skipped when `AuditStatus == approved`):** `TryAcquireAsync(connectionId, TikTokEndpoint.CreatorInfo, ct)` (denied → defer like step 9), then `GetCreatorInfoAsync`; `privacy_level_options` containing `PUBLIC_TO_EVERYONE` means the account is public, which K9 forbids for an unaudited client → `failed` `tiktok_account_not_private`, **no** `init` call, no incident; a non-`ok` `creator_info` result defers the run (`next_attempt_at` + jitter), never a guess.
   8. artefact key from the episode's render output → `GetSignedUrlAsync(bucket, key, TimeSpan.FromMinutes(TikTokOptions.UrlTtlMinutes), ct)` (CR-4); fail-closed unless the URI is `https` and non-redirecting (K16).
   9. `TryAcquireAsync(connectionId, TikTokEndpoint.Init, ct)`; denied → `next_attempt_at = now + retryAfter + jitter(≤ 20 %)`, `tiktok_rate_limit_backoff_total{endpoint="init"}`, return 2xx (never `failed`, D6/UC-3).
   10. TX-A (marker written), then `InitAsync` **outside** the transaction: a `RateLimited`/`Retryable` **HTTP response** → set `lastDisposition = "retryableResponse"` and rethrow for Hangfire's exponential retry (≤ 3); no HTTP response (connect/TLS/timeout) → set `lastDisposition = "sent"` and finalise `failed` `tiktok_upload_failed` + one warning naming only ids (UC-8/F04); `PlatformIncident` → 07.3.3-T1's raise path; success → TX-B.
6. No recurring registration here (07.3.2-T1 owns `tiktok-status-poll`).
7. Options: read only `TikTokOptions` (D19); startup validation rejects `TikTok:Transfer != "pull_from_url"` and any TTL below the documented 1-hour download window.

## Acceptance checks

- Given a consented TikTok publication, when the consent handler runs, then `PublishTikTokJob` is enqueued exactly once and a YouTube publication of the same batch is not routed to it (TT1).
- Given one job run, then `FakeTikTokServer` recorded **exactly one** `init` with `source_info.source = PULL_FROM_URL`, an `https` `video_url`, and a signed-URL TTL ≥ 120 min.
- Given a 2xx init, when TX-B commits, then `platform_payload.tiktok.publishId` is present, `status = uploading`, one `publication_updated.v1`, and no status poll could have run before that commit.
- Given TX-A has committed `initAttempt` and the process dies while the POST is in flight, when the job re-runs, then **no second `init`** is recorded and the row ends `failed` with `tiktok_upload_failed` (gate `07-post-private`); given instead that TikTok answered 5xx and Hangfire retries, then the re-entry **is** allowed to re-init and `initAttempt.n` is 2.
- Given 7 acquires in one minute for one connection, when the 7th arrives, then it is denied, no HTTP call was made and the publication is not `failed`.
- Given `AuditStatus = pending` with `privacyLevel = PUBLIC_TO_EVERYONE`, then no HTTP call and `failed` `tiktok_invalid_post_settings`.
- Given `AuditStatus = pending` and a public account (`creator_info.privacy_level_options` contains `PUBLIC_TO_EVERYONE`), then `failed` `tiktok_account_not_private` and **no** `init` call (07 CR-14).
- Given TikTok answers 500, then the job throws, Hangfire retries, and the row is neither `failed` nor re-initialised twice within one attempt.
- Given an open client incident, then the row is held with a concrete `next_attempt_at` and no HTTP call.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| access token 401 | refresh once via `ITokenService` then retry in the same command (D13/F24); still 401 → 07.3.3-T1's `tiktok_reauth_required`; **no** client incident on the first 401 |
| token endpoint itself fails | incident first, per TT4/07.3.3-T1 (never a per-connection `expired` on an unknown error) |
| open `platform_incidents` row for the client | hold with `HoldForIncident`, deferred concrete `next_attempt_at`, no HTTP call (YR17/YR24) |
| signed URL expired / storage 5xx | expired ⇒ re-sign on the next attempt; storage 5xx ⇒ retryable, row untouched, the publication never fails on our own storage blip |
| signed URL is `http` or redirects | throw before the HTTP call, `failed` `tiktok_upload_failed`, warning log (K16) |
| `reached_active_user_cap` / `unaudited_client_can_only_post_to_private_accounts` (403) | 07.3.3-T1's map: cap metric + P2 alert, or platform incident (residual race past the step-7 account-privacy gate) |
| public account while unaudited (step 7) | `failed` `tiktok_account_not_private`, no `init`, no incident; the user switches the account private and re-posts (07 CR-14) |
| `privacy_level_option_mismatch` (creator changed options after consent) | `failed` `tiktok_invalid_post_settings`, no incident; the user re-creates the post with the new options |
| unknown 403/400 code | `failed` `tiktok_upload_failed`, `log_id` logged, never a silent success (D10's default row) |
| process dies mid-`init` / socket timeout with no response | `initAttempt.lastDisposition = "sent"`, `publishId` absent ⇒ the re-entry finalises `failed` `tiktok_upload_failed` and **never re-inits**; the creator's account may hold an orphan private task (listed in the 07.4.1-T1 evidence pack) | no duplicate post (F04/D7, UC-8) |
| TikTok 429/5xx (a real HTTP response) | `lastDisposition = "retryableResponse"` ⇒ Hangfire exponential retry may re-init up to `Retries = 3`, then `failed` `tiktok_upload_failed` | D16/K1 |
| two jobs for one publication | forbidden by TX-A's marker + the `publishId` guard + the per-connection semaphore; the counter test asserts one `init` | |
| `video_upload`/`SEND_TO_USER_INBOX` | out of scope ([OPEN] §11) — never requested by this job |

## Notes

- Traps: with `PULL_FROM_URL` TikTok downloads server-side, so the dangerous failure is a **lost response**, not a lost byte count; K3's `upload_url` and K4/K5's chunk rules exist only in `FakeTikTokServer` (F01/D2).
- README D7's prose mentions a `video_url` written to `platform_payload`, while D8's authoritative key list has only `videoUrlExpiresAt`; this plan follows D8 (the URL is recomputed per attempt, never persisted) — reported as a contract inconsistency.
- Only `TikTokOptions` keys are read (D19); no `ffmpeg`/chunk/config beyond it.
- [OPEN] O-3 (distributed limiter only if the Worker is scaled out) and O-4 (recurring cadence belongs to 07.3.2-T1).
