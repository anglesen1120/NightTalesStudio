## Goal

Every `uploading`/`processing` TikTok publication reaches a terminal state on time: the recurring `PollTikTokStatusJob` claims at most 25 due rows through the pinned system-work port, one command per row applies **D9's** `status` + `fail_reason` map (single mapping, no second copy), a retryable reason backs off at most 3 attempts, a deadline fails the row as `tiktok_poll_timeout`, held rows are skipped without an HTTP call, and `tiktok_post_latency_seconds` is observed exactly once per publication at `PUBLISH_COMPLETE`.

## Design

public sealed record RecordTikTokStatusCommand(Guid PublicationId, TikTokStatusSnapshot Snapshot) : IRequest<ErrorOr<Success>>;

**`TikTokStatusMap` (D9 ✅, verbatim — no extra values)**

| wire `status` | outcome status | `error_code` | retry |
|---|---|---|---|
| `PROCESSING_DOWNLOAD` | `processing` | — | n/a; `next_attempt_at = now + interval` |
| `PROCESSING_UPLOAD` | `processing` | — | n/a (FILE_UPLOAD path exists only in `FakeTikTokServer`) |
| `PUBLISH_COMPLETE` | `published` | — | terminal; `externalPostId = PubliclyAvailablePostIds.FirstOrDefault()` ⇒ `null` when empty (TT5) |
| `FAILED` + `internal`, `video_pull_failed` | `processing` | — | yes: `next_attempt_at = now + interval × 2^attempt` while `attempt < 3`, else `failed` `tiktok_upload_failed` |
| `FAILED` + `file_format_check_failed`, `duration_check_failed`, `frame_rate_check_failed`, `picture_size_check_failed` | `failed` | `tiktok_video_invalid` | no |
| `FAILED` + `auth_removed` | `failed` | `tiktok_reauth_required` | no (connection → `expired` via 07.1.2-T2's path) |
| `FAILED` + `spam_risk_too_many_posts` | `failed` | `tiktok_creator_cap` | no |
| `FAILED` + `spam_risk_user_banned_from_posting` | `failed` | `tiktok_creator_banned` | no |
| `FAILED` + `spam_risk_text`, `spam_risk` | `failed` | `tiktok_content_rejected` | no |
| `FAILED` + `publish_cancelled` | `cancelled` | — | terminal |
| `FAILED` + anything else / unknown 200 code | `failed` | `tiktok_upload_failed` | no; `log_id` logged, never a silent success |
| `SEND_TO_USER_INBOX` | `failed` | `tiktok_upload_failed` | no (inbox mode is out of scope, [OPEN] §11 — must not appear) |
| deadline: `now - platform_payload.tiktok.initAt > Poll:MaxMinutes` | `failed` | `tiktok_poll_timeout` | no; `publishId` retained for support |

**Tick**:

```csharp
public sealed class PollTikTokStatusJob(ISystemWorkQuery work, ISender sender, ITikTokApiClient client, ...) : IBackgroundJob
{
    public async Task RunTickAsync(CancellationToken ct);   // recurring entry: ids-only rule = only ct
}
```

1. `work.PendingAsync<Publication>(p => p.Platform == "tiktok" && (p.Status == uploading || p.Status == processing) && (p.NextAttemptAt == null || p.NextAttemptAt <= now), 25, ct)` — ordered by `next_attempt_at`; the port is the only allow-listed bypass (`09.2.3-T1:36`).
2. For each `(id, userId)`: a **fresh** `ISystemContext.For(userId)` scope, load the tracked row, skip when `next_attempt_at > now` (TT2) or terminal; a row with `heldByIncidentId` present → skip, `next_attempt_at = now + 5 × Poll:IntervalSeconds`, **no HTTP call** (YR17/YR24 — never `NULL`).
3. `ITokenService.GetAccessTokenAsync(connectionId)`; `TryAcquireAsync(connectionId, TikTokEndpoint.Status, ct)` (30/min per token, K7); fetch the snapshot; `sender.Send(new RecordTikTokStatusCommand(id, snapshot))`.
4. One command per row; a failing row is logged and the batch continues (06 YR26).

**Handler**: `For(userId)` → tracked row → no-op when `next_attempt_at > now` / terminal / `publishId` missing → `TikTokStatusMap.Map(...)` → `Publication.ApplyTikTokStatus(outcome, now)` → when `published`, `Episode.MarkPublished(...)` **in the same transaction** (C7) → outbox `publication_updated.v1 { status, errorCode? }` + realtime ids-only via the interceptor, latency histogram observed once (only on the first `published` transition, enforced by the guarded update).

**Domain member**: `Publication.ApplyTikTokStatus(TikTokStatusOutcome outcome, DateTimeOffset now)` — sets status, `external_post_id`, `error_code`, `platform_payload.tiktok.lastStatus`/`pollAttempts`, `next_attempt_at`; never touches `publish_at` (= `consent_at`, TT6) and never re-inits. Held/incident transitions reuse `HoldForIncident`/`ReleaseHold` (06.2.3-T3).

**Registration** (`src/NightTales.Worker/Jobs/PublishingRecurringRegistrations.cs`): `AddOrUpdateRecurring<PollTikTokStatusJob>("tiktok-status-poll", cron, (j, ct) => j.RunTickAsync(ct))` **only while `tiktok_publish` is on**, otherwise `RemoveRecurringIfExists("tiktok-status-poll")` (D1 + 06.2.5-T1:70). Target spacing 20 s from `TikTok:Poll:IntervalSeconds`; [INFERENCE] `IJobScheduler.AddOrUpdateRecurring(id, cron, call)`'s granularity is checked first — if the scheduler is minute-based, register the closest tick and let the per-row `next_attempt_at` (20 s) govern spacing, never a self-scheduling busy chain.

## Steps

1. `TikTokStatusSnapshot`, `TikTokStatusOutcome`, `TikTokStatusMap` (pure, `TimeProvider`-free, plus the deadline rule) in `Application/Features/Publishing/TikTok`.

3. `Publication.ApplyTikTokStatus(outcome, now)` in Domain + its unit tests; reuse `HoldForIncident`/`ReleaseHold` unchanged (no second hold convention).

5. `platform_payload.tiktok` bookkeeping: `pollAttempts`, `lastStatus`, `lastFailReason`, `uploadedBytes` — the declared extension subset of `plan.md` §3 (contract gap reported); the settings keys stay exactly D8's, and `initAt` is written once by 07.3.1-T1.

8. Confirm the claim index covers `uploading` (see 07.3.1-T1 step 1) and prove it with `EXPLAIN` on the port's generated SQL; no sequential scan on `publications` per tick.

## Acceptance checks

- Given an `uploading` row whose `next_attempt_at` is in the future, when the tick runs, then no `status/fetch` request and no transition (TT2).
- Given `PROCESSING_DOWNLOAD`, when the tick runs, then the row is `processing`, `next_attempt_at = now + 20 s`, and exactly one `publication_updated.v1`.
- Given `PUBLISH_COMPLETE` with `publicaly_available_post_id = [123]`, then `published` + `external_post_id = "123"` and the episode is `published` in the same transaction; with an empty list, then `published` + `external_post_id = null` (**success**, K7/TT5).
- Given `FAILED` + `internal` three times, then the row stays `processing` with a growing `next_attempt_at` and only the 4th attempt finalises `failed` `tiktok_upload_failed`.
- Given `FAILED` + `auth_removed`, then `failed` `tiktok_reauth_required` and no retry (`next_attempt_at = NULL`).
- Given `now - initAt > 30 min`, then `failed` `tiktok_poll_timeout`, `publishId` still in `platform_payload`, one outbox row.
- Given a row held by an open incident, then it is skipped, its `next_attempt_at` is concrete and no HTTP call is recorded.
- Given an already-`published` row claimed again, then no outbox row, no second histogram observation, no status call.
- Given 30 due rows, then one command per row and one row's failure does not stop the rest; every row respects the 30/min status bucket.
- Given `tiktok_publish` off, then the recurring id is absent; on, it is registered exactly once (idempotent upsert).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `status/fetch` 5xx / timeout | row unchanged, `next_attempt_at = now + interval`, `outcome="retry"`; the poll deadline still bounds the total |
| TikTok 429 | `next_attempt_at = now + RetryAfter + jitter(≤ 20 %)`, `tiktok_rate_limit_backoff_total{endpoint="status"}`, never `failed` (D6) |
| token 401 | refresh once + retry in the same command (D13/F24); still 401 → `tiktok_reauth_required` + connection `expired` (07.3.3-T1's ladder) |
| `publishId` missing on an `uploading` row | skip with a single warning (07.3.1-T1 must commit it first); never call `status/fetch` without an id. A row whose `platform_payload.tiktok.initAttempt.lastDisposition != "retryableResponse"` is 07.3.1-T1's to finalise (it fails closed) — the poll job never re-drives an init and never finalises that row itself |
| `publish_cancelled` | `cancelled`, `next_attempt_at = NULL`, no re-publication from our side (TT10) |
| duplicate tick (two Workers, same recurring id) | the guarded UPDATE + the `next_attempt_at` check make the second a no-op; Hangfire's recurring upsert is idempotent (09.2.6-T1) |
| incident raised mid-poll | held from the next tick (`heldByIncidentId`, concrete `next_attempt_at`); `ReleaseHold` re-announces the row and TT1's handler re-reads it |
| connection `revoked` | never call TikTok with wiped tokens; the row is finalised per 07.1.2-T1's disconnect rules (`awaiting_consent|scheduled` cancelled there) |
| clock | `TimeProvider` everywhere (`FakeClock`); no `DateTime.UtcNow` in this path |
| a row stuck in `uploading` with `initAt` absent | fail closed: treat as `failed` `tiktok_upload_failed` once the connection is healthy, and log — never poll forever |

## Notes

- Traps: `publicaly_available_post_id` is TikTok's own spelling on the wire while our DTO field is `externalPostId` (TT5); a `NULL` `external_post_id` on a `published` row is correct for `SELF_ONLY`, so no KPI may read it as a failure (CR-9 groups by `status`, never `publish_at`).
- Held rows **must** carry a concrete `next_attempt_at` — a `NULL`-held row head-blocks the 25-row batch (documented 06 failure mode).
- `publish_at` is written once at consent (TT6) and never read as a publish time here.
- The bounded one-command-per-row claim is what keeps a single poisoned row from stalling every TikTok publication (06 YR26).
- [OPEN] §11 carries `POST /v2/post/publish/cancel/` and the inbox mode out of scope for R2.
