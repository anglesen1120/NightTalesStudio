## Goal

D10 exists **exactly once** and is wired end to end: every TikTok failure code is declared in Domain `PublicationErrorCodes` with the `tiktok_` prefix, each is mapped either to a wire ProblemDetails `code` or to a publication `error_code`, our own broken client becomes one `platform_incidents` row and a P1 alert instead of a per-user failure, the creator/active-user caps get their own metrics and a P2 alert, and every code has one vi and one en copy key under `errors.tiktok.*`.

## Design

**Domain codes** (one declaration, `PublicationErrorCodes`, TT3/06 YR27): `TiktokInvalidPostSettings`, `TiktokVideoTooLong`, `TiktokCannotPostNow`, `TiktokAccountNotPrivate` (07 CR-14), `TiktokCreatorCap`, `TiktokRateLimited`, `ConsentTextOutdated` (shared with 06), `TiktokActiveUserCap`, `TiktokCreatorBanned`, `TiktokContentRejected`, `TiktokVideoInvalid`, `TiktokPollTimeout`, `TiktokUploadFailed`, `TiktokReauthRequired`, `PlatformIncident` (shared).

**The surface (D10 ✅ — the only mapping; nothing else may invent a code)**

Anything unmapped ⇒ `tiktok_upload_failed`; an unknown HTTP-200 code logs `log_id` and is treated the same (never a silent success).

**401 recovery ladder (F24/D10, shared helper `TikTokAuthRecovery`)** — (1) force a refresh through `ITokenService` and retry the call **once inside the same command**; (2) still 401 ⇒ connection `expired` + publication `failed` `tiktok_reauth_required`, no deletion request, re-consent copy; (3) **only** when the token endpoint itself fails, or ≥ 2 distinct connections of the same `oauth_client_id` fail within 1 h ⇒ `platform_incident` for that client and publications hold in `scheduled` (never a per-connection `expired` on an unknown error, TT4).

**Incident path** — `url_ownership_unverified` / `scope_not_authorized` at client level: `RaiseAsync("tiktok", connection.OAuthClientId, PublicationErrorCodes.PlatformIncident, clock.UtcNow, ct)`; then the publication returns to `scheduled` and holds:
```csharp
public ErrorOr<Success> ReturnToScheduledForIncident(Guid incidentId, DateTimeOffset nextAttemptAt);
// uploading → scheduled (or scheduled stays scheduled); error_code = platform_incident;
// platform_payload.heldByIncidentId = incidentId; next_attempt_at = nextAttemptAt (never NULL)
```
This is the one member this task adds ([DECISION] 07.3, named here): 06.2.3-T3's `HoldForIncident` keeps the status unchanged, but D10 requires `scheduled` so a row that never received a `publishId` can be re-initialised after the clear (TT1's handler re-reads the row, no re-init happens while non-terminal, D7). If `HoldForIncident` already models the return-to-scheduled case, extend it instead of adding a member (TT11 anti-duplication rule) — record the choice in Notes when it lands. Clearing stays exclusively 06.2.3-T3's `nts-worker incident clear` + `ReleaseHold` sweep (YR25, no second sweep).

**Metrics (D18)** — `tiktok_publish_attempts_total{outcome}` (`success|retry|failed|backoff|skipped`), `tiktok_rate_limit_backoff_total{endpoint}` (`init|creator_info|status|token|revoke`), `tiktok_active_user_cap_hit_total` (incremented on every `reached_active_user_cap` sighting, init 403 or HTTP-200 creator-info error), `tiktok_post_latency_seconds` (histogram, observed by 07.3.2-T1). No label ever carries a publication id, nickname, caption or `open_id`.

**Alerts (rule catalogue, CR-10)** — `tiktok_active_user_cap_hit_total > 0` ⇒ **P2**; the existing `platform_incident_open > 0` ⇒ **P1** covers `url_ownership_unverified` and `scope_not_authorized`; P2 when the same client produces ≥ 2 distinct failing connections within 1 h (ladder step 3). No alert for a user-level `tiktok_creator_cap`/`tiktok_content_rejected` (expected product behaviour).

**Logs (structured, ids only)** — `publicationId`, `channelConnectionId`, `oauth_clientId`, `endpoint`, `errorCode`, `logId`, `outcome`; a `LoggerMessage`-generated class per job; never content, never a token.

**i18n** — one copy key per row of the table above, vi + en, in the Api's resource files (`errors.tiktok.*`, `errors.publishing.*` shared with 06): the screen renders `errors.tiktok.<code>` for `PublicationDto.errorCode` (D18). The `blockReason` text from `creator_info` is passed through verbatim by 07.2.1-T1 (U2) and is not re-translated.

## Steps

1. Add the `tiktok_` codes to `PublicationErrorCodes` (single declaration, TT3) and a `TikTokErrorCatalog` map (`code → httpStatus | null, retryable, alert, copyKey`) so no call site branches on a string literal.
2. Implement `TikTokAuthRecovery` (the ladder) and wire it into `PublishTikTokJob`/`PollTikTokStatusJob`'s token 401 path; connection `expired` + outbox through 07.1.2-T2's shipped path (no new transition).
3. Implement the incident path: `RaiseAsync` + `Publication.ReturnToScheduledForIncident` (or the existing hold member, per Notes) in **one** transaction, so a crash cannot leave a raised incident without a held row (mirror of 06.2.3-T3:57).
4. Emit `tiktok_active_user_cap_hit_total` on both cap sightings and `tiktok_rate_limit_backoff_total{endpoint}` at every denied acquire; add the histogram registration (07.3.2-T1 observes).
5. Add the two alert rules to 11.6.2-T1's catalogue (soft dependency; if it is not yet written, record the rule text in `plan.md` §11 and raise the CR in the final report — never edit a file outside this folder).
6. Add the vi/en copy for every key; add the i18n test that fails on a missing or orphan key.
7. Test pass: fault-injection theories over every D10 row against `FakeTikTokServer`.

## Acceptance checks

- Given every D10 row, when the corresponding `FakeTikTokServer` fault is served, then the publication ends in exactly the table's status/`error_code`, the retry flag matches, and the alert flag matches — one theory row per line, no unmapped code.
- Given `url_ownership_unverified` for two publications of the same client, when both jobs run, then exactly **one** `platform_incidents` row exists (`IsNew = false` on the second), both publications are `scheduled` with `error_code = platform_incident` and a concrete `next_attempt_at`, and the P1 alert fires once.
- Given `nts-worker incident clear`, then both publications are released (06.2.3-T3 sweep), `publication_updated.v1 { status: "scheduled" }` is emitted per row, and the next `PublishTikTokJob` is allowed to init (no `publishId` was ever set).
- Given `reached_active_user_cap`, then `error_code = tiktok_active_user_cap`, `tiktok_active_user_cap_hit_total` incremented, P2 rule expression true, and **no** retry scheduled (`next_attempt_at = NULL`).
- Given `access_token_invalid` with a working refresh, then the call is retried once and succeeds — no `expired`, no incident (F24).
- Given `access_token_invalid` with a refused refresh, then the connection is `expired` and the publication `failed` `tiktok_reauth_required` — and **no** incident (unless ≥ 2 distinct connections fail within 1 h).
- Given the whole copy catalogue, then every `tiktok_` code has exactly one vi and one en key and no key is orphaned.
- Given any log line from these paths, then it contains no caption, nickname, token or `open_id`.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| unknown 403/400/200-error code | `tiktok_upload_failed`, `log_id` logged, no retry, no alert — never a silent success |
| two distinct codes in one response | the first mapped code wins; the raw body is logged once with `log_id` |
| incident raised while a row is `uploading` with a real `publishId` | hold + keep the id; after the clear the row is re-polled, never re-initialised (D7/TT1) |
| incident raised twice in a row | the partial unique index keeps **one open** row per `(platform, oauth_client_id)`; `IsNew = false` ⇒ no duplicate P1 |
| clear fails mid-sweep | rows stay held (concrete `next_attempt_at`), retried by the sweep; no row is lost or freed twice (06.2.3-T3) |
| cap hit for one creator, other creators fine | per-user outcome only; the metric/alert is aggregated, never a client incident (K10) |
| vi/en key missing | the i18n test fails the build, not production |
| alert rule file not yet written (11.6.2-T1 soft) | the rule text is recorded in `plan.md` §11 and reported as a CR target — this folder never edits another plan |
| token expired at 24 h (routine, K13) | ladder step 1 refreshes silently; only a refused refresh reaches the user (F24) |

## Notes

- Traps: `url_ownership_unverified` is **our** misconfiguration (F06) — per-user failure messaging would page the wrong person; the cap is client-wide (K10) while `spam_risk_too_many_posts` is per creator (K10) — two different buckets, two different messages.
- `platform_incident` is a shared code (06 owns the entity/events/clear verb); 07 only raises and holds (TT12: no second sweep, no second table).
- No 429 of ours may ever be produced by a job (`tiktok_rate_limited` is the inbound policy's code); a TikTok 429 is internal backoff (D6).
- Audit untouched: no new `publishing.*` action (D14/06 D17); incident rows are audited by 06.2.3-T3.
