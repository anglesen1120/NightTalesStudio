## Goal

The TikTok Content Posting API audit evidence pack exists, is redacted, and is handed to `13.4.3-T1` (13 owns the filing, C10): (a) a **continuous screencast** of the live screen `/episodes/:id/publish/tiktok` covering every required-UX obligation **U1–U13** on staging, (b) both consent texts as rendered (`tt.v1.music`, `tt.v1.branded`, vi + en), (c) the data-handling summary, (d) the intended-use statement (K11 — authentic creators, wide audience; "a utility tool to help upload contents to the account(s) you or your team manages" is **not acceptable**), (e) the claimed 24-h active-creator volume = `TikTokOptions.MonthlyActiveCreators` (K10, CR-8), (f) the OAuth/error and rate-limit evidence (`tiktok-errors-limits.json`). The **internal U1–U13 checklist** is filled row-by-row against the running app and the server rules: every row is `pass` with an evidence pointer, `fail` with a CR to the owning task or to Lead10S, or `deviation-accepted` with the reviewer-facing justification. Nothing about the screen or the product code is changed by this task.

**Capture protocol (the runbook, executed on staging, one `run_id` per attempt).** 1. Confirm `TikTokOptions.AuditStatus = pending` and the flag is owner-only (`SELECT rules FROM feature_flags WHERE key = 'tiktok_publish'`, owner ids only) and that `07.1.1-T1`'s `docs/ops/tiktok-oauth-setup.md` records a **verified** `PULL_FROM_URL` domain/URL prefix (K16/D2 — without it init cannot start at all). 2. Start the screencast of the whole flow before opening the page; keep it continuous (one take per consent variant: `tt.v1.music` for a never-commercial post, `tt.v1.branded` for a branded one). 3. Record the SQL of `plan.md` §3 before and after each run (`channel_connections`, `publications`, `platform_incidents`, `audit_logs`, `outbox_messages`) into the screenshot appendix — never a token, never the presigned URL. 4. Export the outbound bodies captured by the app's request logging as the "what we sent" columns: `source_info.source = PULL_FROM_URL`, `privacy_level`, `title` length in UTF-16 code units, `disable_comment`/`disable_duet`/`disable_stitch`, `brand_content_toggle`, `brand_organic_toggle`, `is_aigc` (D8/D2) — the reviewer compares these with the screencast. 5. Run the probes below and paste each raw response. 6. Redaction pass (§8 of `plan.md`), then sign `tiktok-internal-checklist.md`.

**Hand-off mechanism.** The pack lands in the 13-owned location and `13.4.3-T1` is notified with a message naming `the pack index (see Deliverable layout)`, the claimed volume, and the 4 renderings of `tiktok-consent-texts.json`; per CR-8 the filing states that `MonthlyActiveCreators` *is* the claimed number and that it must not exceed what the platform can serve while unaudited (≤ 5 posting users / 24 h, K9). No filing content is written by this task (C10).

## Steps

1. Verify the four DoR conditions of `plan.md` §10: real token/revoke taxonomy recorded (`07.1.1-T1`), `PULL_FROM_URL` verification + TTL proven (`07.3.1-T1`), 10.7.3-T0 approved against §1.3 and 10.7.3-T1 shipped, and the two `[OPEN]` items still out of scope. Write the result into `the pack index (see Deliverable layout)` as the run precondition block.
2. Confirm the staging facts of the capture protocol step 1 (audit status, flag rules, verified domain) and record them verbatim (`AuditStatus = pending` is expected at this point).
3. Perform the two private posts (one per consent variant) with the screencast running from page open to terminal status; save the take, then write the timestamp index (one row per U1–U13) into `the screencast row`.
4. Capture `tiktok-consent-texts.json` (both variants × vi/en with their `consent_text_version`), `tiktok-data-handling.md` (data-handling), `tiktok-intended-use.md` (intended-use, K11 + K17 assertions), `tiktok-volume.md` (claimed volume from the bound `TikTokOptions.MonthlyActiveCreators`).
5. Assemble `tiktok-errors-limits.json` from `07.1.1-T1`'s recorded taxonomy + `07.3.3-T1`'s D10 table, with one run or `FakeTikTokServer` test per code and the observed per-endpoint limits (`init` 6/min, `creator_info` 20/min, `status` 30/min, `token` 10/min).
6. Run probes P1–P5 (`plan.md` §9) and paste each raw response; a probe whose code differs from the D10 table is a **CR to the owning task**, not a checklist note.
7. Fill `tiktok-internal-checklist.md` row by row; every `fail` or `deviation-accepted` row must name a CR id or an owner decision.
8. Redaction pass, then hand off to `13.4.3-T1`; open ``tiktok-response-log.md``.
9. Drive the response loop until the verdict (or a rejection) arrives; log every exchange and every artefact it changed; close with a one-page summary to `07.4.1-T2`.

## Acceptance checks

- Given the staging run of a `tt.v1.music` post, When the screencast and the SQL snapshots are compared, Then the publication goes `scheduled` → `uploading` → `processing` → `published` with `privacy = SELF_ONLY`, `contains_synthetic_media = true`, `consent_source = user`, `consent_text_version = tt.v1.music`, and `platform_payload->'tiktok'->>'publishId'` present before the first status poll (D7).
- Given the branded run, When the consent declaration is captured, Then `consent_text_version = tt.v1.branded` and the rendered text cites TikTok's Branded Content Policy **and** the Music Usage Confirmation (U9, D5); a create body carrying `tt.v1.music` for that selection is refused with 400 `consent_text_outdated`.
- Given the checklist, When `tiktok-internal-checklist.md` is read, Then it has exactly one row per U1…U13, each with an evidence pointer (screencast timestamp, probe id or SQL result) and a result; no row is blank, `TBD` or `n/a`.
- Given a tampered create body (privacy ∉ `privacy_level_options`; `PUBLIC_TO_EVERYONE` while `AuditStatus = pending`; a creator-disabled interaction enabled; `brandedContent = true` with `SELF_ONLY`), When it is sent, Then the server answers 400 `tiktok_invalid_post_settings` and the UI is not the enforcement point (UC-2).
- Given a fresh page render (twice), When the outbound call log is inspected, Then `creator_info` was called on each render (U1) and the nickname of the connected account is visible in the screencast.
- Given `creator_info` returning HTTP 200 with `spam_risk_too_many_posts`, When the page is rendered, Then the attempt is stopped with `blockReason` shown and no publication is created (U2, D11).
- Given the volume artefact, When ``tiktok-volume.md`` is compared with the bound `TikTok:MonthlyActiveCreators`, Then the numbers are identical and the line "while unaudited, ≤ 5 posting users / 24 h (K9)" is present (CR-8).
- Given the pack, When it is scanned for secrets, Then no `access_token`, `refresh_token`, `open_id`, `client_secret`, `code_verifier`, `browser_nonce_hash` or presigned URL appears anywhere (D14).
- Given the pack as handed over, When `VP7_RedactionClean` (06.5.1-T1:117) runs over the repo index and every text artefact, Then it reports no token/e-mail/IP/video-id pattern, no binary sits in the repo (binaries live in `~/.nts/compliance/evidence-<yyyy-mm-dd>/`), and the index carries the app version and the sha256 of each binary (13.5.1-T1).
- Given the hand-off, When `13.4.3-T1` starts, Then it needs no additional input from 07 to write the submission.

## Tests

No new automated test file is created here (the folder changes no product code). Evidence uses the tests owned by the code tasks and the probes owned by this one:

- `NightTales.Api.IntegrationTests` (`PostgresFixture`, real PostgreSQL 17) with `FakeTikTokServer` from `NightTales.TestKit` (Kestrel, hand-written, **no mocking library**): must be green and are cited per `tiktok-errors-limits.json` row — `creator_info` public/private option sets + `comment_disabled` + the 200-with-error families (U2/U5/U6), init ok + each 403/429 code + URL expiry, status every terminal transition and each `fail_reason` family (U11), token with **rotating** refresh, revoke, per-endpoint counters (D17/F22).
- `NightTales.Application.UnitTests`: the D5 validation matrix and the D9/D10 maps (hand-written fakes from `NightTales.TestKit`) — cited by the U3/U4/U8/U9/U13 and error rows instead of a hand-run probe where a test already exists.
- `NightTales.Architecture.Tests`: cited for the guards the checklist depends on (one of `[Audited]`/`[NotAudited]`/`[AllowAnonymousRequest]` per command; only `UnitOfWorkBehavior` calls `SaveChangesAsync`).
- Probes P1–P5 of `plan.md` §9 are **manual, scripted and recorded** (request body → response → DB row), because the evidence must show the live staging surface, not a test harness: P1 render ×2, P2 the six validation/authorization refusals, P3 lost-response resume (no second init, no second post), P4 the status ladder, P5 disconnect while `scheduled`.
- The screencast is the only artefact that cannot be reproduced from a log; it is stored with the pack and indexed, and a failed take is retaken whole (never stitched).
- Redaction is verified mechanically, not by eye: the `VP7_RedactionClean` grep runs over `docs/compliance/evidence-<yyyy-mm-dd>/index.md` and every text artefact, and the command + result are recorded in the index's `Redaction checked` column (13.5.1-T1 / 06.5.1-T1:117).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| 10.7.3-T0 not yet approved against §1.3, or 10.7.3-T1 not shipped | **Blocked, do not improvise a screen**: report the dependency; the checklist cannot be run against a design that may change (README §5 residual risk) |
| A U-row fails because the screen deviates (default privacy, missing grey-out, rewritten declaration, no preview) | Open a CR to Lead10S with the U id + timestamp; the row stays `fail` until the shipped screen is re-captured; never mark `pass` on a verbal promise |
| A U-row fails because the server allows what the screen forbids | CR to the owning 07.x task (U3/U4/U8/U9/U13 → `07.2.2-T1`, U2 → `07.2.1-T1`, U11 → `07.3.2-T1`); the probe output is attached |
| `creator_info` returns a 200-error at run time (`spam_risk_*`, `reached_active_user_cap`) | The private post cannot complete: record the block as the U2 evidence (it is the requirement working) and reschedule the publish run; do **not** retry in a loop (`tiktok_cannot_post_now`, D10) |
| TikTok returns `url_ownership_unverified` or `unaudited_client_can_only_post_to_private_accounts` during a run | Platform incident on `oauth_client_id` (P1) — raise via `IPlatformIncidentStore.RaiseAsync`, publication back to `scheduled`, wait for `nts-worker incident clear` (06 D14), then repeat the run; the incident is evidence, not a workaround |
| `access_token_invalid` mid-run (24 h expiry) | Follow the D10 401 ladder: one refresh + retry inside the command; still 401 → connection `expired` + `tiktok_reauth_required`, reconnect, resume the take from the page open (a legal break only if the U-row evidence is unaffected) |
| Presigned URL (TTL ≥ 120 min, K16/D2) expires before the download completes | The run fails with a pull error; retake with a fresh render (the URL is never stored, D8) |
| A screencast frame contains another user's data or a token | Delete the take and re-record after fixing the environment (staging test account only); a redaction pass must never be applied to a frame that already leaked (the leak is reportable, 13 decides). Binaries stay in `~/.nts/compliance/evidence-<yyyy-mm-dd>/` — a take or index copied into the repo (or onto `/Volumes/Project`) is a redaction failure, not a convenience (13.5.1-T1 D14/O7/T5) |
| Reviewer asks for a product change | Becomes a CR; the pack is updated only after the change ships and is re-captured — never by editing the artefact text |
| Reviewer asks for the cancel endpoint or inbox mode | Answer "not used" quoting the `[OPEN]` items (K8, D9) — no task implements them |
| Audit rejected | The pack is closed as-is; the reasons go to `07.4.1-T2` (UC-5) and become follow-up CRs |
| Volume claim challenged as too high | `MonthlyActiveCreators` is an owner decision in `07.1.1-T1`; re-filing a lower number is a CR to D19, not an edit of `tiktok-volume.md` |

## Notes

- The acceptance instrument is the **server**, not the screen (UC-2): a tampered request must be refused even with a perfect UI, which is exactly what the audit reviewer will try.
- `publish_at` is the consent instant (D3/F21) — never cite it as a publish time in an artefact, and never build a volume number from it (CR-9).
- Posting spends no credits and writes no `credit_ledger` row (D16/F19); do not add a refund artefact.
- Status/metrics used as evidence: `tiktok_publish_attempts_total{outcome}`, `tiktok_post_latency_seconds` (init → `PUBLISH_COMPLETE`), `tiktok_active_user_cap_hit_total`, `tiktok_rate_limit_backoff_total{endpoint}` (D18); alert rules per CR-10.
- Keep every caption/consent rendering in the pack tied to its `consent_text_version`; an unversioned text is unauditable (D5).
- Evidence legend: ✅ file/run observed · ⚠️ unverified · [DECISION] · [OPEN] · [INFERENCE]; the two `[OPEN]` items are `POST /v2/post/publish/cancel/` and the inbox mode (`video.upload`) — both stay out of the audited path.
- Pack boundary: rows enter `13.5.1-T1`'s pack only as one of its seven flows (connect · publish form · per-video consent · disconnect + revoke explanation apply to 07) or as an artefact a citing task names (`13.4.3-T1` §2's required-UX matrix). The submitted-copy location stays 13's [OPEN]; 07 never writes the filing.
