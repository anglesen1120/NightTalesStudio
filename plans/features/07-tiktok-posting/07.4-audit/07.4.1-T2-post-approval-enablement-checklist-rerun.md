# 07.4.1-T2 — Post-approval enablement: `AuditStatus = approved`, production re-verification, rollout

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 07.4.1 | S (0.5) | BA + Ops | 07.4.1-T1, 13.4.3-T1 | — (unlocks public posting + `tiktok_publish` rollout, 07 CR-6) | P · R2 |

## Goal

After `13.4.3-T1` reports TikTok's **approval**, public posting is enabled and proven on production: `TikTokOptions.AuditStatus` is set to `approved` (a config value, no code change), the full `privacy_level_options` from `creator_info` becomes selectable instead of the pre-audit `SELF_ONLY` intersection, **one public post** ends `published` with `external_post_id` set when `publicaly_available_post_id` is non-empty, the **U1–U13 checklist is re-run on production** (not staging) and signed, and the `tiktok_publish` feature flag may leave owner-only for a percentage rollout (CR-6). If the verdict is a rejection, the opposite happens on purpose: `AuditStatus` stays `pending` (or becomes `rejected`), the flag stays owner-only, the reasons become follow-up CRs, and private posting keeps working (UC-5).

- `07.4.1-T1` outputs: the 07.4.1-T1 pack rows (`docs/compliance/evidence-<yyyy-mm-dd>/index.md` + binaries in `~/.nts/compliance/evidence-<yyyy-mm-dd>/`), the signed U1–U13 checklist artefact (`tiktok-internal-checklist.md`), the screencast timestamp index, the CR list.
- `13.4.3-T1` verdict: the approval (or rejection) record, any reviewer conditions attached to it, and its §7 exchange log; `13.4.3-T1` is the only task allowed to talk to TikTok about the filing (C10), and it owns `docs/compliance/tiktok-audit-<yyyy-mm-dd>.md` ([INFERENCE] name — whether the submitted copy lives there or in 07.4.1-T1's output is its **[OPEN]**).

- Ops: `11.6.2-T1` rollout rules + alert rules, `11.2-*` per-env secret/config mechanism (`nts/<env>/api/TIKTOK_CLIENT_SECRET`, D14), the `TikTok` config section in the production deployment, and `nts-worker` for incident/job inspection.
- Production test data: a **real public** TikTok account (test account switched public) connected through the normal connect flow (`07.1.2-T1`), and one episode whose video satisfies K6 (MP4/WebM/MOV, H.264, 23–60 FPS, 360–4096 px, ≤ 4 GB, duration ≤ `max_video_post_duration_sec`).

## Design

**Enablement is configuration plus verification, never a code change.**
- The only state flip is `TikTok:AuditStatus: approved` in the production config (D19; the same value 07.1.1-T1 recorded in `docs/ops/tiktok-oauth-setup.md` as `pending`). It is read through `IOptionsMonitor`, so the app picks it up on the next binding without a restart; the cached value must be re-read (verify behaviour after the change, do not assume).
- Behaviour that must change with it: the allowed privacy set goes from `creator_info.privacy_level_options ∩ { SELF_ONLY }` to the full `privacy_level_options` (D4); the validator's refusal of non-`SELF_ONLY` disappears — nothing else (validation matrix, consent variants, `is_aigc = true`, D7 idempotency, D9 status map stay identical).
- The flag: `feature_flags.tiktok_publish` `rules` moves from owner user ids to the documented rollout (CR-6). Recurring jobs (`PollTikTokStatusJob`, the TikTok branch of `TokenHealthJob`) may then register outside the boundary owner scope — their registration is flag-driven (D1, 06 D1 pattern), so the rollout step and the job-registration step are the same step.
- Volume guard: the live 24-h *active creator* count (creators with ≥ 1 posting attempt, computed from `publications` by `status` transitions — never by `publish_at`, CR-9) must stay below the **claimed** `TikTokOptions.MonthlyActiveCreators` (K10); the number filed by `13.4.3-T1` is a commitment (CR-8).
- Production re-verification reuses 07.4.1-T1's checklist **verbatim** (same U1–U13 rows, same evidence-pointer shape) against the production origin, with the additional U-row evidence that the privacy list now contains the account's real public options and that a public post is actually public.

**Rejection branch (must be planned, not improvised).** `AuditStatus` semantics: leave `pending` if the reviewer asked for changes (we are still applying), set `rejected` if the client was refused, so no future reader believes we are mid-audit. The flag stays owner-only, recurring jobs stay in the owner scope, and every reviewer reason becomes a CR with an owner; the app remains fully usable for private posting (K9 means nothing is broken by not being approved).

## Steps

1. Record the verdict: copy the approval/rejection text (or the reviewer's conditions) into the pack's `tiktok-response-log.md` row (`13.4.3-T1` §7 mirrors it) with its date, and note that `13.4.3-T1` is the filing owner (C10).
2. If approved: change the production config value `TikTok:AuditStatus` from `pending` to `approved` (config/secret store path per `11.2-*`); confirm the effective value the running process holds (config read-back + observed behaviour) before touching the flag.
3. Reconnect the public test account through the normal connect flow (the pre-audit connection is `SELF_ONLY`-bound in behaviour, not in data — a fresh connect also proves `07.1.2-T1`/`07.1.2-T2` on the post-audit path) and open the screen once on production.
4. Confirm on production that `GET /channels/{id}/tiktok/creator-info` now yields the account's real option set (e.g. `PUBLIC_TO_EVERYONE` present) and that the screen offers the full list with **no default** (U5).
5. Publish **one** episode publicly through the screen (real consent click, `tt.v1.music` or `tt.v1.branded` matching the disclosure selection), and follow it to `PUBLISH_COMPLETE`: record `status` transitions, `privacy`, `is_aigc`, `external_post_id` vs `publicaly_available_post_id`, and `tiktok_post_latency_seconds` (init → `PUBLISH_COMPLETE`).
6. Re-run the **U1–U13 checklist** on production and sign a second copy (the checklist artefact `tiktok-internal-checklist.md`, section "post-approval (production)"), keeping the staging section intact — a new capture date means a **new** `docs/compliance/evidence-<yyyy-mm-dd>/` folder and a fresh index row set, per this pack's per-capture-date rule.
7. Release the flag: set `feature_flags.rules` to the documented rollout (CR-6) and verify that `PollTikTokStatusJob`/`TokenHealthJob` register outside the owner scope (job registration log), and that the CR-10 alerts are live (`tiktok_active_user_cap_hit_total > 0` → P2).
8. Record the enablement for 13 (date, `AuditStatus`, flag rules, the public post id and its `external_post_id` state): hand the detail to `13.4.3-T1` §7, the enablement date to the enablement record, and the difference list (what changed vs staging) back to `13.4.3-T1`.
9. Rejection path: perform steps 1 and the rejection branch of `## Design`, open the follow-up CRs, and stop (no flag change, no config flip).
10. Write the rollback procedure into the same record: set `AuditStatus` back to `pending`, flag rules back to owner ids, and confirm the option list collapses again (prove it once on staging, not in production).

## Outputs

- Production config change `TikTok:AuditStatus = approved` (and the matching line in `docs/ops/tiktok-oauth-setup.md`).
- `tiktok-internal-checklist.md` §"post-approval (production)" — signed U1–U13 rows with production evidence pointers (new pack rows, new capture date).
- `tiktok-response-log.md` (mirrored into `13.4.3-T1` §7) — verdict + enablement record (public post id, `external_post_id` state, latency metric value).
- Flag-rollout record per CR-6 (+ the alert-rule confirmation per CR-10).
- On rejection: the CR list derived from the reviewer's reasons, with `AuditStatus` left `pending` (or set `rejected`) and no rollout.
- No code change, no migration, no new test file.

## Acceptance checks

- Given approval and `TikTokOptions.AuditStatus = approved` on production, When the screen is rendered for the public account, Then the privacy dropdown contains the account's real `privacy_level_options` (not just `SELF_ONLY`) and still has **no default** selection (U5, D4).
- Given the same state, When a `PUBLIC_TO_EVERYONE` publication is created and consented, Then it reaches `published` (never 400 `tiktok_invalid_post_settings`, never 403 `unaudited_client_can_only_post_to_private_accounts`) and `contains_synthetic_media = true` (U12).
- Given that public post, When its row is read, Then `privacy = PUBLIC_TO_EVERYONE` and `external_post_id` equals `publicaly_available_post_id[0]` when that list is non-empty and is `NULL` when it is empty (D9/K7) — both outcomes are acceptable; a fabricated id is not.
- Given the production re-run, When the checklist artefact is read, Then all thirteen U rows exist again with production evidence, the staging section is unchanged, and the file carries two dated signatures (one per capture date).
- Given `feature_flags.rules` after the rollout, When the flag is read, Then it matches the documented rollout (CR-6) and, on the previous state, was owner ids only — the before/after pair is recorded.
- Given the rollout, When job registration is inspected, Then `PollTikTokStatusJob` and the TikTok branch of `TokenHealthJob` register outside the owner scope, and the CR-10 alert rules are enabled.
- Given the live 24-h active-creator count, When it is compared with `TikTokOptions.MonthlyActiveCreators`, Then it is below the claimed number (K10) — and the count comes from `publications.status` transitions, not `publish_at` (CR-9).
- Given a rejection instead, When the session closes, Then `AuditStatus` is `pending` (or `rejected`), `feature_flags.tiktok_publish` is still owner-only, private posting still succeeds, and every reviewer reason is a CR with an owner (UC-5).
- Given the rollback procedure, When it is exercised on staging, Then the option list collapses to the `SELF_ONLY` intersection without a restart or migration.

## Tests

- No new automated test file (this task changes configuration and observes behaviour). Verification is the production probe **P6** of `plan.md` §9 plus the observations above, each recorded with its raw output.
- Cited (owned by the code tasks, must be green before the flip so a public-post failure is a config/environment issue and not a regression): `NightTales.Api.IntegrationTests` (`PostgresFixture`, real PostgreSQL 17) with `FakeTikTokServer` from `NightTales.TestKit` (hand-written, **no mocking library**) for the full `creator_info` option sets and the init/status paths; `NightTales.Application.UnitTests` for the D5 validation matrix with both `AuditStatus` states (pre-audit refusal of non-`SELF_ONLY`, post-audit acceptance of a real option); `NightTales.Architecture.Tests` unchanged.
- `TikTokOptions` binding/validation (`AuditStatus ∈ pending|approved|rejected`, section `TikTok`, D19) is verified by reading the effective production value and by one behaviour probe (option list before/after) — a config read-back, not a placeholder.
- The public post is a **single** live observation: no load test, no repeated posting (K10's ~15 posts/day/creator cap is shared with other Direct Post clients).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Verdict arrives with **conditions** (approve-after-fix, partial approval) | Treat as not approved until every condition is met and re-verified; keep `AuditStatus = pending`, open CRs per condition, re-run the affected U rows, then flip |
| Rejection | UC-5 path: `pending`/`rejected`, no rollout, reasons → CRs, private posting untouched |
| No verdict within the planned window | No flip, no rollout; chase through `13.4.3-T1`; log the delay in `tiktok-response-log.md` (a silent wait is not a status) |
| `AuditStatus = approved` but TikTok still rejects a public post with `unaudited_client_can_only_post_to_private_accounts` | **Our** state is wrong or the approval is not effective on that client id: re-check `ActiveClientId` vs the client the audit approved (D19), raise a P1 platform incident (D10/F06), revert to `pending`, and re-verify — never re-file a "public" post repeatedly against a 403 |
| The privacy list still shows only `SELF_ONLY` after the flip | The running process kept the cached option set: verify the effective config, restart/rebind if needed; a cached `creator_info` is not the cause (D11 caches nothing across users) |
| Public post ends `failed` | Read `fail_reason` → D10 code; `internal`/`video_pull_failed` are retryable once, `duration_check_failed`/`frame_rate_check_failed`/`picture_size_check_failed`/`file_format_check_failed` are K6 constraints on our file (fix the render, do not retry), `spam_risk_*` is a creator/platform limit |
| `reached_active_user_cap` during verification | P2 alert + `tiktok_active_user_cap` on the publication; wait for the next 24-h window — the cap is per client, so do **not** retry with other connections (K10) |
| `publicaly_available_post_id` empty | Legal for a private/unmoderated post; for a public post it means moderation has not populated it yet — record `NULL` and the observation time, do not fabricate an id |
| Rollout shows failures (init 5xx, latency spike) | Roll the flag back to owner ids (CR-6 rules), keep `AuditStatus = approved` (the audit is not the problem), and treat as a normal reliability incident |
| Someone "fixes" a U-row by editing the screen copy during verification | The screen is 10.7.3's; a change during post-approval verification invalidates the re-run — re-verify after the change lands, or open a CR and keep the row `fail` |
| Public posting desired for a branded post | `brandedContent = true` with `SELF_ONLY` is still refused (U8/D5) even after approval — the rule is not an audit artefact |
| Audit approval later revoked by TikTok | Flip back to `pending` immediately (rollback path), alert via the existing incident rules, and inform 13 |

## Notes

- Boundary: this task turns on a config value and records proof; it writes **no** code, migration, DTO or route (C5/CR-3's code surface is owned by 09/07.x).
- `publish_at` is the consent instant (D3/F21); the enablement record must not present it as a publish time (CR-9).
- Token health, refresh rotation and the 401 ladder (D13, D10/F24) are unchanged by approval — a public account does not change token lifetime (K13).
- The claimed volume stays the cap after approval too: `MonthlyActiveCreators` is refiled/raised only as a new audit action, never by editing config during this task (CR-8).
- Metrics to watch during the rollout window: `tiktok_publish_attempts_total{outcome}`, `tiktok_post_latency_seconds` (init → `PUBLISH_COMPLETE`), `tiktok_active_user_cap_hit_total`, `tiktok_rate_limit_backoff_total{endpoint}` (D18); alerts per CR-10, `platform_incident_open > 0` covers `url_ownership_unverified`.
- The enablement must leave the pack auditable: the production re-run is a **new** `evidence-<yyyy-mm-dd>/` capture (the pack's per-capture-date rule), the binaries stay in `~/.nts/compliance/evidence-<yyyy-mm-dd>/` and pass `VP7_RedactionClean`, and the enablement date lands in the enablement record.
- Two `[OPEN]` items remain out of the audited path and unlock nothing here: `POST /v2/post/publish/cancel/` (K8) and the inbox mode (`video.upload`, `SEND_TO_USER_INBOX`, D9).
- Evidence legend: ✅ observed · ⚠️ unverified · [DECISION] · [OPEN] · [INFERENCE] — everything this task records is a live observation or a configuration read-back.
