## Design

**Rule entry.** `id, severity (page | warn), for, expression | db_check, owner, runbook (docs/runbooks/<slug>.md), dedup_key, window`. `ops/alerts/rules.yml` [INFERENCE: exact path pinned by 11.6.2-T1's Outputs] is the single source; a threshold change is a reviewed diff, never a console edit.

**DB checks (this task owns them; D8).** `login_failures_spike`, `refresh_token_reuse`, `moderation_spike`, `token_refresh_failures`, `payment_integrity`, `security_email_failed` (template in the pinned 09 set), `post_deploy_smoke_failed` (pushed by 11.5.1-T1), `email_queue_stale` (oldest `email_messages` row `queued` > 15 min).

**Job.** `OpsAlertSweepJob` — recurring in 09.2.6-T1's `RecurringJobs.cs` (CR-8), single-instance via the house `[JobPolicy]`, interval `OpsAlerts:SweepMinutes` (5); loads the file once per run; one statement per check; pushes `(id, severity, dedup_key, summary)` to 11.6.2-T1's alert endpoint with 3 attempts and the owner e-mail fallback (09.2.6-T3's `SendEmailJob`); logs rule id/severity/counts only. `OpsAlertsOptions { Enabled, SweepMinutes = 5, PageCooldownMinutes = 60, RuleFile = "ops/alerts/rules.yml", EmailFallbackEnabled = true }`. Metrics `ops_alerts_fired_total{rule,severity}`, `ops_alert_sweep_duration_seconds`.

**Reconciliation.** A table in the task's evidence records each 08 §5.2 row → its new home (`11.6.2-T1` rule number, `12.8.x`, or one of the DB checks), with the D17 value for the shared ones; CR-9 writes the same table into the high-level plan.

**Contract check.** `tools/ops/check_alert_contract.sh` (same family as 11's `check_metrics_contract.sh`): every rule has `owner` + `runbook`; the referenced runbook file exists; every rule id appears in `docs/runbooks/index.md`.

## Acceptance checks

- [ ] Every rule in the file has `id`, `severity`, `owner`, `runbook`, `dedup_key`, `window`, and `expression` xor `db_check`; the referenced runbook paths exist.
- [ ] All eight DB checks are present with their thresholds; `payment_integrity` values equal 12's, not new numbers.
- [ ] Two consecutive sweeps of one stuck condition produce exactly one page (dedup key + `repeat_interval` = 60 min); a cleared condition produces none.
- [ ] An alert endpoint failure triggers the e-mail fallback once and increments `ops_alerts_fired_total{severity="send_failed"}`; a throwing check does not stop the other checks.
- [ ] An invalid rule file pages `severity="invalid_config"` and the job keeps running instead of crashing.
- [ ] `check_alert_contract.sh` exits 0 on the shipped file, 1 when one rule loses its `owner` or its runbook, and 1 when the index omits a rule id.
- [ ] The reconciliation table has no orphan 08 §5.2 row and no duplicated threshold.

## Tests

- Rule file: table-driven validation of every entry; negative cases (missing owner, missing file, duplicate id, unknown severity).
- Job: seeded rows at the threshold and one over, per check, with `FakeClock`; asserting exactly the expected `(id, severity)` set; idempotency across two runs; cooldown behaviour; a check that throws; the send-failure path.
- Metrics: `ops_alerts_fired_total` increments per rule and per send failure; the sweep duration histogram is recorded.
- CI: `check_alert_contract.sh` positive + negative; the existing metrics-contract check still passes (the shared file must satisfy both).
- Manual: one provocation per DB check on staging (the full drill matrix is 08.2.1-T2).

## Failure handling and edge cases

- Alert endpoint unreachable → 3 attempts with backoff, then the e-mail fallback; both failing increments the metric and leaves the condition for the next sweep (no local state, no lost condition).
- Clock skew → all windows use `IClock`; never `now()` in SQL where the test needs a boundary.
- A check whose SQL is slow (> 2 s) → logged with the rule id; the sweep does not abort.
- `OpsAlerts:Enabled = false` → the DB checks are skipped entirely; metric rules from 11 keep working (independent switches).
- A rule file that is missing at start-up → the job fails fast with a configuration error and does not run the sweep.
- Threshold changes go through a diff; a threshold with two owners is a defect caught by the reconciliation table, not by convention.

## Notes
