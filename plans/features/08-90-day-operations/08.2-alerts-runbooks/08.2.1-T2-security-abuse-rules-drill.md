## Goal

Route every security and abuse condition that 08 §5.2 names but no metric can express into 11.6.2-T1's pipeline with an owner and a runbook link, and prove delivery by firing each S rule once on staging — including the security e-mail that must use the configuration active **before** the change (D9, F9, F16).

- 08.2.1-T1's rule file, `OpsAlertSweepJob` and `check_alert_contract.sh`.
- 09.10.4-T3's `ISecurityAlerter.AlertAsync(SecurityEvent evt, ct)` / `SecurityEvent(string Kind, Guid? SubjectUserId, string? Detail)` (09.3-auth/09.10.4-T1:53-54; severity/template routing is 09.10.4-T3's `SecurityEventCatalog` lookup, not a payload field); the pinned security template set (`security_alert`, `owner_action_pending`, `setting_change_pending`, `approval_cancel`, `mfa_failed_notice`, `session_new_device`, `mfa_reset_forced`) — consumed, never re-implemented (K23, D9).

- `../../../09-backend-api.md:278` — the pre-change-config e-mail rule and the P1-on-failed-security-e-mail requirement.
- 11.6.2-T1's alert channel; 11.5.1-T1's deploy pipeline (smoke-test push); 12.3.3-T2 and 11.6.2-T1 rule 16 (linked, not duplicated).

## Design

**Rule rows added here (all in 08.2.1-T1's file).** The nine D9 security events become real **metric** rules — `expression: security_events_total{kind="<event>"} > 0`, `severity: page` — one id per event (`sec_settings_change`, `sec_role_change`, `sec_mfa_change`, `sec_recovery_code_used`, `sec_owner_login_new_ip`, `sec_grant_above_cap`, `sec_settings_rollback`, `sec_owner_action_pending` (08 O-4), `sec_break_glass`), each with `owner = owner-role` and `runbook = docs/runbooks/security-incident.md`, loaded by 11.6.2-T1's pipeline like its other 21 rules (K25, 08 CR-17) — no longer a prose-only mapping; plus `login_failures_spike`, `refresh_token_reuse`, `moderation_spike` (runbook `moderation-abuse.md`), `token_refresh_failures` (runbook `token-refresh.md`), `post_deploy_smoke_failed` (runbook `api-error-spike.md`), `security_email_failed` (runbook `security-incident.md`), `email_queue_stale` (runbook `security-incident.md`).

**Drill matrix.** `docs/ops/drills/2026-10-alert-drill.md`: one row per rule — `rule id | provocation on staging | expected destination (channel + owner e-mail) | detection latency | cleared | notes`; every S rule is provoked once (synthetic row for DB checks, a threshold-crossing burst for metric rules, a settings change for the security events), the latency is measured from provocation to notification, and the condition is cleared while the rule stays enabled; each `sec_*` row's provocation also asserts `security_events_total{kind="<event>"}` incremented by exactly one.

**Pre-change-config assertion.** Change the `email` integration, then trigger a security event: the owner e-mail must arrive through the **old** configuration (09 §278), `security_events_total{kind="<event>"}` must increment by exactly one, and the corresponding `sec_*` metric rule must page; the failed-e-mail path is exercised by pointing the security template (`approval_cancel` or another from the pinned set) at a failing address, which must raise `security_email_failed` as a P1.

**Links, not duplicates.** Rule 16 (`platform_incident_open`, 11.6.2-T1) and 12's `paid_volume_anomaly` are verified present in the drill sheet with their owners and runbooks, but their thresholds stay 11's/12's.

## Steps

1. Add the rule rows above (ids, severity, owner, runbook, dedup key, window) to the file.
2. Verify rule 16 and 12's paid-volume rule are covered by an owner + runbook entry in the index; record the link in the drill sheet.
3. Run the drill on staging stage by stage and fill the matrix (latency, destination, cleared).
4. Perform the pre-change-config assertion and record the two e-mails (old configuration delivers; the failing case raises the P1 rule).
5. Record the outcome, defects and owners in `/tmp`? No — in `docs/ops/drills/2026-10-alert-drill.md` and, for anything that needs work, as a backlog row (08.3.2-T1).

## Outputs

- The added rule rows in 08.2.1-T1's file.
- `docs/ops/drills/2026-10-alert-drill.md` with the complete matrix and latencies.
- The pre-change-config evidence (two e-mails) referenced in that file.

## Acceptance checks

- [ ] Every rule listed in this task exists in the file with an `owner` and an existing runbook, and `check_alert_contract.sh` exits 0.
- [ ] The drill matrix has one completed row per S rule with a measured latency and a "cleared" note; no rule is left firing.
- [ ] The security e-mail arrived through the configuration active before the change; the deliberately failed case raised `security_email_failed` as a page; each `sec_*` rule fired from `security_events_total{kind}` crossing 0, not from a manual push.
- [ ] Rule 16 and 12's paid-volume rule appear in the matrix as linked (owner + runbook only, no threshold copy).
- [ ] Any rule whose detection exceeded 5 minutes is recorded as a defect with an owner and a date, not accepted silently.
- [ ] No user content, e-mail address or story text appears in any payload captured during the drill.

## Tests

- CI: the rule-presence test (every drill-sheet rule id exists in the file) and `check_alert_contract.sh`.
- Staging (manual acceptance): the drill itself; provocation scripts are one-off, not committed as tests.
- Regression: after the drill, one sweep with no condition produces zero pages (proves the cleared state).

## Failure handling and edge cases

- No alert channel chosen yet (`11.2.1-T1` `[OPEN]`) → the e-mail fallback is the delivery path and the drill records that the channel is unproven; this is a recorded defect with an owner, never a silent pass.
- A provocation that cannot be produced on staging (e.g. a real OAuth-client failure) → simulate the row that the rule reads and say so in the matrix ("synthetic row").
- Duplicate pages during the drill → expected until the cooldown window passes; the matrix notes it so it is not mistaken for a defect.
- Staging e-mail delivery blocked by the provider → use the mailpit/Mailpit-style sink configured for staging (11.1.1-T1) and note the destination difference.
- A rule that fires but has no runbook link → the drill fails; fix the file, do not edit the runbook list to match.

## Notes

- Security-event alerts go only to owners and are never shared with users or third parties (K12).
- The drill file is the evidence the DoR and the day-30 checkpoint read.
