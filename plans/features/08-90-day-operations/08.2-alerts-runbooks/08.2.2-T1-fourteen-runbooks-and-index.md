# 08.2.2-T1 — The 14 S runbooks and the runbook index

## Goal

Fourteen operational runbooks in `docs/runbooks/` with a fixed shape, and `docs/runbooks/index.md` mapping every alert rule to an owner and a runbook — the artifact NFR-08-1 ("each alert has an owner, a threshold and a runbook link") is verified against (FR-08-2, D11).

## Inputs

- `../../../08-90-day-operations.md` §5.3 (the scenario list) and §7 (fire each alert once and follow its runbook end to end).
- 08.2.1-T1's rule file (rule ids, owners) and `tools/ops/check_alert_contract.sh`.
- P runbooks to reference, never rewrite: `restore-drill.md` (11.6.1-T1), `node-deploy.md` (11.3.1-T3), `secrets-rotation.md` and the key-leak runbook (11.5.2-T1), `source-finder-allow-list.md` (02.7.2-T1), plus 08.4.4-T1's takedown runbook.
- Contracts the fix steps must cite: 06.2.3-T3 (`platform_incidents` clear verb), 09.10.7-T1 (break-glass verbs/exit codes), 12.8.3-T1 (runway + resume probe), 12.3.3-T2 (payment anomaly), 13.3.1-T1 (deletion due), 11.6.2-T1 (channel/board).

## Design

**Shape (every file).** `Symptoms` · `Checks` · `Fix steps` (copy-pasteable commands, no placeholders beyond documented variables) · `User communication (vi/en)` (templates per error class, referencing 09 §5.4 code names) · `Follow-up` · `Owner`.

**The 14 slugs** (D11): `worker-down`, `api-error-spike`, `outbox-lag`, `render-queue`, `openai-outage`, `openai-balance`, `moderation-abuse`, `youtube-quota`, `token-refresh`, `payments-integrity`, `deletion-deadline`, `security-incident`, `owner-recovery`, `support-sla`.

**Per-runbook scope (one line each).** `worker-down`: node down/no capacity, `render_worker_unavailable`, drain/activate via `/admin/worker-nodes`; `api-error-spike`: 5xx burst, deploy rollback, smoke-test push; `outbox-lag`: lag metric, stuck subscriber, replay; `render-queue`: queued-too-long, capacity and `Render:QueueAlertMinutes`; `openai-outage`: 429/5xx, retry budget, story/render impact; `openai-balance`: runway, top-up, resume probe (`POST /admin/funding/resume`); `moderation-abuse`: spike handling, suspend via 09.10.5-T1, report path (13); `youtube-quota`: quota exhausted, wait vs extension, publication holds; `token-refresh`: refresh failures and `invalid_client` (OAuth-client hold + clear verb, 06.2.3-T3); `payments-integrity`: signature failures, `needs_review`, anomaly, chargeback (12); `deletion-deadline`: `due_at < 24 h`, the 13.3.1-T1 path; `security-incident`: suspected key leak (rotate the node image key per 11's runbook and each node's adapter key), account takeover, token reuse, D9 events; `owner-recovery`: break-glass `nts owner recover|restore|resolve`, sealed codes (08.2.2-T2 fills the rehearsal record); `support-sla`: a stuck support queue, SLA breach triage, macro/FAQ update.

**Index.** `docs/runbooks/index.md`: `alert id | rule id in ops/alerts/rules.yml | severity | owner | runbook | last rehearsed`. It is generated by hand and checked in CI: every rule id (metric rules included) must appear exactly once, and every `runbook` path must exist.

## Steps

1. Write the six worker/infra runbooks (`worker-down`, `api-error-spike`, `outbox-lag`, `render-queue`, `openai-outage`, `openai-balance`).
2. Write the four publishing/money runbooks (`youtube-quota`, `token-refresh`, `payments-integrity`, `deletion-deadline`).
3. Write the three account/abuse runbooks (`security-incident`, `moderation-abuse`, `owner-recovery` — the last with the rehearsal record placeholder filled by 08.2.2-T2).
4. Write `support-sla` and then the index with all rule ids and owners.
5. Wire `check_alert_contract.sh` (from 08.2.1-T1) to fail when a rule or an index row is missing.
6. Walk the three most likely runbooks (worker down, token refresh, openai-balance) once end to end on staging and record the result in each file's follow-up section.

## Outputs

- 14 files under `docs/runbooks/` + `docs/runbooks/index.md`.
- The three walk records (one per walked runbook).
- The CI check green on the complete set.

## Acceptance checks

- [ ] All 14 files exist, each with the six sections of the shape above; no section is empty.
- [ ] Every rule id in `ops/alerts/rules.yml` appears in the index with an owner and a runbook that exists, and no index row points at a missing rule.
- [ ] Every fix step uses a real command or a documented variable and cites its owning contract (06/09/11/12/13); no invented flags.
- [ ] `tools/ops/check_alert_contract.sh` exits 0 on the shipped set.
- [ ] Each runbook has vi **and** en user-communication templates and a named owner (role, not a person's phone number).
- [ ] No runbook contains a secret, a token, a password, a webhook URL with a key, or a personal data example.

## Tests

- CI: `check_alert_contract.sh` (rule ↔ runbook ↔ index completeness) and the existing metrics-contract check.
- Manual walk: three runbooks end to end on staging with the record written into the file's follow-up section.
- Review: a reviewer reads each fix step against its cited contract line; runbooks are ≤ 1 page and readable under pressure.
- No automated test asserts runbook prose (that would be source-text testing).

## Failure handling and edge cases

- A scenario whose contract is still `[OPEN]` (e.g. the alert channel) → the runbook names the fallback path (owner e-mail) and marks the unproven part.
- A runbook discovered to be wrong during the walk → fix the file in the same session and note the change in its follow-up section.
- Two rules sharing one runbook → allowed and normal (`security-incident` covers several); the index still lists each rule id separately.
- A new rule without a runbook → CI fails, so the index cannot drift.
- Retention: runbooks are repository files; nothing is stored in the platform.

## Notes

- P runbooks are referenced by link; do not copy them, and do not move them.
- Keep the user-communication templates short, in vi and en, and free of legal promises.
- The index is the single place where "who owns this alert" is answered.
