# 08.2.2-T2 — Break-glass rehearsal and sealed recovery codes

## Goal

Prove on staging that the owner can be recovered with the audited one-shot job, and write the sealed offline recovery-code procedure — including the measured time from starting recovery to a working owner login (08.2.2 story; D12).

## Inputs

- `docs/runbooks/owner-recovery.md` (08.2.2-T1) — the file this task fills the rehearsal record into.
- `../../../09-backend-api.md:289-292` — break-glass: one-shot `nts-admin` job, `nts owner recover --email` (sole owner: MFA reset + forced password reset; with several owners: a time-locked request), `nts owner restore --email`, `nts owner resolve --request|--change`, verbs/exit codes 0/2/3 (K23).
- `11.6.4-T1` — the `nts-admin` job image, proposed by 09 W3 CR-6, still `[OPEN]` (K23). If it does not exist, this task is blocked, not faked.
- 11.6.2-T1's alert pipeline (an alert must fire on job start) and the owner e-mail path (09.10.4-T3).
- `../../../08-90-day-operations.md` §8 — "≥ 2 owners or sealed offline recovery codes"; DECISIONS §10 (owner dispute/restore conditions).

## Design

**Preconditions.** Staging only (never production); the rehearsal is announced to all owners; two owners exist **or** the sealed codes are the sole path; the staging owner's MFA state is captured before the run so it can be restored.

**Rehearsal script.** (1) `nts owner recover --email <staging owner>` → expect MFA reset + forced password reset; (2) complete the reset flow and log in; (3) `nts owner restore --email <owner>` to restore the previous state; (4) exercise `nts owner resolve --request|--change` against a synthetic pending request; (5) record the timestamps of start, job start, alert, owner e-mail receipt and first successful login.

**Assertions.** The platform job audit shows the operator identity (09 §289); the alert pipeline fires on job start; every owner receives the e-mail; the time from start to working login is recorded; exit codes are 0 (success), 2 (nothing to do) and 3 (refused) as documented, and a refused case is demonstrated deliberately (e.g. resolving an expired request).

**Sealed code procedure (written into the runbook).** Two copies on paper, one stored off-site, never in the repository, never in a password manager's shared vault; each use rotates the codes through the platform's MFA settings; the storage location and the last rotation date are recorded in the runbook (the codes themselves never are); ≥ 2 owners is preferred over a single-owner sealed set.

**Evidence table** (inside `docs/runbooks/owner-recovery.md`): `step | command | expected | observed | timestamp | operator`.

## Steps

1. Confirm `11.6.4-T1` exists and the staging owners agree on a maintenance window; capture the pre-run MFA state.
2. Run steps 1–2 of the script; fill the evidence table with timestamps.
3. Run steps 3–4 (restore + a synthetic `resolve`), including one deliberately refused case for exit code 3.
4. Verify the four assertions (audit, alert, owner e-mail, measured time) and record the numbers.
5. Write the sealed-code procedure and the rotation rule into the runbook; restore the staging owner state and confirm a normal login.

## Outputs

- The filled rehearsal record and sealed-code procedure in `docs/runbooks/owner-recovery.md`.
- A short outcome note (measured time, defects, owners) linked from `docs/runbooks/index.md` (`last rehearsed` column).

## Acceptance checks

- [ ] The evidence table has every step with a command, an observed result and a timestamp; the start-to-working-login time is a number.
- [ ] The job audit names the operator; the alert fired at job start; all owners received the e-mail (headers recorded).
- [ ] Exit codes 0, 2 and 3 were each observed at least once.
- [ ] The sealed-code procedure exists with the two-copy/off-site/rotation rules and contains no code.
- [ ] The staging owner's original MFA state is restored and login is verified; no production system was touched.
- [ ] Nothing in the runbook or the records contains a secret, a TOTP seed or a recovery code.

## Tests

- Manual acceptance: the rehearsal itself, with the transcript pasted into the evidence table (commands and outputs, secrets redacted by hand).
- Syntax check: each command's flags are compared against 09.10.7-T1's contract before the run; a mismatch stops the rehearsal and becomes a defect for 09.
- Regression: after restore, a normal MFA login and one ordinary admin action prove the account is healthy.

## Failure handling and edge cases

- `11.6.4-T1` missing → stop and report blocked `[OPEN]`; never hand-run an unreviewed recovery path against staging, and never rehearse in production.
- Owner e-mail not received → treat as the P1 path (`security_email_failed` / `email_queue_stale`); record it and file a defect with an owner.
- Restore fails or leaves the account in a mixed state → freeze staging, keep the evidence, and escalate to 09; do not improvise a second recovery.
- A second owner is unavailable during the window → the sealed codes are the fallback and the record states which path was used.
- The rehearsal exceeds the window → stop at the last completed step, restore, and reschedule; a partial record beats an unverified claim.
