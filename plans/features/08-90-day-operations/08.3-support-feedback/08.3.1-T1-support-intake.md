# 08.3.1-T1 — Support intake: alias, tags, SLA clocks and macros

## Goal

The support process itself: a shared `support@<domain>` alias, a fixed tag taxonomy mapped to 08 §5.4's response targets, bilingual macros, a weekly SLA log that feeds the KPI `support_*` keys, and the explicit **no impersonation** rule (FR-08-3, D10, flag `no-impersonation`).

## Inputs

- `../../../08-90-day-operations.md` §4 (08.3.1) and §5.4 (the four response-target rows).
- §B3 D10 — channel, tag set, SLA mapping, macro rules, staff-access rules, retention.
- `../../../09-backend-api.md:284` and `../../../13-compliance.md:115` — no impersonation; content only inside a moderation/report case, each view audited (K12).
- 09.10.5-T1 — the audited staff actions (reason required, `audit_logs` category `support`, `visibility = internal`).
- 11.2.1-T1 — the e-mail provider whose plan carries the alias; the domain from `App:PublicOrigin`.
- 08.1.2-T1's weekly template (the `## Support themes` section) and 08.3.1-T2 (`/{locale}/help`).

## Design

**Channel.** `support@<domain>` on the existing provider (no forwarding to a personal mailbox, spam filtering on, no auto-reply, attachments rejected, 180-day retention stated in the process doc). The alias never receives a token or a story excerpt: users are told, in the FAQ and the macros, to send ids only.

**Tags (fixed).** `billing`, `render`, `publish`, `account`, `content_report`.
**SLA mapping to §5.4.** `account` (locked, or paid with no credits) → 8 business hours; `render` and `publish` → 1 business day; `content_report` → 72 h; general `billing` questions → 2 business days. The business-hours window (time zone, holidays) is defined once in the process doc.

**Macros.** One canned vi/en reply per tag plus one per error code a user is likely to quote (names taken from 09 §5.4's catalogue, never invented). Rules: a macro never asks for a password, TOTP code, recovery code or a screenshot containing a token; it always states what the user should see when the fix works; it never promises a date that the platform cannot keep. Credential-receipt cases (a user sends their password) get a dedicated macro that instructs a forced reset via 09.10.5-T1.

**Staff access — no impersonation.** Support acts only through 09.10.5-T1's actions with a reason and an audit row; account/billing/session data may be viewed, story text/sources/videos only inside a moderation event or a report case (each view audited as `content_viewed`). There is no view-as-user, no session sharing and no "log in as" path anywhere in the platform (D10, F7). The process doc states this in one paragraph and the macros repeat it.

**SLA log.** `docs/support/sla/YYYY-WW.md`, one row per ticket: `ticket | tag | opened_at | first_response_at | first_response_minutes | sla_target | breach | theme`. It is the manual source of `support_first_response_median_hours` and `support_sla_breaches` (D7) and feeds 08.1.2's weekly review.

## Steps

1. Configure the alias on the provider (spam filter on, auto-reply off, attachment rejection, no forwarding) and write `docs/support/process.md`: channel, tags, SLA mapping, business hours, retention, no-impersonation rule, escalation path to `docs/runbooks/support-sla.md`.
2. Write the macro set (vi + en) as `docs/support/macros.vi.md` / `macros.en.md`, one per tag plus the top error codes and the credential-receipt case.
3. Create `docs/support/sla/TEMPLATE.md` and the first `YYYY-WW.md`, aligned with 08.1.2's `## Support themes` section.
4. Send a test message to the alias and complete the first row end to end (tag, first response, target, breach flag).
5. Record the escalation path: a queue older than the target is a runbook action, not an alert (no new platform alert is added here).
6. Announce the channel to the beta cohort (support address in the app footer via 08.3.1-T2's Help page).

## Outputs

- `docs/support/process.md`, `docs/support/macros.vi.md`, `docs/support/macros.en.md`, `docs/support/sla/TEMPLATE.md` + the first week's log.
- The configured alias (provider-side) and its settings recorded in the process doc.

## Acceptance checks

- [ ] A test message arrives at the alias; the first-response time is recorded and compared with the tag's target; the log row is complete.
- [ ] Every tag has an SLA target from §5.4 recorded in the process doc, and every tag has at least one macro in vi and en.
- [ ] The no-impersonation rule is written in the process doc, and no macro asks for a password, TOTP code or recovery code.
- [ ] The credential-receipt macro exists and instructs a forced password reset through 09.10.5-T1.
- [ ] Provider settings match the design (no forwarding, spam filter on, no auto-reply, attachments rejected, 180-day retention stated).
- [ ] The SLA log's columns match what 08.1.2's weekly review reads, and one full week is filled.

## Tests

- Manual acceptance: the live test message, the triage, the tagged reply and the log row.
- Review: a read-through of every macro for forbidden prompts and for promises the platform cannot keep; the tag set is compared with 08 §4 and 08.3.1-T2's FAQ sections.
- No automated test: this is a process artifact with no platform code.
- Sanity: a second person follows `process.md` alone and reproduces the triage of a sample ticket (one dry run).

## Failure handling and edge cases

- The alias cannot be created on the current provider plan → use a temporary alias on the same provider, record it in the process doc, and note the swap in the backlog.
- A spam flood → provider filtering plus no auto-reply; the weekly theme count reveals it and the mitigation is recorded.
- A ticket about a user's own content → no content is copied into the log; the log stores ids and themes only.
- A user requests deletion through support → hand off to the account-deletion path (13.3.2) rather than handling it by e-mail.
- A breach that repeats for the same tag → raise it in the weekly review; if it persists, it becomes a backlog item (08.3.2-T1), not a silent covenant.

## Notes

- Support is a process, not a product feature: no ticket table, no ticket API, no help-desk integration (D10).
- Do not add an alert for SLA breaches here; the escalation lives in the `support-sla` runbook and the weekly review.
- The SLA log is a manual KPI source: keep the columns stable so 08.1.1-T1's `manual` block and the review template never disagree.
