# 08.3.1-T2 — Help/FAQ page and in-app Help link

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 08.3.1 | XS (0.25) | FE | 08.3.1-T1, 10.3.1-T2 (soft) | — | S · M2 |

## Goal

A public, prerendered FAQ page at `/{locale}/help` (vi + en) plus the in-app Help link that opens it with a prefilled, id-only support message (D10; the page 08.3.1-T1's process points users to).

## Inputs

- 08.3.1-T1's process, macro set and tag taxonomy; the FAQ section list must match the tags.
- 10's public shell and prerender list (SD2) with the sitemap; Lead10S agreed to add `/{locale}/help` (2026-09-25, CR-13).
- Shared web pieces: `PageHeader`, `EmptyState`/`ErrorState` (10.1.3-T1), `safe-filename`-style pure helpers pattern, `shared/util/` conventions, i18n scopes (10 README §6).
- 10.10.1-T1's `@axe-core/playwright` pass (WCAG 2.1 AA).
- 09 §5.4's error-code names for the FAQ's "what does this message mean" section.

## Design

**Route.** `/{locale}/help` — public, no auth, prerendered at build time (static output, no data call), included in 10's SD2 prerender list and in the sitemap. Content: static sections, no form, no upload, no tracking.

**Sections.** Getting started; Credits and billing; Publishing (YouTube; TikTok when it ships); Render and video; Account and security; Content reports and abuse. Each section ends with the "Contact support" button.

**Support link builder.** `shared/util/support-link.ts`: `buildSupportMailto(origin, tag, ids, appVersion, uiLocale)` returning `mailto:support@<domain>?subject=…&body=…` with `subject = [nts:<tag>] <short title>` and `body` containing only `episode`, `renderJob`, `publication`, `appVersion`, `uiLocale`. It must never include a token, a cookie, a story title, an e-mail address or a full error message; the address is also rendered as copyable text for clients where `mailto:` fails.

**Navigation.** A `help` nav entry in the app shell (visible to signed-in users; signed-out users reach the page from the footer link) and the same link from the `/help` page itself.

**Content authoring.** The reviewed source is `docs/support/faq.vi.md` / `faq.en.md` (08.3.1-T1's folder set); the page's content files are updated in the same pull request, so the doc and the page never drift. No CI test asserts prose (that would be source-text testing); the review of the pull request is the check.

## Steps

1. Add the route and feature folder (`features/help/`) with the section skeletons in vi and en.
2. Write the content from `docs/support/faq.{vi,en}.md`, one FAQ entry per recurring question and one per 09 §5.4 error code that a user can hit.
3. Implement `buildSupportMailto` with tests (pinned keys, encoding, no token, fallback text).
4. Wire the nav/footer links and ask 10 to include `/{locale}/help` in the prerender list and sitemap (CR-13 — already agreed).
5. Add the Playwright spec (both locales, axe pass, mailto assertion) and verify the prerendered output contains the content without a client call.

## Outputs

- `features/help/**` (route, page, content sections, `support-link.ts`, tests).
- `docs/support/faq.vi.md` / `faq.en.md` (the reviewed twins of the page content).
- The nav entry/footer link and the CR-13 prerender + sitemap entry.
- `web/e2e/help.spec.ts` (vi/en render, axe, mailto).

## Acceptance checks

- [ ] `/{locale}/help` renders for both locales as prerendered HTML, without authentication, and appears in the sitemap.
- [ ] Every section ends with a "Contact support" button; the link's query keys are exactly the pinned ones and contain no token or title.
- [ ] The FAQ covers the five tags and the error codes a beta user is most likely to see; no promise of a timeline or a refund appears.
- [ ] The page passes the axe check with the WCAG 2.1 AA tag set; headings are sequential and the content is readable without JavaScript.
- [ ] A signed-in user sees the Help entry next to the account menu; a signed-out visitor can still reach the page from the footer.
- [ ] `docs/support/faq.{vi,en}.md` and the page content describe the same entries after the pull request.

## Tests

- Unit (TS): `buildSupportMailto` key set, encoding, tag placement, absence of token-like values, and the plain-address fallback.
- E2E (Playwright): both locales load, axe passes, the support button's `href` equals the builder output for a fixed input.
- Build: the prerender step produces `/{locale}/help` (asserted by the existing prerender test harness, not by a prose check).
- Manual: open the link on a phone and confirm the mail client opens with the ids; on a desktop without a mail client, the copyable address is usable.

## Failure handling and edge cases

- Missing i18n key → the build/test fails; never fall back to a partial translation.
- No `mailto:` handler on the device → the address is shown as copyable text with instructions.
- A user pastes a token or a password into the message anyway → the macro set (08.3.1-T1) handles it with a forced reset; the page itself cannot prevent it, and it never asks for it.
- The support alias changes → one constant in the builder plus the rendered text; update the FAQ's copy in the same pull request.
- The page is reachable from search engines → intended; it contains no user data and no dynamic content.

## Notes

- No form and no file upload: spam resistance and the "never store content" rule (D10/F14) both depend on the mailto model.
- 10 owns the shell, the i18n setup and the prerender list; this task only adds the route, the content and the nav entry (CR-13).
- Keep the page short: the FAQ answers, the macros handle the reply.
