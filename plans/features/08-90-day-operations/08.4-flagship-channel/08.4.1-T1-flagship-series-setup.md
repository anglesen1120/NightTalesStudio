# 08.4.1-T1 — Flagship series setup: topic line, style, voice, length tier, autopilot settings + authorization, 12-week calendar

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

Stand up the one flagship series the Channel phase runs on, entirely through the product, and leave behind two documents: `docs/ops/flagship/setup.md` (the configuration, the accepted authorization and the audit snapshot) and `docs/ops/flagship/calendar.md` (12 weekly rows). After this task the series is configured, authorized, and its planner produces slots — but it is not yet required to be publicly publishing (that is the rehearsal in 08.4.2-T1 and §11 of the folder plan).

The deliverable is **configuration + documents**: no code, no migration, no route, no config key, no new table. Every setting written here is owned and validated by 02.8.3-T2 (`autopilot_settings`) or lives on the series aggregate.

## Inputs

- `docs/ops/gate-2.md` — signed by the owner (08.5.1-T1). Hard prerequisite: `../README.md` F4/D4 and K3 say the Channel phase must not start before the Gate 2 criteria exist. This task records the document's date and the owner's sign-off line in `setup.md`.
- 02.8.3-T2 — `/series/{id}/autopilot` GET/PUT, `…/authorization` POST/DELETE, `AutopilotSettingsValidator` ranges, the rendered authorization text (`textVersion`, `textHash`), re-auth requirement (09.3.2 `POST /auth/reauth`, 5-minute freshness).
- 06.1.2-T2 — `GET /channels`: the YouTube connection exists and is `active`, with a channel title.
- 13.4.2-T1 (soft) — the audit filing; until it is filed `YouTube:AuditStatus = pending` (06.1.1-T1 records `pending` for both environments), so this task runs the private rehearsal path and records the status it observed.
- 03/04 catalogs — the voice and style candidates for the 3-candidate test (the same catalogs 03/04 expose; the test is run on the M0 outputs, `../README.md` D1).
- 02.8.2 `plan.md` §3.3 — `Autopilot:Gates` thresholds and `DryRun`; `AutopilotDto.GatesDryRun` / `GatesDryRunRemaining` tell this task whether the phase can auto-approve yet.
- `../README.md` D1 (the defaults to apply), K2, K6, K7; 02.8.3 `plan.md` §3.1 (`autopilot_settings` jsonb), §3.5 (authorization covered fields).

## Design

**1. Series identity.** Create one series through the normal product path (series editor, 10.4.x) with the D1 values:

| Field | Value | Note |
|---|---|---|
| Topic | `ghost` | D1; `true_crime` would force owner review on every episode (K2) and is not the flagship topic |
| Language | `vi` | D1 |
| Aspect | `landscape` | D1; the 02 length band is keyed by `length_tier × language` (02.8.2 §3.1 check 11) |
| Length tier | `standard` | D1: 5–8 min band; upgrade to `long` only after one week of cost/render data (K1 measurement) |
| Voice | winner of the 3-candidate test (below) | from the 04 catalog |
| Style | winner of the 3-candidate test (below) | from the 03/04 catalogs; drives `ScenePromptBuilder` (03 §5.2) |

**2. The 3-candidate test (D1).** Generate or render three short candidate outputs that differ **only** in voice and style, listen/watch them in one sitting, and score each 1–5 on: intelligibility on a phone speaker · fit with the ghost-story tone · pace/atmosphere · how well it survives the intended 5–8 min length. Pick the winner per dimension; write the scores and the winner into `setup.md`. One candidate pair may be re-run once if a candidate fails technically (artifact), never to fish for a favourite.

**3. Autopilot settings (D1 + K6).** Written through `PUT /series/{id}/autopilot` with the `ETag` from the preceding `GET` (428 `if_match_required` otherwise). Payload to apply:

```jsonc
{
  "schema_version": 1,
  "cadence": { "days_of_week": ["mon", "thu", "sat"], "publish_time": "19:00", "time_zone": "Asia/Ho_Chi_Minh" },
  "daily_cap": 1,                            // D1/K2 default
  "buffer_days": 2,
  "privacy": "public",                       // effective only when AuditStatus = approved (K8)
  "veto_window_hours": 12,                   // D1; >= YouTubeOptions.MinVetoWindowHours = 2 (06 D11)
  "pre_audit_mode": "keep_cadence_private",  // D1 until the audit is approved
  "gate_thresholds_ref": "default",
  "tone": "<from the 3-candidate test; ≤ 500 chars>",
  "banned_themes": ["children in danger", "real named people"],
  "render_lead_minutes": null,               // null → Autopilot:RenderEstimate:Minutes
  "story_lead_minutes": null                 // null → Autopilot:StoryEstimate:Minutes
}
```

Notes that must be respected while filling this in: `tone` and `banned_themes` are **not** part of the authorization text, so editing them later does not revoke (02.8.3 §3.1); `days_of_week` must be exactly 3 entries for the D1 cadence; the time zone string must resolve via `TimeZoneInfo.FindSystemTimeZoneById` — a typo is 400 `autopilot_settings_invalid` with `errors["cadence.time_zone"]`, never a silent UTC fallback.

**4. Authorization.** Sequence, all inside the re-auth freshness window: `GET /series/{id}/autopilot` → read `AuthorizationText {textVersion, text, textHash}` and confirm the rendered text names the right series, topic label, channel title, cadence, cap, privacy label and veto window → accept via `POST /series/{id}/autopilot/authorization` (201 `{version, acceptedAt}`; re-auth + legal acceptance) → re-GET and confirm `RequiredAuthorization = false` and `Authorization.Version/TextHash` match what `setup.md` records. Two different values must not be conflated: the **series authorization** carries `version` + `textHash` (the text the owner accepted, per cadence/cap/privacy/veto window), while the **publication consent** written later records `consent_text_version` — which is `YouTubeOptions.ConsentTextVersion` (`pc.v1`, the consent-dialog version, 06.2.2-T3/06.2.1-T1) plus `consent_source = autopilot` and `autopilot_authorization_id` (06.2.2-T3:183, 06.2.2 plan §F-10). `setup.md` records the authorization's `version`/`textHash` **and** the `ConsentTextVersion` in force, and the weekly routine checks that (a) the authorization in force is still the accepted one and (b) each autopilot publication's `autopilot_authorization_id` points at it.

**5. Audit snapshot.** Record in `setup.md`: `YouTube:AuditStatus` as observed (`pending` expected until 13.4.2-T1) ⚠️ (env-owned, `IOptionsMonitor`), the resulting upload behaviour (K8: `private`, no `publishAt`, `platform_payload.preAudit = true`), and the `pre_audit_mode` currently set. At the moment the audit flips to `approved`, the rendered authorization text changes (the pre-audit note disappears) so the covered-field/text check **revokes** the authorization (`revoked_reason = text_changed`, 02.8.3-T2:123/170) — the owner must re-accept (re-auth + legal) before the first public slot, and this section gets a dated one-line append recording the flip and the re-acceptance before `privacy` takes effect.

**6. Gates state.** Record `AutopilotDto.GatesDryRun` and `GatesDryRunRemaining` (02.8.2-T3). While dry run is on, no fiction episode is auto-approved (02.8.2 §11.2: the phase is trusted only after `DryRunMaxEpisodes = 10` evaluated episodes), so every slot waits for the owner. `setup.md` states this and the calendar's first weeks are annotated accordingly — the 12 **public** weeks of K1 must not be claimed while dry run or the pre-audit private mode is still in effect (F4).

**7. Calendar.** `docs/ops/flagship/calendar.md`, one row per week for 12 weeks (D1), from the series' start week:

| Week | Dates (Mon–Sun) | Planned slots (dates at the cadence) | Theme notes | Risk notes |
|---|---|---|---|---|

- **Week** 1..12; **Planned slots** = the 3 dates the cadence produces (derived from `AutopilotDto.NextSlots` for the first weeks and from the cadence arithmetic for the rest — same 3 weekdays, one slot per day because `daily_cap = 1`).
- **Theme notes**: the intended angle for the week (e.g. "urban legend", "family heirloom", "hospital night shift"), written as *notes*, never as an instruction that would bypass the idea planner (02.8.1 owns idea generation and the variety guard).
- **Risk notes**: what could make the week fail (a true-crime signal in a source → owner review; a `gate_failed_streak` pause; holiday/scheduling conflicts; quota).
- The calendar is a plan, not a contract: a week's actual output is recorded in that week's `weekly/YYYY-WW.md` and counted in `kpi.md`.

## Steps

1. Confirm the entry gate: `docs/ops/gate-2.md` exists and is signed (date + signer line recorded); `GET /channels` shows one `active` YouTube connection; note its channel title.
2. Create the series with the D1 identity fields (topic/language/aspect/tier) and title it so the channel and the series names are distinguishable in the run log.
3. Run the 3-candidate test (§Design 2) on the M0 outputs; record the four scores per candidate and the two winners.
4. Open the Autopilot tab, `GET` the settings, and note the current `ETag`; apply the §Design 3 payload with `PUT` + `If-Match`; re-`GET` and diff the echo against the payload key by key.
5. Read the rendered authorization; check the eight placeholders render with the values just written (series title, topic label, channel title, days, time, zone, cap, privacy, veto hours) plus `{{pre_audit_note}}` while the audit is pending.
6. Complete the acceptance: `POST …/authorization` after re-auth; re-`GET`; verify `RequiredAuthorization = false` and record `version`, `textVersion`, `textHash`, `acceptedAt`.
7. Write `docs/ops/flagship/setup.md`: series id/title/identity, candidate-test table, the applied settings payload (verbatim), the authorization record, the audit snapshot, the gates-dry-run state, and the enable/disable order (rehearsal → audit approved → public).
8. Write `docs/ops/flagship/calendar.md` with the 12 rows and the pre-filled risk notes.
9. Do **not** enable public autopilot here: leave the series in the state §11.3 of the folder plan describes (rehearsal with `pre_audit_mode = keep_cadence_private`), or enabled-with-private-output if the first rehearsal week is being run immediately by 08.4.2-T1.
10. Hand over: `/Volumes/Project/NightTalesStudio` untouched outside `docs/ops/flagship/`; nothing under `src/`, `tests/`, `infra/` changes.

## Tests

BA dry runs and document checks (no xunit/Testcontainers — 13.4.2-T1 §9 precedent):

1. **V1 settings accepted** — paste the recorded payload into the Autopilot tab `PUT` on staging: expect 200 + new `ETag`, no 400 `autopilot_settings_invalid`; then a deliberate negative run with `"time_zone": "Asia/Ho_Chi_Minh "` (trailing space) → 400 with `errors["cadence.time_zone"]`, proving the recorded value is what the validator judged.
2. **V2 authorization round-trip** — `GET` → accept (re-auth) → `GET`: `RequiredAuthorization = false` and the hashes equal `setup.md`; then `DELETE …/authorization` and re-`GET` → `RequiredAuthorization = true` (proves the recorded version is the live one), then accept again and leave the series authorized.
3. **V8 calendar vs planner** — compare the calendar's first three planned weeks with `AutopilotDto.NextSlots` (three slots returned before the first tick): same weekdays, `19:00` local, `StartAt` earlier than `SlotAt`, no day with two slots.
4. **V3 pre-audit rehearsal (needs the connected channel)** — while the audit is `pending`, let one slot run and confirm the publication ends `published` with `privacy = private` (or a pause with the recorded reason); record which of the two happened in `setup.md` §audit snapshot.
5. **Negative, cadence/authorization coupling** — change `publish_time` to `19:30` (a covered field) and re-`GET`: the product must report the authorization as required again (K7); restore `19:00` and re-accept, restoring the recorded state.
6. **Document scan** — the secret/forbidden-string grep of the acceptance checks, run twice (before and after the acceptance `POST`), plus a read-through that `setup.md` contains no reporter e-mail, no video id that is not the owner's own, and no Studio URL with a query string.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| `docs/ops/gate-2.md` missing or unsigned | Stop; do not create the series. The entry gate is the whole point of K3/F4. Message the 08.5.1-T1 owner, record the blocker in the weekly file's "decisions" section for the week it cleared. |
| No `active` channel connection | 06.1.2-T2's connect flow first (re-auth + legal gate); record the connection `status` and `last_verified_at` in `setup.md`. |
| `PUT` answers 428 `if_match_required` | Re-`GET` for a fresh `ETag`; never retry with a stale one. |
| `PUT` answers 400 `autopilot_settings_invalid` | Read `errors[...]`; fix the offending key (the time zone, the day list or a range); never relax the value to force acceptance. |
| 409 `autopilot_topic_locked` | The topic cannot change after the authorization/consent path is live (02.8.3-D8); keep `ghost` and record why in `setup.md`. |
| Re-auth stale (401 `reauth_required`) | Re-enter the password/TOTP and repeat the accept inside the 5-minute window; do not hand-write an authorization note instead. |
| The rendered authorization text does not match the settings (e.g. still shows the old veto window) | Re-`GET`; the text is rendered from the current settings (02.8.3-T2 §Routes) — a mismatch means the `PUT` did not land; fix the settings before accepting. |
| Audit still `pending` at the time the phase is meant to go public | That is expected until 13.4.2-T1; keep `keep_cadence_private`, keep rehearsing, and do **not** count those weeks against the 12 (F4). |
| Audit flips to `approved` while the phase is armed | Expected side effect: the authorization is revoked (`text_changed`) because the pre-audit note leaves the rendered text — re-accept (re-auth + legal) and only then expect public uploads; record the flip date in `setup.md` §audit snapshot (02.8.3-T2:170). |
| Audit comes back `rejected` | Record it in `setup.md`; the phase cannot go public at all (K8) — escalate as a Gate 2 input rather than a setup problem. |
| Gates still in dry run | Every fiction episode waits for the owner (02.8.2 §11.2). Record it, expect higher touch time in the first weeks, and let 02.8.2-T3's calibration finish before claiming the 12-week clock. |
| A candidate in the 3-candidate test renders with an artifact | Re-run that candidate once at the same settings; if it fails again, drop it and pick from the remaining two — never compare outputs produced with different parameters. |
| The owner wants a different cadence/tier after week 1 | Legitimate: apply it through the product (a covered-field change revokes → re-accept, K7) and update `calendar.md` + `setup.md` as a dated amendment; only the D1 reasoning ($ cost/render data) justifies the `long` upgrade. |

## Notes

- Everything in this task is product configuration plus two documents; the validation ranges live in 02.8.3-T2, not here. If a value is rejected, the product is right and the document is wrong.
- `privacy: "public"` is written now but is **ineffective** until `YouTube:AuditStatus = approved` (K8/YR2): a pre-audit row is created private and a `PATCH` to non-private on it is refused with 409 `publication_privacy_locked` (YR20). Do not "fix" that by editing the row.
- The anchor 08.4.2-T1 checks weekly is the pair (authorization `version`/`textHash` in force, `consent_text_version = YouTubeOptions.ConsentTextVersion` on each autopilot publication) — the series authorization and the consent-dialog version are different values by design (06.2.2-T3:183); a publication whose `autopilot_authorization_id` is not the accepted authorization is the finding, not a changed `consent_text_version`.
- [INFERENCE] the exact series-editor field labels for `length_tier`/aspect (10.4.x owns the copy); the values written are the D1 ones regardless of the label.
- [OPEN] the 3-candidate test's absolute scores are unverifiable until the M0 outputs exist; the task records the scores as measured, not against a target, and the choice is the owner's.
