# 08.4.4-T1 — Takedown runbook: flagged/reported autopilot video → pause, private/remove in Studio ≤ 24 h, record cause

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 08.4.4 | XS (0.25) | BA/Ops | 02.8.2-T2, 02.8.3-T4 (soft) | — | P · Channel phase |

## Goal

Write and rehearse once the one P runbook: what the owner does when an autopilot video is flagged, reported or struck — pause the series, get the video out of public view within **24 h**, record the cause, then decide whether to resume. The artefact is `docs/ops/flagship/takedown.md`.

Deliverable is a runbook plus one recorded rehearsal: no code, no new route, no alert, no endpoint. The pause mechanics it invokes are 02.8.3-T4's; the report path is 13.3.4's (`ReportCreated` → `content_reported`).

## Inputs

- 02.8.3-T4 — the pause path: `POST /series/{id}/autopilot/pause` (`owner_paused`), the automatic `content_reported` pause from the report handler, the alert e-mail listing already-scheduled videos, and the fact that pausing stops **new runs only** — publications already created are untouched.
- 13.3.4 / `reports` (00 §6) — the report path and its columns (`reporter_email, target_type, target_id, reason, status, resolved_at`); the runbook uses `target_id` + `reason` only (privacy rule, K11).
- 02.8.2-T2 — the real-world/framing detector and the moderation stage `autopilot_gate`; a takedown that points at content the gate let through is evidence for the gate's thresholds (a Gate 2 input), not just an incident.
- 11.6.2-T1 alert rules (K9) — rule 12 (any `autopilot_pause_total` increment → **page**, which is how the owner hears about `content_reported`), rule 15 (render queued too long), rule 16 (`platform_incident_open`).
- `GET /series/{id}/autopilot/runs` and the Autopilot tab — the run log to find other in-flight publications whose slots are still ahead.
- YouTube Studio — the only place a video's privacy/removal can be changed (the API path is not used for takedowns).
- `../README.md` D5 (only this runbook is in P), K9/K10/K11, F6; `plan.md` §4 UC-4.

## Design

**1. Triggers → detection sources.** The runbook names the four ways a takedown starts, each with its timestamp source (the clock for the 24 h SLA is the **earliest** of them):

| Trigger | Detection | Timestamp used |
|---|---|---|
| YouTube Studio policy notice (community-guidelines strike, misleading/synthetic-content action, age restriction) | Studio notification + e-mail | the notice's timestamp |
| Copyright claim / Content ID claim | Studio notification + e-mail | the notice's timestamp |
| Viewer report that reaches the platform | Studio "reports" area or a platform e-mail | the notice's timestamp |
| Product-side report | `reports` row (13.3.4) → series paused with `content_reported` (K10/K11) → alert rule 12 page | `reports` row's arrival (as surfaced by the pause + alert) |
| Owner decides it should come down (no external trigger) | the weekly sample audit (08.4.2-T1 §2) or a spot check | when the owner noticed; recorded as `owner_decision` |

A serious strike is also a **monetization/audit event**: it is recorded in the weekly file and, if the video was public, quoted in the next Gate 2 checkpoint (K4 context).

**2. The runbook `docs/ops/flagship/takedown.md`** — sections in this order, written as a checklist an operator can execute without reading the plan:

```
# Flagship takedown runbook
Scope: one autopilot video on the owner's channel. SLA: out of public view ≤ 24 h from detection.
Preconditions: runbook rehearsed once (see the rehearsal record at the bottom); the channel is connected
and `active`; the owner can sign in to YouTube Studio.

### 1. Detect and timestamp
<the trigger table above; record detected_at and its source>

### 2. Contain the series (≤ 15 min)
1. Open the series' Autopilot tab; read the state.
   - If already paused with reason `content_reported` (or another reason): keep it paused, note the reason code.
   - Else: Pause now. If the product pause is not available for any reason, stop the source of new work
     (see §5 fail-safes) and record why.
2. Record the pause reason code verbatim and the pause timestamp.

### 3. Take the video out of public view (≤ 24 h from detected_at — target ≤ 2 h)
1. In YouTube Studio, set the video to **private** first (reversible), then decide removal.
2. Remove/delete it only if the notice requires removal or the content is clearly unsafe.
3. Record action_at, the action taken (private / removed / age-restricted by YouTube) and the Studio URL in
   the event record below.

### 4. Handle other in-flight publications
Pausing stops new runs and blocks `awaiting_consent` rows — `AutopilotConsentJob` skips a paused series (02 CR to 06.2.2-T3) — but it does **not** touch rows already consented (02.8.3-T4). From the run log:
1. List every publication of the series whose slot is still ahead, with its `status`.
2. Act by state, not by one blanket rule:
   - `awaiting_consent` — cannot proceed while paused: it holds until you resume (or cancel it if you will not resume).
   - `scheduled` — **still uploads**; cancel it (veto/cancel link or publication cancel) or let it publish. Decide each.
   - `uploading` / `processing` / `published` — the product refuses to cancel these (`Publication.Cancel` accepts `awaiting_consent|scheduled` only, 06.2.1-T1:74 → 409 `publication_invalid_state`) — handle them in **Studio** (§3).
   - `failed` — nothing to do; note the `error_code`.
3. Check the alert e-mail's list of already-scheduled videos as a cross-check.

### 5. Fail-safes if the product pause is unavailable
1. For a publication in `awaiting_consent`/`scheduled`: cancel it through its veto/cancel link (the `publication_cancel` token) — that alone contains the immediate risk.
2. If the planner keeps creating new publications, disable autopilot in the series settings. **This revokes the current authorization** (`enabled = false` → `revoked_reason = disabled` + audit `autopilot.disabled`, 02.8.3-T2:87), so the owner must re-accept (re-auth + legal) before autopilot resumes; record that consequence, and the reason the pause route failed.
3. For an `uploading`/`processing`/`published` row: Studio only (§3) — the product answers 409 `publication_invalid_state`.
4. The DB is never edited by hand — escalate as an incident.

### 6. Record the cause
Event record (one block per event; keep them in this file so the whole history is one artefact):
| Event id | detected_at | source | series/publication/episode | reason (report reason / policy / claim) | action | action_at | elapsed | was it public? | views/impressions | decision (resume / adjust / stop) | decision_at |
Plus: the target `reports` row id when a report is the trigger, never the reporter's e-mail (K11);
for a strike/claim, the notice type and whether an appeal window exists.

### 7. Decide
- Resume only after the cause is clear and the settings/threshold that allowed it are revisited
  (tone, banned_themes, gate thresholds via 02.8.2-T3) — never resume "to see if it happens again".
- Resume re-checks the triggers (02.8.3-T4), so a still-open cause keeps the series paused; record what
  cleared it.
- A confirmed policy strike on a public video → record it as a Gate 2 input and consider running the rest
  of the phase in `private`/pre-audit mode until the checkpoint.

### 8. Rehearsal record
| date | exercised path | detected_at | action_at | elapsed | what surprised us |
```

**3. The 24 h SLA.** Measured from `detected_at` (earliest trigger timestamp) to `action_at` (the moment the video stopped being publicly visible). Target inside the SLA: ≤ 2 h when the owner is at a keyboard, because a strike is not a slow-moving event. The rehearsal fills one block of §8 so the flow (sign in → private → record) is proven end to end before public autopilot starts (`../README.md` §7 gate).

**4. Boundaries.** The runbook never edits the DB, never uses the YouTube API for privacy changes, never copies reporter personal data into the ops docs (K11), never deletes an episode to make a problem disappear (an episode also feeds the KPI sheet's cost/quality columns — the record is the artefact), and never resumes without naming what changed.

## Steps

1. Write `docs/ops/flagship/takedown.md` with §1–§8 above and the empty (§8) rehearsal table.
2. Verify each mechanism named in the runbook exists and behaves as described, on staging: `POST /series/{id}/autopilot/pause` pauses and stops the planner; the run log distinguishes publications still in flight; a veto/cancel link can cancel one; disabling autopilot in the settings stops new publications; the pause e-mail lists already-scheduled videos.
3. Rehearse once end to end on **staging** with a deliberately chosen publication (the rehearsal of the folder plan's V7): pause → set the staging video private in Studio → fill the event record → resume and confirm the trigger re-check.
4. Time the rehearsal from `detected_at` to `action_at` and write the elapsed time into §8; an elapsed time above 2 h on staging means the runbook's steps are too coarse — tighten §3 to concrete clicks before the phase starts.
5. Rehearse the **other-publications** step (§4) once: with one `awaiting_consent` and one `scheduled` publication in flight, pause and confirm the first holds (consent job skips the paused series) while the second still uploads unless cancelled — cancel it, record both decisions, then resume.
6. Add a one-line sign-off to `docs/ops/flagship/setup.md` (08.4.1-T1's file) recording that the runbook exists and was rehearsed (the entry gate requires it).
7. Keep the rehearsal's staging evidence out of the repository (no Studio URLs with tokens, no thumbnails); the event record is text only.

## Tests

BA rehearsal (no xunit/`PostgresFixture`):

1. **V7 runbook rehearsal** — the end-to-end rehearsal of §Design 3 on a staging publication; the recorded elapsed time is the proof; passes only with a filled §8 row.
2. **Pause behaviour proof** — on staging, pause via the product and confirm no new `autopilot_runs` row is created for the following slots (the planner skips paused series) while an already-created publication still proceeds (unchanged) — the exact asymmetry §4 exists for.
3. **In-flight handling rehearsal** — with two publications in flight, cancel one and let the other publish; both decisions recorded in the rehearsal event record.
4. **Resume re-check proof** — resume while a cause is still open and confirm the product refuses/keeps the pause (02.8.3-T4's resume re-checks triggers), then clear the cause and resume successfully.
5. **Fail-safe walkthrough (table-top)** — with the pause route artificially unavailable (e.g. the operator cannot reach the Autopilot tab on the rehearsal device), follow §5's fallback on staging and confirm the listed alternative actually stops new publications.
6. **Record completeness check** — a second reader fills a dummy event record from the rehearsal's notes alone; every column must be fillable without asking the operator what happened.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| The pause route is unavailable (product bug, session problem) | §5's fallback: cancel the affected publication, then disable autopilot in the series settings, then escalate; never edit the DB by hand (`takedown.md` §5). |
| The series was **not** paused automatically (report handled outside 13.3.4) | Pause manually with `owner_paused` and record that the automatic path did not fire — that is a finding for 13.3.4/02.8.3-T4, reported through the weekly file. |
| Other publications are in flight | §4: a `scheduled` row still uploads while the series is paused; an `awaiting_consent` row is blocked (the consent job skips paused series, 02 CR to 06.2.2-T3); `uploading`/`processing`/`published` can no longer be cancelled through the product (06.2.1-T1:74) and need Studio. Decide each row by its state, using the alert e-mail's scheduled-video list as the cross-check. |
| A YouTube strike on a public video | Record it as a Gate 2 input; the phase may continue only after the settings that allowed the content have been revisited, and consider pre-audit `private` mode until the next checkpoint. |
| Copyright claim rather than a policy strike | Same containment; the record notes claim vs strike, the claimant class and whether an appeal window exists — the decision to appeal is a business decision recorded in §7, not taken inside the routine. |
| The video is already very public (thousands of views) | `private` still satisfies the SLA; removal is a judgement recorded with the reason. Do not let view count delay containment. |
| The takedown is the owner's own decision (no external trigger) | Same runbook, source `owner_decision`; if the cause is content quality, the follow-through is a gate-threshold/tone change (02.8.2-T3), not a manual re-edit of that episode. |
| The trigger is a platform OAuth incident, not content | Alert rule 16, not this runbook: no video is at risk; the platform incidents path (06.2.3-T3, `platform_incident_open`) applies. The runbook says so explicitly to avoid misusing the flow. |
| A deletion request from a viewer (13.3.1) targets the episode | That path is 13.3.1's (deletion windows, `data_deletion_requests`); the runbook records the takedown action and hands the deletion duty over rather than mixing the two. |
| The rehearsal cannot use a real Studio notice | Rehearse the containment and record steps with the owner's own staging video and an `owner_decision` source; the §8 row names it as a rehearsal, not as a real event. |

## Notes

- XS (0.25) covers writing the runbook and one rehearsal; the runbook is deliberately short — it is executed under pressure, and a long document does not get read during a strike.
- The runbook is the **only** P runbook (D5); the 08.2 runbooks are S. When the S slice lands, this file stays where it is and the other runbooks go to `docs/runbooks/`.
- The event record is the takedown history for the whole Channel phase: it is what a Gate 2 checkpoint reads to decide whether the channel is safe to keep automating.
- [INFERENCE] the exact Studio affordances (where the notification appears, the "reports" area) are the current console flow; the runbook states the *action* (set private, then remove) rather than a fragile click path, so a console redesign does not invalidate it.
- [OPEN] whether the platform surfaces a viewer report to the owner at all before it becomes a strike; until that is known, a strike arriving without a prior notice is treated as the normal case (detection at the notice).
