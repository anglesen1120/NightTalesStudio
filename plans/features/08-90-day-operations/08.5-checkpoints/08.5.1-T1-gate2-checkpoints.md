## Design

**The single repo artifact (text only):**

```
docs/ops/gate-2.md
  §0 Header            owner sign-off (name + date) · phase start rule · revision counter · links to the inputs
  §1 Gate 2 criteria   one row per criterion: value · measurement source · owner-accepted? · revision
  §2 Checkpoints       week-4 / week-8 / week-12 entries: the six questions, the outcome, the settings diff,
                       the per-criterion verdict table at week 12, the Gate 2 recommendation
  §3 Fields            field → source table (file, column/route), so no criterion is unmeasurable
  §4 Clock             audit-approval precondition · "counted week" definition · late/paused handling
  §5 Revisions         append-only history of criteria changes after sign-off
```

**§1 schema** — `| # | Criterion | Value (owner-accepted) | Measured how (source) | Where recorded | Verdict (week 12) |`. Rows, with the **proposed** defaults (all marked "proposed — owner to accept or change"; K3 forbids assuming them):
- **C1 cost per episode**: owner sets a ceiling; proposed derivation = mean measured cost/episode of the first 4 public weeks × 1.25, in USD and VND. Measured from `usage_records` (`cost_usd`, `gpu_seconds`, `operation`, `estimated`, `price_version`) via `queries.sql` (D3). Plan 12 is **deleted** (DEC 10.14) and it never carried a P target number — its cost model was measurement-based and its $0.708 worked example was illustrative ⚠️; the former ≥ 60 % margin (00 §3) was a pricing rule and is **gone** with it (no revenue exists by design). ⚠️
- **C2 owner touch time ≤ 20 min/episode** — from `weekly/YYYY-WW.md` minutes ÷ that week's episodes (D2/D3).
- **C3 ≥ 90 % of planned slots published without manual rescue** — `autopilot_runs.outcome` + `publications.status` ÷ `calendar.md` planned slots.
- **C4 zero YouTube policy strikes, no channel restriction** — Studio (manual) + platform incident rows; a stop-signal, not a tunable.
- **C5 sampled-output quality**: the weekly sampled video's 02-rubric score ≥ the 02 threshold in force, no gate-fail streak — `weekly/*.md` scores + `autopilot_runs.gate_results`.
- **C6 channel trend recorded, not pass/fail**: subscribers, watch hours, views, CTR, average view duration + distance to K4's YPP thresholds — Studio export into `kpi.md`; YPP eligibility for an autopilot channel unverified ⚠️.
- **C7 automation health**: render success ≥ 95 %, no unresolved platform incident, no quota-exhausted skipped slot — mirrors 11.6.2-T1 rules 5/10/12 (`:34-50`) so a checkpoint never asserts what the alerts would have paged.

**§2 checkpoint questions (identical at weeks 4/8/12, the answer set narrowing by week):**
1. Did the phase run as planned? (counted weeks, slots published/missed vs `calendar.md`)
2. What did it cost per episode and how does that compare with the owner's C1 ceiling and the first-4-week mean?
3. How much of my time did each episode take, and which task ate it? (from `weekly/*.md` categories: veto review, edits, true-crime approvals, incidents)
4. How many times did the automation need rescue, and why? (pauses by `pause_reason`, gate failures from `gate_results`)
5. What does the channel show? (Studio trend; YPP distance recorded, not required)
6. **Decision: continue / adjust settings (which, exactly) / stop** — and, at week 12 only, the per-criterion verdict table against §1 and the **Gate 2 recommendation** (continue / adjust settings with named changes / stop).
Any "adjust" that touches a covered field (`topic`, `default_channel_id`, `cadence.*`, `daily_cap`, `privacy`, `veto_window_hours`, `pre_audit_mode` — `10.4-series-autopilot/plan.md:59`) is recorded together with the resulting authorization re-accept obligation; the document never instructs a route call, it records the outcome and the required next act.

**§4 clock rule.** The 12 counted weeks start only when `YouTube:AuditStatus = approved` (`../README.md:11` K7; `plans/00-overview.md:95`) **and** the first public upload lands; a **counted week** = ≥ 90 % of that week's planned slots published with no open pause at week end; partial/paused weeks are skipped (the counter advances only on a counted week), and private pre-audit weeks are a rehearsal, never counted (F4).

**Boundaries.** Do not create or edit `docs/ops/flagship/*` (08.4.1-T1…08.4.4-T1 own calendar, weekly log, KPI sheet, `queries.sql`, runbook); do not add alerts/metrics (D5); do not touch 08 §5.2 thresholds (F6/D5 — 11.6.2-T1's D17 values are authoritative); do not flip `AuditStatus`; do not define the former SaaS criteria (that was 08.5.1-T2, deleted by DEC 10.14); do not write `docs/compliance-calendar.md` or any 13 file. This task writes exactly one file, plus its own notes.

**Ratio.** No runtime path; batching/streaming/N+1/DDL do not apply; the only SQL is 08.4.3-T1's read-only snippet run against existing tables and indexes (`usage_records`, `autopilot_runs`, `publications` PKs/tenant indexes). Tenant-404 / CSRF / idempotency / ETag / audit events are **not applicable** (no endpoint, no state change) — stated so a reviewer does not look for them. Idempotency here means: one signed document per phase; later criteria changes append a §5 revision instead of editing the signed row.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| The owner does not accept a proposed default | the row keeps the owner's value and §1 records it; the proposal history goes to §5 as `rev.1`. The document is signed with the owner's numbers, never the author's |
| C1 has no credible ceiling yet (fewer than 4 public weeks) | the criterion is written as a **formula** over the first 4 counted weeks (mean × 1.25, then converted at the top-up FX rate) and the concrete number is filled at the week-4 checkpoint as `rev.n` — the phase still starts, because the *rule* is signed, not a guessed number |
| The audit is never approved / is rejected | the clock never starts (§4); the document stays valid. The audit is a **precondition**, not a criterion — recorded as such; no channel-side action is taken here (that is 13.4.2-T1's and the owner's) |
| A week is paused (gate-fail streak, spend cap, incident, owner pause) | the week is not counted; the pause and its `pause_reason` go to §2's next entry; a pause caused by a covered-field settings change also carries the re-accept note (`10.4-series-autopilot/plan.md:59`) |
| `docs/ops/flagship/*` does not exist yet at drafting time | the document names the **source file and field** it will read (D2/D3 contracts) and marks the row `source pending`; the weekly routine cannot start before those files exist (08.4.2/08.4.3), so this does not block sign-off, only the first checkpoint |
| The owner wants to add a criterion mid-phase | append a §5 revision and a new §1 row with `effective from` — never rewrite history; the week-12 verdict table grows by one row |
| A measured value contradicts the weekly log (e.g. touch time differs) | the weekly log wins (it is the primary record, D2) and the discrepancy is noted in §2 — the checkpoint never silently re-derives a number |
| A criterion turns out unmeasurable in P (e.g. YPP eligibility for an autopilot channel ⚠️) | it is recorded as trend-only (`C6` style) with the reason — "not measurable" is an allowed verdict in the week-12 table |
| Someone proposes changing 08 §5.2 alert thresholds to match | refused: D5/F6 make 11.6.2-T1's D17 values authoritative; the note goes to 08.4.2-T1's weekly log instead (the S folder that would have owned it, 08.2, is deleted by DEC 10.14) |
| Rollback | none needed (a document). A wrong criterion is corrected by a §5 revision + owner initials; the signed baseline is preserved |
