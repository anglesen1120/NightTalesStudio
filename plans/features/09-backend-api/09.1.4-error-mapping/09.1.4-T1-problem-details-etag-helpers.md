## Goal

Any `ErrorOr` result maps to the right status and a uniform ProblemDetails body. Paid POSTs without a key and D9/D15 routes without `If-Match` are rejected at the endpoint.

## Inputs

- README D7, D14, D15, D17; 09 §5.4 (catalogue); 02 README D8 (02 codes), D9 (ETags); 02 CR-20.

Mapping rules:
- If any error has `Type == Validation` → 400 `validation_failed`, with `errors` grouped by `metadata["field"]`.
- Otherwise the first error's code → `ErrorCatalogue.Status`. An unknown code → 500 `internal_error`, and the error is logged as a bug.
- A 429 with `metadata["retryAfterSeconds"]` sets the `Retry-After` header.
- `ETag`: `ToCreatedResult` / `ToHttpResult` set the `ETag` header when the value implements `IHasETag { string ETag { get; } }`.

Filters:
- `RequireIdempotencyKey()`: the `Idempotency-Key` header must be present, 1–128 chars, printable ASCII `0x21–0x7E`. Otherwise 400 `idempotency_key_required`.
- `RequireIfMatch()`: the `If-Match` header must be present. Otherwise 428 `if_match_required`.
- Binder: `[FromHeader(Name = "If-Match")] string? ifMatch`, passed into the command.

Exceptions: `app.UseExceptionHandler` + `AddProblemDetails` customisation → 500 `internal_error`, with the `traceId` from `Activity.Current`.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Several non-validation errors | the first determines the status; all are listed under `errors` only if they are validation errors |
| A 202 body code returned as an error by mistake | `AcceptedBodyCodes` is excluded from `Status`; the unit test fails if a code appears in both |
| A client sends `If-Match: *` | not matched → 412 with the resource code [DECISION]; clients must send the exact ETag |

## Notes

- The 02 codes are catalogued here once (02 D8 is the source). Later plans add theirs.
- ⚠️ E4 → ✅ **verified 2026-09-29** against `dotnet/aspnetcore` `release/10.0`:
  - `AddProblemDetails(options => options.CustomizeProblemDetails = …)` is applied by `DefaultProblemDetailsWriter.WriteAsync`, **after** `ProblemDetailsDefaults.Apply` and after the writer adds `Extensions["traceId"] = Activity.Current?.Id ?? TraceIdentifier`; the body goes out as `application/problem+json`.
  - The parameterless `UseExceptionHandler()` (`ExceptionHandlerOptions.ExceptionHandler == null`) answers through `IProblemDetailsService.TryWriteAsync` with `ProblemDetails { Status = 500 }`, and the middleware **throws at construction** when no `IProblemDetailsService` is registered — so `AddProblemDetails()` is mandatory next to it.
  - ASP.NET Core 10's `WebApplication` still inserts the developer exception page first when the environment is Development, and `WebApplicationFactory` forces Development. For a client that does not accept `text/html` the dev page itself routes through `IProblemDetailsService` (`DisplayExceptionContent` → `CreateProblemDetails` with `Detail` = the exception message and `Extensions["exception"]` = the stack). The customisation is therefore the **single** place that keeps the exception text out of every 5xx JSON body, in Development and in Production; both paths are asserted (`UnhandledException_Returns500_WithoutExceptionText`, `UnhandledException_InDevelopment_AlsoHidesTheExceptionText`).
- Implementation notes (09.1.4-T1):
  - The catalogue is **three disjoint frozen sets**, each `ErrorCodes` constant in exactly one: `Status` (118 rows, code → §5.4 HTTP status), `AcceptedBodyCodes` (3: `grant_requires_approval`, `owner_action_pending`, `objection_recorded`) and `NonHttpCodes` (40: job outcomes/job state, `render_worker_unavailable`, `provider_funds_exhausted`, the three 302-only TikTok redirect values and the 02 D8 job-outcome codes). `ErrorCodes` holds **161** constants: 09 §5.4 + D17 + 02 D8 + the concrete 12 §5.3 codes behind the §5.4 `payment_*` / `package_*` / `promo_*` wildcard row.
  - §5.4 rows that are **dual** ("202 body / 409"): `setting_change_pending` and `owner_action_disputed` stay in `Status` with 409 and are never in `AcceptedBodyCodes`, because the mapper only reads `Status` — a code in `AcceptedBodyCodes` can never be mapped, so an error carrying it would answer 500. Both readings of those rows still hold and the three sets stay disjoint.
  - `internal_error` is not a §5.4 row but the mapping rules require it; it is catalogued in `Status` → 500 so a handler may return it on purpose, and the unknown-code path writes the same code.
  - No §5.4 row is left unclassified. `story_not_in_review` (retired → `episode_invalid_state`) and `keyword_limit_exceeded` (withdrawn) deliberately have **no** constant.
  - `ErrorCatalogue` is `public` where the design sketch says `internal`: the invariant test lives in `NightTales.Api.IntegrationTests` and the solution has no `InternalsVisibleTo`.
  - `ProblemDetailsWriter` builds the body itself (`Results.Json`, `application/problem+json`, camelCase) instead of going through `IProblemDetailsService`, so a mapped error keeps exactly the documented members plus the allow-listed metadata (`retryAfterSeconds`, `field`, `limit`). In a validation body `field` is consumed by the `errors` group and not repeated at the top level; a validation error without a usable `field` is grouped under `""` rather than dropped.
  - `Program.cs` gained one `using`, `builder.Services.AddProblemDetails(ProblemDetailsWriter.ConfigureProblemDetails)` and `app.UseExceptionHandler()`; no existing line was reordered.
  - `ErrorCodes_AreSnakeCaseAndUnique` also asserts `PascalCase(value) == constant name`, so a row whose name and value disagree fails the build's own test instead of reaching a handler.
  - Negative proofs run: unknown code → 500 `internal_error` with no such code in the body (mutation: answer 400 and skip the log → red); `*` accepted (mutation) → red; a 129-char `Idempotency-Key` → 400 and the key is never echoed; a `sql` / `select * from users` metadata value never reaches the body.
