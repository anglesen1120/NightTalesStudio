## Goal

Any `ErrorOr` result maps to the right status and a uniform ProblemDetails body. Paid POSTs without a key and D9/D15 routes without `If-Match` are rejected at the endpoint.

## Inputs

- README D7, D14, D15, D17; 09 §5.4 (catalogue); 02 README D8 (02 codes), D9 (ETags); 02 CR-20.

Mapping rules:
- If any error has `Type == Validation` → 400 `validation_failed`, with `errors` grouped by `metadata["field"]`.
- Otherwise the first error's code → `ErrorCatalogue.Status`. An unknown code → 500 `internal_error`, and the error is logged as a bug.
- A 429 with `metadata["retryAfterSeconds"]` sets the `Retry-After` header.
- `ETag`: `ToCreatedResult` / `ToHttpResult` set the `ETag` header when the value implements `IHasETag { string ETag { get; } }`, and the delegate overloads of `ToHttpResult` / `ToNoContentResult` read it after commit instead (D15); a delegate that finds nothing sets no header rather than falling back to the pre-commit value.
- Only the allow-listed metadata keys (`field`, `retryAfterSeconds`, `limit`) reach the body, and only as bounded scalars (a string ≤ 128 chars, a finite number or a bool); a nested object, an array, a `DateTime`/`Guid` or an oversized string is dropped and logged at Debug.

Filters:
- `RequireIdempotencyKey()`: the `Idempotency-Key` header must be present, 1–128 chars, printable ASCII `0x21–0x7E`. Otherwise 400 `idempotency_key_required`.
- `RequireIfMatch()`: the `If-Match` header must be present. Otherwise 428 `if_match_required`.
- Binder: `[FromHeader(Name = "If-Match")] string? ifMatch`, passed into the command.

Exceptions: `app.UseExceptionHandler` + `AddProblemDetails` customisation → 500 `internal_error`, with the `traceId` from `Activity.Current`.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Several non-validation errors | the first determines the status; all are listed under `errors` only if they are validation errors |
| A validation error plus a non-validation one | the 400 `validation_failed` body takes its metadata from the first **validation** error only, and the dropped non-validation codes are logged at Warning — a suppressed error's `limit`/`field` must not leak into the validation body |
| A metadata value under an allow-listed key that is not a bounded scalar | dropped, logged at Debug: a nested object, an array, a `DateTime`/`Guid`, a string longer than `ProblemDetailsWriter.MaxMetadataStringLength` (128) or a non-finite float (which JSON cannot encode) |
| A 202 body code returned as an error by mistake | `AcceptedBodyCodes` is excluded from `Status`; the unit test fails if a code appears in both |
| A client sends `If-Match: *` | not matched → 412 with the resource code [DECISION]; clients must send the exact ETag |
| An `etag` delegate that finds nothing | on `ToHttpResult` / `ToNoContentResult` no `ETag` header is written, even when the value implements `IHasETag` (a pre-commit tag is stale and would poison the client's next `If-Match`); on `ToCreatedResult` the created value's own tag stands |
| A non-JSON `Accept` (e.g. `text/html`) on a 500 | the Production body is **empty** by design (the default problem writer only writes when the `Accept` allows `application/problem+json`), not a bug; verified live 2026-09-29: `text/html` and `application/xml` → 500 with no content type and `len=0`, while `application/json`, `application/problem+json`, `*/*` and no `Accept` at all → 500 `application/problem+json` with the `internal_error` body (200 bytes) |

## Notes

- The 02 codes are catalogued here once (02 D8 is the source). Later plans add theirs.
- ⚠️ E4 → ✅ **verified 2026-09-29** against `dotnet/aspnetcore` `release/10.0`:
  - `AddProblemDetails(options => options.CustomizeProblemDetails = …)` is applied by `DefaultProblemDetailsWriter.WriteAsync`, **after** `ProblemDetailsDefaults.Apply` and after the writer adds `Extensions["traceId"] = Activity.Current?.Id ?? TraceIdentifier`; the body goes out as `application/problem+json`.
  - The parameterless `UseExceptionHandler()` (`ExceptionHandlerOptions.ExceptionHandler == null`) answers through `IProblemDetailsService.TryWriteAsync` with `ProblemDetails { Status = 500 }`, and the middleware **throws at construction** when no `IProblemDetailsService` is registered — so `AddProblemDetails()` is mandatory next to it.
  - ASP.NET Core 10's `WebApplication` still inserts the developer exception page first when the environment is Development, and `WebApplicationFactory` forces Development. For a client that does not accept `text/html` the dev page itself routes through `IProblemDetailsService` (`DisplayExceptionContent` → `CreateProblemDetails` with `Detail` = the exception message and `Extensions["exception"]` = the stack). The customisation is therefore the **single** place that keeps the exception text out of every 5xx JSON body, in Development and in Production; both paths are asserted (`UnhandledException_Returns500_WithoutExceptionText`, `UnhandledException_InDevelopment_AlsoHidesTheExceptionText`).
- Implementation notes (09.1.4-T1):
  - The catalogue is **three disjoint frozen sets**, each `ErrorCodes` constant in exactly one: `Status` (119 rows, code → §5.4 HTTP status, including the CR-38 `unauthorized` row), `AcceptedBodyCodes` (3: `grant_requires_approval`, `owner_action_pending`, `objection_recorded`) and `NonHttpCodes` (40: job outcomes/job state, `render_worker_unavailable`, `provider_funds_exhausted`, the three 302-only TikTok redirect values and the 02 D8 job-outcome codes). `ErrorCodes` holds **162** constants: 09 §5.4 + D17 + 02 D8 + the concrete 12 §5.3 codes behind the §5.4 `payment_*` / `package_*` / `promo_*` wildcard row + `unauthorized` (09 CR-38).
  - §5.4 rows that are **dual** ("202 body / 409"): `setting_change_pending` and `owner_action_disputed` stay in `Status` with 409 and are never in `AcceptedBodyCodes`, because the mapper only reads `Status` — a code in `AcceptedBodyCodes` can never be mapped, so an error carrying it would answer 500. Both readings of those rows still hold and the three sets stay disjoint.
  - `internal_error` is not a §5.4 row but the mapping rules require it; it is catalogued in `Status` → 500 so a handler may return it on purpose, and the unknown-code path writes the same code.
  - No §5.4 row is left unclassified. `story_not_in_review` (retired → `episode_invalid_state`) and `keyword_limit_exceeded` (withdrawn) deliberately have **no** constant.
  - `ErrorCatalogue` is `public` where the design sketch says `internal`: the invariant test lives in `NightTales.Api.IntegrationTests` and the solution has no `InternalsVisibleTo`.
  - `ProblemDetailsWriter` builds the body itself (`Results.Json`, `application/problem+json`, camelCase) instead of going through `IProblemDetailsService`, so a mapped error keeps exactly the documented members plus the allow-listed metadata (`retryAfterSeconds`, `field`, `limit`). In a validation body `field` is consumed by the `errors` group and not repeated at the top level; a validation error without a usable `field` is grouped under `""` rather than dropped.
  - `Program.cs` gained one `using`, `builder.Services.AddProblemDetails(ProblemDetailsWriter.ConfigureProblemDetails)` and `app.UseExceptionHandler()`; no existing line was reordered.
  - `ErrorCodes_AreSnakeCaseAndUnique` also asserts `PascalCase(value) == constant name`, so a row whose name and value disagree fails the build's own test instead of reaching a handler.
  - Negative proofs run: unknown code → 500 `internal_error` with no such code in the body (mutation: answer 400 and skip the log → red); `*` accepted (mutation) → red; a 129-char `Idempotency-Key` → 400 and the key is never echoed; a `sql` / `select * from users` metadata value never reaches the body.
- Review fixes (2026-09-29, second pass on this task — the D15/CR-38/metadata-seam review findings):
  - **D15 delegate gap closed.** D15 names the post-commit ETag delegate of `ToCreatedResult` **and** `ToHttpResult`, but only `ToCreatedResult` had one, while 09.7.1-T1/09.7 plan §5 already call `ToHttpResult`'s delegate. Added `ToHttpResult(result, http, etag)` and `ToNoContentResult(result, http, etag)` (both `Func<T, CancellationToken, Task<string?>>`); the parameterless signatures are unchanged. On these two the delegate is **authoritative** — a delegate that yields nothing sets no header, even when the value implements `IHasETag`, because the value was built before the commit and its tag would poison the client's next `If-Match`. `ToCreatedResult` keeps the opposite rule (its fallback is pinned by `ToCreatedResult_FallsBackToTheValueETag`).
  - **`unauthorized` added (09 CR-38).** Two wave-1 sources require it and §5.4 has no plain-401 row: `09.1.3-T2`:72 (`!currentUser.IsAuthenticated` → `Error.Unauthorized(code: ErrorCodes.Unauthorized)`, 401) with step 4 listing the code among this wave's additions, and 09 §4 Epic 09.1 (`09-backend-api.md`:72) requiring `Unauthorized` → 401. `ErrorCodes` is now **162** constants, `Status` **119** rows (`unauthorized` → 401); the three sets stay disjoint and no existing status changed. The plan-table row itself is a change request — see README §4 **CR-38**.
  - **Validation-body metadata leak closed.** A 400 `validation_failed` takes its top-level allow-listed metadata from the first **validation** error only; the non-validation errors the response suppresses are logged at Warning (`problem_details.suppressed_non_validation`, codes + traceId), which also gives QA's "mixed list leaves no trace" observation a home.
  - **`field` seam closed.** The key is `ErrorMetadata.Field` in `Application/Common/Errors/ErrorMetadata.cs` (`Field`, `RetryAfterSeconds`, `Limit`), written by `ValidationBehavior` and read by the writer's allow-list; `ProblemDetailsWriter.FieldMetadataKey`/`RetryAfterMetadataKey` were removed in favour of the shared constants. `ValidationFieldSeamTests` runs the real behavior (hand-built context, no HTTP) into the real writer.
  - **Metadata values are bounded scalars.** An allow-listed key now accepts only a string of at most `ProblemDetailsWriter.MaxMetadataStringLength` (**128**) characters, a finite number or a bool; a nested object, an array, a `DateTime`/`Guid`, an oversized string, `null` and a non-finite float are dropped and logged at Debug (`problem_details.metadata_value_dropped`, key + shape only, never the value). The old behaviour copied the value verbatim, so a handler could leak a structured payload through `limit`, and a `NaN` would have thrown in the serializer.
  - **`retryAfterSeconds` is no longer silently dropped.** Present but unparseable → Warning (`problem_details.retry_after_unusable`); the QA tests that pin "no header" still pass.
  - **Invariant hardened.** `ErrorCodes_EveryPublicStaticFieldIsAConstCode` fails on any public static non-`const` (non-string) field not on the (currently empty) allow-list, and `ErrorCodes_HasNoNestedTypes` refuses nested holders — both were invisible to the two older rules, so a smuggled `static readonly string` or a nested `ErrorCodes` would have escaped the closed-set invariant. Mutation-proved: adding either turns exactly the new test red while the old two stay green.
  - **Cheap allocations removed.** An error with no allow-listed metadata returns `null` instead of an empty dictionary (JSON byte-identical; `Map_ProblemWithoutExtraMetadata_HasExactlyTheDocumentedMembers` pins the six members), and `GroupByField` returns its `Dictionary<string, List<string>>` directly instead of copying into a second dictionary (`ProblemBody.Errors` is typed for it).
  - **Mutation proofs of this pass:** ETag delegate made to fall back to the value's tag → `ToHttpResult_WithETagDelegateThatFindsNothing_IgnoresTheValueTag` and `ToNoContentResult_WithETagDelegateThatFindsNothing_IgnoresTheValueTag` red; `IsBoundedScalar` forced to accept everything → both metadata-value tests red; metadata source reverted to `errors[0]` → both validation-body tests red; the behavior writing `ErrorMetadata.Limit` instead of `.Field` → the seam test red; the retry-after warning removed → all four `Map_429RetryAfterUnusableValue_LogsAWarning` cases red.
