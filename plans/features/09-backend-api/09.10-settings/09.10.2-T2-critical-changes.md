# 09.10.2-T2 — Critical settings: time-locked changes, approve/cancel

## Goal

A validated change to `payment.*`, `youtube.*` or `tiktok.*` is never applied immediately: it is frozen as a pending `system_setting_changes` row, every owner gets their own cancel link, a second eligible owner can approve it at once, and otherwise a 24 h time-lock applies it — closing the "a stolen owner session repoints the payment provider" attack (D7).

## Design

Implements §C3 **D7**.

```csharp
public sealed record SubmitCriticalChangeCommand(string Integration,
    IReadOnlyDictionary<string, JsonNode?> Values, IReadOnlyDictionary<string, SecretString> Secrets,
    string RequestedBy, string? Reason) : ICommand<ErrorOr<SettingChangeDto>>;

[Audited("settings.change_pending", Category.Support, Visibility.Internal)]
public sealed class SubmitCriticalChangeCommandHandler(ISystemSettingChangeRepository repo,
    ISettingsEncryptor encryptor, IEmailSender emailSender, IOwnerDirectory owners,
    IOutboxWriter outbox, TimeProvider clock)
{
    public async Task<ErrorOr<SettingChangeDto>> Handle(SubmitCriticalChangeCommand cmd, CancellationToken ct)
    {
        // partial unique index ix_system_setting_changes_pending (W3 CR-1f) enforces "one pending per integration";
        // an INSERT that violates it maps 23505 -> Error.Conflict("setting_change_pending")
        var payload = encryptor.Protect("change", cmd.Integration, /* whole payload as SecretString(json) */ ..., nodeId: null);
        var change = SystemSettingChange.Create(cmd.Integration, cmd.RequestedBy, cmd.Reason,
            payloadCiphertext: payload, hints: HintsFor(cmd.Values, cmd.Secrets), requestedAt: clock.GetUtcNow());
        var id = await repo.InsertPendingAsync(change, ct);   // throws on 23505 -> mapped above
        foreach (var owner in await owners.ActiveOwnersAsync(ct))   // approval_cancel: queued here, minted at send time by 09.10.8-T1 (09 W3 CR-23)
            await emailSender.QueueAsync(new EmailMessage(owner.Id, "approval_cancel", owner.UiLocale,
                new Dictionary<string, string> { ["displayName"] = owner.DisplayName, ["requestKind"] = "setting_change",
                    ["reason"] = cmd.Reason ?? "", ["deadline"] = change.ApplyAfter.ToString("O"), ["requestId"] = id.ToString() }), ct);
        await outbox.EnqueueAsync(new EmailRequested("setting_change_pending", /* per-recipient params, §C3.5 — plain, un-tokenised cancelUrl */), ct);
        return change.ToDto();
    }
}
```

`SystemSettingChange.ApplyAfter = requestedAt + SettingsOptions.ChangeTimeLock` (24 h). Approve/cancel/apply share one **lock order** with 09.10.4-T2's owner-action apply: `change row → (no owner rows needed here, unlike 09.10.4) → target setting rows ordered by (integration, key)`, `SET LOCAL lock_timeout = 3s`.

```csharp
[Audited("settings.change_approved", Category.Support, Visibility.Internal)]
public sealed class ApproveSettingChangeCommandHandler(...)
{
    public async Task<ErrorOr<SettingChangeDto>> Handle(ApproveSettingChangeCommand cmd, CancellationToken ct)
    {
        var change = await repo.LoadForUpdateAsync(cmd.Id, ct);           // FOR UPDATE, WHERE status = 'pending'
        if (change is null) return Error.NotFound();
        if (change.Status != "pending") return Error.Conflict("setting_change_applied_or_cancelled");  // idempotent no-op
        if (cmd.ApprovedBy == change.RequestedBy) return Error.Validation("owner_not_eligible");  // a requester never approves their own change (D7, 09 W3 CR-22)
        var approverEligible = await owners.IsEligibleApproverAsync(cmd.ApprovedBy, minAgeDays: 30, ct);
        if (!approverEligible) return Error.Validation("owner_not_eligible");  // caller retries with a different owner
        ApplyPayload(change);   // decrypt, write system_settings + versions, in the same transaction
        change.MarkApplied(cmd.ApprovedBy, clock.GetUtcNow());
        return change.ToDto();
    }
}
```

`SettingChangeApplyJob` (owned here per §C3.3 S5) is the 1-minute recurring sweep: `WHERE status = 'pending' AND apply_after <= now() ORDER BY apply_after LIMIT 50 FOR UPDATE SKIP LOCKED`, one `ISender` dispatch per id through an internal `ApplyDueSettingChangeCommand` (re-checks env-lock — a change whose integration is now env-locked is cancelled with `reason = 'env_locked'`, never applied).

## Steps

1. Add `SystemSettingChange` domain aggregate (`Create`, `MarkApplied`, `MarkCancelled`, `ApplyAfter` computed at creation) and the repository with `InsertPendingAsync` (catches `23505` → `Error.Conflict`), `LoadForUpdateAsync`, `ListPendingAsync` (cursor).
2. Add `SubmitCriticalChangeCommand`/Handler, wired as 09.10.2-T1's critical-path delegate (in-process call, same assembly).
3. Add `ApproveSettingChangeCommand`/Handler with the terminal-status guard (idempotent second call → 409, not a double apply) and the "different owner not promoted in last 30 days" eligibility check (`IOwnerDirectory.IsEligibleApproverAsync`).
4. Add `CancelSettingChangeCommand`/Handler (`[Audited("settings.change_cancelled", …)]`) — any owner with re-auth; also the internal hook 09.10.8-T1 calls for the public-token cancel path (soft, that task owns the HTTP route).
5. Implement `SettingChangeApplyJob` (`[JobPolicy(Retries = 0)]`, `[Audited("settings.change_applied", …)]` on its internal command), register in 09.2.6-T1's recurring list at 1-minute cadence.
6. Migration: add the partial unique index `ix_system_setting_changes_pending ON system_setting_changes (integration) WHERE status = 'pending'` (W3 CR-1f).
7. Add `GetPendingChangesQuery` (`AdminPageDto<SettingChangeDto>`) for `GET /admin/settings/changes?status=pending`.
8. Wire the `setting_change_pending` e-mail template call (W3 CR-8 params: `integration, changedKeys, applyAfter, approveUrl?, cancelUrl`) through the existing e-mail outbox — `cancelUrl` a **plain**, un-tokenised `/admin` deep link (§C3.5). Separately, queue one `approval_cancel` message per recipient via `IEmailSender.QueueAsync` (09 W3 CR-23) so 09.10.8-T1's `SendEmailJob`-time minter can mint that recipient's single-use public cancel token.

## Acceptance checks

1. Given a critical `PUT` passes validation, Then it returns 202 `setting_change_pending`, writes exactly one `system_setting_changes` row, mints one cancel token per active owner, and sends one `setting_change_pending` e-mail per owner with **their own** `cancelUrl`.
2. Given a second critical change is submitted for the same integration while one is pending, Then 409 `setting_change_pending` and no second row exists.
3. Given a different owner not promoted in the last 30 days approves, Then the change applies immediately (`applied`, `approved_by` set) and `SettingsChanged` is published in the same transaction.
4. Given no eligible second owner exists, Then `apply_after = requested_at + 24h`; `SettingChangeApplyJob` applies it only after that time, and a second job run for the same id is a no-op (terminal-status guard).
5. Given an owner cancels a pending change, Then `status = cancelled`, `cancelled_by` set, and `SettingChangeApplyJob` never touches it again.
6. Given the integration becomes env-locked while a change is pending, Then the apply job cancels it with `reason = env_locked` rather than applying.
7. Given an OAuth (`youtube`/`tiktok`) client change applies, Then existing `channel_connections` keep their old `oauth_client_id` and `TokenHealthJob`'s `invalid_client` mapping still goes to a platform incident, never a user revoke.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Approve and cancel race on the same change | Both acquire `FOR UPDATE`; whichever transaction commits first wins, the second sees `status != 'pending'` and returns its terminal-state response (409/204 per its own rule), never a partial apply |
| `SettingChangeApplyJob` picks up a row another instance is mid-approving | `FOR UPDATE SKIP LOCKED` — the job simply skips a locked row this tick and picks it up next tick |
| Owner who requested the change is later suspended or loses the owner role before it applies | Auto-cancelled in the same transaction as the suspend/role-change, via 09.10.4-T4's `IOwnerRequestCleanup.CancelRequestsByRequesterAsync(userId, ct)` (reused, not re-implemented here) — it never applies by time-lock for a requester who is no longer an active owner |
| e-mail send fails for one recipient | `email_requested.v1` retries per 09.2.6-T3's own policy; a permanent failure raises a platform incident, the pending change itself is unaffected (the owner can still act via the admin UI) |
