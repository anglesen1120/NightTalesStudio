# 09.10.3-T1 — Hot reload: `DbSettingsProvider` and degraded start

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 09.10.3 | S (0.5) | BE | 09.10.1-T1, 09.2.4-T1, 09.10.4-T3 (`ISecurityAlerter` degraded-start alert); 09.10.2-T1 soft, 12.8.3-T1 soft (`IPaidDispatchGate`) | 02.8.3-T3 soft (audit status via settings) | S · M2 |

## Goal

Rotating a key or flipping a base URL takes effect without a restart: the Api reflects an applied change within 30 s and the Worker reflects it through the outbox; a running job keeps the values it started with (no torn reads mid-render); and if the key-encryption key is missing or wrong at boot, the app starts in a **degraded** state (paid dispatch paused, alert fired) rather than running with an empty or default secret.

## Inputs

- README §C3 **D6** (hot-reload half), **D17** (observability — the `SettingsChanged` consumer must not log secrets or full URIs).
- `plans/09-backend-api.md:266-269` §09.10.3 acceptance text: `DbSettingsProvider` as an `IOptionsMonitor` source, ≤ 30 s in Api, outbox `SettingsChanged` for the Worker, typed clients read current options per request, in-flight jobs keep their starting snapshot, degraded start = paid dispatch paused (12.8.3) + alert, never an empty key.
- Reused P types: outbox publish/consume (**09.2.4-T1**); `IOptionsMonitor<T>` convention already used by `CachedFeatureFlags`' 30 s cache (09.9.2-T2) — same TTL, same "fail toward safe" shape; `ISecurityAlerter`/D9 alert path (09.10.4-T3, soft — this task raises the alert, that task owns the alerter contract).

## Design

Implements §C3 **D6** hot-reload clause.

```csharp
// Api side: an IOptionsMonitor<T> source per typed-options family (OpenAiOptions, PaymentOptions, EmailOptions,
// YouTubeOptions, TikTokOptions, MptAdapterOptions) all backed by the SAME provider instance.
public sealed class DbSettingsProvider(ISystemSettingsReadRepository repo, ISettingsEncryptor encryptor,
    IMemoryCache cache, TimeProvider clock) : IOptionsChangeTokenSource<OpenAiOptions>, IConfigureOptions<OpenAiOptions>
    // one small adapter class per options type, all delegating to a shared internal `SettingsSnapshotCache`
{
    // cache key "settings:v1:{integration}", TTL 30s, absolute; miss -> repo read + decrypt secrets in memory only
    // never persisted to IMemoryCache as SecretString.ToString() would; the cache VALUE holds SecretString itself,
    // whose ToString()/serialization is still masked (defense in depth, not the primary control)
    public IChangeToken GetChangeToken() => _tokenSource.Token;   // triggered by (a) TTL expiry (b) explicit Invalidate()
    public void Invalidate(string integration) { /* new CancellationTokenSource, cancel the old one */ }
}
```

```csharp
// Worker side: outbox consumer, existing SettingsChanged event, no new type (D20)
public sealed class SettingsChangedHandler(DbSettingsProviderInvalidator invalidator) : IOutboxHandler<SettingsChanged>
{
    public Task HandleAsync(SettingsChanged evt, CancellationToken ct)
    {
        invalidator.Invalidate(evt.Integration);   // same cache-eviction call as the Api's write path uses locally
        return Task.CompletedTask;                  // ids/integration only in the payload — never a value (D17)
    }
}
```

Typed HTTP clients (`OpenAI text`, `mpt-adapter`, `payment`, SMTP) resolve their options via `IOptionsMonitor<T>.CurrentValue` **per request** (never captured once at client construction) — this is the mechanism that makes "no restart" true. A render job already holds its `RenderOptions` snapshot passed in at start (existing 03/05 convention) so it is unaffected by a mid-render key rotation.

**Degraded start.**

```csharp
public sealed class SettingsStartupCheck(ISystemSettingsReadRepository repo, ISettingsEncryptor encryptor,
    IPaidDispatchGate dispatchGate, ISecurityAlerter alerter) : IStartupFilter // or IHostedService.StartAsync guard
{
    public async Task RunAsync(CancellationToken ct)
    {
        var criticalKeys = await repo.LoadAllSecretsAsync(ct);     // ids/integration/key only, values stay encrypted
        foreach (var row in criticalKeys)
        {
            try { encryptor.Unprotect(row.Integration, row.Key, row.SecretCiphertext!, row.WorkerNodeId); }
            catch (CryptographicException)
            {
                await dispatchGate.PauseAsync(reason: "settings_decrypt_failed", ct);   // 12.8.3's gate
                await alerter.RaiseAsync("settings_decrypt_failed", severity: "P1", ct);
                // startup CONTINUES in degraded mode — health checks read caches only (09.9.5/health design),
                // the app never crashes and never substitutes an empty/default secret
            }
        }
    }
}
```

`/health/ready` is unaffected by this check (it reads caches only, per README §C6 "Health/degradation" row) — degraded mode is visible through the paused-dispatch gauge and the alert, not through a failing readiness probe (an HIBP/Turnstile/settings-decrypt outage must not fail `/health/ready`, README §C6).

## Steps

1. Implement `SettingsSnapshotCache` (one internal 30 s cache keyed by integration, shared by every per-options-type `IOptionsMonitor` adapter) and the six adapter classes (`OpenAiOptions`, `PaymentOptions`, `EmailOptions`, `YouTubeOptions`, `TikTokOptions`, `MptAdapterOptions`) wrapping it.
2. Wire the Api-local invalidation path: 09.10.2-T1's `UpdateSettingsCommandHandler`/09.10.2-T2's apply path calls `SettingsSnapshotCache.Invalidate(integration)` in the same request after `SaveChangesAsync` succeeds (not before — an invalidate-then-rollback would serve a value that was never committed).
3. Implement `SettingsChangedHandler` in the Worker, subscribing to the existing `SettingsChanged` outbox event, calling the same invalidation method.
4. Implement `SettingsStartupCheck`, wired into host startup (after the DB migration check, before the app accepts traffic) calling `IPaidDispatchGate.PauseAsync` (12.8.3's port, soft dependency) and `ISecurityAlerter.RaiseAsync` (09.10.4-T3's port, soft dependency) on any decrypt failure — collecting **all** failures before deciding degraded-vs-healthy (one bad key must not mask a second).
5. Ensure every typed client resolves options via `IOptionsMonitor<T>.CurrentValue` at call time (audit existing 03/05/06/07/12 client registrations that currently capture `IOptions<T>` — flag any found as a follow-up note, do not silently rewrite files outside this task's ownership).
6. Add the `youtube.audit_status` read path used by `02.8.3-T3` (soft) — confirm it goes through the same `IOptionsMonitor<YouTubeOptions>` and picks up an owner's `pending → approved` flip within 30 s, no separate poll.

## Acceptance checks

1. Given a non-critical value changes via `PUT`, When 30 s pass with no restart, Then a new request in the Api uses the new value (assert via a probe endpoint or the options snapshot directly in a test).
2. Given the same change, When the Worker's `SettingsChangedHandler` runs, Then its next use of that integration's options is the new value.
3. Given a render job started before a key rotation, When the rotation completes mid-render, Then the job finishes using the options snapshot it started with (no torn read).
4. Given the key-encryption key is wrong at boot, When the app starts, Then it does not crash, `/health/ready` still reports ready (caches-only), paid dispatch is paused, and one P1 alert fires — never an empty-string secret substituted.
5. Given two secrets fail to decrypt at boot, Then both failures are recorded (dispatch paused once, but the alert or its detail names both integrations) — a second failure is never masked by the first.
6. Given `youtube.audit_status` flips from `pending` to `approved`, Then 02.8.3-T3's read of `YouTubeOptions.AuditStatus` reflects it within the same 30 s window, with no separate polling mechanism added.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Invalidate fires before the write transaction commits | Ordered explicitly after `SaveChangesAsync` succeeds in the same request/handler — a rollback never triggers an invalidate |
| Worker misses the `SettingsChanged` event (transient outbox delay) | The 30 s TTL is the backstop — even with a missed/delayed event, the Worker's cache expires and re-reads within 30 s |
| A render job's snapshot is stale by the time it makes an external call | Documented as accepted (README §C6 residual: "the ≤ 30 s stamp window and the ≤ 30 s flag window are accepted"); a long-running job re-resolves per request if the job itself is written that way (03/05's own convention, not changed here) |
| Both `payment` and `youtube` secrets fail to decrypt at once | Startup check enumerates all rows first, then decides degraded state once, alert detail lists every failing integration |
| KEK is fixed and the app is restarted | Degraded flag clears on the next successful `SettingsStartupCheck` run (no manual reset needed); the previous alert is not auto-resolved (D17: alerts are append-only; resolution is an ops action) |
