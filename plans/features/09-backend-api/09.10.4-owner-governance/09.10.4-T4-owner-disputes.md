## Design

Implements the remainder of §C3 D8 on top of T2's `OwnerActionRequest`:

```csharp
// extends src/NightTales.Domain/OwnerGovernance/OwnerActionRequest.cs (same file, T2 owns the class; this task adds the members below)
public partial class OwnerActionRequest
{
    // Detects a re-issued request against the same (action, target) with an existing pending row, OR a "counter"
    // request filed by the target against the original requester while the original is still pending.
    public static ErrorOr<Success> DetectAndMarkDisputed(
        OwnerActionRequest incoming, IReadOnlyList<OwnerActionRequest> openRowsForSamePair, DateTimeOffset now)
    {
        foreach (var existing in openRowsForSamePair.Where(r => r.Status == OwnerActionStatus.Pending))
        {
            existing.Status = OwnerActionStatus.Disputed;
        }
        incoming.Status = OwnerActionStatus.Disputed;
        return Result.Success;
    }

    public ErrorOr<Success> CancelAsNonTargetOfSystemRequest(Guid cancellerId, DateTimeOffset now)
    {
        if (RequestedByUserId is not null) return Error.Failure("owner_action.not_a_system_request");
        // stays pending; recorded as an objection, never becomes disputed and never gets a third-party cancel
        return Result.Success;  // handler maps this to 202 objection_recorded, no state mutation beyond an audit row
    }

    public ErrorOr<Success> AutoCancelOnRoleLossOrSuspend(DateTimeOffset now)
    {
        if (Status is OwnerActionStatus.Applied or OwnerActionStatus.Cancelled) return Result.Success;
        Status = OwnerActionStatus.Cancelled; CancelReason = "requester_lost_role";
        return Result.Success;
    }
}
```

- **Re-issue/counter detection** runs inside `RequestOwnerActionCommand`'s handler (owned by T2, this task adds the query + call): before creating a new row, `SELECT * FROM owner_action_requests WHERE target_user_id = @target AND action = @action AND status IN ('pending','disputed') FOR UPDATE` — any hit means the new request and every open row for that `(action, target)` pair become `disputed` via `DetectAndMarkDisputed`. A **counter** request (X, currently the target of a pending `demote`, files `demote`/`suspend` against the original requester) is detected the same way but keyed on the *reverse* pair — implemented as a second lookup `WHERE target_user_id = @originalRequesterId AND requested_by = @target AND status = 'pending'`, since D8 defines "counter" as the target striking back at the requester, not at themselves.
- **`system`-request non-cancellability:** a `system`-originated row (`requested_by IS NULL`) is never disputed by a re-issue (there is only ever one break-glass MFA-reset path per target at a time, enforced by 09.10.7-T1's own precondition, out of folder) and never gets a normal owner cancel; any owner other than the target calling `POST /admin/owner-actions/{id}/cancel` on it returns 202 `objection_recorded` (audit-only, row stays `pending`) instead of the usual 204/409 — this is a **branch inside T2's `CancelOwnerActionCommand` handler**, added here as `if (row.RequestedByUserId is null) return CancelAsNonTargetOfSystemRequest(...)` before T2's normal cancel-cap logic runs.
- **No owner-on-owner delete (D8):** `RequestOwnerActionCommand` validates `action != Delete` when `target.Role == Owner` at the domain-validation step, independent of the hierarchy check (an owner is never a valid `action=delete` target regardless of who requests it) — returns `Error.Validation(ErrorCodes.ValidationFailed)` if ever attempted (defence in depth; `09.10.5-T1`'s endpoint is not expected to route owner targets to delete at all).
- **30-day post-demotion / restore freeze (`owner_dispute_freeze_until`):** set by `09.10.7-T1`'s `nts owner restore` (out of folder) on the restored user; **read** here in the apply-time re-check (T2's job already re-checks it per §Design; this task adds the **write** path for the *approver-age* exclusion: `Approve`'s `isThirdOwnerReauth` computation in T2 must additionally read each candidate approver's `PromotedAt` and reject if `now - PromotedAt < ApproverMinOwnerAgeDays` — this task supplies `IOwnerPromotionHistory.GetPromotedAtAsync(userId, ct)`, a thin read over `audit_logs` (`action = 'account.role_changed'`, `params.to = 'owner'`, newest row) since `users` has no dedicated `promoted_at` column).
- **Auto-cancel on role loss/suspend:** hooked into the **existing** suspend/demote apply paths (T2's job, and `09.10.5-T1`'s synchronous admin suspend) via a new port `IOwnerRequestCleanup.CancelRequestsByRequesterAsync(userId, ct)`, called in the same transaction right after a user's role/status changes to non-owner or non-active — never a separate sweep job (D20 "no new" scope discipline; this runs inline where the state change already happens). **Reused by the sibling `09.10-settings/` folder** (09 W3 CR-22): `09.10.2-T2`'s `ApproveSettingChangeCommandHandler`/apply path also calls `CancelRequestsByRequesterAsync` for the same trigger, so a `system_setting_changes` row whose `requested_by` lost the owner role or was suspended is cancelled in the same transaction — `EfOwnerRequestCleanup`'s implementation therefore cancels **both** `owner_action_requests` and `system_setting_changes` pending rows for the given user id, not only the former.
- **MFA-reset forces password reset:** when an `mfa_reset` request `Apply()`s, the side-effect handler (T2's job apply step) queues `EmailMessage(targetUserId, "password_reset", target.UiLocale, new Dictionary<string,string> { ["displayName"] = target.DisplayName, ["expiresHours"] = "1" })` via the signed `IEmailSender.QueueAsync` (09.2.6-T3) — the reset link itself is minted later, at send time, by 09.3.3-T1's `PasswordResetTokenMinter` (already registered against the `password_reset` template); this task adds **only** the `QueueAsync` call in the apply-side-effect switch, alongside `RotateStampAsync`, never a new minter or a new template.

## Acceptance checks

- Given a `pending demote` request against owner X, When a second `demote` request against X is filed, Then both rows become `disputed` and neither can apply by time-lock.
- Given a `disputed` row, When any owner (the original requester or the counter-filer) calls cancel, Then 409 `owner_action_disputed` and the row is unchanged.
- Given a `system` `mfa_reset` row (multi-owner case), When a non-target owner calls cancel, Then 202 `objection_recorded`, the row stays `pending`, and an audit row is written; When the *target* itself tries to cancel it (impossible via the normal route since the target never approves — verified as a 403/404 depending on which guard fires first, exact code confirmed against `09.10.5-T1`'s endpoint wiring, not invented here).
- Given owner Y attempts `action=delete` against owner Z (another owner), When the request is created, Then 400 `validation_failed` regardless of role hierarchy.
- Given owner A was promoted 10 days ago, When they try to approve as the "third owner" on a pending request, Then their approval does not count (`isThirdOwnerReauth = false`) and the row stays `pending`.
- Given user X filed two `pending` requests as requester and is then suspended by a separate action, When that suspend applies, Then both of X's filed requests become `cancelled` (`cancel_reason = "requester_lost_role"`) in the same transaction as the suspend.
- Given an `mfa_reset` request applies, When `Apply()` runs, Then a `password_reset` e-mail is queued for the target (via `IEmailSender.QueueAsync`, `email_messages` row created with `status = 'queued'`) in addition to `RotateStampAsync` — the reset link itself is minted later by `SendEmailJob`, not by this task.

## Failure handling and edge cases

| Condition | Behavior | Code |
|---|---|---|
| Re-issued request against an existing `pending` row for the same `(action, target)` | Both rows → `disputed` | 202 `owner_action_pending` (creation still succeeds; disputed is the resulting state, not a create-time error) |
| Counter request from the target against the original requester | Both rows → `disputed` | 202 `owner_action_pending` |
| Cancel attempted on a `disputed` row by anyone | Rejected, row unchanged | 409 `owner_action_disputed` |
| Non-target cancels a `system` row | Row stays `pending`, audit-only | 202 `objection_recorded` |
| `action = delete` with target role = `owner` | Rejected at creation | 400 `validation_failed` |
| Approver promoted `< ApproverMinOwnerAgeDays` ago | Approval does not count as the qualifying third owner | (no error — silent no-op per T2's `Approve`) |
| Requester loses owner role/is suspended while requests are open | All their `pending`/`disputed` filed requests auto-cancel in the same transaction | — |
| `mfa_reset` applies | Password-reset flow triggered alongside stamp rotation | — |
