# 09.10.8-T1 — Public cancel links: `approval_cancel_tokens`, uniform errors, token-path cutoff

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

Own the `approval_cancel_tokens` table, the `IEmailTokenMinter` implementation registered against the **already-signed** `approval_cancel` e-mail template (minting the single-use token **at send time**, inside `SendEmailJob`, per [RULED WT17/WT30] — never proactively at request-creation time), and the public, anonymous `POST /security/cancel-links/{kind}/{id}` endpoint that always answers with the same uniform 400 `cancel_token_invalid`, including the 7-day token-path cutoff.

## Design

Implements §C3 D8's cancel-link half and F13, aligned with the signed 09.2.6-T3 send-time-minting contract.

```csharp
// src/NightTales.Domain/OwnerGovernance/ApprovalCancelToken.cs
public enum RequestKind { SettingChange, OwnerAction }

public sealed class ApprovalCancelToken : Entity   // not IUserOwned: minted for a recipient, read anonymously by token
{
    public RequestKind RequestKind { get; private set; }
    public Guid RequestId { get; private set; }
    public Guid RecipientUserId { get; private set; }
    public byte[] TokenHash { get; private set; } = default!;   // SHA-256(rawToken), never the raw value
    public DateTimeOffset ExpiresAt { get; private set; }       // = the underlying request's apply_after
    public DateTimeOffset? UsedAt { get; private set; }

    public static (ApprovalCancelToken Token, string RawToken) Mint(
        RequestKind kind, Guid requestId, Guid recipientUserId, DateTimeOffset expiresAt)
    {
        var raw = Convert.ToHexString(RandomNumberGenerator.GetBytes(32));   // 256-bit, never logged
        var hash = SHA256.HashData(Encoding.UTF8.GetBytes(raw));
        return (new ApprovalCancelToken { Id = Guid.CreateVersion7(), RequestKind = kind, RequestId = requestId,
            RecipientUserId = recipientUserId, TokenHash = hash, ExpiresAt = expiresAt }, raw);
    }

    public ErrorOr<Success> Consume(string rawToken, RequestKind kind, Guid requestId, DateTimeOffset now)
    {
        if (RequestKind != kind || RequestId != requestId) return Error.Validation(ErrorCodes.CancelTokenInvalid);   // 09 W3 CR-27: bind the token to the path
        if (UsedAt is not null) return Error.Validation(ErrorCodes.CancelTokenInvalid);
        if (now > ExpiresAt) return Error.Validation(ErrorCodes.CancelTokenInvalid);
        var candidateHash = SHA256.HashData(Encoding.UTF8.GetBytes(rawToken));
        if (!CryptographicOperations.FixedTimeEquals(candidateHash, TokenHash))
            return Error.Validation(ErrorCodes.CancelTokenInvalid);
        UsedAt = now;
        return Result.Success;
    }
}

// src/NightTales.Infrastructure/Email/TokenMinters/ApprovalCancelTokenMinter.cs
public sealed class ApprovalCancelTokenMinter(IAppDbContext db, IClock clock, IOptions<...> origin) : IEmailTokenMinter
{
    public async Task<ErrorOr<IReadOnlyDictionary<string, string>>> MintAsync(
        Guid userId, string template, IReadOnlyDictionary<string, string> parameters, CancellationToken ct)
    {
        // requestKind/requestId are producer-supplied, allow-listed params (see the CR below) — not rendered in the
        // template text, consumed only here to resolve which row this recipient's token belongs to.
        var kind = Enum.Parse<RequestKind>(parameters["requestKind"], ignoreCase: true);
        var requestId = Guid.Parse(parameters["requestId"]);
        var applyAfter = await ResolveApplyAfterAsync(kind, requestId, ct);   // reads owner_action_requests/system_setting_changes
        var (token, raw) = ApprovalCancelToken.Mint(kind, requestId, userId, applyAfter);
        // idempotent per SendEmailJob attempt (09 W3 CR-26): a prior unused row for this (kind, request, recipient) is
        // superseded in place, never a second row and never a 23505 unique-index failure on a retry after a transient SMTP error
        await db.Database.ExecuteSqlInterpolatedAsync($@"
            INSERT INTO approval_cancel_tokens (id, request_kind, request_id, recipient_user_id, token_hash, expires_at, used_at)
            VALUES ({token.Id}, {kind.ToString()}, {requestId}, {userId}, {token.TokenHash}, {applyAfter}, NULL)
            ON CONFLICT (request_kind, request_id, recipient_user_id) DO UPDATE
                SET token_hash = EXCLUDED.token_hash, expires_at = EXCLUDED.expires_at
                WHERE approval_cancel_tokens.used_at IS NULL", ct);
        var link = $"{origin.Value.PublicOrigin}/cancel-request#kind={kind}&id={requestId}&token={raw}";
        return new Dictionary<string, string> { ["cancelLink"] = link };
    }
}
```

- **Minting is at send time, not at request creation.** `09.10.4-T2`/`09.10.4-T3` never call this task's code directly to mint a token; they queue `EmailMessage(recipientId, "approval_cancel", locale, { displayName, requestKind, reason, deadline, requestId })` via the signed `IEmailSender.QueueAsync`, and `SendEmailJob` (09.2.6-T3, consumed) resolves `ApprovalCancelTokenMinter` for the `approval_cancel` template and calls `MintAsync` right before rendering — exactly mirroring `PasswordResetTokenMinter`'s registration. No token row, and no raw token, ever exists before send time.
- **[OPEN] proposed CR** to `09.2.6-T3`'s `EmailTemplateCatalog.All["approval_cancel"]`: extend the Keys set from `["displayName", "requestKind", "reason", "deadline", "cancelLink"]` to include `"requestId"` (a producer-supplied GUID string, consumed only by `ApprovalCancelTokenMinter.MintAsync`, never rendered as a `{{requestId}}` placeholder in the template text) — without this key, the minter cannot resolve which row a given recipient's token belongs to. Cited, not applied by this folder; designed against this "new text" per the folder convention.
- **A no-token guarantee for the target/disputed/system cases (F13, D8) is enforced by the *caller*, not this task:** `09.10.4-T2`/`09.10.4-T3` simply never queue an `approval_cancel` message for the target of an owner action, for a `disputed` row, or for a `system` row — so `SendEmailJob` never calls `MintAsync` for those, and no row is ever created. `ApprovalCancelTokenMinter` additionally re-checks the row's `status = 'pending'` before minting (defence in depth): if the row has since become `disputed`/`applied`/`cancelled` between queueing and send time, `MintAsync` returns `Error.Failure("approval_cancel.stale_request")` and `SendEmailJob` records the message `Failed` (observable via `email_messages`, never silently dropped).
- **Uniform validation order (F13 — token validated before any status lookup):** the endpoint (1) hashes the posted token, looks up `approval_cancel_tokens WHERE token_hash = @hash AND used_at IS NULL`; a miss → `cancel_token_invalid` immediately, **before** even checking whether `{kind}/{id}` exists.
- **Token-path cutoff (7 days, `TokenPathCutoffDays`):** after a successful `Consume`, before applying the cancel: `SELECT 1 FROM approval_cancel_tokens t2 JOIN owner_action_requests r ON r.id = t2.request_id AND t2.request_kind = 'owner_action' WHERE r.target_user_id = (SELECT target_user_id FROM owner_action_requests WHERE id = @requestId) AND t2.used_at IS NOT NULL AND t2.used_at > @now - interval '7 days' AND t2.id <> @thisTokenId` (mirrored for `setting_change` keyed on `system_setting_changes.integration`) — a hit rolls back this token's own `Consume()` and the response is `cancel_token_invalid`.
- **`cancelled_by`:** the endpoint's downstream call into `09.10.4-T2`'s cancel command passes `cancellerId = token.RecipientUserId`, so `cancelled_by` is always the token's recipient.

## Acceptance checks

- Given a `pending` owner-action request with two other active owners, When `09.10.4-T2`'s `RequestOwnerActionCommand` handler queues `approval_cancel` for both via `IEmailSender.QueueAsync` (09 W3 CR-23), Then `SendEmailJob` (signed, consumed) calls `ApprovalCancelTokenMinter.MintAsync` for each and two `approval_cancel_tokens` rows exist — none proactively created before send time.
- Given a token minted for `owner_action`/`{A}`, When it is POSTed to `/security/cancel-links/owner_action/{B}` (a different request id), Then 400 `cancel_token_invalid` and request `B` is unchanged (09 W3 CR-27).
- Given `SendEmailJob` fails once on SMTP for a queued `approval_cancel` message and retries, When the retry calls `MintAsync` again for the same recipient, Then no `23505` occurs, the row's `token_hash` is rotated to the retry's token, and the link delivered on the successful attempt works while the original (never-sent) token is superseded (09 W3 CR-26).
- Given a valid, unused token in the request body, When `POST /security/cancel-links/owner_action/{id}`, Then 204 and the underlying row's `cancelled_by` equals the token's `recipient_user_id`.
- Given the same token POSTed a second time, When the request repeats, Then 400 `cancel_token_invalid` (not a second 204).
- Given an unknown `{id}` with a syntactically well-formed but non-matching token, When POSTed, Then 400 `cancel_token_invalid` — identical body/status to the used-token case.
- Given the underlying row became `disputed` between queue time and send time, When `SendEmailJob` calls `MintAsync`, Then it returns `approval_cancel.stale_request` and no token row is created; `email_messages.status = 'failed'` for that message.
- Given owner A used their cancel link for target T's `demote` request 2 days ago, and a fresh, unused token exists for owner B on a later request against the same target T within the 7-day window, When owner B POSTs it, Then 400 `cancel_token_invalid` (token-path cutoff), not 204.

## Failure handling and edge cases

| Condition | Behavior | Code |
|---|---|---|
| Token hash has no match at all | Reject before any id/status lookup | 400 `cancel_token_invalid` |
| Token already used | Reject | 400 `cancel_token_invalid` |
| Token expired (`now > expires_at`) | Reject | 400 `cancel_token_invalid` |
| Underlying request went `disputed`/`applied`/`cancelled` between queue and send time | `MintAsync` refuses, no token row created, `email_messages` marked `failed` | — (no HTTP path reached — this happens inside `SendEmailJob`) |
| A different recipient's token was used for the same target/integration within 7 days | Reject (token-path cutoff), even if this token is itself fresh/unused | 400 `cancel_token_invalid` |
| Rate limit exceeded on the `anon` policy | Reject before token lookup | 429 `rate_limited` (09.3.5-T1's policy) |
| Underlying request already `applied`/`cancelled` at cancel-link POST time (mint succeeded earlier, state changed since) | Downstream cancel call is a no-op guarded by T2's terminal-status check, surfaced uniformly | 400 `cancel_token_invalid` |
