## Goal

The `InitialCore` migration creates the core set on an empty database. From then on, CI rejects any migration that fails on an empty database, fails on the previous schema with data, or leaves the model out of sync.

## Inputs

- Plan §3, §7; README D9 (naming rule), NFR-09-6 (expand → migrate → contract); 02.2.2 plan L738 (02 relies on this harness).

## Design

- Generate: `dotnet ef migrations add InitialCore --project src/NightTales.Infrastructure --startup-project src/NightTales.Api --context AppDbContext --output-dir Persistence/Migrations`. [DECISION] `InitialCore` keeps EF's timestamp prefix. The owner-naming rule `<yyyyMMddHHmm>_<Owner>_<What>` applies from the next migration on, for example `202610051200_02_SourcesAndFetchTasks`.
- Design-time factory `Infrastructure/Persistence/AppDbContextDesignFactory.cs` (`IDesignTimeDbContextFactory<AppDbContext>`). It reads `ConnectionStrings:Postgres` from env and uses a null `ICurrentUser`, so the tools do not need the Api host.
- Bundle: `dotnet ef migrations bundle --self-contained -r linux-x64 -o artifacts/nts-migrate`, run by 11.5.1 as a one-shot job; in CI/cloud the connection comes from the environment (`ConnectionStrings__Postgres`, masked with `::add-mask::`), never argv; `--connection` is for local use only (11 CR-14).
- CI job `migrations`, added to `.github/workflows/backend.yml` (09.1.5-T1), runs `tests/NightTales.Api.IntegrationTests/Migrations/`:

```csharp
[Fact] Migrations_ApplyOnEmptyDatabase()                 // MigrateAsync on a fresh DB (not the template)
[Fact] Migrations_ApplyOnPreviousSchemaWithSeed()        // migrate to N-1 via IMigrator.MigrateAsync(target), run SeedPrevious, migrate to N, assert seed rows intact
[Fact] Model_HasNoPendingChanges()                       // db.Database.HasPendingModelChanges() == false (EF 8+) ⚠️ confirm name
[Fact] Migrations_ContainNoDestructiveOperations()       // scan the latest migration's operations: DropTable/DropColumn/AlterColumn narrowing → fail unless the migration class has [ContractMigration]
```

- `SeedPrevious` (`Migrations/SeedPrevious.cs`) inserts a realistic minimal dataset through raw SQL that is valid for schema N-1: one user, one series, two episodes, one story version, one usage record. Each feature migration extends it when it adds tables. With only `InitialCore`, N-1 is the empty schema and the test degenerates to "apply on empty".
- Review checklist, recorded in the PR template (`.github/pull_request_template.md`, section "Migration"): expand-only? locks taken (avoid `ALTER TABLE … SET NOT NULL` on large tables without a default)? backfill in batches? down script present?

## Steps

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two feature branches add migrations in parallel | the snapshot conflicts at merge → the later branch regenerates its migration on top (documented in `docs/dev-setup.md`) |
| A migration needs a long backfill | split: an expand migration plus a batched backfill job, never one blocking migration |
| `HasPendingModelChanges` is unavailable | fallback: generate a script from the snapshot vs the model with `migrations script --idempotent` and diff it [DECISION] |

- [DECISION owner 2026-09-30: option (a)] NTS-922-SEC-001 (security review 09.2.2-T1, medium; 09 W3 CR-45): child tables reference user-owned parents by id alone (`episodes.series_id`, `story_versions.episode_id`, `assets.episode_id`, `moderation_events.episode_id`, `autopilot_runs.series_id`, …), so the database accepts user B's row pointing at user A's parent, and A's delete cascades or SET NULLs B's row. TL decision before `InitialCore` is generated: (a) composite same-owner FKs — alternate key `(id, user_id)` on each parent, FK `(parent_id, user_id)` on each child; a nullable SET NULL FK needs PostgreSQL's column-list `ON DELETE SET NULL (parent_id)`, which EF does not emit (raw SQL in the migration); or (b) no DB rule, and the 09.2.3-T1 application invariant is the only control. Cheapest before this migration exists. **Owner chose (a) on 2026-09-30:** `InitialCore` ships the composite same-owner keys and FKs (raw SQL for the column-list `ON DELETE SET NULL (parent_id)` cases), and the 09.2.3-T1 application invariant stays as a second control.
