# 09.2.3-T1 — Tenant filter, `ICurrentUser`, `ISystemContext`, `ISystemWorkQuery`

## Goal

No query in the Api or the Worker can see another user's rows without an allow-listed bypass. Worker code acts as one user only after `ISystemContext.For(userId)`.

## Inputs

- Plan §3, §8; README D10, D13, N9; 09 L88–95.

## Design

```csharp
public interface ICurrentUser { Guid? Id { get; } bool IsAuthenticated { get; } PlatformRole Role { get; } ActorType Actor { get; } }
public interface ISystemContext { IDisposable For(Guid userId); }

// Infrastructure/Security/ScopedCurrentUser.cs — registered Scoped as ICurrentUser and ISystemContext in the Worker
public sealed class ScopedCurrentUser : ICurrentUser, ISystemContext
{
    public IDisposable For(Guid userId);   // throws on Guid.Empty, on a second call, or if an AppDbContext/ReadDbContext was already resolved in this scope
}
// Api: HttpCurrentUser (Scoped) from IHttpContextAccessor; ISystemContext is also registered in the Api
// (a ScopedCurrentUser decorator) for outbox-style work started in-process — used only by tests [DECISION]

// Infrastructure/Persistence/Conventions/TenantFilterConvention.cs, applied from ApplyNightTalesConventions(context)
foreach (var et in model.GetEntityTypes().Where(t => typeof(IUserOwned).IsAssignableFrom(t.ClrType)))
    // builds: e => ((IUserOwned)e).UserId == context.CurrentUserId  as HasQueryFilter("tenant", lambda)
```

- The "already resolved" guard: `AppDbContext` and `ReadDbContext` call `ScopedCurrentUser.MarkObserved()` in their constructor. `For` after `MarkObserved` throws `InvalidOperationException("ISystemContext.For must run before any DbContext is created in this scope")`. This makes the D10 ordering rule fail fast.
- `CurrentUserId` is captured at context construction (`Guid?`). The filter references the context field, so EF parameterizes it (T2f).
- `ISystemWorkQuery.PendingAsync<T>(where, batch, ct)` runs `IgnoreQueryFilters(["tenant"]).Where(where).Select(e => (e.Id, e.UserId)).Take(batch)` on `ReadDbContext`. It is the only allow-listed bypass outside `Features/Admin` apart from the three named jobs.
- 404 policy helper: `Application/Common/Errors/Errors.cs` → `Errors.NotFound()` = `Error.NotFound(code: ErrorCodes.NotFound)`. Handlers return it whenever a filtered lookup misses.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| A handler needs a platform (non-user) table | platform tables (`voices`, `style_templates`, `feature_flags`) are not `IUserOwned`; no filter applies |
| An admin feature needs cross-user reads | only under `Features/Admin` (the admin surface `09.9.1` is dropped by DEC 10.14); disabling only `"tenant"` keeps any future named filters active |
| A user is deleted while a Worker item is in flight | the item's rows are gone or restricted; the handler sees nothing and exits (idempotent) |

- [IMPLEMENTED 2026-09-30] Two types beyond plan §3, both required to make D10's guards work in both
  hosts; they are the deviation to review with this file.
  - `Application/Abstractions/ITenantScopeObserver.cs` (`void MarkObserved()`): `AppDbContext` and
    `ReadDbContext` report "a `DbContext` exists in this scope" through the scope's `ICurrentUser`, so
    the `For`-after-context guard fires without the persistence layer depending on a concrete type.
    `ScopedCurrentUser` (Worker) and `HttpCurrentUser` (Api, forwarding to the `ScopedCurrentUser` it
    decorates) implement it; `ISystemContext` keeps exactly the `For` member D10 pins.
  - `Conventions/TenantFilterConvention.cs` also declares the internal `ITenantFilterContext`
    (`Guid? CurrentUserId`), implemented by `AppDbContext`/`ReadDbContext`: one convention serves both
    contexts without reflection, and its body references the *context instance* member, so EF
    parameterizes the filter per query (plan §2 T2f). `ApplyNightTalesConventions` therefore takes the
    context as an argument.
- [IMPLEMENTED 2026-09-30] `HttpCurrentUser` pins the claim shape (QA 09.2.3-T1): `sub` counts only
  when it parses as a **non-empty** `Guid` (empty or unparseable → no user), and `role` is read only
  behind a valid `sub` — a request with no user is `PlatformRole.User`/`ActorType.User` even when it
  carries `role=admin`, so a claim set cannot elevate an actor it does not name. Covered by

  and `HttpCurrentUserClaimsTests` (absent/empty/unparseable/`Guid.Empty` `sub`, plus the system-scope
