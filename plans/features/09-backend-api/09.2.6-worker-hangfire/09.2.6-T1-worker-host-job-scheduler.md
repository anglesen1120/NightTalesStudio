## Goal

The Worker runs background jobs from PostgreSQL-backed Hangfire on named queues. Application code schedules them only through `IJobScheduler`, a job's retry policy comes from `[JobPolicy]`, and recurring jobs are kept in sync with the code at every start.

## Inputs

- Plan §3, §7; README D12 (port signatures, queues, rules), D13 (`WorkerHost` modes), D1, N5, N6, H3; 09 W3 CR-42 (composition root, no `manual` prefix exception, framework reference, health probe, native dev DB).

## Design

```csharp
// Application/Abstractions/Jobs/
public interface IBackgroundJob;                                   // marker; job classes are sealed, resolved from DI
public enum JobQueue { Default, Render, Publish, Email }
[AttributeUsage(AttributeTargets.Class)]
public sealed class JobPolicyAttribute : Attribute { public JobQueue Queue { get; init; } = JobQueue.Default; public int Retries { get; init; } }
public interface IJobScheduler
{
    string Enqueue<TJob>(Expression<Func<TJob, CancellationToken, Task>> call) where TJob : class, IBackgroundJob;
    string Schedule<TJob>(Expression<Func<TJob, CancellationToken, Task>> call, TimeSpan delay) where TJob : class, IBackgroundJob;
    void AddOrUpdateRecurring<TJob>(string id, string cron, Expression<Func<TJob, CancellationToken, Task>> call) where TJob : class, IBackgroundJob;
    void RemoveRecurringIfExists(string id);
}
public interface IRecurringJobRegistration { string Id { get; } void Register(IJobScheduler scheduler); }
```

- `HangfireJobScheduler` rewrites `(j, ct) => j.RunAsync(id, ct)` into Hangfire's `Expression<Func<TJob, Task>>` by substituting `ct` with `CancellationToken.None` (H3). It then calls `IBackgroundJobClient.Enqueue(queue, expr)`, with the queue read from `[JobPolicy]` on `TJob` (lowercase name).
- `JobPolicyFilterProvider : IJobFilterProvider` returns `new AutomaticRetryAttribute { Attempts = policy.Retries, OnAttemptsExceeded = AttemptsExceededAction.Fail }` for the job type (`JobFilterScope.Type`). API confirmed against Hangfire.Core/NetCore 1.8.25 (implementation 2026-09-30): it is **not** added to `GlobalJobFilters`/`JobFilterProviders.Providers` (a global `AutomaticRetryAttribute` would still win, because Hangfire elects the first filter that moves the candidate state); it is the host's DI `IJobFilterProvider`, composed with `JobFilterProviders.Providers`, which the client and the server both resolve from DI. The global default `AutomaticRetryAttribute` (10 attempts) is **removed** from `GlobalJobFilters.Filters`, so the default is 0.
- `RecurringJobRegistrar.StartAsync`:
  1. Register every `IRecurringJobRegistration`.
  2. Read the current recurring ids from the host's own `JobStorage` (`storage.GetConnection().GetRecurringJobs()`), never `JobStorage.Current`.
  3. Remove **every** id that is not registered — no prefix exception, no opt-out (09 W3 CR-42).
  4. Cron is UTC.
- `AddWorkerServices(this IServiceCollection, IConfiguration)` is the one Worker composition root used by both `Worker/Program.cs` and `WorkerHost` (D13): `AddPersistence`, `AddMediator` (Scoped), `AddJobs`, the hosted `OutboxDispatcher` (appended by 09.2.4-T1), the health listener below, and the `IRecurringJobRegistration` scan. `Program.cs` calls it and adds nothing role-specific that the tests must fake.
- Worker project file: `src/NightTales.Worker/NightTales.Worker.csproj` needs `<FrameworkReference Include="Microsoft.AspNetCore.App" />` in addition to its `Microsoft.NET.Sdk.Worker` defaults — `Worker/Program.cs` builds a `WebApplication` (Kestrel) for the `/health/*` listener, which the plain Worker SDK does not reference (09 W3 CR-42).
- Storage: one `PostgreSqlStorage` per host, registered as the host's `JobStorage` singleton (`new PostgreSqlStorage(new NpgsqlConnectionFactory(cs, options), options)` with `PostgreSqlStorageOptions { SchemaName = Jobs:SchemaName ("hangfire"), PrepareSchemaIfNecessary = true, QueuePollInterval = TimeSpan.FromSeconds(Jobs:QueuePollSeconds) }`) and passed to `AddHangfire(... UseStorage(...))`. No code reads the process-static `JobStorage.Current`: the Worker and a test host, or two parallel test hosts, share one process (D13).
- Process-static Hangfire state is made per host (implementation 2026-09-30): `AddJobs` registers the host's own `JobActivator` (`AspNetCoreJobActivator` over its `IServiceScopeFactory`) before `AddHangfire`, so the server never falls back to `JobActivator.Current`; and `HangfireLogProviderRelease` (the first hosted service, so it stops last) resets Hangfire's process-global `LogProvider` on stop. Without the reset a disposed host leaves the static pointing at a disposed `ILoggerFactory`, the next host's `PostgreSqlObjectsInstaller` static constructor fails, and every later storage silently runs in degraded mode.
- Server: `AddHangfireServer(o => { o.Queues = ["default","render","publish","email"]; o.WorkerCount = sum(Jobs:Workers:*) })`. [DECISION] One server with all queues in P. Per-queue servers come when a queue needs isolation (render, 09.6).
- Api: registers `IJobScheduler` **only** with a throwing implementation ("the Api schedules through the outbox", H4). An accidental Api use fails fast in tests.
- Worker `Program.cs` (in order): Serilog; `AddWorkerServices` (which itself adds persistence, Mediator, jobs, the hosted `OutboxDispatcher` and the recurring scan); the Hangfire server; the health listener on `Worker:HealthPort`. The `OutboxDispatcher` is **not** named in this order — 09.2.4-T1 appends it inside `AddWorkerServices` (09 W3 CR-42).
- Health and logging here are deliberately minimal: `/health/live` and `/health/ready` on `Worker:HealthPort`, bound to `127.0.0.1:8082`, for the native dev stack (Homebrew `postgresql@17`) and the optional compose smoke test only. 09.9.3-T1 replaces them with the shared observability/health surface, and `/health/ready` answers 503 **only** when the database check fails (a Hangfire/storage/registry degradation is reported in the body, never as 503 — 09.9-D2).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two Workers start together | Hangfire.PostgreSql installs its schema in one Serializable transaction and tolerates a concurrent install instead of locking ⚠️ (Notes; not load-tested); recurring upserts are idempotent |
| A job class is not registered in DI | Hangfire fails the job at activation; a start-time check resolves every `IBackgroundJob` type found in Application and fails the Worker boot if one is missing [DECISION] |
| A long job during shutdown | the server's cancellation token fires; jobs must honour `ct`; Hangfire requeues aborted jobs |
| Spike fails (H2) | see the plan's open items; the port and tests stay unchanged |

## Notes

- Spike result: **PASSED (2026-09-30)** — Hangfire.PostgreSql 1.21.1 + Npgsql 10 on the Homebrew PostgreSQL 17.11 server: `HangfirePostgres_OnNpgsql10_EnqueueAndRun` enqueues a probe job on a real Hangfire server, the job runs and its row exists in `probe_job_effects`; the `Jobs` test filter is 23/23 twice, the full integration assembly 135/135 three times.
- `/health/ready` takes about 62 s to answer while Hangfire storage has **never initialised** in this process (cold start with the database down): `HangfireStorageHealthCheck` opens a storage connection to read the recurring-job set, which runs `PostgreSqlStorage.EnsureInitialized()` with its startup retries (5, backoff up to 1 min). Once storage has initialised, a later outage answers 503 in about 80 ms (QA 2026-09-30). The 503 contract holds in both cases (only the database check decides it); 09.9.3-T1, which replaces this dev-only surface, should bound the cold-start case.
- **PERF (2026-09-30).** The readiness check reads the recurring-job set with one indexed lookup (`GetConnection().GetAllItemsFromSet("recurring-jobs")`) instead of `GetMonitoringApi().GetStatistics()`, whose aggregate groups the whole job table on every probe. Warm reads on the test database: storage-level `GetStatistics` 0.5–3.9 ms vs `GetAllItemsFromSet` 0.1–0.3 ms; warm `/health/ready` through the probe (20 samples each) median 0.6 ms → 0.4 ms — the test database's job table is empty, where the aggregate is cheap, which is why the difference is small there. The cold path is unchanged: a real Worker with the database down answered the first three probes in 57.9/62.0/62.0 s before and 58.4/61.9/62.0 s after, because both reads initialise the storage first.
- Two Workers starting together: Hangfire.PostgreSql installs its schema in one Serializable transaction and swallows the version-already-applied guard, so a concurrent install is tolerated rather than serialised (read from the 1.21.1 installer, not load-tested).
- The ids-only argument rule is enforced by 09.1.2-T1 `Jobs_TakeIdsOnly`.
- **`manual` prefix exception dropped (09 W3 CR-42 / WRK-9).** The former "[DECISION] keep ids prefixed `manual`" rule is gone: an id no longer produced by an `IRecurringJobRegistration` is deleted on the next Worker start, and `RecurringRegistrar_RemovesUnregisteredId_OnNextStart` pins it.
- **`AddWorkerServices` is the composition root (09 W3 CR-42 / WRK-1, WRK-6).** `Worker/Program.cs` only calls it; `OutboxDispatcher` (09.2.4-T1) and every other hosted service are registered inside it, so `WorkerHost` gets exactly the production graph minus the Hangfire server.
- **Two `WorkerHost` modes (09 W3 CR-42 / WRK-6, WRK-7).** Inline is the default (no Hangfire server; `InlineJobScheduler` records and runs jobs) and matches the 09.2.1-T2 wording; the real-server mode is opt-in and exists only for this task's enqueue/queue/routing tests.
- **Framework reference (09 W3 CR-42 / WRK-18).** The Worker builds a `WebApplication` for `/health/*`, so it needs `<FrameworkReference Include="Microsoft.AspNetCore.App" />`; without it the Kestrel listener cannot compile. 11.1.1-T1 pins the Worker image as `mcr.microsoft.com/dotnet/aspnet:10.0` for the same reason.
