## Goal

Only an owner or admin who has just proven password + TOTP can see the Hangfire dashboard. Owners can act on jobs and admins can only read. Everyone else gets a 404, and every access is audited.

## Inputs

- 09 L109 (requirements); README D1 (`Hangfire.AspNetCore` in Api), D10; 09.10.4-T1 (TOTP, re-auth); 09.3.6-T1 (`audit_logs`).

## Design

- Hosted in the Api: `app.UseHangfireDashboard("/internal/jobs", new DashboardOptions { Authorization = [new JobsDashboardAuthorizationFilter()], IsReadOnlyFunc = ctx => !IsOwner(ctx), AppPath = null, DisplayStorageConnectionString = false })`. The Api uses the same storage as the Worker (read side). Only the dashboard, no server, runs in the Api.
- Cookie scheme `JobsDashboard` (`__Host-nts-jobs`, `HttpOnly`, `Secure`, `SameSite=Strict`, 30 min absolute, no sliding):
  - issued by `POST /internal/jobs/login`, which requires a valid access token **and** a successful re-auth (password + TOTP within 5 min, 09.10.4-T1 `reauth_required` rules);
  - carries `sub`, `role` and the `security_stamp`, and is re-validated on each request against the live account: one bounded, no-tracking read of the user's `role`, `status` and `security_stamp`; an account that no longer exists, is not `active`, or no longer matches the ticket's role or (when the ticket carries it) stamp is answered 404 with the cookie cleared. `[DECISION]` 09.3.2-T2's stamp cache is not landed, so the dashboard reads the account row itself rather than wait for it; when that cache lands, this check becomes its caller.
- `JobsDashboardAuthorizationFilter : IDashboardAuthorizationFilter`: cookie valid, role `owner`/`admin`, and the IP on `InternalJobs:AllowedCidrs` when configured. Otherwise the response is **404** (the filter writes 404 instead of Hangfire's default 401 ⚠️ confirm).
- Antiforgery: the Hangfire dashboard POSTs carry its own antiforgery token when `app.UseAntiforgery()` is registered ⚠️ confirm for 1.8. Otherwise add a middleware that requires `X-Requested-With` + an `Origin` check on every POST under `/internal/jobs`.
- Audit: middleware writes `audit_logs` rows `internal.jobs_viewed` (once per session) and `internal.jobs_action` (per POST: retry/delete/trigger, with the job id), `category = support`, `visibility = internal` (09.3.6-T1 writer).

## Steps

1. Add the cookie scheme and the login endpoint (reusing 09.10.4-T1 re-auth).
2. Add the authorization filter, the read-only function and the IP check.
3. Add the antiforgery/origin protection and the audit middleware.
4. Write the tests.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| The user's role or stamp changes | the next request fails the live-account check → 404, and the cookie is cleared |
| The dashboard leaks job arguments | job arguments are ids only (09.1.2-T1), so there is nothing sensitive to show |
