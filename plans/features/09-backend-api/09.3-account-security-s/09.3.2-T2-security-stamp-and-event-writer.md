# 09.3.2-T2 — Security stamp validation and the single rotation writer

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 09.3.2-T2 | M (1.0) | BE | 09.3.2-T1, 09.2.4-T1; 09.8.1-T1 soft (connection abort) | 09.10.4-T2, 09.10.4-T4, 09.10.5-T1, 09.3.3-T3 soft | S · M2 |

## Goal

Close the ≤ 30 s revocation window described in §C3 D9: add the `security_stamp` claim to the access token, validate it (plus the family's live state) on every authenticated request, and give the whole codebase exactly **one** place that rotates `users.security_stamp` — `ISecurityEventWriter.RotateStampAsync` — so a stamp rotation, its `UserSecurityChanged` outbox row and the connection abort always happen together (F11).

- README §C0 brief 1, §C3 **D9**, §C5 (session theft row), §C6 (residual ≤ 30 s window), §C1 W3-9, F11.
- Reuse (never re-implement): `ITokenIssuer.IssueAccessToken(AppUser, Guid familyId, AuthMethod amr, DateTimeOffset now)` (09.3.2-T1:31, extended here with one claim, not a signature change — see Design), `IRefreshTokenService` (09.3.2-T1:57-65: `StartSessionAsync`, `RotateAsync`, `RevokeFamilyAsync`, `RevokeAllFamiliesAsync`, `MarkReauthenticatedAsync`, `RegisterReauthFailureAsync`, `GetReauthStateAsync`), `ICurrentUser` (09.2.3-T1:18), `IRealtimeNotifier`/the `security` `pg_notify` channel and `RealtimeConnectionRegistry.AbortUser` (09.8.1-T1:55-65, 107, 114, 170), `[OutboxEvent]` (09.2.4-T1:18-19), `IAuditWriter`/`AuditEntry` (09.3.6-T1:31-34).
- The `security` NOTIFY channel and its consumer already exist: 09.3.2-T1:140 emits `NOTIFY security` with the user id on family revocation, and 09.8.1-T1's `RealtimeListenerService` already forwards that channel to `RealtimeConnectionRegistry.AbortUser(userId)` (09.8.1-T1:107, 114). This task reuses the **same channel**, it does not add a second one.
- **Resolved by W3 CR-19 (withdrawn OPEN item).** No new `IRefreshTokenService` member and no per-request database read are added: `IStampValidator`'s cache entry carries the stamp, the user's `status` and the set of currently-revoked family ids together, loaded in one query on a cache miss and refreshed as a unit on eviction. 09 W3 CR-30 extends the signed `09.3.2-T1`'s `RevokeFamilyAsync` to publish `UserSecurityChanged` on **every** revoke (not only "when the caller is a credential event") so a single `/me/sessions/{id}` revoke also evicts this cache.

## Design

**JWT claim (extends `Es256TokenIssuer`, additive).** `IssueAccessToken` gains one claim, `security_stamp` (the value of `users.security_stamp` at issuance) alongside the existing `sub`, `role`, `sid`, `amr`; no existing claim or the method signature changes.

**Validation (`Application/Abstractions/Security/IStampValidator.cs`).**

```csharp
public interface IStampValidator
{
    Task<ErrorOr<Success>> ValidateAsync(Guid userId, string stampClaim, Guid familyId, CancellationToken ct);
}
```

```csharp
// Infrastructure/Security/CachedStampValidator.cs
public sealed record StampCacheEntry(string Stamp, string Status, IReadOnlySet<Guid> RevokedFamilyIds);

public sealed class CachedStampValidator(
    IReadDb db, IMemoryCache cache, IOptions<SecurityOptions> options) : IStampValidator
{
    public async Task<ErrorOr<Success>> ValidateAsync(Guid userId, string stampClaim, Guid familyId, CancellationToken ct)
    {
        var key = $"stamp:{userId}";
        if (!cache.TryGetValue<StampCacheEntry>(key, out var entry))
        {
            var user = await db.Users.Where(u => u.Id == userId).Select(u => new { u.SecurityStamp, u.Status }).FirstOrDefaultAsync(ct);
            var revoked = await db.RefreshTokens.Where(t => t.UserId == userId && t.RevokedAt != null)
                .Select(t => t.FamilyId).ToHashSetAsync(ct);   // bounded: a revoked row disappears once the family's own lifetime expires
            entry = new StampCacheEntry(user?.SecurityStamp ?? "", user?.Status ?? "suspended", revoked);
            cache.Set(key, entry, TimeSpan.FromSeconds(options.Value.StampCacheSeconds));   // 30 s (§C3.3), one query per miss, zero per hit
        }
        if (string.IsNullOrEmpty(entry.Stamp) || !CryptographicOperations.FixedTimeEquals(Encoding.UTF8.GetBytes(entry.Stamp), Encoding.UTF8.GetBytes(stampClaim)))
            return Errors.SessionRevoked();
        if (entry.RevokedFamilyIds.Contains(familyId)) return Errors.SessionRevoked();
        if (entry.Status != "active") return Errors.SessionRevoked();
        return Result.Success;
    }
}
```

Wired as a `JwtBearerEvents.OnTokenValidated` handler (Api host only — the Worker's `ScopedCurrentUser` never carries a bearer token, D10) so the check runs before any endpoint filter/handler sees the request; a failure fails the authentication result with 401 `session_revoked` (not a 500), matching D9's mapping.

**Cache eviction.** `IMemoryCache` entry for `stamp:{userId}` is removed by the `UserSecurityChanged` outbox handler (below) the moment the event is dispatched, so the ≤ 30 s window is an upper bound, not a guaranteed wait; on an instance whose `LISTEN` connection to `security` reconnects (a dropped/park connection), the **whole** cache is cleared (`IMemoryCache.Compact(1.0)`) because any number of stamps may have rotated while the instance was not listening.

**The single writer (F11).**

```csharp
// Application/Abstractions/Security/ISecurityEventWriter.cs
public interface ISecurityEventWriter { Task RotateStampAsync(Guid userId, string reason, CancellationToken ct); }
```

```csharp
// Infrastructure/Security/SecurityEventWriter.cs
public sealed class SecurityEventWriter(IAppDbContext db, IClock clock) : ISecurityEventWriter
{
    public async Task RotateStampAsync(Guid userId, string reason, CancellationToken ct)
    {
        var user = await db.Users.SingleAsync(u => u.Id == userId, ct);
        user.SecurityStamp = Guid.NewGuid().ToString("N");                        // one rotation, one row
        db.Add(new UserSecurityChanged(userId, reason, clock.UtcNow));            // [OutboxEvent] below — joins this SaveChanges (D11)
        await db.Database.ExecuteSqlRawAsync("SELECT pg_notify('security', {0})", new object[] { userId.ToString() }, ct);
    }
}

[OutboxEvent("user_security_changed.v1")]
public sealed record UserSecurityChanged(Guid UserId, string Reason, DateTimeOffset OccurredAt) : IDomainEvent;

// Application/Features/Security/UserSecurityChangedHandler.cs
public sealed class UserSecurityChangedHandler(IMemoryCache cache) : IOutboxHandler<UserSecurityChanged>
{
    public ValueTask HandleAsync(UserSecurityChanged e, OutboxContext ctx, CancellationToken ct)
    { cache.Remove($"stamp:{e.UserId}"); return ValueTask.CompletedTask; }
}
```

`RotateStampAsync` never calls `SaveChangesAsync` itself (D5/UnitOfWork rule) — it is always called from inside a command handler's ambient transaction, so the stamp, the outbox row and (via the existing `security` `pg_notify`, reused verbatim from 09.3.2-T1:140) the connection abort all commit or roll back together.

**Known gap ([OPEN], flagged to the TL, not fixed here).** Two **signed** wave-2 handlers already rotate `users.SecurityStamp` **inline**, without calling this writer: `ResetPasswordCommand` (09.3.3-T1:105-106: "Rotate `user.SecurityStamp` … and raise `UserSecurityChanged`") and the MFA `VerifyMfaCommand`/`DisableMfaCommand` handlers (09.10.4-T1:91, 93: "rotate `SecurityStamp` + outbox `UserSecurityChanged`"). F11's acceptance line — "a scan test fails if `security_stamp` is assigned outside that file" — cannot pass against the current signed code without a CR to those two files replacing their inline rotation with a call to `ISecurityEventWriter.RotateStampAsync`; no such CR exists in README §C4 (CR-1…CR-16). This task's scan test is therefore scoped to the assignments it can enforce (§Tests), and the two pre-existing sites are listed as accepted exceptions pending that CR — reported to the TL (see Notes).

## Steps

1. Add `IStampValidator`, `CachedStampValidator`, `ISecurityEventWriter`, `SecurityEventWriter`, `UserSecurityChanged`, `UserSecurityChangedHandler`.
2. Extend `Es256TokenIssuer.IssueAccessToken` with the `security_stamp` claim (one line; no signature change).
3. Wire `CachedStampValidator` into `JwtBearerEvents.OnTokenValidated`; map a failed `ValidateAsync` to 401 `session_revoked`.
4. Register the `IMemoryCache` eviction handler on the outbox dispatch path and the `LISTEN`-reconnect full-compact hook (reuses 09.8.1-T1's listener lifecycle events).
5. Wire the four new call sites (09.10.5-T1, 09.10.4-T2, 09.3.7-T1) to call `RotateStampAsync` — coordinate via `agent://` with the folder(s) that own those handlers so they call this port instead of assigning the field themselves.
6. Write the scan test, the credential-event test matrix, and the two-instance/`LISTEN`-reconnect tests.

## Acceptance checks

- [ ] Given a user's stamp is rotated by any of the four new call sites, When the same user's next request presents the old-stamp JWT, Then it answers 401 `session_revoked` within ≤ 30 s (observed via `stamp_cache_evictions_total{reason}`), and sooner if the outbox handler has already fired.
- [ ] Given a rotation and its outbox row committed, Then exactly one `UserSecurityChanged` row exists for that transaction and `stamp:{userId}` is absent from the cache immediately after dispatch.
- [ ] Given a rotation whose transaction is rolled back (a later step in the same handler fails), Then neither the stamp nor the outbox row persists (both-or-neither).
- [ ] Given a family that is revoked (independently of a stamp rotation), When a request with a still-valid stamp but that family's `sid` arrives, Then 401 `session_revoked` within the same ≤ 30 s cache window as a stamp change (the cached `RevokedFamilyIds` set gates the route, zero per-request DB read) — sooner once `RevokeFamilyAsync`'s `UserSecurityChanged` (09 W3 CR-30) evicts the entry.
- [ ] Given two Api instances, one of which loses its `LISTEN` connection to `security` and reconnects, Then that instance's **entire** stamp cache is cleared on reconnect (not just the one user who triggered the drop).
- [ ] Given `grep -rn "\.SecurityStamp\s*=" src/` outside `SecurityEventWriter.cs`, Then only the two accepted pre-existing sites (09.3.3-T1's `ResetPasswordCommand`, 09.10.4-T1's MFA handlers) remain — any **new** site fails the scan test.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two rotations for the same user race (e.g. suspend + a concurrent MFA reset) | Both are separate transactions; both stamps are new GUIDs, the last commit wins, and **both** produce an outbox row/cache eviction — no lost update because neither reads-then-writes the old value |
| The outbox dispatcher is behind (backlog) | The claim check still fails once the cache TTL (≤ 30 s) expires even without the eviction event — the cache is the hard upper bound |
| `pg_notify('security', …)` fails (connection issue) | The transaction still commits (the `ExecuteSqlRawAsync` call is a plain statement, not a 2PC); a dropped notification only delays the SignalR abort, never the stamp/outbox commit — the stamp check still revokes the session on the next request within the cache window |
| A request without a `security_stamp` claim (an old token minted before this task) | Treated as a stamp mismatch → 401 `session_revoked`, forcing a fresh login/refresh |
| The two pre-existing inline rotation sites (09.3.3-T1, 09.10.4-T1) | Still correct in isolation (they write their own outbox row) but bypass the single-writer invariant; flagged as an [OPEN] CR target, not silently patched here (out of folder scope) |
