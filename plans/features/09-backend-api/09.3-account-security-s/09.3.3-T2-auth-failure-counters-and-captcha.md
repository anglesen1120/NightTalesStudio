## Goal

Give the login/forgot/reauth/register surface a PostgreSQL-backed, two-instance-safe brute-force gate (§C3 D10): 3 failures for a (account, IP/device) pair trigger CAPTCHA, further failures add a progressive delay, and the whole state lives in the new `auth_failure_counters` table — never in memory (W3-TL5).

## Design

**Table (W3 CR-1, D10).** `auth_failure_counters(id uuid, scope text CHECK (scope IN ('account_ip','account_device')), key_hash text, failures int, window_started_at timestamptz, last_failure_at timestamptz, delay_until timestamptz NULL, captcha_required_at timestamptz NULL, user_id uuid NULL, updated_at timestamptz)`; unique `(scope, key_hash)` — **one row per (account, IP) or (account, device) pair, never an independent per-account/per-IP/per-device counter** (D10; three independent scopes would let failures against the owner's e-mail from any IP challenge/delay the owner's own trusted device); index `(updated_at)` for the sweep.

**Port and gate.**

```csharp
// Application/Abstractions/Security/IAuthFailureGate.cs
public sealed record GateOutcome(bool CaptchaRequired, TimeSpan? Delay);
public interface IAuthFailureGate
{
    Task<GateOutcome> CheckAsync(string account, string ip, string? device, CancellationToken ct);   // before the credential check
    Task RecordFailureAsync(string account, string ip, string? device, CancellationToken ct);        // after a wrong credential
    Task ClearAsync(string account, string ip, string? device, CancellationToken ct);                // after a successful login
}

// Application/Abstractions/Security/ICaptchaVerifier.cs
public interface ICaptchaVerifier
{
    Task<ErrorOr<Success>> VerifyAsync(string? token, string? remoteIp, Guid idempotencyKey, CancellationToken ct);
}
```

**`EfAuthFailureGate` (PostgreSQL, upsert per pair, W3-TL5, D10).** Each of `scope ∈ {account_ip, account_device}` is tracked as its **own row**, keyed by `key_hash = HMAC-SHA256(Auth:CounterPepper, accountKey + '|' + ip)` (scope `account_ip`) or `HMAC-SHA256(Auth:CounterPepper, accountKey + '|' + deviceFingerprint)` (scope `account_device`) — never a bare per-account, per-IP or per-device key; `CheckAsync` reads only the **two rows for the current request's pair** (the `account_ip` row when the e-mail resolves to a user and the request has a resolvable IP, the `account_device` row when a `__Host-nts_device`-adjacent fingerprint is present) and returns `CaptchaRequired = true` when **either of those two rows** (never an unrelated pair for the same account) has `failures ≥ SecurityOptions.CaptchaAfterFailures` (3) inside `CounterWindowMinutes` (30), and `Delay` = `min(2^(failures-3), ProgressiveDelayMaxSeconds)` seconds once a valid CAPTCHA has cleared the gate but failures continue. The upsert is one statement per pair (scope, key):

```sql
INSERT INTO auth_failure_counters (id, scope, key_hash, failures, window_started_at, last_failure_at, user_id, updated_at)
VALUES (gen_random_uuid(), @scope, @key_hash, 1, now(), now(), @user_id, now())
ON CONFLICT (scope, key_hash) DO UPDATE SET
  failures = CASE WHEN auth_failure_counters.window_started_at < now() - interval '30 minutes'
                   THEN 1 ELSE auth_failure_counters.failures + 1 END,
  window_started_at = CASE WHEN auth_failure_counters.window_started_at < now() - interval '30 minutes'
                            THEN now() ELSE auth_failure_counters.window_started_at END,
  last_failure_at = now(), updated_at = now()
RETURNING failures;
```
No row-level lock is held across requests — the `ON CONFLICT` upsert is atomic and safe from two Api instances writing the same key concurrently (§C6 backpressure). `ClearAsync` deletes only the two rows for the **current request's** `(account, IP)`/`(account, device)` pair on a successful login — never a bare account-wide row and never another pair's rows for the same account — so a legitimate user is never left mid-delay after signing in correctly, and an attacker failing from a different IP/device cannot re-arm or clear the owner's own pair.

**`TurnstileVerifier` (D4).**

```csharp
public sealed class TurnstileVerifier(IHttpClientFactory clients, IOptions<CaptchaOptions> options,
    IMeter meter, IAuditWriter audit, ILogger<TurnstileVerifier> log) : ICaptchaVerifier
{
    public async Task<ErrorOr<Success>> VerifyAsync(string? token, string? remoteIp, Guid idempotencyKey, CancellationToken ct)
    {
        if (string.IsNullOrEmpty(token)) return Errors.CaptchaInvalid();
        var form = new Dictionary<string, string> {
            ["secret"] = options.Value.SecretKey.Reveal(), ["response"] = token,
            ["remoteip"] = remoteIp ?? "", ["idempotency_key"] = idempotencyKey.ToString() };
        try
        {
            using var res = await clients.CreateClient(HttpClients.Turnstile).PostAsync(options.Value.VerifyUrl, new FormUrlEncodedContent(form), ct);
            var body = await res.Content.ReadFromJsonAsync<SiteverifyResponse>(ct);
            if (body is { Success: true }) return Result.Success;
            log.LogInformation("captcha_rejected {Codes}", string.Join(',', body?.ErrorCodes ?? []));   // codes only, never the token
            return Errors.CaptchaInvalid();   // covers wrong / timeout-or-duplicate / invalid-input-response — one code, no oracle
        }
        catch (Exception ex) when (ex is HttpRequestException or TaskCanceledException)
        {
            await audit.WriteAsync(new AuditEntry(null, ActorType.System, null, "security.captcha_unavailable",
                Category.AccountSecurity, Visibility.Internal, null, null, "{}", null, null, null, DateTimeOffset.UtcNow), ct);
            meter.CaptchaChallengesTotal.Add(1, new("outcome", "unavailable"));   // 09 W3 CR-25: metric, not a SecurityEvent — "captcha_unavailable" is not one of §C3.3's nine frozen `security.*` kinds
            return options.Value.FailOpen ? Result.Success : Errors.CaptchaUnavailable();
        }
    }
}
```

`idempotencyKey` is generated **once per logical attempt** by the caller (the endpoint filter, below) and reused across the ≤ 1 transport retry the `turnstile` named client performs, so a network retry never burns the single-use Turnstile token (F08). `SecretKey` (`SecretString`) is read from the `captcha` settings integration (09.10.1-T1 soft, W3 CR-2) — never hardcoded, never logged.

**Endpoint wiring (one filter, five routes).** `CaptchaGateFilter : IEndpointFilter` runs after model binding, before the handler: resolves `(account, ip, device)` from the request, calls `IAuthFailureGate.CheckAsync`; if `CaptchaRequired` and no `captchaToken` → 400 `captcha_required`; if a token is present → `ICaptchaVerifier.VerifyAsync`, mapping a verifier failure to 400 `captcha_invalid` (or, **only** on `/auth/register`, an unavailable verifier to 503 `captcha_unavailable` per D4 — every other route fails open); on success the filter calls next() and the handler's own failure path calls `IAuthFailureGate.RecordFailureAsync`, success calls `ClearAsync`. The filter is attached once per route in each owning file (09.3.2-T1's login group, 09.3.3-T1's forgot-password, 09.10.4-T1's reauth, 09.3.1-T2's register) — this task ships the filter and the two ports; it does not re-map the handlers themselves.

**Progressive delay.** Once `CaptchaRequired` is cleared but failures continue past 3, `RecordFailureAsync`'s returned count feeds `delay_until = now() + min(2^(failures-3), 60s)`; the **next** attempt inside `delay_until` is rejected by the same filter as 429 `rate_limited` with `Retry-After` computed from `delay_until - now()` (reusing `RateLimitRejection`'s `ProblemDetails` shape, not its partition store — this is a per-pair DB-backed delay, not the in-process rate limiter).

**Sweep job.**

```csharp
[JobPolicy(Queue = JobQueue.Default, Retries = 0)]
public sealed class AuthFailureSweepJob : IBackgroundJob
{
    public async Task RunAsync(CancellationToken ct)
    {
        int deleted;
        do { deleted = await db.Database.ExecuteSqlRawAsync(
            "DELETE FROM auth_failure_counters WHERE ctid IN (SELECT ctid FROM auth_failure_counters WHERE updated_at < now() - interval '24 hours' LIMIT 5000)", ct);
        } while (deleted == 5000);
        log.LogInformation("auth_failure_sweep_deleted {Count}", deleted);   // count only
    }
}
```
Registered hourly through `IRecurringJobRegistration` (09.2.6-T1's registrar).

## Acceptance checks

- [ ] Given 3 wrong passwords for one (account, IP) pair, When a 4th attempt is made without a token, Then 400 `captcha_required`, and a **second Api instance** sees the same requirement immediately (PostgreSQL-backed, not per-process).
- [ ] Given a `captcha_required` state, When a valid Turnstile token is submitted, Then the login proceeds (or fails on the real credential check, independently), and the pair's counters are cleared on success.
- [ ] Given a Turnstile token that is wrong, expired, or answers `timeout-or-duplicate`, Then 400 `captcha_invalid` in every case (one code, no oracle), and the SPA-facing response never includes Turnstile's raw `error-codes`.
- [ ] Given a transport-level retry of the same logical attempt, When the same `idempotency_key` is reused, Then the token is not burned by the retry (a second `siteverify` call with the same key does not report `timeout-or-duplicate` against **this** attempt).
- [ ] Given Turnstile is unreachable, When `/auth/login` is attempted, Then the request proceeds without a CAPTCHA (fail-open), one audit row exists, and `captcha_challenges_total{outcome="unavailable"}` increments — no `SecurityEvent`/`ISecurityAlerter` call is made (09 W3 CR-25: `captcha_unavailable` is not one of the nine frozen `security.*` kinds).
- [ ] Given Turnstile is unreachable, When `POST /auth/register` is attempted, Then 503 `captcha_unavailable` (fail-closed only here, per D4).
- [ ] Given failures continue past the CAPTCHA threshold, Then each further failure inside the 30-minute window returns 429 `rate_limited` with a `Retry-After` that doubles up to 60 s, and a successful login before `delay_until` still succeeds only once the delay has elapsed.
- [ ] Given `AuthFailureSweepJob` runs against rows both older and newer than 24 h, Then only the older rows are deleted, in batches of ≤ 5,000.
- [ ] Given a login that succeeds, Then the account/ip/device rows for that pair are removed (a subsequent failed attempt starts a fresh window).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `Auth:CounterPepperSecretRef` missing at startup | Fail fast — the pepper is required, never defaulted (a default would make `key_hash` guessable) |
| A row's `window_started_at` is stale (> 30 min) at upsert time | The upsert resets `failures = 1` and restarts the window in the same statement (no separate read) |
| The same (scope, key) pair hits from two Api instances in the same millisecond | `ON CONFLICT` serializes at the database; no lost increments |
| `CaptchaOptions.Enabled = false` | The filter short-circuits to `next()` immediately; the progressive delay from `IAuthFailureGate` still applies (D10 requires the delay independent of CAPTCHA) |
| Turnstile responds `success: true` for an idempotency-key replay outside its own 300 s validity | Rejected upstream by Turnstile itself (`timeout-or-duplicate`) — this task does not need its own expiry check |
| `remoteip` cannot be resolved (no forwarded header trusted) | Sent as empty string to `siteverify`; Turnstile still validates the token, just without IP context |
| Sweep job runs while a counter is mid-upsert | The `updated_at` predicate excludes rows touched inside the last 24 h, so an in-flight row is never deleted mid-write |
