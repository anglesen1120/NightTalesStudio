# 09.3.3-T3 — MFA failure detector, trusted devices and the re-auth limit

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

Add the two MFA abuse ceilings §C3 D11 requires (5-wrong/30-min notice, 50-wrong/24-h lock for **untrusted** devices only), the `trusted_devices` cookie/table that lets a recognised device skip the ceiling and the CAPTCHA delay while **never** skipping TOTP, and the fixed evaluation order that keeps a legitimate owner from being locked out by their own trusted device (F09).

## Design

**Table (W3 CR-1d, index only — the table itself is 00 §6's, D9's non-goal-turned-goal for S).** `trusted_devices(id uuid, user_id uuid, refresh_family_id uuid, token_hash text, user_agent text, created_at, last_used_at, expires_at, revoked_at)`; this task adds the index `(user_id, expires_at)` and is the **first** writer (P deliberately created no row, README Part B §11 "trusted_devices … is not created in P").

**Cookie.** `__Host-nts_device`: 32 random bytes, `Secure; HttpOnly; SameSite=Strict; Path=/` (no `Domain`, `__Host-` prefix requires it), only its SHA-256 hash is stored (`token_hash`), 30 days (`SecurityOptions.TrustedDeviceDays`). Minted on a **successful** MFA verification (`VerifyMfaCommand`/`LoginMfaHandler` outcome) when the caller opts in (`rememberDevice: true` in the MFA-step body — a new optional field on the signed `LoginMfaCommand`, additive) and bound to that request's `refresh_family_id`.

**Ports.**

```csharp
public interface ITrustedDeviceService
{
    Task<ErrorOr<Success>> IsTrustedAsync(Guid userId, string? deviceCookie, CancellationToken ct);
    Task<string> IssueAsync(Guid userId, Guid refreshFamilyId, CancellationToken ct);          // returns the plaintext cookie value once
    Task RevokeForFamilyAsync(Guid refreshFamilyId, CancellationToken ct);                      // family revocation cascade
    Task RevokeAllForUserAsync(Guid userId, CancellationToken ct);                              // suspend / restore / "sign out everywhere"
}

public interface IMfaFailureDetector
{
    Task<MfaFailureOutcome> RecordFailureAsync(Guid userId, bool deviceTrusted, CancellationToken ct);
}
public sealed record MfaFailureOutcome(bool NoticeSent, bool LockedUntrusted, DateTimeOffset? LockedUntil);
```

`EfMfaFailureDetector` keeps its own per-user counters in `auth_failure_counters` with `scope = 'account'` and a distinct `key_hash` namespace (`HMAC(pepper, "mfa:" + userId)`) — **reusing 09.3.3-T2's table and pepper**, not a second table (D19/D20: no second store). `RecordFailureAsync`: increments the 30-minute bucket; at `failures == 5` sends `mfa_failed_notice` (§C3.5: `displayName, failedCount, windowMinutes, securityUrl`) and writes `account.mfa_failed` audit (+ a D9 `ISecurityEventWriter`-adjacent security event for admin/owner, via `ISecurityAlerter`, **not** a stamp rotation — a wrong code is not a credential change); tracks a separate 24-hour bucket that, at `failures == 50` **and** `deviceTrusted == false`, sets `LockedUntrusted = true` with `LockedUntil = now() + 24h` (or cleared early by a completed e-mailed password reset, which already revokes all families per 09.3.3-T1:107 and therefore implicitly lifts the lock — no separate unlock call needed).

**Fixed evaluation order (F09, the whole point of this task).** Every MFA-bearing request (`/auth/login/mfa`, `/me/mfa/*`, `/auth/reauth`) evaluates, **in this order, stopping at the first non-pass**:

```csharp
public sealed class MfaGuardPipeline(IStampValidator stamps, ITrustedDeviceService trusted,
    IMfaFailureDetector detector, IAuthFailureGate captchaGate)
{
    public async Task<ErrorOr<MfaGuardContext>> EvaluateAsync(Guid userId, string? deviceCookie, string? captchaToken, string ip, CancellationToken ct)
    {
        // 1. stamp/status — handled upstream by IStampValidator on the bearer token / pre-auth cookie; not re-checked here for the MFA step itself
        var isTrusted = await trusted.IsTrustedAsync(userId, deviceCookie, ct);       // 2. trusted device
        if (isTrusted.IsError) return isTrusted.Errors;                              // device revoked/expired → treat as untrusted, fall through
        var trustedOk = !isTrusted.IsError;
        if (!trustedOk)
        {
            var ceiling = await detector.PeekLockStateAsync(userId, ct);              // 3. detector ceiling — never applied to a trusted device
            if (ceiling.LockedUntrusted) return Errors.MfaLockedUntrusted(ceiling.LockedUntil);
        }
        if (!trustedOk)                                                               // 4. CAPTCHA/delay — never applied to a trusted device
        {
            var gate = await captchaGate.CheckAsync($"user:{userId}", ip, deviceCookie, ct);
            if (gate.CaptchaRequired && captchaToken is null) return Errors.CaptchaRequired();
        }
        return new MfaGuardContext(trustedOk);                                        // TOTP is still required regardless of trustedOk (D11: never skips TOTP)
    }
}
```

A trusted device **still calls** `ITotpVerifier.VerifyAsync`/`IRecoveryCodeService.RedeemAsync` exactly as an untrusted one — `trustedOk` only elides steps 3/4, never the TOTP check itself, matching "never skips TOTP" (00 §6, D11).

**Re-auth limit.** `IReauthGuard`'s existing 5-wrong-attempt-revokes-the-family rule (09.10.4-T1:78-82, `refresh_tokens.reauth_attempts`) is the re-auth limit D11 refers to; this task adds no new counter for it — it wires `MfaGuardPipeline` ahead of `POST /auth/reauth` too, so a trusted device is exempt from the CAPTCHA/delay steps there as well, while the existing 5-attempt family revocation (401 `session_revoked`) still applies unconditionally (a revoked family is not a "ceiling", it is the existing hard limit).

## Acceptance checks

- [ ] Given 5 wrong TOTP codes in 30 minutes, Then `mfa_failed_notice` is queued (params `displayName, failedCount, windowMinutes, securityUrl`) and one `account.mfa_failed` audit row exists; for an admin/owner account, an additional security alert fires.
- [ ] Given 50 wrong codes in 24 h from an **untrusted** device, Then further MFA attempts answer 429 `mfa_locked_untrusted` until an e-mailed password reset completes or 24 h elapse.
- [ ] Given the same 50-wrong sequence from a **trusted** device, Then the ceiling never applies (no 429 `mfa_locked_untrusted`), and TOTP is still required and still checked on every attempt (the trusted-device cookie alone never authenticates).
- [ ] Given the 4-case matrix — (a) trusted device during an active ceiling, (b) untrusted device during the same ceiling, (c) a trusted device immediately after a credential event (stamp rotated), (d) a trusted device whose `refresh_family_id` was revoked — Then (a) passes without the ceiling, (b) is blocked, (c) is treated as untrusted (the family/stamp link is gone) and (d) is treated as untrusted.
- [ ] Given 5 wrong `/auth/reauth` attempts for one family, Then that family is revoked → 401 `session_revoked` (the existing 09.10.4-T1 rule, unaffected by this task).
- [ ] Given a user suspended by an admin, Then every `trusted_devices` row for that user is revoked in the same operation that revokes their sessions (09.10.5-T1 → `RevokeAllForUserAsync`).
- [ ] Given a family revoked by any path, Then its `trusted_devices` row is revoked in the same transaction (no orphaned trust after the session it was bound to is gone).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| A trusted-device cookie presented for a **different** user than the caller | `IsTrustedAsync` fails closed (treated as untrusted) — the cookie's `user_id` must match the authenticated caller |
| Cookie present but its row is `revoked_at IS NOT NULL` or `expires_at <= now()` | Untrusted path (steps 3/4 apply); no error surfaced to the caller beyond the normal ceiling/CAPTCHA responses |
| `RememberDevice: true` on an account without MFA enrolled | Rejected — trusted devices only make sense as an MFA companion; the field is ignored (no row created) when `two_factor_enabled` is false |
| 50-wrong ceiling reached exactly as a password reset e-mail is requested | The ceiling stays until either 24 h passes or the reset **completes** (family revocation), not merely requested |
| Two devices for one user, one trusted one not | Independent state — the untrusted device's ceiling/delay never affects the trusted one and vice versa |
| `Security:TrustedDeviceDays` changed mid-flight (config reload) | Only affects newly issued cookies; existing rows keep their original `expires_at` |
| Detector and 09.3.3-T2's brute-force gate keyed collision | Prevented by the `"mfa:"` prefix in the HMAC input — the two namespaces never share a `key_hash` |
