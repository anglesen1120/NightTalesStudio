## Goal

Let a user see and control their own active sessions (§C3 D12): `GET /me/sessions`, `DELETE /me/sessions/{id}`, `POST /me/sessions/revoke-all`, plus the `session_new_device` e-mail on a login from an IP/device not seen in 90 days.

## Design

**Query.**

```csharp
public sealed record GetSessionsQuery : IQuery<ErrorOr<IReadOnlyList<SessionDto>>>;
public sealed record SessionDto(Guid Id, DateTimeOffset CreatedAt, DateTimeOffset LastUsedAt,
    DateTimeOffset ExpiresAt, string? Ip, string? UserAgent, string? DeviceLabel, bool IsCurrent);   // §C3.1 verbatim
```

```sql
SELECT family_id, MIN(created_at) AS created_at, MAX(last_used_at) AS last_used_at, MAX(expires_at) AS expires_at,
       (ARRAY_AGG(ip ORDER BY created_at DESC))[1] AS ip, (ARRAY_AGG(user_agent ORDER BY created_at DESC))[1] AS user_agent
FROM refresh_tokens
WHERE user_id = @userId AND revoked_at IS NULL AND expires_at > now()
GROUP BY family_id
ORDER BY MAX(last_used_at) DESC
LIMIT 20;   -- uses ix_refresh_tokens_user_revoked_expires (W3 CR-1c)
```

One row per **family** (a session = a refresh-token family, not a single row — a family accumulates rows across rotations); `Id` in `SessionDto` is the `family_id`; `IsCurrent = family_id == ICurrentUser.SessionId`; `DeviceLabel` is a small heuristic over `user_agent` (`"Chrome on macOS"`-style, parsed with a minimal UA table — never the raw string surfaced as the label, though `UserAgent` itself is still returned raw per the DTO). A user with more than 20 active families keeps only the 20 newest in the list (§C3 D12) — the rest are **not silently dropped from the system**, they remain revocable in bulk via `revoke-all`, just not individually listed.

**Delete one session.**

```csharp
public sealed record DeleteSessionCommand(Guid FamilyId) : ICommand<ErrorOr<Success>>;
```
Handler: confirm the family belongs to `ICurrentUser.Id` (an explicit `WHERE user_id = @me` predicate — `refresh_tokens` **is** `IUserOwned` per 09 conventions, so the tenant filter already applies and another user's id is a 404 for free, D10) → `IRefreshTokenService.RevokeFamilyAsync(familyId, "user_revoked", ct)` → 204. A revoked family aborts its own SignalR connections through the already-existing `security` NOTIFY (09.3.2-T1:140) — no new abort path is added here.

**Revoke-all.**

```csharp
public sealed record RevokeAllSessionsCommand : ICommand<ErrorOr<Success>>;
```
Handler: `IRefreshTokenService.RevokeAllFamiliesAsync(ICurrentUser.Id, "user_revoked_all", exceptFamilyId: ICurrentUser.SessionId, ct)` → audit `account.sessions_revoked_all` with `{count}` (§C3.4) → 204. This is the self-service counterpart of 09.10.5-T1's admin-triggered `/admin/users/{id}/sessions/revoke`, which calls the **same** port with `exceptFamilyId: null` — no second revoke path is created.

**New-device notice (D12).**

```csharp
public interface INewDeviceDetector
{
    Task<bool> IsNewAsync(Guid userId, string ip, string? userAgent, CancellationToken ct);   // true ⇒ not seen in 90 days
}
```
`EfNewDeviceDetector.IsNewAsync`: `SELECT NOT EXISTS(SELECT 1 FROM refresh_tokens WHERE user_id = @userId AND ip = @ip AND user_agent = @userAgent AND created_at > now() - interval '90 days')` (uses the existing `(user_id, revoked_at, expires_at)` index's leading column plus a sequential filter on `ip`/`user_agent` — acceptable because the row count per user is small and bounded by session churn, not an unbounded table; if profiling later shows otherwise, a supplementary index is a follow-up, not blocking this task). Called from `LoginHandler`'s success path (09.3.2-T1, one call added at the point a new `IssuedRefreshSession` is created) — **on a new device**, queue `session_new_device` (§C3.5: `displayName, device, ip, at, securityUrl`, **no token**) and write `account_security` audit (no §C3.4 action name currently reserves this row's `messageKey`; this task reuses `account.login_succeeded` for the feed entry and adds the e-mail as a side effect, so no new allow-list entry is needed).

## Acceptance checks

- [ ] Given a user with 3 active sessions (one current), When `GET /me/sessions` is called, Then all 3 are listed newest-first, exactly one has `isCurrent = true`, and each row groups its family's rotations into one entry.
- [ ] Given `DELETE /me/sessions/{id}` for the caller's own family, Then 204 and that family alone is revoked (the other two sessions remain valid).
- [ ] Given `DELETE /me/sessions/{id}` for another user's family id, Then 404 `not_found` (no information about the id's existence leaks).
- [ ] Given `POST /me/sessions/revoke-all`, Then every family **except** the caller's current one is revoked, and one `account.sessions_revoked_all` audit row with `{count}` exists.
- [ ] Given a login from an IP/user-agent pair not seen in the caller's last 90 days of `refresh_tokens` rows, Then `session_new_device` is queued with `{displayName, device, ip, at, securityUrl}` and **no token**, and one `account_security` audit row exists.
- [ ] Given a login from a pair seen within 90 days, Then no `session_new_device` e-mail is queued.
- [ ] Given a user with more than 20 active families, Then `/me/sessions` lists only the 20 newest, and `revoke-all` still revokes every family beyond those 20 too (bulk revoke is not limited to the visible list).
- [ ] Given the sessions query's `EXPLAIN` output, Then it uses `ix_refresh_tokens_user_revoked_expires` (CR-1c), not a sequential scan.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| A family with rows both revoked and live (mid-rotation) | Grouped query filters `revoked_at IS NULL AND expires_at > now()` **before** the `GROUP BY`, so a rotated-out old row never resurrects a dead session |
| `DELETE /me/sessions/{id}` on the caller's **current** session | Allowed — 204, and the caller's own next request with that token now answers 401 `session_revoked` (self-logout via this route is intentional, not blocked) |
| `revoke-all` called with only one active family (the current one) | 204, zero families revoked, `{count: 0}` audit row — not an error |
| New-device detection races with a concurrent login from the same new pair (two tabs) | Both may queue the notice — a duplicate courtesy e-mail is accepted (§C6 does not require de-duplication for this low-volume, non-security-critical notice) |
| `ip`/`user_agent` both null (a test client / an odd proxy) | Treated as "new" conservatively (queues the notice) rather than silently skipping detection |
| 09.3.2-T2's stamp cache has not yet evicted when `revoke-all` returns | Acceptable — `RevokeAllFamiliesAsync`'s `UserSecurityChanged` (09 W3 CR-30) evicts 09.3.2-T2's `stamp:{userId}` cache entry, which carries `RevokedFamilyIds` alongside the stamp, so the next request answers 401 `session_revoked` within the same ≤ 30 s window — not via a separate per-request `IsFamilyActiveAsync` call |
