## Goal

Own RFC 6238 TOTP verification with `users.last_totp_step` replay protection, Data-Protection-protected authenticator
secrets, SHA-256 recovery codes, `/me/mfa/setup|verify|recovery-codes`, `DELETE /me/mfa` (403 for admin/owner), the
enrolment-only token rule, `POST /auth/reauth` with a 5-failure family revocation and `IReauthGuard` for sensitive routes.

## Design

```csharp
public interface ITotpVerifier
{
    Task<ErrorOr<long>> VerifyAsync(Guid userId, string code, TotpSlot slot, CancellationToken ct);   // ErrorOr<long step>
}

public enum TotpSlot { Pending, Active }   // WT31: only VerifyMfaCommand passes Pending

public interface ITotpSecretStore
{
    Task<ErrorOr<string?>> GetActiveSecretAsync(Guid userId, CancellationToken ct);    // base32, decrypted
    Task<ErrorOr<Success>> SetPendingSecretAsync(Guid userId, string base32Secret, CancellationToken ct);
    Task<ErrorOr<Success>> PromotePendingSecretAsync(Guid userId, CancellationToken ct);
    Task<ErrorOr<Success>> DeleteAsync(Guid userId, CancellationToken ct);
    Task<ErrorOr<bool>> IsEnrolledAsync(Guid userId, CancellationToken ct);
}

public interface IRecoveryCodeService
{
    Task<ErrorOr<IReadOnlyList<string>>> RegenerateAsync(Guid userId, CancellationToken ct);   // 10 codes, returned once
    Task<ErrorOr<Success>> RedeemAsync(Guid userId, string code, CancellationToken ct);
    Task<int> CountRemainingAsync(Guid userId, CancellationToken ct);
}

public interface IReauthGuard { Task<ErrorOr<Success>> RequireRecentAsync(TimeSpan window, CancellationToken ct); }
public interface ISecurityAlerter { Task AlertAsync(SecurityEvent evt, CancellationToken ct); }   // 09.10.4 P: audit + log
public sealed record SecurityEvent(string Kind, Guid? SubjectUserId, string? Detail);
```
`Rfc6238TotpVerifier`: HMAC-SHA1, 30 s step, 6 digits, window **±1** (RFC 6238); the candidate steps are compared with
`CryptographicOperations.FixedTimeEquals` against the computed code; no code is ever logged. On a match it runs the
compare-and-set that makes replay impossible (BD4, W6):
```sql
UPDATE users SET last_totp_step = @step, updated_at = now()
WHERE id = @id AND (last_totp_step IS NULL OR last_totp_step < @step)
```
0 rows → `Error.Unauthorized(ErrorCodes.InvalidMfaCode)` (the step was already used → replay). [RULED — README §B10 WT31] The slot is explicit: only `VerifyMfaCommand` passes `TotpSlot.Pending`; password login (09.3.2-T1), `/auth/login/mfa` (09.3.2-T3) and `/auth/reauth` (below) pass `TotpSlot.Active`, so a pending, unverified secret is never accepted for a real sign-in.

**Cross-challenge TOTP guessing.** [RULED — README §B10 WT35] Wrong TOTP and recovery codes are counted **per user across all challenges and reauth**, not per challenge: >= 10 wrong codes within 15 min make `/auth/login` and `/auth/login/mfa` answer 429 `rate_limited` with `Retry-After: 900` for that user and write one `account_security` audit row. The window is owned by this task (one counter shared by the password step, the MFA-completion step and `/auth/reauth`) and the per-challenge 5-attempt death from 09.3.2-T3 stays on top of it.
`DataProtectionTotpSecretStore`: `IDataProtectionProvider.CreateProtector("identity.totp.v1")` (BD4 purpose), **directly and never through `ITokenProtector`** ([RULED — README §B10 WT43]), over the base32
secret; rows live in Identity's `user_tokens` with `LoginProvider = "[AspNetUserStore]"`, `Name = "totp_secret"`
(active), `"totp_secret_pending"` [INFERENCE] (unverified enrolment) and `"recovery_codes"` (BD4); accessed through
`AppDbContext.Set<IdentityUserToken<Guid>>()` inside the caller's transaction. Nothing is written to `users` except the
columns 00 §6 already defines, so this task adds **no** migration for TOTP state.
`CrockfordBase32RecoveryCodes`: 10 codes of 10 characters from the Crockford alphabet
(`0123456789ABCDEFGHJKMNPQRSTVWXYZ`, no I/L/O/U), 50 bits each from `RandomNumberGenerator`; stored as the
`;`-joined SHA-256 hex list in the single `recovery_codes` token row (the shape Identity's store uses, W7) so the row
can be replaced atomically. `RedeemAsync` locks the row (`SELECT … FOR UPDATE`), compares every stored hash with
`FixedTimeEquals`, removes the matched one and saves — single use, concurrent-safe. `RegenerateAsync` replaces all
(exactly 10 new codes) and returns them once.

**No migration in this task.** The durable per-family counter BD4 needs ("5 wrong re-auth attempts per family revoke
it") ships with `refresh_tokens` in 09.3.2-T1's `_09_RefreshTokens`: `reauth_attempts smallint NOT NULL DEFAULT 0` and
`reauth_last_attempt_at timestamptz NULL` (+ `CHECK (reauth_attempts BETWEEN 0 AND 5)`), **ruled in** there ([RULED — README §B10 WT32])
because README B10 WT23 adds them beyond W2 CR-1's column list (W2 CR-14). The increment targets `WHERE family_id = @f AND revoked_at IS NULL` and rotation copies both values to the successor row (WT32). This task only reads/increments them through
`IRefreshTokenService.GetReauthStateAsync` and `RegisterReauthFailureAsync`. TOTP state likewise needs no migration:
`users.last_totp_step`/`two_factor_enabled` come from 00 §6 and the secret/codes live in Identity's `user_tokens`.

**Endpoints / handlers** (`/me/*` requires an authenticated user; all queries are filtered by the caller's `ICurrentUser.Id`,
another user's id never appears in a route → 404 `not_found`).

| Route | Handler | Behaviour |
|---|---|---|
| `POST /me/mfa/setup` | `SetupMfaCommand` | **Always** requires a recent re-auth — `IReauthGuard.RequireRecentAsync(5 min)`, else 401 `reauth_required` — even when `two_factor_enabled` is false, **unless** the caller holds the enrolment-only token (`scope = mfa_enrol`, [RULED — README §B10 WT41]). Generates a 20-byte base32 secret, `SetPendingSecretAsync`, returns `{ secret, otpauthUri }` (`otpauth://totp/NightTales:{email}?secret=…&issuer=NightTales&algorithm=SHA1&digits=6&period=30`); audit `mfa.setup_started`. The SPA renders the QR — no QR library dependency. |
| `POST /me/mfa/verify` | `VerifyMfaCommand` | Same recent-re-auth rule as `/me/mfa/setup`, waived only for the enrolment-only token ([RULED — README §B10 WT41]); `ITotpVerifier.VerifyAsync(..., TotpSlot.Pending, ...)` → `two_factor_enabled = true`, `PromotePendingSecretAsync`, `IRecoveryCodeService.RegenerateAsync` → 200 `{ recoveryCodes[10] }` (once), call `ISecurityEventWriter.RotateStampAsync(userId, "mfa_enrolled", ct)` (09.3.2-T2, D9, 09 W3 CR-20) instead of assigning the stamp inline, audit `mfa.enrolled`, `ISecurityAlerter` for admin/owner. Errors: 401 `invalid_mfa_code`, 400 `validation_failed`. |
| `POST /me/mfa/recovery-codes` | `RegenerateRecoveryCodesCommand` | `RequireRecentAsync(5 min)` → 401 `reauth_required`; regenerates 10, replaces all, audit `mfa.recovery_codes_regenerated`, security alert. |
| `DELETE /me/mfa` | `DisableMfaCommand` | Role `Admin`/`Owner` → **403 `forbidden`** (BD4: admin/owner cannot disable MFA); otherwise `RequireRecentAsync` → delete secrets + codes, `two_factor_enabled = false`, call `ISecurityEventWriter.RotateStampAsync(userId, "mfa_disabled", ct)` (09.3.2-T2, D9, 09 W3 CR-20) instead of assigning the stamp inline, `RevokeAllFamiliesAsync(…, exceptFamilyId: current sid)`, audit `mfa.disabled`, alert. |
| `POST /auth/reauth` | `ReauthCommand` | Authenticated. `ICredentialVerifier.VerifyPasswordAsync` (dummy-hash timing for a wrong/missing account is not reachable here) then `ITotpVerifier.VerifyAsync` when `two_factor_enabled`; success → `IRefreshTokenService.MarkReauthenticatedAsync(sid, now)` → 200 `{ reauthenticatedAt }`. Failure → the handler returns the success-typed `ReauthOutcome.Failed` so the counter, the revocation and the audit row commit before the endpoint maps it to 401 ([RULED — README §B10 WT29]); `RegisterReauthFailureAsync(sid, now)`, one statement `UPDATE refresh_tokens SET reauth_attempts = LEAST(reauth_attempts + 1, 5), reauth_last_attempt_at = now() WHERE family_id = @familyId AND revoked_at IS NULL RETURNING reauth_attempts` ([RULED — README §B10 WT32]) (the `LEAST` keeps the `0..5` CHECK satisfied under a concurrent double-submit); 401 `invalid_mfa_code` / 401 `invalid_credentials`; at 5 → revoke the family ("reauth_failed") and 401 `session_revoked`. Admin/owner's first failure raises `ISecurityAlerter`. |

Route guards ([RULED — README §B10 WT34]): the **fallback authorization policy rejects `scope = mfa_enrol`**, and `RequireMfaEnrolmentScope()` with policy `MfaEnrolment` lets such a request reach only `/me/mfa/setup|verify` and answers **404 `not_found`** everywhere else (BD4); `RequireMfaEnrolled()` answers 404 `not_found` on `/admin/*`
until `two_factor_enabled` is true; `RequireReauth(TimeSpan window)` is a thin endpoint filter over `IReauthGuard` that
later plans attach to their sensitive routes (settings, role change, MFA reset, grants). `SessionLimits` from
09.3.2-T1 is validated on start (owner/admin 12 h absolute / 30 min idle) and the re-auth window is
`Auth:Reauth:WindowMinutes` = `5` (BD4).
`ISecurityAlerter` P implementation `AuditAndLogSecurityAlerter`: one `account_security` `visibility = internal` audit
row plus a redacted structured log; the owner e-mail fan-out and the 11.6.2 pipeline are S (see Notes).
The enrolment-only token itself (`scope = mfa_enrol`) is issued by `ITokenIssuer.IssueEnrolmentToken` (declared in
09.3.2-T1) and this task fixes its semantics: 15-minute lifetime, `amr = pwd`, no refresh cookie, accepted only by the
two enrolment routes.

## Failure handling and edge cases

- Missing/broken Data-Protection key ring (WF15): the app starts **degraded** and paid dispatch stays paused (12.8.3); a
  TOTP secret that cannot be decrypted → 401 `invalid_mfa_code` and a P1 alert, never a silent `two_factor_enabled = false`.
- Clock skew on the server: ±1 step absorbs ~30 s; a code is never accepted after its step was recorded (replay CAS).
- A user with no recovery codes (pre-enrolment) calling `/auth/login/mfa` with `recoveryCode` → 401 `invalid_mfa_code`.
- Concurrent `RegenerateAsync` + `RedeemAsync`: both lock the single `recovery_codes` row; the loser sees the replaced set.
- Deleting MFA while a challenge exists (09.3.2-T3): the challenge still needs a code → dead challenge; `DisableMfaCommand` also
  invalidates the user's live challenges.
- Rollback: this task changes no schema; 09.3.2-T1's `_09_RefreshTokens` (including the two `reauth_*` columns) is
  expand-only, so a revert is an app rollback and the columns stay in place unused (never `DROP COLUMN`).
- Bounded work: TOTP = one token read + one `UPDATE … WHERE` CAS (+1 HMAC per candidate step, ≤ 3); recovery redeem = one
  row lock + ≤ 10 hash compares; re-auth = one family read + one update. No listing, no N+1.
