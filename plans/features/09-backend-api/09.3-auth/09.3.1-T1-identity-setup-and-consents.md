## Design

**Application ports (`Application/Abstractions/Identity/`).**
```csharp
public enum RegistrationMode { Closed, Invite, Open }            // Registration:Mode
public enum LegalDocument { Tos, Privacy }                       // stored snake_case: tos | privacy

public interface IPasswordPolicy
{
    Task<ErrorOr<Success>> ValidateAsync(string password, CancellationToken ct);
}

public interface IBreachedPasswordChecker
{
    Task<ErrorOr<bool>> IsBreachedAsync(string password, CancellationToken ct);
}

public interface ICredentialVerifier
{
    Task<ErrorOr<AppUser>> VerifyAsync(string email, string password, CancellationToken ct);   // 401 invalid_credentials
    Task<bool> VerifyPasswordAsync(AppUser user, string password, CancellationToken ct);       // re-auth, no error mapping
}

public interface IConsentWriter
{
    Task<ErrorOr<Success>> RecordAsync(Guid userId, LegalDocument document, string version, IPAddress? ip, CancellationToken ct);
}

public interface IRegistrationFlow                                             // P impl = closed
{
    Task<ErrorOr<Success>> RegisterAsync(RegisterCommand command, RequestInfo info, CancellationToken ct);
}
```

`IdentityCredentialVerifier` calls `UserManager.FindByEmailAsync` (`RequireUniqueEmail`, `normalized_email` unique, no
citext) and `UserManager.CheckPasswordAsync`. For an unknown e-mail it hashes a fixed, non-secret placeholder with
`IPasswordHasher<AppUser>` **once at construction** and runs `VerifyHashedPassword` against that dummy hash so the
unknown- and wrong-password paths cost the same (BD4 timing rule; no hard-coded hash literal, so a hasher upgrade
cannot invalidate it). `FindByEmailAsync` misses also run the dummy verification.

`IdentityPasswordPolicy` enforces only what BD2 fixes (`RequiredLength = 12`, no composition rules; `IdentityOptions`
performs the length check) and then calls `IBreachedPasswordChecker`; a hit → `Error.Validation(ErrorCodes.BreachedPassword)`
(400 `breached_password`). `KAnonymityRangeChecker` sends **only the first 5 hex characters** of `SHA1(password)`
(sha1 is used purely as the range key, never as a password store) to the ⚠️ range provider and searches the response;
`TopListPasswordChecker` binary-searches a bundled list resource. `Security:BreachedPasswords:Mode` ∈ `range | list | off`
(default `list`, so dev/CI need no network and no privacy decision); in `range` mode an unreachable provider fails
**closed** (503 `service_unavailable`) rather than accepting a possibly-breached password.

**Infrastructure.**
```csharp
// DependencyInjection/IdentityServiceCollectionExtensions.cs
services.AddIdentityCore<AppUser>(o =>
    {
        o.Password.RequiredLength = 12;
        o.Password.RequiredUniqueChars = 1;
        o.Password.RequireDigit = o.Password.RequireLowercase = o.Password.RequireUppercase = o.Password.RequireNonAlphanumeric = false;
        o.Lockout.AllowedForNewUsers = false;          // no account lockout (BD2, 09.3.3)
        o.User.RequireUniqueEmail = true;
        o.SignIn.RequireConfirmedEmail = false;        // 09.3.2-T1 answers 403 email_not_verified itself
        o.Stores.ProtectPersonalData = false;          // 09.10.4-T1 protects the TOTP secret itself (BD4)
    })
    .AddRoles<AppRole>()
    .AddEntityFrameworkStores<AppDbContext>()
    .AddDefaultTokenProviders();
services.AddOptions<RegistrationOptions>().BindConfiguration("Registration").ValidateDataAnnotations().ValidateOnStart();
services.AddOptions<BreachedPasswordOptions>().BindConfiguration("Security:BreachedPasswords").ValidateOnStart();
```
`AppUser` has **no** new property: `role`, `status`, `ui_locale`, `two_factor_enabled`, `last_totp_step`,
`security_stamp`, `last_login_at` come from 09.2.2-T1. `LegalDocumentVersions` is read from
`LegalDocuments:Current:Tos` / `LegalDocuments:Current:Privacy` (required, 1–32 chars, validated at startup).

**`user_consents` (migration `<yyyyMMddHHmm>_09_UserConsents`).**
```sql
CREATE TABLE user_consents (
    id          uuid        PRIMARY KEY,
    user_id     uuid        NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    document    text        NOT NULL CHECK (document IN ('tos','privacy')),
    version     text        NOT NULL,
    accepted_at timestamptz NOT NULL,
    ip          inet        NULL
);
CREATE INDEX ix_user_consents_user_id_document ON user_consents (user_id, document);
```
`UserConsentConfiguration : IEntityTypeConfiguration<UserConsent>`: `ToTable("user_consents")`,
`Id` `ValueGeneratedNever()` (UUIDv7 from `Guid.CreateVersion7()` in the entity factory), `Document`
`HasConversion<string>().HasMaxLength(16)` + `HasEnumCheck<LegalDocument>(…)`, `Version.HasMaxLength(32)`,
`AcceptedAt` `HasColumnType("timestamptz")`, `Ip` `HasColumnType("inet")`, index above, `HasOne<AppUser>().WithMany().OnDelete(Restrict)`.

**Endpoint (`Api/Endpoints/AuthEndpoints.cs`).**
```csharp
group.MapPost("/auth/register", async (RegisterCommand cmd, ISender sender, CancellationToken ct) => (await sender.Send(cmd, ct)).ToHttpResult())
     .AllowAnonymous().RequireRateLimiting("auth");     // policy applied by 09.3.5-T1; see Notes
```
`RegistrationGateHandler : ICommandHandler<RegisterCommand, ErrorOr<Success>>` resolves `IRegistrationFlow`;
P registers `ClosedRegistrationFlow` returning `Error.Forbidden(ErrorCodes.RegistrationClosed)` → 403
`registration_closed` for every request. 09.3.1-T3 (S) replaces the DI registration with the mode-aware flow and
reuses the same command, endpoint and validator — the P behaviour is the complete "closed" behaviour, not a stub.

Consent recording reuses the ambient transaction (D5): `ConsentWriter.RecordAsync` only `Add`s rows; the handler's
`UnitOfWorkBehavior` commits them. No `SaveChangesAsync` in the writer.

## Failure handling and edge cases

- Unknown e-mail, wrong password and suspended account must be indistinguishable in status/timing from the caller's
  point of view: unknown/wrong → `invalid_credentials` after the dummy hash; suspended → 09.3.2-T1 answers
  `session_revoked` (status is checked there, after the password, so a suspended account still needs the right password).
- Breached-list resource missing with `Mode = list` → startup failure (fail fast), never a silent `off`.
- Range provider timeout (2 s budget, `HttpClient` timeout) → 503 `service_unavailable`, request not retried with `off`.
- `user_consents` FK violation (user deleted between steps) → 400 `validation_failed` from the handler's validation, never a raw 500.
- Rollback: the migration is expand-only; a revert is an app rollback plus leaving `user_consents` in place (13.2.1-T1
  and 09.2.5-T2 must keep working). `Registration:Mode` is never flipped by code, only by config/owner action (09.10.6).
- Concurrency: two concurrent inserts of the same consent are allowed by design (history); no unique index.
