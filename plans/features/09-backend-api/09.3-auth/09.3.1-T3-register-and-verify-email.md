## Goal

With `Registration:Mode` `invite` or `open`, `POST /auth/register` creates an unconfirmed user with consent rows and a
24 h verification e-mail, answers identically for an existing e-mail, and `POST /auth/verify-email` confirms the
account; paid routes reject unverified users with 403 `email_not_verified`.

## Design

```csharp
public sealed record RegisterCommand(string Email, string Password, IReadOnlyList<ConsentAcceptance> Consents,
                                    string? InviteCode, string? UiLocale) : ICommand<ErrorOr<Success>>, IAllowAnonymousRequest;
public sealed record ConsentAcceptance(LegalDocument Document, string Version);

public sealed class ModeAwareRegistrationFlow(
    UserManager<AppUser> users, IPasswordPolicy passwordPolicy, IConsentWriter consents,
    IUserActionTokenService actionTokens, IEmailSender email, IRegistrationPolicyProvider policy,
    IOptions<RegistrationOptions> options, ILogger<ModeAwareRegistrationFlow> log) : IRegistrationFlow;

public sealed record RegistrationPolicy(RegistrationMode Mode, IReadOnlySet<string> DisposableDomains);
public interface IRegistrationPolicyProvider { RegistrationPolicy Current { get; } }   // P: config; S: settings read side
```
`RegisterValidator` (FluentValidation) checks shape only — e-mail ≤ 254 and syntactically valid, password 1–128,
exactly one `tos` and one `privacy` acceptance with a non-empty version ≤ 32 — and returns 400 `validation_failed`
**before** any account lookup, so validation never leaks existence. Then, in one UnitOfWork transaction (D5):

1. `Registration:Mode = closed` → 403 `registration_closed`.
2. `Mode = invite` → `InviteCode` hashed (SHA-256 hex) and compared constant-time to
   `Registration:Invite:CodeHash`; mismatch/absent → the same 403 `registration_closed` (no oracle, no "wrong invite" code).
3. Disposable-domain policy (09 §4 story 09.10.6, `plans/09-backend-api.md:287`: "`POST /auth/register` honours them"):
   when the e-mail domain (lower-cased, IDN-normalised) is in `IRegistrationPolicyProvider.Current.DisposableDomains`
   (`registration.disposable_domains`, P default empty) → 400 `validation_failed` with the field `email` and the same
   generic message as any invalid address — evaluated **before** the account lookup, so it is not an enumeration oracle.
   `trial.credits` from the same story is explicitly **out of scope here** (see Notes/§10): credits are 02's ledger
   (`ICreditLedger` in 02.2.2, W13) and this flow writes none.
4. `UserManager.FindByEmailAsync(normalized)`:
   - **found** → do **not** touch the account; run the same password-hash work (hash into a throwaway) for timing;
     queue `email_verify_duplicate` to the existing owner; return success.
   - **not found** → `IPasswordPolicy.ValidateAsync` (`breached_password` 400), then
     `UserManager.CreateAsync(new AppUser { Email, UserName = Email, DisplayName = null, Role = PlatformRole.User,
     Status = Active, UiLocale = command.UiLocale ?? "vi", EmailConfirmed = false, CreatedAt = now }, password)`;
     Identity failures → 400 `validation_failed` with safe Identity codes, never the password.
5. Accepted consent rows via `IConsentWriter.RecordAsync(userId, doc, version, info.Ip, ct)` (versions are checked
   against `LegalDocuments:Current:*`; a stale version is accepted and recorded as-is — re-acceptance is 13's rule).
6. `IUserActionTokenService.IssueAsync(userId, UserActionKind.EmailVerify, info, ct)` → 24 h single-use token.
7. `IEmailSender.QueueAsync(new EmailMessage(userId, "email_verify", ToLanguage(user.UiLocale),
   new Dictionary<string, string> { ["displayName"] = displayName, ["link"] = EmailLinks.Verify(origin, token), ["expiresHours"] = "24" }))`
   → `ErrorOr<Guid>` (exact record + catalog: `09.2.6-T3-email-pipeline.md:21-24`, `:78-88`; unknown template →
   `email_template_unknown`, unknown param key → `email_template_keys`) — the outbox write and the job enqueue are
   09.2.6-T3's (BD9); this task never writes `EmailRequested` itself and never touches SMTP.
8. Audit (`[Audited("auth.register", Category.AccountSecurity, Visibility.User)]`, BD15) and `users.last_login_at` untouched.

Verification and the unverified gate:
```csharp
public sealed record VerifyEmailCommand(string Token) : ICommand<ErrorOr<Success>>;
public sealed class RequireVerifiedEmailFilter : IEndpointFilter;   // 403 email_not_verified
```
`VerifyEmailHandler`: `IUserActionTokenService.ConsumeAsync(token, EmailVerify)` → `validation_failed` for
unknown/used/expired; then `EmailConfirmed = true` **and `EmailVerifiedAt = now`** via `UserManager.UpdateAsync` (no
stamp rotation — verification is not a credential event, 09 §4 09.3.2), audit `auth.email_verified`, 200 — the column
is `users.email_verified_at` (09.2.2-T1, 09 W3 CR-39).
`POST /auth/resend-verification { email }` → 202 `{ }` always; when the user exists and is unconfirmed it issues a new
token (which invalidates the previous one, see 09.3.3-T1) and queues `email_verify`; otherwise it does the dummy path.
`RequireVerifiedEmailFilter` (Api) reads `users.email_confirmed` for `ICurrentUser.Id` through `IReadDb` (single PK
lookup, no tracking) and returns 403 `email_not_verified`; 02/06 paid endpoints add this filter in their own tasks.

3. Implement `ModeAwareRegistrationFlow`, `VerifyEmailHandler`,
   `ResendVerificationHandler`, `EmailLinks` (fragment links: `{origin}/verify-email#t={token}`), `RequireVerifiedEmailFilter`.
4. Register the flow + filter; map `POST /auth/verify-email` and `POST /auth/resend-verification` (both
   `AllowAnonymous` + `RequireRateLimiting("auth")`).
5. The templates are registered by 09.2.6-T3 (`09.2.6-T3-email-pipeline.md:81,84`): `email_verify` (`displayName`, `link`,
   `expiresHours`) and `email_verify_duplicate` (`displayName`, `occurredAt` — token-free, so nothing sensitive is stored
   in `email_messages.params`); all four file variants (vi/en × txt/html) must exist or that host fails at startup.
6. Add the S-phase tests below and confirm the P tests still pass with `Registration:Mode` left at `closed`.

## Failure handling and edge cases

- Identity `CreateAsync` duplicate race (two concurrent registrations of the same e-mail): one wins; the loser returns
  the same 202 and queues `email_verify_duplicate` — never a 409, never a raw unique-violation 500.
- E-mail queue failure: the outbox write is in the same transaction as the user row (D11), so the account and the mail
  are consistent; a later dispatch failure is 09.2.6-T3's retry/dead-letter concern.
- Invite code stored hashed only; a missing `Registration:Invite:CodeHash` with `Mode = invite` is a startup failure.
- Token never logged and never placed in a query string (fragment only, BD3); `Referrer-Policy: no-referrer` (09.9.4-T1) protects the fragment.
- Rollback: drop nothing; flip `Registration:Mode` back to `closed` (unconfirmed users simply cannot use paid routes).
- Bounded work: the register path performs one user lookup, one create and two inserts; no listing, no N+1.
