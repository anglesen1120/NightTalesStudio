## Goal

`POST /auth/login` returns an ES256 access token plus a rotating `__Secure-nts_rt` refresh token, `POST /auth/refresh`
rotates it (reuse revokes the family with 401 `refresh_token_reused`) and `POST /auth/logout` revokes the family and
clears the cookie.

## Design

**Token issuing (`Application/Abstractions/Security/ITokenIssuer.cs`).**
```csharp
public enum AuthMethod { Pwd, Otp, Rc }                       // amr claim
public sealed record IssuedAccessToken(string Token, DateTimeOffset ExpiresAt, string Kid);

public interface ITokenIssuer
{
    IssuedAccessToken IssueAccessToken(AppUser user, Guid familyId, AuthMethod amr, DateTimeOffset now);
    IssuedAccessToken IssueEnrolmentToken(AppUser user, DateTimeOffset now);   // scope = mfa_enrol, 15 min, no refresh cookie
    string CreateRefreshToken();                              // 32 cryptographic random bytes, base64url
    string HashToken(string token);                           // SHA-256 hex, the only stored form
}
```
`IssueEnrolmentToken` is declared here (the signer is the same ES256 key, and `/auth/login` calls it) while its
**semantics** belong to 09.10.4-T1 (BD4): `scope = mfa_enrol`, `amr = pwd`, 15 minutes, accepted only by
`/me/mfa/setup|verify` — every other route answers 404. `LoginHandler` uses it when the role is `Admin`/`Owner` and
`two_factor_enabled` is false → 401 `mfa_enrolment_required` [INFERENCE code] with no refresh cookie.
`Es256TokenIssuer` (Infrastructure, singleton): loads `ECDsa` from the PEM secret
`nts/<env>/api/JWT_SIGNING_KEY` at startup (missing/malformed key = startup failure, never a fallback algorithm);
`kid` = first 16 hex of `SHA256(SubjectPublicKeyInfo)`; signs with `JsonWebTokenHandler` (W1) using ES256. Claims:
`sub` = `user.Id`, `role` = snake_case `PlatformRole`, `sid` = `familyId`, `amr` ∈ `pwd|otp|rc`, `stamp` = `user.SecurityStamp`
[INFERENCE claim name], `jti` = random 16 bytes, `iat`, `exp` = `now + (role is Admin or Owner ? 5 min : 15 min)`
(BD3); `iss` = `Auth:Jwt:Issuer` (default `nts-{env}`), `aud` = `nts-api`, `ClockSkew = 30 s`. Tokens are never logged
and never placed in a URL. `expires_at` inside the access-token record is what the DTO returns.

`SessionLimits` (owned here, also consumed by 09.10.4-T1's role/session-limit rule):
```csharp
public sealed record SessionLimits(TimeSpan Absolute, TimeSpan? Idle)
{
    public static SessionLimits For(PlatformRole role) => role switch
    {
        PlatformRole.Owner or PlatformRole.Admin => new(TimeSpan.FromHours(12), TimeSpan.FromMinutes(30)),
        _ => new(TimeSpan.FromDays(14), null)

```
Options `Auth:Session:*` mirror these values and are validated on start (owner/admin absolute ≤ 24 h, idle ≤ 30 min);
a configuration that widens the admin/owner values beyond BD3 fails startup.

**`refresh_tokens` (migration `<yyyyMMddHHmm>_09_RefreshTokens`).**
```sql
CREATE TABLE refresh_tokens (
    id                  uuid PRIMARY KEY,
    user_id             uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    family_id           uuid NOT NULL,
    token_hash          text NOT NULL,
    created_at          timestamptz NOT NULL,
    last_used_at        timestamptz NULL,
    expires_at          timestamptz NOT NULL,
    revoked_at          timestamptz NULL,
    revoked_reason      text NULL,      -- rotated|logout|reuse_detected|session_expired|session_idle|password_reset|mfa_change|admin_revoke
    replaced_by_id      uuid NULL REFERENCES refresh_tokens(id) ON DELETE SET NULL,
    reauthenticated_at  timestamptz NULL,
    ip                  inet NULL,
    user_agent          text NULL,
    reauth_attempts     smallint NOT NULL DEFAULT 0,        -- BD4 5-wrong-attempts rule [INFERENCE] beyond W2 CR-1
    reauth_last_attempt_at timestamptz NULL
);
CREATE UNIQUE INDEX ux_refresh_tokens_token_hash ON refresh_tokens (token_hash);
CREATE INDEX ix_refresh_tokens_family_id ON refresh_tokens (family_id);
CREATE INDEX ix_refresh_tokens_user_id ON refresh_tokens (user_id);
CREATE INDEX ix_refresh_tokens_expires_at_live ON refresh_tokens (expires_at) WHERE revoked_at IS NULL;
ALTER TABLE refresh_tokens ADD CONSTRAINT ck_refresh_tokens_reauth_attempts CHECK (reauth_attempts >= 0 AND reauth_attempts <= 5);
```
`RefreshTokenConfiguration`: snake_case mapping, `ExpiresAt`/`CreatedAt` `timestamptz`, `Ip` `inet`, `RevokedReason`
`HasConversion<string>().HasMaxLength(32)` + `HasEnumCheck<RevocationReason>(…)`, `ReauthAttempts` default `0`,
`ReauthLastAttemptAt` nullable, navigation-free `HasOne<AppUser>().WithMany().OnDelete(Cascade)`. Enum → CHECK via
`HasEnumCheck` (09.2.1-T1). [RULED — README §B10 WT32] The two `reauth_*` columns are **ruled in** (WT23 adds them; W2 CR-14 to `plans/00-overview.md` §6) beyond W2 CR-1's column list: BD4's
"5 wrong attempts per family revoke it" needs a durable per-family counter, and per-instance memory is wrong across Api
instances — the increment is `WHERE family_id = @f AND revoked_at IS NULL`, and rotation copies `reauth_attempts`/`reauth_last_attempt_at` to the successor row (WT32). The increment must clamp — `reauth_attempts = LEAST(reauth_attempts + 1, 5)` — so a
concurrent double-submit right after the 5th failure cannot violate the CHECK and surface as a 500 instead of 401.

**Rotation algorithm** (`EfRefreshTokenService`, raw SQL inside the handler's UnitOfWork transaction, D5 — no retrying
execution strategy per D5):
```sql
SELECT r.id, r.user_id, r.family_id, r.expires_at, r.last_used_at, r.revoked_at, r.reauthenticated_at,
       root.created_at AS family_started_at, r.reauth_attempts, r.reauth_last_attempt_at
FROM refresh_tokens r
JOIN LATERAL (SELECT created_at FROM refresh_tokens WHERE family_id = r.family_id ORDER BY created_at LIMIT 1) root ON TRUE
WHERE r.token_hash = @hash
FOR UPDATE
```
1. no row → 401 `session_revoked` (unknown cookie; nothing to revoke).
2. `revoked_at IS NOT NULL` **and** `revoked_reason = 'rotated'` → **reuse detected**: revoke the whole family (`reuse_detected`), audit
   `account_security` `refresh.reuse_detected`, queue `refresh_token_reuse` (params `displayName`, `occurredAt`, `device`,
`sessionsLink` — 09.2.6-T3's allow-list) to the user, 401 `refresh_token_reused`. [RULED — README §B10 WT36]
2b. Any **other** revoked row (`logout`, `session_expired`, `session_idle`, `reuse_detected`, `password_reset`, `mfa_change`, `admin_revoke`, `account_not_active`) → 401 `session_revoked`, **no** alert e-mail and no further revocation (stale cookie, not theft); reuse detection never fires for these. [RULED — README §B10 WT36]
3. `expires_at <= now` (absolute per role) or (`Idle` set and `now - last_used_at > Idle`) → revoke family
   (`session_expired` / `session_idle`) → 401 `session_revoked`.
4. otherwise insert the successor row (`family_id` unchanged, `expires_at = min(family_started_at + Absolute, now + Idle ?? Absolute)`,
   `reauthenticated_at`, `reauth_attempts` and `reauth_last_attempt_at` copied (WT32), new `ip`/`user_agent`) and mark the presented row `revoked_at = now`,
   `revoked_reason = 'rotated'`, `replaced_by_id`, `last_used_at = now`.
Two concurrent refreshes with the same cookie serialise on `FOR UPDATE`: the loser sees `revoked_at` set and is treated
as reuse (family revoked) — the intended theft-detection behaviour; the SPA must not refresh in parallel (client note for 10).
`StartSessionAsync` inserts the family's first row (`family_id = Guid.CreateVersion7()`, `expires_at = now + Absolute`, `last_used_at = created_at` — the idle clock starts at creation [RULED — README §B10 WT33]),
returns the plaintext token once; only `HashToken(token)` is stored. `RevokeFamilyAsync` updates all live rows of the
family (`revoked_at`, `revoked_reason`) in one statement, emits `NOTIFY security` with the user id so every Api instance aborts that user's live hub connections (WT37), and writes the outbox event `UserSecurityChanged` →
`user_security_changed.v1` [INFERENCE outbox name] when the caller is a credential event. [RULED — README §B10 WT36, WT37]

**Login / refresh / logout handlers.**
```csharp
public enum LoginOutcome { Tokens, MfaRequired, EnrolmentRequired }
public sealed record LoginResult(LoginOutcome Outcome, IssuedAccessToken? Access, IssuedRefreshSession? Refresh, string? MfaToken);
public sealed record LoginCommand(string Email, string Password, RequestInfo Info) : ICommand<ErrorOr<LoginResult>>, IAllowAnonymousRequest;
public sealed record RefreshCommand(string PresentedToken, RequestInfo Info) : ICommand<ErrorOr<IssuedAccessToken>>, IAllowAnonymousRequest;
public sealed record LogoutCommand(string PresentedToken) : ICommand<ErrorOr<Success>>;
public interface IMfaChallengeService { /* port declared here; 09.3.2-T3 implements it and calls it — no interim implementation, [RULED — README §B10 WT39] */ }
```
`LoginHandler` order: validator (400 `validation_failed`) → `ICredentialVerifier.VerifyAsync` (unknown e-mail and wrong
password → 401 `invalid_credentials`; the dummy hash is 09.3.1-T1's) → `Status != Active` → 401 `session_revoked` →
`!EmailConfirmed` → 403 `email_not_verified` → role `Admin`/`Owner` → 401 `mfa_required` (when `two_factor_enabled = true`) or 401 `mfa_enrolment_required` (false) with **no** `mfaToken` in this task — 09.3.2-T3 edits this same handler to call `IMfaChallengeService.BeginAsync` and add the pre-auth cookie ([RULED — README §B10 WT22, WT39]); while that user's TOTP wrong-code window is exceeded (>= 10 wrong codes in 15 min across all challenges and reauth) `/auth/login` answers 429 `rate_limited` with `Retry-After: 900` ([RULED — README §B10 WT35]) → else
`StartSessionAsync` + `IssueAccessToken(..., AuthMethod.Pwd, ...)` → update `users.last_login_at`, audit
`account_security` (`login.succeeded` / `login.failed` with `data = { reason, emailHash }`, never the address). Every
result also has a latency-equalising path for the "user not found" case (09.3.1-T1).
`RefreshHandler`: verify `Origin` at the endpoint filter (`RequireSameOriginFilter` → 403 `forbidden` on missing/other
origin), `RotateAsync`, then re-check the account from `refresh_tokens.user_id` (one indexed read) before issuing:
`Status != Active` → `RevokeFamilyAsync(familyId, "account_not_active")` + 401 `session_revoked`;
`!EmailConfirmed` → 403 `email_not_verified` **without** revoking (the user can verify and keep the session); otherwise
issue a fresh access token (`AuthMethod.Pwd`, `sid` = family). In P this is the only enforcement point for suspension —
the per-request stamp/status check is S (09.3.2-T2, WF12) — so without it a suspended or unconfirmed account could keep
renewing for the family's whole lifetime (up to 14 days).
`LogoutHandler`: `RevokeFamilyAsync(familyId, "logout")` resolved from the presented token; 204 + cookie cleared
(WF12: logout revokes the **family**). The Api layer (not the handler) sets/clears cookies with `HttpOnly; Secure;
SameSite=Strict; Path=/api/v1/auth` and `Max-Age` = remaining lifetime (`__Secure-nts_rt`, cookie name from config).

## Failure handling and edge cases

- Signing key missing/rotated: startup failure for missing/malformed; a **rotation** is a deploy-time operation
  (the `kid` changes, old tokens stay valid until expiry because validation uses the configured key — two keys are not
  supported until S-phase key rotation; [OPEN] note in plan §10 if the TL wants overlap).
- DB failure: D5 → 503 `service_unavailable`, no partial family row (the whole rotation is one transaction).
- Concurrent refresh (double-click, two tabs): serialised by `FOR UPDATE`; the loser counts as reuse — documented so
  10's client refreshes with a single-flight mutex.
- Clock skew: `ClockSkew = 30 s` is a validation-only tolerance; `expires_at` values are computed from `IClock`.
- Rollback: `_09_RefreshTokens` is expand-only and additive; reverting the app leaves the table unused; deleting rows
  revokes nothing server-side (access tokens are validated statelessly, ≤ 5 min residual, WF12).
- Bounded work: login/refresh run a fixed number of indexed statements (1 lookup + 1 insert/update + 1 audit); no N+1, no listing.
