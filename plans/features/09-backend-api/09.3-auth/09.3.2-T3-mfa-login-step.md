## Goal

After a correct password, `POST /auth/login` answers 401 `mfa_required` with a single-use 5-minute `mfaToken` bound to a
pre-auth cookie and the user agent, and `POST /auth/login/mfa` exchanges that challenge plus a TOTP or recovery code for
the access/refresh tokens; 5 wrong codes revoke the challenge and an IP change is audited, never rejected.

## Design

public sealed class EfMfaChallengeService(IAppDbContext db, ITotpVerifier totp, IRecoveryCodeService recoveryCodes,
    IRefreshTokenService refreshTokens, IEmailSender email, ISecurityAlerter alerter, IClock clock) : IMfaChallengeService
{
    public Task<ErrorOr<MfaChallenge>> BeginAsync(Guid userId, RequestInfo info, CancellationToken ct);

**`auth_challenges` (migration `<yyyyMMddHHmm>_09_AuthChallenges`).**
```sql
CREATE TABLE auth_challenges (
    id                  uuid PRIMARY KEY,
    user_id             uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token_hash          text NOT NULL,
    preauth_cookie_hash text NOT NULL,
    user_agent          text NULL,
    ip                  inet NULL,          -- logged, never enforced (09.3.2 line 2)
    attempts            smallint NOT NULL DEFAULT 0,
    expires_at          timestamptz NOT NULL,
    used_at             timestamptz NULL
);
CREATE UNIQUE INDEX ux_auth_challenges_token_hash ON auth_challenges (token_hash);
CREATE INDEX ix_auth_challenges_user_id_expires_at ON auth_challenges (user_id, expires_at);
```
Configuration: `Attempts` `smallint`, `Ip` `inet`, `ExpiresAt` `timestamptz`, FK cascade to `users`, plus a
`HasCheckConstraint("attempts", "attempts >= 0 AND attempts <= 5")`. Only SHA-256 hex hashes of the two secrets are stored.

**`BeginAsync`** (09.3.2-T3 [RULED — README §B10 WT22, WT39] edits 09.3.2-T1's `LoginHandler` to call this for every `Admin`/`Owner` login, per BD4 "always"; no interim "pending" service exists):
one statement invalidates the user's live challenges (`UPDATE auth_challenges SET used_at = now() WHERE user_id = @u AND
used_at IS NULL`) so at most one challenge exists per user, then inserts a row with a 32-byte base64url `mfaToken`
(only its hash stored), a separate 32-byte `PreAuthCookie`, `user_agent`, `ip`, `expires_at = now + 5 min`
(`Auth:Mfa:ChallengeMinutes`), returns the plaintext pair once.

**`CompleteAsync`** — one transaction (D5), challenge row locked (`SELECT … FOR UPDATE`):
1. row by `token_hash`; absent/`used_at` set/`expires_at <= now`/`attempts >= 5` → 401 `mfa_token_invalid`.
2. `user_agent` differs from the stored value → 401 `mfa_token_invalid` (bound; empty UA never matches a stored UA).
3. `preauth_cookie_hash` compared with `CryptographicOperations.FixedTimeEquals` → mismatch → 401 `mfa_token_invalid`.
4. `ip` differs from the login step → **audited only** (`account_security` `mfa.ip_changed` with old/new hash, never the
   raw addresses in `data`) and the challenge continues (BD4).
5. exactly one of `Code`/`RecoveryCode` present (validator, else 400 `validation_failed`):
   - `Code` → `ITotpVerifier.VerifyAsync(userId, code, TotpSlot.Active, ct)` (09.10.4-T1; [RULED — README §B10 WT31] `Active` slot — only `VerifyMfaCommand` passes `Pending`; replay-safe via `users.last_totp_step` CAS) →
     `ErrorOr<long>`; failure → `invalid_mfa_code`.
   - `RecoveryCode` → `IRecoveryCodeService.RedeemAsync(userId, recoveryCode, ct)` → failure → `invalid_mfa_code`.
6. failure path: `UPDATE auth_challenges SET attempts = attempts + 1 WHERE id = @id`; audit `account_security`
   (`login.mfa_failed`, `data = { attempts }`); for `Admin`/`Owner` the **first** failure also raises `ISecurityAlerter`
   (D9 event); at `attempts = 5` the same statement sets `used_at = now()` so the challenge is dead and the next call
   answers 401 `mfa_token_invalid` (no separate e-mail is queued here — the owner warning is `ISecurityAlerter`'s, S).
7. success path: `used_at = now()`; recovery-code branch additionally `RevokeAllFamiliesAsync(userId, "recovery_code_used", exceptFamilyId: null)`
   (there is no family yet at login), audit `account_security` `login.mfa_succeeded` with `{ method }`, and
   `ISecurityAlerter` for `Admin`/`Owner`; returns `MfaChallengeOutcome(userId, method)`.

**Endpoint (`POST /api/v1/auth/login/mfa`)** then: read the pre-auth cookie, `CompleteAsync`, issue tokens through
`ITokenIssuer.IssueAccessToken(user, familyId, outcome.Method, now)` + `IRefreshTokenService.StartSessionAsync(user, info)`
(cookie set by the Api layer, same attributes as 09.3.2-T1), update `users.last_login_at`, audit `login.succeeded`.
The endpoint is `AllowAnonymous` + `RequireRateLimiting("auth")` and requires no `Idempotency-Key` (D6 lists this as an
auth route, not a paid/platform POST).

## Failure handling and edge cases

- Replay of a `mfaToken` after success → `used_at` guard → 401 `mfa_token_invalid`; a stolen pre-auth cookie alone is
  useless without the TOTP code.
- Two parallel completions with the same `mfaToken`: the row lock serialises them; the loser sees `used_at` set → 401.
- Recovery code presented as `code` (or TOTP as `recoveryCode`): TOTP validation fails first; the validator keeps the two
  fields mutually exclusive so a caller cannot brute-force both in one request.
- `attempts` never exceeds 5 (DB CHECK) even if two requests race.
- `user deleted` between the password step and the MFA step → FK cascade deletes the challenge → 401 `mfa_token_invalid`.
- Rollback: expand-only migration; reverting the app leaves orphan rows that expire by `expires_at`.
- Bounded work: `Begin` = one update + one insert; `Complete` = one locked select + one update (+ at most one TOTP CAS);
  no listing, no N+1.
