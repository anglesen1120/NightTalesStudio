## Goal

`POST /auth/forgot-password` always answers 202 with the same body and timing budget, an existing user receives a
60-minute single-use reset link whose token travels only in the URL fragment, and `POST /auth/reset-password` changes the
password, revokes **all** refresh-token families, rotates the security stamp and e-mails the user.

## Design

```csharp
public enum UserActionKind { PasswordReset, EmailVerify, PublicationCancel }   // BD3 kinds; PublicationCancel (TTL = until veto end / upload start) added by 06.2.2-T2 (06 CR-6)

public interface IUserActionTokenService
{
    Task<ErrorOr<string>> IssueAsync(Guid userId, UserActionKind kind, RequestInfo info, CancellationToken ct);
    // 06 CR-6 / YR8: subject-scoped overload for PublicationCancel — column `subject_id uuid NULL`, explicit expiry,
    // invalidation limited to (user, kind, subject_id); ConsumeAsync returns the subject for the caller to compare.
    Task<ErrorOr<string>> IssueAsync(Guid userId, UserActionKind kind, Guid subjectId, DateTimeOffset expiresAt, RequestInfo info, CancellationToken ct);
    Task<ErrorOr<Guid>> ConsumeAsync(string token, UserActionKind kind, CancellationToken ct);
}

public sealed record UserActionTokenOptions
{
    public TimeSpan PasswordResetTtl { get; init; } = TimeSpan.FromMinutes(60);   // BD3
    public TimeSpan EmailVerifyTtl { get; init; }   = TimeSpan.FromHours(24);     // BD3, consumed by 09.3.1-T3
}
```
[RULED — README §B10 WT17, WT30] `IssueAsync` is called **only at send time**, from 09.2.6-T3's `PasswordResetTokenMinter` inside `SendEmailJob` — never from the request path; the request queues ids and token-free params, `link` is **not** an allow-listed `params` key, and neither the outbox payload nor `email_messages.params` ever holds a token. `EfUserActionTokenService.IssueAsync`: 32 cryptographic random bytes → base64url plaintext returned **once**; only
`HashToken(token)` (SHA-256 hex, from 09.3.2-T1's `ITokenIssuer`) is stored, `expires_at = now + ttl(kind)`; the same
statement invalidates the user's previous unused tokens of that kind (`UPDATE … SET used_at = now() WHERE user_id = @u
AND kind = @k AND used_at IS NULL`) so at most one live token exists per `(user, kind)` — this is what makes
"resend" and "forgot again" invalidate the older mail.
`ConsumeAsync` is a single replay-proof round trip:
```sql
UPDATE user_action_tokens SET used_at = now()
WHERE token_hash = @hash AND kind = @kind AND used_at IS NULL AND expires_at > now()
RETURNING user_id
```
zero rows → `Error.Validation(ErrorCodes.ValidationFailed)` (09 §4: a used or expired token is `validation_failed`, 400).

**`user_action_tokens` (migration `<yyyyMMddHHmm>_09_UserActionTokens`).**
```sql
CREATE TABLE user_action_tokens (
    id         uuid PRIMARY KEY,
    user_id    uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    kind       text NOT NULL CHECK (kind IN ('password_reset','email_verify')),
    token_hash text NOT NULL,
    created_at timestamptz NOT NULL,
    expires_at timestamptz NOT NULL,
    used_at    timestamptz NULL
);
CREATE UNIQUE INDEX ux_user_action_tokens_token_hash ON user_action_tokens (token_hash);
CREATE INDEX ix_user_action_tokens_user_id_kind ON user_action_tokens (user_id, kind);
```
`UserActionTokenConfiguration`: `Kind` uses `HasEnumCheck<UserActionKind>(…)` (D8: snake_case `text` + closed `CHECK`; no second enum converter),
`CreatedAt`/`ExpiresAt`/`UsedAt` `timestamptz`, FK cascade to `users` (a deleted user's links die with the account).

**Handlers.**
```csharp
public sealed record ForgotPasswordCommand(string Email) : ICommand<ErrorOr<Success>>, IAllowAnonymousRequest;
public sealed record ResetPasswordCommand(string Token, string NewPassword) : ICommand<ErrorOr<Success>>, IAllowAnonymousRequest;
public static class AuthLinks
{
    public static string PasswordReset(Uri origin, string token) => $"{origin.GetLeftPart(UriPartial.Authority)}/reset-password#t={token}";
    public static string VerifyEmail(Uri origin, string token)   => $"{origin.GetLeftPart(UriPartial.Authority)}/verify-email#t={token}";
}
```
`ForgotPasswordHandler`: validate the e-mail shape (400 `validation_failed`), look the user up by normalized e-mail
through `IReadDb`; if found and `Status == Active` → [RULED — README §B10 WT17, WT30] queue through `IEmailSender` with ids and token-free params only (no `IssueAsync` on this path — the token row is created by the reset minter inside `SendEmailJob`) and
`IEmailSender.QueueAsync(new EmailMessage(userId, "password_reset", ToLanguage(user.UiLocale),
new Dictionary<string, string> { ["displayName"] = displayName, ["expiresMinutes"] = "60" }))`
→ `ErrorOr<Guid>` (the `email_messages` id; record + catalog at `09.2.6-T3-email-pipeline.md:21-24`, `:80`). [RULED — README §B10 WT30] A queue failure
is **swallowed for the response** — the endpoint answers the identical 202 no matter what, otherwise the error would
betray whether the account exists and whether a mail went out — but it is never silent operationally: it is logged with
the template name and a hash of the user id (never the token, never the address) and counted in
`auth_action_token_total{kind="password_reset",result="enqueue_failed"}`; otherwise the same
amount of work (a dummy `IssueAsync`-equivalent hash computation) and **no** e-mail; always `ErrorOr.Success` → 202
`{ }` with no body variation, so neither the status, the body nor the timing reveals existence (BD16) — both paths are padded to a fixed floor of 300 ms plus jitter <= 50 ms ([RULED — README §B10 WT40]). Tokens, the
e-mail address and the IP are never logged; audit rows are written for the *request* only as
`account_security` `account.password_reset_requested` with `data = { emailHash }` (never the address).

`ResetPasswordHandler` (one UnitOfWork transaction, D5):
1. `IPasswordPolicy.ValidateAsync(newPassword)` → 400 `breached_password` (09.3.1-T1's checker, first 5 SHA-1 hex only).
2. `ConsumeAsync(token, PasswordReset)` → 400 `validation_failed`.
3. Load the user; `Status != Active` → the same 400 `validation_failed` (never "suspended").
4. `UserManager.RemovePasswordAsync(user)` then `UserManager.AddPasswordAsync(user, newPassword)`; any Identity failure
   → 400 `validation_failed` with a safe description (never the password).
5. Call `ISecurityEventWriter.RotateStampAsync(userId, "password_reset", ct)` (09.3.2-T2, D9, 09 W3 CR-20) —
   stamp rotation, the `UserSecurityChanged` outbox row and the SignalR abort happen in one call, inside the same
   transaction (D11), instead of assigning `user.SecurityStamp` inline.
6. `IRefreshTokenService.RevokeAllFamiliesAsync(userId, "password_reset", exceptFamilyId: null)` → every family dies
   (WF12, 09 §4 story 09.3.3).
7. Audit `account_security` `account.password_reset` (BD15) and `ISecurityAlerter.AlertAsync` (owner/admin accounts only).
8. `IEmailSender.QueueAsync(new EmailMessage(userId, "password_changed", ToLanguage(user.UiLocale),
   new Dictionary<string, string> { ["displayName"] = displayName, ["occurredAt"] = now.ToString("O") }))` →
   `ErrorOr<Guid>` — the "your password changed" notice (template + params registered by 09.2.6-T3:83; token-free, so
   the stored row keeps nothing sensitive).
9. 204 (no body; the SPA signs in again).

The reset link is only ever built server-side from `App:PublicOrigin` and the token is placed **after the `#`**, so it
never reaches a server access log, a proxy log or the `Referer` header (BD3/WF11); `Referrer-Policy: no-referrer`
(09.9.4-T1) is the second layer.

## Steps

1. Add `UserActionKind`, `IUserActionTokenService`, `UserActionTokenOptions`, `AuthLinks`.
2. Implement `EfUserActionTokenService` (issue with invalidation, consume by `UPDATE … RETURNING`); register it.
3. Add the `UserActionToken` entity + configuration; generate and review `_09UserActionTokens` (unique hash index,
   kind CHECK, FK cascade).
4. Implement `ForgotPasswordHandler`, `ResetPasswordHandler` and their validators; wire the `password_changed`
   notice and the `UserActionKind.EmailVerify` TTL contract used by 09.3.1-T3. The reset token is minted inside 09.2.6-T3's `SendEmailJob` (`PasswordResetTokenMinter` → `IUserActionTokenService.IssueAsync`), so the message carries the user id and kind only and the forgot path never inserts a `user_action_tokens` row itself ([RULED — README §B10 WT17, WT30]).
5. Map `POST /api/v1/auth/forgot-password` (202, `RequireRateLimiting("auth")`, `AllowAnonymous`) and
   `POST /api/v1/auth/reset-password` (204, no `Idempotency-Key` required — D6 does not require one on auth routes).
6. Both templates are registered by 09.2.6-T3 (`09.2.6-T3-email-pipeline.md:80,83`): `password_reset`
   (`displayName`, `expiresMinutes` — `link` is minted at send time, [RULED — README §B10 WT17, WT30]) and `password_changed` (`displayName`, `occurredAt`, token-free); a param
   outside the allow-list is `Error.Validation("email_template_keys")` (`link` is **not** allow-listed for `password_reset` — the minter fills it at send time, [RULED — README §B10 WT17, WT30]) and an unknown template
   `Error.Validation("email_template_unknown")`.
7. Add the tests below.

## Failure handling and edge cases

- Unknown e-mail / inactive user: identical response, no mail, no audit row that differentiates (`emailHash` only).
- Mail dispatch failure after 202: the outbox row is in the same transaction (D11), so the user keeps a valid link even
  if delivery retries; a dead-lettered mail is 09.2.6-T3's alert.
- Reset of the last active owner: permitted here (the reset link goes to the owner mailbox) — the 09.10.4 recharge/owner
  action rules do not veto a self-service reset; the security alert fires.
- Race between two resets: `ConsumeAsync`'s `UPDATE … RETURNING` serialises them; the loser gets 400 `validation_failed`.
- Breached-password fail-closed behaviour is 09.3.1-T1's (503 `service_unavailable` in `range` mode).
- Rollback: expand-only migration; reverting the app leaves unexpired links that simply stop working (the endpoint is gone).
- Bounded work: forgot = one indexed user lookup + one invalidating update + one insert + one outbox write;
  reset = one consume + one user update + one family update. No listing, no N+1.

## Notes

- E-mail contract (09.2.6-T3, aligned with its owner): `QueueAsync(EmailMessage) → ErrorOr<Guid>`; never send inline and
  never touch SMTP; the locale is the account's `ui_locale` (`Language { Vi, En }`, D16); `email_messages.params` is
  emptied once the row reaches `sent`, and the raw token appears only in the link value — never in audit `data`, logs or
  `IEmailDeliveryStatus` (BD9/BD16).
- [RULED — README §B10 WT17, WT30, WT40] Reset tokens are minted at send time by 09.2.6-T3's `PasswordResetTokenMinter` inside `SendEmailJob`; this task queues ids only, `link` is not an allow-listed param, and the forgot-password response is padded to a 300 ms floor plus jitter <= 50 ms on both paths.
- Brute-force protection (per account+IP failure counting, `captcha_required`, progressive `429` delays) is
  **09.3.3-T2/T3 (S)**; this task only applies the `auth` rate limit policy owned by 09.3.5-T1 (BD14) — no hard edge in B8.1.
- ⚠️ [OPEN] `09.3.1-T3` (S) consumes the `email_verify` kind defined here; B8.1 has no edge for it (plan §10 Open items).
- [INFERENCE] the `user_security_changed.v1` outbox name; the story only names the `UserSecurityChanged` event.
- [`NotAudited`] The `ConsumeAsync` failure path returns before any write, so no audit row is produced for a rejected
  token (deliberate: it would be a free oracle for token guessing).
