## Goal

An abusive caller meets a wall before the work is done: credential stuffing against `/auth/*` is capped per IP, cost-incurring POSTs per user, and hub ticket minting per user; every rejection is a 429 `rate_limited` `ProblemDetails` with a `Retry-After`, and the IP the limiter uses is trustworthy because a forwarded header counts only when it comes from the load balancer.

## Design

```csharp
// Api/RateLimiting/
public static class RateLimitPolicies { public const string Auth = "auth"; public const string Paid = "paid"; public const string Hub = "hub"; public const string Anon = "anon"; }   // W3 CR-7

public interface IClientIpResolver { IPAddress Resolve(HttpContext context); }

public sealed class ClientIpResolver : IClientIpResolver          // after UseForwardedHeaders
{
    private readonly ForwardedHeadersOptions _options;
    public IPAddress Resolve(HttpContext context) =>
        context.Connection.RemoteIpAddress ?? throw new InvalidOperationException("no remote address");   // Kestrel always sets it
}

public static class RateLimitPartitionKeys
{
    public static string Ip(HttpContext ctx, IClientIpResolver ip) => $"ip:{Hash(ip.Resolve(ctx))}";
    public static string User(HttpContext ctx) =>
        ctx.User.FindFirst("sub")?.Value is { Length: > 0 } sub ? $"user:{sub}" : $"anon:{Hash(ctx.Connection.RemoteIpAddress!)}";
}
```

```csharp
services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    options.OnRejected = RateLimitRejection.WriteAsync;                                          // ProblemDetails + Retry-After
    options.AddPolicy(RateLimitPolicies.Auth, ctx => RateLimitPartition.GetFixedWindowLimiter(
        RateLimitPartitionKeys.Ip(ctx, ip), _ => AuthOptions()));
    options.AddPolicy(RateLimitPolicies.Paid, ctx => RateLimitPartition.GetSlidingWindowLimiter(
        RateLimitPartitionKeys.User(ctx), _ => PaidOptions()));
    options.AddPolicy(RateLimitPolicies.Hub, ctx => RateLimitPartition.GetFixedWindowLimiter(
        RateLimitPartitionKeys.User(ctx), _ => HubOptions()));
    options.AddPolicy(RateLimitPolicies.Anon, ctx => RateLimitPartition.GetFixedWindowLimiter(
        RateLimitPartitionKeys.Ip(ctx, ip), _ => AnonOptions()));                                // W3 CR-7
});
```

- Options come from config with the BD14 defaults: `RateLimiting:Auth:{PermitLimit=10, WindowSeconds=60}`, `RateLimiting:Paid:{PermitLimit=30, WindowSeconds=60, SegmentsPerWindow=6}`, `RateLimiting:Hub:{PermitLimit=10, WindowSeconds=60}`, `RateLimiting:Anon:{PermitLimit=60, WindowSeconds=60}` (per resolved IP, fixed window; W3 CR-7); every limiter gets `QueueLimit = 0`, `AutoReplenishment = true`.
- `RateLimitRejection.WriteAsync(OnRejectedContext ctx, CancellationToken ct)`: status 429, D7 `ProblemDetails` (`type` = `https://nighttales.app/errors/rate_limited` ⚠️ placeholder host, `title`, `code` = `rate_limited`, `traceId`, `retryAfterSeconds` = the policy's `RetryAfterSeconds`), plus the `Retry-After` header (D7/L424). `OnRejected` exposes no reset instant (W8 ⚠️), so the value is the policy window (`RateLimiting:RetryAfterSeconds`, default 60) — never a computed or negative remainder. The body is written once and the delegate never throws (a throw here would surface as a 500): the policy name is read from a small `ConcurrentDictionary<string, int>` populated at registration.
- Forwarded headers: `app.UseForwardedHeaders(new ForwardedHeadersOptions { ForwardedHeaders = XForwardedFor | XForwardedProto, ForwardLimit = 1, KnownNetworks = …, KnownProxies = … })`. **`XForwardedHost` is never trusted** (host-header injection) [DECISION]. `KnownNetworks`/`KnownProxies` are parsed from `Http:ForwardedHeaders:KnownNetworks` / `:KnownProxies` (CommaSeparated CIDR/IP list): empty in Production/Staging ⇒ forwarded headers are ignored and the peer IP is used (fail closed); Development defaults to `127.0.0.1/32, ::1/128`. The list is validated at startup (an unparseable CIDR fails boot).
- Middleware order: `UseForwardedHeaders` → `UseSerilogRequestLogging` → `UseAuthentication` → `UseRateLimiter` → endpoints. The user-keyed policies need `sub`, so the limiter must run after authentication; `/health/live`, `/health/ready` and the generated `openapi` route are excluded by mapping them on a group without a policy (they are cheap, cache-only reads, BD16).
- Mounting (one line per owning group, no duplication of numbers): `auth` on the `/api/v1/auth` group of 09.3.2-T1; `paid` on 02's cost-incurring POSTs (02.2.2-T2), 09.6.1-T1's `POST /episodes/{id}/render` and 06's publish POSTs; `hub` on 09.8.1-T2's `POST /hubs/ticket`; `anon` on `POST /auth/register` (09.3.1-T3, S), `POST /reports` (13, S) and `POST /security/cancel-links/{kind}/{id}` (09.10.8-T1, S) — each owning task applies its own `RequireRateLimiting(RateLimitPolicies.Anon)` (W3 CR-7).
- Observability: `rate_limit_rejections_total{policy}` and one structured log per rejection carrying the policy and the **hashed** partition key — never a raw IP or user id (BD16).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| A partition key is unbounded (every IP is a key) | keys are per resolved IP; the IP can only vary if the client controls it, which requires coming from inside a trusted CIDR [DECISION]. [RULED — README §B10 WT48] **No `MaxPartitions` claim**: step 1 confirms the built-in idle-partition cleanup of the rate limiter used on .NET 10 (⚠️ verify against the actual API at implementation); if that cleanup is absent, a size-limited store with idle expiry wraps the limiter instead of an assumed config key |
| The peer is a proxy inside the LB CIDR claiming many hops | `ForwardLimit = 1` takes exactly one hop, so a client-supplied chain cannot mint buckets |
| Health checks / probes | no policy; they are cache-only reads (BD16) and must never be rate limited by a shared IP (a probe fleet shares an IP) |
| Legitimate shared NAT exceeds 10 logins/min | the client gets a 429 with `Retry-After`; the counter for CAPTCHA/progressive delay (09.3.3) is separate and per (account, IP) |
| `RateLimiting:Enabled=false` during an incident | policies are not registered, no 429; the consequence is documented in the rollout section and reverted by redeploying config |
| `OnRejected` runs before authentication for some route | impossible by the middleware order; a user-keyed policy still falls back to `anon:<iphash>` if `sub` is missing |
| A rejected request must not consume quota elsewhere | the limiter runs before endpoints and before any UnitOfWork, so no transaction, no idempotency key and no audit row is created |

## Notes

- [RULED — README §B10 WT48] Partition storage relies on the rate limiter's built-in idle-partition cleanup (confirmed in step 1, ⚠️ implementation-time check against the real API); `RateLimiting:MaxPartitions` is **not** a supported option and is not claimed — if the cleanup is missing, a size-limited store with idle expiry wraps the limiter.
- [RULED — README §B10 WT48] **Step-1 finding, confirmed against the .NET 10 API at implementation time** (`System.Threading.RateLimiting`, `DefaultPartitionedRateLimiter.cs`): the built-in idle-partition cleanup exists. The store's heartbeat (`TimerAwaitable`, 100 ms) evicts every partition whose limiter reports an idle duration longer than `s_idleTimeLimit = 10 s`, and removes the key from the lookup table, so the next request for that key runs the partition factory again. A partition that is never idle keeps its limiter (a `FixedWindowRateLimiter` reports an idle duration only once its window has replenished). The `Enabled = false` pass-through is a `NoopLimiter`, whose idle duration is always null and which is therefore evicted 10 s after its last access, through the entry's own timestamp. Consequence: the framework's own partition store is kept, no size-limited store is wrapped around it, and `RateLimiting:MaxPartitions` stays a non-option. Evidence: `RateLimitTests.IdlePartitions_AreReclaimed_OrStoreIsSizeLimited` observes the partition factory run a second time for the same key after the idle period.
- **One-liner for the other policy owners (step 4)** — name the registered policy, never define a second one: `.RequireRateLimiting(RateLimitPolicies.Paid)` on the cost-incurring POSTs (02.2.2-T2, 09.6.1-T1's `POST /episodes/{id}/render`, 06's publish POSTs); `.RequireRateLimiting(RateLimitPolicies.Anon)` on `POST /auth/register` (09.3.1-T3), `POST /reports` (13) and `POST /security/cancel-links/{kind}/{id}` (09.10.8-T1); `.RequireRateLimiting(RateLimitPolicies.Hub)` on `POST /hubs/ticket` (09.8.1-T2). 02.2.2-T2 applies its own. The `/api/v1/auth` group already carries `auth` (`AuthEndpoints.AuthRateLimitPolicy`, 09.3.2-T1).
- Process deviation of the first implementation pass: it discovered code on the filesystem (ls, ranged reads, grep) and never used the codebase-memory graph, as the shared contract requires. Its findings were re-grounded here against the .NET 10 and ASP.NET Core 10 sources named above, and this pass used the graph for the endpoint/route/host discovery.
- The numbers live in config with the BD14 defaults as the shipped values; changing a limit is a config edit, not a code edit.

- The 429 shape is shared with 09.3.3's progressive delay; that task reuses `RateLimitRejection` (and may set `Retry-After` to the progressive value) instead of writing a second body.
- [DECISION — SEC-0935-02, review of the first pass] BD14's "per resolved IP" is per IPv4 address and per IPv6 **prefix**, not per full IPv6 address: an IPv6 subscriber controls a whole /64, so keying all 128 bits would hand it a fresh budget for every interface address it rotates — a bypass needing no forwarded header. `RateLimiting:Ipv6PrefixLength` (default 64, validated 32..128 at start-up) is the prefix an address-keyed partition — and the user-keyed `anon:` fallback — keeps; IPv4-mapped IPv6 still collapses to the IPv4 address, so one client over either family shares one bucket.
- [DECISION — SEC-0935-01, review of the first pass] An empty `Http:ForwardedHeaders` configuration is fail-closed by construction: when both trust lists are empty after configuration, the options are set to `ForwardedHeaders.None`, because ASP.NET Core's `ForwardedHeadersMiddleware` reads two empty lists as "check no sender" and would believe every peer's `X-Forwarded-For`/`X-Forwarded-Proto`. Development's loopback lists keep the local-proxy simulation working, and a configured list keeps the strict sender check.
- [PERF-P1/P2, review of the first pass] The partition key is SHA-256 hashed over spans (stack, with a pooled fallback for a subject longer than the stack bound) and formatted straight into the prefixed key string; the computed key is parked on `HttpContext.Items` so the rejection path logs it instead of re-hashing the address; and the per-policy limiter-options factory is built once at setup and still yields a fresh mutable options instance per partition.
