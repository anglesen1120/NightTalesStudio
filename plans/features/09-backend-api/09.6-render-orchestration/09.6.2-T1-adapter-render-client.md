## Goal

One type-safe way to talk to a node's `mpt-adapter` over `render-node.v1` (05 D4) that survives node hiccups without failing jobs: two clients with deliberately different resilience (BD6, WF08), a complete adapter-error mapping, and contract tests that fail when the adapter's wire shape drifts (fixtures from 05.4.1-T2).

## Design

**Implementation.** `MptRenderClient` and `RenderDownloadClient` (Infrastructure `Rendering/`) obtain their `HttpClient` from **`RenderNodeConnectionFactory`** (11.3.3-T1), which owns the base address (node `BaseUrl`), the per-node `x-api-key` and the pinned certificate (constant-time `CryptographicOperations.FixedTimeEquals` against the node's TLS cert SHA-256, 05 D4/11 D13). Bodies and responses are serialised with `RenderNodeJson.Tolerant` (11 D4/D13), so an unknown field from a newer adapter is ignored in production — the strict profile is used only by the fixture tests below.

**Resilience (BD6 — custom, never `AddStandardResilienceHandler`, W9).**

```csharp
// Infrastructure/Rendering/RenderClientResilience.cs
services.AddHttpClient<MptRenderClient>(...)
        .AddResilienceHandler("render-node", b => {
            b.AddTimeout(TimeSpan.FromSeconds(cfg.Render.Client.TotalSeconds));        // 30 — total
            b.AddRetry(new HttpRetryStrategyOptions {
                MaxRetryAttempts = cfg.Render.Client.MaxRetries,                        // 3
                BackoffType = DelayBackoffType.Exponential,
                UseJitter = true,
                ShouldHandle = args => ValueTask.FromResult(
                    args.Outcome.Exception is not OperationCanceledException              // cancellation is never retried
                    && args.Outcome.Result?.RequestMessage?.Method != HttpMethod.Delete    // DELETE is not idempotent
                    && (args.Outcome.Exception is not null                               // transport error
                        || args.Outcome.Result!.StatusCode is HttpStatusCode.RequestTimeout
                            or HttpStatusCode.ServiceUnavailable or >= HttpStatusCode.InternalServerError))
                    // 429 (`adapter_capacity_full`) is deliberately NOT handled here: BD6/11 T6 make it a `Deferred`
                    // carrying the adapter's `Retry-After: 30`, which would outlive the 30 s total timeout anyway.
            });
            b.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions {
                SamplingDuration = TimeSpan.FromSeconds(60),
                MinimumThroughput = 5,                    // opens on 5 consecutive failures at P volume
                FailureRatio = 1.0,
                BreakDuration = TimeSpan.FromSeconds(30)
            });
            b.AddTimeout(TimeSpan.FromSeconds(cfg.Render.Client.AttemptSeconds));       // 10 — attempt
        });
```

- Retried calls: `GET /v1/renders/{task_id}` (read), `POST /v1/renders` (idempotent by `render_job_id` + body sha256, 05 D4), `POST /v1/renders/{task_id}/cancel` (202/200 no-op, 05 D4).
- `DeleteAsync` runs on a **second named client** (`render-node-no-retry`: same connection factory, timeout + breaker, **no retry handler**). A transport failure has no `RequestMessage`, so no pipeline predicate can reliably identify a `DELETE` — routing the call is the only correct guard, and the retry predicate above covers only status-based outcomes.
- `RenderDownloadClient` uses a **separate** named client with **no** resilience handler: `HttpCompletionOption.ResponseHeadersRead`, `AllowAutoRedirect = false`, `Timeout = InfiniteTimeSpan`, an idle timer of `Render:Download.IdleSeconds` = 60 s (a stall aborts the read), and a total budget of `Render:DownloadMaxMinutes` = 20 that must not kill a legitimate large file (WF08).

**Streamed download with incremental hash and caps.**

```csharp
public async Task<ErrorOr<DownloadResult>> DownloadAsync(WorkerNode node, string taskId, RenderOutputKind kind,
    Stream destination, long maxBytes, CancellationToken ct)
{
    using var hasher = IncrementalHash.CreateHash(HashAlgorithmName.SHA256);   // never buffers the file
    // GET {BaseUrl}/v1/renders/{taskId}/{video|subtitles}; require the expected Content-Type
    // (video/mp4 or application/x-subrip); reject Content-Length > maxBytes before reading;
    // read in 80 KiB chunks, hasher.AppendData per chunk, stop with render_output_invalid past maxBytes.
}
```

Caps: `Render:MaxVideoBytes` = 2 GiB, `Render:MaxSubtitleBytes` = 2 MiB (BD6). The result carries `Bytes`, `Sha256` and `ContentType`; the ingest (09.6.3-T2) compares `Sha256` with `output.video.sha256` and the bytes with `output.video.bytes`.

**Adapter error mapping (BD6 + 05 D4/D5).**

| Adapter code / status | Mapping | Consequence |
|---|---|---|
| `adapter_capacity_full` 429 + `Retry-After: 30` | `Deferred(retryAfter: header)` | 09.6.3-T1 reschedules `SubmitRenderJob`, no retry budget spent (11 T6) |
| `adapter_node_unhealthy` 503 | `Deferred(RetryNodes:HealthPollSeconds)` | pick another node later |
| `adapter_task_unknown` 404 on a **submitted** task | `TerminalFailure("render_lost")` | retryable by `RenderRetryPolicy` (05 D5) |
| `adapter_output_not_ready` 409 | `OutputNotReady` | transient: the ingest job retries the download |
| `adapter_output_absent` 404 (subtitles) | `OutputAbsent` | **not** an error: no subtitle asset is written |
| `adapter_task_busy` 409 (`DELETE`) | `Deferred(30 s)` | cleanup retried later |
| `adapter_contract_violation` 400 | `TerminalFailure("render_node_error", alert: true)` | never retried (a bug on either side) |
| `adapter_idempotency_conflict` 409 / `adapter_body_too_large` 413 / `adapter_unauthorized` 401 / `adapter_route_not_found` 404 | `TerminalFailure("render_node_error", alert: true)` | never retried; alerts (key rotation, contract drift) |
| 5xx / timeout / transport error after the pipeline | `TransientFailure("render_node_error")` | transient per 05 D5 (may go to another node) |
| any unknown code | `TerminalFailure("render_node_error", alert: true, detail: code)` | fail closed, never silently swallowed |

Messages are the adapter's fixed sentences only (05 D4 S4); the mapping never copies a raw MPT error text into `render_jobs.error_message` (≤ 2,000 chars, safe text, D8/BD16).

**Metrics:** this task registers **no** instrument of its own. `render_dispatch_unavailable_total` stays 11.3.3-T2's (incremented on the failed pick, never here); `render_jobs_active`, `render_duration_seconds{stage,outcome}` and `render_retries_total{code}` are emitted by 09.6.3-T1/09.6.3-T2 from the same meter (09.9.3-T1 owns the pipeline).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Node returns 401 (rotated key) | `render_node_error` non-retryable + alert; the job is not stuck (the operator updates `worker_nodes`); the key is never logged |
| Adapter answers 200 with an unparsable body | `render_node_error`, alert, non-retryable (contract drift, not a transient fault) |
| `Retry-After` missing on 429 | default `Deferred(30 s)`; the value is clamped to ≤ 300 s |
| Very large video | streamed to the caller's `Stream` (a temp file in the ingest); the client never allocates the file |
| Subtitles absent on a successful task | `OutputAbsent`; the ingest writes the video asset only and the evaluator's `subtitles_present` check decides (05 D10) |
| Transport error during a download mid-stream | the caller's partial temp file is discarded in its `finally`; the ingest job retries from scratch (idempotent by sha256) |
| Rollback | revert the DI registrations and the two client classes; no schema, no data migration; 09.6.3 fails fast at startup if `IRenderClient` is missing |

## Notes

- **Security:** the node key is read from the sealed `WorkerNode` aggregate (11.3.3-T1) and injected per request; TLS is pinned per node (05 D4, D15 S1); redirects are off so a node cannot bounce the Worker to another host; caps are enforced before and during the read; no story text, prompt or token is ever logged (BD16).
- **Performance:** requests are bounded (attempt 10 s / total 30 s), retries are jittered, the CB is bounded by throughput, downloads stream (no buffering) and the hash is incremental; the two clients share one connection factory but not one pipeline, so a slow download cannot trip the API-facing breaker (WF08).
- **Code reuse:** `WorkerNode` (11.3.3-T1), `RenderNodeConnectionFactory` (11.3.3-T1), `NightTales.RenderNode.Contract` types + `RenderNodeJson` (11 D4/D13), `AdapterSubmitRequestV1` from `RenderSubmitMapper.BuildSubmit` (05.1.2-T1) — no wire DTO is redefined here.
- **Hard gate:** 05.4.1-T2 must be closed before this task starts (05 CR-3): the fixture set and `render-node.v1` are frozen there. `05.1.2-T1` supplies `AdapterSubmitRequestV1` and the mapper.

4. Named clients `render-node` (retrying) and `render-node-no-retry` (DELETE); Polly via `AddResiliencePipeline<string, AdapterCallResult>`; `RenderDownloadClient` takes `IRenderNodeConnectionFactory` directly.
5. The connection factory client is built once per logical call, before the pipeline. A build failure (missing pin or key, non-https) is terminal alert `render_node_error` with detail `render_node_misconfigured`: never retried, never counted by the breaker.
6. TLS pin or auth failure (`AuthenticationException` anywhere in the inner chain) is terminal alert `render_node_tls_failure`, not retried.
7. Mapper order: transport/timeout transient; 3xx terminal; adapter code honoured only on its documented status; then status class (408 and >=500 transient; 429 deferred); then fail-closed terminal alert. Detail carries an adapter code only when it matches `^[a-z][a-z_]{0,63}$` (`AdapterErrorMapper.IsSafeCode`).
8. Retry-After: floor 1 s, default 30 s, clamp 300 s. An explicit `Retry-After: 0` never gives a zero wait.
9. `GetStatus` fails closed when the node answers for another task id (terminal alert, detail `render_task_mismatch`).
10. Answer body cap 64 KiB with Content-Length precheck; cancel/delete 2xx bodies are not read; download chunk 64 KiB; the idle timer is disarmed during the destination write; the destination write is bounded only by the caller's token (documented ruling); any destination exception (including OperationCanceledException) is rethrown unchanged, never mapped to a node failure.
11. Node `state` is logged only when it matches `^[a-z_]{1,32}$`, else `invalid`.
12. Extra detail codes [INFERENCE]: `render_task_id_invalid`, `render_download_cap_invalid`, `render_output_content_type_mismatch`, `render_output_too_large`, `render_output_sha256_mismatch`, `render_node_misconfigured`, `render_node_tls_failure`, `render_task_mismatch`. 09.6.1-T1 catalogues them (H4).
