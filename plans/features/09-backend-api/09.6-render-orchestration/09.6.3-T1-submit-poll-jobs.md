## Goal

Render work runs as small idempotent jobs: dispatch picks a node with free capacity and survives "no capacity" without burning retries, a 10 s background poller (not Hangfire `Schedule`, WF07/W12) advances every active job, terminal states run the 03.4.2-T1 order, and only transient codes are auto-retried (≤ 2, a new row per attempt).

**`PollRenderJob` step order.** 1) load job (skip when terminal). 2) `IRenderClient.GetStatusAsync`. 3) `Deferred` → `next_poll_at = now + Render:PollSeconds`. 4) `UpdateProgress(status.stage, status.percent, now)` if changed → `IRealtimeNotifier.NotifyAsync(userId, new RealtimeEvent(RealtimeEventName.RenderProgress, RealtimeIds(EpisodeId, RenderJobId), new RealtimeData(Stage, Percent)), ct)` inside the same transaction (BD7/BD11) — `RealtimeData` carries **only** `stage` and `percent` (0–100) and the NOTIFY body stays ≤ 8 KB [RULED — README §B10 WT54]. 5) `Failed` → 03.4.2-T1 order (`RecordImageUsage` → `Classify` → fail **or** ingest) then `RenderRetryPolicy`; a terminal `failed` refunds `reservationId` once and raises `RenderFailed { EpisodeId, RenderJobId, ErrorCode, Attempt, Final }` with `Final = !ShouldRetry(...)` [RULED — README §B10 WT28/WT50]. 5b) adapter `cancelled` → `job.Cancel(now)` + `Episode.RenderFailed(now)` + `RefundAsync(renderJob.ReservationId, reason)` **once, here** (never in the `DELETE` request) [RULED — README §B10 WT51/WT50]; an adapter answer of `succeeded` on a `cancel_requested_at` job is **not** cancelled — it goes through the normal ingest and is settled (terminal state wins, WT51). 6) still non-terminal → `next_poll_at = now + Render:PollSeconds`. 7) `now − submitted_at > Render:MaxMinutes` (60) → `render_timeout` (never re-submit the same adapter task, 05 D15 P7); the guard is skipped while `submitted_at` is null (the job is still `queued`, 11 D20 H14 owns that alarm).

**Stage/percent.** The adapter's `stage` text is stored verbatim in `render_jobs.stage`; `RenderStage { Queued, Voice, Subtitles, Images, Assembling, Checking, Done }` [INFERENCE: enum name] exists only for the realtime payload and the `render_duration_seconds{stage}` label. `percent` comes from the adapter (05 D4) and `UpdateProgress` refuses a decrease.

**Hook points 03.4.2-T1 edits** (already reserved in the plan, no re-design): `RecordImageUsage.ExecuteAsync(renderJob, report, ct)` (own transaction, idempotent per render job), `ImageOutcomeClassifier.Classify(...)`, `ImageModerationRecorder`, `image_report_invalid_total`, and the rule that the adapter cleanup is requested **only after** usage + classification committed (F15). // src/NightTales.Application/Features/Rendering/RenderRetryPolicy.cs
public sealed class RenderRetryPolicy : IRenderRetryPolicy
{
    private static readonly FrozenSet<string> Transient = new[] {
        "tts_failed", "render_assembly_failed", "render_node_error",
        "render_lost", "render_timeout", "render_output_invalid"        // 05 D5; contract_violation excluded
    }.ToFrozenSet(StringComparer.Ordinal);
    private static readonly FrozenSet<string> Never = new[] {
        "image_moderated", "story_moderated", "render_quality_failed"    // 03 D7; image_generation_failed is NOT here
    }.ToFrozenSet(StringComparer.Ordinal);

    // BD7's signature (the extra parameter is optional, so `ShouldRetry(code, attempt)` still binds).
    // `outcomeRetryable` carries 03.4.2-T1's per-outcome decision (`ImageOutcome.Failed(..., retryable: true/false)`)
    // and overrides the static sets: `image_generation_failed` IS retried (rows 5 and 8) except when the classifier
    // marks it non-retryable (`provider_funds_exhausted`, moderated). BD7's blanket "never image_generation_failed"
    // contradicts 03 D7 + 09 §10's plan-03 hand-over — raised as a plan §10 [OPEN]/CR item.
    public bool ShouldRetry(string code, int attempt, bool? outcomeRetryable = null) =>
        attempt < 2 && !Never.Contains(code) && (outcomeRetryable ?? Transient.Contains(code));

    public async Task<RenderJob> CreateRetryAsync(RenderJob failed, CancellationToken ct)
    {
        // re-run IImageCostEstimator.WorstCase + IBudgetGuard.CheckAsync + ICreditLedger.ReserveAsync  (03 D8/CR-4)
        // each attempt row owns its own `reservation_id` (uuid NOT NULL) from that ReserveAsync; the failed row's
        // reservation was already refunded exactly once ([RULED — README §B10 WT50])
        // new RenderJob(attempt + 1) with the same EpisodeId/StoryVersionId/Params, state Queued, next_poll_at = now
        // same transaction as the failure (D5); enqueue SubmitRenderJob
    }
}

## Steps

1. `SubmitRenderJob` (row `FOR UPDATE` before the adapter call + re-check after it, WT55) + `RenderRequestedHandler` + the outbox registration (D11, enqueue-only).
2. `RenderPollingService` (advisory lock, tick, bounded parallelism, per-job `ISystemContext.For`) registered from `Worker/Jobs/RecurringRegistrations` — a `BackgroundService`, not a recurring job (WF07/W12).
3. `PollRenderJob` with the status→progress→terminal order, the realtime push, the `cancelled` terminal (refund by `reservation_id`, once — WT51), the `RenderFailed` raise on terminal `failed` (WT28) and the timeout guard.
4. `RenderRetryPolicy` + `IRenderRetryPolicy` + `RenderStage` + the `RenderProgress` event — `RealtimeEvent(RealtimeEventName.RenderProgress, RealtimeIds(episodeId, renderJobId), RealtimeData(Stage, Percent))`, where `RealtimeData` allows only `stage` (enum) and `percent` (0–100) and the NOTIFY body stays ≤ 8 KB ([RULED — README §B10 WT54]); the failed row's reservation is refunded once and the retry row gets a **new** `reservation_id` (WT50).
5. Wire the 03.4.2-T1 hook points as named no-op extension points so that task's diff stays local.
6. The three instruments + the observable gauge.
7. Write the terminal-outcome audit rows this task owns (`failed`, `render_timeout`, adapter `cancelled`) with `IAuditWriter.WriteAsync` (`actor_type = system`, actions `render.failed` / `render.cancelled`, `Category.Episodes`, `Visibility.User`, `data` = ids + code) inside the job's **own** `IUnitOfWork.BeginAsync/CommitAsync` — a job has no Mediator pipeline and `EfAuditWriter` throws without an ambient transaction (09.3.6-T1 L62/L180). The `RenderFailed` outbox row (WT28) is written in the same transaction as the `Fail`/refund.
8. Tests with `WorkerHost`, `InlineJobScheduler`, `FakeClock`, mock-mpt.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Worker restart mid-flight | `adapter_task_id` is stored before any poll; the poller re-claims by `next_poll_at`; no duplicate adapter task |
| Adapter task unknown on a submitted job | `render_lost` → retryable; the old adapter task is never polled again |
| Job row deleted/foreign tenant | the system scope reads only `(id, user_id)` pairs and processes each under `ISystemContext.For`; a missing id is a logged no-op |
| Node returns a transient failure 5× | the pipeline's breaker opens; `PickAsync` then returns nothing → the Deferred path, not a flood of failures |
| Two ticks overlap (slow tick) | the advisory lock covers claim + dispatch; leftover jobs are picked up by the next tick |
| `next_poll_at` is in the past for many jobs | the batch cap + parallelism bound the work; the index makes the claim cheap; `render_jobs_active` exposes the backlog |
| Retry budget exhausted | the job stays `failed`, `RefundAsync(reservationId, reason)` runs once, `RenderFailed` is raised with `Final = true` (no automatic retry follows — [RULED — README §B10 WT28/WT50]), the episode is back to `story_approved` |
| Cancel lands while `SubmitRenderJob` is in flight | the job row is taken `FOR UPDATE` before the adapter call and re-checked after it; when `cancel_requested_at` is set (or the row left `queued`) the adapter task is cancelled **and** deleted at once, no `MarkSubmitted`, no orphan adapter task ([RULED — README §B10 WT55]) |
| Adapter reports `succeeded` on a `cancel_requested_at` job | terminal state wins: the normal ingest runs, the job is settled, no cancel and no refund ([RULED — README §B10 WT51]) |
| Rollback | stop `RenderPollingService` (Worker image revert); `queued`/`submitted` rows stay and are re-polled by the previous image; no schema change |
