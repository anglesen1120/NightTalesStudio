## Goal

A successful adapter task becomes reviewed, durable video: the output is streamed to temp files and verified against `output.video.sha256` + size/type caps, the video and SRT are written to object storage, `assets` rows and `final_video_asset_id` are created idempotently, `quality_report` (`render-quality.v1` + 03's `images`) is written in one transaction, the episode moves to `video_review`, `RenderSucceeded` is raised, and only then is the adapter asked to clean up.

## Design

```csharp
// src/NightTales.Application/Features/Rendering/Jobs/IngestRenderOutputJob.cs   (D12; 03.4.2-T1 edits the hook lines only)
[JobPolicy(Queue = JobQueue.Render, Retries = 5)]
public sealed class IngestRenderOutputJob : IBackgroundJob
{
    public async Task RunAsync(Guid renderJobId, CancellationToken ct);
}
```

**Steps (two short transactions — [RULED — README §B10 WT45]: step 2 commits alone *before* the download; steps 7–9 commit together *after* the upload).**

1. Load the job under `ISystemContext.For(userId)`; skip when status is already `succeeded`/`failed`/`cancelled` or the asset already exists (idempotent on at-least-once delivery).
2. `job.MarkIngesting(now)`; release the poller (`next_poll_at = null`) so no tick touches it again — **committed in its own short transaction before any download** ([RULED — README §B10 WT45]).
3. Temp files: `Path.Combine(cfg.Render.Ingest.TempDirectory, $"{renderJobId:N}-{Guid.NewGuid():N}.{ext}")` with `FileOptions.DeleteOnClose`/explicit `finally` cleanup — never under the repo, never world-readable.
4. `IRenderDownloadClient.DownloadAsync(node, taskId, RenderOutputKind.Video, stream, Render:MaxVideoBytes, ct)` → `DownloadResult(Bytes, Sha256, ContentType)`; then the same for `Subtitles` (an `OutputAbsent` result is **not** an error — no subtitle asset).
5. Verify: `Sha256 == status.output.video.sha256`, `Bytes == status.output.video.bytes`, `ContentType == video/mp4` (subtitles `application/x-subrip`); any mismatch or cap breach → `render_output_invalid` (retryable, 05 D5) and no partial write. On the **last** attempt (Hangfire attempts exhausted) the job is failed `render_output_invalid`, `RenderRetryPolicy` is applied, `RefundAsync(reservationId, reason)` runs once and `RenderFailed { …, Final }` is raised ([RULED — README §B10 WT52/WT28]).
6. `IBlobStore.PutAsync(bucket, key, stream, contentType, ct)` with `bucket = StorageBuckets.Media` (`nt-media-<env>`, 09.7.2-T1; constant name [INFERENCE]) and keys `media/{userId}/{episodeId}/{renderJobId}/video.mp4` and `…/subtitles.srt` (BD7/BD10); `BlobInfo.Sha256` must equal the verified hash.
7. `assets` rows (00 §6 L288): video (`kind = "video"`, `storage_key`, `content_type`, `size_bytes`, `duration_sec` = `output.narration_seconds` when present, `sha256`, `retention_until = now + Assets:UnapprovedRetentionDays` (30)) and, when downloaded, subtitle (`kind = "subtitle"`, same stamp); idempotent by `storage_key + sha256` (see Notes: the table has no `render_job_id` column). The ingest stamp is the "abandoned render" retention — the approve path re-stamps it with `Assets:RetentionDays` ([RULED — README §B10 WT56]).
8. `RenderQualityEvaluator.Evaluate(status.check, new RenderExpectations(aspect, subtitlesEnabled, musicSelected), policy)` → `RenderQualityReportV1`; write it into `render_jobs.quality_report` with 03.4.2-T1's `images` object in the **same** transaction; `Pass == false` → `job.Fail("render_quality_failed")` + `episode.RenderFailed(now)` + `ICreditLedger.RefundAsync(job.ReservationId, "render_quality_failed")` once and stop (no asset is kept, no adapter cleanup before the failure commits, 05.5.1-T2 UC2) — refund by reservation id, never by job id ([RULED — README §B10 WT50]).
9. `RenderMarkers`: `episode.FinalVideoAssetId = videoAssetId` [INFERENCE: column/name per 00 §6 episodes], `episode.RenderSucceeded(now)` (`→ video_review`), **`SettleAsync(job.ReservationId)`** ([RULED — README §B10 WT50]), `job.Succeed(now)`, `ImageModerationRecorder` for kept-video moderated slots (03.4.2-T1), `RenderSucceeded { EpisodeId, RenderJobId }` domain event → outbox `render_succeeded.v1` (02 CR-23).
10. Commit the **single final short transaction** (steps 7–9: assets, report, episode, job, settle, outbox) — the download and the blob PUTs stay outside it ([RULED — README §B10 WT45]); **then** adapter cleanup: `IRenderClient.DeleteAsync(node, taskId, ct)` — fire after commit, never inside (03.4.2-T1 F15; a `409 adapter_task_busy` is retried once, then logged); temp files removed in `finally`.

## Steps

1. `IngestRenderOutputJob` + `RenderSucceeded` event + the `PollRenderJob` enqueue line (09.6.3-T1's file).
2. Temp-file helper with guaranteed cleanup (`finally`) and a startup check that the directory exists and is writable.
3. Verification step (sha256, bytes, content type) and the fail path.
4. Blob uploads through `IBlobStore` (09.7.2-T1) with the BD7 keys.
5. `assets` writer (idempotent) + `final_video_asset_id`.
6. `RenderQualityEvaluator` call, `quality_report` write and the 03.4.2-T1 `images` merge point.
7. Post-commit adapter `DELETE` + logging on failure.
8. Write the success audit row (`IAuditWriter.WriteAsync`, action `render.succeeded`, `actor_type = system`, `Category.Episodes`, `Visibility.User`, `data` = ids + sha256 only) inside this job's own `IUnitOfWork` transaction — no Mediator pipeline runs in a job (09.3.6-T1 L62/L180).
9. Tests with `WorkerHost` + mock-mpt fixtures.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `IBlobStore` unavailable | the job throws → Hangfire retries (≤ 5); the transaction rolls back; temp files are cleaned; no half-written asset; on the **last** attempt the job fails `render_output_invalid`, `RenderRetryPolicy` runs, the reservation is refunded once and `RenderFailed` (`Final`) is raised ([RULED — README §B10 WT52/WT28]) |
| Crash between the `MarkIngesting` commit and the upload | the row is `ingesting` with `next_poll_at = null`, so no tick re-claims it; the Hangfire retry resumes the ingest and steps 7–9 commit once — the two short transactions are the whole of WT45 ([RULED — README §B10 WT45]) |
| Blob upload succeeds, DB commit fails | the key is content-addressed per render job, so the retry overwrites the same key (`PutAsync` is idempotent) — no orphan variant |
| Adapter task gone (`adapter_task_unknown`) at download | `render_lost` path: the ingest is not run; `PollRenderJob`/the retry policy owns it |
| `check` missing but state succeeded | `RenderQualityEvaluator.Evaluate(null, …)` fails closed → `render_quality_failed` (05 D10) |
| `OutputAbsent` for subtitles | video is kept and **no** `subtitle` asset row is written. The ingest never writes `subtitles_present` (05 D10: the evaluator owns every `render-quality.v1` field); it passes `RenderExpectations(Aspect, SubtitlesEnabled: params.subtitles.enabled, MusicSelected)` and the node's `check` block decides — with `subtitles.enabled = true` a missing SRT normally ends in `render_quality_failed`, and only `subtitles.enabled = false` still succeeds |
| Worker restart between upload and commit | retry re-verifies the hash and re-uploads idempotently; the asset row is written once |
| `image_plan.needed` present but `images` report missing | 03.4.2-T1 writes one estimated usage row and `image_report_missing_total`; the ingest proceeds with `quality_report.images` from that outcome |
| Rollback | disable the job's registration (the poller stops enqueuing); blobs and assets already written stay and are inert; no schema change |

## Notes

- **Last-attempt detection — OPEN ITEM, owner IngestB/Main (Infrastructure adapter not wired yet):** there is no scheduler-coupled attempt API in Application, so 09.6.3-T2 adds the port `IJobAttempt` (+ `AmbientJobAttempt`/`JobAttemptScope`, AsyncLocal-based) and `AddRenderIngest` registers it. **Nothing in this tree calls `JobAttemptScope.Set` yet** (`grep -rn JobAttemptScope src tests` finds only doc references), so on a real Hangfire attempt `AmbientJobAttempt.IsLastAttempt` is `1 >= 1 = true`: a retryable `render_output_invalid` (or blob-store-down) failure would end the row on the **first** attempt instead of throwing for another one, so the `Retries = 5` budget would never be spent. - **S57 QA round — defect-closing decisions (D3, D4, D5, D7):**
  - **Unexpected exceptions (D3).** Every exception the download/verify/blob-PUT/final-transaction section escapes is handled in one place (`catch (Exception)` guarded only by *this job's own* token, so a host shutdown is never swallowed): this attempt's unsaved changes are dropped (`ChangeTracker.Clear` — the `GenerateFactSheetPipeline`/`StoryGenerationProgress` precedent), the open transaction is rolled back, and the row is re-read **as committed**. On the scheduler's last attempt (`IJobAttempt.IsLastAttempt`) the row is ended in-job through `IRenderFailureRecorder` with `render_output_invalid` (one refund by reservation id, `render_failed.v1`, the retry policy's `Final` flag) and the keys this attempt PUT are deleted best-effort; on an earlier attempt the exception is rethrown for the scheduler and the keys are kept on purpose (the next attempt overwrites the same content-addressed keys, BD7). A row that is **already terminal** when it is read back — this attempt committed, or another delivery ended it — is left exactly as it is and nothing is deleted, because the keys it names are now the committed asset's (`render_ingest_terminal_noop`, logged with ids only). *(Superseded for `failed`/`cancelled` rows by C5/S3 — see the object-cleanup bullet below; a `succeeded` row still keeps both keys.)*
  - **Settle decision (D5).** `ICreditLedger.SettleAsync` documents no idempotence per reservation and is **not** part of this job's unit of work, so it is called before the row turns terminal and its failure travels (`render_ingest_settle_failed`, then a throw): the final transaction rolls back and the attempt is retried, or ended on its last attempt — a delivered job never commits `succeeded` over an unsettled reservation (AC3). **Gap closed in the S57 review round (C3):** the settle is now the **last statement before the commit**, so the kept-video hook, the outbox raise, the audit write and the row's own transitions can no longer fail after it — only the commit itself can, and its rollback ends the attempt through the failure recorder (one refund, no settled-short success). A ledger that still has to survive a commit failure keeps its operations idempotent per reservation (12.1.2-T1). The settle cannot be moved after the commit without recreating exactly the state D5 forbids.
  - **Concurrent deliveries (D7).** The final transaction opens on `LockRenderJobForUpdateAsync` (the 09.6.3-T1 `SubmitRenderJob` shape; `AppDbContext.cs:218`), so two deliveries of one job that both passed the entry guards serialise there: the loser re-reads the committed row and returns as the logged no-op without a second asset row, object, outbox row, refund or settlement. The insert-time backstop stays for a delivery the lock did not serialise: a `DbUpdateException` whose provider error is `23505` on `ix_assets_storage_key` (read through `DbException.SqlState` + `Data["ConstraintName"]`, the `FactSheetFlushConflict`/`BibleProposalRunConflict` shape, since Application may not reference Npgsql) is the same no-op; anything else rethrows. No new claim contract — README §B10 names none.
  - **Objects of a non-keeping attempt (D4; extended by C5/S3 in the S57 review round, corrected by N2/N3 in the S57 delta round).** Every ending that does not keep the output — a quality refusal, a node error, a refused attach, an exhausted attempt, and a delivery that finds the row already ended as `failed`/`cancelled` — clears the row's **two deterministic keys** (BD7's video key and subtitle key), best-effort through one helper (`render_ingest_blob_delete_skipped`, ids and keys only) and with a token of the helper's own, because the ending can be running precisely because the job's token was cancelled. The **shutdown** path is the one ending that is *not* in that list: it neither deletes nor reads anything (`IngestRenderOutputJob`'s cancellation catch). A delete decided there could only come from an unlocked status read, and a duplicate delivery that has already PUT these exact keys but has not committed yet still reads `ingesting` — clearing them would leave its imminent success verdict pointing at nothing, silently and permanently; the keys are content-addressed, so the next attempt overwrites them, and a row that never runs again is 09.7.3-T1's failed/cancelled sweep's. The status read that used to sit there was also unbudgeted and unguarded, so a slow or failing database could replace the `OperationCanceledException` Hangfire requeues on and, on the last attempt, strand the row (WT52).   - **N1 (a commit that fails after the settle).** The settlement is the last statement before the commit, so a commit that fails after it — a competing writer on the `render_jobs` row, a transient fault, any non-`23505` `DbUpdateException` — leaves a **settled reservation beside a rolled-back row**. A retried attempt therefore settles the **same reservation a second time**, and a last attempt **refunds a reservation this job already settled**. Both are deliberate, and they are safe only because the 12.1.2-T1 ledger is **idempotent per reservation id**: `SettleAsync` twice on one reservation must be one settlement, and a `RefundAsync` for an already-settled reservation must answer a **typed no-op or a refusal** — never a second money movement.
