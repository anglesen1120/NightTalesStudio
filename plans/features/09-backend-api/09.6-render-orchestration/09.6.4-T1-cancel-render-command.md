# 09.6.4-T1 — `CancelRenderCommand` and `DELETE /render-jobs/{id}`

## Goal

A creator can stop a stuck or unwanted render: a queued job is cancelled at once, a submitted/running job is asked to cancel (the adapter releases the image plan and the poller turns MPT's terminal state into `cancelled` — **the refund happens there, never in the request path**, [RULED — README §B10 WT51]), an ingesting job is refused, and every cancel terminal refunds the reserved credits **by `reservation_id`** and returns the episode to `story_approved` (BD8) [RULED — README §B10 WT50].

## Design

```csharp
// src/NightTales.Application/Features/Rendering/Commands/CancelRender/CancelRenderCommand.cs
[Audited("render.cancelled", Category.Episodes, Visibility.User)]    // members verified: plans/09-backend-api.md:143-144
public sealed record CancelRenderCommand(Guid RenderJobId) : ICommand<ErrorOr<Success>>;

public sealed class CancelRenderCommandHandler : ICommandHandler<CancelRenderCommand, ErrorOr<Success>>;
```

Handler, one transaction (D5), tenant filter active:

| Job status | Action |
|---|---|
| `queued` | `job.Cancel(now)` immediately; refund `RefundAsync(job.ReservationId, "cancelled")`; `episode.RenderFailed(now)` → `story_approved` |
| `submitted`, `running` | `job.RequestCancel(now)` (sets `cancel_requested_at`); outbox `RenderCancelRequested`; **no refund here** — the refund happens when the poller records MPT's terminal `cancelled` ([RULED — README §B10 WT51]); episode stays `rendering` until then |
| `submitted`/`running` with `cancel_requested_at` set | idempotent: 204, no second outbox row |
| `cancelled` | idempotent: 204, no writes |
| `ingesting` | 409 `episode_invalid_state` (BD8) |
| `succeeded`, `failed` | 409 `episode_invalid_state` [INFERENCE: BD8 pins only `ingesting`] |

```csharp
// src/NightTales.Api/Endpoints/RenderingEndpoints.cs   (same group as 09.6.1-T1, D14)
group.MapDelete("/render-jobs/{id:guid}", async (Guid id, ISender s, CancellationToken ct) =>
        (await s.Send(new CancelRenderCommand(id), ct)).ToNoContentResult())   // 204
    .RequireAuthorization();
```

`PollRenderJob` terminal branch added here (the extension point 09.6.3-T1 leaves named): adapter `state == "cancelled"` → `job.Cancel(now)` + `episode.RenderFailed(now)` + `ICreditLedger.RefundAsync(job.ReservationId, "cancelled")` **once, at the terminal** (guarded by `status != Cancelled` so the refund cannot double-fire) + `render_duration_seconds{stage = "done", outcome = "cancelled"}` observed by 09.6.3-T1's instrument. This is the **only** refund for a `submitted`/`running` cancel — the `DELETE` request never refunds ([RULED — README §B10 WT51], refund by `reservation_id` per WT50). A job the adapter reports `succeeded` instead is **not** cancelled: the normal ingest runs and the reservation is settled (terminal state wins, WT51); whatever the branch, the refund and the settle are mutually exclusive. Outputs of a cancelled task are never downloaded (the adapter never serves them, 05 D4), and no blob or `assets` row is created.

**Metrics:** no new instrument. The cancel terminal feeds 09.6.3-T1's `render_duration_seconds{stage,outcome}`; `render_cancelled` is a **state** (`render_jobs.status = cancelled`), never written to `error_code` (05 D5, 09 §5.4 L412).

## Acceptance checks

- [ ] `DELETE /api/v1/render-jobs/{id}` on a `queued` job → 204, `render_jobs.status = cancelled`, `cancel_requested_at` null, credits refunded exactly once, episode back to `story_approved`, no adapter call (no outbox row beyond the original `render_requested.v1`, and the queued `SubmitRenderJob` becomes a no-op).
- [ ] On a `submitted`/`running` job → 204, `cancel_requested_at` set, one `render_cancel_requested.v1` outbox row; the Worker handler issues exactly one `POST /v1/renders/{task_id}/cancel`; **no refund in this path** — the refund is applied once when the poller records the terminal `cancelled` ([RULED — README §B10 WT51]).
- [ ] Repeating the same `DELETE` before the poller reacts → 204 with no second outbox row and no second refund.
- [ ] On an `ingesting` job → 409 `episode_invalid_state` and nothing changes.
- [ ] The adapter's `state = "cancelled"` on the next poll → `render_jobs.status = cancelled`, episode `story_approved`, `RefundAsync(reservationId, …)` applied exactly once **at that instant**, no blob, no `assets` row, one `render_duration_seconds{outcome = "cancelled"}` observation ([RULED — README §B10 WT51]).
- [ ] A `cancel_requested_at` job that the adapter answers as `succeeded` is **not** cancelled: the normal ingest path runs, `SettleAsync(reservationId)` is applied and the refund is skipped (terminal state wins, 05 D4/WT51).
- [ ] A `DELETE` that lands while the queued `SubmitRenderJob` is between its `FOR UPDATE` read and its adapter call leaves no adapter task: the job re-checks the row, sees `cancel_requested_at` and issues cancel + delete at once (WT55).
- [ ] Another user's `render_job_id` → 404 `not_found`; no auth → 401; the audit row carries ids only.
- [ ] The adapter cancel call is issued from the Worker only (the API process must not perform any node call — assert with a failing `IRenderClient` registration in the Api).
- [ ] `error_code` stays null on every cancel path (`render_cancelled` is not an outcome code, 05 D5).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Node unreachable when the cancel handler runs | `Deferred`/transport error → the handler throws → the outbox retries with backoff (≤ 10 attempts, D11); the job stays `cancel_requested` and the 60 min timeout eventually fails it |
| Cancel races the poller's terminal `succeeded` | first writer wins by `xmin`; the loser gets `DbUpdateConcurrencyException` → 409 `concurrency_conflict` (D5) and the client re-reads the job |
| Cancel after the ingest started (`ingesting`) | 409; no refund, no adapter call — the output is already being stored (BD8) |
| `RequestCancel` on a job whose adapter task was never created | `cancel_requested_at` is set and the queued `SubmitRenderJob` skips on `cancel_requested_at`; no adapter call is attempted with a null task id |
| Refund already applied (retry of the same command) | the guard is `status` + `cancel_requested_at`, not a timestamp comparison; the refund itself is by `reservation_id` and is applied once at the terminal `cancelled` ([RULED — README §B10 WT51/WT50]) |
| Double cancel across two API instances | the second transaction loses on `xmin` → `concurrency_conflict`, then the client's retry sees `cancelled` and gets 204 |
| Rollback | remove the route + handler registration; already-cancelled rows stay `cancelled`; `render_jobs` and credits are unaffected; no schema change |

## Notes

- **Security:** the guard is the D10 tenant filter → another user's job is 404, never 403; the command is ids-only and the outbox payload carries ids only (D11/D12); the Api never calls a node, so no node key is reachable from the request path; the audit row has no content.
- **Performance:** one transaction, one row update, at most one outbox insert; the adapter call happens once in the Worker under the outbox's backoff, not in the request path (BD11/BD16).
- **Code reuse:** `RenderJob.Cancel`/`RequestCancel` (09.6.1-T1), `IRenderClient.CancelAsync` + `AdapterErrorMapper` (09.6.2-T1), `PollRenderJob`'s terminal handling (09.6.3-T1), `ICreditLedger.RefundAsync` (02 D1), `IJobScheduler`/outbox plumbing (D11/D12) — no new adapter or ledger code.
- ✅ (WT51/WT50) Refund timing is ruled: the `DELETE` on a `submitted`/`running` job only sets `cancel_requested_at` + the outbox row; the refund is applied once when the poller records the terminal `cancelled`, by `reservation_id`, and a job the adapter reports `succeeded` is ingested and settled instead [RULED — README §B10 WT51/WT50].
- ⚠️ BD8 names the outbox handler but not the event; `RenderCancelRequested` / `render_cancel_requested.v1` is [INFERENCE] — recorded in plan §10 Open items.
- The `cancelled` terminal written by the `PollRenderJob` branch this task adds goes through `IAuditWriter` too (action `render.cancelled`, `actor_type = system`) inside the poller's own `IUnitOfWork`, like the other terminal rows (09.3.6-T1 L62/L180 lists render done/failed as job-written).
