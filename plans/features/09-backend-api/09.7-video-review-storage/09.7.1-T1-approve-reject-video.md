## Goal

From `video_review`, `POST /episodes/{id}/video/approve` moves the episode to `ready` (**re**-stamping the 30-day asset retention over the ingest's unapproved stamp — WT56), and `POST /episodes/{id}/video/reject` stores the reason and moves it to `story_review` or re-renders it per 00 §7. Both paths are audited with a bounded `IAuditData` projection, both raise their outbox event, and the same `ApproveVideoCommand` serves the owner and the 02.8.2 autopilot gate.

## Design

```csharp
// Domain/Episodes/Episode.VideoReview.cs  [INFERENCE: partial file; 02 extends Episode in partials, D16]
public enum RejectTarget { Story, ReRender }                     // wire: "story" | "re_render" [RULED — README §B10 WT3]

public partial class Episode
{
    public DateTimeOffset? ReadyAt { get; private set; }
    public string? VideoRejectReason { get; private set; }        // ≤ 500 chars, safe text

    public ErrorOr<Success> ApproveVideo(DateTimeOffset now)
        => Status is EpisodeStatus.VideoReview
            ? SetReady(now)                                       // Status = Ready; ReadyAt = now
            : Error.Conflict(ErrorCodes.EpisodeInvalidState, "The episode is not in video review.");

    public ErrorOr<Success> RejectVideo(string reason, RejectTarget target, DateTimeOffset now)
        => Status is not EpisodeStatus.VideoReview
            ? Error.Conflict(ErrorCodes.EpisodeInvalidState, "The episode is not in video review.")
            : SetRejected(reason, target, now);                   // reason stored; Story → StoryReview
}                                                                 //                 ReRender → StoryApproved
                                                                  // [RULED — README §B10 WT3: targets `story` | `re_render`]

// Application/Features/VideoReview/Commands/ApproveVideoCommand.cs
[Audited("episode.video_approved", Category.Episodes, Visibility.User)]
public sealed record ApproveVideoCommand(Guid EpisodeId, string? Note, string? IfMatch = null)
    : ICommand<ErrorOr<Success>>, IAuditData;                     // pinned: BD1 + 02.8.2 plan L220

[Audited("episode.video_rejected", Category.Episodes, Visibility.User)]
public sealed record RejectVideoCommand(Guid EpisodeId, string Reason, RejectTarget Target,
                                        string? IfMatch = null, string? IdempotencyKey = null)
    : ICommand<ErrorOr<VideoReviewResult>>, IIdempotentCommand, IAuditData;   // D4 markers

public sealed record VideoReviewResult(Guid EpisodeId, string Status, RejectTarget? Target);
public sealed class ApproveVideoCommandValidator : AbstractValidator<ApproveVideoCommand>;   // Note ≤ 500
public sealed class RejectVideoCommandValidator  : AbstractValidator<RejectVideoCommand>;    // Reason 1–500, Target enum
public sealed class ApproveVideoHandler : ICommandHandler<ApproveVideoCommand, ErrorOr<Success>>;
public sealed class RejectVideoHandler  : ICommandHandler<RejectVideoCommand, ErrorOr<VideoReviewResult>>;
```

`IAuditData` (BD15 — `AuditBehavior` fills `data` from the command's projection **only**; member names are 09.3.6-T1's, [INFERENCE]) is implemented by both commands. The projections carry ids, the target and the status and **never** `Reason`/`Note` text, a key or a URL:

```csharp
// ApproveVideoCommand
public AuditData Project() => new(EntityType: "episode", EntityId: EpisodeId,
    Data: new { episodeId = EpisodeId, status = "ready", notePresent = Note is not null });
// RejectVideoCommand
public AuditData Project() => new(EntityType: "episode", EntityId: EpisodeId,
    Data: new { episodeId = EpisodeId, target = Target.ToString(), status = "…", reasonPresent = true });   // target wire value: story | re_render (WT3)
```

`IfMatch` is an **optional third parameter** on the pinned `ApproveVideoCommand` so 02.8.2-T1's in-process `ApproveVideoCommand(episodeId, note: "autopilot")` keeps compiling while D7 ("the `IfMatchHeader` binder → `string?`, passed into the command") holds for HTTP callers. `null` = non-HTTP caller: the stale-ETag check is skipped, the state check is not ([INFERENCE], plan §10 Open items). `IdempotencyKey` is the D6 key of the reject route (its spend now happens in the Worker, so a repeated POST must not reject twice).

Handler sequence (both, D5 — no `SaveChanges`, no transaction, no nested send):

1. `_db.Episodes.SingleOrDefaultAsync(e => e.Id == cmd.EpisodeId)` — tenant filter applies (D10); absent or foreign → `Error.NotFound("not_found")` → 404.
2. `cmd.IfMatch is not null && cmd.IfMatch != $"ep-{episode.Version}"` → `Error.Conflict(ErrorCodes.EpisodeConflict)` → 412 (strong, exact compare, D15).
3. `episode.ApproveVideo(_clock.UtcNow)` / `episode.RejectVideo(cmd.Reason, cmd.Target, _clock.UtcNow)`; `EpisodeInvalidState` → 409.
4. Approve only: the episode's live assets are loaded (`_db.Assets.Where(a => a.EpisodeId == id && a.DeletedAt == null)`, bounded — a render produces ≤ 5) and each is **re-stamped** with `a.ScheduleRetention(now + TimeSpan.FromDays(_options.RetentionDays))`, overwriting the ingest's `Assets:UnapprovedRetentionDays` value ([RULED — README §B10 WT56]). No `ExecuteUpdate` (the entity method owns the rule).
5. `episode.Raise(new VideoApproved(...))` / `new VideoRejected(...)` — the outbox interceptor writes one row in the same `SaveChanges` (D11).
6. Return `Success` / `new VideoReviewResult(id, status, target)`.

Endpoints (`Api/Endpoints/VideoReviewEndpoints.cs`, `IEndpointGroup`, D14):

- `RejectVideoRequest { string Reason; RejectTarget Target; }`, `ApproveVideoRequest { string? Note; }`, `EpisodeStateDto(Guid Id, string Status, string Etag)` [INFERENCE: no response DTO is pinned; 00 §8 only names the routes]. - Both routes require an authenticated user (default policy per 09.3.2-T1); no `[AllowAnonymousRequest]`.

**[DECISION L1 → RULED WT3] reject → re-render (README §B10 WT3).** `RejectVideoCommand` moves `video_review → story_approved` and raises `video_rejected.v1` with `Target = re_render`; it sends **no** command, and the route answers **202** [RULED — README §B10 WT3]. `VideoReRenderHandler` starts the render in its own scope, through the pipeline, with the idempotency key `video-reject-rerender:{messageId}`, citing BD5's signature [RULED — README §B10 WT3]:

```csharp
public async ValueTask HandleAsync(VideoRejected e, OutboxContext ctx, CancellationToken ct)
{
    if (e.Target is not RejectTarget.ReRender) return;                    // story_review needs no render
    var etag = await _episodeEtag.ForEpisodeAsync(e.EpisodeId, ct);       // [INFERENCE] IEpisodeEtagReader; read at send time
    var r = await _sender.Send(new RenderEpisodeCommand(e.EpisodeId, IfMatch: etag,
                              IdempotencyKey: $"video-reject-rerender:{ctx.MessageId:N}"), ct);
    if (r.IsError) throw new OutboxRetryError(r.FirstError);              // 412/409/… → dispatcher backoff (D11)
}
```

- `ctx.MessageId` is stable across dispatcher retries (D11), so one rejection reserves credits once even if the send is retried; a concurrent `xmin` change produces a retryable 412 instead of a lost action.
- The command's spend is not in the reject transaction: 00 §7's `video_review → rendering` is realised as `video_review → story_approved` (rejection committed) → `rendering` (render command, Worker). The intermediate state is what 00 §7 already uses for "user can re-render", and a render error (`keywords_flagged` 409, `budget_exceeded` 402) leaves the episode there with the error surfaced by the render job/`EpisodeUpdated`.
- The reject route therefore requires `Idempotency-Key` (00 §8 covers credit-spending POSTs; the key now protects the *rejection reply* of the command, D6) and the command implements `IIdempotentCommand`.

`IRealtimeNotifier.NotifyAsync(userId, new EpisodeUpdated(EpisodeId, Status, NextActions), ct)` (BD11; `nextActions` from 09.5.1-T1) is called by the handlers, never by the command handlers.

`autopilot` caller (02.8.2-T1): system scope via `ISystemContext.For(run.UserId)` + `ISender.Send(new ApproveVideoCommand(episodeId, "autopilot"))`; the gate writes its own `autopilot.video_auto_approved` row, so History shows both rows (02.8.2 plan ¶4/L193).

## Failure handling and edge cases

- **No final video asset** (a hand-inserted `video_review` episode): approve still returns 200 — `final_video_asset_id` is 09.6.3-T2's invariant and this task must not invent a second guard; the `video-url` route is the one that 404s without an asset. [OPEN] if the TL wants a guard, it belongs in the domain method as `episode_invalid_state`.
- **Concurrent approve and reject**: both read `xmin` at load; the loser's `SaveChanges` throws `DbUpdateConcurrencyException` → D5 maps it to 409 `concurrency_conflict` (not 500).
- **`VideoReRenderHandler` send fails** (`412` stale ETag, `409` invalid state, `402` budget, `503` node unavailable): the handler throws so the dispatcher retries with backoff (D11, 10 attempts then dead-letter, `outbox_dead_letters_total`); the rejection is already committed and the episode stays `story_approved`, so the user can still start a render from the UI. No retry loop inside the handler.
- **Duplicate rejection** (client retry without the same key): the second POST finds the episode no longer in `video_review` → 409 `episode_invalid_state`; with the same `Idempotency-Key` the stored response is replayed (D6) and no second event is raised.
- **Outbox realtime failure**: retried by the dispatcher; nothing is lost (the state change is committed).
- **Clock**: `_clock.UtcNow` only; `ReadyAt`/`retention_until` are `timestamptz` in UTC (D8).
- **Rollback**: remove the endpoint group (no migration, no data change). An approve is reversed by 02's `POST /episodes/{id}/story/reopen` (episode back to `story_review`) and a new render; a wrong reject is reversed the same way.
