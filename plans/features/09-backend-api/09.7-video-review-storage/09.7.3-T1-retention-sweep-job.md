## Goal

A daily `RetentionSweepJob` deletes the objects behind every live `assets` row whose `retention_until` has passed, marks the rows `deleted_at`, and applies the ordered `audit_logs` retention rules of 09 §4 09.3.6 — in bounded batches with guaranteed progress, under `ISystemContext.For(userId)` per row, driven entirely by the database (never by a client-supplied key).

## Design

```csharp
// Application/Features/Platform/Retention/IAuditRetentionStore.cs   (09.7.3-T1-owned: audit rows are NOT IUserOwned,
//                                                                    so the pinned PendingAsync<T> port cannot serve them)
public sealed record AuditRetentionCandidate(Guid Id, AuditRetentionRow Row, DateTimeOffset CreatedAt);
// AuditRetentionRow: 09.3.6-T1's record; CreatedAt is the keyset key

public interface IAuditRetentionStore
{
    // keyset scan over the (created_at, id) index: WHERE (created_at, id) > (@afterCreatedAt, @afterId)
    // ORDER BY created_at, id LIMIT @take — no OFFSET, no newest-first re-scan [RULED — README §B10 WT47]
    Task<IReadOnlyList<AuditRetentionCandidate>> LoadAfterAsync(DateTimeOffset? afterCreatedAt, Guid? afterId,
                                                                int take, CancellationToken ct);
    Task<int> DeleteAsync(IReadOnlyList<Guid> ids, CancellationToken ct);          // set-based WHERE id = ANY(@ids)
}
```

`AuditRetentionStore` (Infrastructure/Persistence, plain `AppDbContext` read) projects `Id, Category, ActorType, Visibility, HasPaymentLink, CreatedAt` into 09.3.6-T1's `AuditRetentionRow`, ordered `created_at ASC, id ASC` and read by **keyset** (`(created_at, id) > (@afterCreatedAt, @afterId)`) over the `ix_audit_logs_created_id` index `(created_at, id)` ([RULED — README §B10 WT47]) — no `OFFSET`, no newest-first re-scan, so the scan stays index-only and a cursor always terminates. It needs **no** `IgnoreQueryFilters` entry: 09.3.6 plan §55 rules that `AuditLog` is not `IUserOwned` ("carries `subject_user_id` **and** `actor_user_id`, which one tenant filter cannot express"), so `audit_logs` carries no tenant filter at all and there is nothing to bypass — the D10 allow-list keeps only `RetentionSweepJob` from this task (see Notes). `HasPaymentLink` is computed from the `audit_logs` linkage columns and is **always false in P** — still computed from the real columns, not hard-coded, so rule `payment_linked` survives plan 12 landing. The expired decision itself is made in C# from the rules, never re-encoded in SQL:

```csharp
// Application/Audit/AuditRetentionPredicate.cs  [INFERENCE: file name] — one place, unit-tested per rule
public static IReadOnlyList<Guid> Expired(IReadOnlyList<AuditRetentionCandidate> candidates,
                                          IReadOnlyList<AuditRetentionRule> ordered, DateTimeOffset now)
    => candidates.Where(c => FirstMatch(ordered, c.Row) is { Retain: { } retain }
                             && c.Row.CreatedAt < now - retain).Select(c => c.Id).ToList();
```

The assets query runs through the **pinned** wave-1 port (09.2.3-T1:36; its `plan.md`:39 pins the single member — do not widen it):

```csharp
// exactly 09.2.3-T1's signature; T = Asset (Entity, IUserOwned)
IAsyncEnumerable<(Guid Id, Guid UserId)> PendingAsync<T>(Expression<Func<T, bool>> where, int batch, CancellationToken ct);

var due = _systemWork.PendingAsync<Asset>(
    a => a.DeletedAt == null && a.RetentionUntil != null && a.RetentionUntil < now && !excludedIds.Contains(a.Id), batch, ct);
```

The pair projection carries no `storage_key`/`kind`, so each pair is processed inside its own `ISystemContext.For(userId)` scope where the asset is loaded before the delete — the D10 pattern verbatim ("cross-user sweeps read `(id, user_id)` pairs through `ISystemWorkQuery` and process each one under `ISystemContext.For`"). Audit rows are **not** `IUserOwned`, so they cannot go through that port at all: they use 09.7.3-T1's own `IAuditRetentionStore` + the C# rule evaluation above. Neither port is extended ([OPEN] in plan §10 records the ruling).

Job sequence:

1. **Lock.** `SELECT pg_try_advisory_lock(hashtext('retention_sweep'))` in a short transaction; `false` → log `retention_sweep_skipped reason=locked` and return (Api×2/Worker×1 must not double-sweep). Release in `finally` (or rely on session end).
2. **Asset phase**, a `while` loop with **two** stopping conditions and a failure memory — without both, a batch where every row fails returns the same 500 rows forever:
   - `iterations++`; stop when `iterations > RetentionSweep:MaxBatches` (`20`) and emit `retention_sweep_batches_capped_total{phase="assets"}` + a `capped` counter in the summary log (the backlog is reported, not silently dropped);
   - stop when the query returns fewer than `RetentionSweep:BatchSize` (`500`) pairs;
   - every failed asset id goes into the run-local `failedIds` set, which is pushed into the next query's `!excludedIds.Contains(a.Id)` clause, so a poison object is retried tomorrow, not in the same run;
   - per pair: `using var scope = _systemContext.For(userId)` (D10; one scope per row, so the tenant filter resolves to the owner) → load the asset in that scope (the pair has no `storage_key`) → `IBlobStore.DeleteAsync(BlobLocator.BucketFor(asset.Kind, _storage), asset.StorageKey, ct)` → success **or** `NoSuchKey` (idempotent) → `asset.MarkDeleted(now)`; any failure → `failedIds.Add`, `retention_sweep_asset_failures_total++`, one `Warning` with the asset id + code (never the key), continue.
   - `deleted_at` is written **after** the object delete, so a crash between the two leaves a live row with a missing object (the next run deletes again: `DeleteAsync` is idempotent, then marks it) — never a row that claims deleted while the file is still public.
3. **Audit phase**, the same bounded loop (`MaxBatches`, `BatchSize`) over `IAuditRetentionStore.LoadAfterAsync(afterCreatedAt, afterId, batch, ct)` — a **keyset** scan over the `(created_at, id)` index ([RULED — README §B10 WT47]) → `AuditRetentionPredicate.Expired(candidates, AuditRetentionRules.Ordered, now)` → `DeleteAsync(ids)` (one set-based `WHERE id = ANY(@ids)`, so no per-row scope is needed); the cursor advances to the last candidate's `(created_at, id)` on every iteration, so no row is ever re-read and a failed batch is simply skipped by the cursor (no `excludedIds` set on the audit side, no `OFFSET`). A failure ends this phase and is logged (asset deletions already committed stay). `HasPaymentLink` is always false in P but is read from the real columns, so rule `payment_linked` (`Retain = null` = never) keeps working the day plan 12 lands.
4. **Metrics + one log line** (ids and counts only).
5. No outbox event: retention is invisible to the user; 13.3.1-T1 owns the hard delete and its own audit rows.

Registration is a `Worker/Jobs/` class only (D12); the Api never schedules it. `RetentionSweepJob` is on D10's `IgnoreQueryFilters` allow-list, so 09.1.2-T1's architecture test must include it. `AuditRetentionStore` needs **no** entry: `audit_logs` is not `IUserOwned` (09.3.6 plan §55), so it carries no tenant filter to bypass — a dedicated test asserts the store calls no `IgnoreQueryFilters`.

## Failure handling and edge cases

- **Job aborted mid-batch** (deploy, crash): `deleted_at` is set after each object delete, so the next run re-processes only unmarked rows; object deletes are idempotent. Nothing is half-marked.
- **`deleted_at` and `UpdatedAt` (09 W3 CR-38, 09 W3 CR-40).** `Asset` implements `IAuditable`; `MarkDeleted` is a tracked change, so `AuditableSaveChangesInterceptor` stamps `UpdatedAt` in the same `SaveChanges`. If the sweep path is ever rewritten as a set-based `ExecuteUpdateAsync`, that statement must add `SetProperty(a => a.UpdatedAt, now)` — set-based updates bypass the interceptor. The migration stays index-only: `assets`' column types (incl. `StorageKey`/`Sha256`) belong to 09.2.2-T1's `AssetConfiguration`.
- **Storage outage**: every object of a batch fails → the failures go into `failedIds`, the loop continues to the next batch, and the run stops at `MaxBatches` (not "ends normally" with an infinite loop — the earlier draft's exit condition was unreachable in this case). Nothing is marked deleted; tomorrow's run retries the same rows.
- **Audit-phase failure** (e.g. a column renamed by a future 09.3.6-T1 edit): the candidate load or the delete throws, the run logs the failure and stops the audit phase; asset deletions already committed stay; the exception surfaces in the Hangfire job log (0 retries, per `[JobPolicy]`).
- **Replication/backup window**: deletion is irreversible; the `nt-media-<env>` → `nt-backup-<env>` copy (owner 11.4.1-T3, T80; asserted by 11.6.1-T1) is a rollout prerequisite — a deleted object leaves the backup within 30 days (GOVERNANCE lock 29 d + `NoncurrentVersionExpiration` 29 d, T87) — and `Assets:RetentionDays` (30) is tuned in 12 (11 CR-15).
- **Timezone/DST**: cron is UTC and every comparison is `timestamptz` vs. `IClock.UtcNow` (D3/D8) — no local-time arithmetic.
- **Concurrent 09.6.3-T2 ingest**: an asset created after the batch query is not in the batch; every ingested asset already carries `retention_until = now + Assets:UnapprovedRetentionDays` (30) and approve **re-stamps** it to `now + Assets:RetentionDays` (30) ([RULED — README §B10 WT56]), so a video under review is swept at most 30 days after ingest while an approved one lasts 30 days after approval.
- **Rollback**: `RetentionSweep:Enabled=false` (skips the run and removes the registration on next Worker start) + revert the index migration; already-deleted objects are only recoverable from `nt-backup-<env>`.

This task specifies no persisted cursor or retained-row skip, so behaviour is unchanged; a watermark (or a predicate that skips never-expiring rows) is a follow-up if `capped` ever appears on the audit phase.
- ⚠️ **[OPEN → plan 12] Payment link is a stopgap (QA-5 / SEC-2)**: `audit_logs` has no payment linkage column in P, so `AuditRetentionStore` marks **every `billing` row** `HasPaymentLink = true` and rule `payment_linked` (never delete) keeps it — the user-actor, `visibility=user`, `billing` row older than 12 months from Acceptance now survives (`AuditRetention_KeepsPaymentLinkedRows_RegardlessOfAge`, 400 d and 1,800 d rows; a same-age `episodes` row is still swept). **Plan 12 must replace the category test with the real payment link** and may then release unlinked billing rows to the 365-day rule; the predicate unit tests already pin both outcomes.
- **Per-row due re-check (SEC-1)**: `IAssetRetentionStore.FindDueAsync(assetId, now, ct)` replaces `FindLiveAsync`; it re-applies `deleted_at IS NULL AND retention_until IS NOT NULL AND retention_until < now` on the write context immediately before the irreversible object delete, because the id query ran on `ReadDbContext`. A row re-stamped (09.7.1-T1 approve) or soft-deleted in between is **skipped** — not a failure, not counted in `Failed` — and joins the run's exclusion set so the id query does not return it again.
- **Capped is exact (QA-2)**: a phase that has run `MaxBatches` batches issues one more one-row query/load; `capped` and the capped counter are set only when that probe finds a row, so exactly `MaxBatches` full batches with nothing left is reported as finished. The probe is one extra statement per phase, only at the cap.
