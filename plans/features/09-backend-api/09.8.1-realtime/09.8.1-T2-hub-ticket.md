# 09.8.1-T2 — `hub_tickets`, `POST /hubs/ticket`, single-use claim and cleanup job

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 09.8.1 | S (0.5) | BE | 09.8.1-T1 | 09.9.3-T2, 10.2.4-T1 (10 CR-8), 10.2.4-T0 | P · M1 |

## Goal

A logged-in client exchanges its access token for a short-lived, single-use **ticket** and connects to the hub with `/hubs/episodes?ticket=…`, so the JWT never appears in a URL. The ticket is stored only as a hash, dies after 60 s, is consumed by one atomic `UPDATE` (two instances cannot both win), and every failure is the same `401 hub_ticket_invalid`.

## Design

Migration `<yyyyMMddHHmm>_09_8_1_HubTickets` (owner 09.8.1-T2 per D9/CR-5 ✅), expand-only, no backfill:

```sql
CREATE TABLE hub_tickets (
    ticket_hash text        PRIMARY KEY,        -- SHA-256 hex of the 32-byte ticket; the ticket itself is never stored
    user_id     uuid        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at  timestamptz NOT NULL,
    expires_at  timestamptz NOT NULL,           -- created_at + Realtime:TicketTtlSeconds (60, BD11)
    used_at     timestamptz NULL                -- non-null = consumed; never reset
);
CREATE INDEX ix_hub_tickets_expires_at ON hub_tickets (expires_at);
```

EF configuration (D8 conventions — snake_case, `DateTimeOffset` → `timestamptz`, no DB-generated ids, no `xmin` on this non-aggregate table):

```csharp
internal sealed class HubTicketConfiguration : IEntityTypeConfiguration<HubTicket>
{
    public void Configure(EntityTypeBuilder<HubTicket> b)
    {
        b.ToTable("hub_tickets");
        b.HasKey(t => t.TicketHash);                                   // text PK, length 64
        b.Property(t => t.TicketHash).HasMaxLength(64).IsRequired();
        b.Property(t => t.UserId).IsRequired();
        b.HasOne<AppUser>().WithMany().HasForeignKey(t => t.UserId).OnDelete(DeleteBehavior.Cascade);
        b.HasIndex(t => t.ExpiresAt).HasDatabaseName("ix_hub_tickets_expires_at");
    }
}
```

Application/Infrastructure pieces:

```csharp
// src/NightTales.Application/Features/Realtime/Commands/IssueHubTicket/{IssueHubTicketCommand,IssueHubTicketHandler}.cs
public sealed record IssueHubTicketCommand : ICommand<ErrorOr<HubTicketDto>>;      // no idempotency key: 60 s, single-use
public sealed record HubTicketDto(string Ticket, DateTimeOffset ExpiresAt);

// src/NightTales.Infrastructure/Realtime/NpgsqlHubTicketValidator.cs   (implements 09.8.1-T1's port)
public sealed class NpgsqlHubTicketValidator(AppDbContext db, IClock clock) : IHubTicketValidator
{
    public async ValueTask<ErrorOr<Guid>> ClaimAsync(string ticket, CancellationToken ct)
    {
        var hash = Sha256Hex(Encoding.ASCII.GetBytes(ticket));                     // never log `ticket`
        var rows = await db.Database.SqlQuery<Guid>($"""
            UPDATE hub_tickets SET used_at = now()
            WHERE ticket_hash = {hash} AND used_at IS NULL AND expires_at > now()
            RETURNING user_id
            """).ToListAsync(ct);
        // then: live read of users.security_stamp/status (open item 1) — mismatch → treated as invalid
        return rows.Count == 1 ? rows[0]
             : Error.Unauthorized(ErrorCodes.HubTicketInvalid, "The hub ticket is invalid or was already used.");
    }
}
```

- Ticket value: `RandomNumberGenerator.GetBytes(32)` → base64url (43 chars, ≥ 256 bit, BD16 ✅). Only `Sha256Hex` (lowercase, 64 chars) is persisted; the plaintext exists only in the HTTP response. The lookup is by hash — the primary key — so no in-code secret comparison happens (BD16's constant-time rule does not apply here because nothing is compared in code).
- **Claim is one statement** (`UPDATE … WHERE used_at IS NULL AND expires_at > now() RETURNING user_id`) — no `SELECT`-then-`UPDATE`, no lock, no Redis (BD11/WF10 ✅); `rowcount 0` covers unknown, expired, used and tampered with one indistinguishable answer.
- Endpoint (`Api/Endpoints/HubEndpoints.cs`), bearer access token, rate policy `hub`:

| Method | Route | Success | Errors |
|---|---|---|---|
| POST | `/api/v1/hubs/ticket` | `200 { "ticket": "<43 chars>", "expiresAt": "…Z" }` | `401` unauthenticated, `429 rate_limited` + `Retry-After` (policy `hub`, 10/min per user, BD14), `503 service_unavailable` |

```csharp
group.MapPost("/hubs/ticket", async (ISender sender, CancellationToken ct) =>
        (await sender.Send(new IssueHubTicketCommand(), ct)).ToHttpResult())
     .RequireAuthorization()
     .RequireRateLimiting("hub");     // policy registered by 09.3.5-T1 — plan §10 open item 4
```

- Anti-abuse: at most one live ticket per user is preferred over a flood — [DECISION] the handler **deletes this user's expired tickets** opportunistically in the same transaction (`DELETE FROM hub_tickets WHERE user_id = @u AND expires_at < now()`), so a user's rows cannot accumulate beyond the rate limit; the hourly job still sweeps everyone.
- `HubTicketCleanupJob` (Application `Features/Realtime/Jobs/HubTicketCleanupJob.cs`, `sealed`, `IBackgroundJob`, `[JobPolicy(Queue = JobQueue.Default, Retries = 2)]`, ids-only parameter `retentionHours`):

```sql
DELETE FROM hub_tickets WHERE ctid IN (
    SELECT ctid FROM hub_tickets WHERE expires_at < now() - make_interval(hours => @retention) LIMIT 1000);
```
  Batched (≤ 1000/run) to keep the transaction short; recurring **hourly** via `IRecurringJobRegistration` at Worker start (D12, BD11 ✅). The Api never schedules it (D12/R7).
- Config keys: `Realtime:TicketTtlSeconds` (`60`), `Realtime:TicketCleanupRetentionHours` (`24`), `Realtime:TicketCleanupBatchSize` (`1000`) [INFERENCE: names/defaults].
- Wiring: register `IHubTicketValidator` → `NpgsqlHubTicketValidator` (Infrastructure DI) in the Api, closing the fail-fast seam of 09.8.1-T1; register the cleanup job's recurring id in the Worker.
- [OPEN] Open items 1–2 in the plan touch this table: the **security stamp** (09 L214 wants a stamp check) and the **access-token expiry** (09 L218 wants the connection closed at token expiry; BD3 gives owner/admin 5 min). This task implements BD11's column list plus the live-read variant; if the TL accepts the proposal, this migration adds `security_stamp text NOT NULL` and `token_expires_at timestamptz NOT NULL` and the claim compares them (one extra `AND`), with the endpoint writing the caller's `exp`.

## Steps

1. Add the `HubTicket` entity (Infrastructure `Realtime/`) + `HubTicketConfiguration`; generate the migration `_09_8_1_HubTickets` (table + index only, D8/D9 conventions).
2. Add `IssueHubTicketCommand`/handler: 32 random bytes → base64url, hash, insert `(hash, user_id, created_at, expires_at)`; opportunistic delete of the caller's expired rows; return `{ ticket, expiresAt }`. Never log the ticket.
3. Implement `NpgsqlHubTicketValidator` (single `UPDATE … RETURNING`) and register it in the Api composition root; add the live stamp/status read per plan open item 1 and return the one `hub_ticket_invalid` error for every failure mode.
4. Map `POST /api/v1/hubs/ticket` with `.RequireAuthorization()` + `.RequireRateLimiting("hub")`.
5. Add `HubTicketCleanupJob` (batched delete, `FakeClock`-driven in tests) and its hourly recurring registration in the Worker.
6. Add the integration tests below (single-use, concurrency across two `ApiFactory` instances on one `PostgresFixture`, expiry with `FakeClock`, 429 after 10/min).
7. Confirm the log-redaction check: no ticket/hash in any log or metric label; the access-log rule for the hub query string stays in 09.8.1-T1 (verified by 09.9.3-T2).

## Acceptance checks

- [ ] `POST /api/v1/hubs/ticket` with a valid access token returns `200` with a 43-char base64url ticket and an `expiresAt` exactly `Realtime:TicketTtlSeconds` (60) after `created_at`.
- [ ] `hub_tickets` contains exactly one row per issued ticket and **only** the SHA-256 hash — no plaintext ticket anywhere in the table, and the response's plaintext is never written to a log.
- [ ] The first claim with a valid ticket returns the owning `user_id` and sets `used_at`; a second claim of the same ticket returns `401 hub_ticket_invalid`.
- [ ] Two simultaneous claims of one ticket: exactly one `200`/claimed connection and one `401`; the table has exactly one non-null `used_at` (single `UPDATE … RETURNING`, no `SELECT`-then-`UPDATE`).
- [ ] A ticket older than 60 s (`FakeClock`) → `401 hub_ticket_invalid` and is not claimed; an unknown or tampered ticket → the same `401` with an identical body.
- [ ] A missing ticket on the hub connect (09.8.1-T1) → `401 hub_ticket_invalid`; the JWT is never accepted in a query string.
- [ ] The 11th ticket request in one minute by the same user → `429 rate_limited` with a `Retry-After` header; the 11th request by a *different* user still succeeds (per-user partition).
- [ ] `HubTicketCleanupJob` deletes only rows with `expires_at < now − Realtime:TicketCleanupRetentionHours`, in batches of at most `Realtime:TicketCleanupBatchSize`, and is registered hourly with a stable recurring id in the Worker (never in the Api).
- [ ] `ON DELETE CASCADE` from `users` removes that user's tickets (no orphan rows after account deletion).
- [ ] `GET`/`PUT` on `/hubs/ticket` are not mapped; the route answers `405` for other verbs.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Ticket expired between issue and connect | Claim matches 0 rows → `401 hub_ticket_invalid`; the client fetches a new ticket and reconnects (10.2.4) |
| Two browser tabs / two devices connect at once | Each gets its own ticket; a shared/replayed one loses the race with `401` |
| Ticket used, then the socket drops immediately | Nothing re-usable remains; the client must re-ticket (single use by design) |
| `users` row deleted while tickets exist | `ON DELETE CASCADE` removes them; a live socket is aborted by the `security` channel path (09.8.1-T1) |
| Clock skew between instances | `expires_at` is written from `IClock` (`SystemClock`, UTC — D3) and compared against PostgreSQL's `now()` inside the claim; a skewed instance can shorten/lengthen the effective TTL, but the single-use guarantee is unaffected ⚠️ |
| Rate limit hit by a legitimate reconnect loop | `429` + `Retry-After`; the SPA backs off; a ticket is only needed once per connection, so 10/min is generous |
| `hub` policy not registered (before 09.3.5-T1) | Startup/host error surfaces named in plan open item 4 — the route must not silently run unlimited |
| Cleanup job overlaps with a claim | Both are `UPDATE`/`DELETE` on the same rows inside short transactions; a row deleted while being claimed simply yields 0 rows → `401` (already expired by definition) |
| DB down | `503 service_unavailable` (09.1.4-T1); no ticket is issued and no partial row remains |
| Hash collision / tampering with `ticket_hash` | Primary key on a 256-bit hash; tampering yields an unknown hash → `401` |

## Notes

- Rollback: drop the migration's table (it holds only ≤ 60 s tickets; no other feature reads it) — clients get `401 hub_ticket_invalid` and retry after the next ticket; the hub stays mapped but unreachable by design, so a rollback must ship together with a revert of 09.8.1-T1's scheme registration or an alert. No flag is added (B8.1 has none).
- Reuse: `IHubTicketValidator` port + `HubTicket` scheme from 09.8.1-T1 (no second auth path), `AppDbContext`/D8 conventions from 09.2.1-T1, `IJobScheduler`/`IRecurringJobRegistration` from 09.2.6-T1, policy `hub` from 09.3.5-T1, `ToHttpResult`/catalogue from 09.1.4-T1. `RandomNumberGenerator` (BCL) — no custom crypto, no `Guid`-as-token.
- Deliberate non-goals: no refresh-token-like rotation, no per-device tracking, no ticket in a cookie (it must travel in the connect URL), no audit row — an audit entry per ticket would add one insert per connection attempt; 09 L214 does not require one. If the TL wants one, `IAuditWriter` (`identity.hub_ticket_issued`, `internal`) is the reuse path.
- [INFERENCE]/[OPEN]: the table's missing `security_stamp`/`token_expires_at` columns and the stamp check (plan open items 1–2), the `hub` policy dependency on 09.3.5-T1 (open item 4), the `Realtime:*` key names/defaults and the `{ ticket, expiresAt }` body (BD11 fixes the fields, not the key names).
- **Deviations as implemented (2026-10-02).**
  - The claim compares `expires_at > @now` with the scope's `IClock`, not PostgreSQL's `now()`: `expires_at` is written from `IClock` (SystemClock UTC, D3), and the D13 harness drives expiry with `FakeClock`, so a stored expiry and the database's own clock could never agree in the same row. Single use is unaffected — it is the atomic `UPDATE … WHERE used_at IS NULL` that guarantees it.
  - The claim is one atomic `UPDATE … SET used_at` (`ExecuteSqlRawAsync`, row count = the decision) plus one read of the owner and the owner's **live** `users.role` (which the port requires). The design's single `RETURNING` statement was not used because EF's `SqlQuery` composition cannot execute a data-modifying statement. No `security_stamp`/`status` is read: plan open item 1 is ✅ RULED (WT37) — "no live stamp read" — so BD11's column list stands as written; only 09.8.1-T1's `NOTIFY security` closes a revoked socket.
  - The issue path goes through a new Application port `IHubTicketStore` (`NpgsqlHubTicketStore`, Infrastructure): Application cannot name the Infrastructure `HubTicket` entity and the table has no aggregate. `HubTicketSecret` (Application) owns the mint and the hash; it hashes UTF-8 rather than the design's ASCII, because ASCII folds every non-ASCII byte to `?` and two presented values would collide on one hash.
  - `HubTicketCleanupJob.RunAsync(CancellationToken)` takes no `retentionHours` parameter — retention and batch size are configuration read by the store. `RealtimeOptions` gained `TicketTtlSeconds` (60), `TicketCleanupRetentionHours` (24) and `TicketCleanupBatchSize` (1000), all validated on start in `AddRealtime`; `IHubTicketStore` is registered there (both hosts need it), the validator only in the Api's `AddNightTalesRealtime`. One run deletes at most one batch (the design's "≤ 1000/run").
  - EF's FK convention adds `ix_hub_tickets_user_id` beside the designed `ix_hub_tickets_expires_at` (it also carries the cascade delete); the rest of the migration is the designed table.
  - `HubEndpoints` marks the 200 with `Cache-Control: no-store`, like the auth responses: a ticket is a bearer secret for its 60 seconds.
  - `WorkerHost` now composes `AddRealtime`, exactly as the production Worker's `Program.cs` does; the harness previously omitted it, which would have hidden the store registration this task added.
  - `RealtimeHubTests.Unregistered_TicketValidator_FailsFast_Without_APermissiveFallback` was updated with this task: the production root now registers the production validator (asserted in a scope), and the fail-fast is proved with that registration removed. `SeedPrevious` gained its `hub_tickets` row, per the migration rule in `docs/dev-setup.md`.
