# 09.10.6-T1 — `registration.*` settings + `IRegistrationPolicyProvider` DB implementation

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 09.10.6 | S (0.5) | BE | 09.10.2-T1, 09.3.1-T3; 09.3.1-T2 soft | 12.4.2-T1, 12.8.3-T1 (W3 CR-13) | S · M2 |

## Goal

An owner edits `registration.mode`, `registration.disposable_domains` and `trial.credits` through the existing settings API, and `POST /auth/register` honours the new three-value mode set (`closed | invite | open`, superseding BD2's two-value set, W3-10/D15) without a second settings store or a second read port.

## Inputs

- `../README.md` §C3 **D15** (the three keys, validation rules, `IRegistrationPolicyProvider` is 09.3.1-T3's port, implemented here over `DbSettingsProvider`; unknown mode/malformed domain → 400 `setting_invalid`; `open` → disposable-domain check + CAPTCHA + breach check happens in 09.3.1-T2/09.3.3-T2, not here).
- W3-6: `registration` is an existing settings-catalog integration (non-secret `mode`, `disposable_domains`, `trial.credits`, no secrets, not critical, no base URL) — **no new integration row**, this task adds the key validators and the provider implementation only.
- W3 CR-12 (this README §B3 BD2 correction): `Registration:Mode ∈ closed | invite | open` (P: `closed`); `invite` + `Registration:Invite:CodeHash` are 09.3.1-T3's.
- W3 CR-13 (to `features/12-billing-credits/README.md` §8.1): `12.4.2-T1` and `12.8.3-T1` gain a soft `Depends on: 09.10.6-T1` because `registration.trial.credits` is the owner-editable source of truth 12 reads on signup grant.
- Reused: `09.10.2-T1`'s settings API (`GET /admin/settings`, `PUT /admin/settings/{integration}` with `If-Match`) — this task adds **no new route**, only the `registration` integration's key schema/validators consumed by that shared API; `09.3.1-T3`'s `IRegistrationPolicyProvider` interface and `RegistrationPolicy(RegistrationMode Mode, IReadOnlySet<string> DisposableDomains)` record (extended per W3 CR-9 to also carry `TrialCredits` via this task's implementation, not the interface itself if the interface stays two-field — see Design).

## Design

```csharp
// Domain/Registration/RegistrationMode.cs (extends 09.3.1-T3's enum; this task adds `Invite` if not already present)
public enum RegistrationMode { Closed, Invite, Open }

// Application/Abstractions/Registration/RegistrationSettings.cs — this task's read model,
// separate from 09.3.1-T3's RegistrationPolicy(Mode, DisposableDomains) record so the trial-credit
// value (owned/validated here, consumed by 12) does not force a signature change on 09.3.1-T3's port:
public sealed record RegistrationSettings(RegistrationMode Mode, IReadOnlySet<string> DisposableDomains, int TrialCredits);

// Infrastructure/Persistence/Settings/DbRegistrationPolicyProvider.cs
public sealed class DbRegistrationPolicyProvider(DbSettingsProvider settings) : IRegistrationPolicyProvider
{
    // reads registration.mode / registration.disposable_domains via settings.GetAsync<T>(integration, key, ct)
    // (09.10.1-T1's DbSettingsProvider — no new abstraction), maps to RegistrationPolicy(Mode, DisposableDomains);
    // TrialCredits is exposed via a second method GetTrialCreditsAsync(ct) for 12's read (W3 CR-13), since
    // IRegistrationPolicyProvider's shape is 09.3.1-T3's and out of this task's scope to widen without a CR.
}

// Application/Features/Admin/Settings/RegistrationSettingsValidator.cs
public sealed class RegistrationModeValidator   // registers with 09.10.2-T1's generic per-key validator dispatch
{
    // mode: must parse to RegistrationMode enum → else 400 setting_invalid
    // disposable_domains: array, each entry lowercase + IDN-normalized (`IdnMapping.GetAscii` round-trip check),
    //   no wildcards (`*`/`?` rejected), max 200 entries → else 400 setting_invalid
    // trial.credits: int, 0..10000 inclusive → else 400 setting_invalid
}
```

**No new HTTP route.** `registration.mode`/`registration.disposable_domains`/`trial.credits` are written through `09.10.2-T1`'s `PUT /admin/settings/registration` (existing integration, `If-Match`); this task supplies only: (a) the per-key validators registered into that generic dispatch, (b) `DbRegistrationPolicyProvider` wired as the DI implementation of `09.3.1-T3`'s `IRegistrationPolicyProvider` (replacing whatever placeholder 09.3.1-T3 shipped with), (c) a `GetTrialCreditsAsync` read for 12's signup-grant handler (soft dependency, W3 CR-13). Caching: reuses `09.10.2-T1`'s settings hot-reload (≤ 30 s), no separate cache.

`POST /auth/register` behaviour per mode (owned by 09.3.1-T3/09.3.1-T2, consumed here only as a contract check): `closed` → 403 `registration_closed`; `invite` → 09.3.1-T3's invite-code rule; `open` → 09.3.1-T2's disposable-domain + CAPTCHA + breach checks. This task's job ends at supplying a correct `RegistrationPolicy`/`TrialCredits` value — it does not touch the register handler.

## Steps

1. Add `RegistrationMode` enum value `Invite` (extends 09.3.1-T3's if it shipped with only two values — W3 CR-12 correction) and `RegistrationSettings` record.
2. Implement `DbRegistrationPolicyProvider : IRegistrationPolicyProvider` over `09.10.1-T1`'s `DbSettingsProvider`; register in DI replacing 09.3.1-T3's own default provider.
3. Add `RegistrationModeValidator`/domain/trial-credits validators, registered into `09.10.2-T1`'s per-`(integration, key)` validator dispatch table.
4. Add `GetTrialCreditsAsync(ct)` to the provider (or a narrow `ITrialCreditsReader` if 12 prefers a separate port — coordinate via the soft dependency, not a new HTTP route).
5. Seed migration data: ensure `registration.mode = 'closed'` (P default, WT24) exists as a `system_settings` row (idempotent seed, no new migration file — `09.2.5-T1`'s seed script gains three rows).
6. Tests (below).

## Acceptance checks

- Given an owner, When it `PUT`s `registration.mode = "invite"` via `09.10.2-T1`'s settings route, Then `IRegistrationPolicyProvider.GetPolicyAsync()` returns `Mode = Invite` within the settings hot-reload window (≤ 30 s), and `POST /auth/register` starts honouring the invite-code rule.
- Given an owner, When it `PUT`s `registration.mode = "not_a_mode"`, Then the response is 400 `setting_invalid` and no row changes.
- Given `disposable_domains` containing a wildcard entry, When submitted, Then the response is 400 `setting_invalid` before any write.
- Given `trial.credits = 10001`, When submitted, Then the response is 400 `setting_invalid`.
- Given `trial.credits = 500`, When 12's signup-grant handler reads it, Then it receives exactly `500` via `GetTrialCreditsAsync` — no second source of truth exists.
- Given the P default, When the system is freshly seeded, Then `registration.mode` reads `closed` (WT24).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| `disposable_domains` entry with mixed-case Unicode (e.g. `MÜLLER.de`) | IDN-normalized to lowercase ASCII (`xn--mller-kva.de`) before storage; comparison at register time is on the normalized form |
| Settings row missing entirely (fresh environment, seed not yet run) | `DbRegistrationPolicyProvider` falls back to `Mode = Closed`, empty domain set, `TrialCredits = 0` — never throws, matches the P default (WT24) |
| 12 calls `GetTrialCreditsAsync` before this task's seed runs | Same fallback (`0`) — 12 must treat `0` as "no trial", not an error |
| Concurrent `PUT` to two different `registration.*` keys | Each key is a separate `system_settings` row; `09.10.2-T1`'s per-row `If-Match` prevents lost updates per key, not across keys (accepted, D6/D7 scope) |

## Notes

- Reuses: `09.10.1-T1`'s `DbSettingsProvider`, `09.10.2-T1`'s settings API/validation dispatch/hot-reload, `09.3.1-T3`'s `IRegistrationPolicyProvider` port and `RegistrationPolicy` record shape. No new table, no new route, no new NuGet package.
- `[INFERENCE]`: whether `TrialCredits` is exposed via a widened `RegistrationPolicy` record or a separate `GetTrialCreditsAsync` method — chosen as the latter to avoid an unrequested signature change to 09.3.1-T3's signed port; the TL may prefer widening `RegistrationPolicy` instead at DoR.
- `registration` integration itself (non-secret, no base URL, not critical) is unchanged — this task adds key-level validators and the provider only, never a second settings integration (W3-6, D20).
