## Goal

When the web surface is unreachable (e.g. every owner locked out, or an owner-action dispute needs an operator-forced resolution), a platform operator runs a one-shot CLI image against the production database to recover an owner, restore a demoted owner, or force-apply/reject a stuck request/change — with no HTTP route, ever (D16).

- W3-11/F16: no `nts-admin` (or one-shot job image) exists in plan 11 yet; W3 CR-6 proposes plan-11 task `11.6.4-T1` (S 0.5, one-shot image + platform job manifest) — **this task's Depends-on edge is `[OPEN]`** until the TL applies that CR; this file specifies the CLI's own code (Application-layer commands + Worker-host verb group), not the container/deploy manifest (11's).
- §C10 W3-TL7 (n/a, refers to 09.3.1-T2) — not applicable here; the relevant ruling is D16 itself (binding, not proposed).
- Reused, never re-implemented: `09.9.2-T2`'s `nts-worker` verb-host pattern (`nts-worker flags list|set`, plain-table output, exit codes, no listener) — `nts-admin` follows the **same** hosting shape (`[AllowAnonymousRequest]` commands dispatched via `ISender`, no web listener, reads `nts/<env>/worker/*`-equivalent secrets); `09.10.4-T1`'s `ISecurityAlerter` port (D17); `09.10.4-T2`'s `owner_action_requests` apply/cancel semantics (`resolve --apply|--reject` forces the **same** state machine, never a second one); `09.10.2-T2`'s `system_setting_changes` apply/cancel semantics (`resolve --change` forces that table's state machine).

## Design

```csharp
// Application/Features/Ops/OwnerRecovery/RecoverOwnerCommand.cs
[AllowAnonymousRequest]                                   // CLI-only, no HTTP endpoint (D16, mirrors 09.9.2-T2's SetFeatureFlagCommand)
public sealed record RecoverOwnerCommand(string Email) : ICommand<ErrorOr<OwnerActionOutcome>>;
[AllowAnonymousRequest]
public sealed record RestoreOwnerCommand(string Email, string? DemoteEmail) : ICommand<ErrorOr<OwnerActionOutcome>>;
[AllowAnonymousRequest]
public sealed record ResolveOwnerRequestCommand(Guid? RequestId, Guid? ChangeId, bool Apply)
    : ICommand<ErrorOr<OwnerActionOutcome>>;

public enum OwnerActionOutcome { Applied, PreconditionFailed, EnvironmentError }
```

**`owner recover --email <e>`.** For a **sole** active owner (no other active owner in `users`): applies immediately (no time-lock — this *is* the break-glass path, D16 "Env break-glass is the only immediate path" reused here for the CLI's own bypass) — clears the authenticator key, all recovery codes and `two_factor_enabled` (forcing re-enrolment; MFA is mandatory for owners), calls `RevokeAllFamiliesAsync` (every session, not just a stamp rotation), rotates the security stamp (`ISecurityEventWriter.RotateStampAsync`, D9), issues a one-time password-reset token (reuses 09.3.3-T1's minter) and delivers the reset link through the signed e-mail pipeline (`IEmailSender.QueueAsync`, `password_reset` template); only with an explicit `--tty-only` flag (for a suspected mailer outage) is the link instead printed **exclusively to the interactive terminal** behind an operator acknowledgement prompt — never to a redirected stream or a platform job log (§C5 "never in a log"). **When other active owners exist** (not sole), `recover` no longer refuses: it calls `IOwnerActionRequester.RequestAsync(OwnerActionKind.MfaReset, targetUserId, reason, requestedByUserId: null, ct)` (a `system`-originated row) and prints the pending request id; exit `0` either way.

**`owner restore --email <e> [--demote <other>]`.** Precondition: `<e>` was demoted from owner within `OwnerGovernanceOptions.DisputeFreezeDays` (30 d, reuses `09.10.4-T4`'s dispute-window column) — else `PreconditionFailed`. In the same transaction: restores the role, optionally demotes `--demote <other>` (guarded: cannot demote the last remaining owner post-restore → `PreconditionFailed`, D8 `last_owner` reused as the CLI's own precondition, not a second rule), **sets `owner_dispute_freeze_until = now + 30 d`** on the restored user (HL:292), **cancels every pending/disputed `owner_action_requests` row involving the restored user** as either target or requester (via `09.10.4-T4`'s `IOwnerRequestCleanup`), **resets the restored user's target-cancel budget** (prior cancels of requests against them no longer count toward the 1-per-30-days cap) and **resets the restored user's MFA/credentials** (clears the authenticator key/recovery codes, forces a password reset through the same pipeline as `recover`) so a potentially-compromised account is not simply reinstated with its old factors intact (HL:292).

**`owner resolve --request <id>|--change <id> --apply|--reject`.** Dispatches directly into **09.10.4-T2**'s (`owner_action_requests`) or **09.10.2-T2**'s (`system_setting_changes`) existing apply/reject transaction under a `system` actor, bypassing only the *time-lock wait*, never the serializable re-checks (role, `last_owner`, `owner_dispute_freeze_until`) those handlers already perform. Precondition: the target row is `pending` (or `disputed` for `--request`, per D8's "applies only by a third owner or `nts owner resolve`") — else `PreconditionFailed` ("not pending/disputed — nothing changed").

**Every run** (all three verbs): one `audit_logs` row (`actor_type = system`, `category = account_security`, `data = { verb, target, outcome }`, operator identity read from the platform job/exec audit log — `[INFERENCE]` exact field name `Environment:PlatformJobExecutor` since plan 11 has not named it yet, tracked `[OPEN]`), and one `ISecurityAlerter` call (D17, e-mails every owner) — both **inside** the same transaction as the state change so a crash after the DB write cannot silently skip the alert (mirrors D9's one-writer transaction shape).

**Exit codes** (D16, verbatim — note these differ from `09.9.2-T2`'s `0/1/2`): `0` applied; `2` precondition failed (nothing changed); `3` environment/configuration error (bad connection string, missing secret). Never prints a connection string or a stack trace (mirrors `09.9.2-T2`'s CLI hygiene rule).

## Acceptance checks

- Given a sole active owner account, When `nts owner recover --email <e>` runs, Then the authenticator key/recovery codes/`two_factor_enabled` are cleared, every refresh-token family is revoked, the stamp is rotated, a one-time reset link is delivered via the signed e-mail pipeline (or, with `--tty-only`, printed only to the interactive terminal behind an operator acknowledgement — never to a log), an `audit_logs` row (`actor_type = system`, `category = account_security`) exists, and every owner (i.e. just that one) receives the D17 security alert; exit code `0`.
- Given a non-sole-owner account, When `recover` targets it, Then a `system`-originated `owner_action_requests` row (`action = mfa_reset`, `requested_by IS NULL`) is created in `pending` state, the target's MFA/credentials are untouched until an approval/time-lock applies it, and exit code is `0` with the pending request id printed.
- Given an owner demoted 10 days ago, When `restore --email <e>` runs, Then the role is restored in the same transaction as the audit row and alert; exit code `0`.
- Given the same restore, Then `owner_dispute_freeze_until` is set to 30 days from now, every pending/disputed `owner_action_requests` row naming the restored user (as target or requester) is cancelled, the restored user's target-cancel-budget counter is reset, and their authenticator key/recovery codes/`two_factor_enabled` are cleared with a password-reset link delivered the same way as `recover`.
- Given an owner demoted 40 days ago, When `restore` runs, Then exit code `2`, nothing changes.
- Given a `pending` `owner_action_requests` row, When `resolve --request <id> --apply` runs, Then `09.10.4-T2`'s serializable apply transaction runs exactly as it would for a third-owner approval, under a `system` actor; exit code `0`.
- Given a `disputed` `owner_action_requests` row and no third owner exists, When `resolve --request <id> --reject` runs, Then the request moves to a terminal rejected state and exit code `0` (D8 "applies only by a third owner or `nts owner resolve`" is satisfied by this verb).
- Given a bad `DB_CONNECTION`, When any verb runs, Then exit code `3` and no stack trace or connection string is printed.
- Given the built CLI assembly, When the architecture test runs, Then it has no reference to `NightTales.Api`.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| `recover --email` on an unknown e-mail | `PreconditionFailed`, exit `2` — no enumeration risk (this is an operator-only CLI against a trusted DB connection, not a public surface, so timing-safety is not required here) |
| `resolve --request` and `--change` both given | Rejected at CLI parse time, exit `3` (configuration error — mutually exclusive args) |
| `resolve --request <id>` where the id does not exist | `PreconditionFailed`, exit `2` |
| `restore --demote <other>` where `<other>` is not currently an owner | `PreconditionFailed`, exit `2`, nothing changes (no partial restore-without-demote) |
| Alert send fails (`ISecurityAlerter` throws) after the DB transaction committed | The transaction already committed the state change and audit row (D9-style ordering); the CLI reports exit `0` with a stderr warning that the alert failed — [INFERENCE] since D16 does not specify alert-failure behaviour for the CLI path, unlike D14's P1-on-send-failure for the web alerter (09.10.4-T3) |
| Two operators run conflicting `resolve` calls concurrently on the same request | Second loses on the underlying `owner_action_requests` transaction's own concurrency guard (09.10.4-T2's, not duplicated here) — reported as `PreconditionFailed`, exit `2` |
