## Goal

An admin can operate the platform without a database console: list and act on render jobs, read usage/moderation/quota/reports and (read-only) deletion requests, all behind one authenticated `/api/v1/admin` group that answers 404 — never 403 — to anyone who is not an admin/owner. This task owns the group itself, its policies, its pagination helper and its audit wiring; it does **not** own user management (09.10.5-T1) or any billing route (plan 12).

**Group and policies.** One `MapGroup("/api/v1/admin")` with a group-level fallback: any request that fails both `AdminPolicy` (`RequireRole(Role.Admin, Role.Owner)` — an owner passes the admin subset too, 09 W3 CR-33) and `OwnerPolicy` (`RequireRole(Role.Owner)` for the routes that need it) is mapped by the existing 09.1.4-T1 authorization-failure handler to **404** `not_found` (never the framework's default 403) — a single `IAuthorizationMiddlewareResultHandler` override registered once, shared by every task in this wave that adds an `/admin/*` route (D5). None of this task's own routes require `OwnerPolicy` or `IReauthGuard` (those are 09.9.2-T1's `PATCH /admin/feature-flags/{key}` and 09.10.2/09.10.4's owner-only routes).

**Render-job ops handlers.**
- `AdminListRenderJobsQuery`: `IReadDb.Query<RenderJob>()` (no tenant filter — `IgnoreQueryFilters(["tenant"])`, allowed because this file lives under `Application/Features/Admin/**`), optional `Status` filter, keyset on `(Id DESC)` (render_jobs has no `created_at`, 09.6.1-T1:172), reuses the `Cursor`/`Take(limit+1)` pattern verbatim from `09.5.1-T1`.
- `AdminRetryRenderJobCommand`: loads the job via `ISystemWorkQuery`-style admin read (no tenant scope), requires `Status == Failed`, else 409 `episode_invalid_state` (mirrors `09.6.4-T1`'s own terminal-state guard, D5's "reuses the user command's domain method"); calls `IRenderRetryPolicy.CreateRetryAsync(failed, ct)` (09.6.3-T1's existing method — re-runs the budget guard + credit reservation + enqueues `SubmitRenderJob` in the same transaction) so no second retry implementation exists.
- `AdminCancelRenderJobCommand`: thin admin wrapper that dispatches the **same** `CancelRenderCommand(RenderJobId)` (09.6.4-T1) under an admin-scoped `ISystemContext.For(job.UserId)`, so the state table (queued/submitted/running/ingesting/terminal) and the refund-on-poller-terminal rule are not duplicated.

**Reports/moderation/usage/quota/deletion-requests.** All `[NotAudited]` reads except `AdminUpdateReportCommand` (`[Audited]`). `AdminReportDto` masks `reporter_email` to `a***@domain` in the projection (SQL, never raw) — the raw address stays owner-only (C5 "Admin PII"). `AdminListDeletionRequestsQuery` is a straight read of 13's `data_deletion_requests` — no write, no engine, no retention logic; it lives here only because it is registered on this admin group (W3 CR-16). `GET /admin/kpis?window=7|30` is mapped on the **same** `MapGroup` by 08.1's own handler (08 CR-8) — this task adds the routing hook only, no KPI aggregation logic.

**Tenant-bypass allow-list.** Every route this task adds is appended as a new row to `09.2.3-T2`'s cross-tenant route table, never to a separate bypass mechanism (D5, C5).

## Acceptance checks

- Given a non-admin authenticated user, When it calls any route in this task, Then the response is 404 `not_found` (never 403).
- Given an admin, When it calls `GET /admin/render-jobs?limit=5`, Then it receives ≤ 6 rows internally trimmed to 5 with a `nextCursor`, and a second call with that cursor returns the next page with no overlap.
- Given a render job in `failed`, When an admin calls `POST /admin/render-jobs/{id}/retry`, Then a new `render_jobs` row (`attempt+1`, `queued`) is created in the same transaction and `SubmitRenderJob` is enqueued.
- Given a render job in `succeeded`, When an admin calls `POST /admin/render-jobs/{id}/retry`, Then the response is 409 `episode_invalid_state` and no row is created.
- Given a render job in `submitted`, When an admin calls `POST /admin/render-jobs/{id}/cancel`, Then `CancelRenderCommand`'s existing `RequestCancel` path runs (no refund yet) — no second cancel state machine exists.
- Given `GET /admin/reports`, When the response is inspected, Then every `reporterEmailMasked` matches `^.\*\*\*@` and no field contains the raw address.
- Given `GET /admin/deletion-requests`, When called, Then no write ever occurs against `data_deletion_requests` from this task's code path (grep-provable: no `INSERT`/`UPDATE`/`DELETE` in the query handler).
- Given the cross-tenant route table test, When it runs after this task, Then every route added here is present as a row (test fails otherwise — no separate bypass list exists).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Retry called on a job with no failed attempts yet (`queued`/`running`) | 409 `episode_invalid_state`, no row created |
| Retry called twice concurrently on the same failed job | Second transaction loses on the render_jobs unique partial index (one active job per episode) → 409 `concurrency_conflict`; client retry sees the new `queued` row |
| Cancel called on a job already `cancelled` | 204, idempotent, no second outbox row (delegates entirely to `09.6.4-T1`'s existing idempotency) |
| `GET /admin/usage` with `to < from` | 400 `validation_failed`, field `to` |
| `PATCH /admin/reports/{id}` with an unknown `status` enum value | 400 `validation_failed` |
| `GET /admin/deletion-requests` when 13's table has zero rows | 200 `{ items: [], nextCursor: null }`, never 404 |
| Admin authorization handler double-registered by a second task in this wave | Guarded by a DI check (`TryAddSingleton`) — only 09.9.1-T1 registers it; other tasks' routes just use `RequireAuthorization("AdminPolicy")` |
| `GET /admin/kpis` called before 08.1's handler class is registered | [OPEN] cross-folder ordering — 08.1-T1 soft dependency; this task's routing hook is a no-op stub returning 501 until 08.1-T1 lands, never a fabricated KPI body |
