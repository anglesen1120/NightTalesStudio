# 09.9.2-T1 — `IFeatureFlagWriter` + `PATCH /admin/feature-flags/{key}`

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 09.9.2 | S (0.5) | BE | 09.9.2-T2 | 06.5.2-T1 (W3 CR-15), 10.9.1-T1 (09 W3 CR-hand-off) | S · M2 |

## Goal

An admin or owner flips an existing feature flag (`youtube_publish`, `tiktok_publish`, `billing_enabled`) with an `If-Match` ETag, and the change reaches both the Api and the Worker caches without a restart. This task is the **only** flag write path (D14, D20 "no second feature-flag store"); flag **creation** stays with the signed `nts-worker flags set` CLI (09.9.2-T2).

## Inputs

- `../README.md` §C3 **D14** (`IFeatureFlagWriter.SetAsync`, `feature_flags_changed.v1`, `If-Match "ff-<xmin>"`, owner-or-admin audited, 404 on unknown key, key regex `^[a-z][a-z0-9_]{2,39}$`, `billing_enabled` gating rule — must never gate webhooks/payment reads/refund-requests/sync jobs).
- §C3.1 route row `PATCH /admin/feature-flags/{key}` — `AdminPolicy` + `IReauthGuard`, `If-Match` required, body `{ enabled, note? }` → 200 `{ key, enabled, updatedAt }`.
- F05/W3 CR-11: this is the corrected owner of the flag-write path (`09.9-platform/plan.md`:174 previously misattributed it to 09.9.1-T1); this task's Depends-on edge to `09.9.2-T2` (the read path/table owner) is symmetric.
- Reused: `09.9.2-T2`'s `feature_flags` table (no new migration — table exists), `IFeatureFlags`/`CachedFeatureFlags` read path (evicted, never re-implemented), the `LISTEN`/outbox eviction pair (`FeatureFlagsCacheInvalidator`/`FeatureFlagsChangedHandler`); `09.10.4-T1`'s `IReauthGuard.RequireRecentAsync`; `09.6.1-T1`'s `"ep-" + xmin` ETag pattern (same shape, `"ff-" + xmin`); `09.3.6-T1`'s `[Audited]`.

## Design

```csharp
// Application/Abstractions/Flags/IFeatureFlagWriter.cs
public interface IFeatureFlagWriter
{
    Task<ErrorOr<FeatureFlagDto>> SetAsync(string key, bool enabled, uint expectedXmin, CancellationToken ct);
}
public sealed record FeatureFlagDto(string Key, bool Enabled, DateTimeOffset UpdatedAt);

// Application/Features/Admin/Flags/SetFeatureFlagAdminCommand.cs
[Audited("flag.changed", Category.Support, Visibility.Internal)]
public sealed record SetFeatureFlagAdminCommand(string Key, bool Enabled, string? Note, string IfMatch)
    : ICommand<ErrorOr<FeatureFlagDto>>;
```

Handler (one transaction, D5):
1. Validate `Key` against `^[a-z][a-z0-9_]{2,39}$` → 400 `validation_failed` on mismatch.
2. `SELECT xmin, enabled FROM feature_flags WHERE key = @key` — 0 rows → 404 `not_found` (creation is the CLI's, D14).
3. `IfMatch` parsed as `"ff-" + xmin`; mismatch → 412 `feature_flag_conflict` (09 W3 CR-31) via the existing `RequireIfMatch` endpoint filter (same shape as `09.6.1-T1`'s `"ep-" + xmin`).
4. `UPDATE feature_flags SET enabled = @enabled WHERE key = @key AND xmin = @expectedXmin RETURNING xmin, updated_at` — 0 rows updated (raced) → 409 `concurrency_conflict`.
5. In the same transaction: `IAuditWriter.WriteAsync(new AuditEntry { Action = "flag.changed", Category = Support, Visibility = Internal, Data = { key, enabled, note } })` (§C3.4: `flag.changed` is frozen exactly for this — internal/support, not exposed to `/me/activity`); append outbox `feature_flags_changed.v1 { Key, Enabled, OccurredAt }`; the eviction path (Api `LISTEN` + Worker outbox handler) is `09.9.2-T2`'s existing infrastructure — this task appends the event, never invalidates the cache directly.
6. Route: `PATCH /admin/feature-flags/{key}` on `09.9.1-T1`'s `/api/v1/admin` group, `.RequireAuthorization("AdminPolicy")`, `.AddEndpointFilter<RequireReauth>(TimeSpan.FromMinutes(5))`, `.AddEndpointFilter<RequireIfMatch>()`.

The `billing_enabled` gating boundary (D14: gates `POST /billing/checkout`/`/billing/promo/redeem` only, never webhooks/payment reads/refund-requests/sync jobs) is enforced by the **consumers** of `IFeatureFlags` (plan 12's routes), not by this task — this task only writes the row and the event; no route in this folder reads `billing_enabled`.

## Steps

1. Add `IFeatureFlagWriter`/`FeatureFlagDto` in `Application/Abstractions/Flags/`.
2. Implement `EfFeatureFlagWriter` in `Infrastructure/Persistence/Flags/` using the existing `AppDbContext.FeatureFlags` set (no new `DbSet`, no migration — table from `09.2.2-T2`).
3. Add `SetFeatureFlagAdminCommand` + handler; append the outbox event via the existing `IOutboxWriter` (Part A D11), never a direct `NOTIFY` (that stays the CLI's own path in `09.9.2-T2`).
4. Add the `PATCH /admin/feature-flags/{key}` route on `09.9.1-T1`'s group with `RequireIfMatch` + `RequireReauth(5 min)` filters.
5. Add the route to `09.2.3-T2`'s cross-tenant allow-list (feature_flags is not `IUserOwned`, so this route is a tenant-bypass entry).
6. Tests (below).

## Acceptance checks

- Given an admin with a valid `If-Match`, When it `PATCH`es an existing flag's `enabled`, Then the response is 200 with the new `updatedAt`, `feature_flags.enabled` is updated, exactly one `audit_logs` row and one outbox `feature_flags_changed.v1` row exist.
- Given a stale `If-Match`, When the same request is retried, Then the response is 412 `feature_flag_conflict` (09 W3 CR-31) and `feature_flags.enabled` is unchanged.
- Given an unknown key, When `PATCH`ed, Then the response is 404 `not_found` and no row is created (creation stays with the CLI).
- Given a key that fails the regex (e.g. `"Youtube_Publish"`), When `PATCH`ed, Then the response is 400 `validation_failed` before any DB read.
- Given the Worker's cached copy of a flag, When the Api commits a flag change, Then the Worker's `IFeatureFlags.IsEnabledAsync` reflects it within 30 s via the existing `LISTEN`/outbox eviction (no new eviction path built here).
- Given no recent re-auth, When `PATCH` is called, Then the response is 401 `reauth_required` before the ETag or key checks run.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Two admins PATCH the same key concurrently | Second loses on `xmin` → 412 `feature_flag_conflict`; the client re-fetches and retries with the new ETag |
| `PATCH` with `enabled` already equal to the current value | 200, no-op update, audit row still written (state transitions are recorded even when unchanged, per BD15 convention) |
| `note` field omitted | Allowed (`string?`); stored as `null` in `audit_logs.data.note` |
| Outbox append fails mid-transaction | Whole transaction rolls back (D11 same-transaction guarantee); no partial `feature_flags` update without an event |
| `IReauthGuard` window just expired between filter check and handler execution | Re-checked only once by the endpoint filter (accepted race, ≤ a few ms, consistent with `09.10.4-T1`'s existing `RequireReauth` semantics) |
