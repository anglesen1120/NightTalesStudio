## Goal

In P an operator can switch a feature off without a deploy, and a disabled feature is **indistinguishable from a missing route**: a guarded endpoint answers **404 `feature_disabled`** (never 403), within 30 s on every instance and immediately in the common case; every change writes an `audit_logs` row. Consumers (02.7, 02.8.3, 06) attach the guard themselves (README BD1).

## Design

### Read port and cache (Application + Infrastructure)

```csharp
// Application/Abstractions/Flags/IFeatureFlags.cs
public interface IFeatureFlags
{
    Task<bool> IsEnabledAsync(string key, CancellationToken ct);
}

// Infrastructure/Persistence/Flags/CachedFeatureFlags.cs
public sealed class CachedFeatureFlags(IFeatureFlagReader reader, IMemoryCache cache) : IFeatureFlags
{
    // cache key "flags:v1:{key}" → record CacheEntry(bool Enabled, DateTimeOffset LoadedAt)
    // miss → reader.GetAsync(key) → store with FeatureFlags:CacheSeconds (30 s, absolute)
    // unknown key / DB failure → false (fail-closed). Never throws to the caller.
    public async Task<bool> IsEnabledAsync(string key, CancellationToken ct);
}

// Infrastructure/Persistence/Flags/FeatureFlagReader.cs
public interface IFeatureFlagReader { Task<bool?> GetAsync(string key, CancellationToken ct); }   // null = no row
// EF: Set<FeatureFlag>().AsNoTracking().Where(f => f.Key == key).Select(f => (bool?)f.Enabled).SingleOrDefaultAsync(ct)
```

One row read per key per instance per 30 s (one indexed PK lookup, `AsNoTracking`, no N+1, no tracked graph). Key validation before any lookup: `^[a-z][a-z0-9_]{1,63}$` → invalid keys are rejected by the CLI, and a call with an invalid key from code answers `false`. `rules jsonb` is **not read in P** — the P reader answers from `enabled` only, and a seeded non-null `rules` value must never alter P behaviour (rule evaluation is `06.5.2`, S) **[RULED — README §B10 WT13]**.

### Guard filter (Api)

```csharp
// Api/Http/Filters/RequireFeatureFilter.cs
public static class FeatureFilters
{
    public static Func<EndpointFilterInvocationContext, EndpointFilterDelegate, ValueTask<object?>> RequireFeature(string key)
        => async (ctx, next) =>
             await ctx.HttpContext.RequestServices.GetRequiredService<IFeatureFlags>().IsEnabledAsync(key, ctx.HttpContext.RequestAborted)
                 ? await next(ctx)
                 : /* the 09.1.4-T1 catalogue mapping for Error.NotFound(ErrorCodes.FeatureDisabled) */;
}
```

- Off → the **same ProblemDetails** a handler error produces: `{ "type": "https://nighttales.app/errors/feature_disabled", "title", "status": 404, "code": "feature_disabled", "traceId" }` (D7). No handler execution, no exception, no 403.
- On → the request continues unchanged; the filter does not consume the body.
- Guarded routes are the consumers' (`02.7`, `02.8.3`, `06`); this task adds no route and edits no consumer file.

### Operator CLI (Worker host)

```
nts-worker flags list
nts-worker flags set <key> on|off
```

- Registered in the same verb host as `nodes list|set-state` (11.3.3-T1); the Worker has **no web listener** (11 §10:242), it reads `nts/<env>/worker/*` secrets and the shared `DB_CONNECTION`.
- `flags list` prints `key`, `enabled`, and `rules: (unused in P)`; no user data.
- `flags set` dispatches one Mediator command:

```csharp
// Application/Features/Platform/Flags/SetFeatureFlagCommand.cs
[AllowAnonymousRequest]                                    // CLI-only: no HTTP endpoint exists (D4)
public sealed record SetFeatureFlagCommand(string Key, bool Enabled) : ICommand<ErrorOr<FeatureFlagSetDto>>;

public sealed record FeatureFlagSetDto(string Key, bool Enabled, bool Changed);
```

  Handler (sealed, `ErrorOr`): validate the key format → `400 validation_failed`; `UPDATE feature_flags SET enabled = @e WHERE key = @k RETURNING true`; 0 rows → `404 not_found`; then `IAuditWriter.WriteAsync(new AuditEntry { ActorType = system, Data = { actor = "system:operator", key, enabled }, Category = support, Visibility = internal })` in the **same** UnitOfWork transaction (D5 + BD15), and `NOTIFY feature_flags_changed, '<key>'` in the same transaction (sent at commit). Action string `feature_flag_changed` is `[INFERENCE]`.
- Exit codes: `0` success (including "already in that state" → `Changed = false`), `1` validation, `2` DB/transport failure. Never print a connection string or a stack trace.

3. Add `FeatureFlagsCacheInvalidator` (`LISTEN`) + `FeatureFlagsChangedHandler`; register the handler in the Worker outbox handler registration and the invalidator in both hosts.
4. Add `SetFeatureFlagCommand` + handler + audit + `NOTIFY`; add the arch-test-safe `[AllowAnonymousRequest]` marker justification in the class comment.
5. Add `FeatureFilters.RequireFeature(key)` and reuse the 09.1.4-T1 code→ProblemDetails mapping (no duplicated error body writer).
6. Add the `flags` verb group to the `nts-worker` host next to the `nodes` verbs; wire `--json` output off (plain table) and the exit codes above.
7. Document the flag lifecycle in the plan README of the feature (`FeatureFlags:CacheSeconds`, the two eviction paths, the fail-closed rule).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Flag row missing / key typo in a route | `false` (fail-closed) + one warning log with the key only, rate-limited to 1/min per key |
| Database unreachable | `false`; readiness (`09.9.3-T1`) reports the DB failure separately; the request still gets 404 |
| `NOTIFY`/`LISTEN` connection lost | invalidator reconnects with backoff 1→30 s; the 30 s TTL bounds staleness; a lost notification is never fatal |
| Concurrent `set` and read | last committed write wins; the cache can serve the previous value for ≤ 30 s (single-row update, no lock needed) |
| `set` to the current value | no-op success, `Changed = false`, **no** audit row (nothing changed) — audited only on a real transition |
| `rules` non-null (seeded by 06.5.2 later) | ignored in P; must not alter behaviour **[RULED — README §B10 WT13]** |
| Flag checked on a route that also needs auth | the guard runs before authentication semantics matter — a disabled feature is 404 for everyone, which is the point of BD13 (no existence leak) |
| Cache stampede on a cold instance | one load per key; concurrent misses may both read (idempotent single-row read, acceptable) |

Rollback: delete the `.RequireFeature(...)` call on a route (additive), remove the `flags` verb; there is **no migration** to revert and no data to unwind. Keep the audit rows (they are history).
