## Goal

The API ships safe defaults: HTTPS-only surfaces with HSTS and hardening headers, a CORS allow-list reduced to `App:PublicOrigin`, a 1 MiB default request-body cap, an ASP.NET Core Data Protection key ring persisted in PostgreSQL and encrypted with the `DP_KEK` certificate, an `ITokenProtector` built on that ring with a purpose per channel connection, and a CI dependency-vulnerability gate.

## Design

### Data Protection key ring (WF15, W1)

```csharp
// src/NightTales.Infrastructure/Persistence/AppDbContext.cs  (09.2.1-T1 owns the file; this task extends it)
public sealed partial class AppDbContext : IdentityDbContext<AppUser, AppRole, Guid>, IAppDbContext, IDataProtectionKeyContext
{
    public DbSet<DataProtectionKey> DataProtectionKeys => Set<DataProtectionKey>();
}
```

```csharp
// Composition root (Api and Worker)
var kek = X509CertificateLoader.LoadPkcs12FromFile(cfg["DataProtection:KekPfxPath"]!, cfg["DataProtection:KekPfxPassword"],
                                                 X509KeyStorageFlags.EphemeralKeySet);
if (!kek.HasPrivateKey) throw new InvalidOperationException("DataProtection:KekPfxPath has no private key");
services.AddDataProtection()
        .SetApplicationName(cfg["DataProtection:ApplicationName"])            // "nts-<env>"
        .PersistKeysToDbContext<AppDbContext>()
        .ProtectKeysWithCertificate(kek);                                     // the DP_KEK certificate (11 §10:284)
```

Migration `<yyyyMMddHHmm>_09_DataProtectionKeys` (expand-only):

```sql
CREATE TABLE data_protection_keys (
    id            integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    friendly_name varchar(256) NOT NULL,
    xml           text         NOT NULL
);
CREATE UNIQUE INDEX ix_data_protection_keys_friendly_name ON data_protection_keys (friendly_name);
```

- The `xml` value is the key-ring payload **already encrypted** with the KEK certificate; the file is never written to disk in the Api/Worker (no `PersistKeysToFileSystem`), so the container's ephemeral filesystem holds nothing worth stealing.
- Key lifetime and rotation are the framework defaults (a new key every 90 days, old keys retained). **No job ever prunes this table** — removing a key makes earlier protected values unrecoverable (plan §11).
- Both Api and Worker read the ring from the same `AppDbContext`, so a value protected by one is unprotected by the other (11 §10:284 shares `DP_KEK`).

### `ITokenProtector`

```csharp
// Application/Abstractions/Security/ITokenProtector.cs
public interface ITokenProtector
{
    string Protect(string purposeSuffix, string plaintext);                            // BD12 signature
    bool TryUnprotect(string purposeSuffix, string cipher, out string plaintext);      // [INFERENCE] read side
}

// Infrastructure/Security/DataProtectionTokenProtector.cs
public sealed class DataProtectionTokenProtector(IDataProtectionProvider provider) : ITokenProtector
{
    // purpose = $"tokens.v1/{purposeSuffix}"      → IDataProtector cached per purpose (ConcurrentDictionary)
    // Protect    → Convert.ToBase64String(...)    → a wrong purpose throws CryptographicException → TryUnprotect returns false
}
```

- Purpose isolation is the security property: `tokens.v1/{connectionId}` for a channel connection (06). The **TOTP secret store does not use `ITokenProtector` at all** — it calls `IDataProtectionProvider.CreateProtector("identity.totp.v1")` **directly** on the shared ring (its purpose root is `identity.totp.v1`, not `tokens.v1/*`; going through `ITokenProtector` would silently produce `tokens.v1/identity.totp.v1` and break the isolation root) [RULED — README §B10 WT43]. A cipher protected for one purpose must fail for another (tested).
- Callers treat `TryUnprotect == false` as "invalid token" (a uniform error, never a stack trace); the protector logs nothing about the value (only the purpose on a failure, at `Warning`).
- Plaintext is never cached, copied into a record for logging, or put in an exception message. Constant-time comparison is not needed here (the framework's authenticated encryption is the check), but any caller comparing a token to a stored value uses `CryptographicOperations.FixedTimeEquals` (BD16).

### Headers, CORS, limits (BD12)

```csharp
app.UseHsts();                       // HSTS 1 y — Production only (never Development)
app.Use(async (ctx, next) => {       // hardening headers, written before the response body starts
    ctx.Response.Headers["X-Content-Type-Options"] = "nosniff";
    ctx.Response.Headers["Referrer-Policy"]        = "no-referrer";
    ctx.Response.Headers["X-Frame-Options"]        = "DENY";
    await next();
});
```

- HSTS: `UseHsts` with `MaxAge = 365 days`, `IncludeSubDomains = true` **[INFERENCE]**; HTTPS redirection stays outside `Development` (behind the 11 TLS terminator the app also trusts the forwarded proto — `KnownNetworks` is BD14/09.3.5-T1's, this task must not duplicate it).
- CSP applies to the **API docs page only** (BD12): `default-src 'none'; frame-ancestors 'none'; img-src 'self' data:` on the OpenAPI/Swagger HTML response. The SPA CSP + Trusted Types belong to plan 10.
- CORS: `App:PublicOrigin` is required, absolute, `https`, no trailing slash (validated at startup → fail fast with a fixed message); in `Development` only, `http://localhost:<port>` is also accepted (10 CR-3). The SPA is served from this same origin behind the LB (`../../10-web-ui/README.md` D3), so browsers never send cross-origin API calls in staging/prod; the two policies below stay as defence in depth and for tools. Two policies:
  - `spa` — `WithOrigins(origin)`, methods `GET,POST,PATCH,DELETE`, headers `Authorization, Content-Type, If-Match, Idempotency-Key`, **no** credentials; applied to the versioned API group. `Authorization` is in the allowed headers on **both** policies (the bearer token travels in the header; without it the preflight blocks every authenticated call) **[RULED — README §B10 WT42]**.
  - `spa-auth` — same origin **with** `AllowCredentials()`, applied only to `/api/v1/auth/*` (BD12: credentials only on auth routes; the refresh cookie needs it, BD3); same allowed headers including `Authorization` **[RULED — README §B10 WT42]**.
  No `AllowAnyOrigin`, no wildcard header reflection, no `AllowCredentials` on the general group.
- Request limits: `Kestrel:Limits:MaxRequestBodySize` = `1048576` (1 MiB) applied in `ConfigureKestrel`; per-endpoint overrides keep their own metadata (e.g. a render command with a large brief list) via `.WithMetadata(new RequestSizeLimitAttribute(bytes))` at the endpoint. A body over the cap is rejected by Kestrel with **413** before the handler (no ProblemDetails — documented in `plan.md` §9).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `DP_KEK` missing / wrong password | **fail fast at startup**, fixed message naming the config key (never the value); the orchestrator restarts the task and alerts |
| Key ring table missing (migration not applied) | the first `Protect`/startup call throws; the message names the missing migration — deploy order is migration-then-app (plan §11) |
| Certificate behind a proxy vs app instance | both Api and Worker must be given the same PFX; a mismatch shows as `TryUnprotect == false` on the other service (test covers it) |
| `TryUnprotect` on tampered ciphertext | framework throws `CryptographicException` → caught → `false`; callers answer a uniform `invalid_token` (no oracle) |
| Body over the limit | 413 from Kestrel before routing; no ProblemDetails (documented, and the SPA handles 413 generically) |
| CORS misconfiguration (`App:PublicOrigin` with a trailing slash) | startup fails, so a broken browser flow cannot ship silently |
| Vulnerability found in a transitive package | the CI step fails with the package id + advisory link from the JSON; the fix is a version bump or a documented, time-boxed exception in `tools/ci/check-vulnerable.py` (reviewable, not a silent `--no-restore`) |
| Development over HTTP | HSTS and HTTPS redirection stay off, headers stay on |

Rollback: restore the previous app image (the `data_protection_keys` table **stays** — dropping it destroys the ability to unprotect existing refresh/action tokens; plan §11). The vulnerable-package step can be made non-blocking only by an explicit, reviewed allow-list entry, never by deleting the step.
