## Design

Files (all new, under `web/e2e/journeys/`, following `10.10.2-T1`'s one-spec-per-journey convention):

- `saas-onboarding.spec.ts` (+ `.en.spec.ts`) — J-S1: register → verify e-mail (mail service, same as any P spec that reads `mail:8025`) → legal + 18+ acceptance dialog → `/billing` packages → checkout via the sandbox/fake provider return page (`page.route` fakes the provider redirect target, mirroring `10.10.2-T1`'s fake-Google precedent for OAuth-shaped flows) → `/billing/return` resolves `paid` → render an episode through to `queued` (reuses `10.10.2-T1`'s `pipeline-fiction` template as its first half, never duplicates it — imports the shared step helpers from `journey.ts`).
- `saas-admin-actions.spec.ts` — J-S2: `loginAsOwner` (or a seeded `admin` fixture account, reusing `09.2.5-T2`'s owner-seed pattern if a second seed is needed — `[OPEN]`, flagged to the TL, not invented here) → suspend a seeded user (`POST /admin/users/{id}/suspend`) → approve a seeded `pending_approval` credit-grant request (`10.9.4-T2`) → toggle a feature flag through `ReauthDialog` step-up (`PATCH /admin/feature-flags/{key}`, 401 `reauth_required` → dialog → retry once).
- CAPTCHA: the register step runs against Cloudflare Turnstile's documented **always-passes test site/secret key pair** (`[INFERENCE]` — the exact key strings are Cloudflare's public test constants, not this repo's; wired through the same `openai-stub`-style compose override this folder already owns, as `NTS_CAPTCHA_SITE_KEY`/the matching test secret on the Api side) so the widget renders and resolves without a real challenge; never the production site key.
- No new stub, no new compose service beyond the one CAPTCHA test-key env override; the sandbox provider return is a `page.route` fake, exactly like `10.10.2-T1`'s fake Google OAuth callback (WT-W2 precedent) — no real payment provider is contacted.

## Steps

1. Add the CAPTCHA test-key env override to `web/e2e/docker-compose.e2e.yml` (this folder's existing override file, one line — coordinated with `10.3.3-T2`'s widget contract, no new file).
2. Write `saas-onboarding.spec.ts`: register (202) → verify e-mail via the mail service → legal/18+ dialog → packages → checkout → `page.route` fake provider return → `/billing/return` `paid` → render to `queued`.
3. Write `saas-admin-actions.spec.ts`: seeded admin login → suspend user → approve credit-grant request → feature-flag toggle behind re-auth.
4. Add the `en` locale variant of `saas-onboarding.spec.ts` last (cheapest once the base file is stable, mirroring `10.10.2-T1`'s ordering rule).
5. Run `expectA11yClean` at each terminal screen of both journeys (register success, `/billing` packages, `/billing/return`, the three admin screens).
6. Wire both specs into the existing `e2e.yml` job (no new CI job; `10.10.2-T1`'s O-W4 asks already cover the stack flags this needs, `youtube_publish` excepted).

## Acceptance checks

- **Given** a fresh e-mail, **When** the onboarding journey runs, **Then** register answers 202, verify-e-mail completes via the mail service, the legal + 18+ dialog is accepted once, checkout resolves through the sandbox return page to `paid` with **no client-side credit grant**, and the subsequent render reaches `queued`.
- **Given** the CAPTCHA widget on the register step, **When** the test-key override is active, **Then** the widget resolves without a real Turnstile challenge and no request reaches the production Turnstile endpoint.
- **Given** a seeded user, **When** the admin journey suspends it, **Then** the user row shows `suspended` and a second suspend attempt is rejected per the existing admin contract.
- **Given** a seeded `pending_approval` credit-grant request, **When** the admin approves it, **Then** the request's status becomes resolved and the grant is reflected on a refetch (server state, no client arithmetic, A10).
- **Given** the feature-flag toggle, **When** `reauth_required` is returned, **Then** `ReauthDialog` succeeds and the toggle retries once, landing the new `enabled` value.
- **Given** every terminal screen in both journeys, **When** axe runs, **Then** `expectA11yClean` reports zero violations (10.10.1-T1's matrix rows for these screens are the manual-audit counterpart, not duplicated here).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Sandbox/fake provider return page never resolves to a terminal status | Journey fails loudly at the polling timeout (`10.8.1-T1`'s `expiresAt` → `failed`/`payment_expired`), not a silent skip |
| CAPTCHA test key rejected (misconfigured secret) | Preflight fails by name (mirrors `10.10.2-T1`'s WT-W1 preflight precedent), never a silent fallback to a token-less submit |
| Credit-grant request already resolved by another actor before the approve step | Journey asserts the 409 `grant_request_not_pending` path explicitly rather than treating it as flaky |
| Feature-flag toggle's re-auth dialog times out | Journey fails with the re-auth timeout surfaced, not retried indefinitely (single retry only, per the shared `ReauthDialog` contract) |
| `10.10.1-T1`'s extended a11y fixture not yet landed (soft dependency) | This task's own `expectA11yClean` calls use the harness already shipped by `10.10.2-T1`; no functional dependency on `10.10.1-T1`'s matrix file |
