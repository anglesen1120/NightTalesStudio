## Goal

A paid/platform POST carries one `Idempotency-Key` per **user intent** — generated when the user acts, reused
unchanged by every automatic retry (the single 401 retry of 10.2.1-T1) and by a manual retry after a network error,
and replaced only when the user starts a new intent — so a double click or a retried request can never produce two
server-side effects.

## Design

Files:
- `web/src/app/core/http/idempotency-keys.ts` (new) —
  ```ts
  export class IdempotencyIntent {
    readonly key: string;          // crypto.randomUUID(), 36 chars, within the API's 1–128 printable-ASCII rule
    readonly intent: string;       // e.g. 'episode.generate' — for the dev console and the store tests only
    private settled = false;
    get isSettled(): boolean { return this.settled; }
    settle(): void { this.settled = true; }
  }
  @Injectable({ providedIn: 'root' })
  export class IdempotencyKeys {
    begin(intent: string): IdempotencyIntent;   // always a NEW key
    newKey(): string;                           // crypto.randomUUID()
  }
  ```
- `web/src/app/core/http/http-context-tokens.ts` (changed, additive) — add
  `export const IDEMPOTENCY_INTENT = new HttpContextToken<IdempotencyIntent | null>(() => null);` next to the
  `SILENT_REQUEST` token defined by 10.2.1-T1.
- `web/src/app/core/http/http-context.ts` (changed, additive) — add
  `export function withIdempotency(intent: IdempotencyIntent): (ctx: HttpContext) => HttpContext` returning a
  context that sets `IDEMPOTENCY_INTENT`. Repositories call it; stores never build `HttpContext` themselves (D5).
- `web/src/app/core/http/idempotency.interceptor.ts` (new) —
  `export const idempotencyInterceptor: HttpInterceptorFn`: reads `req.context.get(IDEMPOTENCY_INTENT)`; when it is
  non-null and the method is not `GET`/`HEAD`/`OPTIONS`, clones the request with
  `setHeaders({ 'Idempotency-Key': intent.key })` **only if the header is not already present** (so a retried
  request keeps the same value and a generated client that sets its own key is not overwritten); otherwise passes
  the request through unchanged.
- `web/src/app/app.config.ts` (changed, 10.1.1-T1 file) — the interceptor is listed **before** `sessionInterceptor`
  in `provideHttpClient(withInterceptors([idempotencyInterceptor, sessionInterceptor]))`, so the 401 retry performed
  by `sessionInterceptor` clones a request that already carries the key and the header survives the retry
  (`HttpRequest.clone()` keeps headers and `context`).
- `web/src/app/core/http/index.ts` (changed) — export `IdempotencyKeys`, `IdempotencyIntent`,
  `withIdempotency`, `idempotencyInterceptor`.

Usage contract (documented in the two files' doc comments and asserted by tests — this is what 10.5.2-T1 follows):
```ts
// in a feature store, once per user click / form submit:
const intent = this.keys.begin('episode.generate');
const generation = this.session.generation();
const requestGeneration = this.requestGeneration; // reset/destroy/new intent increments it
this._busy.set(true); // private writable; public busy = this._busy.asReadonly()
// repo sends withIdempotency(intent) AND userAction() (WR11: this call came from a UI event, so a 401 may refresh
// even while the activity gate is idle) — one intent object is reused by every retry of this click
const result = await this.repo.generate(episodeId, { intent }, signal);
if (generation !== this.session.generation() || requestGeneration !== this.requestGeneration) return;
if (result.ok) intent.settle();        // success, or any non-retryable answer, ends this intent
else if (!isRetryable(result.error)) intent.settle();
```
- `begin()` is called at the top of the user-intent handler, never inside the repository and never inside a retry.
- A "Retry" button that re-runs the same failed intent reuses the **same** `IdempotencyIntent` object (the store
  keeps it in a signal next to the error), so the server sees the identical key and returns the original outcome
  instead of a second effect; a genuinely new click after success calls `begin()` again.
- Errors: 400 `idempotency_key_required` (the repository forgot `withIdempotency`) and 422
  `idempotency_key_reused` (same key, different body — a client bug) map through `AppErrorMapper` to
  `kind: 'client_bug'`, show the code-specific message and log one dev-console line with `code/status/traceId`
  only; both `settle()` the intent so the next click gets a fresh key.
- Capture the page/request and SessionStore generation with the intent; reset/destroy discards the open intent.
  Late success/error after that boundary cannot settle a newer intent, clear its busy signal or reinstall a retry
  action. Keep command body immutable for the intent; edits can start a new intent only after prior settlement.
  Generated transport lives in data-access. Story-generation consumer integration is planned under 02.2.2-T2,
  not implemented by this helper or proven available at the audited develop snapshot.

## Acceptance checks

- [ ] Two `run()` calls of one store intent (double click) reach the repository with **one** header value
      (`fakeRepo.keys` has length 2 with `new Set(keys).size === 1`).
- [ ] After `intent.settle()` and a new `begin()`, the key differs (UUIDv4 shape asserted).
- [ ] A 401 retry performed by `sessionInterceptor` shows the **same** `Idempotency-Key` on both attempts
      (one test with the two interceptors chained in `app.config` order).
- [ ] A "Retry" of a failed intent reuses the key; a retry of a *different* user action does not.
- [ ] `GET`s and requests without `withIdempotency(...)` carry no `Idempotency-Key` header (asserted for a list call
      such as `GET /api/v1/episodes`).
- [ ] Header value is 36 chars, printable ASCII, and never logged (console spy clean; no header echo in any
      dev-console line).
- [ ] 400 `idempotency_key_required` / 422 `idempotency_key_reused` render `errors.<code>` through
      `AppErrorMapper` with `kind: 'client_bug'` and no body content.
- [ ] No automatic retry of a paid POST is added by this task (only the existing one 401 retry), so a server-side
      duplicate effect cannot be produced by the client; nothing is persisted (no storage write in the test spies).
- [ ] Deferred result after session end/page destroy does not restore busy/error/retry UI or mutate a newer
      intent. Repeating the same intent preserves body/key; editing the body creates a new intent. Run full
      idempotency key/interceptor spec files with HttpClient providers before HttpClientTesting and verify no
      outstanding requests, including the existing chained 401 replay cases.
- [ ] a11y (D16) contract for consumers, documented in `idempotency-keys.ts` and checked in 10.5.2-T1's e2e: while
      an intent is open the triggering control is `disabled` **and** `aria-busy="true"` with a text/`Spinner`
      sibling (never colour alone), the failure path renders `FormErrorAlert` (`role="alert"`, focus stays on the
      retried control), and the double-click case must not announce twice (no duplicate live-region text). This
      task has no visual surface and therefore produces no component; the `OnPush`/input-output rule applies to the
      consumers.
- [ ] The wave-1 consumer route is marked unconditionally: `POST /api/v1/episodes/{id}/story/generate` requires the
      header (`02.2.2-T2:28`, `:114`), and 10.5.2-T1's e2e asserts one generation run for a double submit.
- [ ] vi and en keys for both codes exist (checked here by hand, enforced by 10.2.5-T1's parity check).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Repository forgets `withIdempotency` | server 400 `idempotency_key_required` → client-bug mapping; the store test in 10.5.2-T1 is the guard, and the header absence is visible in one dev-console line |
| Same key + different body (user edited the form between attempts while the intent stayed open) | 422 `idempotency_key_reused` → message + `settle()`; the next click gets a new key |
| Two tabs acting at once | two different keys (each tab has its own store instance) → two intents, which is correct: they are two user actions |
| `crypto.randomUUID` unavailable (very old browser / insecure context) | not supported in the wave-1 target matrix; `[OPEN]` if the e2e ever runs on an insecure origin, a `crypto.getRandomValues` UUIDv4 fallback is added then |
| Request already carrying `Idempotency-Key` (generated client or a retry clone) | left untouched — the "only if absent" rule is what makes the retry share the key |
| Session ends between attempts | the retry is never sent (10.2.1-T1 signs out); the intent is discarded with the store's `reset()` |
| Header on a non-paid route | harmless: the server only reads it where a filter requires it; the task still restricts marking to POSTs the plan marks as paid (wave 1: generate) |

## Notes

- Produces: `IdempotencyKeys`, `IdempotencyIntent`, `withIdempotency`, `idempotencyInterceptor` — reused by
  10.5.2-T1 (episode story generate) and by every later paid command (S phase, plan 12).
- Reuses: the interceptor-chain conventions and `core/http` layout of 10.2.1-T1/10.1.4-T1, `AppErrorMapper` from
  10.2.2-T1, `SESSION_SCOPED` (`reset()` drops an open intent) from 10.2.1-T1. Adds no UI component and no i18n
  key of its own (the two codes belong to the `errors` scope of 10.2.2-T1).
- Deliberately not built here: a per-request retry policy, a queue of unsent intents, offline replay (out of P
  scope), and an `Idempotency-Key` on GETs.
- **As-built surface for consumers** (`web/src/app/core/http/`, re-exported from `@core/http`):
  `IdempotencyKeys.begin(intent: string): IdempotencyIntent` (new UUID per call) and `newKey(): string`;
  `IdempotencyIntent` has a public constructor `(key, intent)`, `readonly key`, `readonly intent`, `isSettled`,
  one-way `settle()`; `withIdempotency(intent, ctx = new HttpContext()): HttpContext` (the second parameter lets it
  compose with `userAction()` / `silently()`: `withIdempotency(intent, userAction())`, plan text showed a curried
  `(ctx) => ctx` form); token `IDEMPOTENCY_INTENT`; `idempotencyInterceptor` (skips GET/HEAD/OPTIONS and unmarked
  requests, never overwrites an existing header). `app.config.ts` registers `[idempotencyInterceptor,
  sessionInterceptor]`. `AppErrorMapper`/`ERROR_CODES` (10.2.2-T1) and the `errors.idempotency_key_*` i18n keys
  already existed, so this task added no mapper or i18n change. Specs: `idempotency-keys.spec.ts`,
  `idempotency.interceptor.spec.ts` (the interceptor spec chains both interceptors in `app.config` order).
