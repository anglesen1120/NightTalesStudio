## Goal

Complete owner authentication in P: the MFA step inside `/login` (TOTP **or** one recovery code), the enrolment screen at
`/account/security/mfa-setup` (QR, manual key, code verification, the 10 recovery codes shown exactly once, regeneration behind
re-auth), and the shared `ReauthService` + `ReauthDialog` that turns a `401 reauth_required` into a password + code challenge and
retries the original call once. This task exists because owner login is always MFA and enabling autopilot needs re-auth (F04);
`10.9.5-T1` keeps only the S items (disable MFA for users, `/admin` redirect).

## Design

Extends `features/auth/` and adds one root `core/session` service plus one shared component.

- `features/auth/domain/mfa.port.ts` — `MfaRepository` (`setup()`, `verify(code)`, `regenerateRecoveryCodes()`), types
  `MfaSetup { secret, otpauthUri }`, `RecoveryCodes = readonly string[]` (exactly 10).
- `features/auth/data-access/mfa.repository.ts` — `MfaApiRepository implements MfaRepository` over `@shared/api`;
  `features/auth/data-access/auth.repository.ts` **gains** `loginMfa(mfaToken, code, mode)` (T1 declared the port without it).
- `features/auth/application/login.store.ts` (edited) — `LoginStep` widens to `'password' | 'mfa'`; `recoveryMode = signal(false)`;
  `submitMfa(code)` sends `code` in TOTP mode and `recoveryCode` in recovery mode (never both, C10); on `ok` →
  `SessionStore.signIn` + navigate [WR8]; on `invalid_mfa_code` keep the step with a retryable error; on `mfa_token_invalid`
  `backToPassword()` with `auth.mfa.challengeExpired`.
- `features/auth/application/enrolment.store.ts` — signals `step: 'loading'|'show'|'verify'|'codes'|'error'`, `setup`, `codes`,
  `error`, `confirmedSaved`; `load()` → `POST /me/mfa/setup`; `verify(code)` → `POST /me/mfa/verify` → `codes` (10) and
  `step 'codes'`; `regenerate()` → `ReauthService.ensureReauthenticated()` **then** `POST /me/mfa/recovery-codes`; `confirmSaved()`
  drops `codes` and returns to the shell (or `/login` when entered with the enrolment token).
- `features/auth/ui/mfa-setup-page/` — `PageHeader` + a `Stepper`-free 3-block layout (show → verify → codes):
  the QR `@defer (on viewport)` from `qrcode.toDataURL(otpauthUri)` rendered as `<img [src] alt="auth.enrol.qrAlt">` (never a
  link, never logged), the manual key through `CopyableCode` (10.1.3-T1, [WR4]), the code field, the recovery-code `<ol>` with a copy button per code
  plus a download (`auth.enrol.download` → `recovery-codes-YYYYMMDD.txt` through `shared/util/safe-filename.ts`), the "shown once"
  warning in `role="alert"`, and a `confirmSaved` checkbox that must be ticked before the primary action leaves the page.
  After `verify` the page shows `auth.enrol.reLogin` and routes to `/login` (an enrolment-only token cannot call anything else, C6).
- `features/auth/ui/login-page/` (edited) — the MFA block: `core.reauth`-independent `auth.mfa.*` copy, a single code field with
  `inputmode="numeric" autocomplete="one-time-code"`, a "use a recovery code" toggle that swaps the label/hint and the request mode,
  and a "back to password" link.
- `features/auth/auth.routes.ts` (edited) — add `/account/security/mfa-setup` with **one** guard:
  `canActivate: [mfaEnrolmentGuard]`, where that guard accepts a full session (`SessionStore.mode === 'full'`) **or** the
  enrolment-only token (`mode === 'enrolment'`). Angular's `canActivate` is AND, so listing `authGuard` **and** the enrolment guard
  together would bounce the enrolment-only owner to `/login` and kill the F04 flow — never do that (Notes).
- `core/session/reauth.port.ts` — `abstract class ReauthPort { abstract reauth(password, code): Promise<Result<{ reauthenticatedAt: string }>>; }`.
- `core/session/data-access/reauth.repository.ts` — `ReauthApiRepository` over `@shared/api` (`POST /auth/reauth`). The
  `data-access` directory is **mandatory**: D5 (`../README.md:135`) allows `@shared/api` only from `features/*/data-access/**` and
  `core/**/data-access`, and 10.1.2-T1's lint (`../README.md:112`) fails a file outside one.
- `core/session/reauth.service.ts` — `@Injectable({ providedIn: 'root' })` `ReauthService`:
  `ensureReauthenticated(): Promise<Result<void>>` opens `ReauthDialog` once (**single-flight**: concurrent callers share one
  promise and one dialog), resolves `ok()` after `200 { reauthenticatedAt }` — **no** client-side re-auth state is written, the
  server owns `reauthenticated_at` [WR8] — resolves `err(session_revoked)` and lets 10.2.1-T1 end the session after the 5th wrong
  attempt, and exposes
  `isDialogOpen: Signal<boolean>`. It registers a `reset()` with the session-scoped provider so an open dialog closes on logout (D6).
- `shared/ui/dialog/reauth-dialog/` — `ReauthDialog` component (D11: inputs/outputs only) with a typed reactive form

## Failure handling and edge cases

- **Enrolment token expires** (15 min) mid-enrolment: the next call answers 404 `not_found`; the page shows `auth.enrol.reLogin`
  and sends the owner back to `/login` (no retry).
- **`reauth_required` on `setup` from an authenticated session** (an owner re-visiting enrolment): open `ReauthDialog`, then retry
  `setup` once; a cancelled dialog leaves the page on a "re-auth required" state with a retry button — never a silent failure.
- **`409 concurrency_conflict`** on `setup`: a stale pending secret exists; call `load()` again (one retry, no loop) and keep the
  manual key and QR from the new response.
- **5 wrong enrolment codes**: the challenge stays alive through `invalid_mfa_code` (attempt counting is server-side); the UI only
  surfaces the error and, on `429`, the countdown. Recovery: leave and re-enter enrolment (the pending secret is regenerated).
- **Data-Protection failure server-side** (`invalid_mfa_code` for a secret that cannot be decrypted): surface the generic error;
  the owner can re-enrol. No client-side mitigation exists and none should be invented.
- **QR generation failure** (should not happen): the manual key and the URI's secret remain usable; the `@defer` block renders an
  `ErrorState` with a retry, and enrolment is still completable by hand.
- **Clipboard unavailable** (`navigator.clipboard` undefined on an insecure origin): the copy button falls back to selecting the
  text and announces `auth.enrol.copied` only after a successful selection.
- **Reload during the MFA step**: the `mfaToken` is memory-only, so the user returns to the password step; this is intended (no
  token in a URL or a storage) and is asserted.
- **Reload during enrolment `codes`**: the 10 codes are gone by design (`POST /me/mfa/verify` will not return them again) — the
  page warns *before* the reveal and requires `confirmSaved`; after a reload the owner can still log in with a TOTP code and
  regenerate codes behind a re-auth.
- **A second tab** holds a challenge or the enrolment flow: the server invalidates the previous `auth_challenges` row (one live
  challenge per user, `09.3.2-T3-…:58-61`), so one tab gets `mfa_token_invalid` → back to the password step; no client state is
  shared between tabs.
- **Logout while the dialog is open**: the session-scoped `reset()` closes it; a late 200 is ignored.
- **Bounded work**: MFA login = one POST; enrolment = one POST per step; regeneration = re-auth + one POST; no listing, no N+1, no
  poll, no timer other than `RetryCountdown`'s (cleaned up via `DestroyRef`).
