## Goal

Ship `/register` and `/verify-email`: the register form builds the **exact** SC30 body, handles every server outcome (mode `open`/`invite`/`closed`, CAPTCHA outcomes, `breached_password`, `rate_limited`) and always ends on the same neutral "check your e-mail" page with **no auto-login**; `/verify-email` reads its token from the URL **fragment**, removes it with `history.replaceState`, and renders verified / expired / invalid / resent.

## Design

Files under `web/src/app/features/auth/` (D2):

- `domain/register.model.ts` — `ConsentDocument`, `ConsentAcceptance`, `RegistrationMode`, `RegisterRequest`, `RegisterOutcome`, `VerifyEmailOutcome` (`plan.md` §3.2).
- `domain/register.port.ts` — abstract `RegisterRepository { register(req: RegisterRequest): Promise<RegisterOutcome>; verifyEmail(token: string): Promise<VerifyEmailOutcome>; }`.
- `data-access/register.repository.ts` — `RegisterApiRepository implements RegisterRepository`; maps DTO → model and `ProblemDetails` → `RegisterOutcome` via `AppErrorMapper` (D9); calls `@shared/api` only here (D5).
- `ui/register.page.ts` — typed Reactive Form: `email`, `password` (rules from `shared/util/password-rules.ts`, single implementation), `confirm`, `consents` (three checkboxes: `tos`, `privacy`, `age_18`), `inviteCode` (shown only when mode is `invite`), `CaptchaWidget` (present when mode is `open`, otherwise revealed after 400 `captcha_required`; never pre-loaded). **Mode source is F29 `[OPEN]`** — until it lands, `mode` is unknown and the fallback applies: widget revealed on 400 `captcha_required`, invite field revealed on the 400 09 names, closed/invite copy keyed off `registration_closed`.
- `ui/verify-email.page.ts` — reads `#token=`, `history.replaceState`, POST `/auth/verify-email`, renders the four outcomes.
- `ui/register.store.ts` — signals: `mode`, `captchaVisible`, `submitting`, `fieldErrors`, `formError`, `retryAfterSeconds`; `submit()` builds the body with `uiLocale` = current Transloco language.
- Routes: `/register`, `/verify-email` in `auth.routes.ts` (lazy).

i18n: scope `auth` + `errors` (exist); new error keys for `captcha_required`, `captcha_invalid`, `captcha_unavailable`, `breached_password`, `registration_closed`, `rate_limited`, `forbidden`, `age_attestation_required` in vi + en (F16/F20). Invite/closed copy keys off the **single** code 09 names (`registration_closed`, 09 README:1040); no second invite code is invented — the client-visible `registration.mode` source is `[OPEN]` (F29), so the invite field renders from the fallback in `## Failure handling` below.

## Steps

1. Add `register.model.ts` / `register.port.ts` and the fake repository for tests (NightTales.TestKit, hand-written).
2. Implement `RegisterApiRepository` with full outcome mapping (F16) and indistinguishability-safe error copy (F17).
3. Build `register.store.ts` (signals) and `register.page.ts` from the 10.3.1-T0 design.
4. Wire the three consent checkboxes to version strings read from the legal content (SC16); wire `uiLocale` to Transloco.
5. Wire `CaptchaWidget`: reveal on `captcha_required`, reset on `captcha_invalid`; on `captcha_unavailable` show `RetryCountdown` and block submission (no token-less register submit, D4/09 W3 CR-34); attach `captchaToken` to the body (SC14).
6. Bind `breached_password` to the password control; show `RetryCountdown` on `rate_limited`; show neutral form-level copy for `registration_closed` / invite errors.
7. Implement `verify-email.page.ts` with fragment read + `history.replaceState` (D6) and the four outcomes.
8. Add axe specs (WCAG 2.2 tags) and the i18n key checks; run the register→verify→login e2e against the real API.

## Acceptance checks

- **Given** a valid form, **When** submitted, **Then** the body is exactly `{ email, password, consents: [{ document, version }], inviteCode?, uiLocale, captchaToken? }` with exactly one `tos` and one `privacy` acceptance and the `age_18` attestation (SC30).
- **Given** an existing e-mail, **When** submitted, **Then** the same neutral "check your e-mail" page appears as for a new e-mail, and no session is created (F17, no auto-login).
- **Given** mode `open` and a public mode source (F29 `[OPEN]`), **When** the page loads, **Then** the `CaptchaWidget` is present; **until that source lands**, **When** the page loads, **Then** the widget is revealed on 400 `captcha_required` and the invite field on a 400 naming the invite code — **given** mode `invite`, an `inviteCode` field is shown; **given** mode `closed`, the form is replaced by the closed copy (both keyed off `registration_closed` until F29 closes).
- **Given** a 400 `captcha_required`, **When** received, **Then** the widget is revealed; **given** 400 `captcha_invalid`, **Then** the widget resets and the token field clears; **given** 503 `captcha_unavailable`, **Then** the form shows `RetryCountdown` and blocks submission — **no token-less submit on register** (D4, 09 W3 CR-34).
- **Given** 400 `breached_password`, **When** received, **Then** the error binds to the password control; **given** 429 `rate_limited`, **Then** `RetryCountdown` shows the `Retry-After` value.
- **Given** `/verify-email#token=…`, **When** opened, **Then** the token is read from the fragment, removed via `history.replaceState` before the POST, and never appears in the address bar or a log.
- **Given** the four verify outcomes, **When** each occurs, **Then** verified / expired / invalid / resent render their own copy.
- **Given** axe runs with `wcag2a,wcag2aa,wcag21a,wcag21aa,wcag22aa`, **When** register and verify-email render in vi and en, **Then** zero violations.
- **Given** the compose stack, **When** the register→verify→login e2e runs, **Then** it completes against the real API.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| `CaptchaWidget` (10.3.3-T2) not yet merged | Use a contract-true fake in component tests; the e2e needs the real widget |
| Legal content missing version strings | Record `[OPEN]`; do not hardcode a version |
| No client-visible `registration.mode` (F29) | `[OPEN]` — fallback: reveal the widget on 400 `captcha_required`, reveal the invite field on the 400 09 names, key closed/invite copy off `registration_closed`; **never invent a route or an error code**; the proposed CR extends ST-7's `runtime-config.json` with `registrationMode` |
| `captcha_unavailable` on login/MFA | Not this task — the fail-open token-less submit applies to login/forgot/reauth (10.3.3-T1's own handling); **register itself is fail-closed** and never allows a token-less submit (D4, 09 W3 CR-34) |
| User reloads `/verify-email` after success | Fragment already consumed → renders `invalid`; the neutral copy explains |
| Double submit | `submitting` disables the control; no `Idempotency-Key` is required on register |
| `forbidden` 403 | Show mapped copy; never reveal account state |
