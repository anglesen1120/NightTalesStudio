## Goal

`/dashboard` is the creator's overview: three status groups — "Needs your review" (`story_review`, `video_review`), "In progress" (`story_generating`, `rendering`) and "Ready to publish" (`ready`) — each driven by the episode list API, with a "next action" affordance per card. It contains **no** credit balance, quote or buy button in P (D14; the buy button is 12/S and the `cost-line`/`header-end` slots stay empty).

## Design

**Files produced.**
- `web/src/app/features/dashboard/application/dashboard.store.ts` — `DashboardStore`, `@Injectable()` provided by the routed page:
  ```ts
  type Group = 'needsReview' | 'inProgress' | 'ready';
  readonly needsReview = signal<readonly EpisodeSummary[]>([]);
  readonly inProgress = signal<readonly EpisodeSummary[]>([]);
  readonly ready      = signal<readonly EpisodeSummary[]>([]);
  readonly loading    = signal(false);
  readonly error      = signal<AppError | null>(null);
  readonly refreshing = signal(false);          // focus refresh: keeps the current cards on screen
  readonly lastRefreshedAt = signal<number | null>(null);
  readonly isOwner = computed(...);             // from SessionStore, controls the idle-window copy only
  load(): Promise<void>;                        // 3 calls in Promise.all, one AppError if any fails
  refresh(): Promise<void>;                     // coalesced: ignored while `refreshing()` is true
  ```
  Group queries: `needsReview` = `status=story_review` (`limit=10`), `inProgress` = `status=video_review,story_generating,rendering` (`limit=20`), `ready` = `status=ready` (`limit=10`) — see [OPEN-2] below. One request per group, issued in parallel, never chained.
- `web/src/app/features/dashboard/feature/dashboard-page.ts` — the page: `PageHeader` (`dashboard.title`) + three `<section>`s; each section renders `LoadingState` skeletons while `loading()`, an inline `EmptyState` when its list is empty, and a `<ul>` of `NextActionCard`s otherwise. A whole-page failure renders `ErrorState` with a Retry action; a partial failure (one group failing) is not possible in P because `load()` fails atomically — instead, each group keeps the last good data and the page shows a non-blocking hint `dashboard.partialRefreshFailed`.
- `web/src/app/features/dashboard/ui/next-action-card.ts` — `NextActionCard`, `OnPush`, inputs `@Input({required:true}) episode: EpisodeSummary`, `@Input() group: Group`; outputs `@Output() open = output<string>()` and `@Output() primaryAction = output<{id: string; action: string}>()`. Renders the episode title, series name, a relative `updatedAt` through `Intl.RelativeTimeFormat` (with the absolute date in `title`), the `StatusChip` re-exported from the episodes feature, and exactly one primary action per group: `needsReview` → "Review story" (`story_review`) / "Review video" (`video_review`), `inProgress` → "Open" (a link, no mutation), `ready` → "Publish" (navigates to the publication flow owned by wave 2 / 10.5.x).
- `web/src/app/features/dashboard/dashboard.routes.ts` + `index.ts` — `authGuard` + `loadComponent`; the shell nav entry is 10.2.6-T1's.
- `web/src/app/features/dashboard/testing/fake-episode.repository.ts` — thin re-export/wrapper of the episodes feature's fake with a canned fixture per status and a call log; kept here so the dashboard store test does not depend on the episodes tests' fixtures.

**Reuse rule (D2).** `EpisodeSummary`, `EpisodeRepository` and the status presentation come from `@features/episodes` (`features/episodes/index.ts` is the only legal import path). This task must **not** copy `episode-status.ts`; if a status label is missing there, it is added in the episodes feature by 10.5.1-T1's file, not here [OPEN-3: coordination item with 10.5.1-T1 — this task's `## Notes` records the request; no file outside this folder is edited].

**Focus refresh.** `dashboard-page.ts` registers `afterNextRender` + a `focus`/`visibilitychange` listener (throttled to at most one `refresh()` per 10 s, coalesced by the store's `refreshing` guard) so returning to the tab shows current data without polling. Cleanup through `DestroyRef`. No `setInterval` (D17).

**Copy keys (scope `dashboard`, vi + en).** `dashboard.title`, `dashboard.refresh`, `dashboard.needsReview|inProgress|ready`, `dashboard.<group>.empty`, `dashboard.partialRefreshFailed`, `dashboard.card.action.reviewStory|reviewVideo|open|publish`, `dashboard.card.updated` (relative time is produced by `Intl`, the key is only the fallback label), `dashboard.updatedJustNow`; plus `errors.network_error|rate_limited|unknown_error` (D9). Cross-plan keys used verbatim: the episode status labels from 10.5.1-T1 (e.g. `episode.status.story_review`) — not re-authored here.

**A11y (D16).** Each group is `<section aria-labelledby>` with a heading and the count as text; after a refresh the counts are re-announced once via `aria-live="polite"` (not per card); every card's primary action is a button or a link with an accessible name including the episode title; `StatusChip` carries an icon + text (never colour only); focus is visible; the skeleton has `aria-busy="true"` on the section; 360 px stacks the cards; `prefers-reduced-motion` disables the skeleton shimmer.

**Performance.** Exactly 3 HTTP calls per `load()` (asserted in the store test with the fake's call log), 0 calls while the page is hidden, ≤ 1 coalesced refresh per 10 s on refocus, `track episode.id`, no images on this page, no heavy `@defer` target (the page is above-the-fold content), and the lazy `dashboard` chunk stays a few kB.

**Security.** No mutation on this page (navigation only) → no `If-Match`/idempotency concerns; no token in storage (D6); episode/series titles are ordinary interpolated text (no `innerHTML`, D2/D4); nothing logged; the store is provided by the routed page and therefore dropped on navigation, so no stale data survives a logout (D6 `SESSION_SCOPED` is not needed for a page-provided store, but the router guard re-runs `load()` after a new login).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| One group failing (e.g. a 500 on `status=ready`) | `load()` reports one `AppError`; the page shows `ErrorState` with Retry and keeps nothing stale (a partial render would be misleading). The focus `refresh()` instead keeps the last good data and shows `dashboard.partialRefreshFailed`. |
| 429 on any of the 3 calls | `RetryCountdown` from `Retry-After`; Retry disabled until 0; the other groups' data is discarded to keep the view consistent. |
| No episodes at all (new account) | Three empty states + a primary "Create series" link (the key already exists in the `series` scope — the dashboard links, it does not duplicate the flow). |
| `status=a,b` unsupported by the API ([OPEN-2]) | The store falls back to per-status calls and merges by `updatedAt`; the assertion is downgraded to "≤ 4 requests, no duplicates by id"; recorded as a follow-up to 10.5.1-T1. |
| Episode status drifts between the 3 calls (an episode moves from `rendering` to `ready` mid-load) | A duplicate id is de-duplicated by the store preferring the most advanced status, so it appears in exactly one group. |
| Session ends while loading | The interceptor's `SessionEnded` navigates to `/login?returnUrl=/dashboard` (D6); no error state is painted. |
| Unknown/new status value from the wire | Ignored (it belongs to no group) — never rendered as an unknown chip; the count reflects only known statuses. |
| Deep link while unauthenticated | `authGuard` → login with `returnUrl=/dashboard` (validated per D6). |
| Rollback | Remove the route entry + the lazy chunk; nothing else in the app depends on the dashboard. |
