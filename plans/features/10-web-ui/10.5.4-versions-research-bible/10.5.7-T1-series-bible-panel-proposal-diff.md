## Goal

`/series/:id/bible` shows what the series remembers — narrator, recurring characters, places, rules and past episode summaries — lets the owner edit it (typed form, `If-Match` on save) and shows a banner when a story approval produced a **proposal**: the proposed changes with their reasons, the server-computed preview counts, and Accept / Dismiss.

**Wire shapes** (client models mirror `BibleDto` exactly, no extra fields — D18/D13):

```ts
export interface Bible { seriesId: string; version: number; etag: string; content: BibleContent; proposal: BibleProposal | null; }
export interface BibleContent {
  narrator: { name: string; persona: string; voiceNotes: string };                  // wire keys: name | persona | voice_notes
  recurringCharacters: BibleCharacter[]; places: BiblePlace[]; rules: BibleRule[];
  episodeSummaries: BibleEpisodeSummary[];
}
export interface BibleCharacter { id: string; name: string; description: string; firstEpisodeId?: string; }
export interface BiblePlace { id: string; name: string; description: string; }
export interface BibleRule { id: string; text: string; }
export interface BibleEpisodeSummary { episodeId: string; title: string; summary: string; structure?: unknown; approvedAt?: string; }
export interface BibleProposal { basedOnVersion: number; proposedFromEpisodeId: string; proposedAt: string;
  ops: BibleOp[]; preview: { characters: number; places: number; rules: number; summaryForEpisodeId: string | null }; }
export interface BibleOp { kind: string; summary?: string; name?: string; description?: string; text?: string; reason?: string; }
```

**Wire mapping (snake_case `bible.v1` ↔ model, D5)** — `bible.mapper.ts` has explicit functions, one per field, no generic casing transform (so a future field cannot silently mis-map): `narrator.{name,persona,voice_notes}` ↔ `narrator.{name,persona,voiceNotes}`; `recurring_characters[].first_episode_id` ↔ `firstEpisodeId`; `places[].{id,name,description}`; `rules[].{id,text}` (a rule has **`text`**, not name/description); `episode_summaries[].{episode_id,title,summary,approved_at}` ↔ `{episodeId,title,summary,approvedAt}`. The PUT body is `{ content }` carrying the full `bible.v1` **without** `schema_version` (the backend writes it; a client value is ignored — 02.6.3 §3.1). Ids `ch1`/`pl1`/`rl1` are server-assigned and never renumbered (02.6.3 §3.1): existing entries echo their `id` back unchanged, a newly added entry is sent without `id` and takes the id assigned by the server on the next refetch [INFERENCE — §3.1 documents the ids as server-assigned; the page refetches after every save].

`BibleStore`:

```ts
readonly bible = signal<Bible | null>(null);
readonly proposal = computed(() => this.bible()?.proposal ?? null);
readonly loading = signal(false); readonly saving = signal(false);
readonly committing = signal(false);                       // accept/dismiss
readonly error = signal<AppError | null>(null);
readonly fieldErrors = signal<Record<string, string[]>>({});
readonly conflict = signal<boolean>(false);                // 412 bible_conflict → banner + reload action
load(seriesId: string): Promise<void>;
save(seriesId: string, content: BibleContent, etag: string): Promise<Result<void>>;   // PUT { content } + If-Match
acceptProposal(seriesId: string): Promise<Result<void>>;   // POST accept (no If-Match) → refetch
dismissProposal(seriesId: string): Promise<Result<void>>;  // POST dismiss → refetch
readonly proposedTitle = signal<string | null>(null);       // one GET /episodes/{proposedFromEpisodeId} when proposal !== null (P5); fallback copy on 404/403
reset(): void;
```

The page owns a **typed reactive form** (D13) built from `content`: a narrator group with three fields (`name` ≤ 80, `persona` ≤ 1,000 and **required** — an empty persona blocks Save, 02.6.3 §3.1/§3.2, `voiceNotes` ≤ 1,000), three `FormArray`s — characters `{ id, name (≤ 60), description (≤ 300) }` (the server-owned `first_episode_id` is shown read-only as `series.bible.character.firstEpisode`), places `{ id, name (≤ 60), description (≤ 300) }`, rules `{ id, text (≤ 300) }` — and an `episodeSummaries` array where only `title` (≤ 100) and `summary` (≤ 200) are editable and removal is allowed (02.6.3 §4 U2 — `structure`/`approved_at` are re-derived server-side and client values are ignored). Each field carries a `CharCounter` with the documented limit and the add buttons disable at 30 entries per array; a name containing angle brackets is rejected before the request (the server rejects `<b>` in names — 02.6.3 §3.2/F36). `Save` is enabled only while the form is dirty and no save is in flight; the payload is built from the form value through the mapping functions (`{ content: <snake_case bible.v1> }`, no `schema_version`) and with the summaries reduced to `{ episode_id, title, summary }`.

**Op rendering** (`BibleProposalBanner` → `DiffView [rows]`, WR16/P3): the page maps each `BibleOp` to a generic `DiffRow` — `kind: 'add'` for an `add_*` op and `'change'` for any unforeseen kind; `label` = the mapped kind label (`series.bible.op.summary|character|place|rule`, `series.bible.op.other` as the fallback), `after` = the first present of `name` / `text` / `summary` / `description` (`before` stays undefined) and the op's `reason` is rendered as the row's secondary line — then renders `<app-diff-view mode="rows" [rows]="rows()" [label]="…">` inside the lazy `@defer (on viewport)` block; **no local row renderer** (D11). The kind→label mapping is normalisation-tolerant: `kind.replace(/^add_?/i,'').replace(/[^a-z]/gi,'').toLowerCase()` → `summary|character|place|rule`, so neither `AddCharacter` nor `add_character` can break the UI. Banner title: `series.bible.proposal.banner` with `{ n: ops.length }` and `{ title: proposedTitle() }`, where `BibleStore.load()` issues **exactly one** `GET /api/v1/episodes/{proposedFromEpisodeId}` when `proposal !== null` and never for a proposalless bible (P5/WR16), falling back to `series.bible.proposal.bannerNoTitle` on 404/403 or a network failure (see [OPEN] 8 in Notes).

**Copy keys** — `web/src/assets/i18n/series/{vi,en}.json` (02.6.3 §6 hand-over keys used **verbatim**, D10): `series.bible.title`, `.empty`, `.narrator`, `.characters`, `.places`, `.rules`, `.summaries`, `.saved`, `.error.conflict`, `.error.ifMatch`, `.error.limits`, `.field.{too_many,too_long,duplicate,unknown_episode}`, `.proposal.{banner,accept,dismiss,none,autoAccepted}` (all with the vi/en text fixed in `plan.md` §6), plus new: `series.bible.save`, `series.bible.saving`, `series.bible.reload`, `series.bible.addCharacter|addPlace|addRule|addSummary`, `series.bible.remove`, `series.bible.narrator.name|persona|voiceNotes`, `series.bible.rule.text`, `series.bible.character.firstEpisode`, `series.bible.limitReached`, `series.bible.summary.title`, `series.bible.summary.body`, `series.bible.proposal.bannerNoTitle`, `series.bible.proposal.more` (op reason label), `series.bible.op.{summary,character,place,rule,other}`, `series.bible.conflict.reload`; the server's per-field error keys (`recurring_characters`, `recurring_characters: too_many`, `episode_summaries[2].episode_id`) map onto `series.bible.field.{too_many,too_long,duplicate,unknown_episode}` (02.6.3 §6).

## Steps

1. Model + `bible.mapper.ts` + port + `HttpBibleRepository` (GET/PUT/accept/dismiss; `readEtag`; `AppErrorMapper`; no `If-Match` on accept/dismiss per 02.6.3 §4 U3/U4; the mapper's round-trip test lands here).

3. `BibleSection` (repeatable `fieldset` with `legend`, add/remove rows, `aria-label` per removal carrying the entry name/number).
4. `BibleProposalBanner` (`role="status"`, counts from `preview`, ops list, Accept then Dismiss in DOM order, `series.bible.proposal.none` toast when 409).
5. `BiblePage`: typed reactive form, dirty tracking, Save, reload-after-conflict action, empty state (`series.bible.empty`), linking from the series page (`/series/:id/bible`).
6. Realtime/navigation: **no subscription** (B3, D17) — `load()` runs on route activation and after accept/dismiss. Reload after a 412 is explicit via the conflict action, never automatic.
7. i18n keys in both files; e2e spec `series-bible.spec.ts`.

## Acceptance checks

- [ ] `/series/:id/bible` loads `GET /api/v1/series/{id}/bible` once and renders the five sections with the server's data; a series with an empty bible shows `series.bible.empty` (not an error).
- [ ] Editing any field marks the form dirty and enables "Save"; saving sends `PUT` with `{ content }` and `If-Match: "sb-<version>"`, then adopts the response `{ version, etag }` and announces `series.bible.saved` politely.
- [ ] Summary rows expose only title and summary; removing a summary row is possible; the payload never carries `structure`/`approved_at`/`schema_version`.
- [ ] 412 `bible_conflict` shows `series.bible.error.conflict` with a "Reload" action; the edited values are kept in the form until the user reloads (no silent overwrite, D9).
- [ ] 400 `bible_invalid_content` maps `errors` keys (e.g. `recurring_characters`, `episode_summaries[2].episode_id`) onto the matching controls and shows `series.bible.error.limits` with the field name; unmapped keys go to a form-level alert.
- [ ] A pending proposal renders the banner as a `role="status"` live region with `{ n }` = `ops.length`, the preview counts (characters/places/rules) and the episode title resolved by one `GET /api/v1/episodes/{proposedFromEpisodeId}`; every op is a `DiffRow` rendered through `DiffView [rows]` inside `@defer (on viewport)` with its kind label, value and reason.
- [ ] A bible with **no** proposal issues no episode-detail request; a 404/403 on that one title call falls back to `series.bible.proposal.bannerNoTitle` with no error state and no retry loop.
- [ ] `Accept` calls `POST …/bible/proposal/accept` (no `If-Match`), refetches the bible, shows the new `version` and hides the banners; `Dismiss` calls `…/dismiss`, refetches and hides it; a 409 `bible_proposal_not_pending` shows `series.bible.proposal.none` and refetches.
- [ ] The panel performs **no** periodic fetch: an idle page makes no request for 60 s (assert request count in the e2e), and no `SeriesBibleUpdated` subscription exists.
- [ ] The narrator section has exactly three fields (`name`, `persona`, `voiceNotes`); clearing `persona` blocks Save with the required hint; a rule row exposes a single `text` field.
- [ ] The save payload is snake_case `bible.v1` (`narrator.persona`, `recurring_characters[].first_episode_id`, `rules[].text`, `episode_summaries[].episode_id`) and contains `{ content }` without `schema_version`; a stored `structure`/`approved_at` is echoed on load and omitted from the request.
- [ ] Per-field counters enforce the documented limits (name 80, persona/voiceNotes 1,000, character/place name 60, description 300, rule text 300, summary title 100, summary 200) and the add buttons disable at 30 entries; a name containing `<` is rejected before the request with the field marked.
- [ ] Existing entries keep their server ids across a save/reload; a newly added entry receives its `ch1`-style id from the refetched response.
- [ ] Both languages render, including the vi/en texts handed over by 02.6.3; axe clean on the page with and without a proposal; keyboard-only editing/saving works and the banner buttons are focusable in the Accept → Dismiss order.

## Failure handling and edge cases

- **Accept after manual edits** (F27): safe by construction (ops only append) — the client does not pre-merge; it refetches after the call.
- **Op dedupe/limit skips** (`AddCharacter` on an existing name, or a full array) are counted server-side and returned as `applied`/`skipped` — the UI shows the result of the refetch, never a claim about what was applied [INFERENCE: the counts are not in the client contract read here].
- **`bible_proposal_not_pending`** (409) on either action → `series.bible.proposal.none` + refetch; the proposal may have been dismissed in another tab or auto-accepted by autopilot (02.6.3 §7) — the copy `series.bible.proposal.autoAccepted` is shown when the audit says `actor = system` [OPEN: not part of `BibleDto`; rendered only when a future field carries it].
- **A proposal based on an older version** (`basedOnVersion < version`): accepted as-is (append-only), the banner notes the base version when it differs from the current one [INFERENCE — the copy uses `series.bible.proposal.banner` plus the version numbers].
- **Two tabs saving** → the second gets 412 → conflict copy + explicit reload.
- **Empty arrays** → sections render a compact empty hint; the empty-bible state shows `series.bible.empty` and the sections still allow adding a first entry.
- **Large bible content** (many summaries): the list has no paging in P (the backend returns the whole bible); rows use `@for … track entry.id` and the form is built once per load — no per-keystroke walk over all rows (D18-style discipline applied here).
- **Missing entry id** (a stale response after a concurrent accept) → the refetch replaces the list; no local reconciliation.
- **428 `if_match_required`** = client bug → dev console warning, generic message (D9).
- **Series not found / other tenant** → 404 → `ErrorState` with a link back to the series list.

- **412 handling** [DECISION]: a `bible_conflict` keeps the edited form and renders a `role="alert"` banner (`series.bible.error.conflict`) with an explicit Reload (`series.bible.conflict.reload`); it does not auto-refetch, per Acceptance check 4 and D9. 02.6.3 §4 U2 line 154 ("the UI re-fetches on 412") is superseded for this task; reload discards the local edits after the explicit press.
- **`proposalGone`**: `BibleStore.proposalGone` is set by a 409 `bible_proposal_not_pending` on accept/dismiss; the store still refetches and the page renders `series.bible.proposal.none` while suppressing the form-level alert.
- **Save resolves after the refetch**: `BibleStore.save` adopts the returned `{ version, etag }` (plus the stored content as a fallback), then `fetchAndAdopt`; it resolves only after the refetch, so the page rebuilds the form from the refetched bible (server-assigned ids, new version) and only then marks the form clean. A committed save whose refetch fails keeps the adopted version/content and raises no error.
- **Narrator i18n keys**: `series.bible.narrator.name`, `.persona` and `.voiceNotes` are literal dotted leaves in the `series` scope next to the `series.bible.narrator` string leaf; Transloco resolves the exact dotted key, so both coexist. The page maps per-field server issues to the same keys.
- **BIBLE-3**: `BiblePage.buildForm` adds a required (trimmed) validator to `narrator.persona` and `canSave` requires `form.valid`, so a fresh bible (`persona = ""`) blocks Save with `series.bible.field.required` ("Enter the narrator persona before saving.") and never sends an empty persona. The editor half of BIBLE-3 is addressed; whether the backend validator/plan should allow empty stays with the TL.
