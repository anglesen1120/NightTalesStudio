## Goal

The owner can start a render from an approved story and can stop one they no longer want. "Make video" appears only where the server says it may (`nextActions` contains `render` or `retry_render`) and only while no keyword is flagged; it asks once through a confirm dialog, sends `If-Match` with the episode's ETag and one `Idempotency-Key` that survives an unknown outcome (so a retry replays the same logical command instead of reserving credit twice), and the 409 `keywords_flagged` response is handed to the single owner of the flag state so the offending segments light up in the editor. "Cancel render" appears only on a job the server would accept a cancel for, confirms once, shows "Cancelling…" until the terminal event, and never claims a status the server has not reported.

## Design

```ts
// domain/render.repository.ts
export abstract class RenderRepository {
  /** 202 → the render job id parsed from `Location: /render-jobs/{id}`. Throws AppError.
   *  `intent` is the caller's `IdempotencyIntent` (10.2.3-T1) — the interceptor writes the header. */
  abstract requestRender(episodeId: string, etag: string, intent: IdempotencyIntent): Promise<string>;
  /** 204 (also on a repeat). Throws AppError. */
  abstract cancelRender(renderJobId: string): Promise<void>;
}
```

```ts
// data-access/render-http.repository.ts
@Injectable()
export class RenderHttpRepository implements RenderRepository {
  private readonly http = inject(HttpClient);
  private readonly mapper = inject(AppErrorMapper);

  async requestRender(episodeId: string, etag: string, intent: IdempotencyIntent): Promise<string> {
    const res = await firstValueFrom(this.http.post<unknown>(
      `/api/v1/episodes/${episodeId}/render`, null,
      { ...withIfMatch(etag), ...withIdempotency(intent), context: USER_ACTION }));   // WR11: a user click may refresh on 401
    const id = renderJobIdFromLocation(res.headers.get('Location'));  // `readEtag`-adjacent response helper (D5)
    if (!id) throw this.mapper.fromClientBug();   // [INFERENCE: the mapper's client-bug entry (10.2.2-T1) — the 428/dev-console path, D9]
    return id;
  }
  async cancelRender(renderJobId: string): Promise<void> {
    await firstValueFrom(this.http.delete<void>(`/api/v1/render-jobs/${renderJobId}`, { context: USER_ACTION }));
  }
}
```

**Idempotency convention (WR4/10.2.3-T1:57-62, D5):** the key is **not** built in the repository. The store holds the `IdempotencyIntent` and the repository only passes `withIdempotency(intent)`; `idempotencyInterceptor` writes `Idempotency-Key` from the `IDEMPOTENCY_INTENT` context (and leaves an existing header untouched, so the session interceptor's 401 retry keeps the same key). `stores never build HttpContext` (D5/wave-1 plan §3.4) — the wave-1 precedent for the alternative (repository-attached header) is `../10.5.1-episodes-editor/10.5.2-T1-new-episode-generate-live-state.md:82`; this folder follows the *intent* form because the store must also reuse the key across its own retries.

`RenderRepository` is registered in `episodes.routes.ts`'s route providers beside `EpisodesRepository` (D2 boundary: the port lives in `domain`, the adapter in `data-access`, and only `data-access/**` imports `@shared/api`).

```ts
// application/make-video.store.ts — `@Injectable()`, provided by the episode page
@Injectable()
export class MakeVideoStore {
  private readonly repo = inject(RenderRepository);
  private readonly detail = inject(EpisodeDetailStore);          // the only owner of GET /episodes/{id}
  private readonly editor = inject(StoryEditorStore);            // WR6: keywordFlags/videoBlocked owner (10.5.10-T1)
  private readonly messages = inject(MatDialog);                 // ConfirmDialog (10.1.3-T1)

  private readonly keys = inject(IdempotencyKeys);               // 10.2.3-T1
  readonly submitting = signal(false);
  readonly error = signal<AppError | null>(null);
  readonly needsRefresh = signal(false);                         // 412 → the view shows the retry prompt after a refetch
  readonly intent = signal<IdempotencyIntent | null>(null);      // ONE intent per user intent: minted on the click, reused by every retry, settle()d on a terminal answer
  readonly blockedByKeywords = computed(() => this.editor.videoBlocked());
  readonly allowed = computed(() => { const a = this.detail.episode()?.nextActions ?? []; return a.includes('render') || a.includes('retry_render'); });
  readonly canMakeVideo = computed(() => this.allowed() && !this.blockedByKeywords() && !this.submitting());

  async makeVideo(): Promise<void>;      // confirm → repo.requestRender(episodeId, etag, intentFor())
  private intentFor(): IdempotencyIntent;// an un-settled held intent, else keys.begin('episode.render')
}
```

`makeVideo()` sequence: (1) return early when `!canMakeVideo()`; (2) open `ConfirmDialog` with `render.make.confirm.title/.body`, the `cost-line` slot **empty**; (3) on confirm set `submitting`, take `intentFor()` and call the repository with `detail.episode()!.etag`; (4) on success (202) `intent.settle()`, clear the signal and let the **episode's own status** drive the view (no optimistic write): `detail.refetch()` runs through the event/`resync` path, and the timeline branch takes over as soon as the server reports the job (F1/09.6.1-T1:196). No status is set locally. The 409 `keywords_flagged` branch forwards `error.problem?.errors ?? []` to `editor.setKeywordFlags(...)` **exactly once**, stores only `error` (never the flag array — WR6) and leaves the dialog closed with `errors.keywords_flagged` in the alert region.

**Intent lifecycle (10.2.3-T1:57-86).** `intentFor()` returns the held, un-settled intent when there is one (a retry of the same click → the server replays the stored 202 instead of creating a second job) and otherwise `keys.begin('episode.render')` (a genuinely new click → a **new** key). `network_error`, a 5xx or a timeout leaves the intent un-settled, so the retry replays. Success (202) and every non-retryable answer (400/409/412/422/428/429) `settle()` and clear it, so the **next** click — including one after a cancel returned the episode to `story_approved` — sends a **different** key and can create a real second render job. This is the 10.5.2-T1:67 discipline with the key object owned by the store; `dismiss()` on view teardown just drops the local reference (the intent is not persisted anywhere).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Double click on "Make video" | `submitting` disables the button and the store returns early on the second call — one request, one key |
| Response lost after `POST /render` (the job exists server-side) | The key is kept, so the user's retry replays the stored 202 and no second job/credit reservation is created (09.6.1-T1:197) |
| Make video → cancel → make video again | The first intent is settled on its 202, so the second click mints a **new** key and the server creates a real second job; reusing the key would replay the stored 202 and silently no-op (09.6.1-T1:197) |
| Two tabs, two different keys, same episode, concurrently | The server's partial unique index wins → 409 `concurrency_conflict`; this tab refetches, and `nextActions` then offers `cancel` instead of `render` (F8) — no client-side dedupe beyond the disabled button |
| A second tab already rendered | `nextActions` no longer contains `render`; a stale tab that calls anyway gets 409 `episode_invalid_state` → refetch, never a silent success |
| Flags are stale locally (another tab fixed and saved them) | The server is the authority: the render either starts (200/202) or returns 409 `keywords_flagged` with the current rules, which are forwarded to the editor store (WR6) — the client never clears flags by itself |
| `rule: "no_scenes"` (the image plan needs no scenes) | Same 409 branch; the editor store's flag list carries the rule and `SegmentChips` highlights the addressed segments (10.5.10-T1) — this task adds no special case |
| Cancel races the poller's terminal `succeeded` | The server keeps the terminal state (WT51); this tab's refetch shows the finished job and the review view, never "Cancelling…" forever |
| Cancel a job whose adapter task was never created | The server skips the adapter call (09.6.4-T1:109) and answers 204; the UI behaves identically to any other accepted cancel |
| The episode page is left while a cancel is in flight | `DestroyRef` teardown drops the local `cancelling`; the server-side cancel stands, and reopening the page re-derives the state from the detail (no resume UI, no orphan timer) |
| `RetryCountdown` running and the user navigates away | The timer is `DestroyRef`-scoped (10.2.2-T1 owns it); on return the fresh detail/`429` state governs |
| Rollback | Remove the two actions and their wiring; the timeline and the review remain read-only, and the server keeps whatever state it is in — no migration, no data change |

## Notes

- **Reuse (D11/WR4):** `IdempotencyKeys`/`IdempotencyIntent`/`withIdempotency` (10.2.3-T1) — no hand-rolled UUIDs and no repository-built `Idempotency-Key` header (D5: stores never build `HttpContext`); `withIfMatch`/`readEtag`-style header helpers (D5); `ConfirmDialog` + its empty `cost-line` (10.1.3-T1); `RetryCountdown`, `AppErrorMapper`, `bindFieldErrors` (10.2.2-T1); `StoryEditorStore.setKeywordFlags`/`videoBlocked` (10.5.10-T1, WR6) — this task keeps **no** second flag store; `EpisodeDetailStore` is the only caller of `GET /episodes/{id}`. Nothing here duplicates 10.5.2-T1's generation flow: the key discipline is the same rule, applied to the render command.
