## Goal

Before anything goes out the owner watches the finished cut on the `/episodes/:id` page: an HTML5 player fed by a **short-lived signed URL** that the page refreshes under the player's feet so playback cannot die mid-scene, the render-quality notes shown as advice (never as a blocker), the scenes the image pipeline dropped or blocked named in a banner, and the three decisions — approve video, reject (fix the script), re-make video — plus a download of the MP4. Every decision is gated by the server's own `nextActions`, carries `If-Match`, and paints nothing the server has not reported.

## Design

```ts
// domain/video-review.repository.ts
export interface VideoUrl { url: string; expiresAt: string; }        // ISO-8601 UTC
export type RejectTarget = 'story' | 're_render';
export abstract class VideoReviewRepository {
  abstract getVideoUrl(episodeId: string): Promise<VideoUrl>;                         // never cached, never persisted
  abstract approveVideo(episodeId: string, etag: string, note?: string): Promise<{ status: string; etag: string }>;
  abstract rejectVideo(episodeId: string, etag: string, reason: string, target: RejectTarget, intent: IdempotencyIntent):
    Promise<{ status: string; etag: string; accepted: boolean }>;                     // 202 ⇒ accepted = true (F9, no Location)
}
```

```ts
// data-access/video-review-http.repository.ts — `@Injectable()`; only `data-access/**` imports @shared/api (D2/D5)
getVideoUrl(episodeId)  → firstValueFrom(http.get<VideoUrl>(`/api/v1/episodes/${episodeId}/video-url`))   // no USER_ACTION when automatic
approveVideo(...)       → firstValueFrom(http.post(…'/video/approve', { note }, { ...withIfMatch(etag), context: USER_ACTION }))
rejectVideo(...)        → firstValueFrom(http.post(…'/video/reject', { reason, target },
                            { ...withIfMatch(etag), ...withIdempotency(intent), context: USER_ACTION,
                              observe: 'response' }))                          // 202 must be observable as `accepted`; the interceptor writes `Idempotency-Key`
```

Both adapters throw `AppError` from `AppErrorMapper` (10.2.2-T1); `204`/`202`/`200` are the only success shapes and no response body is trusted beyond `status`/`etag`/`accepted`.

```ts
// application/video-review.store.ts — `@Injectable()`, provided by the episode page component (`providers`)
@Injectable()
export class VideoReviewStore {
  private readonly repo = inject(VideoReviewRepository);
  private readonly detail = inject(EpisodeDetailStore);         // the only owner of GET /episodes/{id}
  private readonly keys = inject(IdempotencyKeys);               // 10.2.3-T1 (core/http)

  readonly url = signal<VideoUrl | null>(null);
  readonly loadingUrl = signal(false);
  readonly urlError = signal<AppError | null>(null);
  readonly playerError = signal(false);
  readonly deciding = signal(false);
  readonly error = signal<AppError | null>(null);
  readonly note = new FormControl<string>('', { nonNullable: true, validators: [Validators.maxLength(500)] });
  readonly reason = new FormControl<string>('', { nonNullable: true, validators: [Validators.required, Validators.maxLength(500)] });
  readonly target = signal<RejectTarget>('story');                // the re-make entry point sets 're_render'
  readonly intent = signal<IdempotencyIntent | null>(null);       // ONE per reject click: minted by reject(), reused by that click's retry, settle()d on a terminal answer

  readonly finalVideo = computed(() => this.detail.episode()?.finalVideo ?? null);
  readonly notes = computed<readonly string[]>(() => this.detail.episode()?.renderJob?.hints ?? []);        // codes only, never prose
  readonly skipped = computed<readonly SkippedScene[]>(() => this.detail.episode()?.renderJob?.images?.skipped ?? []);
  readonly canApprove = computed(() => (this.detail.episode()?.nextActions ?? []).includes('approve_video') && !this.deciding());
  readonly canReject  = computed(() => (this.detail.episode()?.nextActions ?? []).includes('reject_video') && !this.deciding());
  readonly canDownload = computed(() => (this.detail.episode()?.nextActions ?? []).includes('download'));
  readonly downloadName = computed(() => `${safeFilename(this.detail.episode()?.title ?? 'nighttales')}.mp4`);
  readonly refreshDueAt = computed(() => this.url() ? Date.parse(this.url()!.expiresAt) - 60_000 : Number.POSITIVE_INFINITY);   // compared with `Date.now()` (Vitest `vi.setSystemTime` controls it)

  loadUrl(opts?: { userAction?: boolean }): Promise<void>;   // on view open; USER_ACTION only when the owner pressed a retry
  refreshUrl(): Promise<void>;                               // silent; keeps the previous URL when it fails
  approve(): Promise<void>;                                  // confirm (note from the dialog) → repo.approveVideo
  reject(): Promise<void>;                                   // confirm (reason + target) → keys.begin('episode.video.reject') when no un-settled intent is held → repo.rejectVideo(…, intent)
  startUrlRefresh(): void;                                   // visible-poll wiring, see below
}
```

`reject()` mints **one `IdempotencyIntent` per click** (`keys.begin('episode.video.reject')`) when it does not already hold an un-settled one, so a retry after a lost response replays the stored reply (09.7.1-T1:167 — the route requires the key exactly for that) instead of rejecting twice; `settle()` and clear it on success (200/202) or any non-retryable answer, so the next click sends a different key. `approve()` carries no key (the route does not require one — F9).

**URL lifecycle (WD4/WB3/F10).** The URL is fetched when the view opens and is **never** persisted, cached for the session, put in the URL bar or logged. `startUrlRefresh()` registers `visiblePoll({ intervalMs: 60_000, run })` from `core/state/visible-poll.ts` (10.2.6-T1, `DestroyRef`-scoped, runs only while the document is visible **and** `isActive()` — D7/WR11); `run` refreshes only when `Date.now() >= refreshDueAt()` and no fetch is in flight, so ≤ 1 request per visible minute and, in practice, one per 14 minutes of viewing (F10's 15-minute TTL minus the 60 s safety margin). A player `error` event sets `playerError` and calls `refreshUrl()` **once** (then, if it fails again, the view replaces the player with `render.review.urlFailed` + a retry button). A refresh keeps the old `url` while in flight and swaps both `url` and `expiresAt` atomically on success, so playback is never interrupted by a null source; the success emits `data-testid="video-url-refreshed"` (a count-only hook for 10.10.2-T1, `plan.md` §10 O-3) and nothing is announced to assistive tech (a silent, non-user-visible action must not chatter).

**Decisions (WD4/F9).** All three buttons come from `nextActions` (`approve_video`, `reject_video`, `download`), so the view degrades with the server's own state. `approve()` opens `ConfirmDialog` (`render.review.approve.title/.body`) with an optional note `<textarea>` + `CharCounter` (500) and sends `If-Match` + no body when the note is blank. `reject()` opens the **one** reject dialog (`render.review.reject.*`) with a required reason `<textarea>` (1–500, `CharCounter`, `bindFieldErrors` on `reason`) and a target `fieldset` with two radios (`render.review.reject.targetStory`, `.targetReRender`); the high-level "Re-make video" button opens the **same** dialog with `target = 're_render'` preselected and `render.review.reMake.title/.body` — the server's validator requires a reason on **both** targets (09.7.1-T1:54), so there is no second form and no client-side shortcut around it. Reject sends `If-Match` + one `IdempotencyKeys.begin('episode.videoReject')` per click (reused by that click's retries, `settle()`d on success/non-retryable; the intent travels as `withIdempotency(intent)`, never as a repository-built header — 10.2.3-T1:57-86/D5); on the `story` 200 the view refetches and the page switches to the editor; on the `re_render` 202 the view refetches (`accepted = true`, **no** render job id is invented — F12) and the page switches to the timeline branch once the server reports `rendering`. When the episode reaches `ready`, this view renders **only** the `finalVideo` metadata and the download link — the publication state of a `ready`/`scheduled`/`published` episode (per-publication status, cancel, YouTube Studio link) is 10.7.4-T1's (WD7) and is not added here.

**Notes and scenes (WD4/C11/WR6).** `notes()` are hint **codes** from `renderJob.hints` (10 CR-12) rendered through i18n keys (`render.quality.subtitleSyncSuspect`, `render.quality.subtitleCuesLong`, `render.quality.musicNone`, plus 03's `render.quality.scenesTrimmed` / `render.quality.scenesSparse`); an unknown code renders as nothing (never raw). They are advisory: **no** decision button is disabled by a hint, ever (C11 — only `keywordFlags` block a decision, and that is 10.6.1-T2's/in-story-approve concern, not this view). The skipped-scenes banner renders `render.images.skippedBanner` + counted rows with `render.images.moderatedScene` guidance for `moderated` rows, and each row links to `/episodes/:id?segment=<address>` through `segment-address.format` when the address parses (the same helper the editor uses).

**Download (WD4/F10).** `<a [href]="url()?.url" [attr.download]="downloadName()" target="_blank" rel="noopener">` labelled `render.review.download`; `safe-filename.ts` (10.1.6-T1) builds the suggested name, and the **server's** `Content-Disposition` is the authority when the media origin differs from the app origin (browsers ignore `download` cross-origin). No blob is fetched through the API, so no extra authenticated request and no bytes in memory.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| The signed URL expires while the video is paused/buffered | The due check swaps the URL; the `<video>` keeps its element and re-seeks from the last known position intent, so the owner does not restart from 0 (the swap is `src` + `load()` on the same node) |
| The refresh request itself 401s (the 5-minute owner token expired) | The interceptor's single refresh + one retry handles it (D6/WR9); if the session ends the page routes to `/login` with `returnUrl` and no URL is left in memory (D6/SessionEnded) |
| The URL is fetched while the episode changed to `story_approved` (a reject raced approval) | The next `EpisodeUpdated`/`resync` refetch switches the branch; `getVideoUrl` then 404s and the 404 path renders instead of a stale player |
| `finalVideo` is null but the status says `video_review` (a race, or a hand-inserted row) | The meta block is hidden, `getVideoUrl` 404s → `errors.not_found` + the honest message; the decision buttons stay governed by `nextActions`, and the server remains the authority on approve (09.7.1-T1:181 records this as no extra server guard) |
| Approve/reject returned 409 because a second tab already decided | Refetch; the server state (editor or timeline) is shown and the mapped `errors.episode_invalid_state` is displayed once — never a second decision request |
| Reject 202 but the Worker's re-render fails (412/409/402/503 in the outbox, 09.7.1-T1:183) | The rejection is committed and the episode stays `story_approved`; this view refetches and the page shows the approved state with `nextActions`, so the owner can start the render from 10.6.1-T2's action — the client does not retry the reject |
| Duplicate reject without a key replay | A second POST with the same key replays the stored response (F9); without a key the episode is no longer in `video_review` → 409 → refetch, never a double decision |
| The owner has a hint list full of warnings | Nothing is blocked (C11); the copy states the notes are advisory |
| Storage 503 (the store is degraded) | `errors.service_unavailable` + `RetryCountdown`/retry; the download link is rendered disabled with the same message rather than a dead `href` |
| The page is left while the URL fetch is in flight | `DestroyRef` teardown; the response is discarded, nothing is stored, and returning refetches (the audit row stays server-side) |
| Rollback | Remove the two `@case` branches + this task's files; the server state, the audit rows and the assets are untouched (no migration, no route) |
