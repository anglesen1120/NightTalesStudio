## 1. Scope

**User value.** (a) While a render runs the owner sees *where the work is* — the three guaranteed stages, the finer node sub-steps when the adapter reports them, how long it has been running, and (when the job sits queued) that the platform is waiting for a free studio slot rather than broken — and can cancel a job they no longer want. (b) Before publishing the owner **watches the cut**: an HTML5 player fed by a short-lived signed URL that refreshes under the player's feet, the render-quality advisory notes, the scenes the image pipeline dropped or blocked, and the three decisions (approve video / reject with a reason / re-make video) plus a download.

**In scope.** The render-timeline view (guaranteed stages, sub-steps, waiting-for-slot, failure states with their named scenes), the "Make video" action (the `nextActions`-driven enablement, the keyword gate, `If-Match` + `Idempotency-Key`), the cancel action, and the video-review view (player + URL refresh, quality hints, skipped/moderated scenes, approve / reject / re-make, download). All client code lives in the existing `episodes` feature (WD1) under `web/src/app/features/episodes/`.

**Out of scope (named, not stubbed).** Publishing, channels and veto pages (10.7.x — 10.7.2-T1 consumes this folder's review outcome), the owner journeys (10.10.2-T1), the story editor and its save/approve flows (10.5.x), version history, the series bible, credit/quote/balance text (P is metering-only — D14/F12), admin and S items (10.8.x, 10.9.x), and **all** server code: this folder consumes the frozen contracts of 09.6/09.7 and adds no route, no migration and no backend task.

**Contracts consumed, not re-derived.** `POST …/render` (F1), `DELETE /render-jobs/{id}` (F2), `RenderProgress` (F3), `GET /episodes/{id}` + `renderJob` (F5/F6), `POST …/video/approve|reject` (F9), `GET …/video-url` (F10), job outcome codes (F7), `nextActions` (F8), the realtime API (F15) and the shared UI/helpers of WR4 (F16).

## 3. Domain and data

All paths are `web/src/app/features/episodes/`. Domain code imports **nothing** from `@angular/*` or `rxjs` (lint, D2); only `data-access/**` imports `@shared/api` (D5).

### 3.1 Models

```ts
// domain/render.model.ts
export type RenderStatus = 'queued' | 'submitted' | 'running' | 'ingesting' | 'succeeded' | 'failed' | 'cancelled';
export type RenderStage =                 // wire strings, kept verbatim (F3/F5)
  'queued' | 'running' | 'ingesting' |    // guaranteed
  'voice' | 'subtitles' | 'images' | 'assembling' | 'checking';   // finer, optional
export interface RenderJob {
  renderJobId: string; status: RenderStatus; stage: RenderStage | string;   // `| string`: unknown values are stored, never rendered raw
  percent: number; attempt: number; imagesNeeded: number;
  submittedAt: string | null; finishedAt: string | null;
  errorCode: string | null;               // F7 outcome codes
  hints: readonly string[];               // F5 (10 CR-12)
  images: RenderImages | null;            // F6 (03.4.2-T1, soft)
}
export interface RenderImages { needed: number; succeeded: number; skipped: readonly SkippedScene[]; }
export interface SkippedScene { segment: string; reason: 'moderated' | 'rate_limited' | 'relay_rejected' | 'timeout' | 'upstream_error' | string; }
export interface RenderTimelineStep { key: 'queued' | 'running' | 'ingesting'; state: 'done' | 'active' | 'todo' | 'failed'; percent: number | null; subStepKey: string | null; }
export interface VideoUrl { url: string; expiresAt: string; }
export type RejectTarget = 'story' | 're_render';
export interface VideoReviewDecision { kind: 'approve' | 'reject' | 're_make'; note?: string; reason?: string; target?: RejectTarget; }

// domain/video-review.model.ts
export interface QualityNote { code: string; }            // F11 — `code` is a copy-key leaf, never prose from the server
export interface VideoReviewModel { finalVideo: FinalVideo | null; notes: readonly QualityNote[]; skipped: readonly SkippedScene[]; }
```

`FinalVideo { assetId, sizeBytes, sha256, contentType, durationSec, retentionUntil }` is already mapped by wave 1's `episode.mapper.ts` (09.5.3 `FinalVideoAssetDto`) — this folder **extends** the existing mapper instead of introducing a second one.

### 3.2 Ports (abstract classes) and their HTTP adapters

```ts
// domain/render.repository.ts
export abstract class RenderRepository {
  abstract requestRender(episodeId: string, etag: string, intent: IdempotencyIntent): Promise<string>;  // → renderJobId from `Location`
  abstract cancelRender(renderJobId: string): Promise<void>;                                          // 204
}
// domain/video-review.repository.ts
export abstract class VideoReviewRepository {
  abstract approveVideo(episodeId: string, etag: string, note?: string): Promise<{ status: string; etag: string }>;
  abstract rejectVideo(episodeId: string, etag: string, reason: string, target: RejectTarget, intent: IdempotencyIntent):
    Promise<{ status: string; etag: string; accepted: boolean }>;   // 202 ⇒ accepted = true (no Location, F12)
  abstract getVideoUrl(episodeId: string): Promise<VideoUrl>;       // TTL ≤ 15 min (F10)
}
```

Both ports import `IdempotencyIntent` from `core/http` (10.2.3-T1) — no local key type. `data-access/render-http.repository.ts` and `…/video-review-http.repository.ts` implement the ports over the D5 generated client and return **`Promise<T>` only** (no `HttpResponse`, D5); they throw `AppError` built by `AppErrorMapper` (10.2.2-T1). `requestRender` sends `withIfMatch(etag)` + `Idempotency-Key` and reads `Location` through `readEtag`-adjacent response handling; `approveVideo`/`rejectVideo` send `withIfMatch` (D5) and the reject sends an `Idempotency-Key`; `getVideoUrl` sends no `If-Match`. `EpisodesHttpRepository` (10.5.3-T1) still owns `GET /episodes/{id}`; the two new adapters are registered in the episode page component's `providers` next to it (component scope — `Route.providers` would outlive the page).

## 7. Jobs and integrations

- **Realtime.** `RenderProgress` is read from `RealtimeService.progress`, keyed by episode id, and merged **in place** (no refetch, F15); `subscribeEpisode(episodeId, handler)` is subscribed **before** the first `makeVideo()` call and torn down by the page component's `DestroyRef`. `EpisodeUpdated` and `resync` only schedule `EpisodeDetailStore.refetch()` (coalesced 250 ms by the realtime service itself). The view never parses an event payload as state.
- **Timers.** Two, both `DestroyRef`-scoped to the page component and gated (D13/F18): (1) a 1 s `now` tick that runs only while `status ∈ {queued, submitted, running, ingesting}` and `document.visibilityState === 'visible'`, and stops at the first terminal status — it drives `elapsedSec` and the 30 s `waitingForSlot` threshold (WB2/WD2). The elapsed baseline is `submittedAt ?? queuedSince`, because `submittedAt` is `null` for exactly as long as the job waits for a node (09.6.1-T1 sets `submitted_at` only at `MarkSubmitted`); `queuedSince` is a **client-side, non-persisted** stamp taken the first time the store sees `status = 'queued'`, and it is cleared once `submittedAt` exists or the job reaches a terminal status. (2) the URL-refresh check, `visiblePoll({ intervalMs: 60_000, run })` from `core/state/visible-poll.ts` (10.2.6-T1) which refreshes when `Date.now() >= Date.parse(expiresAt) − 60_000` (WB3), plus one forced `refreshUrl()` from the player's `error` event. `visible-poll` already pauses when the tab is hidden or the user is idle, so no refresh happens from an unwatched tab (D7/WR11) — the number of URL requests per session is bounded by `ceil(sessionVisibleMinutes)`.
- **No polling of the render job.** The timeline is event-driven; when realtime is paused by the activity gate the shared `realtime.paused` bar (10.2.6-T1) offers "Continue" (a user action → refresh → reconnect → `resync` → refetch) instead of this folder adding a second poll (D17 keeps polling for the autopilot run log).
- **Storage.** The signed URL is fetched on demand, held in memory only, never logged, never in `localStorage`/`sessionStorage`/the URL, and dropped on teardown (WD10).
- **E2E integration.** 11.5.1-T1's `e2e.yml` runs the Playwright specs against compose + mock-mpt (F17); `MOCK_RENDER_SECONDS` keeps the timeline scenario short, `MOCK_IMAGE_REPORT=moderated_all` and `MOCK_FAIL_MODE=quality:<check>` produce the skipped-scenes and `render_quality_failed` screens, `MOCK_FAIL_MODE=image_moderated` produces the "Edit scenes" failure. 10.10.2-T1's journeys drive this folder end to end and select by the `data-testid` values fixed in each task (see §10 O-3).

## 8. Security and privacy

- **Session.** No new auth mechanism: the access token stays in `SessionStore` memory and the D6 interceptor attaches it; the 401 matrix of WR9 is untouched (`episode_conflict`/`keyword` 409s are never retried; only a code-less/`unauthenticated` 401 refreshes once). `If-Match` is sent on every mutating call (F1/F9) — no blind writes; `Idempotency-Key` is a client UUID that never appears in a URL, in logs or in the hub ticket (10.5.2-T1:77).
- **Signed URLs (WD10/F10).** Fetched per view open, refreshed in place, never persisted, never logged (dev console included), never placed in the URL bar or in an `href` other than the player/download element, and never sent to the hub. The file name is built by `safe-filename.ts` (D4/WR4) and the **server's** `Content-Disposition` is the authority. `download` opens with `rel="noopener"`.
- **No third-party script** on any wave-2 screen; the player is the native `<video>` element and the signed media URL is a plain attribute value, so no `bypassSecurityTrust*` is needed. **The served CSP does have to allow the storage origin**: a presigned URL points at the storage service's public origin (`Storage:PublicServiceUrl`, media origin per **10 CR-21**), which the environment must list in `NTS_CSP_MEDIA_ORIGINS` so the D4 header's `media-src 'self' ${NTS_CSP_MEDIA_ORIGINS}` matches (per-environment config owned by 10.1.1-T2/10.1.6-T1 — D4/WR2/WR13). The header and the directive list are untouched by this folder, and each task's e2e assertion includes the CSP fixture while the player gets its `src` and plays (T3 acceptance) — so a missing origin fails the spec instead of silently producing a black player.
- **Rendering text.** Stage names, hint codes, failure codes and scene reasons are **our** keys, resolved through i18n and interpolation only — the server's `detail` is never rendered (F20); no `[innerHTML]`, no Markdown. A scene address from the server is parsed by `segment-address.parse` and rendered only when it parses.
- **Data minimisation.** The client stores `renderJob` fields it displays (no `params`, no prompt text — they never leave the server anyway, F7/09.6.1-T1:202), and the review view holds no asset bytes. Nothing is written to `localStorage`/`sessionStorage` (D2/D6 lint).
- **Tenant isolation** is the API's job: another user's episode/job is 404 (F1/F2/F10) and the UI renders `errors.not_found` without probing.
- **Audit** claims are server-side only (`episode.video_url_issued`, `episode.video_approved`, `episode.video_rejected`); the client never claims an audit row.
