## Goal

Ship the owner-facing `/channels` page of the new `publishing` feature: list the owner's YouTube connections (`GET /channels`), start a connect through the API's two gates (re-auth ≤ 5 min → 401 `reauth_required`; legal acceptance → 409 `legal_acceptance_required`) and hand the browser to the API-returned authorization URL with an origin allow-list check, render the callback outcome (`?connected=youtube` / `?error=<oauth_state_invalid|oauth_denied|oauth_exchange_failed|channel_already_connected>`) exactly once and without leaving it in history, and disconnect a connection behind a confirm dialog that states the immediate Google revoke, the 7-day deletion and the Google permissions link (`DELETE /channels/{id}`). The whole page is behind `authGuard` and the `youtube_publish` flag, in vi and en, WCAG 2.1 AA, with Vitest suites on hand-written fakes and a Playwright + axe spec that runs in 11.5.1-T1's `e2e.yml`.

**Store surface** (exactly as `plan.md` §3): `channels`, `status('idle'|'loading'|'ready'|'error')`, `error` (blocking), `connectState('idle'|'starting'|'navigating')`, `disconnecting: string|null`, `actionError`, `result: ChannelResult|null`, `featureEnabled = computed(() => session.hasFeature('youtube_publish'))`; methods `load(): Promise<Result<void>>`, `connectYouTube(): Promise<Result<'navigating'|'blocked'>>`, `disconnect(id): Promise<Result<void>>`, `readCallbackResult({connected,error}): void`, `dismissResult(): void`. No optimistic state; no `localStorage`; no timers.

**Connect flow.** `POST /channels/youtube/connect` (no body, no `Idempotency-Key` — the route is deliberately non-idempotent). On `200` validate the URL before navigating (WD10 + **WT-W13**): `new URL(u)` with `protocol === 'https:'`, `hostname === 'accounts.google.com'`, `pathname === '/o/oauth2/v2/auth'`, empty `username`/`password`, empty `port`, and a `redirect_uri` query parameter that is the same-origin callback (`new URL(u).searchParams.get('redirect_uri')` parsed to `origin === location.origin` and `pathname === '/api/v1/channels/youtube/callback'` — never a hardcoded host, so dev `http://localhost:4200` and prod agree; the endpoint path is the API's configured `YouTubeOptions.AuthorizationEndpoint`, `06.1.2-T1`, so a change there must change this allow-list too); then `Location`-free `window.location.assign(u)` (fresh top-level navigation; the URL exists only in a local variable — never logged, never bound to an anchor). On `401 reauth_required` → `ReauthService.ensureReauthenticated()` (10.3.3-T3; single-flight, writes no client state — WR8) and on `ok` retry the `POST` **once**; `invalid_credentials`/`invalid_mfa_code` stay in the dialog, `session_revoked` ends the session (WR9/D6), `rate_limited` shows `RetryCountdown` from `retryAfterSec`. On `409 legal_acceptance_required` → **this page** opens 13.2.1-T1's dialog (the account feature's `LegalAcceptanceStore` + `LegalAcceptanceDialog` at `features/account/{application/legal-acceptance.store.ts,ui/legal-acceptance-dialog/}`, reached through `@features/account/index.ts` — D2's only legal cross-feature path) for the documents in `AppError.fieldErrors['documents']` (sorted; the dialog refreshes `GET /me/legal` itself and never parses actions from the body), and on acceptance retry the `POST` **once**; the page owns this wiring because 13 hands the 409 → dialog mapping to 10.2.2-T1 (`13.1-legal-acceptance/plan.md:147-149`) while 10.2.2-T1's produced list has no legal branch (`10.2.2-T1-app-error-mapper.md:175-178`) — a mapped-but-unopened dialog would dead-end the connect. If 10.2.2-T1 later adds that branch, this page's explicit `AppError.code` check still wins and nothing double-opens. A second failure of either gate is terminal (no third attempt). Retries are `USER_ACTION` (WR11) and re-evaluated by the server (the re-auth window and the legal versions may both have moved) — a late `reauth_required` after a successful re-auth is shown as `errors.reauth_required`, not retried again.

**Callback handling.** In the page constructor, read `ActivatedRoute.snapshot.queryParamMap` **once**: `connected === 'youtube'` → `{ kind: 'connected' }` + `load()` (so the banner can name the channel from the freshly fetched first row); `error` ∈ the closed four-value set → `{ kind: 'error', code }`; anything else → nothing. Then `Location.replaceState('/channels')` so the outcome is out of history and never re-renders on back/forward. The banner renders in a `role="status"` `aria-live="polite"` region that gets programmatic focus (`tabindex="-1"`) on that landing, and is dismissed with `channels.result.dismiss` (focus then moves to the list heading). Because the callback is a full page load on our origin, the normal boot path applies (`provideAppInitializer` refresh → `authGuard`); if the refresh family was revoked the guard sends the user to `/login?returnUrl=/channels?connected=youtube` and the query survives to re-render the result after login (D6's `returnUrl` regex accepts it).

**Disconnect flow.** `channel-row` emits `disconnect(id)`; the page opens 10.1.3-T1's `ConfirmDialog` (no `cost-line` — D14) with `channels.disconnect.title` (names the channel) and the `channels.disconnect.*` body paragraphs (access removed now, revocation at Google only requested, pending publications cancelled, running uploads not stopped, data scheduled for deletion 7 days after, published videos untouched) *(10.7.1-T0 S75)* and a link to `https://security.google.com/settings/security/permissions` (`target="_blank" rel="noopener noreferrer"`, `channels.disconnect.googlePermissions`) plus `/{locale}/privacy` (`channels.disconnect.privacyLink`; the routes are 10.3.1-T1's, D12). Confirm → `DELETE /channels/{id}` (no `If-Match`, no `Idempotency-Key` — the route is idempotent by contract) → `204` → `load()` + `channels.disconnected` in the live region. Cancel → no request, focus back to the row menu trigger. Disconnect is offered for `active`/`expired`/`error` (06.4.1-T1 handles any non-revoked row, step 2) and hidden for `revoked`.

**Shell integration.** Append to `NAV_ITEMS`: `{ id: 'channels', labelKey: 'shell.nav.channels', route: '/channels', visible: () => hasFeature('youtube_publish') }` (10.2.6-T1:27 — the screen task adds its own entry with its child route; if the shell already ships it, assert instead of appending, see plan.md §10 [OPEN] 1 — check the `hasFeature` signature and fall back to `session.me()?.features ?? []` with an absent array meaning flag **off**). Add the lazy route in `app.routes.ts`. No `@defer` (nothing heavy on this page), `track channel.id` in the list, everything `OnPush`.

**Performance.** One `GET /channels` per page entry and one after each successful action; the server projects it in a single SQL command with no paging (`06.1.2-T2-channel-connection.md:96`), so no N+1, no hydration loop and no client cache (D13/F23) — the list is intentionally re-read so a returning owner never sees a stale status. No polling, no timer, no realtime subscription (06 raises no SignalR frame for a channel change — `06.1-connect/plan.md:253`), therefore nothing to dispose; the only unavoidable round trip is the OAuth navigation itself. The chunk contains no new dependency (bundle: Material components already in the initial bundle + this feature's small lazy chunk).

**Security.** (a) Allow-list check on `authorizationUrl` before navigating (WD10 + WT-W13): `https:`, host exactly `accounts.google.com`, path exactly `/o/oauth2/v2/auth`, no credentials, no explicit port, and `redirect_uri` equal to `${location.origin}/api/v1/channels/youtube/callback`; a failing value disables the navigation path and shows `channels.error.badAuthorizationUrl` with a dev-only console error; (b) the `state`/PKCE URL is never logged, stored, or rendered into the DOM; (c) the OAuth hand-off uses a **top-level** `location.assign` so the `SameSite=Lax` `__Host-nts_oauth` cookie set by the `POST` response (HttpOnly, Secure, 10 min) is sent on the callback GET — the SPA never reads or writes it; (d) only the closed set of four redirect codes maps to copy; an unknown value is ignored (no reflection into the DOM) while the URL is still cleaned; (e) no token, `oauth_client_id` or `authorizationUrl` is logged (the token never reaches the SPA at all — `ChannelConnectionDto` has no token field); (f) `USER_ACTION` on every call so an idle tab does not silently refresh (WR11) and `reauth_required` is never replayed by the interceptor (WR9); (g) nothing persists client-side; (h) no third-party script/font, no `innerHTML`/`bypassSecurityTrust*`, and the one external link is a plain `rel="noopener noreferrer"` anchor — 10.1.6-T1's CSP/Trusted-Types header needs no new source; (i) the revoke/disclosure duty is discharged by the server cascade (Google revoke → token wipe → 7-day `data_deletion_requests(scope=channel, reason=in_app_revoke)`) and stated in the dialog (DECISIONS §10.6:277).

**Accessibility (D16, screen-specific).** Live-region result banner (`role="status"`, `aria-live="polite"`, focusable, dismissible, focus handed to the list heading after dismissal); every status shown as text + icon in `StatusChip` and repeated as the `expired`/`error` hint sentence (never colour alone); Connect is a native button with `aria-busy`/`disabled` while starting and a decorative spinner that becomes static text under `prefers-reduced-motion`; the row menu has an accessible name including the channel title, Escape closes it and restores focus; `ConfirmDialog`/`ReauthDialog`/`LegalAcceptanceDialog` trap focus and restore it to their trigger; `actionError` renders in an inline `role="alert"` region linked by `aria-describedby`; 360 px stacks a row (chip, title with `overflow-wrap: anywhere`, dates, menu) with no horizontal scroll, including the longest vi dialog text (the `channels.disconnect.*` paragraphs together) *(10.7.1-T0 S75)*; contrast ≥ 4.5:1 and focus ring ≥ 3:1 in both themes; targets ≥ 24 px; full keyboard path skip-link → nav → Connect → (dialog) → confirm.

**Reuse boundaries.** Consumed as listed under Inputs; produced for others: `Channel`, `ChannelStatus`, `ChannelResult`, `ChannelRepository`, `ChannelsStore`, `fake-channel.repository.ts`, `publishing.routes.ts`, `index.ts`, the `channels` scope (consumed by 10.7.2-T1 and 10.7.4-T1/T2). Deliberately not used, with reasons: `IdempotencyKeys` (non-idempotent connect, idempotent delete — no header on either route), `ConflictDialog`/`If-Match` (no conditionally-written resource; no ETag on the list), `visible-poll` (D17/WR16 limit polling to the run log and the veto tick), `RealtimeService.subscribeEpisode` (no channel event; `RealtimeData` is reserved for `RenderProgress`), `keywordFlags`/`setKeywordFlags` (keyword moderation gates make-video, WD3/WR6), `EpisodeDetailStore` (the list has its own store; the episode page's publication block is 10.7.4-T1's), `safe-filename`/`download-blob` (nothing is downloaded).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `authorizationUrl` host is not `accounts.google.com` (or `http:`, credentials, an explicit port, a path other than `/o/oauth2/v2/auth`, or a `redirect_uri` that is not `${location.origin}/api/v1/channels/youtube/callback`) | no navigation; `actionError` + `channels.error.badAuthorizationUrl`; dev-only console error; nothing stored or logged |
| The user never returns from Google (tab closed, 10 min state TTL) | nothing client-side to clean up; the next `/channels` visit is a plain load; the stale `oauth_states` row is purged by the next connect (06.1.2-T1 step 5) |
| The callback answers `oauth_state_invalid` (expired/used state, another browser, revoked family) | banner `channels.result.error.oauth_state_invalid`; Connect is offered again and mints a fresh state — the page never retries the callback itself |
| `channel_already_connected` | banner from the callback redirect (`?error=channel_already_connected`) and a defensive `actionError` mapping for a fabricated POST `409` with the identical wording — defensive only: the shipped connect route never returns it, the code arrives only as a callback redirect value (10.7.1-T0 S75); the row for the *other* account is not visible to this owner (tenant filter, 404 for foreign ids) |
| Session died during the OAuth round trip | `authGuard` sends the user to `/login?returnUrl=/channels?connected=youtube`; after login the query re-renders the result exactly once (only if it is still the same mount — `readCallbackResult` runs once per mount) |
| The owner reloads `/channels?connected=youtube` by hand later | the banner may appear again (a manual URL is a fresh landing): acceptable and documented — the state and the channel list are authoritative, and the query is stripped so the address bar no longer carries it for sharing/bookmarks |
| `404 not_found` on disconnect (another owner's id, or the row was purged between render and click) | reload the list + `errors.not_found`; no retry loop |
| `DELETE` double-submit (double click, second tab) | the second call is a contract no-op `204`; `disconnecting` disables the row while in flight, so the UI cannot stack dialogs |
| Disconnect accepted by the API but Google's revoke failed after 3 attempts | the API still returns `204` (tokens wiped, deletion request created); the page shows success — the failure is only visible server-side (`youtube_channel_revoke_failed_total`, §11 of plan.md) |
| A row disappears (`displayName` null after a purge, `externalAccountId` null) | renders `channels.status.unknownChannel` without crashing; `lastVerifiedAt` null hides the second date line |
| An unforeseen `status` value from a newer API build | mapped to `'error'` in the repository; the row renders the error chip + `channels.status.errorHint`, never an empty cell |
| The list returns while the user is already connecting/disconnecting | `load()` only replaces `channels`/`status`; `connectState`/`disconnecting`/`actionError` are untouched, so the in-flight action is never visually cancelled |
| `429 rate_limited` on the list | `RetryCountdown` on the Retry action; the page keeps the last good rows (no blanking) |
| `503 service_unavailable` on connect (client secret unreadable) | `actionError` + Retry copy; no state row was written, so retrying is safe |
| A re-auth succeeds but the retried `POST` still answers `reauth_required` | terminal failure with `errors.reauth_required` and a Retry button (never a third automatic attempt) |
| Legal documents are behind a version bump while the dialog is open | the dialog itself answers `409 legal_version_outdated` (`account.legal.outdated`); the page's single retry then reports `errors.legal_acceptance_required` and the user re-opens the dialog |
| Second tab connects the same channel while this tab is open | this tab's list is stale until the next navigation or action; there is no realtime frame for a channel change (06) and no poll (D17); the second tab's `POST` is not rejected (no conflict branch on the shipped route — 10.7.1-T0 S75), so completing its OAuth round trip lands on the callback with `?error=channel_already_connected` and shows that banner |
