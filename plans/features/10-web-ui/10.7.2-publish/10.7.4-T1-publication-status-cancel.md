## Goal

The episode page shows what happened after consent: one row per publication with its state (`awaiting_consent`, `scheduled`, `uploading`, `processing`, `published`, `failed`, `cancelled`), a stage indicator, the schedule/consent/quota times the DTO actually carries, and — when the row is still cancellable — a **Cancel publishing** action behind a confirm dialog. After the upload has started the row stops offering cancel and instead links to YouTube Studio (the API's own answer to a late cancel is a 409 that points there: `publication.cancel.uploaded_use_studio`, `06.2.6-T1:30`). The list is correct without polling storms: `PublicationUpdated` (ids only) triggers a refetch, `resync` covers reconnects and tab returns, and a 60 s visibility-gated poll covers a hub that is paused or down. This is the screen the owner returns to while an upload is queued, retrying or finished, so it must never show a stale state as current.

   readonly conflict = signal<{ id: string; etag: string } | null>(null);

3. `index.ts` — append the two exports above.
4. i18n keys (scope `publishing`, D10) — every key in `plan.md` §6.2 with `vi` + `en` values in `web/src/assets/i18n/publishing/{vi,en}.json`, including the handed-over `publications.status.*`, `publications.pre_audit_private`, `publications.go_live_unconfirmed`, `publishing_temporarily_unavailable` and the 409 key `publication.cancel.uploaded_use_studio` (verbatim from 06.2.6-T1:30).
5. Tests + the Playwright spec (below).

**Realtime and timers.** `subscribe()` registers `RealtimeService.subscribeEpisode(episodeId, handler)` (WR7/D8): `PublicationUpdated` with a matching `episodeId` → `refresh()`; `resync` → `refresh()`; both coalesced ≤ 1 per 250 ms; unsubscribe in `DestroyRef`. **There is no timer in this task** — no `visible-poll`, no interval (TL ruling, Main, 2026-09-25: D17's helper belongs to the autopilot run log alone), so the row list is refreshed only by the initial load, the realtime event, `resync`, and the user action that just ran (`cancel`). A store test asserts no interval/timeout is registered.

**Performance (WD9).** Exactly one list request per load/refresh; `@for` uses `track p.id`; the component reads `EpisodeDetailStore` for `nextActions` instead of calling `GET /episodes/{id}` again; no `@defer` is used (the list is small and must be visible), so nothing lazy-loads on this screen beyond the feature chunk itself.

**Security (WD10, 06 D17).** The cancel is destructive and always goes through the confirm dialog; a foreign/unknown row surfaces as `404 not_found` and is rendered as a generic missing-publication copy (no existence oracle); no publication title/description is logged (ids and codes only); the Studio link is external — `target="_blank" rel="noopener noreferrer"` (D4 CSP allows it because it is a navigation, not a fetch); no token or signed URL is handled here.

**A11y (D16, `plan.md` §6.2).** Rows are a list with a heading per row (publication title) so screen readers can navigate; the status change is announced **once per change** (the component diffs the previous status per id and writes to a single `aria-live="polite"` region, never on every render); icons always carry text (`StatusChip`); the stage indicator is an `<ol>` with text labels and `aria-current`; the cancel button uses `aria-describedby` pointing at the confirm dialog title and the row title; after the dialog closes focus returns to the cancel button; the empty state explains why there is nothing yet; ≥ 24 px targets, 360 px layout, no colour-only signal, `prefers-reduced-motion` honoured (the stage indicator never animates a transition it cannot skip).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Hub down / realtime paused (idle) | there is no timer fallback (TL ruling 2026-09-25): the rows keep the last known state, and `resync` on reconnect or on the tab becoming visible refetches once (D7/D8). A user action (`cancel`, reopening the panel) refetches too |
| `PublicationUpdated` arrives before the first fetch resolves | the fetch's result is kept and one coalesced refresh follows; no duplicated rows (keyed by publication id) |
| Late snapshot for a terminal row | the server drops it (06.2.5-T1:194); the client's refetch returns the same terminal state — no announcement, no flicker |
| Cancel racing the worker's first upload step | one of the two wins the row lock (06.2.6-T1:96): a 409 shows the Studio-link copy; the user is never told the cancel succeeded |
| Row already cancelled in another tab | repeat 204 → success copy; no second confirm loop |
| The channel was disconnected while the row was pending | the disconnect path already cancelled it (06.2.6-T1:102); the refetch shows `cancelled` |
| Quota-held / incident-held row | the row stays `scheduled` and shows the next attempt time, or the incident banner after two consecutive held fetches (O-W8); no cancel is offered again unless the state allows it |
| `failed` without an `errorCode` | `errors.unknown_error` + `traceId`, status chip still `publications.status.failed` |
| Studio link cannot be built (`externalUrl` null, no `externalPostId`, and no `externalAccountId` for the channel fallback) | the link is omitted and the state chip remains the truth; `publication.cancel.uploaded_use_studio` guidance still tells the owner to manage the upload in Studio (O-W3, CR-W8) |
| List request fails | previous rows stay on screen with an inline retry (`ErrorState`); the next refetch comes from `resync` or a user action, so the single-in-flight guard cannot be starved |
| Session ends (401 after refresh failure) | the route is discarded by the session flow (D6/WR9); the store holds no persistent state |
