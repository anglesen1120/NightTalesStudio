## Goal

The two links in the veto e-mail land on real pages instead of the app's 404. The **cancel link** is a capability URL: a public, session-less page that reads `#p=<publicationId>&t=<token>`, strips the fragment from the URL **before** any request, asks for one explicit confirmation, POSTs `{ publicationId, token }` to `/api/v1/publications/cancel-by-link`, and answers with one of two states — done, or one generic "link no longer valid" (used, expired, foreign or wrong-state token all look identical, so `06.2.2-T2`'s single `400 cancel_token_invalid` never becomes an enumeration oracle). The **approve link** is an owner page: `#p=&e=` in the fragment, no token at all, a session required (a signed-out visitor signs in and comes back to the full link), a preview of what is about to be published plus the `pc.v1` text, and one "Approve now" that consents with the row's `If-Match`. Both pages are deliberately thin: one request each, no polling, no third-party script, nothing written to storage. Owner value: the veto window is only useful if acting on it takes one tap.

## Design

**Files produced** (under `web/src/app/features/publishing/`; no new port and no HTTP code — the models are 10.7.2-T1's, `listForEpisode`/`consent` are wave-1's `PublicationRepository` via `@features/series` (CR-W7 adds its missing `ifMatch` argument), and `cancelByLink`/`consentText` are 10.7.2-T1's new `PublishingRepository`; §10 items 1–2, §3.2).

1. `application/veto-link.store.ts` — `VetoLinkStore` (provided by the public page):
   ```ts
   readonly phase = signal<'confirm' | 'submitting' | 'done' | 'invalid' | 'rate_limited'>('confirm');
   readonly error = signal<AppError | null>(null);
   readonly retryAt = signal<number | null>(null);          // 429 → RetryCountdown
   private publicationId = ''; private token = '';          // memory only, never persisted (D6)
   init(params: { p: string | null; t: string | null }): void;   // validates shape, strips the fragment, issues NO request
   confirm(): Promise<void>;                                // USER_ACTION; single-flight
   reset(): void;
   ```
   `init()` accepts only two GUID-shaped values; anything else → `phase = 'invalid'` with **zero** repository calls. `confirm()` calls `repository.cancelByLink(publicationId, token)` exactly once (a repeat call after `done` is a no-op — the token is already consumed, `06.2.2-T2:200`); the request goes out **without** an `Authorization` header and with no refresh path (the interceptor excludes the cancel endpoint — WT-W12; the boot refresh may have run earlier in the page's life, so the invariant is "no authenticated call to this endpoint"); a `400 cancel_token_invalid` (or any other failure that is not a rate limit) collapses to `invalid` with the one generic message; `429` → `rate_limited` + `retryAt` from `Retry-After`; `404 feature_disabled` → `invalid` (the visitor has no session and no other affordance). Nothing about the token is logged.
2. `application/approve-link.store.ts` — `ApproveLinkStore` (provided by the owner page):
   ```ts
   readonly phase = signal<'loading' | 'ready' | 'approving' | 'done' | 'invalid' | 'state' | 'not_found'>('loading');
   readonly publication = signal<PublicationDetail | null>(null);
   readonly consentText = signal<ConsentText | null>(null);
   readonly error = signal<AppError | null>(null); readonly conflictOpen = signal(false);
   readonly returnUrl = computed(() => ...);                 // '/publications/approve#' + the original fragment, URL-encoded (D6)
   init(params: { p: string | null; e: string | null }): Promise<void>;   // strips the fragment first
   approve(): Promise<void>;            // USER_ACTION; POST …/consent with If-Match = publication().etag
   reloadConsentText(): Promise<void>;                        // WT-W13: reload + re-render, then wait for a fresh explicit click
   reset(): void;
   ```
   `init()` with a missing/invalid `p` or `e` → `invalid` + `publication.approve.expired`, no request (F10). Otherwise it loads `GET /episodes/{e}/publications`, finds `id === p`: not found → `invalid`; `awaiting_consent` → `ready` (and the consent text loads in parallel through 10.7.2-T1's `consentText(locale)`); `scheduled|uploading|processing|published` → `done` with the row's status chip (revisiting the link after the fact, or after the autopilot job already consented — idempotent by design, `06.2.2-T4:92`); `failed|cancelled` → `state` with the status/error copy and no action. `approve()` posts the displayed version with the row's `If-Match`; `consent_text_outdated` → reload the text, re-render, and leave the CTA enabled for a **fresh explicit click** (`reloadConsentText()` — WT-W13: no automatic retry; a second consecutive failure after that click stops with the error copy, no loop); `409` → refetch and show `state`; `412` → `conflictOpen` (`ConflictDialog`, O-W7) with a refetch-first option; `429` → `RetryCountdown`. **No expiry gate**: a row past `vetoEndsAt` but still `awaiting_consent` stays approvable (`06.2.2-T4:61`).
3. `feature/cancel-by-link.page.ts` + `feature/approve-by-link.page.ts` — the two route components (`OnPush`, standalone, lazy). The cancel page never injects `SessionStore` and the authors must keep it that way (asserted by a unit test that injects the page's store with a repository spy and checks the interceptor-free path — see Tests); the approve page is wrapped by `authGuard` and computes `returnUrl` for the sign-in redirect.
4. `publishing.routes.ts` + `app.routes.ts` — append `/publications/cancel` and `/publications/approve` (both `RenderMode.Client` by D1's catch-all, WR1; the panel routes are untouched). 10.7.1-T1 created the file (coordination confirmed 2026-09-25).
5. i18n keys (scope `publishing`, D10) — `plan.md` §6.3/§6.4 with `vi` + `en`: `publication.cancel.title|body|confirmCta|done|invalidTitle`, `publication.approve.title|cta|done|expired|signIn`, and the shared `publication.error.cancel_token_invalid`.
6. Tests + the Playwright spec (below).

**Fragment handling (both pages, WD10/F9/F10).** Read `location.hash` once in the page component, hand it to the store, and immediately `history.replaceState(null, '', location.pathname)` — **before** the first request, so the token never appears in a request URL, a `Referer` of a later navigation, a share sheet or a back/forward entry. The value lives in the store's private fields only; no `localStorage`/`sessionStorage`/`core/prefs` write (D2/D6). A reload after `done` therefore shows the invalid/expired state rather than re-posting — which is the honest presentation, because the token is already consumed server-side (`06.2.2-T2:200`).

**Routes and guards.** `/publications/cancel`: no guard, no session dependency, one POST, no polling, no realtime (`D8` unused) — the page must remain usable when the hub and the refresh cookie are both irrelevant. `/publications/approve`: `authGuard`; if the session is gone the guard redirects to `/login?returnUrl=<encoded full link>` and the page restores the fragment after login (F10, D6's regex accepts `/publications/approve#p=…&e=…`). No `ReauthDialog` (this route has no re-auth gate; that gate is 10.7.1-T1's connect path, WD5).

**Security (WD10, WT-W12, 06 D17).** The cancel page's only request is the unauthenticated cancel-by-link POST — the interceptor attaches no `Authorization` header and runs no refresh for it (the boot refresh may have run earlier), which the e2e spec asserts from the request log as "no authenticated call to the cancel endpoint" rather than "no request at all"; the approve page sends no fragment value to the server (only the ids are used client-side, and `p`/`e` are validated as GUIDs before use); the consent text is rendered as text (no `innerHTML`, no `bypassSecurityTrust*`, plan §8/O-W6); no third-party script, no analytics, no new CSP directive (D4); nothing is logged beyond ids and codes.

**A11y (D16, plan §6.3/§6.4).** One `h1` per page, one primary action, the result announced once (`role="status"`, `aria-live="assertive"` for the destructive outcome), focus moved to the result heading after the POST, the confirm action never autofocused, the consent text block keyboard-scrollable with `aria-labelledby`, the conflict dialog traps and restores focus, ≥ 24 px targets, 360 px layout, no colour-only state, reduced-motion honoured.

**Performance.** Two lazy route chunks, one request each (cancel: 1; approve: 2 — list + consent text), no timers, no realtime, no `@defer` needed; both pages are trivially small and inherit the feature chunk's budget.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Double click / reload after success | the first POST consumes the token; the client refuses to re-POST (`done`), and a reload shows the invalid state — never a state leak, never a second cancel attempt (`06.2.2-T2:144,200`) |
| Token for another publication, or a publication that is no longer `awaiting_consent` | the same generic `cancel_token_invalid` message; the page cannot tell the difference (by design, F9) |
| Owner's account deleted (token row cascaded) | generic invalid, no error detail (`06.2.2-T2:202`) |
| Mail client prefetch/open-graph fetch | nothing happens: the page renders `confirm` and only a user click POSTs; the fragment is never sent to the server, so a prefetcher cannot consume the token (F9, WD10) |
| Fragment plus a query string (`?utm=…#p=…`) | the fragment is read and stripped; the query is left untouched |
| Approve link opened in a second tab after the first approved | the second load finds the row `scheduled` → `done` with the status chip (`06.2.2-T4:92`) |
| Approve link for a row past `veto_ends_at` | still approvable while `awaiting_consent` (`06.2.2-T4:61`) |
| `consent_text_outdated` twice in a row | one automatic reload-and-retry, then the error copy with a manual retry; no loop (F10) |
| Session ends between load and approve | the 401 goes through the interceptor (WR9); the page's next action re-runs the guard → sign-in with the fragment preserved (F10) |
| `youtube_publish` turned off | cancel → generic invalid; approve → the flag's error state (D14) |
| Rate limited (`auth` policy) | `RetryCountdown`; the confirm/approve action stays disabled until zero |

### Angular implementation amendment (2026-10-02)

- Frame evidence is the public-cancel/owner-approve family in screen 06 via `plan.md` §12; consent failure/reconfirm and fragment-cleanup focus remain behavioral/T0 proof.
- Each route is its own container with a page-scoped readonly store. Fragment values are parsed into memory, validated and removed before the first request; anonymous cancel uses the explicitly auth-suppressed data-access path. Route/session/request generations discard late results and teardown clears token, dialog and countdown state.
- Repository mapping owns 204/status/ETag/`Retry-After`; no token is logged, persisted or echoed. Consent outdated reloads text and waits for a new click; server row state/ETag is re-read before retry. Mockup approval controls do not authorize a client-side veto expiry rule or any additional action.
