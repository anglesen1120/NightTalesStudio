## 1. Scope

**User value.** After the owner approves the video, they publish the episode to their YouTube channel from the Studio itself: they fill the YouTube metadata (title, description, tags, visibility, optional schedule), see the exact `pc.v1` consent text the API will check, consent, and — when the daily YouTube quota is spent — see *when* the upload will happen instead of a failure. Afterwards the episode page shows the publication's live state (scheduled → processing → published), lets the owner cancel it before the upload starts, and points at YouTube Studio once it is up. From the veto e-mail the owner can act without hunting for the Studio: a single-use **cancel link** (public page, no session) and an **approve-now** link (owner page) that consents the publication with one tap.

**In scope (this folder).**
- `10.7.2-T1` — the publish form on the ready episode (metadata rules mirrored from the server, `pc.v1` consent step, quota-wait state from the ETA endpoint).
- `10.7.4-T1` — publication status widgets on the episode page (realtime + visibility-gated poll), cancel before upload, YouTube Studio link after upload.
- `10.7.4-T2` — the two e-mail landing pages: `/publications/cancel` (public, capability token in the fragment) and `/publications/approve` (authenticated owner page).

**Out of scope (named owners, do not duplicate).** Channels page, OAuth connect, callback result, disconnect (10.7.1-T1 — **WD5**); render timeline, make-video, video review (10.6.1-T1/T2, 10.6.2-T1 — **WD2/WD3/WD4**); the Playwright owner journeys and the e2e stack extras (10.10.2-T1, **WD8**, **WT-W1**); the veto-window **list** and the publication **edit** dialog (`PATCH`, 10.4.3-T2, wave 1, C9); TikTok publishing (10.7.3, R2); every S item (credits, buy buttons — D14); every server-side change (06/09 own the routes; this folder consumes them and files CR requests in §10 instead).

## 7. Jobs and integrations

- **Subscriptions.** `PublicationsStore` and `PublishFormStore` subscribe with `RealtimeService.subscribeEpisode(episodeId, handler)` (WR7) and unsubscribe in `DestroyRef` (D13). `PublicationUpdated` → refetch (ids only, F8); `EpisodeUpdated` → the episode page's own `EpisodeDetailStore.refetch()` (10.5.2-T1), which drives the panel's `nextActions`; `resync` (reconnect or tab visible, D8) → one coalesced refetch per store (≤ 1 per 250 ms).
- **No timers.** **There is no polling in this folder** (TL ruling, Main, 2026-09-25): D17's `visible-poll` stays the autopilot run log's alone, so publication state is driven purely by `PublicationUpdated` + `resync` + the action that just ran (`10.2.6-T1`'s helper is not imported here; `RetryCountdown`'s own tick belongs to 10.2.2-T1's component, and the veto-list countdown is 10.4.3-T2's). The ETA is re-read when the panel opens, after a consent, and on a `resync`-driven refresh while the quota-wait block is shown — a user-triggered action is never needed because the API is the authority on submit. Nothing recomputes on a timer, so D7's activity gate has no work to do here.
- **Performance.** No N+1: one `GET /episodes/{id}/publications` per episode (the list is a handful of rows, F1) plus one ETA read per open/consent/resync; the panel does not re-fetch the episode (it reads `EpisodeDetailStore`, WT-W10); the consent text is fetched once per consent step and cached in the store for the panel's lifetime; rendering is limited to the status list (`@for … track p.id`); the panel is lazy through the `publishing` feature chunk (`loadComponent`), and the two fragment pages are separate lazy routes so the publish bundle never loads on `/publications/cancel`. No publication state is persisted (no client cache, D13).
- **Flows.** Submit → create → consent → wait is one store with explicit steps; the button is disabled while `submitting` (single-flight) because the route has no idempotency key (F1); a lost create response is recovered through 409 + refetch (F5).

## 8. Security and privacy

- **Fragment tokens.** `/publications/cancel#p=&t=` — read once on init, `history.replaceState(null, '', location.pathname)` **before** any request; never placed in a query string, never in a header, never logged, never stored (`localStorage`/`sessionStorage` are forbidden outside `core/prefs`, D2); the token lives only in `VetoLinkStore` memory and is discarded on `done`/`invalid`. The approve page's `#p=&e=` are ids, still stripped the same way (they are not secrets, but the strip is uniform and keeps the URL clean).
- **No session on the cancel page (WT-W12).** The route is public; its component and store never inject `SessionStore`, never call an authenticated route, and the only request is `POST /publications/cancel-by-link` (WD10). The interceptor **excludes** that route: it attaches no `Authorization` header and never runs the 401 refresh for it (the boot refresh from `provideAppInitializer` may still have run earlier in the page's life, which is why the claim is "no authenticated call to the cancel endpoint" rather than "no request at all"). The API's own `Referrer-Policy: no-referrer` + `Cache-Control: no-store` (F1) is the server half; the web container already sends `Referrer-Policy: no-referrer` on every response (D4).
- **Owner page.** `/publications/approve` is behind `authGuard`; a signed-out visitor is redirected to sign-in with the **full** link (path + fragment) URL-encoded as `returnUrl`, which satisfies D6's `^/(?![/\\])[^\s]*$`; the fragment is restored by the client after login (F10). `ReauthDialog` is not needed here (no re-auth gate on this route — that gate is 10.7.1-T1's connect path, WD5).
- **Errors.** The mapper (`AppErrorMapper`, 10.2.2-T1) turns ProblemDetails into `AppError { code, status, fieldErrors, retryAfterSec, traceId }`; the closed envelope carries **no** action list (F6) — the UI never parses actions out of an error body, it refetches the row. `detail` is never shown raw; `traceId` is shown in a collapsible line for support (D9). 428 is treated as a client bug (logged in dev, generic copy).
- **XSS/CSP.** The consent text is rendered as text (O-W6) — no `innerHTML`, no `bypassSecurityTrust*` (D2/D4); no third-party script on any page in this folder (WD10); no new CSP directive is needed (`connect-src 'self'`, `frame-ancestors 'none'`, `form-action 'self'` cover these screens); the e2e fixture fails on any `securitypolicyviolation` (D4).
- **Data minimisation.** No publication titles/descriptions/tokens are logged (06 D17): the client logs ids and codes only; `traceId` from the error envelope is the support handle. Nothing about a publication is written to `core/prefs`.
