# 10.7.3-T0 — TikTok posting UI design (connect + creator info + composer states)

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 10.7.3 | S (0.5) | UX | 10.1.3-T1, 07.2.1-T1 (soft) | 10.7.3-T1, 10.7.3-T2 | S · R2 |

## Goal

Produce the approved interface design for the two R2 TikTok surfaces — the TikTok section of `/channels` and the composer at `/episodes/:id/publish/tiktok` — covering **every** state of §C3 SD1/§6 of this folder's `plan.md` at 360/768/1280, in vi and en, dark and light, with focus order, keyboard path and a11y annotations, built from the D11 design-system components. The deliverable is the design link plus the screen × state inventory recorded in `plan.md` §6 and the **owner's approval**; no implementation task in `10.7.3-tiktok-post/` starts before that approval (SD11, §C7 design gate). This is a design-only task: it writes no application code.

## Design

**Artboards (project file `10.7.3-tiktok-post`, one page per screen, one frame per state × breakpoint).**

Screen A — `/channels` TikTok section (state matrix):

| # | State | Notes for the mockup |
|---|---|---|
| A1 | no connection | empty-ish card, `Connect TikTok` = the page's single primary action, one sentence on what will be asked (`video.publish`) |
| A2 | connecting | button disabled + `aria-busy`, spinner that becomes static text under `prefers-reduced-motion`; the "you will leave the app" wording is explicit before navigating |
| A3 | connected | `StatusChip` (`active`), `nickname` + avatar, authenticated-since text from the DTO only, secondary `Reconnect` hidden while healthy |
| A4 | expired / `tiktok_reauth_required` | reconnect card (`role="alert"`), why (grant died / needs re-consent), `Reconnect` primary, the reason is text + icon, never colour alone |
| A5 | creator info loading / ready | skeleton with the avatar box reserved (no layout shift at 360 px) |
| A6 | `canPost = false` | blocked card showing `blockReason` verbatim (dynamic server text, not a key) with the retry affordance and a link to `/channels` refresh |
| A7 | callback result | banner for `connected=tiktok` and the five error codes (`oauth_state_invalid`, `oauth_denied`, `tiktok_scope_missing`, `oauth_exchange_failed`, `channel_already_connected`) — `role="status"`, focusable, dismissible; generic copy that never echoes `code`/`state` |
| A8 | flag off | the section is absent, no hole in the layout (spacing behaves as if the card never existed) |

Screen B — `/episodes/:id/publish/tiktok` composer (state matrix):

| # | State | Notes for the mockup |
|---|---|---|
| B1 | loading | creator info + consent text in flight; Post disabled |
| B2 | episode not render-ready | why the composer is unavailable + back link (no action buttons) |
| B3 | creator blocked | same blocked card as A6, Post disabled with the reason referenced by `aria-describedby` |
| B4 | form | caption `<textarea>` (seeded from `title`) + `CharCounter` (UTF-16 units, `2200` shown as the limit), the **credit-free** note is absent (no `cost-line`, 07 D16), settings switches (comment/duet/stitch/disclosure/organic/branded content), variant radios in a `fieldset`/`legend` |
| B5 | private-only notice | the persistent, non-dismissible `role="note"` "private until the TikTok audit passes" — visually attached to the Post button, present in **every** composer state that can submit |
| B6 | validation error | inline per-field error (`bindFieldErrors`), summary at the top of the form; caption over-limit highlighted on the counter |
| B7 | consent block | variant `music` / `branded` selected → the server's consent text rendered as plain text above Post; loading and missing-text states |
| B8 | `consent_text_outdated` | the text is replaced by the refetched one, a warning explains the version changed and the user must click again (no auto-retry) |
| B9 | submitting / created | Post disabled + `aria-busy`; then the explicit **"no upload happens here — TikTok downloads the video from our storage"** statement in place of any progress UI (FC13) |
| B10 | consenting / done | consent submitted → the publication status panel (10.7.4-T1's widgets) embedded below the form with its own states |
| B11 | mapped failures | 400 `tiktok_invalid_post_settings`, 400 `tiktok_video_too_long`, 409 `tiktok_cannot_post_now`, 409 `channel_already_connected`, 429 `tiktok_creator_cap`, 429 `tiktok_rate_limited` — one alert frame each, copy keys from §C1/07 D10 |
| B12 | flag off / 404 | a plain "not available" page with the nav back, no composer chrome |

**Breakpoints.** 360 px (single column; textarea full width; consent text and notice stack above a sticky Post bar; no horizontal scroll; ≥ 24 px targets), 768 px (two columns: creator/notice left, form right), 1280 px (same grid inside a max-width content column; the status panel spans both columns).

**Themes and text.** Dark + light from the D11 tokens only (no raw hex in the mockups); vi and en frames side by side with the longest realistic strings (German-style expansion is not required, but no truncation of `tiktok.section.privateNotice`, `tiktok.blocked`, the longest `blockReason` sample, and the two consent texts). The `tiktok` scope keys from `plan.md` §6 are the mockup labels; dynamic server text is annotated as "server text, not a key".

**Focus order and keyboard path (annotated per frame).** Screen A: page header → channel list rows → TikTok card (connect/reconnect) → creator card's refresh → banner (focusable, then `Escape`/dismiss returns focus to the card heading). Screen B: `PageHeader` → caption textarea → counter (announced via `aria-live="polite"`) → settings → variant radios → consent section → private notice → **Post** → status panel. Tab order matches the visual order at every breakpoint; the dialogs used (`ReauthDialog`, `LegalAcceptanceDialog`, `ConfirmDialog`) trap focus and restore it to their trigger; no keyboard trap outside them; `Escape` closes the banner and dialogs; every interactive element has a visible focus ring at both themes and at 200 % zoom.

**A11y annotations in the file.** `role`/`aria-live` per region (`status` banner, `alert` blocked card, `note` private notice, `polite` counter), `aria-busy` on submitting buttons, `aria-describedby` from Post to the notice and to the block reason, list semantics for the channel card group, form labels + `aria-invalid`, target sizes (24 px min, 44 px for the primary), contrast values against the D11 token pair used, and the `prefers-reduced-motion` variant of every transition.

**D11 components used (inventory, no new component).** `PageHeader`, `StatusChip`, `EmptyState`, `ErrorState`, `LoadingState`, `ConfirmDialog`, `CharCounter`, plus the wave-1 form controls and inline error alert. Screens consume them as-is; if a state needs a component that does not exist, that is a design-gate finding recorded in §10 of `plan.md`, not a silent new component.

**Nothing to design (explicit non-goals).** No upload widget, no progress bar, no file picker, no schedule/date field (07 D3 manual publishing), no public-privacy selector, no credit/price line (07 D16), no TikTok-branded assets beyond the DTO's avatar (no vendor logo is invented), no mobile breakpoint below 360 px.

## Steps

1. Confirm the design tool, the project file name and the approval channel with the owner; read `10.1.3-T1`'s delivered component list and the D11 token sheet on disk (do not sketch a component that does not exist).
2. Sketch low-fidelity wireframes for screen A's A1–A8 and screen B's B1–B12 (one frame per state), then review the flow order with the TL: connect → callback → creator info → composer → create → consent → status.
3. Produce hi-fi mockups from the D11 tokens/components for the three breakpoints × two themes; add vi and en text frames with the longest strings.
4. Annotate focus order, keyboard path, `aria-*` per region, target sizes, contrast pairs and the reduced-motion variants.
5. Cross-check the state list against `plan.md` §6 and §C3 SD1 (`:654`) — every state in the table has a frame, and every frame maps to a state (no orphan frames).
6. Walk the design with the owner; record approval (date, design revision, approver, link) in `plan.md` §6 and in the record below; hand the link to 10.7.3-T1/T2 (they have this task as a hard dependency).
7. File any state that the design cannot express with the current D11 components or routes as an `[OPEN]`/CR note for the TL (e.g. the nav-target question of `plan.md` §10.2, the `?connected=tiktok` reader of §10.1).

## Acceptance checks

- **Given** the design file, **when** the TL compares its frames with `plan.md` §6 and §C3 SD1's state list, **then** every state has a frame and every frame maps to a state (bidirectional coverage), with no state marked "TBD".
- **Given** the hi-fi mockups, **when** checked against the D11 inventory, **then** every component used exists in 10.1.3-T1's delivered set and no new component/token is introduced (or the exception is filed as an `[OPEN]` in `plan.md` §10).
- **Given** the three breakpoints, **when** the 360 px frames are inspected, **then** no frame has horizontal scroll, every target is ≥ 24 px, and the private notice and the Post button are both visible without scrolling past the consent text.
- **Given** the vi and en frames, **when** compared, **then** no label, notice or consent-text sample is truncated, and every string maps to a key in the `tiktok`/`errors` scopes or is annotated as dynamic server text.
- **Given** the annotation layer, **when** read with a keyboard-only walkthrough, **then** the focus order per frame matches the visual order, every region's role/`aria-live` is stated, and the dialog focus trap/restore behaviour is documented.
- **Given** FC13's policy trap, **when** the design is reviewed, **then** it contains no upload widget, no progress bar, no file picker and no public-privacy selector, and the persistent private-only notice is in the inventory.
- **Given** the design gate (§C7 `:722`), **when** the owner approval row in `plan.md` §6 is filled, **then** 10.7.3-T1/T2 may start; while the row is PENDING neither task may begin.

## Tests

No automated test: a `-T0` design task ships no application code (SD11/ST-3 pattern). Verification is the review evidence above:

- Coverage table produced in the design file: state id → frame id → breakpoint → theme → language (a human-checkable matrix, the design analogue of the `plan.md` §6 table).
- A one-line check in the review notes that the D11 component inventory was compared against 10.1.3-T1's delivered list (with the file paths read).
- The annotation walkthrough script (keyboard-only order per screen) recorded in the design file; it becomes input to 10.10.1-T2's manual matrix for the publishing screens.

## Failure handling and edge cases

| Situation | Handling in the design |
|---|---|
| The D11 component set cannot express a state (e.g. a two-step consent block) | compose from existing primitives only; if impossible, record an `[OPEN]` in `plan.md` §10 for the TL instead of inventing a component |
| `blockReason` from the server is long or in one language only | layout reserves two lines + expandable text; the string is rendered verbatim and never translated locally |
| The consent text is long (either variant, both languages) | the consent block is a scrollable region with `max-height` on 1280 px and an inline expander on 360 px, always fully readable before Post |
| Caption at exactly 2200 UTF-16 units with astral characters | the counter's emoji test frame (UTF-16 units, not code points) is drawn and annotated |
| Dark-theme contrast for `StatusChip` variants | every chip variant is drawn against both themes with the token pair and its contrast value annotated |
| The owner requests a public-privacy option | it is impossible in R2 (FC13/K11, S-O5) — the design records the refusal and the private-only notice instead |
| The design tool link is not shareable with the repo | export the frames to a PNG/PDF bundle next to the link and reference both in `plan.md` §6 |
| Approval arrives with change requests | apply, bump the revision, re-record the approval row; T1/T2 stay blocked until the new revision is approved |
