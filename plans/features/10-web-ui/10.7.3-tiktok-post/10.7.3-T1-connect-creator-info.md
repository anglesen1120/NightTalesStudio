## Goal

Add the TikTok connecting surface to the existing `/channels` page: a flag-gated section that starts the connect (`POST /channels/tiktok/connect` → top-level navigation after an allow-list check), reads the callback outcome once (`?connected=tiktok` / `?error=<code>`) and clears it from the URL, renders the connection card with its `status` — including the reconnect card for a dead grant (`expired`) or a `tiktok_reauth_required` publication — and shows the creator info from `GET /channels/{id}/tiktok/creator-info` cached per page, with `canPost = false` + `blockReason` rendered verbatim. The whole area is behind `authGuard` + `tiktokEnabledGuard` and `hasFeature('tiktok_publish')` (navbar entry, routes, copy). Design: `10.7.3-T0` (hard dependency, SD11).

**Store surface** (signals + `OnPush`, D13; same shape as `10.7.1-T1:44`):

```ts
class TikTokStore {
  readonly creatorInfo = signal<TikTokCreatorInfo | null>(null);      // cached per page (SD10)
  readonly creatorStatus = signal<'idle' | 'loading' | 'ready' | 'error' | 'hidden'>('idle');
  readonly connectState = signal<'idle' | 'starting' | 'navigating' | 'reauth'>('idle');
  readonly actionError = signal<AppError | null>(null);
  readonly featureEnabled = computed(() => this.session.hasFeature('tiktok_publish'));
  connect(): Promise<Result<'navigating' | 'blocked'>>;   // mints/reuses an IdempotencyKeys intent internally
  loadCreatorInfo(channelId: string, opts?: { force?: boolean }): Promise<Result<void>>;
  hideArea(reason: 'feature_disabled'): void;
}
```

`connect()` sequence: the intent comes from `IdempotencyKeys.begin('tiktok.connect')` (10.2.3-T1) — the key is **kept** while the outcome is unknown (network error, 5xx, timeout) and `settle()`d only on a terminal answer, so a retry replays the same logical attempt and cannot create a second `oauth_states` row (07.1.2-T1:57, plan:164); the interceptor writes the header only when it is absent, so the re-auth/legal retries below carry the same key. `ensureReauthenticated()` is only invoked on a `401 reauth_required` response (the server's re-auth window is ≤ 5 min, `IReauthGuard`, 07 D12) → `ReauthDialog` → **one** retry of the same call (never a loop); `409 legal_acceptance_required` → `LegalAcceptanceDialog` from 13.2.1-T1, then one retry; 404 `feature_disabled` → `hideArea('feature_disabled')` (no error state); 403 `forbidden`/`account_under_review` → mapped copy in `actionError`. On `200 { authorizationUrl }` the allow-list of §8 runs **before** `location.assign`; a rejected URL sets `actionError` (mapped to `tiktok.error.badAuthorizationUrl`) and leaves `connectState = 'idle'`.

**Callback handling.** The page already reads `ActivatedRoute.snapshot.queryParamMap` once for the YouTube codes (10.7.1-T1). The TikTok additive branch maps `connected === 'tiktok'` → `{ kind: 'tiktok-connected' }` + `ChannelRepository.list()` (so the banner can name the freshly connected account) and `error === 'tiktok_scope_missing'` → `{ kind: 'tiktok-error', code: 'tiktok_scope_missing' }`; the other four codes (`oauth_state_invalid`, `oauth_denied`, `oauth_exchange_failed`, `channel_already_connected`) already have copy and are rendered by the same banner. `Location.replaceState('/channels')` still clears the query. The banner is `role="status" aria-live="polite"`, focusable (`tabindex="-1"`) on landing, dismissed with `tiktok.result.dismiss`, after which focus moves to the section heading.

**Connection + creator-info states.** The TikTok rows come from the existing `GET /channels` (no extra call, SC7): `platform === 'tiktok'`. `status === 'active'` → connected card with `nickname`/avatar from `TikTokCreatorInfoDto` (the connection's `displayName` is the creator nickname, 07 D12) and lazy creator-info load; `status === 'expired'` → reconnect card (`role="alert"`) whose copy states that the grant died and re-consent is required (07 D13); any publication with `error_code = 'tiktok_reauth_required'` also lands on the reconnect card (FC18/ST-6: the same affordance for both spellings). `canPost === false` → blocked card rendering `blockReason` **verbatim** (dynamic server text, never an i18n key); `privacyLevelOptions` is displayed as information only (the composer does not offer a choice in R2), and a persistent private-only notice text is owned by 10.7.3-T2's composer.

**Performance.** One `GET /channels` (existing, per page entry and after each action) + exactly one `GET /channels/{id}/tiktok/creator-info` per page per connection, cached in `TikTokStore` and refetched only on an explicit retry (`force`) — no polling, no timer, no realtime subscription (06 raises no channel-change frame, `06.1-connect/plan.md:253`), nothing to dispose beyond the route-scoped store. No `@defer` needed (the card is a few hundred bytes of markup); the `tiktok` chunk stays out of the initial bundle (FC8, asserted by 10.10.1-T2).

**Security.** (a) allow-list before navigation (see §8 of `plan.md`): `https:`, host exactly `www.tiktok.com`, path exactly `/v2/auth/authorize/`, no credentials/port, `redirect_uri` parsed to `${location.origin}/api/v1/channels/tiktok/callback`; (b) the `state`/PKCE URL is never logged, stored or rendered; (c) top-level `location.assign` only (the `__Host-nts_oauth` cookie is the server's, the SPA never reads it); (d) only the closed set of callback codes is rendered, and unknown values are ignored without echoing the string; (e) `404` for a foreign channel id (tenant filter) is treated as "not found", never as an authorization hint (07 D14).

**Accessibility (SD12/WCAG 2.2 AA, A1–A8 of the design).** Banner `role="status"` + focus landing + dismissal focus handover; reconnect card `role="alert"` and not colour-only (text + icon via `StatusChip`); Connect/Reconnect are native buttons with `aria-busy`/`disabled` while in flight and a spinner that becomes static text under `prefers-reduced-motion`; the creator card's retry button has an accessible name including the account; 360 px stacking with ≥ 24 px targets; no focus obscuring when the sticky header is shown.

## Acceptance checks

- **Given** the `tiktok` feature is off for the user, **when** `/channels` mounts, **then** the TikTok section, its nav entry and its requests are absent (no `GET /channels/{id}/tiktok/creator-info`, no empty hole in the layout), and a `404 feature_disabled` from a stale call hides the section with the explanatory banner instead of an error state.
- **Given** the TikTok section on `/channels`, **when** the user activates **Connect TikTok** with a valid session, **then** exactly one `POST /channels/tiktok/connect` is sent with an `Idempotency-Key` (UUID v4) header, the button is `disabled`+`aria-busy`, and on `200 { authorizationUrl }` the browser performs a **top-level** `location.assign` to that URL (asserted by the navigation spy).
- **Given** a connect whose first attempt ends in a `401 reauth_required` (or `409 legal_acceptance_required`), **when** the user completes the dialog, **then** the retry carries the **same** `Idempotency-Key`; **given** a terminal answer, **then** a fresh click mints a **new** key (the previous one is `settle()`d).
- **Given** a `400 validation_failed`/`idempotency_key_required` (missing key) or `422 idempotency_key_reused`, **when** it is handled, **then** the UI shows `errors.unknown_error` with the `traceId` and logs a dev-only client bug — never a silent retry.
- **Given** a connect response whose `authorizationUrl` host is not `www.tiktok.com` (or whose `redirect_uri` is not the same-origin callback), **when** the response is handled, **then** no navigation occurs, `connectState` returns to `idle`, and the user sees the mapped `tiktok.error.badAuthorizationUrl` copy.
- **Given** a connect `401 reauth_required`, **when** the user completes the re-auth dialog, **then** the request is retried exactly **once** and a second `401` surfaces the reconnect card instead of another dialog.
- **Given** a connect `409 legal_acceptance_required`, **when** the legal dialog is accepted, **then** the request is retried once and the connect proceeds; **given** `403 forbidden`, **then** no retry happens and the mapped copy is shown.
- **Given** a TikTok connection whose `status` is `expired` (or a publication whose `error_code` is `tiktok_reauth_required`), **when** the card renders, **then** the reconnect card is shown (not the connected card) with `role="alert"` and text + icon, and `Reconnect` starts the same single-request connect flow.
- **Given** `GET /channels/{id}/tiktok/creator-info` returning `canPost = false` and a non-null `blockReason`, **when** the creator card renders, **then** `blockReason` is displayed verbatim and the card offers the retry action (`force` refetch) while the privacy option set is display-only.
- **Given** the callback `/channels?connected=tiktok`, **when** the page loads, **then** the success banner is announced in the `role="status"` region, `ChannelRepository.list()` is refetched, and the URL becomes `/channels` via `history.replaceState` (back/forward does not re-render the banner); the same holds for each of the five error codes with its own copy.
- **Given** an unknown `error=` value, **when** the page loads, **then** nothing is rendered and the value is never echoed into the DOM or a log.
- **Given** a hot path, **when** the page is re-entered, **then** the creator info is fetched **once per page per connection** and only `force` (explicit retry) refetches it — no polling, no timer, no SignalR subscription exists in this task.
- **Given** the design gate, **when** `plan.md` §6's owner-approval row is still PENDING, **then** this task must not have been started (the dependency is hard, §C8.1 `:750`).

## Failure handling and edge cases

| Situation | Handling |
|---|---|
| `authorizationUrl` fails the allow-list | no navigation; `tiktok.error.badAuthorizationUrl`; dev-only console diagnostic (no token/state logging) |
| `POST …/connect` times out / lost response | no automatic retry beyond the re-auth path; the user may click again (the route is non-idempotent by contract, 07 D12) and the card refetches `GET /channels` on entry |
| `401 reauth_required` twice | first → `ReauthDialog` + one retry; second → reconnect card + `errors.reauthRequired`; never a third attempt |
| `403 account_under_review` / `self_grant_forbidden`-class codes | mapped copy from `errors.*`, no retry |
| `409 channel_already_connected` (second user, same `open_id`) | banner copy `errors.channel_already_connected`, no retry, list refetched |
| `302 …?error=tiktok_scope_missing` (a redirect, never JSON — 07 F25) | banner copy `errors.tiktok.scopeMissing`; the card offers a normal Connect retry after the user grants the scope |
| `status = 'revoked'` or a purged connection (`displayName` null, 06.1.2-T2) | treated as "no connection": the CTA card, no avatar placeholder artefact |
| `creator-info` returns `404` (foreign id) or is deleted mid-session | card shows the not-found state and the list is refetched; no retry storm |
| `creator-info` `canPost = false` with a `blockReason` in one language only | rendered verbatim (server text), never translated locally (SD13) |
| `400 validation_failed` / `idempotency_key_required` / `422 idempotency_key_reused` | a client bug (the key is minted by `IdempotencyKeys`): dev-only console error + `errors.unknown_error` with `traceId`; no automatic retry |
| connect lost response (timeout/5xx) | the intent is kept, so the next click replays the same key and the server returns the same `{ authorizationUrl }` with no second `oauth_states` row (07.1.2-T1 plan:164) |
| flag turned off while the page is open | the next API call returns `404 feature_disabled` → `hideArea()` + the explanatory banner (no crash, no empty card) |
| offline / channel-list failure | the existing `/channels` `ErrorState` + retry (10.7.1-T1) covers the whole page; the TikTok section renders its own `ErrorState` only when the list succeeded |
| `prefers-reduced-motion` | spinner and card transitions render static; no `aria-live` announcement flood |
