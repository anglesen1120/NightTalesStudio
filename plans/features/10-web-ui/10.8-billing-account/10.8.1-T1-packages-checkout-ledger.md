## Goal

Ship the first half of the billing feature: `features/billing/` with the credit-package list, the idempotent checkout dialog (promo code, invoice info, `checkoutUrl` vs `bankQr` branching), the provider return page `/billing/return` that resolves a payment by polling the server, the reservation-grouped credit ledger, the `cost-line` slot filler for `ConfirmDialog`, and the `Billing` nav entry — consuming exactly 12's frozen wire (`README.md` §C1 SC26) and never granting, computing or trusting a credit value in the client (FC3, FC7).

## Design

**Routes (`features/billing/billing.routes.ts`, [DECISION] per SD1).** `/billing` → `redirectTo: 'wallet'`; `packages` → `CreditPackagesPage`; `return` → `BillingReturnPage`; `ledger` → `LedgerPage`. Children of the guarded authenticated shell, lazy-loaded (`loadComponent`), no prerender (D12), no route resolver that would block first paint on money data. `/billing/return` must be reachable **with a payment id and no session-state assumption** but still behind the auth guard (the poll needs the user's token).

**Data access (`features/billing/data/billing.api.ts`).** Injectable functions over `HttpClient` with typed returns; no DTO transformation: `getPackages(): Observable<{ items: CreditPackageDto[] }>`, `getQuote(operation, episodeId)`, `checkout(body, idempotencyKey)`, `getPayment(id)`, `getLedger(cursor, limit)`. `limit=20` [INFERENCE] on the ledger. Every call passes through the existing interceptor (token, error mapping); nothing here formats money beyond the API's integers.

**Checkout dialog (`checkout-dialog.ts`).** Steps: package summary → promo code (`POST /billing/promo/redeem`, own idempotency key, success shows `creditsGranted` + the returned `balance`) → optional invoice info (`companyName`, `taxCode`, `address`) → submit. Submit calls `withIdempotency(IdempotencyKeys, intent, () => api.checkout(...))` so a double click produces one payment and one `Idempotency-Key`; the intent is settled only on a terminal outcome. On success the branch is decided by the response, never by a guessed field: `checkoutUrl != null` → write `{ paymentId, expiresAt }` to `core/prefs/checkout-handoff.ts` (`nts.checkout.v1`, `sessionStorage`) **then** `window.location.assign(checkoutUrl)` (top-level navigation, WD5 rule); else `bankQr != null` → hand the payload to `BankQrCard` (10.8.4-T1) with no navigation. 409 `payment_invalid_state` re-reads `GET /billing/payments/{id}` if an id is known and otherwise closes the dialog with the mapped copy.

**Return page (`billing-return.page.ts`).** On init: `paymentId` = query param, else the `core/prefs` hand-off value; every other parameter (including `orderCode` and anything the provider appends) is ignored and never rendered as a status. Then `visible-poll` on `GET /billing/payments/{id}` with backoff 2/4/8/15 s, `RetryCountdown` visible, running until `paid` | `failed` | `needs_review` | `pending_approval` or `expiresAt` (F6, ST-8). Rendered states: confirming, paid (success panel + one `BalanceStore.refresh()`, `cost-line`-consistent amounts from the DTO), `pending_approval`/`needs_review` (10.8.4-T1's paused panels), failed/expired (failure panel + a fresh-checkout link), unknown/missing id (neutral panel + a link to `/billing/payments`). Terminal states clear the hand-off key. **The page never shows success before the server says `paid`, never adds credits, and never trusts the URL** (FC3).

**Ledger (`ledger.page.ts`, `ledger-fold.ts`).** `cursor-list` over `GET /credits/ledger`; `foldLedger(items)` produces one row per `groupId` (rows without a `groupId` stay their own row), the fold keeps the reservation's `quoted`/`charged`/`released` and `operation`, sorts by `createdAt` desc and never sums anything. Row detail (`@defer`, on expand) shows `kind`, `amount`, `title`, `episodeId` (deep link) and `usage` (`inputTokens`, `cachedInputTokens`, `outputTokens`, `imageCount`, `gpuSeconds`, `estimated`). Empty/filtered-empty/error+retry states from D11; the balance shown on top comes from `BalanceStore`, never from the rows.

**`cost-line` slot (`cost-line.ts`).** A component that projects into `ConfirmDialog`'s `cost-line` slot; it renders `QuoteDto` as "up to N, usually about M" when `typicalCredits != null` and "up to N" otherwise, plus the server's `balanceAfter`; a quote failure renders nothing (silent, no error in a confirm dialog) — D14.

**Nav + i18n.** Append `Billing` to the shell `NAV_ITEMS` (path `/billing`, label key `nav.billing`, icon from D11) — WT-W6 precedent. New Transloco scope `billing` with keys for every state (proposed: `billing.packages.*`, `billing.checkout.*`, `billing.ledger.*`, `billing.return.*`) and the `errors.*` keys of FC10 that reach these screens (`promo_invalid`, `promo_expired`, `promo_exhausted`, `promo_already_used`, `payment_invalid_state`, `payment_expired`, `package_not_found`, `package_below_cost`, `rate_limited`, `unknown_error` with `traceId`) in **vi and en**.

**Non-goals here.** The bank-QR card itself and the paused-processing panels (`10.8.4-T1`); wallet/history/receipt/refund and the `header-end` chip (`10.8.3-T1`); admin billing (10.9.2-T1); the public pricing page (10.3.1-T2).

## Acceptance checks

- **Given** `/billing/packages` with `billing_enabled` on, **when** it loads, **then** cards render from `GET /billing/packages` in `sortOrder` with `credits`, `bonusCredits`, `priceVnd` (and `priceUsd` when non-null), and no total is computed client-side.
- **Given** the checkout dialog, **when** the submit button is double-clicked, **then** exactly one `POST /billing/checkout` is issued with one `Idempotency-Key`, and one payment exists (verified against the API's payment list).
- **Given** a response with `checkoutUrl`, **when** the submit resolves, **then** the `paymentId`/`expiresAt` hand-off is written **before** `window.location.assign(checkoutUrl)` is called; **given** a response with `bankQr` instead, **when** it resolves, **then** no navigation happens.
- **Given** `/billing/return?paymentId=…&status=paid` (a forged status param), **when** the page initialises, **then** the rendered state follows `GET /billing/payments/{id}` only, the forged parameter is ignored, and success appears only for a server `paid`.
- **Given** a payment that reaches `pending_approval`/`needs_review`/`expired`, **when** the poll resolves, **then** the matching panel renders with no balance change, and the hand-off key is cleared on the terminal state.
- **Given** a ledger where several entries share a `groupId`, **when** the ledger renders, **then** exactly one row per reservation shows `quoted`/`charged`/`released` and `operation`; entries with no `groupId` render separately; nothing is summed.
- **Given** `billing_enabled` off, **when** `/billing/packages` loads, **then** the buy/checkout affordance is hidden with the closed-beta explanation while the ledger, balance and packages list still render.
- **Given** any of these screens, **when** axe runs with `wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa`, **then** there are zero violations and zero `securitypolicyviolation` events.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Double submit / retry after a network error | Same `Idempotency-Key` per intent → one payment; a 409 `payment_invalid_state` re-reads the payment instead of showing an error |
| `checkoutUrl` is `null` **and** `bankQr` is `null` | Render an "unavailable, try another method" panel; no navigation, no grant; log nothing but the error code |
| Return page opened with no `paymentId` anywhere | Neutral panel + link to `/billing/payments`; no poll, no error toast |
| Poll returns 404 / 403 | Stop the poll, render the mapped copy (`unknown_error` shows `traceId`); never retry blindly |
| `expiresAt` passes while polling | Stop, render the expired panel, clear the hand-off key, offer a fresh checkout |
| `billing_enabled` turns off mid-session | The next `POST /billing/checkout` answers `feature_disabled`/fails → hide the buy UI and refresh `GET /me` (README D14 flag semantics) |
| Ledger page reaches `nextCursor == null` | Stop paging; keep the last page loaded; no "load more" affordance |
| 429 `rate_limited` on checkout/promo | Mapped copy + retry enabled after the server hint; the intent key is not regenerated for the same intent |
| Slow quote | `cost-line` shows the loading placeholder; a timeout renders nothing (silent) and the confirm dialog stays usable |

## Notes

Two money invariants are non-negotiable and are asserted by tests, not by review: **no client-side credit arithmetic** and **`paymentId` is the only trusted return parameter** (FC3, FC7, ST-8). `IdempotencyKeys` intent strings used here (`billing.checkout`, `billing.promo.redeem`) are [INFERENCE] — the helper's exact intent catalogue belongs to 10.2.3-T1 and is adopted as-is, not re-created. `GET /billing/quote` is called only where a pre-action cost is shown (the `cost-line` slot and 10.8.3-T1's context), never speculatively, and never for `story_review`/`story_revision` (400). The `cost-line` slot's presence in `ConfirmDialog` and the `header-end` slot in the shell are D14's; this task fills only `cost-line`, 10.8.3-T1 fills the chip. Consumed server contracts are 12's and are not modified here; if 12's `CheckoutSessionDto` changes shape, this task's model files change with it (no adapter layer by design).
