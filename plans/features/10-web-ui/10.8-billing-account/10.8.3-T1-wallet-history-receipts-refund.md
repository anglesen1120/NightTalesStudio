## Goal

Ship the wallet and payment surfaces: `/billing/wallet` with the balance card rendered verbatim from `GET /credits/balance` and the low-balance banner, `/billing/payments` (cursor history) and `/billing/payments/:id` (detail, receipt in a new tab + `window.print()`, refund request), plus the shell `header-end` balance chip fed by `BalanceStore` and refreshed on `CreditBalanceChanged`. No credit value is ever computed in the client, and the flag `billing_enabled` must not gate any read or the refund request (FC7, F7).

## Design

**`/billing/wallet` (`wallet.page.ts`).** `BalanceCard` renders the DTO field-for-field: `total`, `free`, `purchased`, and `nextExpiry` (`{ amount, expiresAt }` — hidden when `null`, otherwise label + formatted `expiresAt`). **No** `free + purchased == total` assertion, no rounding, no per-credit price math (FC7). `LowBalanceBanner` renders when `BalanceStore.total < maxCredits` from `GET /billing/quote?operation=render` (12.6.3-T1's frozen contract: the banner is computed on read from `GET /credits/balance` + the quote — **no server flag exists and no DTO field may be added**, 10 CR-41); the quote is fetched once per wallet render and cached in the store with the balance, with a CTA to `/billing/packages`; it is dismissible for the session only (in-memory signal — nothing extra in `core/prefs`, D6). Links to `/billing/payments` and `/billing/ledger`.

**`header-end` chip (`slots/balance-chip.ts`).** Reads `BalanceStore`; states: hidden (no value yet), loading (skeleton, no layout shift), value (`total` + a `StatusChip`-style free/purchased hint), stale/silent-error (last known value, no shell error toast — FC15). Clicking navigates to `/billing/wallet`. Subscribes to `CreditBalanceChanged { userId }` through the existing hub service (10.2.4-T1): the handler calls `BalanceStore.refresh()` only — no arithmetic, no toast, ids-only (SD16). Subscription is disposed via `DestroyRef`.

**`/billing/payments` (`payments.page.ts`).** `cursor-list` over `GET /billing/payments` (`limit=20` [INFERENCE]): each row shows `createdAt`, `packageCode`, `amount` + `currency`, `method`, `credits` + `bonusCredits`, and `status` via `StatusChip` (label from the catalogue incl. `pending_approval`; an unknown status renders as-is rather than hiding the row). Row → `/billing/payments/:id`. States: loading, empty, filtered-empty, error + retry (D11).

**`/billing/payments/:id` (`payment-detail.page.ts`).** Renders `PaymentDetailDto`: the `PaymentDto` fields plus `orderCode` (copyable), `providerPaymentId` (when non-null), `invoiceInfo`, `refundRequest` (`{ id, credits, amount, status }` when present), `refundEligible`, `refundableCredits`. Receipt: when `receiptAvailable`, `ReceiptButton` opens `GET /billing/payments/{id}/receipt` in a **new tab** (`target="_blank" rel="noopener"`) — the API's `text/html` is print-styled server-side and printed by the user with the page's own print (no PDF library, never fetched into the DOM through `[innerHTML]`, SD15/FC14). Refund: when `refundEligible`, `RefundRequestDialog` (reason via `CharCounter`) submits `POST /billing/payments/{id}/refund-request` once per intent (`Idempotency-Key`); success re-reads the detail and shows the pending `refundRequest`; 409 `refund_not_eligible` / 403 `account_under_review` map to copy; a `refundRequest` already present disables the button and shows its status. 404 renders the not-found state.

**`resync()`.** After a promo redemption, a refund request or a payment reaching `paid`, the page calls `BalanceStore.refresh()` and re-reads the current list/detail — never a local mutation of the totals.

**Flag scope.** With `billing_enabled` off, wallet, history, detail, receipt and refund-request keep working; only the buy CTA on the banner/cards is hidden (F7, 12 CR-3).

**i18n.** `billing.wallet.*`, `billing.payments.*`, `billing.refund.*`, `billing.receipt.*`, `billing.balance.*`, `nav.billing` already added by 10.8.1-T1; new `errors.*` keys: `refund_not_eligible`, `account_under_review`, `rate_limited` (reused), `unknown_error`; vi + en.

## Steps

4. Build `PaymentDetailPage`: field rendering, `ReceiptButton`, `RefundRequestDialog` with `IdempotencyKeys`, terminal/refund-pending states.

## Acceptance checks

- **Given** `GET /credits/balance` → `{ total, free, purchased, nextExpiry: { amount, expiresAt } }`, **when** `/billing/wallet` renders, **then** the three numbers and the expiry are shown exactly as received (asserted against the fixture, not a sum) and no arithmetic appears in the template or the component.
- **Given** `nextExpiry` is `null`, **when** the card renders, **then** the expiry row is absent (not "0" or "—").
- **Given** the server signals low balance, **when** the wallet renders, **then** the banner appears with the buy CTA; with `billing_enabled` off, the banner shows the closed-beta copy and no CTA.
- **Given** a `CreditBalanceChanged` event, **when** the hub delivers it, **then** exactly one `GET /credits/balance` follows, the chip updates, and no toast or total is computed.
- **Given** `receiptAvailable = true`, **when** the user activates "Receipt", **then** `ReceiptButton` fetches `/billing/payments/{id}/receipt` with the bearer header, opens the returned `text/html` as `window.open(URL.createObjectURL(blob))` with `noopener` (a bare `target=_blank` navigation cannot carry `Authorization`, 10 CR-42), and the receipt HTML is **not** inserted into the page DOM.
- **Given** `refundEligible = true`, **when** the user submits the refund dialog twice quickly, **then** exactly one `POST /billing/payments/{id}/refund-request` is issued; **given** 409 `refund_not_eligible`, the mapped copy shows and the detail re-reads.
- **Given** `status = pending_approval` on a row, **when** the list/detail renders, **then** the status label is shown from the catalogue, no success affordance appears, and the balance is untouched.
- **Given** axe (`wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa`) on wallet/payments/detail, **then** zero violations; money is never colour-only; every row action has an accessible name.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `GET /credits/balance` fails | Chip keeps the last known value with a stale marker (silent); wallet shows the D11 error state with retry; no toast (FC15) |
| `CreditBalanceChanged` arrives while the tab is hidden | Refresh on the next `visible` transition (the hub service's `ActivityTracker` gate) — one refetch, not a queue |
| Receipt request fails (403/404/500) | Show the mapped copy inline next to the button; `unknown_error` shows `traceId`; nothing is inserted into the DOM |
| Refund request when the balance already changed | Server is authoritative; the detail re-reads and the `refundRequest` object drives the button state |
| `refundEligible = false` but a `refundRequest` exists | Show the request status read-only; no button |
| Payment with `priceUsd = null` / non-VND currency | Render `amount` + `currency` as given; never convert |
| Very long `orderCode`/`providerPaymentId` | `CopyableCode` with truncation + copy action; never break the layout |
| `billing_enabled` flips off mid-session | Read screens continue; the buy CTA hides after the next `/me` refresh (D14 flag semantics) |

## Notes

The receipt is server HTML precisely so the client needs no PDF library and no third-party print service (SD15, FC14, 12 CR-2); the print path therefore is "fetch the API's `text/html` with the bearer token, open it as a blob URL in a new tab, user prints" (10 CR-42). The low-balance source is 12.6.3-T1's contract: `total < GET /billing/quote?operation=render`.maxCredits — the comparison is the contract, not an invented threshold (10 CR-41). The `header-end` chip is the only writer of that slot in this folder, and it never blocks the shell — a missing balance renders nothing. `resync()` is deliberately explicit (promo, refund, paid) instead of a global cache invalidation, so a stale total cannot be shown as fresh (FC7). ### Angular implementation amendment (2026-10-02)

- Frame evidence is screen 07's wallet/payments/detail/refund family via `plan.md` §12; distinct refund submitting/immediate-success and receipt/download failure/disabled states remain T0 evidence.
- Wallet/payment pages are containers over route stores and the readonly immutable `BalanceStore`; cards/rows/dialog bodies are UI-only. Billing data access maps nullable receipt/refund/expiry fields, `Content-Disposition`, response blobs and `Retry-After`; refund uses an explicit typed reason command and the existing idempotency owner.
- Payment/session/request generations reject stale balance, list, detail, receipt and refund completions. Revoke blob URLs/new tabs and shell-slot registrations on destroy; never retain receipt/export URLs or billing traces/videos. No client arithmetic or browser grant: after a refund/payment mutation, only server refetch updates balances, and provider-paid state comes from Plan-12 verification/webhook processing.
