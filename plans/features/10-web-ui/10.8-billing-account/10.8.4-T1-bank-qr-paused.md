# 10.8.4-T1 — Bank-QR checkout card and the paused-processing states (pending approval, needs review, expired)

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 10.8.4 | S (0.5) | FE + Payments | 10.8.1-T0, 10.8.1-T1, 12.7.4-T1, 12.8.3-T1 (soft) | 10.10.1-T1 | S · M2 |

## Goal

Complete the checkout paths that do not redirect and the outcomes that do not finish instantly: render the server's `bankQr` payload verbatim as a scannable QR card with a text alternative (no navigation, no third-party script), and render the `pending_approval` / `needs_review` / `expired` states of a payment on `/billing/return` and in the payment detail — all without ever adding credits to the balance, offering a retry where a human decision is pending, or trusting a URL parameter.

## Design

**`bank-qr-card.ts` (new, lazy).** Inputs: the `bankQr` payload (required) and `expiresAt`. The component never calls the network and never parses the payload: `qrPayload` is passed to the QR encoder exactly as received. Rendering: `qrcode` (self-hosted MIT library, SD15) loaded behind `@defer` with `import('qrcode')` inside the component so the initial and billing chunks stay small (FC8); the encoder draws into a `<canvas>` (or an inline SVG) sized ≥ 240 px at 360 px viewport so nothing is clipped and no zoom is needed. **No CDN, no vendor script, no remote image.**

Text alternative (mandatory, and the primary a11y path): `bankName`, `accountNumber`, `accountName`, `amount` (+currency) and `orderCode` are rendered as text, with `accountNumber`/`orderCode` as `CopyableCode`; the canvas carries `role="img"` + `aria-label` naming the transfer (bank + order code), and the card states the amount that must match. `orderCode` is informational on the return page but is the transfer reference here, so it is displayed and copyable.

Behaviour: **no redirection** and no polling on this card itself — the payment stays `pending` until the provider notifies the server; the card links to `/billing/payments/:id` ("I've transferred — check status") which is where the state is watched, and it shows the `expiresAt` with a `RetryCountdown` when the server's window is close. `billing_enabled` off hides the card entry point together with the rest of the buy UI (12 CR-3) — a card already rendered stays readable.

**Paused-state panels (`payment-state-panel.ts`, shared by `/billing/return` and the detail page).** One component, four server-driven states, no client inference:
- `pending_approval` — "Payment received, waiting for approval" + `amount`/`credits` from the DTO + `expiresAt`; **no** retry button, **no** balance change, **no** success styling; explains that an operator decides (12:224-236, SC17).
- `needs_review` — "We're checking this payment" with the mismatch/QR explanation (amount/currency mismatch or unmatched transfer, SC17), a support link, and no retry that could double-charge; the detail page still shows `providerEvents` timing only if the DTO exposes it (it does not for the user DTO — so no invented timeline).
- `expired` — the checkout window closed (`payment_expired` semantics, ST-8): offer a fresh checkout link to `/billing/packages` and, on `/billing/return`, clear the `core/prefs` hand-off key.
- `failed` — generic failure copy + fresh-checkout link; `unknown_error` shows the `traceId`.

The panels never mutate `BalanceStore`, never call `POST` anything, and never re-poll: the sibling page owns the poll lifecycle.

**`/billing/return` integration.** `10.8.1-T1` owns the poll; this task supplies the panel component and the panel selection for the four paused/failed states, keeping the poll stop conditions (`paid`/`failed`/`needs_review`/`pending_approval`/`expiresAt`) unchanged. The detail page uses the same panel for a payment whose current status is paused (so a user arriving from the payments list sees the same explanation).

**i18n.** `billing.qr.*` (title, scan instructions, account fields, "I've transferred", expiry), `billing.paused.pendingApproval.*`, `billing.paused.needsReview.*`, `billing.paused.expired.*`, `billing.paused.failed.*`; vi + en, `errors.payment_expired` reused.

## Acceptance checks

- **Given** a checkout response with `bankQr != null`, **when** the dialog resolves, **then** the QR card renders with `qrPayload` passed verbatim to the encoder, the bank/account/amount/order-code text is present and copyable, and **no** navigation occurred.
- **Given** the QR card at a 360 px viewport, **when** it renders, **then** the code is at least 240 px and fully visible without horizontal scrolling, and the encoded value equals the server payload byte-for-byte (test compares the encoder input).
- **Given** the card is mounted, **when** the CSP/Trusted-Types spec runs, **then** there is no `securitypolicyviolation` and no `bypassSecurityTrust*` usage; the QR library is loaded only on this route's chunk (`@defer`), not in the initial bundle.
- **Given** a payment whose status becomes `pending_approval`, **when** the return page (or the detail page) renders it, **then** the pending-approval panel shows the amount/credits and the expiry, offers no retry, and `GET /credits/balance` is **not** re-requested and no credit is displayed as added.
- **Given** `needs_review`, **then** the review panel renders with the support path and no actionable retry; **given** `expired`, **then** the expired panel renders, the `core/prefs` hand-off key is cleared and a fresh-checkout link is offered.
- **Given** `billing_enabled` off, **when** `/billing/packages` loads, **then** no QR entry point is offered; **given** an already-created `bankQr` session, **then** the card and its panel still render.
- **Given** axe (`wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa`) on the QR card and the four panels, **then** zero violations, and the QR's accessible name describes the transfer (no colour-only or image-only information).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `qrPayload` is empty/invalid in the response | Render the text alternative only + an "unavailable, use another method" note; never render a broken canvas or call a fallback remote QR service |
| `amount` in `bankQr` differs from the payment amount | Render the server's `bankQr.amount` (verbatim) and keep the mismatch visible; the reconciliation belongs to the server (`needs_review`) |
| User transfers after `expiresAt` | Server decides; the card shows the window and the panel switches to `expired` on the next status read — no client countdown that changes state |
| `pending_approval` then `paid` (operator approves) | The next status read (navigation or the page's poll/refresh) shows `paid`; the balance is refreshed by the page that owns the read, not by the panel |
| QR library fails to load (offline/blocked chunk) | `@defer` placeholder → error state with the text alternative still usable (the transfer can be made from the account number alone) |
| Reduced motion / dark theme | No animation required; the card and the panels use D11 tokens and pass contrast in both themes |
| Long account numbers / bank names | Wrap or `CopyableCode`; never truncate the order code, which is the transfer reference |

## Notes

No mutating request exists in this task: the QR card and the four panels only render server data, and the checkout `POST` with its `Idempotency-Key` belongs to `10.8.1-T1` (FC7 satisfied there) — so there is deliberately no double-submit test here. The base state set for every screen/tab this task adds is loading, empty, error + retry, success, on top of the paused/failed panels above (SD1). SC18 is explicit that **no payment provider is named** in the plans and that bank-transfer QR "if the chosen provider supports bank-transfer QR with payment notifications ⚠️" is provider-dependent — so this task renders whatever the server puts in `bankQr` and never encodes provider-specific semantics, deep links or amounts of its own. `12.7.4-T1` is the API owner; `12.8.3-T1`'s funding-pause path is why this task's acceptance is verified against a stub first (soft) and against the real endpoint when it lands. The paused states are deliberately **dead ends** (no retry, no re-post) because the decision is an operator's and a client retry could double-charge (FC3, ST-8). The QR library is self-hosted MIT and `@defer`-loaded per SD15/FC8; the receipt/print path is untouched here (10.8.3-T1).
