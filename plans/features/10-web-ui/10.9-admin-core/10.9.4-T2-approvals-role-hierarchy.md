## Design

**Role hierarchy (`features/admin/application/role-hierarchy.ts`) — one implementation, consumed everywhere.**

```ts
export type AdminRole = 'user' | 'admin' | 'owner';
export const rank: Record<AdminRole, number> = { user: 0, admin: 1, owner: 2 };

/** Strictly higher rank, or the owner-on-owner exception set (mfa_reset, demote, suspend; never delete). */
export function canActOn(actor: AdminRole, target: AdminRole, action: UserAction): boolean;
/** True when the action must go through the 202 pending flow (owner-on-owner, promote, owner self-demote). */
export function isPendingAction(actor: AdminRole, target: AdminRole, action: UserAction): boolean;
```

Rules encoded: `admin` sees actions only for rank-`user` targets; an `owner` sees `user`/`admin` targets freely and `owner` targets only through `mfa_reset`/`demote`/`suspend` (202 flows); **delete is never offered on an owner target**; the grant action is never offered on the actor's own row; every other 403/404 the server may return (`self_grant_forbidden`, `grant_target_forbidden`, 404 `not_found`) is rendered as copy, not as a hidden state change. `10.9.4-T1`'s `user-actions.ts` consumes these pure functions for both visibility and the dialog variant, so the button rules and the response handling cannot drift.

The registry (same pattern as `ADMIN_NAV_ITEMS`, WT-W6) keeps the page's file owned here while `10.9.3-T2` appends its `setting_change` section without editing it — no shared-file conflict, and the section list order is design-owned.

**Owner actions (`owner-actions.store.ts` + `owner-actions.section.ts`).** `GET /admin/owner-actions?status=pending` (cursor-paged; row membership `[INFERENCE]` — see Notes) with a Disputed badge for `owner_action_disputed` rows and the apply time shown when the payload carries it; actions: Approve → `POST /admin/owner-actions/{id}/approve` (with an optional reason), Cancel → `ConfirmDialog` → `POST /admin/owner-actions/{id}/cancel`; outcomes 200/202/204 → refetch + remove the applied row; 202 `objection_recorded` → informational banner; 409 `owner_action_disputed` / `cancel_limit_reached` / `owner_dispute_frozen` → `ConflictDialog` with the matching copy and a refetch; 401 `reauth_required` → `StepUp` (retry once). The list never claims an action applied by time-lock; `OwnerActionApplyJob` is the only applier.

**Credit-grant queue (`grant-requests.store.ts` + `grant-requests.section.ts`).** `GET /admin/credit-grant-requests?status=pending` → rows of `CreditGrantRequestDto` (`targetUser`, `amount`, `reason`, `source`, `promoCodeId?`, `requestedBy`, `status`, `activatesAt | null`, `requestedAt`); Approve/Reject open a dialog with a **required** decision note → `POST /admin/credit-grant-requests/{id}/approve|reject { note }`; **the Approve button is disabled when `requestedBy` equals the signed-in owner and another owner exists** (the contract's "different person where two owners exist" rule; the actor's id comes from `GET /me` via the session store), with an explanatory helper text and a server-side 403 as the backstop; 409 `grant_request_not_pending` → `ConflictDialog` + refetch (the request was decided or expired by `CreditsMintedDigestJob` at 7 days).

**Payment approvals (`payment-approvals.store.ts` + `payment-approvals.section.ts`).** `pending_approval` rows are the same `AdminPaymentDto` shape used by 10.9.2-T1's `needs_review` queue — this task renders only the owner approval variant: Approve/Reject with a required note → `POST /admin/payments/{id}/resolve/approve|reject { note }` → 200 refreshed `AdminPaymentDto`; codes 409 `grant_request_not_pending` / `payment_already_resolved` / `grant_in_progress`, 403 `forbidden` when the actor is `resolveRequestedBy` (the button is disabled for that case, mirroring the grant queue), 401 `reauth_required` → step-up within the 5-minute window. Reject moves the payment back to `needs_review` — the row leaves this section and the copy says so (12.3.5-T2 step 9).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Approve clicked twice | Submit disabled in flight; the server's 409/idempotent replay (`payment_already_resolved`, `grant_request_not_pending`) prevents a second effect, and the conflict dialog refetches |
| Actor id unavailable (session store cold) | The self-approval rule fails **closed**: Approve stays disabled and a hint says to reload; the server's 403 is the backstop |
| Two owners, one request, race | First decision wins; the second sees 409 and the refetched row shows the decision |
| Request expired by `CreditsMintedDigestJob` (7 days) | Row disappears on the next load; if the action races, 409 `grant_request_not_pending` copy explains it |
| `pending_approval` payment rejected | The row leaves this section and the copy explains the payment is back in `needs_review`; no credit is granted |
| Owner action applied by the 24 h time-lock while the page is open | `OwnerActionApplyJob` applies it server-side; the list refetches on the next navigation and never shows a stale "pending" claim as success |
| Cancel limit reached (`cancel_limit_reached`) / dispute frozen (`owner_dispute_frozen`) | Conflict dialog with the exact code copy; no retry button that would loop |
| `setting_change` section absent | The slot renders nothing (registry-driven); `10.9.3-T2` appends it without touching this page's file |
| Long `reason`/`note` from a requester | Rendered truncated with full text on demand; the decision note field is capped at the server's limit with a counter |
| 5-minute re-auth window exceeded between step-up and submit | The second 401 is surfaced as an error with the re-auth prompt; the request is not silently dropped |
