# 10.9.5-T1 — MFA disable for users, admin/owner redirect to enrolment before `/admin`

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 10.9.5 | XS (0.25) | FE + Security | 10.9.1-T0, 10.3.3-T3, 09.10.4-T1 | 10.10.1-T2 | S · M2 |

## Goal

Ship the two S-slice pieces of MFA management the high-level plan reserves for this task after 10 CR-4 moved enrolment/login-step/re-auth into `10.3.3-T3` (P): (1) a **Disable** action on `/account/security` for `user`-role accounts, and (2) the client-side redirect that sends an `admin`/`owner` account without MFA enrolled to the enrolment screen before it can reach any `/admin/**` route. No new screen is created — both pieces extend surfaces `10.3.3-T3` and `10.9.1-T1` already ship.

## Design

Files:

- `web/src/app/features/account/security/sessions.page.ts` (the `/account/security` page, owned by `10.8.5-T1` — a full-session route inside the shell) — this task adds a `Disable` button, visible only when `role === 'user'` (BD4: `admin`/`owner` never see it — the button is hidden client-side and the 403 `forbidden` is still the server's last word), calling `DELETE /me/mfa` through the existing `ReauthDialog` step-up (`RequireRecentAsync`).
- `web/src/app/features/admin/admin.routes.ts` and its existing `adminGuard` (owned by `10.9.1-T1`) — coordinate the existing role/MFA decision, not a second guard after a guard that already rejects missing MFA. Role rejection remains first; a full-session admin/owner with `!mfaEnabled` returns `router.createUrlTree(['/account/security/mfa-setup'], { queryParams: { enrol: 'admin' } })` from that existing MFA branch, using the settled session snapshot without a new fetch. The target's session-owned `mfaEnrolmentGuard` accepts full or enrolment-only mode. Limited enrolment is handled earlier by `authGuard`/`authChildGuard`, outside the shell and without `/me`; its banner cannot depend on a cached profile. No additional account-to-admin guard import or duplicate route registration is introduced.
- `mfa-setup-page.ts` (10.3.3-T3's enrolment page) reads `enrol=admin` from the query params to show a one-line banner ("MFA is required for admin/owner accounts") above the existing enrolment flow; no new component. The banner is static copy keyed off the param — an enrolment-only session issues zero `/me` requests (WR8), so nothing on this surface may depend on a cached `/me`.
- i18n: `account.security.mfa_disable`, `account.security.mfa_disable_confirm`, `account.security.admin_mfa_required_banner` (vi + en).

**Pinned design hand-off.** Candidate enrolment frames are in commit-pinned [`01-shell-auth.html`](https://github.com/anglesen1120/NightTalesStudio/blob/920b507d0fcbff2195de0e492235425f39ac0c37/design/ui/screens/01-shell-auth.html): `f-enrol-banner`, `f-enrol-show`, `f-enrol-verify-error`, `f-enrol-reauth`, `f-enrol-codes`, `f-enrol-gate`, `f-enrol-done`, `f-enrol-error`. Candidate account-security frames in [`07-tiktok-billing-account.html`](https://github.com/anglesen1120/NightTalesStudio/blob/920b507d0fcbff2195de0e492235425f39ac0c37/design/ui/screens/07-tiktok-billing-account.html) are `f-security-success`, `f-security-loading`, `f-security-empty`, `f-security-error`, but cover sessions only. No frame shows Disable/confirm/submitting/success/403 or the task's admin-required banner. The redirect target is the canonical enrolment route `/account/security/mfa-setup` (with `enrol=admin` carrying the banner) — matching 10.3.3-T3's enrolment captions; `/account/security` remains the sessions page and is kept only for the Disable action. Owner approval is still needed for the missing Disable/confirm/submitting/success/403 and banner states.

**Composition and lifetime.** `SecurityPage` (10.8.5-T1's `/account/security` container) remains the container for the existing account-security store; an MFA presentational block receives `{ role, mfaEnabled, pending }` and emits `disableRequested` without knowing the endpoint or policy. The existing `adminGuard` consumes the settled full-session snapshot and returns a typed navigation result; it owns no extra fetch or mutable role cache. The disable command maps explicitly to bodyless `DELETE /api/v1/me/mfa`; dialog close/destroy/session-generation changes clear pending state and ignore late results.

**Availability and authority.** MFA management is present at `00e7d5d…` (`integration-readiness.md` §1), but the final generated client and `GET /me` role/MFA fields must be pinned to the merged backend SHA. Client hiding and guard routing are UX only: the API's admin/owner 403 and `/admin/*` MFA 404 remain authoritative and require negative tests. Reauth replay is identical and once-only.

## Steps

1. Coordinate the existing `adminGuard` role/MFA branch with `10.9.1-T1`: reject a non-admin role first, then return the canonical setup route for an unenrolled full-session admin/owner.
2. Preserve the existing route guard registration and the session-owned setup guard; limited enrolment follows `authGuard`/`authChildGuard` without bootstrapping `/me` or the shell. Do not add a second guard behind an already-failing MFA check.
3. Add the `admin_mfa_required_banner` query-param banner to `mfa-setup-page.ts` (10.3.3-T3's file, coordinated the same way).
4. Add the `Disable` button to `sessions.page.ts` (10.8.5-T1's `/account/security` page, coordinated the same way), gated on `role === 'user'`, behind `ReauthDialog`'s step-up, calling `DELETE /me/mfa`; on 204 refetch `/me`, on 401 `reauth_required` retry once (existing `ReauthDialog` contract, SC29).
5. Map 403 `forbidden` (unreachable client-side once the button is hidden, kept as a defensive `AppError` toast) and 401 `reauth_required`.
6. Write the unit/component specs and the guard-redirect e2e assertion.

## Acceptance checks

- **Given** a `user`-role account with MFA enabled, **When** `/account/security` renders, **Then** the `Disable` button is visible; **given** an `admin`/`owner` account, **Then** the button is absent (BD4).
- **Given** a `user` clicks `Disable` and completes step-up, **When** `DELETE /me/mfa` returns 204, **Then** the page refetches `/me` and shows the enrolment CTA again (MFA now off).
- **Given** an `admin`/`owner` account without MFA enrolled, **When** it navigates to any `/admin/**` route, **Then** it is redirected to `/account/security/mfa-setup?enrol=admin` and the banner renders; **given** the same account after enrolling, **Then** the same route now matches (`adminGuard` unaffected).
- **Given** a `user`-role full-session account (never admin/owner), **When** it attempts `/admin/**` directly, **Then** the existing `adminGuard` role redirect fires before its MFA branch; no enrolment redirect is selected for that account.
- **Given** a 401 `reauth_required` on `DELETE /me/mfa`, **When** the dialog succeeds, **Then** the delete retries once automatically (existing `ReauthDialog` contract).

## Tests

- Unit (Vitest): existing `adminGuard` role/MFA branch — admin+enrolled, admin+unenrolled, owner+unenrolled and user role against a settled full-session snapshot; limited-enrolment auth/setup guards make zero `/me` requests and never load the full shell.
- Component (Vitest): `sessions.page.ts` — `Disable` button visibility by role, confirm dialog, success/failure toasts; `mfa-setup-page.ts` — `enrol=admin` banner presence.
- e2e (Playwright, extends `10.3.3-T3`'s `auth-mfa.spec.ts`): an owner account without MFA hitting `/admin` is redirected to `/account/security/mfa-setup?enrol=admin`; after enrolling, the same navigation reaches `/admin`.
- Axe spec: the banner and button pass `wcag22aa` (reused fixture, no new page).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| `DELETE /me/mfa` returns 403 `forbidden` (admin/owner reached it despite the hidden button, e.g. stale role cache) | `AppError` toast, no retry; refetch `/me` to correct the cached role |
| `DELETE /me/mfa` returns 401 `reauth_required` | `ReauthDialog` step-up, retry once (existing contract) |
| Full-session guard runs before `/me` has resolved (cold boot, deep link into `/admin/**`) | The existing `adminGuard` awaits its existing full-session resolver and uses the settled snapshot, never stale/empty profile state. In limited-enrolment mode the auth/setup guard path runs instead, with no `/me` resolver or full shell |
| An `admin`/`owner` already on `/account/security/mfa-setup?enrol=admin` navigates back to `/admin/**` without enrolling | Guard re-evaluates on every `canMatch`, redirects again (no bypass via browser back) |
| Disable while a re-auth dialog from another action is open | The existing single-flight `ReauthDialog` service serialises step-ups (10.3.3-T3 contract); no second dialog |
