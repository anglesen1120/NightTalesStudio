# 10.9.5-T1 — MFA disable for users, admin/owner redirect to enrolment before `/admin`

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 10.9.5 | XS (0.25) | FE + Security | 10.9.1-T0, 10.3.3-T3, 09.10.4-T1 | 10.10.1-T2 | S · M2 |

## Goal

Ship the two S-slice pieces of MFA management the high-level plan reserves for this task after 10 CR-4 moved enrolment/login-step/re-auth into `10.3.3-T3` (P): (1) a **Disable** action on `/account/security` for `user`-role accounts, and (2) the client-side redirect that sends an `admin`/`owner` account without MFA enrolled to the enrolment screen before it can reach any `/admin/**` route. No new screen is created — both pieces extend surfaces `10.3.3-T3` and `10.9.1-T1` already ship.

## Design

Files:

- `web/src/app/features/account/feature/security-page.ts` (owned by `10.3.3-T3`) — this task adds a `Disable` button, visible only when `role === 'user'` (BD4: `admin`/`owner` never see it — the button is hidden client-side and the 403 `forbidden` is still the server's last word), calling `DELETE /me/mfa` through the existing `ReauthDialog` step-up (`RequireRecentAsync`).
- `web/src/app/features/admin/admin.routes.ts` (owned by `10.9.1-T1`) — this task adds one `canMatch` guard function, `mfaEnrolmentGuard`, exported from `features/account/data-access/mfa.guard.ts`: reads `role`/`mfaEnabled` off the session-store snapshot (no extra HTTP call — `/me` is already cached, D10); `role ∈ {admin, owner} && !mfaEnabled` → `router.createUrlTree(['/account/security'], { queryParams: { enrol: 'admin' } })`; otherwise `true`. Composed with the existing `adminGuard` (`&&`, first-fail order: role check, then MFA-enrolment check) so a non-admin still gets the existing role redirect, never the enrolment one.
- `security-page.ts` reads `enrol=admin` from the query params to show a one-line banner ("MFA is required for admin/owner accounts") above the existing enrolment flow; no new component.
- i18n: `account.security.mfa_disable`, `account.security.mfa_disable_confirm`, `account.security.admin_mfa_required_banner` (vi + en).

## Steps

1. Add `mfaEnrolmentGuard` to `features/account/data-access/mfa.guard.ts`, reading the cached `/me` snapshot (no new fetch).
2. Wire it into `admin.routes.ts`'s `canMatch` array after `adminGuard` (10.9.1-T1's file, one line, coordinated via `agent://`).
3. Add the `admin_mfa_required_banner` query-param banner to `security-page.ts` (10.3.3-T3's file, coordinated the same way).
4. Add the `Disable` button to `security-page.ts`, gated on `role === 'user'`, behind `ReauthDialog`'s step-up, calling `DELETE /me/mfa`; on 204 refetch `/me`, on 401 `reauth_required` retry once (existing `ReauthDialog` contract, SC29).
5. Map 403 `forbidden` (unreachable client-side once the button is hidden, kept as a defensive `AppError` toast) and 401 `reauth_required`.
6. Write the unit/component specs and the guard-redirect e2e assertion.

## Acceptance checks

- **Given** a `user`-role account with MFA enabled, **When** `/account/security` renders, **Then** the `Disable` button is visible; **given** an `admin`/`owner` account, **Then** the button is absent (BD4).
- **Given** a `user` clicks `Disable` and completes step-up, **When** `DELETE /me/mfa` returns 204, **Then** the page refetches `/me` and shows the enrolment CTA again (MFA now off).
- **Given** an `admin`/`owner` account without MFA enrolled, **When** it navigates to any `/admin/**` route, **Then** it is redirected to `/account/security?enrol=admin` and the banner renders; **given** the same account after enrolling, **Then** the same route now matches (`adminGuard` unaffected).
- **Given** a `user`-role account (never admin/owner), **When** it attempts `/admin/**` directly, **Then** the existing `adminGuard` role redirect fires first — `mfaEnrolmentGuard` never runs ahead of it (guard order).
- **Given** a 401 `reauth_required` on `DELETE /me/mfa`, **When** the dialog succeeds, **Then** the delete retries once automatically (existing `ReauthDialog` contract).

## Tests

- Unit (Vitest): `mfaEnrolmentGuard` — four cases (admin+enrolled, admin+unenrolled, owner+unenrolled, user role) against a fake session-store snapshot.
- Component (Vitest): `security-page.ts` — `Disable` button visibility by role, confirm dialog, success/failure toasts, `enrol=admin` banner presence.
- e2e (Playwright, extends `10.3.3-T3`'s `auth-mfa.spec.ts`): an owner account without MFA hitting `/admin` is redirected to `/account/security?enrol=admin`; after enrolling, the same navigation reaches `/admin`.
- Axe spec: the banner and button pass `wcag22aa` (reused fixture, no new page).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| `DELETE /me/mfa` returns 403 `forbidden` (admin/owner reached it despite the hidden button, e.g. stale role cache) | `AppError` toast, no retry; refetch `/me` to correct the cached role |
| `DELETE /me/mfa` returns 401 `reauth_required` | `ReauthDialog` step-up, retry once (existing contract) |
| Guard runs before `/me` has resolved (cold boot, deep link into `/admin/**`) | `mfaEnrolmentGuard` awaits the same resolver `adminGuard` already awaits (10.9.1-T1's route-resolution contract) — never redirects on a stale/empty snapshot |
| An `admin`/`owner` already on `/account/security?enrol=admin` navigates back to `/admin/**` without enrolling | Guard re-evaluates on every `canMatch`, redirects again (no bypass via browser back) |
| Disable while a re-auth dialog from another action is open | The existing single-flight `ReauthDialog` service serialises step-ups (10.3.3-T3 contract); no second dialog |
