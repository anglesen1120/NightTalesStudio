## Goal

A critical setting change (`payment.*`, `youtube.*`, `tiktok.*`) is never silent: the owner who saved it sees a "Pending change" banner with who requested it and when it applies (or that it is waiting for a second owner), a second owner sees the same banner **plus** Approve/Cancel, and the e-mail every owner receives links to a page that works from a locked phone with no login — one confirm click cancels the change and the token can never be replayed, logged or put in a URL query string. This task is the only place in the web app that touches that token.

## Design

**Part A — pending-change banner (authenticated, inside `10.9.3-T1`'s settings screen).**

```ts
export interface SettingChangeDto { /* server-shaped, rendered verbatim */
  id: string; integration: string; requestedBy: string; applyAfter: string; // ISO-8601
  status: 'pending';
}
```

`GET /admin/settings/changes?status=pending` is polled **only** on navigation/`resync` (SD16 — no timer-based polling); the banner reads the array and, for the card matching the current integration, renders: requester display name, apply time (`applyAfter`, localized) or "waiting for a second owner" when the server has not set an apply time yet, and a "Cancel" button always available to any owner. **If the current session's owner is not the requester**, an "Approve" button is also shown (server enforces "a different owner"; the client does not re-derive identity comparison beyond hiding the label for the requester's own session as a UX nicety — a self-approve attempt still relies on the server's rejection).

- **Approve** → `POST /admin/settings/changes/{id}/approve` (`IReauthGuard`) → `StepUp` retry-once on 401 → success closes the banner and refetches the settings card (the change may now be applied immediately or still time-locked, per the server's D7 rule — the client shows whatever `GET /admin/settings` returns next, it does not assume immediate application).
- **Cancel** → `POST /admin/settings/changes/{id}/cancel` (`IReauthGuard`) → same retry-once → success removes the banner.
- 409 on either action → refetch and show the current pending state (the change may have already been applied/cancelled by someone else).

**Part B — public cancel-request page (`/cancel-request`, unauthenticated, SD8/SC30 exact spec).**

Route: `public` feature, **not** lazy-loaded behind any guard, reachable logged out and logged in. URL shape (frozen, SC30): `<origin>/cancel-request#kind=<setting_change|owner_action>&id=<uuid>&token=<token>`.

```ts
@Component({ selector: 'app-cancel-request-page', changeDetection: ChangeDetectionStrategy.OnPush, standalone: true })
export class CancelRequestPageComponent {
  // reads location.hash exactly once in the constructor/ngOnInit, then calls history.replaceState(null, '', location.pathname)
  // state union: 'confirm' | 'submitting' | 'done' | 'invalid' | 'rate-limited'
}
```

Behaviour, verbatim from SD8/ST-5/WT-W12:
- The fragment (`kind`, `id`, `token`) is read **once**, then `history.replaceState` scrubs it from the visible URL and from `window.history` — a back-navigation or a page refresh can no longer recover the token from history.
- One explicit confirm button (no auto-submit); on click, `POST /security/cancel-links/{kind}/{id}` with body `{ token }` — **no** `Authorization` header is attached (this call bypasses the auth interceptor entirely) and **no** token refresh is attempted around it.
- Success (204) → `'done'` state, generic "The change has been cancelled" (vi/en) — no detail about what the change was.
- 400 `cancel_token_invalid` → `'invalid'` state, one generic message that covers unknown/used/expired alike ("This link is no longer valid") — the page never distinguishes the three so a token cannot be probed for validity.
- 429 `rate_limited` → `'rate-limited'` state using `RetryCountdown` with the server's `Retry-After`.
- `Referrer-Policy: no-referrer` is set for this route (server response header or a `<meta name="referrer" content="no-referrer">` in the page — the writer confirms which the SSR/prerender pipeline supports and uses that one).
- **No third-party asset** on the page: no CAPTCHA, no analytics, no font CDN, no icon CDN — this is an explicit CSP-adjacent rule (SD8), not just a style preference.
- Works at 360 px with no zoom requirement (mobile e-mail client browsers).

**Repository.** A minimal, dedicated port — this call must never pass through the shared authenticated `HttpClient` instance that attaches bearer tokens:

```ts
export interface CancelLinkRepository {
  cancel(kind: 'setting_change' | 'owner_action', id: string, token: string): Promise<void>; // throws AppError on non-204
}
```

**Layout.** D11 `ConfirmDialog`-style single-confirm layout (not a modal — a full page), `RetryCountdown` for 429; no `ReauthDialog` (this page never authenticates); vi/en via a `public` or `errors` scope key set — no new scope needed for four short strings if `errors`/`public` already fits (writer's call, documented in Outputs).

## Acceptance checks

- **Given** a card with a pending change, **When** the current owner is the requester, **Then** the banner shows requester + apply time (or "waiting for a second owner") and only "Cancel"; **Given** a different owner's session, **Then** "Approve" is also shown.
- **Given** Approve or Cancel returns 401 `reauth_required`, **Then** `ReauthDialog` opens and the same call is retried exactly once.
- **Given** Approve/Cancel returns 409, **Then** the banner refetches and shows the current pending state rather than an error toast.
- **Given** `/cancel-request#kind=setting_change&id=<uuid>&token=<token>` is opened, **Then** the URL bar no longer shows the fragment after the page reads it once (`history.replaceState` called exactly once, asserted in the spec).
- **Given** the confirm button is clicked, **Then** the outgoing request carries **no** `Authorization` header (asserted on the captured request in the spec) and no refresh call is made around it.
- **Given** a 204 response, **Then** the page shows the generic "cancelled" state with no detail about the underlying change.
- **Given** a 400 `cancel_token_invalid` response, **Then** the page shows exactly one generic "link invalid or expired" message — the same copy regardless of whether the token was unknown, already used, or expired.
- **Given** a 429 response, **Then** `RetryCountdown` renders using the server's `Retry-After`.
- **Given** the page's network trace, **Then** no third-party asset (script/font/analytics) is requested — explicitly including no request to `challenges.cloudflare.com`, now guaranteed because 10.3.3-T2 loads the Turnstile script on demand only from CAPTCHA-bearing routes, never from `index.html` (09 W3 CR-34).
- **Given** the page's response headers/meta, **Then** `Referrer-Policy: no-referrer` is present.
- **Given** the built axe spec, **Then** `/cancel-request` passes tags `wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa` at 360 px with no zoom requirement, and the CSP fixture reports zero violations on this route.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Page opened without a fragment (`/cancel-request` bare) | `'invalid'` state immediately, no request sent (nothing to POST) |
| Fragment present but malformed (missing `kind`/`id`/`token`) | `'invalid'` state, no request sent |
| User refreshes the page after the first read | Fragment is gone (`history.replaceState` already ran) → `'invalid'` state; this is intentional (SD8: read once) |
| User is also logged in (another tab) | The cancel call still carries no bearer token — verified explicitly, not merely "happens to be true" |
| Double-click the confirm button | Second click is a no-op while `'submitting'`; the button disables itself (idempotency is also the server's `[AllowAnonymousRequest]` design, but the client does not rely on a double 204) |
| Approve/Cancel banner action while another owner already resolved it | 409 → refetch → banner disappears or shows the new state, no stuck spinner |
| `applyAfter` in the past (clock skew / already due) | Rendered as-is (localized date/time); no client-side "overdue" recomputation — the server's next apply-job tick is authoritative |
| Rate-limited on the public page | `RetryCountdown` from `Retry-After`; no automatic retry |
