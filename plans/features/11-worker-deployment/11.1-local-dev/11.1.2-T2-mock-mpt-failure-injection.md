## Goal

Every failure the Worker must classify is reproducible on a laptop: one env variable (`MOCK_FAIL_MODE`) or one trigger keyword in a submit body makes the mock reach exactly the terminal `state` + `outcome.code` of the 05 D5 mapping, `MOCK_FAIL_RATE` makes failure probabilistic but deterministic per submission, and `MOCK_IMAGE_REPORT` selects the `images` block 03.4.3-T2 owns.

## Design

**Mode table** (`MOCK_FAIL_MODE`, parsed once at start; unknown value → exit 2 naming it and listing the accepted set):

| `MOCK_FAIL_MODE` | Terminal `state` | `outcome.code` | `detail` | Mock behaviour |
|---|---|---|---|---|
| (unset) | `succeeded` | — | — | normal path |
| `tts_failed` | `failed` | `tts_failed` | `audio` | the fake backend stops in the `voice` stage and reports the failed stage |
| `image_moderated` | `failed` | `image_moderated` | `materials` | **alias** of `MOCK_IMAGE_REPORT=moderated_all` (05 CR-4); sets the report, and the terminal state follows the report's own rule |
| `lost_task` | `failed` | `render_lost` | `mpt_restart` | the store row is removed at the first poll after submit → every later `GET` is 404 `adapter_task_unknown` |
| `timeout` | **never terminal** | — | — | progress stops at `assembling` 95 % and stays there (the Worker raises `render_timeout`, 05 D5) |
| `assembly_failed` | `failed` | `render_assembly_failed` | `video` | stops in `assembling` |
| `node_error` | `failed` | `render_node_error` | `<stage>` | stops at `preflight` and reports that stage as the failure |
| `quality:<check>` | `succeeded` | — | — | terminal success whose `check` block is the `render-check.v1.*` fixture that fails `<check>` (05.5.1-T2's ids); unknown `<check>` → exit 2 |

`OutcomeMessages[code]` supplies the fixed `message` (D4) — the mock never writes prose into `outcome.message`.

**`MOCK_FAIL_RATE`** — a float in `[0,1]`, default `0`; outside the range → exit 2. The decision is **deterministic per submit**: the mock hashes the `render_job_id` (its own hash, not the body hash) into a uniform value and compares it with the rate, so a test asserting "N of M submissions fail" is exact and a rerun is identical. The applied mode is chosen from the enabled failure set in a fixed order (`tts_failed` → `assembly_failed` → `node_error` → `lost_task`) so a rate test is stable. `MOCK_FAIL_RATE` never fires for a submit that carries an explicit mode keyword.

**Trigger keywords** (searched in the free-text fields of the submit body — `video_script`, `video_terms` — case-sensitive, whole-token):

| Keyword | Effect |
|---|---|
| `__fail_image__` | `MOCK_IMAGE_REPORT=moderated_all` for this submit (03.4.3-T2) |
| `__block_image__` | the `video_terms` entry carrying it becomes a moderated slot (03.4.3-T2) |
| `__fail_<mode>__` | this submit behaves as `MOCK_FAIL_MODE=<mode>` [INFERENCE: generalisation of the `__fail_image__` pattern in 11 §4] |
| `__fixture_<name>__` | this submit replays the named D14 fixture state (resolution implemented in 11.1.2-T1) |

**Precedence** (first match wins, evaluated at submit): (1) a keyword, (2) `MOCK_FAIL_MODE`, (3) `MOCK_FAIL_RATE`'s deterministic draw, (4) normal success. `MOCK_IMAGE_REPORT` is orthogonal: it shapes the `images` block for every submit unless a keyword overrides it, and only its `moderated_all`/`funds` values also force the failed `materials` terminal state (03.4.3-T2's table). The resolved plan for a submission is logged once as `{task_id, mode, source: keyword|env|rate|none}` — ids and names only, never body content (S7).

**Hooks.**

- `IImagePlanSink`: the mock's binding receives the `ImagePlanV1` at submit and produces the report at the terminal tick. This task implements the mode→report selection and keeps the generator behind the 03.4.3-T2 seam so its schema test owns the shape.
- Failure injection never touches the server core: it supplies the core's own `RenderOutcomeV1` fields and state transitions (`IRenderBackend` + the store), so a mode can never make the mock emit a code the contract does not have.
- The `render-submit.v1` field validation 03.4.3-T2 specifies (string `video_terms`, `video_concat_mode ≠ sequential`, missing `video_clip_duration`, `prompt_sha256` length ≠ `video_terms` length → 400 `adapter_contract_violation`) is exercised by this task's tests as part of the mode matrix, without re-implementing the validator (it is `SubmitValidator`'s, D5).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two injection sources at once (keyword + env) | the keyword wins, and the log records `source: keyword` so the reason is visible |
| `MOCK_FAIL_RATE` used with `MOCK_FAIL_MODE` set | the mode wins for every submit; the rate is inert (stated in the README, asserted by a test) |
| `MOCK_FAIL_MODE=image_moderated` **and** `MOCK_IMAGE_REPORT=ok` | the alias wins for that submit until the 03.4.3-T2 report selection replaces it; the mock logs the override |
| A `quality:<check>` id that exists in the fixtures but with a passing value | exit 2 at start (an unusable id is a misconfiguration, not a silent success) |
| Reference-count flakiness | the rate draw uses the `render_job_id`, never a shared process RNG, so tests never race |
| Someone ships a mode as a production default | impossible: these env names exist only in `tools/mock-mpt`, the dev `.env` and the optional compose file; the real adapter has no such keys (D6) |
| Rollback | the mode layer is one file plus its tests; removing it restores the always-succeeding mock, and the tests that used modes fail loudly (intended) |
