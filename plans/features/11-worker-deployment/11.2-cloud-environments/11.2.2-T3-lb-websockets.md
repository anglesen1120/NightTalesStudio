# 11.2.2-T3 — Load balancer: WebSockets only for `/hubs/*`

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 11.2.2 | XS (0.25) | Ops | 11.2.2-T1 | — | P · M1 |

## Goal

With two API instances behind the LB, SignalR must not need sticky sessions. Clients use `skipNegotiation` with the WebSockets transport (P10), so E5's affinity requirement does not apply; the LB must nevertheless upgrade `/hubs/*` correctly, keep the WebSocket alive, and the sticky rule must exist as a documented, off-by-default fallback. This task provisions and asserts that routing — the hub's client/server options are 09's contract, not changed here.

## Inputs

- `../README.md` E5, P10, D16 (rolling API rollout with 2 instances), D11 (TLS); `plan.md` §3 (LB row), §5, §8, §9 check 13.
- `11.2.2-T1` outputs: `lb_address`, `app_base_url`, `staging_base_url`; the LB listener and API target group from that task.
- `../../../11-worker-deployment.md` §5.1 — "SignalR runs WebSockets-only or with sticky sessions"; §4 (11.2.2 story, the same sentence).
- 09's hub route prefix `/hubs/*` and the client's `skipNegotiation` setting (external; consumed, not redefined).

## Design

- A path rule on the HTTPS listener: `/hubs/*` → the API target group **with WebSocket support enabled**, HTTP/1.1, `preserve_host` on, and the query string preserved (`skipNegotiation` clients still send the handshake token in the query string; browsers cannot set WebSocket headers).
- Target-group attribute `stickiness = false` (the LB default) in P; a module variable `hubs_sticky = false` exists so that enabling it is a one-value change if a non-WebSocket transport is ever needed (E5). When `hubs_sticky = true`, the documented fallback is cookie-based affinity scoped to `/hubs/*` only.
- LB idle timeout ≥ 300 s [INFERENCE: above SignalR's default 15 s keep-alive with margin] and the module asserts it, because a too-short timeout drops idle hub connections without an error.
- Access logging for `/hubs/*`: path + status only; query strings excluded (they carry the short-lived handshake token) — the token's lifetime and one-time use are 09's contract.
- No change to `render-node.v1`, and no hub code change: this task's blast radius is LB configuration plus the assertion script.

## Steps

1. Add the `/hubs/*` listener rule to `infra/modules/platform` with WebSockets enabled, `preserve_host`, query string preserved, `stickiness = hubs_sticky` (`false` by default), idle timeout ≥ 300 s.
2. Add the assert: in `assert-plan.sh`, `/hubs/*` routes to the API target group, WebSockets enabled, `stickiness = false`, idle timeout ≥ 300 s (exit 1 otherwise).
3. Write `infra/checks/check-ws.sh <url>` (Bash, 01 D9 conventions): a raw HTTP/1.1 upgrade request on `/hubs/<path>?access_token=<fake>` expecting **101, or an application-level 401/403 — never 404/502**; exit 0/1/2. It must not require a real token (it proves routing, not auth).
4. Document the fallback in `infra/README.md`: when to set `hubs_sticky = true`, what it costs, and that the client must then send cookies.
5. Apply to staging, run `check-ws.sh` twice, and record in the log which API instance answered each upgrade (both should serve traffic; this is the anti-affinity evidence).
6. Confirm the LB access log for those two requests contains the path and status but no query string.

## Outputs

- The `/hubs/*` listener rule + `hubs_sticky` variable + idle-timeout assertion in `infra/modules/platform`.
- `infra/checks/check-ws.sh`.
- The `infra/README.md` fallback note (when to enable stickiness) and the two-request evidence (which instance answered).

## Acceptance checks

- [ ] `assert-plan.sh staging plan.json` shows `/hubs/*` → the API target group, WebSocket support enabled, `stickiness = false`, idle timeout ≥ 300 s.
- [ ] `check-ws.sh wss://staging.<domain>/hubs/<path>` exits 0: the response is 101 or 401/403 from the application, never 404 or 502.
- [ ] Running `check-ws.sh` twice yields two upgrades that were served by the two different API instances (recorded by instance, no affinity).
- [ ] The LB access log entries for those upgrades contain the path and status and **no** query string.
- [ ] `check-ws.sh` exits 1 when pointed at a path outside `/hubs/*` (negative case: no upgrade on a non-hub route).
- [ ] With `hubs_sticky = true` applied on a throwaway plan, the assertion fails as designed (guard test), then the value is reverted.
- [ ] `tofu plan -detailed-exitcode` on staging is empty after the change.

## Tests

## Failure handling and edge cases

- **Provider LB cannot upgrade WebSockets on a path rule** ⚠️: a dedicated `wss` listener or a separate target group for `/hubs/*` is the fallback; if the provider cannot do WebSockets at all, the environment is blocked and 11.2.1-T1's decision must be revisited (the hub is the only live-progress channel).
- **Client configured with automatic transport selection** (negotiation enabled): it will need stickiness. The client setting is 09's; until it is fixed, `hubs_sticky = true` is the documented stopgap and the assertion is toggled with it in the same change.
- **Idle timeout left at the provider default** (often 60 s): hub connections die on quiet stories; the assertion catches it, and the fix is the module value, never a client keep-alive workaround.
- **Token in the query string appears in logs**: LB access logging is configured to drop query strings; if the provider cannot, the log retention for `/hubs/*` is reduced and the token's lifetime is what limits exposure (09's contract).
- **TLS termination vs pass-through**: termination stays at the LB (`wss` → `ws` to the API); the pinned-TLS rule (D11/S3) applies to Worker → node, not to this listener, so no certificate pinning exists here.
- **Rollback**: revert the listener rule/`hubs_sticky` value and re-apply; a rolling API rollout (D16) tolerates both states because no session state is stored on the LB.
