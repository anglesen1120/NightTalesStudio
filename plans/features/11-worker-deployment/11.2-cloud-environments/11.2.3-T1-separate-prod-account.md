# 11.2.3-T1 — Prod on its own account and its own OAuth/OpenAI projects

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 11.2.3 | M (1.0) | Ops | 11.2.2-T4, 11.5.3-T1 | — | S · M2 |

## Goal

Production stops sharing a cloud account with staging and with the owner's other work: it gets its own account/project set, its own keys, registry, storage hosts and buckets (D21), PostgreSQL, secret manager, DNS zone and OIDC role, plus its own Google and TikTok OAuth projects, so that a test, a leaked staging key or a support action can never touch real users. The move is built as a create-and-cut-over with a rollback window, not as an in-place account migration.

## Inputs

- `11.2.2-T4` — the live prod env in the shared account (account A), its state, its `nts/prod/` secret paths, its node tuple.
- `11.5.3-T1` — OIDC deploys and supply-chain settings that must be re-bound to the new account (this task's dependency per `../README.md` §8.1); 11.5.1-T1's `deploy.yml` and the `production` environment are its consumers.
- `../README.md` D1 (S-phase boundary), D15 (resource + secret-path list), D16, D17, E13, E14, O2; `plan.md` §3, §9 check 17, §11.
- `../../../11-worker-deployment.md` §4 (Epic 11.2.3: separate accounts/keys, separate Google/TikTok OAuth projects, separate text OpenAI project with a hard budget, second project for node images).
- `../../../00-overview.md:98-99` — the Google app is set to production without verification for one owner; TikTok Direct Post is unaudited (private-only) and is R2. These set the expectations for the OAuth projects, not the other way round.
- 11.4.1-T3's copy mechanism (the `weed filer.backup` replication of `nt-media-<env>` into `nt-backup-<env>` on `storage-backup-<env>` that T3 owns and 11.6.1-T1 asserts, D21/T80, 11 CR-15) as the model for the data move; 11.3.1-T3/11.3.2-T1/T2 for the node cutover.

## Design

**Two accounts, one codebase.** Account A keeps staging (and dev); account B becomes the only owner of prod. `infra/envs/prod` changes only its provider credentials/backend and account-scoped values (zone id, role ARNs, registry endpoint, instance profiles) — the same `infra/modules/platform` and `infra/modules/render-node`, still no forks; the value-only-diff check from 11.2.2-T4 is re-run against the new account.

**Cut-over sequence** (each step observable, abortable):

1. Build B from the same modules (`env = "prod"`, `gpu_node_count = 1`, B's DNS zone, `nts/prod/` in **B's** secret manager, B's registry).
2. Move data: PostgreSQL by a base backup + WAL replay (E10) or a logical dump into B's 17 instance; buckets by an S3-level sync between the A and B storage hosts (`filer.backup`-style continuous replay for `nt-media-prod`, and `nt-backup-prod` re-seeded on B's `storage-backup-prod` by starting `filer.backup` once with `-initialSnapshot`, then restarting without it — D21/T80/T89, 11 CR-15), verifying object counts and total bytes; registry images re-published by 11.5.1-T1 with the same `sha-<git sha>` tags so tags stay traceable.
3. Re-create every D15 secret in B's manager (values entered by the owner, never copied through a shell history or argv); the A values stay live but unread until the window closes.
4. Re-create the OpenAI projects in B's organization (P8/`DECISIONS` §10.5): `nts-text-prod` and `nts-images-prod` (image models only, hard budget), with new keys.
5. Create the OAuth projects in B: a Google Cloud project with the YouTube Data API enabled and an OAuth client whose redirect URIs use `https://app.<domain>` only, and a TikTok developer app for R2. Both are distinct from staging's clients; 00-overview:98-99 fixes the Google app's production-without-verification stance and the private-only TikTok behaviour.
6. Provision the prod GPU node inside B's render subnet (`infra/modules/render-node`), install it with `nts-node provision --env prod --node <name>` (11.3.1-T3), smoke it (`gpu-smoke.sh`), and add it to `RenderNodes:Nodes[i]` (D13) with its own `RENDER_NODE_<NAME>_API_KEY` and pinned TLS fingerprint (11.3.2-T2).
7. Rebind CI: the prod job uses B's OIDC role and B's registry; 11.5.3-T1's signing/verification follows the same trust.
8. Flip DNS `app.<domain>` and `media.<domain>` to B's LB (short TTL) and run the post-cutover smoke (health, login, one episode read, one render through the B node).
9. Keep A's prod stack running **cold** for the rollback window [INFERENCE: one release cycle] with its containers stopped; after the window, destroy it in a separate reviewed apply (the `prevent_destroy` guards are lifted in that same reviewed change) and revoke A's prod keys.

**Facts that make this a real change, not a rename:** OAuth refresh tokens are bound to the OAuth client, so moving the Google client forces one owner re-consent (autopilot publishing pauses for that window — schedule it); YouTube quota is counted per project, so the new project starts with a fresh quota and 11.6.2-T1's quota alert baseline moves with it; the node's adapter key and TLS fingerprint are per node and per environment, so the node swap follows D11's rotation (drain → new key/cert → activate).

**Naming.** Account B's `pg`-backend state keeps the `prod` database so `tofu -chdir=infra/envs/prod` stays the single entry point; the backend's `conn_str` (B's `nts_tofu` instance, T76/T83) is the only difference, and the old backend config is archived in `infra/envs/prod/README.md` with the date of the move.

## Steps

1. Register/obtain account B, its DNS zone, its OIDC identity provider trust and its role set (11.5.3-T1's shape, new account ids).
2. Point `infra/envs/prod` at B (provider credentials, backend, zone id, roles, registry) and re-run the value-only-diff check against `infra/envs/staging`.
3. Apply B's env (no DNS flip yet); assert the prod-only checks (one render node, `app.<domain>` record prepared but not authoritative, `nts/prod/` prefix in B).
4. Migrate data (PG + buckets) and verify counts/bytes with the comparison script.
5. Fill B's secret manager; record which secret names were written (never their values).
6. Create the OpenAI projects in B and set the image-project hard budget before any node use.
7. Create the Google/TikTok OAuth projects in B; verify distinct client ids and the exact redirect URIs.
8. Provision the B node, run `gpu-smoke.sh`, register it in D13, and prove one render through it (the `11-node` gate's checks reused, not weakened).
9. Rebind CI to B and run `deploy.yml` for prod against B (11.5.1-T1).
10. Flip DNS, run the post-cutover smoke, and record the rollback window start.
11. After the window: stop and destroy A's prod stack in a separate reviewed apply; revoke A's prod keys and disable its secret entries; confirm account A now contains only staging/dev resources.
12. Record the whole move in `infra/envs/prod/README.md` (dates, account ids, DNS TTL, window, rollback command) and update `../../../DECISIONS.md` §10.5/§10.12 pointers if the account/project ids are recorded there.

## Outputs

- Prod running in account B from the unchanged modules, with its own zone, registry, PG, storage hosts and buckets (D21), secret manager, OIDC role and GPU node.
- Migrated and verified data (counts/bytes compared, one render through the B node).
- Separate Google and TikTok OAuth projects in B with distinct client ids and `app.<domain>` redirect URIs; one recorded owner re-consent.
- Separate `nts-text-prod` / `nts-images-prod` projects in B's OpenAI organization with the image hard budget set.
- Account A reduced to staging/dev; its prod keys revoked.
- `infra/envs/prod/README.md` — the move record, the rollback command, the DNS TTL, the window close.

## Tests

- `infra/checks/assert-plan.sh prod plan.json` (prod-only + no cross-env ids) plus the isolation pair: a plan in A must not contain a prod resource and vice versa — a scripted check `infra/checks/check-account-isolation.sh` [INFERENCE: new script name].
- `infra/checks/compare-envs.sh` [INFERENCE: new script name] — PG row counts + bucket counts/bytes A→B, exit 0/1/2.
- Negative: the isolation check must fail if a prod resource is applied in A (deliberate test resource, destroyed immediately).
- Live: `dig`, `curl /health/live`, the render through B, `gpu-smoke.sh` on the B node (11.3.1-T1's script, not a copy), the OAuth re-consent, and the post-window denial of A's keys.
- No secret value is printed by any test; the comparison and isolation scripts compare names/counts/hashes only.

## Failure handling and edge cases

- **Region/GPU capacity differs in B** ⚠️: apply the region from 11.2.1-T1's record; if that region is unavailable in B, the move is blocked and reported, and A keeps serving (no partial cut-over).
- **Google verification or consent issues** (`00 §98`, G6 ⚠️): the new client stays "production, unverified" for one owner; the re-consent is scheduled, and autopilot publishing is paused for the window instead of publishing with a stale token.
- **TikTok** is unaudited (private-only) until R2: the B app is created and left unaudited; nothing in this task changes 07's scope.
- **DNS TTL** (e.g. 300 s [INFERENCE]): the flip is not instant; the rollback window must exceed the TTL plus one release cycle, and both LBs answer during propagation — the A stack therefore stays warm, not destroyed.
- **Data move drift**: writes continue during the copy → the cut-over requires a short write-freeze (containers stopped on A for the final delta), which is why A's prod stack is stopped rather than live during the window.
- **Secrets in two places** during the window: accepted and time-boxed; both are revoked/disabled at window close, in the same reviewed change that destroys A's prod stack.
- **OpenAI spend in two projects** during the window: budgets are set on both; the A image project is disabled when the B node takes over.
- **Node swap**: the B node must be running and dispatchable before the DNS flip, otherwise the first prod render fails; the D11 rotation procedure covers the key/cert swap (drain → new → activate).
- **Rollback**: flip DNS back to A's LB (A is still applied and only stopped), start A's containers, and re-point the Worker's node config to A's node; B is then destroyed in a reviewed apply. The rollback command is written down before the flip.
- **Abort mid-move**: every step is additive in B, so aborting leaves A serving and B as a priced but harmless copy; no step deletes A resources before step 11.

- This task is S because its prerequisite (11.2.2-T4) already proves the env is reproducible from code in P; the S work is the account boundary, the OAuth/OpenAI projects and the disciplined cut-over.
