# 11.3.2-T2 — Egress rules, per-node keys and rotation

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|

## Goal

The node can reach only what it needs (F14): the adapter's relay reaches `api.openai.com` and the music sync reaches the storage endpoint, both on 443 only, while `nts-mpt`, `nts-vieneu` and `nts-proxy` have no network at all; the app subnet, the fetcher subnet and the metadata address are unreachable from every user. Each node's keys exist in the secret manager under their D15 names (`ADAPTER_API_KEY`, `ADAPTER_API_KEY_NEXT`, `NODE_OPENAI_IMAGE_KEY` in project `nts-images-<env>`, `NTS_MUSIC_READ_KEY`/`NTS_MUSIC_READ_SECRET` scoped to `music/`), and the adapter key rotates with no drain (F24, P5).

## Design

- **Egress rules in `worker-node/net/nftables.conf`** (added to T1's file): `chain output { policy drop; }` allowing `ct state established,related`, `oif lo`, `udp dport 53` + `tcp dport 53` to the provider resolver, `udp dport 123`, and `tcp dport 443` **only** for `meta skuid nts-adapter` (relay → OpenAI; the host is fixed in code, so its any-host 443 is recorded here as an **accepted residual risk** [RULED — README §10 T73 (D20 H5)]) and for `meta skuid nts-music` restricted to the storage endpoint's IP set (the music sync) [RULED — README §10 T48/T73 (D20 H5)]. The one other egress is the **deploy egress window**: a temporary nftables set that `nts-node deploy` opens for root, only around a lock change, removed by a `trap` at exit and recorded in the deploy evidence — services never get it [RULED — README §10 T43 (D20 H1)]. Explicit `drop` for the app subnet, the fetcher subnet and `169.254.0.0/16`. No other port is open outbound — no 80, no 22 outbound, no raw. If 11.2.1 finds the provider supports FQDN egress rules (⚠️), the same policy is expressed there as the primary layer with these uid rules as the backstop.
- **Belt and braces.** The three offline units already carry `IPAddressDeny=any` + `IPAddressAllow=127.0.0.1 ::1` — never `localhost`, which also admits the resolver stub `127.0.0.53` [RULED — README §10 T47 (D20 H4)] (D10, S2); this task proves it per unit instead of trusting the unit file, and the nftables layer covers root and any future unit.
- **Per-unit deny tests.** Each deny test runs *inside the unit's sandbox*, not as a bare `su`: `systemd-run --wait -p User=<user> -p IPAddressDeny=any -p IPAddressAllow="127.0.0.1 ::1" …` [RULED — README §10 T47 (D20 H4)]. Under it `curl -sS --max-time 5 https://api.openai.com/v1/models` and any other 443 connect fail; name resolution itself may still succeed through the loopback resolver stub, so the failing *connection* is the proof, not a failed `getent`. As `nts-adapter` the same `curl` returns an HTTP status (401 is fine — it proves reachability).
- **Node → app/metadata deny tests.** From the node: `nc -z -w3 <app subnet host> <port>`, the managed PostgreSQL endpoint, the storage private endpoint, the fetcher subnet, and `curl --max-time 3 http://169.254.169.254/latest/meta-data/` → all fail; the storage endpoint is reachable **only** through `sync-music.sh` as `nts-adapter`.
- **Node image key.** `NODE_OPENAI_IMAGE_KEY` is created in the OpenAI project `nts-images-<env>` (image models only, hard budget — P8, DECISIONS §10.11) and stored as `nts/<env>/node/<name>/NODE_OPENAI_IMAGE_KEY` [RULED — README §10 T51 (D20 H3)]; it reaches only `/etc/nts/adapter.env` (mode 0640, owner `nts-adapter`) and is never used by MPT or the proxy. Rotation = create a new project key, update the secret in the secret manager, run `nts-node sync-env --node <name>`, restart the adapter, revoke the old key [RULED — README §10 T52 (D20 H8)].
- **Music read-only credential.** `NTS_MUSIC_READ_KEY`/`NTS_MUSIC_READ_SECRET` are scoped to the private assets bucket prefix `music/` and are delivered only into `/etc/nts/music-sync.env`. Proof: a `PUT` with it → 403; a `GET` of `music-evidence/…` → 403; a `GET` of `music/<file>` → 200. A credential that can write, or can read the evidence prefix, fails this task.
- **Adapter key rotation (no drain, F24/P5).** Rotation happens **only** in the secret manager; nobody edits an env file by hand [RULED — README §10 T52 (D20 H8)]. (1) write `ADAPTER_API_KEY_NEXT` (new) in the secret manager and run `nts-node sync-env --node <name>` to regenerate `/etc/nts/adapter.env`; (2) restart `mpt-adapter.service`; (3) update `RENDER_NODE_<NAME>_API_KEY` for the Worker (secret manager) and restart the Worker; (4) promote NEXT to current in the secret manager, clear NEXT, `nts-node sync-env --node <name>`; (5) restart the adapter. During (1)–(4) both keys are accepted (constant-time compare against current and next, D5); after (5) the old key is refused with 401 `adapter_unauthorized`. No drain, no dropped render.
- **Key hygiene.** Keys are written from the secret manager into the env file by `nts-node sync-env` (11.3.1-T3), and `deploy` asserts the file against the secret manager by sha256 (values never printed) [RULED — README §10 T52 (D20 H8)]; never on a command line, never in a log line, never in a bundle. `grep -R` for each value over `/etc/nts`, the units, one deploy's journal and the bundle tarball must find nothing (S4).
- **`docs/runbooks/key-leak.md`** (owner per D2): per-node key inventory, detection signals (relay `invalid_api_key` codes, 401 spikes, provider budget alerts), the immediate action per key (adapter key → rotate with NEXT, no drain; image key → new project key + revoke; storage credential → rotate in 11.4.1 and re-run `sync-music.sh`; music read key → rotate and re-run), the evidence to keep, and the escalation path to 11.5.2-T1 for platform-side keys.
- **Tracked artifacts.** The egress rules (in `worker-node/net/nftables.conf`), `worker-node/net/tests/egress.test.sh` [INFERENCE], `worker-node/net/tests/ip-deny.test.sh` [INFERENCE], `docs/runbooks/key-leak.md`, and the key inventory section added to `worker-node/env/*.env.example` comments (11.3.1-T2's files — this task supplies the mapping).

## Steps

1. Extend `worker-node/net/nftables.conf` with the §Design output chain and the two `meta skuid` 443 rules; `nft -c -f`; apply; confirm `nft list ruleset` and idempotence.
2. Write `worker-node/net/tests/ip-deny.test.sh` (static shape checks plus, with `--live`, the in-sandbox `systemd-run` deny matrix of §Design) and run it [RULED — README §10 T47 (D20 H4)].
3. Write `worker-node/net/tests/egress.test.sh` (static: only 443/53/123 outbound, the app/fetcher/metadata drops present, no 80/22 outbound) and run it.
4. Run the live matrix on the node: offline users fail, `nts-adapter` reaches OpenAI, app/PostgreSQL/storage/fetcher/metadata all fail, `sync-music.sh` succeeds as `nts-adapter`.
5. Create `NODE_OPENAI_IMAGE_KEY` in project `nts-images-<env>`; store it as `nts/<env>/node/<name>/NODE_OPENAI_IMAGE_KEY`; deliver it into `/etc/nts/adapter.env` with `nts-node sync-env --node <name>`; restart the adapter and confirm the relay's `image_relay` health block is ok (D7) [RULED — README §10 T51 (D20 H3), T52 (D20 H8)].
6. Create/confirm the read-only music credential; deliver it into `/etc/nts/music-sync.env`; prove the three credential tests of §Design (200/403/403).
7. Rehearse the adapter key rotation on a staging node (D1/O2) end to end, with a render running during the window; record the 401 after step (5) and that the render was not dropped.
8. Write `docs/runbooks/key-leak.md`; cross-reference it from `docs/runbooks/node-deploy.md` (11.3.1-T3).
9. Record evidence: the ruleset, the live matrix output, the three credential probes, the rotation transcript, and the key inventory (names only, no values).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| A unit needs network later (e.g. a new model download) | Not in P: models are offline (D9); a new dependency is a TL decision that changes D9, not a firewall edit. |
| Provider resolver is not 53/UDP but a local stub | Point the resolver set at the actual address (recorded) and keep the rule narrow; never allow all outbound 53. |
| Adapter needs a second OpenAI host (relay + text) | The node only serves images through the relay (03 D4); a second host is a D11 change, not a rule added on the node. |
| Key rotation interrupted after step (3) | Both keys are still valid, so nothing is broken; finish steps (4)–(5) or leave NEXT set (a bounded, auditable state). |
| A key leaked | `docs/runbooks/key-leak.md`: rotate the affected key only; the adapter key rotation needs no drain. |
| Storage endpoint IP changes | The storage rule is uid+port, not IP, so it survives; an FQDN rule (if the provider has it) is updated in 11.2.2-T1. |
| `nts-adapter` also runs `nts-cleanup` | The cleanup unit has no network (D10); the uid rule cannot leak into it because the unit itself denies the network. |
| Rollback | Restore the previous ruleset file with `nft -f`; for keys, re-run the rotation in the opposite direction (the previous value stays valid until NEXT is cleared). |
