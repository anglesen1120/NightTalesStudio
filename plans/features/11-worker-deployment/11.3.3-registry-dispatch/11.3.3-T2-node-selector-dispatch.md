# 11.3.3-T2 — `INodeSelector` dispatch rules and node metrics

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|

## Goal

Give render dispatch one decision point: a node is dispatchable only when it is `active`, its last health answer is fresh (≤ 90 s) and HTTP 200, it reports `capacity.accepting`, and it has more free slots than it is already running. Highest free slots wins, ties by `name`; nothing dispatchable returns `render_worker_unavailable` (503) and the render job stays `queued` — [RULED — README §10 T60] (D20 H14) not an error: `SubmitRenderJob` reschedules itself after `RenderNodes:HealthPollSeconds` while the job is `queued`, outside the outbox retry budget, and an ops alert fires after `Render:QueueAlertMinutes` (360). Also export the node metrics the alerts and the capacity test read.

## Design

```csharp
// src/NightTales.Application/Abstractions/Rendering/INodeSelector.cs
public interface INodeSelector
{
    Task<ErrorOr<WorkerNode>> PickAsync(CancellationToken ct);
}

// src/NightTales.Application/Rendering/NodeSelector.cs   (Application: IReadDb + INodeHealthCache only)
public sealed class NodeSelector : INodeSelector
{
    public NodeSelector(IReadDb readDb, INodeHealthCache cache, IClock clock, RenderNodesOptions options, NodeMetrics metrics);
    public async Task<ErrorOr<WorkerNode>> PickAsync(CancellationToken ct);
}
```

**Dispatch predicate** (all must hold — D13):

| Condition | Source |
|---|---|
| `state = 'active'` | `worker_nodes` (never `draining`, never `down`) |
| health snapshot exists and `clock.UtcNow − PulledAt ≤ RenderNodes:HealthStaleSeconds` (90 s) [INFERENCE: key name, plan §10] | `INodeHealthCache` |
| `HttpOk = true` (a 200 body: `mpt`, `tts_proxy`, `image_relay`, `assets`, `disk`, `gpu`, codec all ok; a 503 body is **not** dispatchable) | `NodeHealthSnapshot` |
| `Accepting = true` | `capacity.accepting` (05 D4) |
| `free = min(capacity, MaxConcurrentTasks) − in_flight > 0` | `worker_nodes.capacity`, health `capacity.max_concurrent_tasks`, `render_jobs` |

`in_flight` is **one** grouped query, never a per-node round trip:

```sql
SELECT n.id, n.name, n.capacity, n.base_url, n.tls_cert_sha256, n.gpu_model,
       COALESCE(c.in_flight, 0) AS in_flight
FROM worker_nodes n
LEFT JOIN (
    SELECT worker_node_id, count(*) AS in_flight
    FROM render_jobs
    WHERE status IN ('submitted','running') AND worker_node_id IS NOT NULL
    GROUP BY worker_node_id
) c ON c.worker_node_id = n.id
WHERE n.state = 'active';
```

(As EF: `readDb.Query<WorkerNode>().Where(n => n.State == WorkerNodeState.Active)` plus the grouped count over `readDb.Query<RenderJob>()` projected into an anonymous/`readonly record struct` join — `AsNoTracking()`, no tenant filter (system data, 09 D10).)

Ordering: free slots **descending**, then `name` **ascending** (ordinal, D13 tie-break) — deterministic, so two dispatchers agree without coordination.

`ErrorOr` shape: no candidate → `ErrorOr<WorkerNode>.From(new Error(ErrorCodes.RenderWorkerUnavailable, "no render node with a free slot"))` — the code is 09's existing constant (09 §5.4 L415); this task adds **no** error code and **no** HTTP mapping. [RULED — README §10 T60] (D20 H14) The result is a *retry signal* at the submit level: 09.6.3 re-dispatches the `queued` job after `RenderNodes:HealthPollSeconds`, outside the outbox retry budget, and raises an ops alert after `Render:QueueAlertMinutes` (360); this task only returns the code. The `ErrorCodes` member name is `RenderWorkerUnavailable` [INFERENCE: naming style only; the string constant is `render_worker_unavailable`].

**Metrics** (D13; 09.9.3 conventions; bounded by node count):

| Instrument | Kind | Update point |
|---|---|---|
| `render_node_free_slots{node}` | observable gauge | reads `INodeHealthCache` + the `in_flight` map refreshed by `PickAsync`/the poller [INFERENCE: D13 fixes the name only] |
| `render_dispatch_unavailable_total` | counter | incremented on every `render_worker_unavailable` return |
| `render_node_gpu_util_pct{node}`, `render_node_gpu_mem_used_bytes{node}`, `render_node_gpu_temp_celsius{node}` (T28), `render_node_disk_used_pct{node}` | observable gauges | read the cached `gpu`/`disk` blocks — never a per-scrape node call (Q1) |

`render_node_up{node}` and `render_node_health_reasons_total{node,reason}` stay with the poller (11.3.3-T1, `plan.md` §7).

**Drift alert** (`render_node_active_tasks_drift`): consecutive-pull counter per node comparing health `capacity.active_tasks` with the derived count; the counter and the emission live in the poller tick (T1) because it owns the pull cadence — this task exposes the derived count through an internal helper (`INodeLoadReader.GetActiveAsync(...)` [INFERENCE]) so both use one query. Metric `render_node_active_tasks_drift_total{node}` [INFERENCE: D13 names the alert, not the metric].

## Steps

1. Add `INodeSelector` + `NodeSelector` in Application with the query above; keep EF usage to core (`IReadDb`, no `Infrastructure` reference — 09 D1).
2. Implement the free-slot computation exactly as `min(capacity, MaxConcurrentTasks) − in_flight`, guarded by `> 0`; skip nodes with no cache entry or stale/`not HttpOk` entries before the DB ordering step.
3. Implement the deterministic ordering and return the `WorkerNode` aggregate (the caller needs `BaseUrl`/`TlsCertSha256` for the adapter client, D13/F13).
4. Return `render_worker_unavailable` when the candidate list is empty; increment `render_dispatch_unavailable_total`; log once per call at warning level with the candidate count and the reason histogram (`no_active`, `stale_health`, `not_accepting`, `no_free_slot`) — never the base URL or key.
5. Register `NodeSelector` + `NodeMetrics` in DI (Application registration; the Worker and Api composition roots both resolve it, 09 README D2).
6. Register the observable gauges/counter listed above against the existing OTel meter (09.9.3-T1 owns the pipeline; add instruments, do not create a second `Meter`).
7. Unit/Integration tests of `plan.md` §9's `NodeSelectorTests` row; report raw output.

## Acceptance checks

- [ ] With two `active` nodes of equal capacity (2 slots each, health `max_concurrent_tasks = 2`), the selector returns the lexicographically first `name`.
- [ ] A node with 1 free slot is preferred over one with 0; a node whose health `max_concurrent_tasks` is 1 with `in_flight = 1` is not dispatchable even though `capacity = 2`.
- [ ] `render_jobs` rows in `queued`, `ingesting`, `succeeded`, `failed`, `cancelled` do **not** consume a slot; `submitted` and `running` do (00 §7 L332).
- [ ] A `draining` or `down` node is never returned; a node with a health snapshot older than 90 s is never returned; a node whose health body was 503 (`HttpOk = false`) is never returned; `accepting = false` blocks dispatch.
- [ ] No candidate → `ErrorOr` error with code `render_worker_unavailable`; the API maps it to 503 and the `render_jobs` row stays `queued` (checked through 09's catalogue mapping test, not a new mapper here); [RULED — README §10 T60] (D20 H14) it is a retry signal — 09.6.3 reschedules after `RenderNodes:HealthPollSeconds` outside the outbox retry budget and alerts at `Render:QueueAlertMinutes` = 360, with no retry logic here.
- [ ] `render_dispatch_unavailable_total` increments exactly once per failed pick; `render_node_free_slots{node}` reports `min(capacity, max_concurrent_tasks) − in_flight` and never a negative value.
- [ ] Scraping the node metrics performs **no** HTTP call to a node and no DB write (assert with a counting fake handler and a counting `IReadDb` [INFERENCE: fake type]).
- [ ] `PickAsync` issues exactly one DB query per call (bounded work; assert via an EF command interceptor or a query-counting test double).
- [ ] The drift signal uses the same derived count as the selector (one implementation, asserted by a test that both return the same number for the same fixture data).

## Failure handling and edge cases

- **All nodes down / staging without a node**: `PickAsync` returns `render_worker_unavailable`; the job stays `queued` and retries later — never an exception, never a partial submit; [RULED — README §10 T60] (D20 H14) the retry is 09.6.3's reschedule after `RenderNodes:HealthPollSeconds` (outside the outbox retry budget, alert at `Render:QueueAlertMinutes` = 360), never an outbox retry (D13, 09 §5.4; staging renders against mock-mpt, D15/F08).
- **Health cache empty at Worker start** (first 30 s): every node is non-dispatchable until the first pull — intended; log the reason `stale_health` once per interval to avoid a log flood.
- **Race between two picks** (two `SubmitRenderJob` jobs in the same tick): the selector is read-only and does not reserve; the `submitted` row inserted by 09.6.3-T1 is what consumes the slot. A double pick on the last slot resolves as an adapter 429 `adapter_capacity_full` (05 F07) and the job is re-queued — the pick itself is not the guard [INFERENCE: D13 fixes no reservation; flag to the TL].
- **Flapping node**: an alternating 200/503 node loses dispatch status as soon as one pull is not `HttpOk`, and a `down` node needs 2 consecutive good pulls (F12) — a flapping node therefore spends more time out of dispatch than in it.
- **Node removed from config while jobs run**: it goes `down` → no new picks; running jobs are unaffected (09.6.3 polls them).
- **Clock jump** (`IClock` forward): freshness becomes stricter (more `stale_health`), never looser — no way to dispatch on an old answer.
- **Rollback**: revert the Worker image; the selector is a pure read path, so nothing to migrate. A node left out of dispatch by a stale cache recovers on the first poll tick after the rollback completes.

## Notes

- [RULED — README §10 T60] (D20 H14) `render_worker_unavailable` is not an error: the job stays `queued`, 09.6.3 reschedules `SubmitRenderJob` after `RenderNodes:HealthPollSeconds` outside the outbox retry budget, and the queued-too-long alert (`Render:QueueAlertMinutes` = 360) is rule 15 in 11.6.2-T1.
- Deliberately no reservation column and no cached count: `worker_nodes` stays a registry and free slots are derived per pick (00 §6 L311 note, D13).
- `min(capacity, health.max_concurrent_tasks)` matters: `capacity` is the operator's ceiling and `max_concurrent_tasks` is what MPT/the adapter actually accept (05 D4 L215); a raise of `NTS_MPT_MAX_CONCURRENT` on the node takes effect without a DB change.
- The three "candidate reasons" (`no_active`, `stale_health`, `not_accepting`, `no_free_slot`) are logging only — no metric label, to keep cardinality bounded.
- 11.6.2-T1 consumes these instruments for the "any node `down` > 5 min" and "`render_dispatch_unavailable_total` rising 15 min" alerts (D17); the initial `staging` environment has no node by default (D15/F08), so the counter is expected non-zero there.
