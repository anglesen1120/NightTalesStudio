**Probe route (12 CR-19, added by this task).** `POST /v1/probe-image` on the same public HTTPS interface (8090), behind the same `ApiKeyMiddleware`/pinned-TLS/auth-throttle as every other route (no new auth path) — a probe-only check that the node's own `NODE_OPENAI_IMAGE_KEY` project/key is funded, **without** submitting a full render job or reserving image-relay slots. No request body; response `ProbeImageResultV1`. `IImageProbeBackend` is implemented in `11.3.5-T2` (MPT backend, same task that owns the relay's OpenAI-facing calls); this task only maps the route, wires auth, and defines the contract seam. Consumer: `12.8.3-T3` (billing's resume-image probe) — until this route lands, that task fail-closes with `probe_route_unavailable`, never a fabricated pass; the `05.4.1-T2` half of 12 CR-19 (a matching `render-node.v1` contract note) is out of this task's scope (another owner).

Request order (05 D15 S2, D5): `ApiKeyMiddleware` (exactly one `x-api-key`, constant-time compare against `ApiKey` and, when set, `ApiKeyNext`; failure → 401; > 10 failures/min per source → 429 `adapter_auth_throttled` + `Retry-After: 60`) → per-endpoint Kestrel `MaxRequestBodySize` = `MaxBodyBytes` (413 `adapter_body_too_large` via the envelope handler) → `Strict` parse (400 rule `request_invalid` on malformed JSON) → `SubmitValidator` (first failing group → 400 `adapter_contract_violation`, `errors[{field, rule}]`); `{task_id}` UUID-parsed **before** any store lookup (404 `adapter_task_unknown`). Submit: sha256 of the **raw** bytes → replay 200 (same `render_job_id` + hash, stored `{task_id, state}`) / 409 `adapter_idempotency_conflict` → `CapacityGate` 429 + `Retry-After: 30` → health not ok 503 `adapter_node_unhealthy` → `IImagePlanSink.Register` → strip `image_plan` → `IRenderBackend.SubmitAsync` → 202. Status (store only, monotonic `percent`, `100` only terminal), outputs (`Content-Length` + `X-Content-SHA256` from `output.video.sha256`, streamed, never re-hashed, P3), cancel (202 idempotent, 200 no-op terminal, `Release` once), delete (204, `cleaned_at` kept, re-delete 204) and the fallback 404 `adapter_route_not_found` are D5 verbatim.

## Acceptance checks

- [ ] Every `worker-node/contract/fixtures/*.json` round-trips through `RenderNodeJson.Strict` value-equal (timestamps compared as instants).
- [ ] Submit replayed with the same `render_job_id` + body → 202 then 200 with the same `task_id`; a different body under the same id → 409 `adapter_idempotency_conflict`.
- [ ] A 2 MiB + 1 byte body → 413 `adapter_body_too_large`; a duplicate property and an unknown top-level member → 400 `adapter_contract_violation`; unknown members in a status body are ignored by `Tolerant`.
- [ ] `x-api-key` missing, duplicated or wrong → 401 `adapter_unauthorized`; the 11th failure in a minute from one address → 429 `adapter_auth_throttled` + `Retry-After: 60`; `ApiKeyNext` is accepted while set.
- [ ] A non-UUID `{task_id}` → 404 `adapter_task_unknown` with **zero** store calls (asserted on the fake store).
- [ ] 3 concurrent submits at `MaxConcurrentTasks = 1` insert exactly one row, the others get 429 + `Retry-After: 30`; health not ok → 503 and no insert.
- [ ] `GET .../video` sends `X-Content-SHA256` = `output.video.sha256` with `Content-Length` = `output.video.bytes` and calls `OpenOutputAsync` exactly once (no hashing path).
- [ ] Unknown route → 404 `adapter_route_not_found`; `OutcomeMessages.For` exists for every 05 D5 code and is ≤ 200 characters.
- [ ] `POST /v1/probe-image` requires the same `x-api-key` as every other route (401 without it) and returns `ProbeImageResultV1` behind the pinned-TLS listener only (12 CR-19); it never registers an image-relay slot and never calls `IRenderBackend.SubmitAsync`.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Malformed or empty JSON | 400 `adapter_contract_violation` rule `request_invalid`; nothing stored |
| Oversized body with no key | auth first (S2) → 401, not 413 |
| Replay after the row was purged (7 d) | no row found → 202 (new task); never a 500 |
| `UpdateAsync` conflict (poller vs cancel) | retried once inside the gate; only `cancel_requested` is last-writer-wins |
| `IRenderBackend.SubmitAsync` fails after insert | record → `failed` `render_node_error`, plan released, later submits blocked by health |
| Health source throws | fail closed → 503 `adapter_node_unhealthy` |
| Unknown member inside `mpt` | 400 (strict key-set check, 05 D3) |
| Rollback | library-only: reverting the release dir reverts contract + core together with the hosts (T2/T4) |

## Notes

- `MptLastSnapshot` extends D5's field list so `render-status.v1` can carry the `mpt` block 05 D4 requires (`[INFERENCE]`, `plan.md` §10 Open items).
- `03.4.3-T1`'s `relay_*` codes are relay errors, not outcome codes; they stay in that task's catalogue.
- The core never touches the filesystem or MPT — everything node-specific arrives through the four seams, which is what lets `NightTales.MockMpt` reuse it (F02).
- Deviations recorded during implementation (each verified against the frozen fixtures/spec, from the implementer report):
  - `MptStateV1.State` is `int?` (the design sketch says `int`): `render-status.v1.lost.json` carries `"state": null` and §10 T63 requires it — the fixture is the truth.
  - `ITaskStore.FindBySubmitKeyAsync(renderJobId, bodySha256)` became `FindByRenderJobIdAsync(renderJobId)`: §3 decides replay 200 / conflict 409 before the capacity gate, and with the pair-only lookup a full node answered 429 for a conflicting body; the insert path still re-checks, so a lost race cannot produce a wrong 409.
  - `RenderTaskRecord.Cues` is optional and omitted while null, and `RenderNodeServerOptions` uses settable properties: the `succeeded` fixture's video block has no `cues` key (a round-trip would add one), and init-only properties cannot be assigned by the binder or the DI configure callback.
  - Health is checked before the capacity gate in the submit path: the acceptance rule "health not ok → 503 and no insert" cannot hold if the gate already inserted; the only observable difference is a node that is both full and unhealthy, which answers 503 instead of 429.
  - `adapter_internal_error` was added to `AdapterErrorCodes`; `AdapterErrorStatus` maps codes→status and the two documented `Retry-After` values; `RenderNodeSchemas`, `RenderNodeRoutes`, `RenderNodeHealthStatuses` and `SubmitRules` were added to the contract surface — §1 requires an envelope for every non-2xx, and the eight paths plus the schema literals must not be duplicated across four consumers (additive constants, no wire change).
  - `ProbeImageResultV1` exposes the C# member `ErrorCode` with wire key `reason`, and its `Schema` is nullable and omitted while null: the design names the member `ErrorCode` while §2 fixes the key `reason`, and no probe fixture or schema literal exists, so the body stays `{"funded":…}` / `{"funded":false,"reason":…}`.
  - `[INFERENCE]` a submit failure after insert answers 503 `adapter_node_unhealthy` with the row `failed`/`render_node_error`/detail `"pipeline"` and the plan released: §3 lists no code for a backend refusal, and `"pipeline"` is inside the closed detail set of §4.
  - `[INFERENCE]` cancel and delete answer a `RenderStatusV1` body (202/200; 204 is body-less), and the throttled probe 429 carries `Retry-After: 60`: the doc fixes the statuses, not the bodies; the probe budget is 11.3.5-T2's.
  - `[INFERENCE]` `sub-title_enabled` is a plain bool, not a fixed value: the §2 table says true for P, but the output contract's `adapter_output_absent` covers "subtitles off", so a false submit must be representable.
  - 2 MiB + 1 byte is asserted at the reader boundary (`BodyLimitTests.RequestBodyReader_RefusesOneByteOverTheFrozenCap`), while the socket-level test uses a 64 KiB cap: with 2 MiB in flight Kestrel closes the connection before the client finishes writing (observed broken pipe), so the wire assertion would be flaky; both exercise the same limit and code path.
- Post-review fix (QA D1): `CapacityGate.TryEnterAsync` re-checks `FindByRenderJobIdAsync` inside its permit before the capacity count, so the §3 replay/conflict decision is race-safe against capacity — two in-flight identical submits give `202` + `200` (never `429`), a same-id different-body pair gives `409`, and distinct ids at capacity still give `[202, 429, 429]`.
