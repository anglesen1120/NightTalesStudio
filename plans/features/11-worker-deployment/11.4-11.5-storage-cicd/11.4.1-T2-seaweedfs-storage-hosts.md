# 11.4.1-T2 — SeaweedFS storage hosts: install, TLS, identities, lifecycle runner, metrics

## Goal

Run self-hosted SeaweedFS on the two storage VMs per environment that `11.2.2-T1`/`11.2.2-T4` create (`storage-<env>` in the `storage` subnet, `storage-backup-<env>` in a second zone), so every consumer keeps using the S3 API with only an endpoint and credentials (README D21, owner O7 2026-09-27, 11 CR-15). This task installs the digest-pinned image with compose + systemd, terminates TLS on the S3 gateway published as TCP 443, ships `sync-identities.sh` (renders `s3.json`, `security.toml`, `replication.toml` from the secret manager), starts the lifecycle runner (`weed admin` + `weed worker`) and exposes metrics. Buckets, policies, `identities.template.json`, CORS and lifecycle rules are `11.4.1-T1`'s; the `filer.backup` copy, delete-propagation and restore proofs are `11.4.1-T3`'s (T80, 11 CR-15).

## Design

- **Host layout.** `/opt/nts/storage/` holds `compose.yml` (services `weed` = `server -s3`, `admin`, `worker`; the backup host adds `backup` = `filer.backup`, wired by `11.4.1-T3`), `security.toml` (`[jwt.signing]` key from the secret manager, `0600`), `s3.json` (`0600`), `replication.toml` (backup host only, `0600`), the TLS cert/key (`0600`). Data: `/var/lib/nts/seaweedfs` on the attached XFS volume. One systemd unit `nts-storage.service` runs `docker compose up` with `Restart=on-failure`; files are shipped from `worker-node/storage/host/` [INFERENCE: path].
- **Flags (T78).** `weed server -dir=/var/lib/nts/seaweedfs -s3 -s3.port=8333 -s3.cert.file=… -s3.key.file=… -s3.config=/etc/seaweedfs/s3.json -master.volumeSizeLimitMB=1024 -volume.max=<floor(0.8 × volume GB)> -metricsPort=9327 -ip=<private address>`; `-s3.port.https` is **never set**. The gateway serves TLS only on container 8333; compose publishes `<private-ip>:443:8333`, so every client uses `https://storage-<env>.internal` (no port, T77). Master 9333, volume 8080/18080, filer 8888/18888 and admin stay bound to the private/host address (D21).
- **Security groups (T78, T86).** `storage-sg` inbound: 443 from `api-sg`, `worker-sg`, the render subnet (music read, `11.3.2-T2`) and the LB; filer 8888/18888 from `storage-backup-sg` only (`filer.backup` runs `-filerProxy`, so no volume port is opened); metrics 9327 from `worker-sg` only (OTel Collector, T16); 22/443 from the VPN/bastion range (operator installs, `apply-buckets.sh`, uploads, restores, T86); nothing from `fetcher-sg` (T77 — the fetcher has no storage route); everything else host-local. `storage-backup-sg` inbound: 22/443 from the VPN/bastion range and 9327 from `worker-sg`, nothing else (T86; the backup host itself initiates outbound to the primary filer and to the collector). `worker-sg` inbound adds 4318 from `storage-backup-sg` for the OTLP push (T85/T86).
- **TLS (T81).** No certificate pinning. An internal root CA (provider private CA, else an owner-generated offline root) issues the certificates for `storage-<env>.internal` and `storage-backup-<env>.internal`; IaC/bootstrap installs the root in every host and node trust store and mounts it into containers; the operator Mac uses `AWS_CA_BUNDLE`/`REQUESTS_CA_BUNDLE`. `media.<domain>`/`media.staging.<domain>` TLS is terminated at the LB, which forwards `GET`/`HEAD` to the gateway with `Host` unchanged (T75, T83).
- **Identities (T82, T92, T94).** `worker-node/storage/sync-identities.sh --env <env>` renders **all three** secret-bearing files — `s3.json` (identity actions from `identities.template.json` + key pairs from the secret manager), `security.toml` (`[jwt.signing]` key = `nts/<env>/storage/SEAWEEDFS_JWT_SIGNING_KEY`, T94) and `replication.toml` — atomically (`mktemp` in the same dir + `mv`, `0600`), then reloads the gateway; it also renders `0600` env files `NTS_CANARY_WRITE` on `storage-<env>` and `NTS_OPS_READ` on `storage-backup-<env>` (lag gauge, T94); values never reach argv, `ps` or output. The storage hosts' role reads `nts/<env>/storage/*` plus the exact names `shared/STORAGE_ACCESS_KEY`/`_SECRET_KEY`, `NTS_MUSIC_WRITE_KEY`/`_SECRET`, `NTS_MUSIC_READ_KEY`/`_SECRET`, `NTS_PREVIEW_WRITE_KEY`/`_SECRET`; each pair is `<NAME>` + `<NAME>_SECRET` — `BACKUP_SECRET_KEY` is not used (T94). This task ships the script and runs it with `--with-admin` so `NTS_OPS_ADMIN` (`Admin`, `nts/<env>/storage/NTS_OPS_ADMIN`/`_SECRET`) is present for `11.4.1-T1`'s `apply-buckets.sh` over the VPN; `--with-admin` is the only path that renders it and the next plain run removes it (T92); once `11.4.1-T1` supplies `identities.template.json`, the script is re-run to add the per-consumer identities. Outside an apply window `s3.json` holds no `Admin` identity and none is ever given to applications (T88/T92).
- **Lifecycle runner.** `weed admin` (bound to the private address, reached through an SSH tunnel only) and one `weed worker` per host execute the `s3_lifecycle` job; the job rules come from `11.4.1-T1`, execution proof from `11.4.1-T3`.
- **Snapshots.** Daily provider snapshots of the **primary** volume only, 7 days — the backup volume is not snapshotted, so no tier holds deleted media past 30 days (T87); configured through `11.2.2-T1`'s module, this task verifies one exists.
- **Checker.** `worker-node/storage/check-storage-host.sh --env <env> [--self-test]`: gateway TLS handshake against the internal CA + `aws s3api list-buckets` with `NTS_OPS_ADMIN` over `https://storage-<env>.internal` (443, T90/T92 — no head-bucket or known key before `11.4.1-T1`); master/volume/filer ports refused from an API host; `volume.list` shows writable slots; metrics endpoint answers from the collector host only; fails while `NTS_OPS_ADMIN` is present in `s3.json` outside an apply window (T92); one line per assertion. The backup assertions (copy, lag, restore) and the `--metrics` mode are added by `11.4.1-T3` (T85).

## Steps

1. Write `worker-node/storage/host/{compose.yml,nts-storage.service,security.toml.template,replication.toml.template}` and `sync-identities.sh` per the Design.
2. Install on `storage-staging` and `storage-backup-staging`; issue the internal-CA certificates; verify TLS + the `storage-sg` port matrix; run `sync-identities.sh --with-admin` (renders `NTS_OPS_ADMIN` for the apply window, T92); hand over to `11.4.1-T1` for buckets and the full template (T80).
3. Start `weed admin` + `weed worker` (the lifecycle runner, bound to the private address); point the OTel Collector at `-metricsPort` (9327, `worker-sg` source only); verify a provider snapshot exists.
4. Write `check-storage-host.sh`; run `--env staging`; then repeat steps 2–4 for `storage-prod` and `storage-backup-prod` (`11.2.2-T4`).
5. Record hosts, ports, image digest, volume sizes, CA choice (provider private CA vs offline root) and commands (never values) in `worker-node/storage/README.md`.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Primary host lost | Recreate from IaC, reattach the volume (or restore the latest snapshot); if the volume is lost, `11.6.1-T1` restores objects from `nt-backup-<env>` |
| Provider has no private CA | Generate the owner offline root per T81; issue both certs from it; record the choice in `worker-node/storage/README.md` — never fall back to client pinning |
| Volume full / no writable slots | D17 alert at 80 %; resize the volume via IaC, raise `-volume.max`, restart |
| Certificate expiry | Renewal owned by the internal CA procedure; the checker fails 14 days before expiry |
| Identity file render fails | Keep the previous files; exit 2; never start the gateway without identities (anonymous-only would break writes, not widen access) |
| Image upgrade | Dependabot PR → staging soak ≥ 24 h → prod; rollback = previous digest, data format unchanged within the pinned minor |
