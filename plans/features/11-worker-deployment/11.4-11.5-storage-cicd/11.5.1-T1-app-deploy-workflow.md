## Goal

Two workflows: `e2e.yml` proves the whole stack on a clean runner against `mock-mpt` with no secrets, and `deploy.yml` builds the five images, applies the migration bundle **before** any rollout, deploys staging automatically on `main`, and deploys prod only through the `production` environment with the owner as required reviewer — authenticating with OIDC, never with a long-lived cloud key. Both environments allow branch `main` only and each role's trust pins `job_workflow_ref = <owner>/<repo>/.github/workflows/deploy.yml@refs/heads/main` (D20 H7); the migration connection comes from the environment, masked and never in argv (D20 H11). Rolling Api, Worker stop → start, and a post-deploy smoke decide whether the release stays or is rolled back by digest.

## Design

**`e2e.yml`** — `pull_request` (paths: app, worker, web, compose) and `workflow_dispatch`; `permissions: contents: read`; no secrets; `concurrency` group per ref with `cancel-in-progress`. **This job is the only place the Compose stack is required — CI only, Docker is available on the runner; daily development runs `tools/dev/up.sh` natively and never needs Docker (11 CR-16).**
Jobs: `compose-up` (docker compose with the `09.1.1-T2`/`11.1.1-T1` file, wait for every `service_healthy`) → `e2e` (the Playwright suite `web/e2e` via `npm run e2e` — config and fixtures owned by 10.1.5-T1 — against `mock-mpt`, with the `web` profile up; fail on any red; traces/videos uploaded on failure) (10 CR-1). The compose call is `docker compose -f docker-compose.yml -f web/e2e/docker-compose.e2e.yml --profile web --profile e2e` (override owned by 10.10.2-T1; it sets `NTS_CSP_MEDIA_ORIGINS` and `Storage__PublicServiceUrl` to the host-reachable storage origin, 10 CR-21); `deploy.yml` passes `NTS_CSP_MEDIA_ORIGINS` = the environment's public storage origins to the `web` container (the `openai-stub` service, `OpenAI__BaseUrl=http://openai-stub:8090/v1`, `NTS_E2E_TARGET=container`) and runs `nts-worker flags set youtube_publish on` before the suite; 10.10.2-T1's global setup seeds the owner's YouTube channel row (10 CR-18, WT-W1/WT-W4) → `teardown` (`if: always()`, `docker compose down --volumes`).

**`deploy.yml`** — push to `main` + `workflow_dispatch`; `permissions: contents: read` + `id-token: write` only in the jobs that assume a role; `concurrency: group: deploy-<ref>` without cancel (a rollout must not be interrupted).

| Job | Environment | Runs | Gate |
|---|---|---|---|
| `build` | — | matrix of the five images (`api`, `worker`, `fetcher`, `web`, `mock-mpt`), each from its own Dockerfile, base images by digest; `artifacts/nts-migrate` built once with the SDK | all green |
| `push` | — | push each image, tag `sha-<git sha>`, capture digests as a job output | `build` |
| `migrate-staging` | `staging` | download the bundle, run `./artifacts/nts-migrate` with `ConnectionStrings__Postgres` from the environment, `::add-mask::`-ed at once and never in argv (D20 H11); one-shot, no retry loop | `push` |
| `rollout-staging` | `staging` | Api rolling ×2 gated on `/health/ready` (each host's `web` container is replaced in the same step, gated on `/healthz`; 10 CR-1), then Worker stop → start, then fetcher; deploy **by digest** | `migrate-staging` |
| `smoke-staging` | `staging` | `curl` health/ready + one API read + one mock-mpt render path | `rollout-staging` |
| `prod` (migrate → rollout → smoke) | `production` (required reviewer = owner) | same substeps against prod | `smoke-staging` |
| `smoke-prod` | `production` | the same smoke set plus one `/voices` read (public data only) | `prod` |

- **Auth:** OIDC only, `id-token: write` per environment-scoped job (`11.5.3-T1` owns the trust policy); no cloud key anywhere. Environments `staging` and `production` allow deployment branch `main` only, and each role's trust requires `job_workflow_ref = <owner>/<repo>/.github/workflows/deploy.yml@refs/heads/main` plus the environment claim (D20 H7). Without GitHub environments (E14) `prod` is `workflow_dispatch`-only with the trust bound to `ref:refs/heads/main` + the workflow file (F17/O4).
- **Rollback:** images are immutable → re-run with `deploy_sha` = the previous `sha-<git sha>`, applying rollout + smoke only (migrations are expand-only, 09 NFR-09-6).
- **Smoke** (both environments, no GPU): `GET /health/ready` 200; one authenticated read; `GET /voices` 200 non-empty; on staging only, one mock render reaching a terminal state within `MOCK_RENDER_SECONDS` + 60 s.
- **Locks:** `dotnet restore --locked-mode` before the bundle build; `npm ci` for the web image; `uv sync --frozen` only if a Python component joins the image set.
- **Release assets (D20 H6):** `deploy.yml` publishes none; the only release asset is the node bundle from `node.yml` on `refs/heads/main` (no tag releases).

## Steps

1. Confirm the five image build contexts and their Dockerfile owners (09, 10, 02, `11.1.2-T1`); a missing Dockerfile is a blocker for its owner, never created here.
2. Write `e2e.yml` (three jobs, unconditional `teardown`, SHA-pinned actions) and `deploy.yml` (`build` + bundle, `push` with digest output, `migrate-*`, `rollout-*`, `smoke-*`, `prod` in `environment: production`).
3. Add a `workflow_dispatch` input `deploy_sha` (default `github.sha`, validated against `sha-[0-9a-f]{7,40}`) so a rollback needs no rebuild; secret-manager values arrive through the OIDC role, never as GitHub secrets (`11.5.2-T1` owns the paths); mask any fetched value with `::add-mask::` and pass it through the environment, never argv (D20 H11).
4. Prove the negative paths on a scratch branch: a failing staging smoke must not start `prod`; a `prod` dispatch without approval must not start.
5. Run a real staging and a real prod deploy; record run URLs, digests, migration exit code and smoke output in `docs/runbooks/deployment.md` [INFERENCE: file]. Hand the files to `11.5.3-T1` (hardening) and `11.5.3-T2` (signing/verify step).

## Acceptance checks

- [ ] `e2e.yml` (CI only): all-healthy compose + green e2e against `mock-mpt`; a broken assertion makes it red; `teardown` runs even then; no `secrets.` in the file; nothing in this workflow is required for local development (11 CR-16).
- [ ] Both files: every `uses:` is a 40-char SHA, every job has an explicit `permissions:`, `id-token: write` only in environment-scoped deploy jobs.
- [ ] On `main`: five images built and pushed as `sha-<git sha>`, digests visible in the job output and used by the rollout.
- [ ] Staging order visible in the run graph: `build` → `push` → `migrate-staging` (exit 0, `__EFMigrationsHistory` row added) → `rollout-staging` (Api rolling ×2 gated on `/health/ready`, then Worker stop → start, then fetcher) → `smoke-staging`.
- [ ] The `prod` job waits for the environment approval, then repeats the order plus `smoke-prod`; a failing `smoke-staging` leaves prod untouched.
- [ ] The `staging` and `production` environments allow deployment branch `main` only, and each OIDC role's trust requires `job_workflow_ref = <owner>/<repo>/.github/workflows/deploy.yml@refs/heads/main` plus the environment claim (D20 H7); a run from another branch fails at the role assumption.
- [ ] `migrate-*` read `ConnectionStrings__Postgres` from the environment, masked with `::add-mask::`; no connection string appears in argv or the run log (D20 H11).
- [ ] `deploy.yml` publishes no release asset; the only release asset is the node bundle from `node.yml` on `refs/heads/main` (D20 H6).
- [ ] `workflow_dispatch` with `deploy_sha=<previous sha>` performs rollout + smoke only (no build, no migration) and the service reports the previous digest; the runbook lets a second person release and roll back without reading the YAML.

## Tests

- Real staging deploy (workflow_dispatch) → all jobs green; then a real prod deploy with approval.
- Negative: (a) break one smoke assertion on a scratch branch → `smoke-staging` red and `prod` never starts; (b) `workflow_dispatch` of `prod` without the reviewer → job waits, does not run; (c) `deploy_sha=notasha` → input validation fails before anything runs; (d) dispatch `deploy.yml` from a non-`main` branch → the environment/role assumption fails (D20 H7).
- Rollback rehearsal: dispatch with the previous `sha-*`, assert the running digest returns to the previous value and smoke passes.
- `docker compose config -q` on the e2e path (validates the compose file the job will use) and `docker compose down --volumes` idempotence.
- Migration safety: run the bundle twice against staging → second run exits 0 with no schema change (idempotent bundle behaviour, EF-managed).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| `build` fails for one image, or the migration job fails | Stop before any rollout: never a partial image set, never a rollout "hoping" the migration applied. Fix and re-run; the previous version keeps running |
| Rollout fails at the `/health/ready` gate, or the smoke fails after it | The orchestrator keeps the previous instances; re-dispatch with the previous digest and record the incident (alert via `11.6.2-T1` thresholds) |
| Prod reviewer unavailable | The job waits (environment protection) and is never bypassed; the documented fallback is an owner-approved `workflow_dispatch` |
| GitHub Pro missing (E14), or staging has no GPU node (D1) | Use the F17/O4 fallback (`workflow_dispatch` from `main`, trust bound to ref + workflow), recorded before this task closes; staging smoke stays on `mock-mpt` |
| Rollback | Re-dispatch with the previous `deploy_sha` (rollout + smoke only); migrations are never rolled back (expand-only, 09 NFR-09-6) |
