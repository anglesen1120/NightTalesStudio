# 11.5.3-T1 — Workflow hardening: OIDC, permissions, SHA pinning, branch protection

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 11.5.3 | S (0.5) | Ops | 11.5.1-T1 | 11.2.3-T1 | P · phase 2 (deploy, 11 CR-18) |

## Goal

The CI/CD surface cannot be hijacked into production: deploys authenticate with OIDC to environment-scoped cloud roles and hold no long-lived key; no `pull_request` workflow can read a secret; `pull_request_target` never exists in this repository; every third-party action is pinned by commit SHA and bumped by a bot, not by hand; each job declares the smallest `permissions:` set it needs; `main` accepts changes only through a reviewed PR with green required checks.

## Design

| Control | Implementation | Verified by |
|---|---|---|
| Deploy identity | OIDC only: `permissions: id-token: write` in the environment-scoped jobs; environments allow deployment branch `main` only; trust policy per environment (`repo:<owner>/<repo>:environment:<env>`) **plus** `job_workflow_ref = <owner>/<repo>/.github/workflows/deploy.yml@refs/heads/main` (D20 H7), never `repo:*` | a job that runs without a role fails; a run from another branch fails the assumption; no cloud key exists in any secret |
| PR isolation | `pull_request` workflows get no secrets and no `id-token: write`; `pull_request_target` is forbidden outright | `grep -rn 'pull_request_target' .github/` → empty; fork PR run shows empty secret context |
| Action pinning | every `uses:` at a 40-char SHA with the version in a trailing comment; bumps only via `11.5.3-T3` | `grep -n 'uses:' .github/workflows/*.yml` shows no tag/branch ref |
| Least privilege | explicit `permissions:` per job: `contents: read` default; `id-token: write` only where a role is assumed; `contents: write` only in the release/artifact-publishing jobs | a job without an explicit block fails review; no repository-wide `write-all` |
| Branch protection on `main` | require a PR, require the status checks of `backend.yml`/`web.yml`/`e2e.yml` and the always-running `node-gate` of `node.yml` (D20 H19), require conversation resolution, block force-push and deletion, no direct pushes (admins included) | a direct push to `main` is rejected; a red PR cannot merge |
| Code owners | `.github/CODEOWNERS` gains `.github/workflows/**`, `.github/actions/**`, `infra/**` → TL | a PR touching a workflow requests TL review |

- **Fallback without environments (E14):** the `prod` workflow keeps `workflow_dispatch`-only with the trust bound to `repo:<owner>/<repo>:ref:refs/heads/main` plus the workflow file name (`job_workflow_ref`, D20 H7); branch protection then carries the whole approval weight, and the decision is recorded in `docs/runbooks/deployment.md`.
- **No new secret:** the OIDC role assumption needs no stored credential; the cloud account/role ARNs are non-secret identifiers and live in the workflow as plain values (`11.2.2-T1`/`T4` produce them).

## Steps

1. Inventory every workflow (`backend.yml`, `web.yml`, `e2e.yml`, `deploy.yml`, `node.yml`) and record its triggers, jobs and current `permissions:` in a table in the review PR body.
2. Replace any floating `uses:` with the resolved 40-char SHA; add `# vX.Y.Z` comments for the next bumper (`11.5.3-T3`).
3. Add explicit `permissions:` per job; remove `id-token: write` from every job that does not assume a role and from every `pull_request` workflow.
4. Create the OIDC side: one role per environment with a trust policy matching only that environment plus `job_workflow_ref = <owner>/<repo>/.github/workflows/deploy.yml@refs/heads/main` (D20 H7) (or, in the fallback, only `main` + the workflow file) and the minimum permissions the deploy needs (`11.2.2-T1`/`T4`).
5. Add `.github/CODEOWNERS` entries for `.github/**` and `infra/**`, preserving the existing `AllowLists.cs` line; enable push protection for the paterns the plan can scan (`11.5.2-T1`).
6. Configure branch protection on `main` with the required checks listed in Design; prove it with two negative tests: a direct push and a red PR.
7. Prove the PR isolation: open a fork PR (or a same-repo PR from a branch with a deliberately `echo ${{ secrets.X }}` step) and show the value is empty; revert the probe.

## Acceptance checks

- [ ] `grep -rn 'pull_request_target' .github/` → empty; no `pull_request` job references `secrets.`.
- [ ] Every `uses:` across `.github/workflows/*.yml` is a 40-char SHA; `11.5.3-T3`'s Dependabot config is the only mechanism that changes them.
- [ ] Every job has an explicit `permissions:` block; `id-token: write` appears only in environment-scoped deploy jobs.
- [ ] A deploy job without the OIDC role fails at the assumption step with a clear error, and no credential value appears in its log.
- [ ] Each environment allows deployment branch `main` only and its role trust requires `job_workflow_ref = <owner>/<repo>/.github/workflows/deploy.yml@refs/heads/main` plus the environment claim; a run from another branch cannot assume the role (D20 H7).
- [ ] Direct push to `main` is rejected; a PR with a red required check cannot merge (the required set includes `node-gate`, D20 H19); force-push and branch deletion on `main` are blocked.
- [ ] A PR touching `.github/workflows/**` or `infra/**` requests TL review via CODEOWNERS (the existing `AllowLists.cs` entry still present).
- [ ] Fork PR run shows no secret and cannot assume a role (negative proof recorded).
- [ ] Fallback path documented if environments are unavailable: `prod` = `workflow_dispatch` from `main`, trust bound to ref + workflow file (F17/O4).

## Tests

- Negative proofs: (a) direct push to `main` rejected; (b) red PR cannot merge; (c) fork PR obtains no secret and no role; (d) a workflow edited to use a tag ref fails the review checklist (`grep` assertion); (e) a `deploy.yml` run from a non-`main` branch cannot assume the environment role (D20 H7).
- Positive: a normal PR with green checks merges; a `deploy.yml` staging run assumes the role and completes.
- `grep` assertions from §Acceptance checks run as a shell block in the review PR body (evidence, not a committed test file).
- CODEOWNERS behaviour: a one-line PR touching a workflow file shows the requested reviewer.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Branch protection unavailable on a private repo without Pro (E14) | Use the F17/O4 fallback, document it, and rely on `deploy.yml` refusing to run without a role |
| A pinned action goes stale or vulnerable | `11.5.3-T3`'s grouped weekly `github-actions` updates keep pins current; never relax a pin to a tag as a fix |
| An OIDC trust policy is too broad (`repo:*` or any environment) | Security defect: narrow it and re-run the negative proof |
| A required check is flaky, or a PR job needs a secret | Fix the check (never un-require it); a PR job must not need secrets (D16/D19 S6) — use the fork-safe mock (`11.1.2-T2`) |
| Rollback | Revert the workflow/permission commit; branch-protection values are re-applied from the runbook |
