## Goal

Every artefact that can reach a running environment is signed and described: the five images are signed keyless and carry a syft SBOM, the node bundle's `SHA256SUMS` is signed the same way and shipped with its SBOM, and the deploy refuses to roll out anything whose signature or identity does not verify against this repository's workflow identity. This is the S-phase half of the split high-level 11.5.3-T2 (README §2 F23); Dependabot and lock enforcement are `11.5.3-T3` (P).

## Design

| Artefact | Signed with | SBOM | Publishes to |
|---|---|---|---|
| Five images by digest (`api`, `worker`, `fetcher`, `web`, `mock-mpt`) | `cosign sign` keyless (GitHub OIDC identity, no key material) | `syft packages <image> -o spdx-json` → `cosign attest --predicate` | registry (signature + attestation) |
| `nts-node-<version>.tar.zst` | `cosign sign-blob SHA256SUMS` (keyless) → `SHA256SUMS.sig` + `SHA256SUMS.pem` | `syft dir <extracted bundle> -o spdx-json` → `nts-node-<version>.sbom.spdx.json` | GitHub release assets alongside the bundle |

- **Identity policy (the actual security boundary):** verification requires the certificate identity to match the exact workflow path and ref (`https://github.com/<owner>/<repo>/.github/workflows/deploy.yml@refs/heads/main` for images, `node.yml@…` for the bundle) and the OIDC issuer `https://token.actions.githubusercontent.com`. A signature from any other identity fails, including one from this repository on another ref.
- **Where verification happens:** in `deploy.yml`, immediately after images are pulled by digest and before `migrate-*`/`rollout-*`; the job fails closed if any digest is unsigned or the identity does not match. For the bundle, `11.3.1-T3`'s `nts-node deploy` gains an optional `--verify-signature` step (`cosign verify-blob` with the shipped `.sig`/`.pem`), enabled by default on the operator's Mac where cosign is available.
- **SBOM content:** SPDX-JSON from syft, containing packages only — no environment variables, no file contents beyond names, no secrets. The node bundle SBOM is generated from the extracted layout, before anything is copied onto a node.
- **No keys to manage:** keyless only, so there is no signing key in the secret manager, nothing to rotate, and the log entry in Rekor is the transparency record (`⚠️ confirm the Rekor instance is reachable from CI at install time`).

## Steps

1. Pin cosign and syft versions (and verify their licences against E11) in the workflow; record version + licence + source URL in `docs/runbooks/deployment.md`.
2. Add to `deploy.yml`: after `push`, sign each image by digest, generate the SBOM with syft and attach it as an attestation; store the identity policy once so verification and signing cannot drift apart.
3. Add the verification job/step that runs before any `migrate-*` step and fails closed with a message naming the offending digest.
4. Add to `node.yml`: sign `SHA256SUMS` as a blob, generate the bundle SBOM, attach `SHA256SUMS.sig`, `SHA256SUMS.pem` and `nts-node-<version>.sbom.spdx.json` to the release.
5. Hand the verification step to `11.3.1-T3` for `nts-node deploy --verify-signature`; document the exact command in `docs/runbooks/node-deploy.md` (owner `11.3.1-T3`).
6. Prove the negative: re-tag an image digest with a signature from a scratch fork (or verify with a wrong identity regexp) → the deploy step fails and no rollout starts. Prove the positive: a normal staging deploy verifies and proceeds.
7. Record the SBOM location for each artefact in `docs/runbooks/deployment.md` so a future CVE question can be answered without rebuilding.

## Acceptance checks

- [ ] `cosign verify --certificate-identity-regexp '<exact workflow path>@refs/heads/main' --certificate-oidc-issuer https://token.actions.githubusercontent.com <image>@<digest>` succeeds for all five digests of a `main` deploy.
- [ ] `cosign verify-blob --signature SHA256SUMS.sig --certificate SHA256SUMS.pem --certificate-identity … --certificate-oidc-issuer … SHA256SUMS` succeeds for a released bundle.
- [ ] An unsigned digest (a locally built image pushed on a scratch tag) fails verification and no rollout job starts, and a signature from a fork/other ref fails against the identity policy (both negative proofs recorded, each naming the digest).
- [ ] The verification step runs before `migrate-*` in the run graph, for staging and prod.
- [ ] SBOMs exist for the five images and the bundle; `jq '.spdxVersion, (.packages|length)'` returns a version and a non-zero count; no env-var or key-like entry inside (`grep -c 'BEGIN .*PRIVATE KEY\\|KEY=' ` → 0).
- [ ] cosign/syft versions are pinned and their licences recorded (E11: Apache-2.0) with the checked date; no signing key exists in the secret manager.
- [ ] The runbook documents how to fetch each SBOM and re-verify a signature months later.

## Tests

- Positive: a normal `main` deploy — every `cosign verify` passes, rollout proceeds.
- Negative 1: an unsigned digest in the deploy input → verification fails, rollout does not start.
- Negative 2: verification with a wrong identity regexp (another ref) → fails.
- Bundle: `cosign verify-blob` on the release assets from a clean machine; then `nts-node deploy --verify-signature` on staging.
- SBOM sanity: `syft` output parses as SPDX-JSON and lists the expected runtime package (e.g. `Microsoft.Data.Sqlite` for the adapter image, `fastapi` for the proxy image) — proves the SBOM describes the right artefact.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Rekor/Fulcio unreachable from CI | Signing fails closed and the deploy stops; retry, and if it persists escalate — never switch to a long-lived key without a TL decision |
| The registry cannot store attestations | Fall back to a release asset / OCI artifact tag for the SBOM (recorded in the runbook); the signature still goes to the registry |
| A digest is re-signed by a legitimate re-run | `cosign sign` is idempotent per digest; a changed digest is a new artefact and is verified on its own |
| An urgent rollback is blocked by verification | The previous digest is already signed (images are immutable) so it verifies normally; an unsigned artefact is never an emergency path |
| SBOM generation fails | Treat as a failed artefact: no SBOM ⇒ no deploy (per-artefact, not per-repository) |
| cosign/syft licence is not permissive at the pinned version | Stop and escalate (E11 says Apache-2.0; re-check the installed version's licence) |
| Rollback | Remove the verify step only by an explicit owner decision recorded in the runbook; artefacts and SBOMs stay published either way |
