## Goal

Configure and prove recovery for `prod`: PITR with WAL 7 d and daily snapshots 30 d; the `nt-media-<env>` → `nt-backup-<env>` copy 30 d **owned by 11.4.1-T1** (asserted here, never re-implemented) [RULED — README §10 T53] (D20 H9); `DP_KEK` exported once offline; then a monthly **timed** drill into a **scratch** DB that re-applies every `data_deletion_requests` row completed after the backup timestamp before the restored system serves data. Targets **RPO 15 min / RTO 4 h** (plan.md §10 Open items). Runbook: `docs/runbooks/restore-drill.md`.

- 11.5.2-T1 — secret names `nts/<env>/<NAME>`: `DB_CONNECTION`, `DP_KEK`, `STORAGE_*` (D15).
- Facts E10, F27, D17, `plans/00-overview.md:412` (plan.md §2). Conventions 01 D9: `set -euo pipefail`, shellcheck clean, idempotent, exit 0 ok / 1 check failed / 2 usage-environment; Python stdlib only; secrets never in argv.

## Design

Tiers (D17): WAL 7 d → PITR to any instant; daily snapshots 30 d → provider restore into a new instance; the `nt-media-<env>` → `nt-backup-<env>` copy — media blobs, 30 d, **applied by 11.4.1-T1's replication rule** (provider replication, else a provider-run scheduled copy; put-only replication credential and object lock where available) and only asserted here [RULED — README §10 T53] (D20 H9); `DP_KEK` offline, indefinite. Deliberately **not** backed up: adapter durable store (lost-task rule, F27), node disks/releases (rebuilt by `nts-node deploy`, D12/F27), logs (journald, 7 d, D8).

- `DP_KEK` is never in a backup: not in the DB, not in a bucket, not in the repo, not reproduced in the runbook. Without it Data Protection payloads cannot be decrypted — the accepted boundary.
- Deleted data ages out of every tier within 30 days (13's promise), so the retention values are asserted, never adjusted ad hoc.

**Drill contract**, in order on the scratch instance: (1) refuse any host that is not the declared scratch instance → **exit 2**; (2) record `now`, read archive lag, fail if > 15 min; (3) restore to `--target-time`; (4) re-apply each `data_deletion_requests` row with `completed_at > --target-time`, ordered by `completed_at`, idempotently, via 13's path; (5) smoke read — aggregate counts, one live object readable, one deleted object still absent; (6) print the elapsed time (measured RTO) and append the runbook's timed row; (7) exit 0 all checks pass / 1 any check failed.

**Scripts** (Bash, 01 D9, idempotent): `tools/ops/restore-drill.sh` [INFERENCE: path] (`--env`, `--target-time`, `--scratch-host`, `--self-test`, `--dry-run`; secrets via `--env-file`/stdin) and `tools/ops/verify-backups.sh` [INFERENCE: path] (retention values, archive lag, `DP_KEK` absence).

## Steps

1. Assert the IaC output for `prod`: PITR on, WAL 7 d, snapshots daily/30 d, `nt-backup-<env>` lifecycle 30 d. A differing value is a CR to 11.2.2, never a local patch; [RULED — README §10 T53] (D20 H9) the `nt-media-<env>` → `nt-backup-<env>` copy itself is 11.4.1-T1's replication rule — asserted, not written here.
2. Prove WAL archiving is live (read the lag twice with a gap and confirm it tracks); a stopped archive must fail the check.
3. Confirm 11.4.1-T1's copy rule with a marker object under `nt-media-<env>` appearing in `nt-backup-<env>`, then delete the marker [RULED — README §10 T53] (D20 H9).
4. Export `DP_KEK` once to the owner's offline store; verify its absence from the bucket listing and the repo tree; record the export date only.
5. Write the runbook: prerequisites, exact commands, the scratch-instance rule, the deletion checklist, the timed table (date, target time, RTO, deletions re-applied, result) with a filled example.
6. Run the first drill **immediately** and correct the runbook where reality differed; then set the monthly operator reminder — [DECISION] no Hangfire job: a schedule able to overwrite a database has no place in the Worker (D17 makes the drill operator-run).
7. Seal the checks into `verify-backups.sh` and hand both script paths to `node.yml`'s shellcheck step (11.5.1-T2 owns that workflow; no fork).

- [ ] After the drill a deleted object is still absent and a live object is readable in the scratch environment.
- [ ] `DP_KEK` material is in neither the backup bucket listing nor the repo tree.
- [ ] Every fenced command block in the runbook passes `bash -n` (shellcheck where it is a full script).

## Tests

- `tools/ops/restore-drill.sh --self-test` [INFERENCE] — fake environment (stdlib fixture or a scratch container in `e2e.yml`): scratch guard (exit 2), archive-lag gate (exit 1 above target), early-abort path, and deletion re-application idempotency (apply twice, compare a resulting-state hash).

- Manual (acceptance): one operator-executed drill against the real `prod` env with the timed row recorded.

## Failure handling and edge cases

- **Archive stopped / lag above RPO** → exit 1 before restoring; the runbook's first fix step is "confirm the archive is running", because a restore from a broken archive silently loses the tail.
- **Target time older than the oldest base backup** → exit 2 with the supported window printed.
- **Deletion completed after the target time but before now** is in scope: the enumeration's upper bound is `now`.
- **Re-application fails halfway** → the failing request id is reported, exit 1, the scratch instance is kept for inspection and recreated on the next (idempotent) run.
- **Missing/empty declared scratch name** → usage error (exit 2); the guard is never skipped.
- **`DP_KEK` unreadable at restore time** → recorded as a runbook-step failure; encrypted payloads are then not asserted.
- **Scratch cost/space** → created from the snapshot, destroyed after the drill, never grown from prod; a failed destroy is a reported cost leak.

## Notes

- F27 is why the adapter store and node disks are not backed up: adapter state is disposable by the lost-task rule, a node is rebuilt by `nts-node deploy`.
- The 30-day figure is a privacy commitment (13, `00-overview.md:412`); changing it is a cross-plan change. RPO/RTO are this plan's targets — different owner numbers change only the runbook constants and the acceptance values above.
- Rollback: the task creates scratch resources and asserts configuration; deleting the scratch instance and re-running the drill from a snapshot is always safe.
