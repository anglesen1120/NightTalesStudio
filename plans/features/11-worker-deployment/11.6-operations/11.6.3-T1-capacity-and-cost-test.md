# 11.6.3-T1 — 20-render capacity and cost test on the prod node

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 11.6.3 | M (1.0) | Ops/BA | 11.3.1-T3, 11.3.2-T2, 09.6.3-T1 | 12.1.1 soft, 12.1.1-T1 | P · phase 2 (deploy, 11 CR-18) |

## Goal

Measure the first GPU node with 20 renders (vi/en, 5–15 min, both aspects) at concurrency 1/2/4 before public autopilot ([RULED — README §10 T61] (D20 H15) one discarded warm-up render first, and cell 1 carries 2 renders at the maximum script length): per-stage wall times, GPU/CPU/RAM/VRAM peaks, failures, the NFR-05-1 check (≤ 20 min per 10-min video, P13) and compute cost per video (`node price/h ÷ videos/h`, dated 11.2.1 page). Outputs: DECISIONS §10.4, 12.1.1, and the final `NTS_MPT_MAX_CONCURRENT`, `VIENEU_MAX_STREAMS`, `Adapter:CheckConcurrency`, `Adapter:CheckTimeoutSeconds`, `ADAPTER_MPT_THREADS`, codec (D9, T4).

## Inputs

- **11.3.1-T3** (node from a versioned bundle, `gpu-smoke.sh` green), **11.3.2-T2** (firewall, pinned TLS, egress verified, D12), **09.6.3-T1** (dispatch path — renders go through the platform), **11.2.1-T1** (dated provider price page), **11.6.2-T1** (dashboards + cost/day rule, so the run is watched).
- Contract: **05 D4** stages (`queued · voice · subtitles · images · assembling · checking · done`, `output.narration_seconds`, `percent` never decreasing); **05 D15 P5/P6/P7** (`NTS_WHISPER_DEVICE=cuda`, `NTS_WHISPER_COMPUTE ∈ {float16, int8_float16}`, `ADAPTER_MPT_THREADS = max(1, floor(cpu_cores ÷ max_concurrent_tasks))`, exceeding the measured concurrency needs a TL ruling, a poll timeout is **not** a failure).
- Limits re-set here: **D6/F20** (`Adapter:CheckConcurrency` 1, `CheckTimeoutSeconds` 900, post-processing competes for CPU); **D9/T4/E4** (codec stays `libx264` unless an `h264_nvenc` run passes 05 D10 **and** is faster); **D10/K8/F28/E2** (`VIENEU_MAX_STREAMS ≥ NTS_MPT_MAX_CONCURRENT`; 16 streams ≈ 0.9–1.1 GB VRAM; ≥ 16 GB VRAM required, 24 GB preferred; whisper large-v2 fp16 ≈ 4.5 GB).

## Design

20 renders split 8/6/6 across concurrency 1/2/4 (this plan's allocation; both aspects per cell, vi/en spread). [RULED — README §10 T61] (D20 H15) One discarded **warm-up** render runs before cell 1 (not counted among the 20) and **cell 1 includes 2 renders at the maximum script length** (20,000 code points, 05 D3). Concurrency 1 = clean baseline and VRAM floor; 2 = intended steady state; 4 = headroom check where post-processing, TTS and whisper compete.

- **Real conditions**: concurrency is the node's `max_concurrent_tasks`/adapter capacity per cell, jobs go through normal Worker dispatch (wall times include every platform hop); stories span 5–15 min with renders at both ends; English only if the vi/en pair exists (04 O2). Sampling: 1 s `nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total,temperature.gpu` + CPU/RAM from `/proc`, timestamped per task (peaks, p95); stage timings from polling `GET /v1/renders/{task_id}` (2 s) via the Worker client, never MPT directly.
- **NFR-05-1 normalized**: `wall_time ≤ 20 min × (narration_seconds ÷ 600)`, `narration_seconds` from `render-status.v1.output` (measured `audio.mp3`, 05 D4) — a 5-min video is judged at ≤ 10 min; a miss is recorded, never averaged away.
- **Cost per video** = `node_price_per_hour ÷ videos_per_hour`, throughput from the steady-state cell (2, incl. queueing); dated page + arithmetic in the report, storage egress separate (`11:232`).
- **Codec A/B (T4)**: one extra `h264_nvenc` set, accepted only if it passes 05 D10 **and** beats `libx264`; else `libx264` stays with the reason recorded (E4 ⚠️).
- **Abort**: infrastructure failure (node unreachable, TLS/key mismatch, disk ≥ 85 %), VRAM exhaustion, or a render failing twice at one concurrency → stop the cell, record, re-run only after a fix. Twenty is a cap, not a number to reach by repeating failures.

## Steps

1. Freeze the node (bundle version, `pins.env`, driver/ffmpeg versions, GPU model/VRAM, config defaults — D9/D12) and write the 20 run specs as files for reproducibility.
2. Verify the driver on **staging against mock-mpt** (no GPU, no cost): submit, poll, parse `render-status.v1`, write the report columns.
3. Run one discarded warm-up render, then cells 1 (8, incl. the 2 at the maximum script length), 2 (6), 3 (6), with sampling on, changing only the concurrency config [RULED — README §10 T61] (D20 H15); capture stage timelines, peaks, failures and the per-render NFR-05-1 verdict.
4. Run the `h264_nvenc` A/B set; apply the T4 rule.
5. Compute cost/video from the dated price and steady-state throughput; write the report.
6. Apply and record the final values (config change + unit restart + `gpu-smoke.sh` + adapter health 200) in DECISIONS §10.4, 12.1.1 and `pins.env`, with `Adapter:CheckTimeoutSeconds` = 2 × the longest measured `checking` time [RULED — README §10 T62] (D20 H15); re-check the 11.6.2-T1 thresholds this run can invalidate.

## Failure handling and edge cases

- **Content failures** (moderation, TTS, assembly): count them, continue while the share stays under the 20 % alert line (D17), and report them separately from infrastructure failures.
- **`h264_nvenc` absent** (E4 ⚠️): the A/B fails at the adapter's P5 codec check → keep `libx264`, record "encoder unavailable in the apt ffmpeg build", close the question for P.
- **VRAM exhaustion at 4×**: whisper (E2, ≈ 4.5 GB fp16 large-v2) + VieNeu (~1.1 GB at 16 streams, K8) + NVENC/ffmpeg; the peak is recorded and the cell dropped, which then justifies the lower `max_concurrent_tasks` (05 P6).
- **Poll timeout is not a failure** (05 P7): resume with the task id, never re-submit while MPT reports `state 4`.
- **Node restart mid-cell** invalidates the cell (MPT keeps task state in memory, in-flight tasks are lost) — re-run those renders once on a clean node.
- **Sampling gaps at 4×** are reported, never zero-filled; **cost overrun** is capped by the 20 + A/B set and watched against the D17 cost/day rule (P8).
- **Post-processing contention at 4×** (D6/F20): the `checking` wall time sets `Adapter:CheckTimeoutSeconds` — [RULED — README §10 T62] (D20 H15) **`Adapter:CheckTimeoutSeconds` = 2 × the longest measured `checking` time**; a timeout that is too tight is raised explicitly, never silently.
