# 11.6.4-T1 — One-shot `nts-admin` job image

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 11.6.4 | S (0.5) | Ops | 11.5.2-T1 | 09.10.7-T1, 08.2.2-T2 | S · M2 |

## Goal

`09.10.7-T1`'s owner break-glass CLI (`nts-admin owner recover|restore|resolve`) needs a host to run in: this task builds the versioned container image and the platform job manifest that runs it as a **one-shot** operator job — no long-running process, no listening port, no API host — reading its secrets from the environment/secret manager the same way every other P component does (11 D15). Added by `09 W3 CR-6` (F16, D16 of the 09 wave-3 review): 09.10.7-T1's CLI commands/handlers are fully specifiable without this task, but its host wiring cannot close until this image and job manifest exist.

- `09.10.7-T1-nts-admin-break-glass-cli.md` (09 wave 3, S-phase, signed as a soft dependency here) — the `NightTales.Worker`-style CLI binary this task packages; `[OPEN] (W3 CR-6, F16)` there: "the host project/binary this CLI ships in… depend on plan 11's `11.6.4-T1`… which does not exist on disk yet" — this file closes that gap from the 11 side.

## Design

- Image `nts-admin:<version>` (`<version>` = `<yyyymmdd>-<git sha 7>`, same scheme as the node bundle, D12): `dotnet publish -r linux-x64 --self-contained` of the `NightTales.Worker` project built with the `nts-admin` entrypoint (09.10.7-T1's CLI verb host), pushed to the same container registry as `api`/`worker`/`fetcher`/`web` (README D15), tagged `sha-<git sha>` + digest.
- Platform job manifest `infra/jobs/nts-admin.yml` [INFERENCE: path]: a one-shot job definition (provider-native batch/task run, not a Deployment/Service) — no exposed port, `restart: never`, env from `nts/<env>/api/<NAME>` (this CLI reuses the API role's secret path; it is not a new principal) plus `nts/<env>/shared/<NAME>` (`DB_CONNECTION`, `DP_KEK`), `command: ["nts-admin", "<verb>", "--email", "<e>", ...]` supplied at invocation time by the operator, never baked into the image.
- Invocation: the operator runs the job over the VPN/bastion (same access path as `nts-node deploy`, D12), passing the verb and arguments as job parameters; the job's own stdout/exit code is the only feedback channel (no HTTP route exists for any `nts-admin` verb, D16 of 09's review) — this task does not add one.
- No new secret principal: the job assumes the existing API-role secret path (H3 of D20 already scopes `nts/<env>/api/<NAME>`); no `nts/<env>/node/*` or `nts/<env>/worker/*` path is touched.

## Steps

1. Add the `nts-admin` publish target to the `NightTales.Worker` project (or a thin wrapper project referencing it) so `dotnet publish` produces the self-contained CLI binary alongside the existing Worker binary — no duplicate Application-layer code (D2 reuse rule).
2. Add the `Dockerfile.admin` (or a multi-stage target in the existing Worker `Dockerfile`) building the `nts-admin` image; wire it into `node.yml`/`backend.yml` (11.5.1-T1/T2's existing CI conventions) as a new build+push step, SHA-pinned actions (D16).
3. Write `infra/jobs/nts-admin.yml`, the one-shot job manifest, parameterised by `env` and the CLI arguments; no listening port, `ReadWritePaths=` none beyond the process's own temp dir.
4. Document the operator invocation in `worker-node/bin/README.md` or the ops runbook: how to run the job over the VPN/bastion, and that output is the only feedback channel.
5. Confirm with `09.10.7-T1` (soft dependency, wave-3) that its CLI entrypoint signature matches what this image invokes; no assumption about its exit codes beyond what 09.10.7-T1 itself defines (`0/2/3`, D16 verbatim).

## Outputs

- New: `Dockerfile.admin` (or a Worker `Dockerfile` stage), `infra/jobs/nts-admin.yml`.
- CI: one new build+push job in the existing `node.yml`/`backend.yml` pipeline (11.5.1-T1/T2), reusing their SHA-pinned-action and OIDC conventions — no new workflow file.
- No new secret path, no new table, no new route.

## Acceptance checks

- [ ] `docker build` produces the `nts-admin` image from the same source tree as the Worker, with no listening port declared (`docker inspect` shows no `ExposedPorts`).
- [ ] The job manifest runs to completion for a no-op verb against a scratch/staging env and exits 0; the container leaves no long-running process (verified: the job's pod/task completes, not "running", within the provider's job-completion window).
- [ ] Env is populated only from the secret manager (`nts/<env>/api/<NAME>`, `nts/<env>/shared/<NAME>`); no CLI argument or image layer contains a plaintext secret (`docker history` scan finds none).
- [ ] The CI job builds and pushes the image with the same tag scheme (`sha-<git sha>` + digest) as the other four images, using SHA-pinned actions.
- [ ] Running the image directly with no arguments prints usage and exits non-zero (never silently succeeds).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| 09.10.7-T1 not yet landed (wave-3 soft dependency) | this task ships the image/manifest against the CLI's already-specified Application-layer contract (commands/handlers); the entrypoint wiring is a thin `Main` that resolves those handlers, so it can be written and tested independently, then wired once 09.10.7-T1's binary target exists |
| Operator runs the job against the wrong env | the job manifest is parameterised per env and reads only that env's secret path; there is no cross-env credential, so a wrong-env run fails on missing/invalid secrets rather than mutating another environment |
| Image contains a stale secret baked at build time | rejected by design: the image never receives secrets at build time, only at job invocation (env injection), and the `docker history` scan is a CI gate |
| Job left "running" past its expected window | the job platform's own timeout/kill applies (provider default); no code in this task keeps the process alive past the CLI's own return |
