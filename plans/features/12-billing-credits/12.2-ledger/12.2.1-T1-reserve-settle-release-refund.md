# 12.2.1-T1 — ICreditLedger (CreditService): reserve, settle, release and refund under the credit_accounts row lock

## Goal

Ship the append-only credit ledger and the one implementation allowed to move credits: `CreditService` implementing 02's `ICreditLedger` port (D1/D2, BR3). Reserve a quote inside the paid command's transaction, settle the actual read from `usage_records` by `reservation_id`, release the difference, refund on failure — serialised by `SELECT … FROM credit_accounts WHERE user_id = @u FOR UPDATE` and guarded by unique `credit_ledger.idempotency_key` values so any retried delivery is a no-op. Replace the P `MeteringOnlyCreditLedger` DI registration. The port grows here by `GrantAsync` and `GetOpenReservationAsync`; `ExpireAsync`/`VoidPaymentLotsAsync` are added by 12.6.1-T1 (BR29; see Notes).

## Design

Port members declared and implemented here (the three existing ones keep 02 D1's exact shapes):

```csharp
Task<ErrorOr<ReservationId>>       ReserveAsync(Guid userId, CreditOperation operation, Guid referenceId, UsageBound bound, CancellationToken ct);
Task<ErrorOr<SettleResult>>        SettleAsync(ReservationId reservationId, CancellationToken ct);   // reads usage_records by reservation_id
Task<ErrorOr<Success>>             RefundAsync(ReservationId reservationId, string reason, CancellationToken ct);
Task<ErrorOr<LotId>>               GrantAsync(Guid userId, CreditLotSource source, long amount, DateTimeOffset expiresAt, CreditGrantReference reference, CancellationToken ct);
Task<ErrorOr<ReservationSnapshot>> GetOpenReservationAsync(Guid referenceId, CancellationToken ct);  // 12.8.3-T2 dispatch gate
```

`SettleResult(long Charged, long Released)`; `CreditLotSource ∈ { Trial, Bonus, Promo, Purchase, Adjust }`; `ReservationState ∈ { Open, Settled, Refunded }`; `LotConsumption(LotId LotId, long Amount)`; `ReservationSnapshot(ReservationId Id, Guid UserId, CreditOperation Operation, long Amount, PriceVersionVersion PriceVersion, ReservationState State, IReadOnlyList<LotConsumption> Lots)`.

**Sign convention (BR18).** `credit_ledger.amount` is signed from the user's balance view: `reserve −R`, `settle −C` (`C = min(R, max(floor, credits(actual)))`), `release +R` (the WHOLE hold, exactly, written only together with `settle`, same transaction), `refund +R` with no settle row, `grant/bonus/purchase +`, `expire −remaining`, `adjust ±`; per reservation `SUM(amount)` = −R open / −C settled / 0 refunded; DTO values derived per reservation group (`quoted = Σ|reserve|`, `charged = Σ|settle|`, `returned = quoted − charged`, `= quoted` when refunded).

One transaction per command (the lock is taken inside it, never in a session scope):

```sql
INSERT INTO credit_accounts (user_id) VALUES (@userId) ON CONFLICT (user_id) DO NOTHING;
SELECT user_id FROM credit_accounts WHERE user_id = @userId FOR UPDATE;          -- serialise

SELECT COALESCE(SUM(amount), 0) FROM credit_ledger WHERE user_id = @userId;      -- balance is derived
INSERT INTO credit_ledger (id, user_id, kind, amount, price_version, reference_type, reference_id, idempotency_key)
VALUES (@reservationId, @userId, 'reserve', -@reserve, @priceVersion, @operationWire, @referenceId, 'reserve:' || @referenceId || ':' || @lotId)   -- one ledger row per consumed lot (BR19)
ON CONFLICT (idempotency_key) DO NOTHING;

SELECT id, remaining FROM credit_lots WHERE user_id = @userId AND voided_at IS NULL
  AND expires_at > now() AND remaining > 0 ORDER BY expires_at ASC, id ASC FOR UPDATE;   -- 12.6.1 owns the full source_rank split

SELECT operation, input_tokens, cached_input_tokens, output_tokens, image_count, gpu_seconds, estimated
FROM usage_records WHERE user_id = @userId AND reservation_id = @reservationId;   -- settle input
```

- Reservation id = the `id` (UUIDv7) of the `reserve` row; open lookup = `kind='reserve' AND reference_id = @referenceId AND NOT EXISTS (settle|refund row with reference_id = reserve.id)`, served by `credit_ledger (reference_type, reference_id)`.
- Lifecycle `open → settled | refunded` once. No open reservation ⇒ `reservation_missing`: increment `billing_reservation_missing_total`, log ids, alert via 11.6.2-T1, **no** movement (BR4).
- `charged = Charge(reserve, actual, p, floor)`; `released = reserve − charged` is a **derived** value only (`returned = quoted − charged`, BR18) — the rows themselves carry `settle` `−C` per lot and `release` `+R` per lot (the whole hold, written only together with `settle`, in the same transaction). Over-run is capped at the reserve with the gap in `billing_provider_loss_total{reason="rate_or_limit"}` + alert; settle snapshots the reservation’s `usage_records` at `settled_at` and a row arriving **after** that is attributed to `credit_ledger (reference_type = 'platform_loss')` (F25/BR30), never re-charged.
- Rows (one per lot, BR19/F24): `settle`/`release`/`refund` carry `reference_type='reservation'`, `reference_id = reservationId`, `lot_id` = consumed lot, keys `settle:{reservationId}:{lotId}`/`release:{reservationId}:{lotId}`/`refund:{reservationId}:{lotId}`; `amount` follows BR18 (`settle` = `−C` on that lot, `release` = `+R` on that lot — the whole hold, written only together with `settle` in the same transaction; `refund` = `+R` with no `settle` row).
- `GrantAsync` writes one `credit_lots` row (`source`, `remaining = amount`, `expires_at`, `payment_id` from `CreditGrantReference`) plus the matching `grant`/`purchase`/`adjust`/`bonus` ledger row, keyed by the caller's reference (`grant:trial:{userId}`, `grant:adjust:{grantRequestId}`, `grant:promo:{promoRedemptionId}`, `purchase:{paymentId}`, `bonus:{paymentId}`). `GrantAsync` rejects a non-positive `amount` (`negative_amount` 400); negative adjustments are `AdjustAsync`'s job — it consumes lots in spend order and returns `insufficient_credits` 402 when the balance would cross zero (F04, 12 CR-23/24).
- DI: the `ICreditLedger` registration switches `MeteringOnlyCreditLedger` → `CreditService`; no caller signature changes.
- Emits `credit_balance_changed.v1 { userId }` (`[OutboxEvent]`) and `CreditBalanceChanged { userId }` (`IRealtimeNotifier`, ids only) inside the movement transaction — this is the only place credits move.
- Migrations (this task owns exactly these three — BR20): `_12_CreditAccounts` (`credit_accounts`, incl. `review_required_at`/`review_note`, CR-14), `_12_CreditLedger` (+ `ux_credit_ledger_idem`, `ix_credit_ledger_user_created`, `ix_credit_ledger_reference`), `_12_CreditLots` (minimal `credit_lots` with `CHECK (remaining >= 0 AND remaining <= amount)`, `ix_credit_lots_user_expiry`, `ix_credit_lots_payment`) and `ix_usage_records_reservation`. This task does **not** create `credit_grant_requests` (BR20: owned by 12.5.1-T1).
- i18n/D18: no server string; client copies `billing.errors.insufficient_credits` (vi "Bạn không đủ credit cho thao tác này" / en "Not enough credits for this action") and `billing.errors.reservation_missing` (vi "Không tìm thấy lượt đặt trước, không trừ credit" / en "No open reservation found, nothing was charged").
- Observability: `billing_reservation_missing_total`, `billing_provider_loss_total{reason ∈ rate_or_limit, late_usage, negative_write}`, `billing_balance_liability_credits`; logs ids-only (`userId`, `reservationId`, `referenceId`, `operation`, `charged`, `released`).

## Steps

1. Declare the five port members in `Application/Abstractions/Billing/ICreditLedger.cs`, reusing `ReservationId`, `LotId`, `UsageBound`, `CreditOperation`, `PriceVersionVersion` — no new synonym.
2. EF configuration + the three migrations `_12_CreditAccounts`, `_12_CreditLedger`, `_12_CreditLots` (BR20 — this task owns them; `credit_grant_requests` belongs to 12.5.1-T1); register `credit_accounts` **outside** the tenant filter with a comment (F10), keep `credit_ledger`/`credit_lots` `IUserOwned`.
3. Domain: `CreditLot` consumption helper (`expires_at ASC, id ASC` here), `ReservationState` resolution over the ledger family, `CreditLedgerKind` constants (`grant`/`bonus`/`purchase`/`reserve`/`settle`/`release`/`refund`/`adjust`/`expire`).
4. `CreditService.ReserveAsync`: lock → derived balance → reserve insert → return `ReservationId`.
5. `CreditService.SettleAsync`: open lookup → usage read by `reservation_id` → `Charge`/cap/alert → per-lot `settle` + `release` rows → `SettleResult`.
6. `CreditService.RefundAsync`: open lookup → full reserve back to the same lots (`kind='refund'`) → close; a second call is `reservation_missing`.
7. `CreditService.GrantAsync` (positive lots only — lot + ledger row, caller reference key) and `AdjustAsync` (negative admin adjustments: consumes lots in spend order, one `adjust` row per lot, no lot created — 12 CR-23) and `GetOpenReservationAsync` (snapshot with lots for the 12.8.3-T2 gate).
8. Switch the DI registration; keep `MeteringOnlyCreditLedger` compiled only until 02 CR-5 lands its removal.

## Acceptance checks

1. **Given** a user with 100 credits and a render bound quoting 203, **When** `ReserveAsync` runs, **Then** it returns `insufficient_credits` (402) and writes no ledger row.
2. **Given** 20 concurrent reserves of 50 on a 600-credit balance, **When** all complete, **Then** at most 12 succeed, `SUM(credit_ledger.amount) ≥ 0`, and every failure is `insufficient_credits`.
3. **Given** an open reservation (`quoted = 203`, `SUM(amount) = −203`) and `usage_records` charging 192 credits, **When** `SettleAsync` runs, **Then** `SettleResult.Charged = 192`, `Released = 11`, one `settle` row (`−192`) and one `release` row (`+203`, the whole hold, same transaction) exist, the reservation’s `SUM(amount)` is `−192`, and the derived DTO values are `quoted = Σ|reserve| = 203`, `charged = Σ|settle| = 192`, `returned = quoted − charged = 11` (BR18).
4. **Given** that reservation, **When** `SettleAsync` runs again, **Then** nothing moves, `billing_reservation_missing_total` increments once and an 11.6.2-T1 alert is raised.
5. **Given** a refunded reservation, **When** `SettleAsync` or `RefundAsync` runs again, **Then** both return `reservation_missing` with no movement (BR4).
6. **Given** two concurrent deliveries of the same settle, **When** both run, **Then** exactly one movement is visible (the second is `ON CONFLICT DO NOTHING`).
7. **Given** actual usage above the reserve, **When** settle runs, **Then** `Charged == reserve`, `Released == 0` (rows per BR18: `settle` `−R`, `release` `+R`, so `returned = 0`), and `billing_provider_loss_total{reason="rate_or_limit"}` grows with an alert.
8. **Given** a `usage_records` row inserted after its reservation was settled, **When** a later settle for a different reservation runs, **Then** the late row charges nothing to the closed reservation.
9. **Given** a failed job, **When** `RefundAsync(reservationId, "job_failed", ct)` runs, **Then** the full reserve returns and each lot's `remaining` is restored in the same transaction.
10. **Given** an admin `adjust` of −5,000 on a 100-credit balance, **When** `AdjustAsync` runs, **Then** it returns `insufficient_credits` (402 — pinned catalogue code, 12 CR-24; was 409) and writes nothing (F04).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| No open reservation for the reference/reservation id | `reservation_missing`; metric + alert; **no** movement (BR4) |
| Duplicate `idempotency_key` | `ON CONFLICT DO NOTHING` ⇒ success-shaped no-op returning the first result |
| `SUM(amount)` would go negative | reject `insufficient_credits` (402 everywhere — user path and negative `adjust`, 12 CR-24); never write |
| `usage_records` under a different `price_version` than the reserve | charge with the **reserve's** version (FR-12-2); log the mismatch |
| No `usage_records` rows at all | charge the operation/tier floor and mark the usage block `estimated = true` |
| Lot expired/voided between reserve and settle | this task logs + `billing_provider_loss_total` (the `remaining <= amount` check fails); the full re-removal rule (`expire:{lotId}:{reservationId}` / `void:{paymentId}:{lotId}`) is 12.6.1-T1 (F06) |
| Two operations reserve for the same `referenceId` | the unique lot-scoped `reserve:{referenceId}:{lotId}` keys return the same reservation (BR19) — a caller bug, alerted |
| Concurrent settle and refund | both take the account lock; the loser sees the closed reservation ⇒ `reservation_missing` |
| Postgres `40001` (deadlock) | pinned lock order avoids it; a surfaced error becomes `concurrency_conflict` 409 |
| DB failure mid-transaction | the command rolls back whole (one `SaveChangesAsync`) — no partial movement |
