# 12.2.2-T1 — Balance and history queries: GET /credits/balance and GET /credits/ledger

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.2.2-T1 | S (0.5) | BE | 12.2.1-T1 | 09.10.5-T1 (soft, `GetBalanceQuery` for admin user detail) (09 W3 CR-13), 10.8.3-T1, 10.8.1-T0 (10/08 CR-hand-off) | S · M2 |

## Goal

Serve the two read routes the credits UI runs on, with the frozen DTOs of README §3.1: `GET /credits/balance` (`CreditBalanceDto { total, free, purchased, nextExpiry }`) and `GET /credits/ledger` (one history line per reservation `groupId`, keyset-cursor paged, max 100). Both are **always on** (not behind `billing_enabled`) and return only the caller's own rows. `GetBalanceQuery { UserId }` is the single balance read port — 09.10.5-T1's admin user-detail bundle reuses it under the admin policy; no second read port is created (README D2).

## Inputs

- README D2 (`GetBalanceQuery { UserId }`), D6 (balance from live lots, never a cached column), D17 (`credit_balance_changed.v1 { userId }`, indexes `credit_ledger (user_id, created_at DESC, id DESC)`, `credit_lots (user_id, expires_at) WHERE voided_at IS NULL`), §3.1 (DTO field lists), BR18 (DTO values derived per reservation group), BR29 (`free`/`purchased` = the D6 lot-source sums), F10 (tenancy), F25 (late usage is platform loss), D18 (`billing.history.*`).
- 12.2.1-T1: `credit_ledger` rows (`kind`, signed `amount`, `reference_id`, `reference_type`, `idempotency_key`), `credit_lots` (`remaining`, `expires_at`, `voided_at`, `source`), `usage_records.reservation_id`, and `groupId` rule (reserve row ⇒ `id`, family rows ⇒ `reference_id`).
- 00 §8 (L365): the two routes exist as written; `IUserOwned` tenant filter + `ISystemContext.For` (09.2.3); 09.10.5-T1 admin bundle.
- 12.1.4-T1: `price_versions` for the price-version label if the client shows one (**not** added to the DTO — the frozen list has no such field).

## Design

**Query 1 — balance (live lots, D6):**

```sql
SELECT COALESCE(SUM(remaining) FILTER (WHERE source IN ('trial','promo','bonus','adjust')), 0) AS free,
       COALESCE(SUM(remaining) FILTER (WHERE source  = 'purchase'), 0) AS purchased
FROM credit_lots
WHERE user_id = @userId AND voided_at IS NULL AND expires_at > now() AND remaining > 0;

SELECT remaining, expires_at
FROM credit_lots
WHERE user_id = @userId AND voided_at IS NULL AND expires_at > now() AND remaining > 0
ORDER BY expires_at ASC, id ASC
LIMIT 1;                                   -- nextExpiry: { amount, expiresAt } | null
```

`total = free + purchased`; `free` = Σ `remaining` of live lots with `source ∈ {trial, promo, bonus, adjust}` and `purchased` = Σ `remaining` of `source = purchase` (BR29, README §3.1); `nextExpiry = null` when no live lot exists. The query reads **live lots**, not `SUM(credit_ledger.amount)`: invariants 1–2 of §3.5 make them equal, and the 04:00 reconciliation job alerts on any drift, so a transient drift must never show a wrong spendable number. Served by `ix_credit_lots_user_expiry`.

**Query 2 — history (keyset over `ix_credit_ledger_user_created`, one DTO item per family):**

```sql
-- page: rows of the user, newest first; cursor is (created_at, id)
SELECT id, kind, amount, reference_id, reference_type, created_at
FROM credit_ledger
WHERE user_id = @userId
  AND (@hasCursor = false OR (created_at, id) < (@cursorCreatedAt, @cursorId))
ORDER BY created_at DESC, id DESC
LIMIT @limit + 1;                          -- limit default 50, max 100; the +1 row only drives nextCursor

-- family + usage joins for the page's reservation ids (2 batched queries, no N+1)
SELECT id, kind, amount, reference_id, lot_id, created_at
FROM credit_ledger WHERE user_id = @userId AND reference_id = ANY(@reservationIds);
SELECT reservation_id, input_tokens, cached_input_tokens, output_tokens, image_count, gpu_seconds, estimated
FROM usage_records WHERE user_id = @userId AND reservation_id = ANY(@reservationIds);
```

- `groupId` = the `reserve` row's `id`; the family's `settle`/`release`/`refund` rows carry `reference_id = groupId` (12.2.1-T1's row shapes).
- DTO values are **derived per reservation group, never per row** (BR18): `quoted = Σ|reserve|`, `charged = Σ|settle|`, `released = quoted − charged` (0 while open, `= quoted` when refunded); `operation` = the reserve row’s `reference_type` wire value (`story_generate`, `fact_sheet`, `render`, …); `episodeId`/`title` come from the owning entity of the reservation (`render_jobs`/`generation_runs` → `episodes`) in one batched query; `usage.*` is the sum over the family’s `usage_records` rows **as snapshotted at `settled_at`**, `estimated = true` when any row is estimated, all six counters 0 when absent. A `usage_records` row landing **after** the settle is never charged to the reservation — it is a `credit_ledger (reference_type = 'platform_loss')` row (F25/BR30) and is not part of this page.
- `adjust`/`expire`/`grant`/`purchase` rows that are not part of a reservation family form their own one-row group (`groupId` = `id`, `quoted = charged = released = 0` unless the row is the movement itself, in which case `amount` is the movement and `charged = ABS(amount)` for a negative row).
- Cursor: opaque base64url of `{ createdAt (ISO-8601 UTC), id }`; `nextCursor = null` on the last page; an unparsable cursor is a standard 400 validation ProblemDetails from the C11 catalogue (no new code) [INFERENCE].
- **Realtime:** the client refreshes on `CreditBalanceChanged { userId }` (ids only, emitted by 12.2.1-T1); this task adds no push path. `credit_balance_changed.v1 { userId }` stays the outbox record (D17).
- **i18n (D18):** no server-side strings; the keys the client formats are `billing.history.title`, `billing.history.quoted`, `billing.history.charged`, `billing.history.released`, `billing.history.usage`, `billing.history.empty`, `billing.errors.balance_unavailable` — vi + en, English fallback, owned by 10.8.x.
- **Performance:** both routes are index-only-ish scans (`ix_credit_lots_user_expiry`, `ix_credit_ledger_user_created`); the family and usage joins are bounded by `limit` (≤ 100 + 1); no per-row round trips; the history query never loads the whole ledger.

## Steps

1. `Application/Billing/Queries/GetBalanceQuery.cs` — `GetBalanceQuery { UserId }` + handler returning `CreditBalanceDto`; `UserId` is filled from the ambient claims on the route and from the admin policy path in 09.10.5-T1.
2. `Application/Billing/Queries/GetCreditLedgerQuery.cs` — `{ UserId, Cursor, Limit }` + handler with the cursor codec and the DTO projection.
3. `Api/Endpoints/CreditsEndpoints.cs` — map `GET /credits/balance` and `GET /credits/ledger` exactly as 00 §8 writes them, authenticated, rate policy `auth`, `.Produces<CreditBalanceDto>()` / `.Produces<CreditLedgerPageDto>()`; no `billing_enabled` filter.
4. DTO records in `Application/Billing/Dtos` with the §3.1 field names verbatim (`CreditBalanceDto`, `CreditLedgerEntryDto`, `CreditLedgerEntryUsageDto`, `CreditLedgerPageDto { items, nextCursor }`, `NextExpiryDto { amount, expiresAt }`).
5. Batched family/usage/episode projection (EF `AsNoTracking`, split queries to avoid a cartesian explosion).
6. Tenant-filter audit: both handlers resolve `UserId` from `ICurrentUser`; a route-level test asserts user B never sees user A's rows.

## Acceptance checks

1. **Given** a user with lots 100 (`purchase`, expires in 300 d) and 30 (`trial`, expires in 10 d) and one open reservation of −50, **When** `GET /credits/balance` runs, **Then** `total = 80`, `free = 0`, `purchased = 80` (12 CR-23: spend order is `expires_at ASC` first — the 10-day trial lot drains before the 300-day purchase lot), `nextExpiry = { amount: 30, expiresAt: <trial expiry> }`.
2. **Given** a settled reservation (quoted 203, charged 192, released 11) with two `usage_records` rows, **When** `GET /credits/ledger` runs, **Then** exactly one item exists for that `groupId` with `quoted = 203`, `charged = 192`, `released = 11` and `usage` = the sum of both rows.
3. **Given** an open reservation, **When** the history is read, **Then** its item reports `quoted > 0`, `charged = 0`, `released = 0` (nothing has been charged yet).
4. **Given** 250 ledger rows, **When** the client pages with `limit=100`, **Then** it receives 100 + a non-null `nextCursor`, then 100, then 50 with `nextCursor = null`, and no row repeats.
5. **Given** `limit=1000`, **When** the request runs, **Then** the effective limit is 100 (clamped, never an error) [INFERENCE].
6. **Given** a lot whose `expires_at` has passed but the 03:00 expiry sweep has not run, **When** the balance is read, **Then** that lot is excluded from `free`/`purchased`/`nextExpiry`.
7. **Given** two users, **When** user B calls both routes, **Then** B sees only B's rows (`total`, items) and never A's `episodeId`/`title`.
8. **Given** a client action (grant, reserve, settle) that moved credits, **When** the movement commits, **Then** `credit_balance_changed.v1 { userId }` is on `outbox_messages` and `CreditBalanceChanged { userId }` was pushed to that user only.
9. **Given** a ledger page whose families include a reservation with no `usage_records` rows, **When** it is projected, **Then** `usage` counters are all 0 and `estimated = false` (no null fields in the DTO).
10. **Given** the admin path (09.10.5-T1) calling `GetBalanceQuery { UserId = <target> }` under the admin policy, **When** it runs, **Then** it returns the target's balance through the same handler (no second port, response unchanged for the user route).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Unparsable/foreign cursor | 400 standard validation ProblemDetails (C11 catalogue); never a 500 |
| `limit` ≤ 0 or > 100 | clamp to 50 / 100; no error [INFERENCE] |
| No lots, no ledger rows (new user) | `total = free = purchased = 0`, `nextExpiry = null`, `items = []`, `nextCursor = null` |
| Ledger/lot drift (expiry job failed) | balance still shows live lots; the drift is 12.2.3-T1's alert — the route must not throw |
| Owning episode deleted (00 §6: `usage_records.user_id` kept, `episode_id` nulled) | `episodeId = null`, `title = null`; the item still renders with `operation` and amounts |
| Very large `usage` numbers | `long` counters; no overflow path (image counts and GPU seconds are `bigint`-safe) |
| Concurrent movement during paging | keyset cursor is stable (no offset drift); a row created after the scan appears on the next page only |
| Unauthenticated request | 401 before any query |

## Notes

- Do **not** add fields to `CreditBalanceDto`/`CreditLedgerEntryDto` — §3.1 is the frozen list 10 S consumes (BR15, 12 CR-9). Any new need is a CR to the README first.
- Balance is never cached (D6); if the balance query ever becomes hot, the answer is an index/`FILLFACTOR` change, not a `credit_accounts.balance` column.
- `GetBalanceQuery { UserId }` deliberately takes an explicit user id so 09.10.5-T1 can reuse it; the **route** never accepts a `userId` query parameter.
- The history endpoint is the only place the UI learns `quoted`/`charged`/`released`, so the DTO's `groupId` must be the reservation id — UI copy for a still-open line is 10.8.x's business.
