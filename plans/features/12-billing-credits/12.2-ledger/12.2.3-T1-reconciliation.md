# 12.2.3-T1 — CreditReconciliationJob: stale reserves, negative balances and lot/ledger drift

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.2.3-T1 | S (0.5) | BE | 12.2.1-T1, 09.2.6-T1 | — | S · M2 |

## Goal

Ship the nightly safety net for the ledger: `CreditReconciliationJob` (daily 04:00 server-local, `[JobPolicy(Queue = JobQueue.Default, Retries = 1)]`, `[DisableConcurrentExecution]`, ids-only arguments — README D7/BR9) which refunds stale reservations of **terminal** rows per operation margin (24 h story/fact sheet, 72 h render), skips held (paused) and still-running rows, and alerts on negative balances, `SUM(remaining) ≠ SUM(amount)` drift and failed `payment_events`. Every refund it performs raises an 11.6.2-T1 alert (D2); it never fixes drift silently.

## Inputs

- README D2 (stale sweep definition), D7 (job table row), D10 (`Credit:StaleReserveHoursStory` 24, `Credit:StaleReserveHoursRender` 72), D17 (reuse `ISystemWorkQuery.PendingAsyncT` + per-user `ISystemContext.For`; metrics), F04, F08, F09, F10, F15 (`platform_loss`), F24 (lot-scoped keys), F25 (late usage), F26 (render hold), C12, C13, BR4/BR5/BR9/BR14, BR18, BR19, BR29.
- 12.2.1-T1: `RefundAsync`, `GetOpenReservationAsync`, the `reserve`/`settle`/`refund` row shapes, `credit_ledger (reference_type, reference_id)`; `generation_runs.pause_reason = provider_funds_exhausted` (C9, 02 D2), render job statuses `succeeded/failed/cancelled` and `generation_runs.status ∈ failed/cancelled/succeeded` (F09), 12.8.3-T2's resume gate.
- 09.2.6-T1 (Hangfire registration, `[JobPolicy]`, ids-only args), `ISender` per-row dispatch (C12), 11.6.2-T1 (the only alert pipeline, C13), `PaymentStatusSyncJob`/12.3.3-T1 (owns `payment_events`).

## Design

**Registration** — `RecurringJob.AddOrUpdate<CreditReconciliationJob>("credit-reconciliation", j => j.RunAsync(CancellationToken.None), "0 4 * * *")` on `JobQueue.Default`, no new queue (BR9), registered **unconditionally** (`billing_enabled` gates only the money-mutating user routes — O-7/CR-3; the beta ledger runs with admin-granted credits). Args: none (ids-only rule).

**Step 1 — stale reserves (F08/F09/BR5).** One set-based candidate query, then one command per row:

```sql
SELECT l.id AS reservation_id, l.user_id, l.reference_type, l.reference_id, -l.amount AS amount, l.created_at
FROM credit_ledger l
WHERE l.kind = 'reserve'
  AND NOT EXISTS (SELECT 1 FROM credit_ledger f
                  WHERE f.reference_id = l.id AND f.kind IN ('settle','refund'))
  AND l.created_at < now() - make_interval(hours => @marginHours)      -- 24 story/fact_sheet, 72 render
  AND (
        EXISTS (SELECT 1 FROM generation_runs g
                WHERE g.id = l.reference_id AND g.status IN ('failed','cancelled','succeeded'))
     OR EXISTS (SELECT 1 FROM render_jobs r
                WHERE r.id = l.reference_id AND r.status IN ('succeeded','failed','cancelled'))
     OR (NOT EXISTS (SELECT 1 FROM generation_runs g WHERE g.id = l.reference_id)
         AND NOT EXISTS (SELECT 1 FROM render_jobs r WHERE r.id = l.reference_id))
      )                                                              -- owning row terminal or gone
  AND NOT EXISTS (SELECT 1 FROM generation_runs g
                  WHERE g.id = l.reference_id AND g.pause_reason = 'provider_funds_exhausted')
ORDER BY l.created_at ASC
LIMIT @batchSize;                                                    -- 500, loop while rows come back
```

Per row: `ISystemContext.For(user_id)` → `ISender.Send(new RefundStaleReservationCommand(reservationId, userId, "reconciliation_stale", marginHours))` ([NotAudited], one command per row so one bad row never rolls back the batch — C12) → **alert on every refund performed** (D2). Held rows and non-terminal rows are counted and logged (`skippedHeld`, `skippedRunning`), never refunded. `@marginHours` comes from `CreditOptions.StaleReserveHoursStory` / `StaleReserveHoursRender`, selected by the row's `reference_type` (`render` ⇒ 72).

**Render-held guard (BR29/F26, resolved).** `render_jobs` has **no** hold column (BR29 forbids inventing one), so a render hold is **derived**: the owning job is `queued` ∧ the `provider_funds_exhausted` flag is open ∧ `GetOpenReservationAsync` still returns an open reservation; `Credit:HoldCancelHours` = 12 cancels + refunds after that (12.8.3-T2). While the flag is open, rows whose owning render job is non-terminal are skipped with reason `skippedFlagOpen`; 12.8.3-T2’s resume path uses `GetOpenReservationAsync` and cancels instead of dispatching when the reservation is gone.

**Step 2 — negative balances (F04).** Late `usage_records` rows are never re-charged (F25): the settle snapshots usage at `settled_at`, and a later row is a `credit_ledger (reference_type = 'platform_loss')` row surfaced by `billing_provider_loss_total{reason='late_usage'}` / `platformLossUsd` (BR30) — this job only reports, it never re-charges.

```sql
SELECT user_id, SUM(amount) AS balance FROM credit_ledger GROUP BY user_id HAVING SUM(amount) < 0;
```

Alert per user with the balance; no auto-fix (a fix is an opposite `adjust` row through `ICreditLedger` by an operator, audited).

**Step 3 — lot/ledger drift (D2/F04, §3.5 invariant 2).** Compare `SUM(credit_ledger.amount)` with `SUM(credit_lots.remaining)` over `voided_at IS NULL` lots, joined through `credit_accounts`; mismatch ⇒ one alert naming the user, counts logged. The comparison is only meaningful because `CreditExpiryJob` (12.6.2-T1, 03:00 server-local) already zeroed expired lots and wrote their `expire` rows an hour earlier — a drifted result is the symptom of a failed expiry run, and the expiry job's own failure pages the owner. Documented in the runbook; no auto-fix.

**Step 4 — provider-event failures.** Count and alert `payment_events WHERE processed_at IS NULL AND error IS NOT NULL` (12.3.3-T1 owns the write and the retry; this job only reports).

Discovery reads are **system** reads: `ISystemWorkQuery.PendingAsyncT` (pinned, single member, never extended — 09.2.3-T1) returns `(id, user_id)`; the operation margin/terminal/held predicates are applied by the caller. [INFERENCE] discovering reservations through a tenant-filtered table with no ambient user would load 0 rows silently (F10), so the candidate query above must run in system scope; if the pinned member cannot express it, that is a CR to 09.2.3-T1 — no member is added here.

**Observability:** counters `billing_reservation_missing_total` (monitored, must stay 0), `billing_balance_liability_credits` (live-lot sum), `billing_provider_loss_total{reason}`; per-run log: `refunded`, `skippedHeld`, `skippedRunning`, `negativeUsers`, `driftedUsers`, `failedEvents`, duration. Alerts ride 11.6.2-T1 only (C13): every stale refund, any negative balance, any drift, any `payment_events` failure.

**i18n:** no user-facing string from this job; the users whose reservations it refunds get nothing (the job/cancel flow, 12.8.3-T2/05, sends the e-mail). Alert texts are internal English.

## Steps

1. `CreditReconciliationJob` + `RunAsync(CancellationToken)`: batch loop over step 1, then steps 2–4; each in its own scope, `ISender` per row.
2. `RefundStaleReservationCommand` ([NotAudited], one row) — re-checks the reservation is still open and still stale **inside** the transaction (the lock makes the check authoritative), then `RefundAsync`.
3. `CreditOptions` binding for the two margins + batch size `Credit:ReconciliationBatchSize` default 500 (add to `CreditOptions`; the two margins are already in D10).
4. Register the recurring job on `JobQueue.Default` with cron `0 4 * * *` and `[DisableConcurrentExecution]`.
5. Alerts through the 11.6.2-T1 client; no new pipeline, no email template.
6. Runbook note (in §11 of `plan.md`'s operator list, not a new doc): what each alert means and the manual correction (opposite `adjust` via the admin grant path).

## Acceptance checks

1. **Given** a `story_generate` reservation 25 h old whose `generation_runs.status = failed`, **When** `RunAsync` completes, **Then** exactly one `refund:{reservationId}:{lotId}` row per reserved lot exists (BR19), the reserve is closed, and an 11.6.2-T1 alert was raised for that refund.
2. **Given** the same reservation 23 h old, **When** `RunAsync` runs, **Then** nothing is refunded (below the 24 h margin).
3. **Given** a render reservation 25 h old (below the 72 h render margin), **When** `RunAsync` runs, **Then** nothing is refunded and the row is counted as running, not stale.
4. **Given** a reservation whose owning row is `running`/`story_generating`, **When** `RunAsync` runs at any age, **Then** it is skipped and logged `skippedRunning`, and an alert is raised **once per run** without moving credits.
5. **Given** a reservation on a series/job held with `pause_reason = provider_funds_exhausted`, **When** `RunAsync` runs, **Then** it is skipped (`skippedHeld`) even if the owning row is terminal and older than the margin (F08/BR14).
6. **Given** a render reservation created while the platform flag is open and whose render job is non-terminal, **When** `RunAsync` runs, **Then** it is skipped (`skippedFlagOpen`).
7. **Given** a reservation whose settle and refund rows both exist (already closed), **When** `RunAsync` runs, **Then** the candidate query never returns it (no duplicate refund).
8. **Given** a hand-written negative `SUM(amount)` for one user, **When** `RunAsync` runs, **Then** one alert names that user and no credit row is written.
9. **Given** `SUM(credit_lots.remaining) ≠ SUM(credit_ledger.amount)` for one user (e.g. a failed expiry run), **When** `RunAsync` runs, **Then** one drift alert names that user, `credit_ledger` is unchanged, and the run logs `driftedUsers = 1`.
10. **Given** 600 stale candidates, **When** `RunAsync` runs with batch size 500, **Then** it processes them in batches, dispatches one command per row, and a failing row (simulated) leaves the other 599 refunded.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Owning row deleted (episode purged) | treated as "owner gone" ⇒ refunded; the alert names the reservation id |
| Reservation created by a future operation type | margin falls back to the story/most-conservative value and the row is logged `unknownOperation` — never refunded blind |
| Job crashes mid-batch | `[DisableConcurrentExecution]` + retry 1; already-refunded rows are no longer candidates (closed reservations are excluded), so a rerun is safe |
| Settle arrives for a reservation the sweep just refunded | the settle path returns `reservation_missing` (12.2.1-T1) — metric + alert, no second refund |
| Drift caused by the expiry job not having run | alert is expected and the expiry job's failure is the paging signal; the job still reports (no silent suppression) |
| Candidate query returns 0 rows | log `refunded = 0`; nothing else |
| Clock/DST | cron is server-local at 04:00; `now()` is `timestamptz` in UTC — margins are computed in absolute hours |
| Reconciliation disabled during an incident | never part of a rollback (§11 of `plan.md`); alerts stay on |

## Notes

- The sweep is the **only** automatic refund path besides the 12 h held-job cancel (12.8.3-T2); both write the lot-scoped `refund:{reservationId}:{lotId}` rows exactly once (BR19), so overlapping runs cannot double-refund.
- No direct SQL correction for drift or negatives: the manual path is an opposite `adjust` row through `ICreditLedger` under the account lock, audited (F04).
- Do not add a second alert pipeline (C13) and do not invent an email template here — `credit_low_balance`/`credit_expiring` belong to 12.6.x.
- `[DisableConcurrentExecution]` plus the closed-reservation exclusion makes the job idempotent-by-construction; there is no "lock the whole run" advisory lock (F02 forbids a session lock).
