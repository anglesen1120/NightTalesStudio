# 12.3.1-T1 — Payment provider evaluation and dated choice

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.3.1 | S (0.5) | BA | — | 12.3.2-T1, 12.7.4-T1 | S · M2 |

## Goal

Score 2–4 candidate payment providers against the checklist of `plans/12-billing-credits.md` §5.4 using **official, dated primary pages only**, and record the chosen provider — with its webhook signature algorithm, status API, refund API, fees and SDK licence verdict — as the `DECISIONS.md` §4/§10.5 entry required by **12 CR-10**. This closes 12.3.2-T1's dependency and closes the **[OPEN]** part of D9 (the signature algorithm shape) and of P5 (payOS-style sorted-field checksum vs raw-body HMAC). No production code is written by this task.

## Inputs

- Checklist: `plans/12-billing-credits.md` §5.4 (merchant eligibility for a Vietnam-registered business, payout currency/bank, methods Vietnamese users actually use, hosted checkout, signed webhooks, status API, refund API, dated official fees, merchant-of-record and tax handling for foreign buyers, e-invoice support ⚠️, sandbox quality, SDK licence).
- Findings/facts to respect: F18 (**no vendor SDK in the repository**; an SDK licence that is AGPL/RPL/non-commercial is rejected regardless of convenience), P2 (Svix-style `svix-id`/`svix-timestamp`/`svix-signature`, HMAC-SHA256 over `${id}.${timestamp}.${rawBody}`, base64, `v1,` prefix, raw body required, constant-time compare, example 300 s tolerance, at-least-once with ~28 h retries plus manual/bulk replay), P5 (the real payOS documentation is *reported* to sign the **sorted `data` fields** with a shared checksum key and to expose payment status but **no** refund endpoint ⚠️), P4 (OpenAI prepaid facts — context only), P1 (`docs.payos.money/*` now serves CrissCross, an Africa/Middle-East merchant-of-record — not a Vietnamese option).
- Decisions: O-1 (provider stays [OPEN] until this task scores candidates from dated pages; the choice goes to `DECISIONS.md`; no vendor SDK), BR16 (the evaluation starts in M0/M1 and the merchant application is filed the day a provider is chosen; the sandbox gate does not wait for onboarding), BR15 (frozen names: `payments.method ∈ card/wallet/bank_qr`, `payments.status` values, `Payment:Providers` capability flags `Card`, `Wallet`, `BankQr`, `StatusApi`, `RefundApi`, config keys of D10).
- Consumers: 12.3.2-T1 (adapter + checkout + return URL), 12.7.4-T1 (bank QR), 12.3.3-T2 (`Capabilities.StatusApi` decides whether the sync job re-fetches or only expires), 12.7.5-T1 (refund API presence decides provider refund vs the manual bank fallback of D12).

## Design

Deliverable is a **document**, not code — but a document a developer can implement from without inventing anything.

1. **Candidate set (2–4, dated).** At least one domestic Vietnamese gateway (local cards, e-wallets, bank QR) and at least one international merchant-of-record option (foreign-buyer cards, tax handling). Candidates are named by their own product name; no candidate is pre-selected in this plan.
2. **Matrix.** One row per candidate, one column per §5.4 checklist item, every cell carrying **URL + read date** and a verbatim quote for the load-bearing cells (fees, method list, signature scheme, refund endpoint, status endpoint, sandbox). Cells filled from memory, blogs, aggregator sites or an SDK README are marked ⚠️ and do not count.
3. **Signature algorithm, stated so it can be coded.** The matrix must answer, for the chosen provider: which HTTP headers carry the event id, timestamp and signature; which bytes are hashed (raw request body, or a canonical concatenation of specific fields and in which order); the hash function; the encoding; the version prefix, if any; the tolerance window. Two acceptable shapes are known from the sources quoted in the README (raw-body HMAC, P2; sorted-fields checksum, P5) — the answer must be a sentence that maps 1:1 onto `IPaymentProvider.ParseAndVerifyAsync(ReadOnlyMemory<byte> rawBody, IReadOnlyDictionary<string,string> headers)`.
4. **Capability flags.** The result fixes `Payment:Providers:<name>:Capabilities:{Card,Wallet,BankQr,StatusApi,RefundApi}` and the method mapping onto `payments.method ∈ card/wallet/bank_qr`. `BankQr` and `RefundApi` are independent: a provider with no refund endpoint is a **valid** outcome and routes refunds to the manual bank fallback (D12, P5); a provider with no status API means 12.3.3-T2 only expires pending rows and never re-fetches. **A `BankQr = false` provider must make `POST /billing/checkout` with `method = bank_qr` answer 400 `payment_method_unavailable` — fail-closed, never a silent card fallback (BR32/CR-7)**; the record states this explicitly so 12.3.2-T1's guard has a dated source.
5. **Licence verdict (F18).** If an SDK exists: its licence name, a link to the licence file, and the verdict `permitted` / `rejected`. The project rule is no AGPL/RPL/non-commercial; a rejected SDK does not disqualify the provider — it means the adapter is hand-rolled with `HttpClient` + `System.Security.Cryptography`.
6. **Onboarding plan.** Document set, bank verification, contract, sandbox access, production approval, and the estimated wall-clock days per step (flagged as vendor-reported), plus who owns the application and the date it is filed (BR16).

## Steps

1. List candidates and open the official domains; record the read date for every page (P-rows of the README are the pre-read baseline: P1/P2 read 2026-09-25, P3/P5 unread ⚠️).
2. For each candidate, fill every §5.4 row from primary pages: pricing/fees page, merchant/onboarding docs, payment-method docs, hosted-checkout page, webhook signature page, payment status endpoint, refund endpoint, sandbox docs, licence file if an SDK exists.
3. Score the matrix (weights: fees 25 %, method coverage 20 %, webhook + status API quality 20 %, refund API 10 %, onboarding feasibility 15 %, licence 10 %) and reject any candidate that cannot sign webhooks or that is limited to markets we do not serve.
4. Record the choice (or a shortlist with exactly one blocking question) in `DECISIONS.md` §4 and the dated provider facts in §10.5 — this is 12 CR-10's first clause.
5. Derive and write down the capability flags and the config values for `Payment:ActiveProvider` / `Payment:Providers`. The config section is **`Payment:`** (BR26/D10).
6. File the merchant application the same day the choice is made and record the filed date, the owner and the vendor-reported timeline (BR16).
7. Hand over to 12.3.2-T1 (adapter shape) and 12.7.4-T1 (bank-QR feasibility) with the matrix attached to the decision record.

## Outputs

- `DECISIONS.md` §4/§10.5 entry (12 CR-10) containing: the chosen provider; the dated candidate matrix with per-cell URLs; the fee schedule as read; the capability flags; the webhook signature algorithm in implementable form (headers, bytes hashed, hash, encoding, prefix, tolerance); the status API and refund API presence; the method mapping onto `card/wallet/bank_qr`; the licence verdict; the e-invoice ⚠️ note for the accountant; the onboarding checklist with the filed date.
- The `Payment:ActiveProvider` value and the `Payment:Providers` block (base URLs + capability flags) that 12.3.2-T1's options class reads (D10).
- A written statement of which D9 invariant holds for this provider: raw-body HMAC and/or sorted-field checksum, plus the tolerance window (default `Payment:WebhookTimestampToleranceSeconds` = 300).

## Acceptance checks

1. **Given** the finished matrix, **when** a reviewer picks any fee, method or endpoint cell, **then** that cell cites a URL and a read date and quotes the page verbatim.
2. **Given** the matrix, **when** it is checked against §5.4, **then** all 12 checklist rows are answered for the chosen candidate (an unanswered row is a ⚠️ with a reason, never blank).
3. **Given** the chosen provider's webhook page, **when** the algorithm sentence is read by an implementer who has not seen the page, **then** they can implement `ParseAndVerifyAsync` with no further question (headers, bytes, hash, encoding, prefix, tolerance all named).
4. **Given** a provider whose status API exists, **then** the matrix names the endpoint and the authentication scheme, and 12.3.3-T2's re-fetch is in scope; **given** no status API, **then** the decision record says so explicitly and only the expiry path applies.
5. **Given** a provider with no refund endpoint, **then** the decision record states that refunds use the manual bank fallback (D12) and the user-visible refund window is unchanged (14 days, FR-12-14).
6. **Given** `Capabilities.BankQr` is false for the chosen provider, **then** 12.7.4-T1 is recorded as dropped (plan §12.7.4: dropped, not replaced by manual statement matching) and this is written in the decision record.
7. **Given** any SDK with an AGPL/RPL/non-commercial licence, **then** the decision record shows `rejected` and the adapter plan is hand-rolled with `HttpClient` + `System.Security.Cryptography` (F18).
8. **Given** the choice is recorded, **then** the merchant application is filed and the filed date + owner appear in the record (BR16), and the M2 sandbox gate is explicitly not waiting on production approval.
9. **Given** the record exists, **when** 12.3.2-T1 starts, **then** it can configure `Payment:ActiveProvider` and build the adapter with no unanswered question in the checklist; **and** `git grep` finds no vendor SDK package reference added anywhere (F18).
10. **Given** a candidate later turns out unavailable (page gone, business rejected), **then** the record keeps the second-scoring candidate as the fallback with its own dated rows, so 12.3.2-T1 is not blocked.

## Tests

No automated test suite: this task's artefact is a decision record. Verification is a two-person review of the record against the primary pages, plus two mechanical checks that can be run in CI-free form:

- **Checklist coverage check** (`D-rows` of the matrix): every §5.4 row present, every cell non-empty, every ⚠️ accompanied by a reason; a script greps for empty cells and fails the review if one exists.
- **Signature-sentence check**: the record contains one sentence naming the headers, the hashed bytes, the hash function, the encoding, the prefix (or "none") and the tolerance; a second reader implements `ParseAndVerifyAsync` from it against the recorded page and confirms it, and any mismatch fixes the record before 12.3.3-T1 starts.
- **Licence check**: the record names a licence verdict per SDK; `grep` over `Directory.Packages.props` for vendor SDK names returns nothing after 12.3.2-T1 lands (that grep lives in 12.3.2-T1's test list and is re-run here as a hand-over gate).
- **Cross-check with 12.3.3-T2**: the record's `Capabilities.StatusApi` value is the single source the job's behaviour is asserted against; the reviewer confirms the acceptance check 4 wording matches the value.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| No provider accepts a Vietnam-registered business | Record the blocker explicitly, keep the two best candidates with their exact rejection wording and date, and escalate to the owner with a concrete alternative (MoR for foreign buyers + a domestic gateway for VND). Never invent an availability claim |
| A page cannot be read (403, login wall, JS-only) | Mark ⚠️ with the URL, the date and what was attempted; a ⚠️ cell cannot be the only support for the final choice — the choice needs at least the merchant-eligibility, fee and webhook rows ✅ |
| Onboarding needs weeks (BR16) | The application is filed on the day of the choice; the sandbox gate proceeds against the contract-true fake so 12.3.2-T1 / 12.3.3-T1 are never blocked |
| payOS-style sorted-field checksum only (P5) | Valid: the record fixes the sorted-field canonicalisation (field order, separator, key) instead of the raw-body variant; D9's invariant list (raw bytes, constant-time compare, replay window, claim-then-act) still binds |
| Provider sends `card`/`wallet`/`bank_qr` naming that does not match our enum | The record gives the mapping table; the adapter normalises, so `payments.method` keeps the frozen values |
| Provider fee is per-transaction with a monthly minimum | Entered verbatim in the record and fed to 12.1.1-T1's `fee_rate` (the margin model), never silently rounded |
| Two candidates score within noise of each other | The record names the tie-breaker used (onboarding lead time, then refund API, then fees) so the choice is reproducible |
| Provider requires an e-invoice integration we do not build in MVP | Recorded as ⚠️ for the accountant (§12.7.3); the checkout still accepts `invoiceInfo` for later manual issuing |

## Notes

- [DECISION] O-1/BR16 are the reason this task has `Depends on: —` and blocks two tasks: it is the only task in 12.3 that can start in M0/M1.
- The webhook **algorithm** stays [OPEN] in D9 until this task finishes; the **invariants** (raw bytes, constant-time comparison, replay tolerance, claim before side effect) are already frozen by BR1/BR10 and are not negotiable per provider.
- Do not apply any CR: CR-10 is applied by the TL. This task produces the content and hands it over.
- Evidence legend for every cell: ✅ read from a primary page with URL + date · ⚠️ unverified/secondary · [OPEN] · [INFERENCE]. Vendor marketing pages count as primary only for their own fees and methods.
- A provider whose `Capabilities.BankQr` is false is not a defect: the capability flag is the contract, and the unsupported method is refused with 400 `payment_method_unavailable` (fail-closed, BR32/CR-7) instead of falling back to another method.
