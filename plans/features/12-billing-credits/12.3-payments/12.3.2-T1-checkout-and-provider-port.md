# 12.3.2-T1 — `IPaymentProvider` port, checkout order and the `payments` row

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.3.2 | M (1.0) | BE + Security | 12.3.1-T1, 12.1.2-T1, 12.7.1-T1 | 12.3.3-T1, 12.7.2-T1 (soft), 12.7.3-T1, 12.7.4-T1 (soft), 10.8.1-T1, 10.8.1-T0 (10/08 CR-hand-off) | S · M2 · flag `billing_enabled` |

## Goal

Give the platform one payment port and one way to create an order: `IPaymentProvider` (D8, shapes verbatim) with a contract-true fake, `POST /billing/checkout` inside flag `billing_enabled` that writes a `pending` `payments` row and returns the frozen `CheckoutSessionDto`, `Idempotency-Key` replay, provider-failure handling, and the additive migrations for **12 CR-1** (`payments.expires_at`, `payments.paid_at`) plus the F20 indexes. Consumer: 10.8.1/10.8.3 (buy page, checkout hand-off, `/billing/return`).

## Inputs

- D8 (**shapes verbatim**): `Capabilities { Card, Wallet, BankQr, StatusApi, RefundApi }`, `CreateCheckoutAsync(CheckoutRequest, ct)`, `GetPaymentAsync(string providerPaymentId, ct)`, `RefundAsync(RefundRequest, string idempotencyKey, ct)`, `ParseAndVerifyAsync(ReadOnlyMemory<byte> rawBody, IReadOnlyDictionary<string,string> headers)`; `CheckoutRequest(Guid PaymentId, string OrderCode, long AmountMinorUnits, string Currency, string ReturnUrl, string? CancelUrl, ProviderMethod Method, string Description)`; `CheckoutSession(string? CheckoutUrl, BankQrDetails? BankQr, DateTimeOffset ExpiresAt)`; `BankQrDetails(string QrPayload, string BankName, string AccountNumber, string AccountName, long AmountMinorUnits, string OrderCode)`; `ProviderPayment(string ProviderPaymentId, long AmountMinorUnits, string Currency, ProviderPaymentStatus Status, DateTimeOffset? PaidAt)`; `ProviderPaymentStatus ∈ { Pending, Paid, Failed, Refunded, PartiallyRefunded, Unknown }`.
- D10 config: `Payment:ActiveProvider`, `Payment:Providers` (base URLs + capability flags), `CheckoutExpiryMinutes` 30, `ReturnUrlBase`; D17: index list; C2 money conventions (`numeric(12,6)`, `id uuid` UUIDv7, `timestamptz`); C13 wire: response fields exactly `{ paymentId, provider, method, amount, currency, checkoutUrl | null, bankQr | null, expiresAt }` — **no `redirectUrl`**; return URL `<PublicOrigin>/billing/return?paymentId={id}&orderCode={orderCode}`; `Idempotency-Key` required.
- D13/BR13 minting context (a package whose `bonus_credits` exceeds `credits` is rejected at save — 12.7.1-T1 owns the save path, this task only trusts the snapshot), D4 (`package_below_cost` is 12.7.1-T1's), BR6 (`IPromoValidator` is **declared by this task** and implemented by 12.7.2-T1; checkout never depends on the promo task at build time), BR17 (the flag gates order creation only), CR-3 `feature_flags` key `billing_enabled` default false; CR-7 codes `payment_invalid_state` 409, `payment_expired` 409, `payment_provider_error` 502, `package_not_found` 404.
- Upstream: 12.3.1-T1 (which provider, capabilities, algorithm), 12.1.2-T1 (`price_versions` incl. `credit_usd`, so the snapshot's `price_version` is meaningful), 12.7.1-T1 (active packages + the `GET /billing/packages` read model; this task **consumes** that read model and never declares a second catalog — D4/BR15).

## Design

**Port + adapter.** `IPaymentProvider` lives in `NightTales.Application.Billing.Payments`; the adapter in `NightTales.Infrastructure.Payments.<Provider>` uses `HttpClient` + `System.Text.Json` only (F18: **no vendor SDK**). `FakePaymentProvider` (in `NightTales.TestKit`) implements the same contract: deterministic `CheckoutSession`, a `ProviderPayment` it can be told to return, and `ParseAndVerifyAsync` over a fixed HMAC vector, so 12.3.2-T1/12.3.3-T1 are buildable while onboarding runs. `ProviderPayment.AmountMinorUnits` is normalised by the adapter (VND integer, USD minor units) with an explicit overflow check (`checked` arithmetic, negative rejected) — F12. A method the active provider does not support is refused **fail-closed** (`method = bank_qr` with `Capabilities.BankQr = false` ⇒ 400 `payment_method_unavailable`, BR32/CR-7) — there is no silent fallback to another method.

**`CheckoutCommand`** — `CheckoutCommand(Guid UserId, Guid PackageId, string? PromoCode, ProviderMethod? Method, InvoiceInfo? InvoiceInfo)` ⇒ `ErrorOr<CheckoutSessionDto>`; handler marker `[Audited]`; tenant-scoped through the ambient `ISystemContext`. Steps with one `SaveChangesAsync` (UnitOfWorkBehavior, 09.2.1-T1):

1. Flag check: `billing_enabled` false ⇒ 404 (the route exists but order creation is closed, BR17) — read through the 09.9.1 flag store, never from a captured static.
2. Load the active package (12.7.1-T1's read model); missing/inactive ⇒ 404 `package_not_found`.
3. Promo: when `PromoCode` is present, call `IPromoValidator.ValidateAsync(code, userId, packageId, amountMinorUnits, ct)` — declared **here** with the frozen BR32 signature `ValidateAsync(string code, Guid userId, Guid packageId, long amountMinorUnits, ct) → ErrorOr<PromoValidation(Guid PromoCodeId, PromoKind Kind, long BonusCredits, long BonusPercent)>`, implemented by **12.7.2-T1** ⇒ `promo_invalid` 400 / `promo_expired` 400 / `promo_exhausted` 409 / `promo_already_used` 409 in that order (D14). No redemption is written here — redemption rides `payment_paid.v1` (BR6).
4. Idempotency (09 D6): hash the body + user into `request_hash`; same `Idempotency-Key` + same hash ⇒ replay the stored `CheckoutSessionDto` (same `paymentId`); different hash ⇒ 409 `payment_invalid_state`.
5. Insert `payments`: `user_id`, `provider = Payment:ActiveProvider`, `method`, `amount` (package price), `currency` (`"VND"`), `status = 'pending'`, `package_id`, `credits`, `bonus_credits`, `price_version`, `promo_code_id`, `order_code` (unique, generated), `invoice_info`, `expires_at = now + CheckoutExpiryMinutes`, `paid_at = NULL`. `bankQr` is **never** written into `payments.raw` (BR32): the QR is derived from `order_code` + the provider account config at response-mapping time
6. Commit, then call `CreateCheckoutAsync` with `ReturnUrl = ReturnUrlBase + "/billing/return?paymentId={id}&orderCode={orderCode}"`. On a provider error: second transaction sets `status = 'failed'` and returns 502 `payment_provider_error` (no live checkout URL ever leaks for a failed row).
7. Map to `CheckoutSessionDto` — `checkoutUrl` from `CheckoutSession.CheckoutUrl`, `bankQr` from `BankQrDetails` (`amount` = integer VND) — derived, never read back from `payments.raw` (BR32) — and `expiresAt` from the row.

**Migrations (BR20, additive).** `_12_Payments` is **this task**'s migration: CR-1 columns + the F20 indexes `payments (status, created_at)`, `payments (provider, provider_payment_id)` unique, `payments (order_code)` unique. `_12_PaymentEvents` is **12.3.3-T1**'s migration (this task only configures the entity), and `credit_lots`/its `(payment_id)` index are not this task's either — `_12_CreditLots` is 12.2.1-T1's (BR20). No backfill (M2 tables are empty in P).

**No `GET /billing/packages` in this task (BR32).** The storefront read belongs to **12.7.1-T1** (active only, `sortOrder`, integer VND prices). This task does **not** mount the route, does not declare its DTO and adds no fallback HTTP surface over that read model; the checkout path only loads the package row through 12.7.1-T1's read model.

## Steps

1. Add `IPaymentProvider`, the D8 DTOs, `ProviderMethod`, `ProviderPaymentStatus`, `MoneyMinorUnits` (Domain) and the `IPromoValidator` seam (Application) with XML docs stating the raw-body contract.
2. Add `Payment`/`PaymentEvent` EF configurations mapped to 00 §6:300/301 columns verbatim + CR-1 columns; register `payments`/`payment_events` as `IUserOwned` (F10); add the migrations and indexes.
3. Implement `FakePaymentProvider` in `NightTales.TestKit` and one adapter shell for `Payment:ActiveProvider` with the capability flags from 12.3.1-T1.
4. Implement `CheckoutCommand` + handler as designed, with the 7 steps in that order and a single `SaveChangesAsync`.
5. Expose `POST /billing/checkout` (policy `paid`, `Idempotency-Key` required) **only** — `GET /billing/packages` stays 12.7.1-T1's and is not mounted here (BR32); add the CR-7 codes this task raises (`payment_invalid_state` 409, `payment_expired` 409, `payment_method_unavailable` 400) to `ErrorCodes.cs` + `ErrorCatalogue.cs` if not already present.
6. Emit logs/metrics: `payment.checkout.created`, `billing_payments_needs_review_total` untouched here, `payment.checkout.failed`; never log the promo code or invoice info values.
7. Hand over to 12.3.3-T1 (the row it must settle) and 12.7.3-T1 (the read DTOs of `payments`).

## Outputs

- `IPaymentProvider` + D8 DTOs + `FakePaymentProvider` + adapter shell; `CheckoutCommand`/handler; `POST /billing/checkout` (and **no** `GET /billing/packages` route — BR32); the `_12_Payments` migration (BR20) with CR-1 columns and the `payments` F20 indexes; the `IPromoValidator` declaration; `PaymentOptions` bound and validated at boot (`ActiveProvider` must exist in `Providers`, `CheckoutExpiryMinutes` 1..120).
- Tests (see below) and the config keys `Payment:ActiveProvider`, `Payment:Providers`, `Payment:CheckoutExpiryMinutes`, `Payment:ReturnUrlBase`.

## Acceptance checks

1. **Given** flag `billing_enabled = true`, an active package and a valid `Idempotency-Key`, **when** the user posts `POST /billing/checkout`, **then** a `payments` row exists with `status = 'pending'`, `expires_at = created_at + 30 min`, `paid_at IS NULL`, the package snapshot (`credits`, `bonus_credits`, `price_version`) and the response is exactly `{ paymentId, provider, method, amount, currency, checkoutUrl | null, bankQr | null, expiresAt }` with **no** `redirectUrl` field.
2. **Given** the same `Idempotency-Key` and the same body twice, **then** the second call replays the stored response with the same `paymentId` and no second `payments` row; **given** the same key with a different body, **then** 409 `payment_invalid_state`.
3. **Given** `billing_enabled = false`, **when** checkout is posted, **then** the order is refused and no `payments` row is created, while the webhook, the payment reads and refund handling still work (BR17).
4. **Given** a `bank_qr` method and a provider whose `Capabilities.BankQr` is true, **then** `bankQr` is non-null with all six fields and `orderCode` matching the row; **given** `BankQr` false, **then** 400 `payment_method_unavailable` — **fail-closed**, never a silent card fallback (BR32/CR-7) — and no `payments` row is written.
5. **Given** the provider throws on `CreateCheckoutAsync`, **then** the row is `failed`, the API returns 502 `payment_provider_error`, and no `checkoutUrl` was returned to the client.
6. **Given** a package id that is missing or inactive, **then** 404 `package_not_found`; **given** an expired/invalid promo code, **then** the D14 code and status are returned and no `payments` row exists.
7. **Given** `ReturnUrlBase = https://app.example`, **then** the `CreateCheckoutAsync` call received `https://app.example/billing/return?paymentId={id}&orderCode={orderCode}` — verified by the fake recording the request.
8. **Given** the migration is applied to an empty P database, **then** the CR-1 columns and the three `_12_Payments` (BR20) indexes — `payments (status, created_at)`, `payments (provider, provider_payment_id)` unique, `payments (order_code)` unique — exist, and `downgrade` removes exactly them; `payment_events`' own indexes are 12.3.3-T1's `_12_PaymentEvents` migration and `credit_lots (payment_id)` is 12.2.1-T1's `_12_CreditLots` (BR20) — neither is asserted here.
9. **Given** a provider that reports amounts in minor units, **then** `payments.amount` holds the VND integer exactly (no ×100 drift) and a negative or overflowing amount is rejected before any provider call (F12).
10. **Given** the arch tests run, **then** `POST /billing/checkout` carries exactly one of `[Audited]`/`[NotAudited]`/`[AllowAnonymousRequest]`, `UnitOfWorkBehavior` is the only `SaveChangesAsync` caller, and `Directory.Packages.props` contains no vendor SDK (F18).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Provider timeout / 5xx on `CreateCheckoutAsync` | Row `failed`, 502 `payment_provider_error`, `payment.checkout.failed` logged with the provider's correlation id only; the user may retry with a **new** `Idempotency-Key` (the old key now maps to a failed row and replays the same error) |
| Provider returns a QR whose `AmountMinorUnits` differs from the row | Log `payment.mismatch` with both integers; the checkout response still returns the row's amount and 12.3.3-T1 will send the payment to `needs_review` on the webhook — never silently accept |
| Package changed between load and insert | The snapshot columns on the row are authoritative for the payment (00 §6 note: "Snapshot of what was bought"), so an admin edit mid-flight cannot change what the buyer pays for |
| `order_code` unique violation | Regenerate once with a new suffix inside the same transaction; a second collision fails the request rather than looping |
| Two checkouts for the same user in parallel | Two distinct `order_code`s, two rows, no shared lock taken here (no credits move at checkout, so the `credit_accounts` lock is not needed until 12.3.3-T1's grant) |
| Provider capability mismatch (`method = bank_qr` but `BankQr` false) | 400 `payment_method_unavailable` **before any row is written** — fail-closed, never a silent card fallback (BR32/CR-7); the client's method list comes from 12.7.1-T1's `GET /billing/packages`/10's copy, so this is a defensive check |
| Provider base URL missing at boot | `PaymentOptions` validation fails fast at startup (never a runtime 500 on checkout) |
| Invoice info supplied | Persisted verbatim in `payments.invoice_info`; no e-invoice is issued in MVP (§12.7.3) |

## Notes

- The flag check happens in the handler, not in middleware, so that 12.3.3-T1's webhook path can never be blocked by `billing_enabled` (BR17).
- No credits move in this task: no `ICreditLedger` call, therefore no `[PaidOperation]` marker and no `credit_accounts` lock. The first credit movement in this folder is 12.3.3-T1's grant.
- `expires_at` is what makes F13 fixable: a `pending` row with no provider id is expired later by 12.3.3-T2, and a late webhook for that `order_code` becomes `needs_review` (BR11).
- Keep the DTO field names exactly as in §3.1 — 10 S codes against them and CR-9 freezes them.
- `IPromoValidator` is **declared here** with the BR32-frozen signature and implemented by 12.7.2-T1: `ValidateAsync(string code, Guid userId, Guid packageId, long amountMinorUnits, ct) → ErrorOr<PromoValidation(Guid PromoCodeId, PromoKind Kind, long BonusCredits, long BonusPercent)>`.
- `bankQr` is derived (from `order_code` + the provider account config) and is **never** persisted in `payments.raw` (BR32); a provider without bank QR answers 400 `payment_method_unavailable`, never a silent card fallback.
