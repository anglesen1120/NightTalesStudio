# 12.3.3-T1 — Webhook endpoint, claim-then-act, verified grant

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

Make `POST /billing/webhooks/{provider}` the only path that turns a provider payment into credits, and make it safe under the real delivery contract: at-least-once with **concurrent** duplicates (F01/P2). Signature is verified over the raw bytes, delivery is claimed atomically before any side effect, amount and currency are verified before any lot exists, the provider's status API is re-fetched when one exists, and every processing outcome answers 200 so the provider stops retrying — while a transport/DB failure answers 5xx so it does retry.

- F01/BR1 (claim first; a check-then-act guard is forbidden), F10 (system path: `IPaymentLookupQuery` — **BR28: frozen with exactly three members** `ByIdAsync(Guid)`, `ByProviderPaymentIdAsync(string)`, `ByOrderCodeAsync(string)`, never extended — then `ISystemContext.For(userId)`), F11/BR10 (webhook posture; ids-only logs; no PII), F12 (minor-unit normalisation, amount+currency equality, > 10× package price ⇒ `needs_review` + owner alert, `provider_payment_id` collision ⇒ alert and no second grant), F13/BR11 (a late webhook for an expired `order_code` ⇒ `needs_review`), BR17 (the route is never gated by `billing_enabled`; an unmatched event is logged + alerted + 200, **never** a new `payments` row), C6 (`purchase:{paymentId}`, `bonus:{paymentId}`), C7 (lock order `credit_accounts` → `promo_codes` → `payments` → `credit_lots`), D6 (purchase and bonus lots expire 12 months from payment), BR6 (the promo lot with `grant:promo:{promoRedemptionId}` and the redemption row are **12.7.2-T1's** `payment_paid.v1` handler — this task must not write them), D17/C11 (metrics + one alert pipeline), C13 (return URL/checkout wire is 12.3.2-T1's).

## Design

**Endpoint** (`/billing/webhooks/{provider}`): no `[FromBody]` parameter at all — the endpoint reads `HttpRequest.Body` into a pooled buffer (`ArrayPool<byte>`, size known from `Content-Length` with a hard 64 KiB cap; over the cap ⇒ 413 and no DB row), asserts `Content-Type` is JSON-ish only as a log signal (never a gate), resolves `provider` against `Payment:Providers` (unknown ⇒ 404 without touching the DB), then dispatches `ProcessPaymentWebhookCommand(provider, rawBytes, headers)`. Headers are passed as an immutable dictionary of the **whitelisted** header names the adapter's verifier needs. Rate policy `auth`; the diagnostic log line is `payment.webhook.received { provider, eventId, paymentId, result }` — never the body, never the signature.

**Handler `ProcessPaymentWebhookCommand`** — marker `[AllowAnonymousRequest]` (exactly one marker, 09.3.6-T1; CR-11 confirms this is the only anonymous route in the system that writes money state), one `UnitOfWorkBehavior` transaction:

1. `ParseAndVerifyAsync(rawBytes, headers)` ⇒ on failure: insert `payment_events` with `signature_valid = false`, `error = 'signature_invalid'`, `processed_at = now()`, return 401 `webhook_signature_invalid`, increment `billing_webhook_signature_invalid_total`, raise a security alert. No `payments` row is touched.
2. **Resolve, then claim (BR34/CR-18, ruled).** First, a plain read (not the check-then-act *guard* BR1 forbids — that guard is only about the event's own idempotency, next): `IPaymentLookupQuery.ByProviderPaymentIdAsync(providerPaymentId)` when the provider payload carries its own payment id, else `ByOrderCodeAsync(orderCode)` (our merchant reference, always present — BR28's frozen three-member port, never extended). Then **claim**: `INSERT INTO payment_events (id, provider, provider_event_id, payment_id, type, signature_valid, payload, created_at) VALUES (…) ON CONFLICT (provider, provider_event_id) DO NOTHING RETURNING id`, with `payment_id` set from the read above (**NULL** when no `payments` row matched — CR-18 makes `payment_events.payment_id` nullable in 00 §6:301). No returned id ⇒ return 200 `{ received: true }` **without any other statement** (BR1); the claim also protects a manual/bulk replay days later (P2).
3. **Branch on the resolution.** Not found ⇒ fill `payment_events.error = 'payment_not_found'`, log, alert, return 200 (BR17). Found ⇒ open `ISystemContext.For(payment.UserId)` for everything after this point (F10).
4. **Amount gate (F12), before any lot**: `ProviderPayment.AmountMinorUnits == payments.amount` **and** `Currency` equal. Mismatch, or amount > 10× the package price ⇒ `MarkNeedsReview`, alert, `billing_payments_needs_review_total`, return 200. An unknown provider status ⇒ the same.
5. **Status re-fetch** when `Capabilities.StatusApi` **and** the event carried a `providerPaymentId`: `GetPaymentAsync(providerPaymentId)` against the configured base URL only (never a host from the body). Result must be `Paid` with equal amount and currency; `Unknown` or disagreement ⇒ `needs_review` + alert + 200. A provider API error is retried with backoff; when the event is still unprocessed after 30 minutes the row becomes `needs_review` (the retry/escalation itself lives in 12.3.3-T2; this handler records `payment_events.error` and returns 202-equivalent 200 only after the escalation, or leaves the event unprocessed so the provider's own retry re-enters here — the escalation path is 12.3.3-T2's `SyncPaymentStatusCommand`). When the event was resolved by `orderCode` alone (no `providerPaymentId` on the payload — e.g. some bank-QR flows), the re-fetch is **skipped** and treated exactly like `Capabilities.StatusApi = false` (acceptance check 7): the grant proceeds on signature + amount match alone.
6. **Grant, then mark paid (BR2 order — credit_accounts before payments, F06 fix).** `ICreditLedger.GrantAsync(userId, CreditLotSource.Purchase, payments.credits, paidAt + 12 months, reference: paymentId, ct)` with `idempotency_key = purchase:{paymentId}` runs **first**: it takes `SELECT … FROM credit_accounts WHERE user_id = @u FOR UPDATE` internally (C7), so `credit_accounts` is locked before the payment row. When `payments.bonus_credits > 0`, a second lot `CreditLotSource.Bonus` with `bonus:{paymentId}` grants in the same call. Only then does `MarkPaid(providerPaymentId, paidAt)` transition and persist the `payments` row — `MarkPaid` writes `payments.provider_payment_id` only when the event actually carried one (a bank-QR flow resolved via `orderCode` alone leaves the column exactly as checkout/12.7.4-T1 last set it — never overwritten with NULL or an unverified value). This ordering is the pinned lock order (`credit_accounts` < `payments`), not a restatement of it.
7. **Effect**: `payments.status = 'paid'`, `payments.paid_at`; outbox `payment_paid.v1` (`{ paymentId, userId, packageId, credits, bonusCredits, amountMinorUnits, currency, provider, paidAt }`); realtime `CreditBalanceChanged { userId }` (ids only); log `payment.grant { paymentId, credits, bonusCredits }`; metric `billing_webhook_received_total{provider,result="paid"}`.
8. **Return** 200 `{ received: true }` for every outcome above; any DB/transport exception ⇒ 5xx (the claim insert rolls back with the transaction, so the provider's retry can claim it again — this is deliberate and tested).

**Reuse by other tasks.** `ApplyVerifiedPaymentAsync(ResolvedPayment payment, ProviderPayment providerPayment, PaymentSource source, ct)` is the internal Application helper that performs steps 4–7; 12.3.5-T1's `ResolvePaymentCommand` (`grant_expected`/`grant_partial`) and 12.3.5-T2's approval call the same helper so admin grants and webhook grants cannot diverge (12.3.5 owns the routes, this task owns the helper). 12.3.4-T1 extends the handler with the `refunded`/`partially_refunded`/chargeback branch.

## Acceptance checks

1. **Given** a valid signature, a `paid` payload whose amount and currency equal the row and (when configured) a status API that agrees, **when** the webhook is posted, **then** the payment is `paid` with `paid_at`, exactly one `purchase` lot (expiry `paid_at + 12 months`) and one `bonus` lot when `bonus_credits > 0`, `payment_paid.v1` is queued once, `CreditBalanceChanged { userId }` is emitted and the response is 200 `{ received: true }`.
2. **Given** two identical deliveries posted **in parallel**, **then** exactly one grants credits and the other returns 200 having written nothing else — asserted on `payment_events` (one row), `credit_ledger` (`purchase:`/`bonus:` once each) and the lot sum.
3. **Given** a successful grant, **when** the same event is replayed (manual/bulk replay, P2) hours later, **then** it is a 200 no-op and no ledger or lot row is added.
4. **Given** a tampered body (one byte, whitespace included) or a stale timestamp beyond the tolerance, **then** 401 `webhook_signature_invalid`, one `payment_events` row with `signature_valid = false`, `billing_webhook_signature_invalid_total` +1, an alert, and **no** 5xx.
5. **Given** an amount or currency that differs from the row (or an amount > 10× the package price), **then** `payments.status = needs_review`, zero lots, `billing_payments_needs_review_total` +1, owner alert, 200.
6. **Given** a status API is configured and it answers `Unknown`, `Failed` or a disagreeing amount, **then** `needs_review` + alert + 200; **given** the API errors, **then** the attempt is retried with backoff and the event is not marked processed until it succeeds or escalates.
7. **Given** the provider has no status API, **then** signature + amount match is the only check and the flow still grants — recorded in `DECISIONS.md` by 12.3.1-T1.
8. **Given** a valid `paid` event whose `order_code` matches no `payments` row, **then** 200, a logged+alerted `payment_events` row with `error = 'payment_not_found'`, and **no** new `payments` row (BR17).
9. **Given** a webhook for a payment of user A, **then** only A's `credit_accounts`/lots change; user B's balance is byte-identical afterwards (F10).
10. **Given** a forced DB failure after the claim (e.g. a constraint violation in the grant), **then** the response is 5xx and the `payment_events` claim row is **not** persisted, so the provider's retry can process the event.
11. **Given** an unknown `provider` segment, **then** 404 with no DB access; **given** a body over 64 KiB, **then** 413 with no DB access.
12. **Given** the architecture tests run, **then** the route carries exactly one of `[Audited]`/`[NotAudited]`/`[AllowAnonymousRequest]` (it is `[AllowAnonymousRequest]`) and no other money-writing route is anonymous.
13. **Given** `_12_PaymentEvents` (this task's migration, BR20) is applied to an empty P database, **then** `payment_events (provider, provider_event_id)` unique and `payment_events (payment_id)` exist, and `downgrade` removes exactly them — `_12_Payments` (12.3.2-T1) and `_12_CreditLots` (12.2.1-T1) are unaffected.
14. **Given** a valid `paid` event resolved via `ByOrderCodeAsync` (no `providerPaymentId` on the payload, a bank-QR flow), **then** the status re-fetch is skipped, the grant proceeds on signature + amount alone, and `payments.provider_payment_id` stays exactly as checkout/12.7.4-T1 set it; **given** the same event resolves to no `payments` row at all, **then** the claimed `payment_events` row carries `payment_id = NULL` (CR-18/BR34) and `error = 'payment_not_found'`.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Provider retries the same event while the first attempt is still in flight | The second attempt's claim conflicts ⇒ 200 no-op; no lock contention on `payments` beyond the first transaction |
| `provider_payment_id` already belongs to another payment | `needs_review` + alert; never a second grant (F12); the unique index is the guard, the violation is caught and mapped, not surfaced as 5xx |
| Payment row is already `failed` (expired, BR11) and a late `paid` webhook arrives | `MarkNeedsReview` (a `failed → paid` transition is illegal in the aggregate), alert, 200 — an admin settles it through 12.3.5 |
| Payment row is already `paid` (duplicate with a different event id) | The aggregate's transition guard rejects `paid → paid`; if the ledger keys are already present the handler logs `payment.duplicate` and returns 200 without touching lots |
| Re-fetch disagrees but the signature was valid | `needs_review` — signature validity is never treated as proof of payment on its own when a status API exists |
| Provider sends an event type we do not handle (`pending`, `expired`, arbitrary) | Recorded in `payment_events.type` verbatim, `payment_events.error = 'unhandled_type'`, 200, no state change; no invented enum |
| Refund/chargeback event arrives here | Delegated to 12.3.4-T1's branch of the same handler; the claim is already taken, so the branch runs in the same transaction |
| Outbox write succeeds but the realtime emit fails | Realtime is best-effort (ids only, WT54); the outbox row is authoritative and 12.7.2-T1's promo handler retries from it |
| Clock skew on the provider side | Tolerance from `Payment:WebhookTimestampToleranceSeconds` (300 s), never a hard-coded value |
| The same `order_code` is reused by two payments | `payments.order_code` is unique, so this cannot happen; a lookup by `order_code` therefore resolves at most one row |

## Notes

- **Migration ownership (BR20):** this task owns `_12_PaymentEvents`; `_12_Payments` is 12.3.2-T1's.
- **Flag scope (BR17/BR10):** this task's canonical §8.1 row is `S · M2` with **no** `billing_enabled` flag, and README's §8 note (L331) lists it as never flagged — the two agree. Implementation follows: the webhook route is never gated, because it must settle payments created before a flag flip, and provider retries/replays last ~28 h (P2), so a flip off would strand a paid event.
- Card data never reaches our servers (hosted checkout only, plan §12.3.1); this endpoint only ever sees provider notifications, and the raw body stays in `payment_events.payload` under normal retention rules.
- No `ICreditLedger.ReserveAsync` call here: a grant is not a paid operation, so the `[PaidOperation]` arch test (CR-11) does not apply to this handler.
- i18n: the `payment_needs_review` e-mail template (D17 catalog) ships vi + en with an English fallback even though its audience is admins (D18).
- Idempotency keys used verbatim: `purchase:{paymentId}`, `bonus:{paymentId}` (this task), `grant:promo:{promoRedemptionId}` (12.7.2-T1's handler), `void:{paymentId}:{lotId}` (12.3.4-T1).
