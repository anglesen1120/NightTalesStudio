# 12.3.3-T2 — Payment status sync and anomaly detection jobs

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.3.3 | M (1.0) | BE | 12.3.3-T1, 09.10.2-T1, 11.6.2-T1 (soft) | 12.5.1-T2 (soft), 08.2.2-T1 (08 W3 CR-hand-off) | S · M2 |

## Goal

Close the two holes the webhook alone cannot close: a payment whose webhook never arrives (F13) and a payment pattern that looks like fraud or a settings change nobody noticed (F07/F21). `PaymentStatusSyncJob` (every 10 min) expires stale `pending` rows and re-fetches their provider status; `PaymentAnomalyJob` (every 15 min, only for 24 h after an applied `payment.*` setting change) compares paid count and amount hour by hour with the previous 7 days and alerts. The size move S → M of this task is already inside the canonical row (CR-4).

## Inputs

Skips silently when the provider has no status API (capability flag)"; `PaymentAnomalyJob` every 15 min, for 24 h after any applied `system_setting_changes` row with `integration = 'payment'`, `Retries = 3`, "compares paid count/amount per hour with the same hours of the previous 7 days; alerts > 3× baseline, > 3 purchases by one user in 1 h, or an admin/owner self-purchase".

## Design

**Sweep read model.** Per C10/D17, the pinned `ISystemWorkQuery` interface is never extended, so this task adds a **new** system-only, single-member query — `IPendingPaymentQuery.PageAsync(DateTimeOffset now, int batchSize, CancellationToken ct)` returning `(PaymentId, UserId, OrderCode, ExpiresAt, ProviderPaymentId?)` rows where `status = 'pending'`, ordered by `created_at ASC, id ASC`, `batchSize` default 200. It is registered for system paths only (never injectable into a user request handler) and, like `IPaymentLookupQuery`, is documented as never-to-be-extended; a future need gets a new query. Paging is by `created_at` cursor so a row created mid-run cannot be skipped or double-processed.

**`PaymentStatusSyncJob`** (`[JobPolicy(Queue = JobQueue.Default, Retries = 3)]`, `[DisableConcurrentExecution]`, no arguments):

1. Cheap configuration guard: if `Payment:ActiveProvider` has no provider entry, exit; if `Capabilities.StatusApi` is false, the re-fetch half is skipped but the expiry half still runs (a provider without a status API is a valid outcome, P5 — the user must still be told the order expired).
2. Expiry half: for each page, rows with `ProviderPaymentId == null && ExpiresAt < now` get `ExpirePendingPaymentCommand(paymentId)` dispatched through `ISender`, one per row. The handler (Application, `[NotAudited]`) opens `ISystemContext.For(userId)`, calls `Payment.MarkExpired()` (a `pending → failed` transition with reason `payment_expired`), queues the `payment_expired` e-mail (vi + en) and logs `payment.expired { paymentId, orderCode }`.
3. Re-fetch half: rows with a `ProviderPaymentId` call `SyncPaymentStatusCommand(paymentId)` (`[NotAudited]`) through `ISender`. The handler re-fetches with `IPaymentProvider.GetPaymentAsync` and routes the result through 12.3.3-T1's `ApplyVerifiedPaymentAsync(source: PaymentSource.StatusSync)`:
   - `Paid` with equal amount and currency ⇒ grant exactly like the webhook (ledger keys `purchase:{paymentId}` / `bonus:{paymentId}` make a race with a concurrent webhook harmless).
   - `Failed` ⇒ `MarkFailed`, no lots, log.
   - `Unknown`, `Refunded`, `PartiallyRefunded` or any disagreement ⇒ `MarkNeedsReview` + alert + `billing_payments_needs_review_total` (refunds are 12.3.4-T1's branch when the provider delivers the event; a status-only refund observation goes to `needs_review` for an admin, never straight to voiding).
   - Provider API error ⇒ retried with backoff by the typed `HttpClient` policy and by the job's `Retries = 3`; the row is left `pending` and logged. Escalation: a `pending` row older than 30 minutes **with** a provider id that still cannot be resolved becomes `needs_review` (same escalation as 12.3.3-T1 step 5), so no payment can sit in `pending` forever.
4. Metrics/logs: `billing_payments_needs_review_total`, `payment.status_sync.expired { count }`, `payment.status_sync.refetched { count, result }`. No PII, ids only.

**`PaymentAnomalyJob`** (`[JobPolicy(Queue = JobQueue.Default, Retries = 3)]`, `[DisableConcurrentExecution]`):

1. Watcher: read the latest applied `system_setting_changes` row with `integration = 'payment'` (09.10.2-T1's writer; read-only here). If none exists or `now - applied_at > AnomalyWindowHours` the job exits after one indexed read — the 24 h window is what makes an unnoticed change visible, not a permanent monitoring loop.
2. Baseline query (one grouped query, no N+1, served by `payments (status, created_at)`):
   `SELECT date_trunc('hour', paid_at) AS hour, count(*) AS cnt, sum(amount) AS amount FROM payments WHERE status IN ('paid','partially_refunded') AND paid_at >= @from GROUP BY 1` over the previous `AnomalyBaselineDays` (7) and the current 24 h.
3. Rules: current hour (and the rolling current window) count or amount `> AnomalyFactor` (3×) the median of the same hour-of-day over the baseline days ⇒ alert; one user with `> 3` paid rows in a rolling 1 h ⇒ alert; any `paid` row whose buyer is an `admin`/`owner` ⇒ report (log + digest input for 12.5.1-T2, BR13).
4. Alerts go **only** through 11.6.2-T1 with a stable dedupe key `payment_anomaly:{hourKey}:{rule}`, so the 15-minute cadence does not spam. [INFERENCE] the pipeline accepts a dedupe key; DoR question if it does not (the fallback is to alert only when the *completed* previous hour first trips, which needs one stored marker per rule).
5. No state change: the job never grants, refunds or blocks anything — it is a detector.

**Registration.** Both jobs register with `IRecurringJobManager` when their provider entry is configured; per BR17 neither registration is conditional on `billing_enabled`.

## Steps

1. Add `IPendingPaymentQuery` (single member, system-only registration) + its EF implementation with the cursor paging and the `(status, created_at)` index.
2. Add `ExpirePendingPaymentCommand` + handler and `SyncPaymentStatusCommand` + handler, both `[NotAudited]`, both opening `ISystemContext.For(userId)`.
3. Extract/reuse `ApplyVerifiedPaymentAsync(source)` from 12.3.3-T1 (it takes a source marker so the ledger metrics can tell a webhook grant from a sync grant) — no duplicated grant logic.
4. Implement both jobs with `[JobPolicy(Queue = JobQueue.Default, Retries = 3)]` and `[DisableConcurrentExecution]`, one command per row through `ISender`, and the cheap guards from the design.
5. Add the two recurring registrations (10 min / 15 min) and the anomaly watcher read; wire the alerts through 11.6.2-T1 (CR-8 adds the metric/alert rows to that task's acceptance list).
6. Add the `payment_expired` e-mail template keys to both locale files (D18) and the per-row commands to the DI + arch-test expectations.

## Outputs

- `IPendingPaymentQuery`; `ExpirePendingPaymentCommand`/`SyncPaymentStatusCommand` + handlers; `PaymentStatusSyncJob`; `PaymentAnomalyJob`; the `payment_expired` template (vi + en); the metrics/logs; tests. No new job queue; no new error code (the 409 `payment_expired` code belongs to 12.3.2-T1's API surface).

## Acceptance checks

1. **Given** a `pending` row with no `provider_payment_id` whose `expires_at` is in the past, **when** the sync job runs, **then** the row is `failed`, the `payment_expired` e-mail is queued once, and no lot or ledger row exists.
2. **Given** a `pending` row with a provider id and a status API that answers `Paid` with an equal amount/currency, **when** the job runs, **then** the payment is `paid` with `paid_at` from the provider answer, exactly one `purchase` lot (plus a `bonus` lot when `bonus_credits > 0`) exists, `payment_paid.v1` is queued once, and the next tick neither re-grants it (the `purchase:{paymentId}` key is present) nor re-reads it (the row is no longer `pending`, so the page query excludes it).
3. **Given** a provider API that answers `Unknown` or a disagreeing amount, **then** the row is `needs_review` + alert, with zero lots.
4. **Given** a provider API that always errors, **when** the job and its retries finish, **then** the row is still `pending` and logged, and after 30 minutes the same row becomes `needs_review` (escalation) — no payment stays `pending` indefinitely.
5. **Given** `Capabilities.StatusApi` is false, **when** the job runs, **then** the re-fetch half performs no provider call **and** the expiry half still expires stale rows (breaker against F13).
6. **Given** two parallel runs of the job (e.g. two workers), **then** `[DisableConcurrentExecution]` plus the one-command-per-row dispatch means no payment is granted twice and no ledger key is written twice.
7. **Given** a `payment.*` setting change applied 5 minutes ago, **then** the anomaly job runs; **given** the last change is older than `AnomalyWindowHours`, **then** the job exits after the watcher read with no baseline query.
8. **Given** the current hour's paid amount is `> 3×` the median of the same hour over the previous 7 days, **then** exactly one alert per rule per hour is raised with the dedupe key; **given** one user with 4 paid rows in 1 h, **then** the user rule fires; **given** an `admin` buys a package, **then** it is reported (BR13).
9. **Given** the jobs run for an empty database, **then** both exit green with zero queries beyond the guard reads (no error, no alert).
10. **Given** the arch tests run, **then** both jobs use ids-only arguments, both carry a `[JobPolicy]` with `Queue = JobQueue.Default`, and neither registration is conditional on `billing_enabled`.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Webhook and sync job race on the same payment | Both go through `ApplyVerifiedPaymentAsync`; the ledger keys and the aggregate's `pending → paid` guard make the loser a no-op; the winner's `paid_at` stands |
| Payment row created microseconds after the page query | Cursor paging by `created_at` means the next tick sees it; never skipped, never processed twice |
| A refund observed by the status API (`Refunded`) with no refund event | `needs_review` + alert for an admin — voiding lots requires 12.3.4-T1's reversal path with its amount check, never a status-poll guess |
| Provider status API returns `Paid` for a row that is already `failed` (expired) | `MarkNeedsReview` (illegal transition), alert — an admin settles it through 12.3.5 |
| Huge backlog after an outage (thousands of `pending`) | Batch 200 per tick, ordered oldest-first; the log reports the remaining count so the runbook can widen the page size via config, never by editing the job |
| Anomaly baseline has fewer than 7 days of data (fresh install) | Rules need at least 3 non-zero baseline days; otherwise the job logs `payment.anomaly.insufficient_baseline` and stays silent |
| Settings change applied while the anomaly job is mid-run | Next tick picks up the new `applied_at`; the 15-minute cadence bounds the delay |
| Clock/timezone | All buckets computed in UTC (`timestamptz`); "the same hours of the previous 7 days" is UTC-hour based, documented so the runbook does not expect local hours |
| Provider entry removed from config after payments exist | The re-fetch half logs and skips; the expiry half keeps working; alert when a `pending` row with a provider id cannot be resolved for 24 h |
