# 12.3.4-T1 — Refunds and chargebacks: void every lot of the payment

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.3.4 | S (0.5) | BE | 12.3.3-T1, 12.2.1-T1, 12.6.1-T1 | 12.7.5-T1 | S · M2 |

## Goal

Handle money going **back**: a provider refund or chargeback event must void every `credit_lots` row that carries that `payment_id` — purchase, package bonus and promo bonus alike — leave the balance never below zero, record the shortfall as platform loss, move the payment to `refunded`/`partially_refunded`, and, on a chargeback only, flag the account so paid commands answer 403 `account_under_review` until an admin clears it. This task owns the refund/chargeback branch of 12.3.3-T1's handler plus the reusable reversal routine that 12.7.5-T1's approved refund calls.

## Inputs

- Plan §12.3.4 (verbatim rules): a provider refund/chargeback event voids every lot with that `payment_id` (purchase and bonus lots, including a promo bonus): a negative `adjust` row removes its `remaining` and `credit_lots.voided_at` is set (balance never below zero; any shortfall logged as platform loss); the account is flagged for review on **chargeback** and paid commands return `account_under_review` until an admin clears it. §12.7.5: an approved refund calls the provider refund API (idempotent), voids every lot of that payment (**12.3.4 rule, without the review flag**) and moves the payment to `refunded`/`partially_refunded`.
- D2: `ICreditLedger.VoidPaymentLotsAsync(Guid paymentId, string reason, CancellationToken ct)`; ledger idempotency key `void:{paymentId}:{lotId}` (a duplicate insert is a no-op); lock order `credit_accounts` → `promo_codes` → `payments` → `credit_lots`; `refund:{reservationId}` is a *reservation* refund and is a different thing from this payment-level void.
- D6: `credit_lots` columns verbatim (`user_id, source, amount, remaining, expires_at, payment_id, voided_at` + CR-2b's `voided_reason` and `CHECK (remaining >= 0 AND remaining <= amount)`); voiding sets `voided_at = now()` plus a negative `adjust` row removing `remaining`; a shortfall is `billing_provider_loss_total` + alert.
- F12 (an amount we did not verify is never treated as a grant; the same discipline applies to a reversal amount), F21/C11 (`billing_provider_loss_total`, alerts only via 11.6.2-T1), BR1 (the claim is already taken by 12.3.3-T1, so a replayed refund event is a no-op), BR15 (frozen names), C1 (00 §6:300 `payments.status` values, :302 `refund_requests`), C13/§3.1 (`POST /billing/payments/{id}/refund-request` ⇒ 403 `account_under_review` when the account is flagged).
- Upstream: 12.3.3-T1 (the handler, `payment_events` claim, `ApplyVerifiedPaymentAsync`), 12.2.1-T1 (`VoidPaymentLotsAsync` on the port, `CreditService`), 12.6.1-T1 (lot rows, `source_rank`, the "always through `ICreditLedger`" rule).
- Consumer: 12.7.5-T1 (its approved refund path calls the reversal routine instead of writing lots itself).

## Design

**`Payment.ApplyRefund(MoneyMinorUnits refundedAmount)`** (Domain, extends 12.3.2-T1's aggregate): allowed from `paid` and `partially_refunded`; total refunded amount > 0 and ≤ `amount`; target status `partially_refunded` when the cumulative refund is below `amount`, else `refunded`. Anything else ⇒ `payment_invalid_state` and no lot change.

**`PaymentReversalPolicy.ReverseAsync(Guid paymentId, string reason, bool flagAccount, CancellationToken ct)`** (Application, one transaction, `[Audited]` when invoked from an admin path and `[NotAudited]` from the webhook — the webhook branch reuses the already-open transaction):

1. Resolve the payment and open `ISystemContext.For(payment.UserId)` (F10).
2. `ICreditLedger.VoidPaymentLotsAsync(paymentId, reason, ct)` — the ledger, not this task, takes the `credit_accounts` row lock (C7) and, for **each** lot with that `payment_id` and `remaining > 0` and `voided_at IS NULL`: `voided_at = now()`, `voided_reason = reason`, plus one negative `adjust` ledger row with `idempotency_key = void:{paymentId}:{lotId}`. A lot whose `remaining` is 0 (fully spent) needs no movement and no row — that is exactly the FR-12-14 loss the user eats.
3. Cumulative shortfall: when a negative movement would cross zero (the credits were already spent or reserved), the ledger clamps at zero and reports the clamped amount; this task adds it to `billing_provider_loss_total` and raises an alert (never a negative balance, F04).
4. `payment.ApplyRefund(refundedAmount)` from the event/request amount.
5. When `flagAccount` (chargeback only): set `credit_accounts.review_required_at` + `review_note` (with the reason) through `AccountReviewPolicy.SetAsync`, write an `audit_logs` row with `category = 'billing'`, and raise a security alert to owners.
6. Log `payment.refund.applied { paymentId, voidedLots, creditsRemoved, platformLossCredits, chargeback }`. No e-mail template is created here — the user-facing `refund_decided` mail belongs to 12.7.5-T1 and chargebacks alert owners (D17 catalog is closed).

**Handler branch (`ProcessPaymentWebhookCommand`).** After the claim (BR1) and the payment lookup, a `refunded` / `partially_refunded` / `chargeback` provider event — the provider's own `type` string, recorded verbatim in `payment_events.type` (no invented enum) — calls `PaymentReversalPolicy.ReverseAsync(paymentId, reason: $"provider:{type}", flagAccount: isChargeback)`. Response is 200 `{ received: true }` in every outcome (BR10); only a DB/transport failure is 5xx, and the claim rolls back with it so the provider can retry.

**Account review flag — RULED (BR26/CR-14, F23).** `credit_accounts` gains `review_required_at timestamptz NULL` + `review_note text NULL` (**CR-14**). This task (a) implements the flag behind one seam — `AccountReviewPolicy.IsUnderReviewAsync(Guid userId, CancellationToken ct)` + `SetAsync(Guid userId, string reason, ct)` / `ClearAsync(Guid userId, string note, ct)` — with an **EF-backed implementation over those two columns**; (b) **writes the columns on a chargeback** (with the chargeback reason in `review_note`); and (c) **owns the owner-only `POST /admin/users/{id}/review/clear { note }`** (re-auth, mandatory `note`, `[Audited]` → `billing.review_cleared`; 403 `forbidden` for non-owner admins). Config section is `Payment:` (D10). **No derived fallback and no second table**: the ruled storage is the contract.**Where it is enforced:** a new `AccountReviewBehavior` in the 09 command pipeline (Application, registered in DI alongside `UnitOfWorkBehavior`) short-circuits with 403 `account_under_review` for paid operations **and** for `RequestRefundCommand`, and never for reads, receipts, the webhook or the reversal itself (otherwise a flagged user could never be un-flagged by an admin approve path, and 12.7.5's approve could not complete).

**Idempotency and races.** The event claim (12.3.3-T1) plus `void:{paymentId}:{lotId}` make a duplicate refund event a no-op; the aggregate's transition guard rejects `refunded → refunded` with a different amount; a refund event arriving while a `ReserveAsync` holds the account lock simply waits (row lock), and the reserve then consumes only lots that are still live (12.6.1-T1's rule: `voided_at IS NULL`).

## Steps

1. Extend `Payment` with `ApplyRefund` and its guards (Domain + unit tests), keeping the status values of 00 §6:300 verbatim.
2. Implement `PaymentReversalPolicy` over `ICreditLedger.VoidPaymentLotsAsync`, including the shortfall/`billing_provider_loss_total` reporting and the `void:{paymentId}:{lotId}` key expectations.
3. Add the `refunded`/`partially_refunded`/chargeback branch to `ProcessPaymentWebhookCommand`, calling the policy with the provider's event type as the reason and `flagAccount` only for chargebacks.
4. Add `AccountReviewPolicy` (**EF-backed over `credit_accounts.review_required_at`/`review_note`**, CR-14/BR26) and the owner-only `POST /admin/users/{id}/review/clear { note }` endpoint (re-auth, mandatory note, `[Audited]` → `billing.review_cleared`), plus the `AccountReviewBehavior` pipeline registration returning 403 `account_under_review` for paid operations and refund requests.
5. Write the `audit_logs` (`category = 'billing'`) row for a chargeback and the owners' alert through 11.6.2-T1; increment `billing_provider_loss_total` on any clamped amount.
6. Publish the policy's call surface for 12.7.5-T1 (its `ApproveRefundCommand` calls `ReverseAsync(..., flagAccount: false)`), and document that `refund_requests.provider_refund_id`/`status = completed` stay 12.7.5-T1's writes — this task never touches `refund_requests`.

## Outputs

- `Payment.ApplyRefund`; `PaymentReversalPolicy.ReverseAsync`; the refund/chargeback branch of `ProcessPaymentWebhookCommand`; `AccountReviewPolicy` (EF-backed over `credit_accounts.review_required_at`/`review_note`, CR-14) + the owner-only `POST /admin/users/{id}/review/clear` endpoint; `AccountReviewBehavior`; the chargeback `audit_logs` row; the loss/alert wiring; tests. No new e-mail template, no new error code (403 `account_under_review` and 409 `refund_not_eligible` already exist).

## Acceptance checks

1. **Given** a `paid` payment with a purchase lot (600 remaining) and a package bonus lot (100 remaining) from the same payment, **when** a `refunded` event arrives, **then** both lots have `voided_at` + `voided_reason` set, two negative `adjust` ledger rows exist with `void:{paymentId}:{lotId}` keys, the payment is `refunded`, and the user's balance drops by exactly 700 — with no other user's balance touched.
2. **Given** the refund is partial (amount < `payments.amount`), **then** the status is `partially_refunded` while **every** lot of that payment is still voided (the 12.7.5 rule: no partial lot leaving).
3. **Given** a bonus lot that was already spent before the refund, **then** the negative movement is clamped at zero, `billing_provider_loss_total` increases by the clamped amount and an alert is raised — the balance never goes below zero and no CHECK constraint is violated.
4. **Given** the identical refund event is delivered twice (or replayed hours later), **then** the second delivery is a 200 no-op with no extra ledger row (claim + `void:{paymentId}:{lotId}`).
5. **Given** a chargeback event, **then** the lots are voided as above **and** `credit_accounts.review_required_at` + `review_note` are set (CR-14/BR26), an `audit_logs` row with `category = 'billing'` is written, and a subsequent paid command returns 403 `account_under_review` while `GET /billing/payments/{id}` and the receipt still work; **when** the owner posts `POST /admin/users/{id}/review/clear { note }` (re-auth), **then** both columns are cleared, an `audit_logs` row for `billing.review_cleared` exists, and the paid command works again.
6. **Given** a plain refund (not a chargeback), **then** `review_required_at`/`review_note` stay NULL (the account is **not** flagged) and the user can keep buying; **given** a non-owner admin calls the clear route, **then** 403 `forbidden` and nothing is cleared.
7. **Given** a chargeback while a `ReserveAsync` is holding the account lock, **then** the reversal waits for the lock, and afterwards the reservation's lots are voided/zeroed so a later settle cannot resurrect credits that are gone.
8. **Given** a lot with `remaining = 0` at reversal time, **then** no ledger row is written for it and the payment still transitions (a fully spent purchase is a legitimate refund case with zero recoverable credits).
9. **Given** a refund event for a payment that is still `pending` or already `failed`, **then** `payment_invalid_state` is recorded in `payment_events.error`, no lot is touched, and the response is 200 with an alert for an admin (12.3.5).
10. **Given** 12.7.5-T1's approved refund runs, **then** it calls the same policy with `flagAccount: false`, producing byte-identical lot/ledger effects to a provider refund event (proved by running both paths in one test against the same seed).
11. **Given** the arch tests run, **then** no code outside `ICreditLedger` writes `credit_lots` or `credit_ledger` (the reversal goes through the port) and the refund branch does not add a second `[AllowAnonymousRequest]` marker.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| Provider refund amount is smaller than the voided credits (fees withheld) | Status is set from the provider's amount; the lot void is always full for that payment; the difference is reported as `billing_provider_loss_total` (never a partial lot leaving) |
| Chargeback arrives before the payment is `paid` (bank reversal of an unsettled order) | `payment_invalid_state` recorded, no lot change, `needs_review` + alert — an admin decides through 12.3.5 |
| Refund event for a payment whose lots were already voided by an earlier chargeback | No-op by keys; status stays `refunded`; log `payment.refund.duplicate` |
| Provider sends a `refund` event with no amount | Treat as a full refund only when the event explicitly covers the whole order; otherwise `needs_review` + alert — never widen a void from an ambiguous payload |
| Admin clears the review flag while a chargeback is still open at the provider | The flag's clear is audited; a later chargeback event re-flags it (the predicate/column is re-set), so clearing is not a way to launder a new chargeback |
| The user has an open reservation when the refund lands | Row lock ordering: the reversal waits, then voids; the reservation's release path (12.6.1-T1/F06) re-removes anything returned to a voided lot with `void:{paymentId}:{lotId}` |
| `refund_requests` row exists and its approve is in flight | This task does not write `refund_requests`; 12.7.5's approve is idempotent on the provider refund id and calls the same policy, so both orders of arrival converge on one lot state |
| Lots total is already zero but the payment is `paid` | The reversal still transitions the payment and logs a zero-void result; no ledger row is written (nothing to remove) |

## Notes

- **Account review storage is RULED (BR26/CR-14, F23):** the chargeback flag is `credit_accounts.review_required_at` + `review_note` — written here on a chargeback, cleared by the **owner-only** `POST /admin/users/{id}/review/clear { note }` owned by this task (re-auth, mandatory note, `[Audited]` `billing.review_cleared`). An unreviewed account keeps returning 403 `account_under_review` on paid commands and is listed in the minted digest. No second storage and no derived fallback remain in this task.
- **Flag scope:** README's §8 note (L331) lists this task among those "never flagged" and its canonical §8.1 row carries no `billing_enabled` flag — the two agree. Implementation follows: the refund/chargeback path is never gated, so a payment created before a flip (or replayed by the provider) can always be reversed.
- **Do not confuse the two refunds:** `refund:{reservationId}` (12.2.1-T1) returns a job's reserve to its lots; `VoidPaymentLotsAsync` (this task) removes payment-backed lots permanently. A chargeback may need both, in that order.
- i18n: no new user-facing copy in this task (the `refund_decided` mail is 12.7.5-T1's); the owners' alert is alert-pipeline text, not UI copy.
- Evidence legend: rules above are from `plans/12-billing-credits.md` §12.3.4/§12.7.5 and README D2/D6/F21 — no vendor API is assumed beyond "a refund/chargeback notification exists", which 12.3.1-T1 verifies (a provider with no refund API is valid, P5: the manual bank fallback applies).
