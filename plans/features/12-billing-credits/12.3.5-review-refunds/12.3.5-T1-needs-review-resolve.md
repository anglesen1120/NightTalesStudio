# 12.3.5-T1 — Admin `needs_review` queue and `ResolvePaymentCommand`

## Goal

Give the operator a queue for payments the webhook path refused to settle (`GET /admin/payments?status=needs_review`) and one audited verb that ends them: `POST /admin/payments/{id}/resolve { action: grant_expected | grant_partial | mark_failed, note }`. A resolve settles the payment (`paid` with the same `purchase:{paymentId}` / `bonus:{paymentId}` grant the webhook writes, or `failed` with no lot) or — above `Credit:ResolveApprovalThresholdCredits` (1,000 credits incl. bonus) or when the resolver owns the payment — parks it in `pending_approval` with a `credit_grant_requests` row and returns 202 `{ creditGrantRequestId }`. The approval half is 12.3.5-T2.

## Design

**Aggregate.** `Payment.Resolve(PaymentResolveAction action, string note, Guid actorId, DateTimeOffset now, ResolveOutcome outcome) → Resolved | PendingApproval` in `NightTales.Domain.Billing.Payments`; guards `Status == needs_review` (else `payment_already_resolved`), non-empty `note`, known action. `PaymentResolveAction { grant_expected, grant_partial, mark_failed }` with the shared snake_case enum converter.

**Arithmetic (pure Domain, unit-tested).** `ResolveCreditArithmetic.Credits(action, receivedMinorUnits, packagePriceMinorUnits, packageCredits)`: `grant_expected` → `packageCredits`; `grant_partial` → `(receivedMinorUnits * packageCredits) / packagePriceMinorUnits` **floored** (D12 — 929,999 ₫ of 1,000,000 ₫ / 1,000 credits grants 929, never 930). Bonus scales `(credits * packageBonusCredits) / packageCredits` floored [INFERENCE — TL confirmation, `../plan.md` §11]. Currency `VND` → `credit_packages.price_vnd`, `USD` → `price_usd`; anything else ⇒ `payment_invalid_state` [INFERENCE]. Approval predicate (D12/O-4): `action != mark_failed && (credits + bonusCredits > Credit:ResolveApprovalThresholdCredits || payment.UserId == actorId)`.

**Handler order (`ResolvePaymentCommandHandler`).**
1. Resolve the owner through the pinned system lookup, then work inside `ISystemContext.For(userId)` (F10 — an unscoped read returns 0 rows silently).
2. `SELECT id, status, expires_at, user_id, amount, currency, credits, bonus_credits, package_id, price_version FROM payments WHERE id = @id FOR UPDATE` (BR2 order `credit_accounts` → `promo_codes` → `payments` → `credit_lots`; the account lock is taken next and the payment re-read under it).
3. `expires_at < now AND status = 'pending'` ⇒ 409 `payment_expired` (BR11 scopes expiry to `pending`; a `needs_review` row is resolvable regardless, `expiresAt` is display-only).
4. Snapshot `credit_packages` + `price_versions`; missing package ⇒ `package_not_found`; currency mismatch ⇒ `payment_invalid_state`.
5. `mark_failed` ⇒ `failed`, `raw` note, no lot, buyer e-mail, `audit_logs`, 200.
6. **Minting gate (F07 fix 2026-09-25 — every grant path shares one cap; `grant_expected`/`grant_partial` only, `mark_failed` exempt since it already returned at step 5).** `pg_try_advisory_xact_lock(hashtext('nts:credit_mint:' || @actorId))` ⇒ false ⇒ 409 `grant_in_progress` (retryable, same wording as 12.3.5-T2). `MintingPolicy.EvaluateAsync(actorId, payment.UserId, credits + bonus, MintingSource.Resolve, ct)` (declared/implemented by **12.5.1-T1**): `Rejected(code)` ⇒ that code, nothing written; `NeedsRequest` **or** the approval predicate below is true ⇒ step 8; otherwise (`Allowed` and the predicate false) ⇒ step 7.
7. Grant path: `SELECT … FROM credit_accounts WHERE user_id = @u FOR UPDATE`, then `ICreditLedger.GrantAsync` for lots `source = purchase` / `bonus`, `payment_id = @id`, `expires_at = now + Credit:PurchasedExpiryMonths`, keys `purchase:{paymentId}` / `bonus:{paymentId}` (a replay finds the keys and is a no-op).
8. Approval path (predicate true, or step 6's `MintingPolicy` returned `NeedsRequest`): insert one `credit_grant_requests` row (`source = admin_grant` (BR33 — the resolve path persists `admin_grant`, discriminated by `target_payment_id`), `target_user_id`, `target_payment_id = @paymentId` (nullable; the resolve discriminator, set for the `promo_code` and resolve sources — CR-15/BR28), `amount = credits + bonus`, `reason = note`, `requested_by = actorId`, `status = pending`, `activates_at = now + Credit:ResolveApprovalHours` (F13 fix — sole-owner time-lock fallback: `CreditGrantRequestApplyJob`, 12.5.1-T2, auto-applies through the same grant path if no second owner decides in time), `requested_at = now`), set `status = pending_approval` + `resolve_requested_by = actorId`, emit `credit_grant_requested.v1`, raise the immediate owner alert + `billing_credit_grant_pending`, return 202 `{ creditGrantRequestId }` — **no** lot, no `payment_paid.v1` (D12/F22).
9. Settled path: `status = paid`, `paid_at = now`, `credits`/`bonus_credits` recorded, `payment_paid.v1 { paymentId, userId, credits, bonusCredits, amount, currency, status }`, `credit_balance_changed.v1 { userId }`, realtime `CreditBalanceChanged { userId }` (ids-only), `audit_logs`, `ETag: "pm-<xmin>"`.
10. Overpayment (`receivedMinorUnits > amount`): the surplus is refunded through `IPaymentProvider.RefundAsync` from an outbox handler (never a DB transaction across an HTTP call), keyed `refund:{paymentId}:overpay` (BR28); with `Capabilities.RefundApi == false` the surplus becomes a manual bank-refund note + owner alert.

**Migration ownership (BR20).** This task owns **no** migration for `credit_grant_requests`: `_12_CreditGrantRequests` (+ index `(status, requested_at)`, F20) belongs to **12.5.1-T1 only**, and this task consumes the table by inserting one `pending` row. Its own migration touches `payments` only — the `payments.status` value `pending_approval` and `resolve_requested_by` (plan §10 contract changes); S-only tables, never in P (09 D9).

**Wire / attributes.** `[Audited]` on the command, `[NotAudited]` on the query; endpoints policy `Admin`, rate policy `hub`, cursor paging `?status=&cursor=&limit=` (max 100, order `created_at DESC, id DESC`); no `If-Match` on POST (D17 requires it on admin `PATCH` only); statuses come from `ErrorCatalogue` by code, never from `ErrorType`.

```sql
SELECT p.id, p.created_at, p.user_id, p.amount, p.currency, p.method, p.order_code,
       p.provider_payment_id, p.expires_at, p.resolve_requested_by, p.status
FROM payments p WHERE p.status = @status
ORDER BY p.created_at DESC, p.id DESC LIMIT @limit;   -- system scope, explicit user projection
```

## Acceptance checks

1. Given a `needs_review` payment, When an admin posts `{ action: "grant_expected", note: "bank transfer matched" }`, Then 200 `AdminPaymentDto` `status = "paid"` with one `purchase:{paymentId}` and one `bonus:{paymentId}` ledger row, one lot each, `paid_at` set, one `audit_logs` row and `payment_paid.v1` + `credit_balance_changed.v1` in `outbox_messages`.
2. Given the same payment resolved twice, Then the second call is 409 `payment_already_resolved` and moves nothing.
3. Given `grant_partial` with `receivedAmount` 929,999 ₫ on a 1,000,000 ₫ / 1,000-credit package, Then exactly 929 credits are granted (rounded down) and `payments.credits` records 929.
4. Given `mark_failed`, Then the payment is `failed`, no lot/ledger row exists, and an empty `note` is rejected (400) before any write.
5. Given `grant_expected` of 1,001 credits incl. bonus, Then 202 `{ creditGrantRequestId }`, `status = "pending_approval"`, `resolve_requested_by` = actor, exactly one `pending` `credit_grant_requests` row, **no** lot and no `payment_paid.v1`, and `billing_credit_grant_pending` rises.
6. Given an admin resolving their own payment, Then the 202 path is taken even below the threshold.
7. Given a payment of another user, Then the handler finds it through the pinned lookup + `ISystemContext.For(userId)` and applies the action (the tenant filter never turns it into "not found").
8. Given a `pending` payment past `expires_at`, Then 409 `payment_expired` and nothing is written.
9. Given `?status=pending_approval&limit=50`, Then the paged `{ items, nextCursor }` row carries `user: { id, email }`, `expectedAmount`, `receivedAmount`, `expiresAt` and `providerEvents`.
10. Given a caller without the `Admin` role, Then 403 `forbidden`; unauthenticated ⇒ 401; neither call changes a metric.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Payment not `needs_review` | 409 `payment_already_resolved`, no write |
| `pending` past `expires_at` | 409 `payment_expired`; left to `PaymentStatusSyncJob` (BR11) |
| Two admins resolve at once | row lock decides; the loser re-reads `paid` ⇒ 409 |
| Grant replayed after a crash | ledger keys make the second insert a no-op |
| Received above package price | granted at the quoted credits; surplus refunded via provider or manual bank-refund note + alert |
| `grant_partial` below price per credit | would floor to 0 ⇒ stay in `needs_review`, 409 `payment_invalid_state` [INFERENCE] |
| Package missing / currency unsupported | `package_not_found` / `payment_invalid_state`, nothing written |
| Provider refund fails | payment stays settled; the refund retries with backoff, then manual note + owner alert |
| Tenant-scope mistake | an integration test asserts a cross-tenant resolve applies, so a silent 0-row read fails the build |
| Exactly 1,000 credits | no approval (strict `>`), asserted by a unit test |
