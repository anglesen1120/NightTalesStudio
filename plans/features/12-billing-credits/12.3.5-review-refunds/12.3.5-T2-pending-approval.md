# 12.3.5-T2 — `pending_approval` four-eyes approval, mint cap and F22 re-alerts

## Goal

Close the `pending_approval` loop opened by 12.3.5-T1: a **different** owner approves (`POST /admin/payments/{id}/resolve/approve`), fulfilling the parked grant under the frozen `purchase:{paymentId}` / `bonus:{paymentId}` keys, or rejects (`.../reject`), returning the payment to `needs_review`. The approval evaluates `MintingPolicy` inside the same transaction under the transaction-scoped advisory lock (busy ⇒ 409 `grant_in_progress`), requires a recent re-auth, and satisfies F22: immediate alert on entry, daily re-alert and a 7-day overdue listing while undecided, **never** an automatic grant.

## Design

**Routes.** `POST /admin/payments/{id}/resolve/approve { note }` and `.../reject { note }` (README §3.1 "`+ /approve, /reject`"; `note` mandatory on both). Policy `Owner` + `IReauthGuard.RequireRecentAsync(5 min)` (D12); rate policy `hub`; no `If-Match` (POST — D17 requires it on admin `PATCH` only).

**`ApproveResolveCommandHandler` order.**
1. Re-auth guard first (its own 09 §5.4 code — no new code here).
2. Resolve the owner through the pinned system lookup, then work inside `ISystemContext.For(userId)` (F10).
3. Lock `credit_accounts` for `payments.user_id` first (`SELECT … FOR UPDATE`), then `SELECT … FROM credit_grant_requests WHERE target_payment_id = @paymentId AND source = 'admin_grant' AND status = 'pending' FOR UPDATE` — BR2 order `credit_accounts` → `promo_codes` → `payments` → `credit_lots` → `credit_grant_requests` (12 CR-28: the request row is BR2's last member, never locked before the account; the earlier wording inverted it). Missing/decided ⇒ 409 `grant_request_not_pending`.
4. Load `payments`; `status != pending_approval` ⇒ 409 `payment_already_resolved`.
5. **F07 gate:** `payments.resolve_requested_by == actorId` ⇒ 403 `forbidden` — the resolver never approves their own resolve (second owner where two exist).
6. `pg_try_advisory_xact_lock(hashtext('nts:credit_mint:' || @requested_by))` ⇒ false ⇒ 409 `grant_in_progress` (retryable).
7. `MintingPolicy.EvaluateAsync(requested_by, payments.user_id, request.amount, MintingSource.Resolve, ct)`: `Allowed` ⇒ fulfil; `NeedsRequest` ⇒ the request stays `pending`, the cap alert fires and the call returns 409 `grant_in_progress` (nothing moves, F22 keeps the row visible); `Rejected(code)` ⇒ 409 with that code.
8. Fulfil: `credit_accounts FOR UPDATE`, `ICreditLedger.GrantAsync` with `purchase:{paymentId}` / `bonus:{paymentId}` (a re-driven approval is a no-op), lots `expires_at = now + Credit:PurchasedExpiryMonths`, `status = paid`, `paid_at`, request `approved` + `decided_by`/`decided_at`/`decision_note`, `audit_logs` (`category = billing`, note included), `payment_paid.v1`, `credit_balance_changed.v1`, realtime `CreditBalanceChanged { userId }` (ids-only), `billing_credits_minted_total{actor}` up and `billing_credit_grant_pending` down, 200 `AdminPaymentDto`.
9. Reject: request `rejected` + decision note, `status = needs_review`, `resolve_requested_by` kept for the audit trail, `payment_needs_review.v1`, `billing_payments_needs_review_total` rises, buyer e-mail `payment_needs_review`, 200 `AdminPaymentDto` with `status = "needs_review"`. Rejecting never grants and never voids.

**F22 with no new job (BR9).** The immediate alert is T1's; the daily re-alert, the `billing_credit_grant_pending` gauge and the 7-day handling ride `CreditsMintedDigestJob` (12.5.1-T2, daily 08:00): a `pending` request older than 7 days is listed as overdue for a manual decision or a manual bank refund — it is **not** expired while its payment is still `pending_approval` (12 CR-29: expiring it would leave the payment unresolvable forever — approve/reject gate on `status = 'pending'`). **Sole-owner fallback (12 CR-30):** when no second owner exists, the request is written with `activates_at = now() + Credit:ResolveApprovalHours` (same mechanism as 12.7.2-T2's promo path) and `CreditGrantRequestApplyJob` (12.5.1-T2) applies it through the same writer with `decided_by = 'system:time-lock'` — a sole owner is never a dead end. The digest query this needs: `SELECT … FROM credit_grant_requests WHERE status = 'pending' AND requested_at < now() - interval '7 days'` (index `(status, requested_at)`, F20) plus the "still pending" count for the daily re-alert — a cross-folder input to 12.5.1-T2; §8.1's `Depends on` is unchanged.

**Concurrency.** Two owners approving at once: both lock the request row; the loser sees `approved` ⇒ 409 `grant_request_not_pending`. Approval racing a late `paid` webhook for the same payment: the payment row lock plus `purchase:{paymentId}` / `bonus:{paymentId}` guarantee exactly one grant set (BR4/D9), and the loser's write hits the `pending_approval` guard.

```sql
SELECT p.id, p.user_id, p.resolve_requested_by, p.status
FROM payments p JOIN credit_grant_requests r
  ON r.target_payment_id = p.id AND r.source = 'admin_grant'
WHERE p.id = @paymentId AND r.status = 'pending'
FOR UPDATE OF p, r;   -- the door this task closes: resolver != approver
```

## Acceptance checks

1. Given a `pending_approval` payment and a **different** owner with a recent re-auth, When they approve with a note, Then 200 `AdminPaymentDto` `status = "paid"`, one `purchase:{paymentId}` and one `bonus:{paymentId}` ledger row, lots created, request `approved` with `decided_by`, one `audit_logs` row, `payment_paid.v1` + `credit_balance_changed.v1` emitted and `billing_credits_minted_total{actor}` incremented.
2. Given the approval replayed after a crash, Then the second call is a no-op (keys found) and no second lot exists.
3. Given `resolve_requested_by == actorId`, Then that actor's approve returns 403 `forbidden`, the request stays `pending` and no lot is created.
4. Given `reject` with a note, Then the payment is `needs_review`, the request is `rejected` with the note, `payment_needs_review.v1` is emitted and no lot exists.
5. Given two concurrent approvals, Then exactly one returns 200 and the other 409 `grant_request_not_pending`, with exactly one grant set.
6. Given a stale re-auth, Then the guard refuses before any read and nothing moves.
7. Given a decided request, Then approve/reject return 409 `grant_request_not_pending`; given a payment no longer `pending_approval`, 409 `payment_already_resolved`.
8. Given the minting advisory lock held for the requesting actor, Then approve returns 409 `grant_in_progress` and the payment stays `pending_approval`.
9. Given a request older than 7 days and still `pending`, When the digest job runs, Then the request is `expired`, the payment stays `pending_approval`, it is listed as overdue and no lot was created.
10. Given any pending request, Then the daily digest reports it (`billing_credit_grant_pending` + re-alert) and no code path creates a lot without an explicit approval.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Resolver == approver | 403 `forbidden`, request untouched |
| Single-owner deployment | stays `pending_approval`; re-alerts + overdue listing keep it visible, **never** auto-granted (F22) |
| Mint cap exhausted for the requesting actor | `NeedsRequest` ⇒ 409 `grant_in_progress`, request stays `pending`, cap alert |
| Advisory lock busy | 409 `grant_in_progress` (retryable; identical wording to T1) |
| Request row missing (12.5.1-T1's migration not applied) | 409 `grant_request_not_pending` + owner alert, no fallback grant |
| Crash between grant and status write | one transaction: both or neither; a re-drive is a no-op via the ledger keys |
| Payment settled by a late webhook while pending | 409 `payment_already_resolved`; the request is closed `expired` with a note [INFERENCE] |
| Non-positive request amount | impossible by construction (T1 writes `credits + bonus > 0`); the handler still asserts it and returns 409 `payment_invalid_state` |
