# 12.7.5-T1 — Buyer refund requests, admin approve/reject and lot voiding

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.7.5 | S (0.5) | BE | 12.3.4-T1, 12.6.1-T1, 12.3.3-T1 | 12.7.3-T1 (soft), 10.9.2-T1 (10/08 CR-hand-off) | S · M2 |

## Goal

Let a buyer unwind an unused purchase and let an admin decide it: `POST /billing/payments/{id}/refund-request { reason }` creates a `pending` `refund_requests` row whose `credits` is the FR-12-14 amount (remaining purchased credits of that payment − bonus credits of that payment already spent) inside the 14-day window; `GET /admin/refund-requests` is the queue; `POST /admin/refund-requests/{id}/approve` calls the provider refund (idempotency key `refund:{refundRequestId}`) and then voids **every** lot of the payment, bonus included, via `VoidPaymentLotsAsync` — moving the payment to `refunded`/`partially_refunded` **without** the review flag a chargeback sets; `…/reject` stores the reason and e-mails the buyer.

## Design

**Request (`RequestRefundCommand`).** Tenant-scoped (`IUserOwned`): another user's payment ⇒ 404 not-found (no existence disclosure; no 12 error code is coined for it). Order: load the payment by id within the user scope → guards → arithmetic → insert.
- Guards (all ⇒ 409 `refund_not_eligible` unless noted): `status ∈ { paid, partially_refunded }`; `paid_at + 14 d >= now` (O-3, FR-12-14 — the window gates **creating** the request [INFERENCE]); account not flagged (`account_under_review` 403 is set by 12.3.4-T1 and cleared by an admin); `refundableCredits > 0`.
- Arithmetic (`NightTales.Domain.Billing.Payments.RefundArithmetic`, unit-tested): `refundableCredits = max(0, remainingPurchasedCredits(paymentId) − spentBonusCredits(paymentId))` from `credit_lots` where `payment_id = @id` (`source = purchase` / `bonus`, `voided_at IS NULL`); `amount = floor(refundableCredits * payments.amount / payments.credits)` in the payment currency's minor units (README §5.6 worked example: 1,000 purchased, 70 bonus spent ⇒ 930 credits) [INFERENCE on the money rounding — TL confirmation in `../plan.md` §11].
- Idempotency: a `pending` row for the payment already existing ⇒ return it (200) instead of a second row; a partial unique index `refund_requests (payment_id) WHERE status = 'pending'` is the backstop (addition to F20's index list). Rejected/expired rows do not block a new request while the window still allows it.
- Writes: one `refund_requests` row (`status = pending`, `credits`, `amount`, `reason`), one `audit_logs` row (`category = billing`), owner-visible queue row; **no** lot or ledger movement at request time. `PaymentDetailDto` keeps exposing `refundEligible` + `refundableCredits`, computed by this task's `IRefundEligibility` (BR32 — rendered by 12.7.3-T1 through the soft edge `12.7.3-T1 Depends 12.7.5-T1`), so the SPA can show the amount before sending (FR-12-14).

**Queue (`GetAdminRefundRequestsQuery`).** `{ items: (RefundRequestDto & { user, payment })[], nextCursor }`, `?status=&cursor=&limit=` (max 100), order `created_at DESC, id DESC` on the F20 index `refund_requests (status, created_at)`; run under the system scope with an explicit user projection (F10).

**Approve (`ApproveRefundRequestCommand(Guid RefundRequestId, string Note)`).** Policy `Admin`; the approver must not be the payment's owner (a `refund_requests` row is buyer-initiated, so an admin who is also the buyer is refused with 403 `forbidden`) [INFERENCE].
1. Lock order `credit_accounts` → `refund_requests` → `payments` → `credit_lots` (BR2); request must be `pending` ⇒ else 409 `refund_request_not_pending` (12 CR-7/BR28 — never `refund_not_eligible`); payment must still be `paid`/`partially_refunded` (else 409 `refund_request_not_pending`).
2. **Recompute** `refundableCredits` at approve time (lots may have been spent since the request): 0 ⇒ 409 `refund_not_eligible` with a decision note; lower than requested ⇒ the request's `credits`/`amount` are updated once and the decision note records the change [INFERENCE].
3. Provider branch (`Payment:Providers[active].Capabilities.RefundApi == true`): the decision commit sets `status = approved` + `decided_by`/`decided_at`/`decision_note`, then the outbox handler calls `IPaymentProvider.RefundAsync` with key `refund:{refundRequestId}` (never inside the DB transaction) and, on confirmation, opens the follow-up transaction that sets `provider_refund_id` and calls `VoidPaymentLotsAsync(paymentId, "refund:{refundRequestId}")`.
4. Manual branch (`RefundApi == false`, ⚠️[OPEN] until a provider without a refund API is chosen, BR28): the approve call sets `status = awaiting_manual_confirmation` with **no** void; the operator then confirms the transfer with `POST /admin/refund-requests/{id}/confirm { bankReference }` (CR-16), which stores `refund_requests.bank_reference` (CR-15), keeps `provider_refund_id` null and runs the void in that transaction.
5. Confirmation (either branch): lots voided for the whole payment (purchase **and** bonus **and** promo bonus of the same `payment_id`) ⇒ `remaining = 0`, `voided_at`, `voided_reason` and one `adjust` ledger row per voided lot (`amount = −remaining`, BR18 sign convention); `payments.status = refunded` when `refund_requests.amount == payments.amount` else `partially_refunded`; `credit_balance_changed.v1 { userId }` + realtime `CreditBalanceChanged { userId }` (ids-only); `refund_completed.v1 { refundRequestId, paymentId, userId, status }`; `refund_decided` e-mail; `audit_logs`; FR-12-3 invariant re-checked in an integration test. A refund never sets the account review flag (only a chargeback does — 12.3.4-T1).
6. Provider failure: the outbox handler retries with backoff; after the retry budget, a P-alert through 11.6.2-T1 and the row stays `approved` with **no** void — credits are never voided without a confirmed refund. The retry is safe because of the frozen idempotency key.

**Confirm (`ConfirmRefundRequestCommand(Guid RefundRequestId, string BankReference)`).** Policy `Admin`; only from `awaiting_manual_confirmation` (else 409 `refund_request_not_pending`), stores `bank_reference` (CR-15), keeps `provider_refund_id` null and runs step 5 in that transaction.

**Reject (`RejectRefundRequestCommand`).** `status = rejected`, decision note stored, no void, `refund_decided` e-mail to the buyer, `audit_logs`. Rejecting is terminal for that row; the buyer may request again while the window allows.

**i18n / metrics.** vi + en `billing.refund.*` (`request.form`, `notEligible`, `decided`, `amount.before`), `admin.billing.refundRequests.queue.*`; no new metric name is invented — F21's list is closed, and refund decisions are counted through the existing admin surface [OPEN: if a queue-depth metric is wanted it must be added to 11.6.2-T1's list — report §11].

## Acceptance checks

1. Given a `paid` payment 3 days old with 1,000 purchased credits and 70 bonus already spent, When the buyer requests a refund, Then 200 `RefundRequestDto` with `credits = 930`, `status = "pending"` and `amount = floor(930 × payments.amount ÷ 1000)`, plus exactly one `refund_requests` row and one `audit_logs` row, and no lot/ledger change.
2. Given the same payment with a `pending` request, Then the call returns that row (200) and the partial unique index guarantees no second `pending` row.
3. Given `paid_at` 15 days ago, Then 409 `refund_not_eligible` and nothing is written.
4. Given a fully spent purchase (`remaining purchased = 0`) or `spentBonus >= remainingPurchased`, Then 409 `refund_not_eligible`.
5. Given a flagged account, Then 403 `account_under_review`; given another user's payment, 404.
6. Given an admin approve with `RefundApi == true`, Then the provider refund is invoked exactly once with key `refund:{refundRequestId}`, every lot of that payment is voided (`remaining = 0`, `voided_reason` set), `payments.status` is `refunded` when the approved amount equals the collected amount (else `partially_refunded`), `refund_completed.v1` + `credit_balance_changed.v1` are emitted, the `refund_decided` e-mail is queued, and `SUM(credit_ledger.amount) = SUM(credit_lots.remaining)` still holds.
7. Given `RefundApi == false`, When an admin approves, Then `status = "awaiting_manual_confirmation"` and no lot is voided; When the admin then posts `{ bankReference }` to `/admin/refund-requests/{id}/confirm`, Then the lots are voided and `refund_requests.bank_reference` is stored with `provider_refund_id` null.
8. Given a second approve (or a `confirm`) on a decided request or a payment that is no longer `paid`/`partially_refunded`, Then 409 `refund_request_not_pending` and no second provider call.
9. Given a reject with a reason, Then `status = "rejected"`, the reason and decider are stored, the lots are untouched and the buyer is e-mailed.
10. Given a request approved after a provider failure, Then the retry uses the same idempotency key, the void happens only once, and no path voids lots without a confirmed refund or a stored bank reference.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Request not `pending` (already decided) | 409 `refund_request_not_pending` (12 CR-7/BR28 — never `refund_not_eligible`) |
| Lots spent between request and approve | recomputed once, decision note records the change; 0 ⇒ 409 + note |
| Provider refund API absent | manual branch: approve ⇒ `awaiting_manual_confirmation` (no void); `POST /admin/refund-requests/{id}/confirm { bankReference }` ⇒ void + `bank_reference` stored |
| Provider refund timeout/5xx | outbox retry with backoff, same key; after the budget an alert + row stays `approved`, no void |
| Chargeback for the same payment while a request is pending | 12.3.4-T1 voids the lots and flags the account; this handler's recompute sees `refundableCredits = 0` ⇒ 409, no double refund |
| Buyer requests again after a rejection | allowed while the 14-day window holds and `refundableCredits > 0` |
| Payment `partially_refunded` already | allowed; the arithmetic uses the still-live lots, and status stays `partially_refunded` unless the new amount closes it out |
| Approver is the buyer (admin buying a package) | 403 `forbidden` |
| Currency without minor units (VND) | amounts are integers; `floor` keeps them integral |
| Concurrency on the account lock | `credit_accounts FOR UPDATE` serialises a refund against a concurrent spend; a spend that wins reduces the refundable amount |
