# 12.4.1-T1 — Per-user daily credit spend cap

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.4.1-T1 | S (0.5) | BE | 12.2.1-T1, 02.2.2-T2 | — | S · M2 |

## Goal

Put a hard ceiling on what one account can spend in a UTC day, so that a loop, a bug or an abuser cannot turn credits into provider burn. The cap is enforced **inside** the reserve transaction of `CreditService` (12.2.1-T1) — after the `credit_accounts` row lock, before any lot or ledger write — so every paid command in 02/03/05 that already calls `ICreditLedger.ReserveAsync` is covered with **zero caller edits**, and the P platform-USD cap of `IBudgetGuard` (02.2.2-T2) keeps running on top of it unchanged. Past the cap the command fails with the *same* code the platform cap uses, `spend_cap_reached` (429), plus `retryAfterSeconds` to the next UTC midnight; crossing 80 % raises one deduped admin alert.

## Design

**Domain (`NightTales.Domain/Credits/`).** `CreditSpendCap` — pure, no I/O:

```csharp
public readonly record struct CreditSpendCapDecision(bool Allowed, bool CrossedWarnThreshold, long Used, long Limit)
{
    public static CreditSpendCapDecision Evaluate(long usedToday, long requested, long limit); // usedToday + requested <= limit
    public static bool IsWarnCrossing(long usedBefore, long usedAfter, long limit);            // 0.8 * limit, first crossing only
}
```

Boundary is inclusive (`used + requested == limit` ⇒ allowed). `limit = 0` ⇒ every positive `requested` is refused (fail-closed [DECISION-L]); `limit < 0` ⇒ `ArgumentOutOfRangeException` (also caught by `ValidateOnStart`).

**Application (`NightTales.Application/Credits/`).** `ICreditSpendCapReader` — **one** member, never extended [DECISION-L]:

```csharp
Task<long> UsedTodayAsync(Guid userId, CancellationToken ct);   // charged/open credits of the current UTC day (BR18, per reservation group)
```

Consumed only by `CreditService` (Infrastructure). No new member on `ICreditLedger` (BR3, README:388 — the port is frozen at 02's three signatures + `GrantAsync`/`ExpireAsync`/`VoidPaymentLotsAsync`/`GetOpenReservationAsync`); the cap is enforcement inside the implementation, therefore invisible to callers.

**Infrastructure (`NightTales.Infrastructure/Ledger/`).** Inside `CreditService.ReserveAsync`, in this order, inside the one command transaction:

1. `SELECT user_id FROM credit_accounts WHERE user_id = @userId FOR UPDATE` (existing, 12.2.1-T1);
2. **new** cap gate: `usedToday = await _spendCapReader.UsedTodayAsync(userId, ct)`; `CreditSpendCapDecision.Evaluate(usedToday, bound.ReserveCredits, _options.Value.MaxCreditsPerUserPerDay)`;
3. on refusal ⇒ return `Error.CreditSpendCapReached(retryAfterSeconds, operation)` **before** the balance check and before any insert (no movement, no lot change);
4. on success ⇒ the existing balance check, lot split and `reserve` row, then the warn/block telemetry (below).

```sql
-- CreditSpendCapReader (raw SQL, one round trip, inside the same transaction/connection)
-- BR18: derived per reservation group, never a row count — an open group counts `quoted = Σ|reserve|`,
-- a settled group counts `charged = Σ|settle|`, a group refunded without a settle (`SUM(amount) = 0`) counts 0.
SELECT COALESCE(SUM(COALESCE(s.charged, abs(r.amount))), 0) AS used_today_credits
FROM   credit_ledger r                                        -- one `reserve` row per lot; the group key is the reservation id (= r.id)
LEFT   JOIN (SELECT l.reference_id, SUM(abs(l.amount)) AS charged
             FROM   credit_ledger l
             WHERE  l.kind = 'settle' AND l.reference_type = 'reservation'
             GROUP  BY l.reference_id) s ON s.reference_id = r.id
WHERE  r.user_id = @userId
  AND  r.kind    = 'reserve'
  AND  r.created_at >= @dayStartUtc
  AND  r.created_at <  @dayEndUtc                           -- @dayStartUtc = date_trunc('day', now() AT TIME ZONE 'utc') AT TIME ZONE 'utc'
  AND  NOT EXISTS (SELECT 1 FROM credit_ledger f            -- refunded without a settle: nothing was charged
                   WHERE f.reference_id = r.id AND f.kind = 'refund');
```

Served by the pinned index `credit_ledger (user_id, created_at DESC, id DESC)` (F20, D17). **BR18 sign convention — one convention, identical in 12.2, 12.4, 12.6 and 12.8:** `reserve` = −R, `settle` = −C, `release` = +R (written only with a settle), `refund` = +R with no settle, `grant`/`bonus`/`purchase` positive, `expire` = −remaining, `adjust` ±; per reservation `SUM(amount)` = −R while open, −C once settled, 0 once refunded. The cap is therefore **derived per reservation group, never per row**: the groups opened inside the UTC day count `charged = Σ|settle|` once settled, `quoted = Σ|reserve|` while still open, and 0 when refunded without a settle — no `COUNT(*)` of ledger rows anywhere. Held (paused) reservations count once, as their open hold (D15/F08). The window is **UTC** because D5 defines `retryAfterSeconds` against the next UTC midnight; the app's other daily jobs stay on server-local time and must not be copied here.

**Rejection and alerting.** `Error.CreditSpendCapReached` maps to **429** ProblemDetails: `code = "spend_cap_reached"`, extensions `retryAfterSeconds` (`ceil(seconds to next UTC midnight)`, never `< 1`) and `operation` (the `CreditOperation` wire value), plus a `Retry-After` header in seconds. The platform cap of 02 produces the identical body, so 10.8.x needs one sentence (`billing.errors.spend_cap_reached`, D18). Alerts ride 11.6.2-T1 with stable dedupe keys `credit_spend_cap_warn:user:{userId}:{utcDate}` and `credit_spend_cap_blocked:user:{userId}:{utcDate}` (one per user per UTC day; the alert pipeline owns dedupe — no cached flag, no table). Metric: `billing_credit_cap_reached_total` (the user-credit-cap refusal) and `billing_spend_cap_hits_total{scope}` with `scope = "user"` here (both names frozen by BR30/CR-8 and owned in the metric registry by 12.5.2-T1); 02's guard emits the same counter with `scope = "platform"` [DECISION-L, additive to F21 — reported as a candidate CR].

**Api/Worker touch points:** none beyond the existing ProblemDetails mapper — no endpoint, no job, no route, no DTO. `billing_enabled` never gates this (BR17/O-7, README:410): the cap protects the ledger, not the shop.

## Acceptance checks

- **AC-1** Given a user whose current UTC-day reservation groups total 5,000 credits (`charged = Σ|settle|` for settled groups, `quoted = Σ|reserve|` for groups still open) and `MaxCreditsPerUserPerDay = 5000`, When `ReserveAsync` requests 1, Then `spend_cap_reached` (429), no `credit_ledger` row is added and no lot changes.
- **AC-2** Given 4,900 credits counted for the current UTC day and a cap of 5,000, When `ReserveAsync` requests 100, Then the reserve succeeds (boundary inclusive).
- **AC-3** Given the cap refusal, Then the ProblemDetails carries `retryAfterSeconds` equal to the seconds to the next UTC midnight (± 2 s, never < 1), `operation`, and a `Retry-After` header with the same value.
- **AC-4** Given `MaxCreditsPerUserPerDay = 0`, When any positive reserve runs, Then it is refused (fail-closed); a negative configured value fails startup validation.
- **AC-5** Given 20 concurrent reserves of 300 with a cap of 5,000 and 10,000 credits of balance, Then at most 17 succeed, the successful sum never exceeds 5,000, every refusal is `spend_cap_reached`, and no lot or ledger row is written by a refused call.
- **AC-6** Given the funding pause flag is open and a paid command reserved 300 credits while paused, Then those 300 are counted toward the day (a later reserve sees them) and the paused row is never swept by the reconciliation job (12.2.3-T1, BR5/BR14).
- **AC-7** Given `usedToday` crosses 80 % of the cap on a successful reserve, Then `billing_spend_cap_hits_total{scope="user"}` and `billing_credit_cap_reached_total` increment and the warn alert key is raised exactly once for that user and UTC day, even when the user crosses 80 % again the same day.
- **AC-8** Given the cap was crossed earlier the same UTC day, When a new reserve is refused, Then the block alert key is raised once for that day (not once per refused call).
- **AC-9** Given a reserve refused by the **platform** cap (02's `IBudgetGuard`), Then the response is byte-identical in shape to the user cap's (same `code`, same extension keys) and the counter is incremented with `scope="platform"`.
- **AC-10** Given a reserve on the first second of a new UTC day, Then `usedToday` is 0 even though the previous reserve was seconds earlier (UTC day boundary, not server-local).
- **AC-11** Given a caller of `ICreditLedger.ReserveAsync` compiled before this task, Then no signature changed and no call site was edited (`Architecture.Tests` and the diff prove it).
- **AC-12** Given a reservation opened and settled inside the UTC day with `quoted = Σ|reserve|` and `charged = Σ|settle|`, Then the day counts the group at `charged` — never `quoted`, never a `COUNT(*)` of ledger rows (BR18); Given a group still open, Then it counts `quoted`; Given a reservation refunded without a settle, Then it counts 0 (`SUM(amount)` = 0 for that group).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `usedToday` read fails (DB error) | The whole reserve command fails (5xx): the cap is fail-closed — a paid command must never proceed when the cap cannot be evaluated |
| Concurrent reserves from the same user | Serialised by the `credit_accounts` row lock (BR2); the cap read is inside that critical section, so no over-spend (AC-5) |
| Reserve refused but the caller already created provider work | Not possible: the reserve is the first step of every `[PaidOperation]` handler and happens inside the command transaction (09.5.2/09.6.1, 12 CR-11) |
| A reservation refunded without a settle the same day | Counts 0 — `SUM(amount)` = 0 for a refunded group and nothing was charged (BR18); a settled charge stays counted even if a later refund returns the credits |
| Cap lowered below `usedToday` by config during the day | Every further reserve is refused until the next UTC midnight; no retroactive movement; documented in the ops note |
| `bound.ReserveCredits` = 0 (a floor of zero) | `used + 0 <= limit` ⇒ allowed; the guard never blocks a genuinely free operation |
| Alert pipeline down | Reserves still succeed/refuse correctly; the alert is best-effort (11.6.2-T1 retries), the metric is the durable signal |
| Held rows after the pause closes | Their reservation re-check (12.8.3-T2) is unaffected; they were counted once (AC-6) |

## Notes

- No new error code: `spend_cap_reached` is already in 09 §5.4 (12 CR-7 lists the four codes 12 adds; this task adds none).
- `retryAfterSeconds` and `Retry-After` always agree; the UI shows a **time**, never "tomorrow".
- The cap is **derived per reservation group** (BR18: an open group counts `quoted = Σ|reserve|`, a settled group `charged = Σ|settle|`, a group refunded without a settle counts 0) and is *not* reset by the sweep — recorded in plan.md §3.1 with the rationale; different net semantics are a config-independent design change (a second reader member) and need their own task.
- `billing_spend_cap_hits_total{scope}` and `billing_credit_cap_reached_total` are the **frozen BR30/CR-8 names** (the registry entry is owned by 12.5.2-T1; *emitted* here at the cap); the two alert keys are additive to F21's list (reported to the README as a candidate CR).
- Backend-only task: the UI consuming the 429 is 10.8.x, whose design task (`<story>-T0 — UI design`, owner rule 2026-09-25) must be approved before those implementation tasks start; this task only fixes the response shape.
