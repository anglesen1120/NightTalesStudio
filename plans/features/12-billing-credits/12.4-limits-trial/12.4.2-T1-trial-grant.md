# 12.4.2-T1 — Trial credits on e-mail verification

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.4.2-T1 | S (0.5) | BE | 12.2.1-T1, 09.3.1-T1, 09.10.6-T1 (soft, `registration.trial.credits` owner-editable source of truth) (09 W3 CR-13) | 12.8.3-T1 | S · M2 |

## Goal

Give every genuine new account exactly one free try, and nothing more: after the e-mail is verified, one `trial` lot of the owner-configured amount is granted with the idempotency key `grant:trial:{userId}` and a 30-day expiry, blocked by a disposable-domain list and an IP/device velocity limit, and **deferred** (outbox `trial_grant_requested.v1`) instead of granted while the flag `trial_grants_paused` (CR-3, BR31) is open. This task owns the only path that creates a trial lot: `GrantTrialCreditsCommand`, its eligibility policy, the published query 12.8.3-T1 sweeps with, and the `trial_granted` e-mail.

## Design

**Domain (`NightTales.Domain/Credits/`).** `TrialEligibility` — pure, no I/O:

```csharp
public enum TrialDenyReason { NotVerified, BlockedDomain, Disabled, AlreadyGranted }
public readonly record struct TrialDecision(long Amount, TrialDenyReason? Deny, bool Defer);

public static TrialDecision Evaluate(bool emailVerified, string emailDomain, long settingsAmount, long seedAmount,
                                     bool trialKeyExists, bool trialGrantsPaused);
```

Order: not verified ⇒ `NotVerified`; domain ∈ list ⇒ `BlockedDomain`; amount (settings, clamped 0…10000, fallback seed) = 0 ⇒ `Disabled`; key exists ⇒ `AlreadyGranted`; trial pause open (`trial_grants_paused`, CR-3) ⇒ `Defer`; else grant. `TrialBlockedEmailDomains` is one **embedded resource** (one lower-case domain per line, punycode); matching is exact or suffix on a label boundary, case-insensitive — `mailinator.com` matches `a.mailinator.com` but not `mailinator.com.evil.com`. A settings key was rejected (it would need a 09.10 CR and a deploy is cheaper than a new config surface for a list that changes rarely) [DECISION-L].

**Application (`NightTales.Application/Credits/`).**

```csharp
[Audited]   // exactly one of the three attributes (09.3.6-T1); audit action credit.trial_granted / credit.trial_denied
public sealed record GrantTrialCreditsCommand(Guid UserId, TrialGrantTrigger Trigger) : IRequest<ErrorOr<Success>>;   // Trigger: EmailVerified | RecoverySweep | Deferred
```

`GrantTrialCreditsCommandHandler`: reads the user (`email_verified_at`, e-mail), reads the settings key `registration.trial.credits`, evaluates `TrialEligibility` against the cached `trial_grants_paused` flag (CR-3, read here; written by 12.8.3-T1), then either

- **grant**: `ICreditLedger.GrantAsync(userId, CreditLotSource.Trial, amount, expiresAt: clock.UtcNow.AddDays(_options.TrialExpiryDays), reference: new CreditGrantReference(TrialUserId: userId))` inside the command transaction — one `credit_lots` row (`source = trial`, no `payment_id`) + one `credit_ledger` row (`kind = grant`, `grant:trial:{userId}`) — then the `trial_granted` e-mail through `IEmailSender` in `ui_locale` (D18); the balance change and realtime signal ride the ledger's existing `credit_balance_changed.v1 { userId }` (no second event from this task);
- **defer**: publish `trial_grant_requested.v1 { userId }` through `[OutboxEvent]` (ids only) and write no lot, no ledger row;
- **no-op**: return success without movement for `NotVerified` / `AlreadyGranted` (races and re-sends must not 500), and for `BlockedDomain` / `Disabled` with an `audit_logs` row carrying the **domain** only.

`ITrialGrantCandidateQuery` — **pinned, one member, never extended** (09.2.3-T1 house pattern, D17):

```csharp
Task<IReadOnlyList<Guid>> PendingAsync(CancellationToken ct);   // verified users with no grant:trial:{userId} row and no open trial_grant_requested.v1
```

Owned here, consumed by 12.8.3-T1's `FundingRunwayJob` (both the recovery sweep and the deferred application). This folder registers **no** job and no `[JobPolicy]` (BR9: `JobQueue.Default`, no new queue); 12.8.3-T1 owns cadence, retries and the per-user `ISystemContext.For(userId)` loop that dispatches one `GrantTrialCreditsCommand` per row through `ISender` (one `SaveChangesAsync` per command, `UnitOfWorkBehavior`, D17).

**Abuse controls.** (a) the disposable-domain list above; (b) one trial per user forever, enforced by the unique `credit_ledger.idempotency_key` (`ON CONFLICT DO NOTHING`) — the real concurrency guard; (c) a **velocity** limit: this task registers the named policy `RateLimitPolicies.Trial` (partition = client-IP hash + the device cookie, permit limit 1 per 24 h) intended for 09's registration/e-mail-verification endpoint; the endpoint attribute itself is **09's to own** (BR30) — this task registers the named policy and files the request with 09, it does not add the attribute to 09's route. It is a velocity limit, not a durable device ledger: nothing in the schema stores a device fingerprint and this plan adds no table [DECISION-L, matching plan §12.4.2's "[DECISION] simple list + rate limit"] — the durable per-user guard still holds if 09 declines the attribute.

**Config.** `CreditOptions.TrialCredits` (seed/fallback), `CreditOptions.TrialExpiryDays` (30), section `Credit` (D10), `ValidateOnStart`; the effective amount is the settings key `registration.trial.credits` (09.10.6-T1). The pause flag `trial_grants_paused` (CR-3) is read through 09.9.1's cached flag service — never a direct `feature_flags` query; this folder never writes it (12.8.3-T1 does).

## Steps

1. Add `TrialEligibility` + `TrialDecision` + the embedded `TrialBlockedEmailDomains` list (Domain) with the matching tests.
2. Add `GrantTrialCreditsCommand` (+`[Audited]`) and its handler — **one** command with one name, no wrapper record (Application).
3. Add `ITrialGrantCandidateQuery` (Application port) + the Infrastructure implementation (raw SQL, no user filter, consumed only by 12.8.3-T1's job).
4. Wire the trigger: 09's verification flow dispatches `GrantTrialCreditsCommand(userId, EmailVerified)` after `email_verified_at` is written (command call, not a second event; C20/12 CR-12b).
5. Publish `trial_grant_requested.v1 { userId }` on the paused path; add the alert (P1-class, 11.6.2-T1) that a trial was deferred.
6. Send `trial_granted` via `IEmailSender`; emit `billing_trial_grant_total{result}` (granted/deferred/already/blocked_domain/blocked_disabled) and reuse `billing_credits_minted_total{actor="trial"}`; log `billing.trial_grant` (userId, amount, decision — never the full e-mail).
7. Register `RateLimitPolicies.Trial` + the partition function (the attribute on 09's verification route is 09's to own, BR30); file the request with 09.
8. Tests per §Tests.

## Acceptance checks

- **AC-1** Given a verified user whose domain is not blocked, When the trigger fires, Then exactly one `credit_lots` row exists (`source = trial`, `expires_at = verified time + 30 days ± 1 s`, `payment_id IS NULL`), one `credit_ledger` row with `kind = grant` and `idempotency_key = grant:trial:{userId}`, one `credit_balance_changed.v1` outbox row, one `trial_granted` e-mail row, and one `audit_logs` row.
- **AC-2** Given the same command runs again (re-send, sweep, deferred event, double dispatch), Then no second lot, no second ledger row, no second e-mail (`UserHasTrial` is true, result `already_granted`).
- **AC-3** Given `registration.trial.credits = 0`, Then no lot, no deferral, no e-mail, metric `blocked_disabled`, and the user can still buy credits (no error surfaced to the caller).
- **AC-4** Given the settings key is absent, Then the amount is `CreditOptions.TrialCredits`; Given the key is outside 0…10000, Then 09.10.6-T1's validation rejects the write and the grant never reads an out-of-range value.
- **AC-5** Given `users.email_verified_at IS NULL`, Then the command returns success with **no** movement and no e-mail (a re-sent verification link is not an error and must not 500).
- **AC-6** Given `mailinator.com` in the list, When a user with `x@mailinator.com` verifies, Then no lot, `billing_trial_grant_total{result="blocked_domain"}` increments, and the audit row contains the **domain** but never the local part; Given `a.mailinator.com` ⇒ blocked; Given `mailinator.com.evil.com` ⇒ **not** blocked.
- **AC-7** Given the `trial_grants_paused` flag (CR-3, written by 12.8.3-T1) is open, When the trigger fires, Then no lot and no ledger row exist, exactly one `trial_grant_requested.v1 { userId }` outbox row is written, and the deferred alert is raised; When the flag closes and 12.8.3-T1's `FundingRunwayJob` applies it, Then the AC-1 state exists exactly once (verified in 12.8.3-T1's test, asserted here only as event uniqueness).
- **AC-8** Given `ITrialGrantCandidateQuery.PendingAsync`, Then it returns verified users with no trial row and no open request, and never a user who already has `grant:trial:{userId}`; a user with an open deferred request is excluded.
- **AC-9** Given the command is invoked through the API/worker pipeline, Then it carries exactly one of `[Audited]`/`[NotAudited]`/`[AllowAnonymousRequest]` (here `[Audited]`), and `Architecture.Tests` finds no trial lot created outside `GrantTrialCreditsCommand`.
- **AC-10** Given the trial lot at the moment of expiry (30 days), Then 12.6.2-T1's `CreditExpiryJob` expires it like any other lot (no trial-specific expiry path exists); Given a refund path, the trial lot is never touched (no `payment_id`).
- **AC-11** Given the rate-limit policy `RateLimitPolicies.Trial`, Then a second verification attempt from the same IP+device partition inside 24 h is rejected by the limiter before the grant runs (and the durable per-user guard remains the backstop). The attribute that applies the policy to 09's verification route is 09's to own (BR30).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two verification triggers race | One wins the unique `grant:trial:{userId}` insert, the loser is a no-op (`ON CONFLICT DO NOTHING`), exactly one lot (AC-2) |
| Flag reads stale (cache) | Worst case the grant defers one cycle late; the recovery sweep retries, and the deferred event is idempotent — never a double grant |
| `GrantAsync` fails after the deferral decision | The command fails (5xx) and the trigger is retried by the verification flow's own policy; no partial state (single transaction, one `SaveChangesAsync`) |
| Realtime notifier down | The balance is still correct on the next read; the e-mail and the ledger row are the source of truth |
| E-mail send fails | The grant stands (money first); the `trial_granted` e-mail is retried by `IEmailSender`'s outbox, never re-granted |
| User deletes the account before applying a deferred grant | The sweep's `ISystemContext.For(userId)` finds no user ⇒ the event is closed as `not_applicable`, no lot, alert only if the count exceeds a threshold |
| Amount changed by the owner between deferral and application | The amount is resolved **at application time** from the settings key, so the owner's new value applies; the `grant:trial` key still guarantees one grant |
| Trial lot expires unused | Ordinary expiry (12.6.2-T1); the user is not re-eligible (the key exists forever) |
| Attacker with fresh IPs/cookies | The velocity limit is evaded; the durable per-user guard still holds and the disposable-domain list still filters. A durable device rule is out of scope (would need a new table + CR) — recorded |
| 09 does not apply the endpoint attribute (BR30: the attribute is 09's to own) | The velocity guard is dropped for M2 with an explicit note in the DoR review; AC-11 becomes a documented gap, the rest of the task is unaffected |
