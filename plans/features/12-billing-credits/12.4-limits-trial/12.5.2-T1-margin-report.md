# 12.5.2-T1 — Margin per day and operation (`GET /admin/usage`)

## Goal

Give the owner the only number that decides whether prices are right: **margin per day × operation**, computed from money actually collected (`payments`, net of refunds) and cost actually metered (`usage_records`) — never from credits × price (F15). One grouped SQL statement, one round trip, no N+1, behind the frozen admin route `GET /admin/usage?from=&to=&operation=` returning `{ items: MarginRowDto[] }`. The same definition is published as `IMarginReportQuery` + `MarginSql` so 12.8.1-T1 (funding view: revenue 7/30 days) and 12.8.4-T1 (the < 50 % package-margin alert) reuse it instead of writing a second revenue query.

## Inputs

- **Contract:** README §3.1 admin usage row (README:232) — `MarginRowDto { day, operation, jobs, creditsCharged, revenueUsd, costUsd, estimatedCostUsd, platformLossUsd, marginPct }`; D11 (README:199) — the report and the set-aside arithmetic it feeds; F15 (README:90) — revenue definition, `estimated` and `platform_loss` sub-totals, one grouped query per (day, operation), no N+1; F20/D17 (README:95, README:202) — pinned indexes; BR7/D16 (README:391, README:201) — one `IFxRateProvider.CurrentAsync()`; BR8 (README:392) — bonus/promo credits are never revenue and revenue is converted at each payment's own `payments.fx_usd_vnd` (CR-15, BR31); BR30 (README:440) — `MarginRowDto`'s `packageCode | null`/`fxRateUsed`/`fxRateDate`, the nullable `marginPct` (null when revenue = 0), `platformLossUsd` derived from `credit_ledger` rows with `reference_type = 'platform_loss'` (no new table), the index `usage_records (created_at, operation)` owned here (12 CR-13, shared with 08.1.1-T1) and the metrics `billing_spend_cap_hits_total{scope}` / `billing_credit_cap_reached_total`; D3/12.1.4-T1 (README:132) — `k = (1+fx_buffer)/((1−margin)×(1−fee_rate))`, `credits(C) = ceil(C × k ÷ credit_usd)`; C18/plan §5.7; plan §12.5.2, plan §5.3 (no new error code).

## Design

**Route and DTO (frozen).** `GET /admin/usage?from=&to=&operation=` ⇒ `200 { items: MarginRowDto[] }`; `MarginRowDto` is exactly README §3.1 — `{ day, operation, jobs, creditsCharged, revenueUsd, costUsd, estimatedCostUsd, platformLossUsd, marginPct }` + `packageCode | null`, `fxRateUsed`, `fxRateDate` (BR30) — and `marginPct` is declared **nullable** (`decimal?`): it is `null` whenever `revenueUsd = 0`, never a div-by-zero; `from`/`to` are UTC `DateOnly` (default: `to` = today, `from` = `to − 29`); `operation` filters `usage_records.operation`. Authorization: 09's `Admin` policy (owner included); **never** behind `billing_enabled` (BR17/O-7, README:410 — reads are always on). No cursor in the DTO (C8), so the window is validated ≤ 90 days ⇒ ≤ 990 rows. Ordering `day DESC, operation ASC`. 10 supplies the vi/en copy and renders `marginPct = null` as "—" (D18; the UI tasks belong to 10.8.x/the admin S screens and need their approved `<story>-T0 — UI design` first, owner rule 2026-09-25).

**Application.** `GetMarginReportQuery(DateOnly From, DateOnly To, string? Operation) : IRequest<ErrorOr<IReadOnlyList<MarginRowDto>>>` + `GetMarginReportQueryValidator` (FluentValidation ⇒ the standard 400; no new error code): `To >= From`, `To − From <= 90 days`, `Operation` ∈ the pinned `usage_records.operation` set (`story`, `story_review`, `story_revision`, `fact_sheet`, `image`, `tts`, `render` + `bible_proposal`, `idea`, `source_find`, `moderation` per 02 CR-4, 00 §6:294) — an unknown value is a 400, never a silent empty list. `[NotAudited]` (a read).

**Infrastructure — one statement** (`Database.SqlQueryRaw<MarginRowDto>`, `Database.RawSqlQuery`), `@toExclusive = to + 1 day 00:00 UTC`:

```sql
WITH cost AS (                                                  -- provider cost, per day × operation
  SELECT (u.created_at AT TIME ZONE 'utc')::date AS day, u.operation,
         COUNT(DISTINCT u.reservation_id) AS jobs,
         SUM(u.cost_usd) AS cost_usd,
         SUM(u.cost_usd) FILTER (WHERE u.estimated) AS estimated_cost_usd
  FROM usage_records u
  WHERE u.created_at >= @from AND u.created_at < @toExclusive
    AND (@operation IS NULL OR u.operation = @operation)
  GROUP BY 1, 2
), charged AS (                                                 -- settled charges, same day/operation
  SELECT (l.created_at AT TIME ZONE 'utc')::date AS day, u.operation,
         SUM(abs(l.amount)) AS credits_charged
  FROM credit_ledger l
  JOIN usage_records u ON u.reservation_id = l.reference_id
  WHERE l.kind = 'settle' AND l.reference_type = 'reservation'
    AND l.created_at >= @from AND l.created_at < @toExclusive
    AND (@operation IS NULL OR u.operation = @operation)
  GROUP BY 1, 2
), platform_loss AS (                                      -- BR30: the day's platform_loss ledger rows
  SELECT (l.created_at AT TIME ZONE 'utc')::date AS day,
         rv.reference_type                       AS operation, -- the reserve row carries the CreditOperation wire value (C13)
         SUM(abs(l.amount) * pv.credit_usd
             / ((1 + pv.fx_buffer) / ((1 - pv.margin) * (1 - pv.fee_rate)))) AS loss_usd
  FROM   credit_ledger l
  LEFT   JOIN credit_ledger rv ON rv.id = l.reference_id      -- reservation id *is* the reserve row's id (C13)
  LEFT   JOIN price_versions pv ON pv.version = l.price_version
  WHERE  l.reference_type = 'platform_loss'
    AND  l.created_at >= @from AND l.created_at < @toExclusive
    AND  (@operation IS NULL OR rv.reference_type = @operation)
  GROUP  BY 1, 2
), revenue AS (                                                 -- payments, net of refunds
  SELECT (COALESCE(p.paid_at, p.created_at) AT TIME ZONE 'utc')::date AS day,
         SUM(CASE p.status
               WHEN 'paid'               THEN @toUsd(p.amount, p.currency, p.fx_usd_vnd)
               WHEN 'partially_refunded' THEN @toUsd(p.amount, p.currency, p.fx_usd_vnd) - COALESCE(r.refunded_usd, 0)
               ELSE 0 END) AS revenue_usd
  FROM payments p
  LEFT JOIN (SELECT rr.payment_id, SUM(@toUsd(rr.amount, p2.currency, p2.fx_usd_vnd)) AS refunded_usd
             FROM refund_requests rr JOIN payments p2 ON p2.id = rr.payment_id
             WHERE rr.status = 'approved' GROUP BY rr.payment_id) r ON r.payment_id = p.id
  WHERE p.status IN ('paid','partially_refunded','refunded')
    AND COALESCE(p.paid_at, p.created_at) >= @from AND COALESCE(p.paid_at, p.created_at) < @toExclusive
  GROUP BY 1
), day_ops AS (                                                 -- a revenue-only day still gets a row
  SELECT day, operation FROM cost UNION SELECT day, operation FROM charged
  UNION SELECT day, 'all' FROM revenue
  WHERE @operation IS NULL
    AND NOT EXISTS (SELECT 1 FROM cost c WHERE c.day = revenue.day)
    AND NOT EXISTS (SELECT 1 FROM charged ch WHERE ch.day = revenue.day)
), alloc AS (
  SELECT d.day, d.operation, COALESCE(c.jobs,0) AS jobs, COALESCE(ch.credits_charged,0) AS credits_charged,
         COALESCE(c.cost_usd,0) AS cost_usd, COALESCE(c.estimated_cost_usd,0) AS estimated_cost_usd,
         COALESCE(pl.loss_usd,0) AS platform_loss_usd,
         COALESCE(r.revenue_usd,0) AS day_revenue,
         SUM(COALESCE(c.cost_usd,0)) OVER (PARTITION BY d.day) AS day_cost,
         ROW_NUMBER() OVER (PARTITION BY d.day ORDER BY COALESCE(c.cost_usd,0) DESC, d.operation) AS rn
  FROM day_ops d
  LEFT JOIN cost c USING (day, operation)
  LEFT JOIN charged ch USING (day, operation)
  LEFT JOIN platform_loss pl USING (day, operation)
  LEFT JOIN revenue r ON r.day = d.day
), share AS (
  SELECT *, ROUND(day_revenue * cost_usd / NULLIF(day_cost, 0), 4) AS revenue_share,
         day_revenue - SUM(ROUND(day_revenue * cost_usd / NULLIF(day_cost, 0), 4)) OVER (PARTITION BY day) AS remainder
  FROM alloc
)
SELECT day, operation, jobs, credits_charged, cost_usd, estimated_cost_usd, platform_loss_usd,
       CASE WHEN day_revenue = 0 THEN 0 ELSE revenue_share + CASE WHEN rn = 1 THEN remainder ELSE 0 END END AS revenue_usd,
       CASE WHEN day_revenue = 0 THEN NULL                                          -- BR30: nullable, never a div-by-zero
            ELSE ROUND((day_revenue - SUM(cost_usd) OVER (PARTITION BY day) - 0) * 100 / day_revenue, 2) END AS margin_pct,
       NULL::text          AS package_code,   -- BR30: always null on this day × operation route (12.8.4-T1's package view sets it)
       @fxRateUsed          AS fx_rate_used,   -- BR30/BR31: read once per request from IFxRateProvider.CurrentAsync()
       @fxRateDate          AS fx_rate_date    -- BR30/BR31: that rate's top-up date, or NULL when the option fallback is used
FROM share
ORDER BY day DESC, operation ASC;
```

**Semantics so the numbers are defensible** (each is a Given/When/Then below):

- `day` is the **UTC** calendar day of the event that produced the money or the cost (settle day for charges, `COALESCE(paid_at, created_at)` for revenue, `usage_records.created_at` for cost) — the report never mixes local time into a money bucket.
- `revenueUsd` — a payment belongs to a **package**, not to an operation, so a day's revenue is **allocated across the day's operation rows by cost share**, the rounding remainder goes to the day's highest-cost row, and the invariant `SUM(revenueUsd per day) == day revenue` is tested. Each payment is converted at **its own** `payments.fx_usd_vnd` (the rate actually paid, 12 CR-15; BR8/BR30), never at the current rate. A fully `refunded` payment contributes 0; a `partially_refunded` one contributes `amount − approved refund_requests.amount` (converted at the same `fx_usd_vnd`); refunds restate the **payment's own day** (re-queries may change a past row, documented). A day with revenue and no usage gets one row with `operation = 'all'` [DECISION-L marker value; §Notes]. Bonus/promo credits never appear here (BR8): revenue is money, not credits.
- `creditsCharged` — magnitude of the **settle** rows for the reservations whose usage rows carry that operation. `abs()` is deliberate: the ledger states the magnitude (12.2-ledger/plan.md:67–68); a test pins `report.creditsCharged == SettleResult.Charged` so a sign change in the ledger breaks a test instead of silently negating margin.
- `estimatedCostUsd` is a **sub-total of** `costUsd` (D11).
- `platformLossUsd` is **derived from `credit_ledger` rows with `reference_type = 'platform_loss'`** (BR30): the settle-cap hits, the negative-balance writes, the late `usage_records` rows of F25 and the void shortfalls are written there by 12.2.1-T1/12.6.1-T1, and this report only sums the window's rows — converting the credit magnitude with the same price-equivalent arithmetic it uses for `creditsCharged` (`× credit_usd ÷ k` of the reservation's `price_version`, C18) inside `MarginSql`. **No new table, no new column**, no second cost derivation; `estimated` rows keep feeding the `estimatedCostUsd` sub-total (F25).
- `marginPct = ROUND((revenueUsd − costUsd) / revenueUsd × 100, 2)`, **`null` when `revenueUsd = 0`** — **BR30**: the DTO field is `decimal?` and a cost-only row is never 0 %, never "−∞ %".
- FX and the row's FX disclosure: `@toUsd(amount, currency, fxUsdVnd) = amount` for `USD`, `amount ÷ fxUsdVnd` for `VND` (the only two currencies `payments` can carry). Revenue uses **the payment's own** `payments.fx_usd_vnd` (12 CR-15; `@toUsd(…, p.fx_usd_vnd)`, BR8/BR30 — never the current rate); where a rate must be shown or no payment rate exists, `@fxUsdVnd` is read **once per request** from `IFxRateProvider.CurrentAsync()` (BR7/D16 — the latest `provider_topups.fx_rate`, fallback `Credit:FxUsdVndFallback`) and the row discloses it as `fxRateUsed` with `fxRateDate` = that rate's date (the top-up date, or `null` when the option fallback is used — BR31/D11). `packageCode` is `null` on these day × operation rows: the field exists so 12.8.4-T1's per-package margin uses the same DTO and `MarginSql`, without a second revenue definition.
- A `platform_loss` row whose `price_version`/`credit_usd` cannot be resolved contributes 0 and is counted in the `billing.margin_report` log's `unpricedReservations`, never guessed.

**Performance.** `credit_ledger (reference_type, reference_id)` serves the settle and `platform_loss` joins, `payments (status, created_at)` the revenue range and `refund_requests (status, created_at)` the refund netting (F20/D17 ✅). This task **owns the pinned index `usage_records (created_at, operation)` (12 CR-13, also used by 08.1.1-T1)**, added by its own migration: the cost scan filters `created_at` **without** `user_id`, so the `usage_records (user_id, operation, created_at)` index (leading `user_id`) cannot serve it. The whole report is **one** command — asserted by a command-interceptor counter.

**Security.** The only user-filter-free read in this folder: reachable through `GetMarginReportQuery` only, `Admin`-guarded at the endpoint, the query class on the architecture-test allow-list of system reads (F10: a global read must be explicit). It returns **aggregates only** — no user id, no e-mail, no payment row.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| No usage rows and no payments in the window | 200 with `items: []` — not an error |
| `IFxRateProvider` has no top-up yet (pre-sales) | `Credit:FxUsdVndFallback` is used (validated at boot, D16/BR7); the log records `fxSource = fallback` |
| `payments.currency` is neither USD nor VND | `@toUsd` returns 0 and the row is logged as `unexpectedCurrency` (the schema can only be VND/USD; a third value is a bug, alerted by the existing anomaly path, never silently converted) |
| A `pending`/`needs_review` payment | Excluded from revenue (money not collected yet); it surfaces in the payment list, not here |
| A refund plus a partial refund on the same payment | Both approved requests are summed by the refund CTE ⇒ the payment's net is reduced once |
| Refund recorded after the window | The payment's own day is restated when re-queried (documented); the funding view's 7/30-day numbers move with it |
| `price_versions` missing for a `platform_loss` row | contributes 0 + `unpricedReservations` logged (AC-12) |
| A reservation is still running when the report is read | No `platform_loss` row exists for it yet (12.2.3-T1 only writes one once the BR5 stale margin passes unsettled), so it is not reported as loss (AC-6) |
| A job settles minutes after the report was read | The next query shows the charge in `creditsCharged` and no `platform_loss` row for it — the report is a point-in-time read, never a stored total |
| Large window | Rejected by the validator (≤ 90 days) ⇒ bounded scan and ≤ 990 rows |
| Clock/time zone confusion | Every bucket is UTC; tests run with a non-UTC `TZ` to prove it |
| Report row count explodes after a schema change | A single log line with `rows`; no paging (the DTO has no cursor) — a widening beyond 90 days is a new task |
