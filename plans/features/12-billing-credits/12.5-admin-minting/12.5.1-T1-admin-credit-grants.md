# 12.5.1-T1 — Admin credit grants, adjustments and `MintingPolicy`

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

Credits enter the platform without a payment in four ways; the one a human controls directly is the admin grant. Ship the minting guard (`MintingPolicy`) and the write path behind `POST /admin/users/{id}/credits` so that a single admin — compromised or dishonest — cannot mint unchecked: no self-grants, no grants to `admin`/`owner` accounts, a rolling 24 h cap of `Credit:MintCapPerActorPer24h` (2,000) summed **inside** the same transaction that moves the credits, under a per-actor transaction-scoped advisory lock, with every movement audited and counted in `billing_credits_minted_total{actor}`. Above the cap nothing moves: the API returns **202** with a `credit_grant_requests` id that an owner must decide (12.5.1-T2), and the owners are alerted immediately.

## Design

**Domain/Application shape.**

```
NightTales.Application/Billing/Minting/
  MintingSource.cs         enum MintingSource { AdminGrant, Resolve, PromoExposure }        // members pinned here (D13 fixes the type only); persisted mapping (BR33, 00 §6:314): AdminGrant/Resolve ⇒ `source = 'admin_grant'`, PromoExposure ⇒ `source = 'promo_code'` — never a literal `payment_resolve`
  MintingDecision.cs       enum MintingDecision { Allowed, NeedsRequest, Rejected }
  MintingEvaluation.cs     sealed record MintingEvaluation(long MintedLast24h, long Cap, long Amount, MintingDecision Decision, ErrorCode? Code)
  MintingPolicy.cs         public abstract Task<ErrorOr<MintingEvaluation>> EvaluateAsync(Guid actorId, Guid targetUserId, long amount, MintingSource source, CancellationToken ct)
  IMintingLedgerQuery.cs   Task<long> MintedLast24hAsync(Guid actorId, CancellationToken ct)
  IPromoExposureQuery.cs   Task<long> ActivePromoExposureAsync(Guid actorId, CancellationToken ct)

NightTales.Application/Billing/Commands/AdminAdjustCreditsCommand.cs
  sealed record AdminAdjustCreditsCommand(Guid TargetUserId, long Amount, string Reason) : IRequest<ErrorOr<AdminAdjustResult>>;
  sealed record AdminAdjustResult(long? CreditGrantRequestId, bool Pending);
```

`MintingPolicy` is called by exactly three commands: this one, `ResolvePaymentCommand` (12.3.5-T1/-T2) and `UpsertPromoCodeCommand` (12.7.2-T1's command, gated by 12.7.2-T2). It is an Application service with two read collaborators injected — no HTTP, no EF in the domain, testable with `NightTales.TestKit` fakes.

**Rule order (first hit wins; never a partial success).**

| # | Condition | Result |
|---|---|---|
| 1 | `amount == 0` | `validation_failed` 400 |
| 2 | `source == AdminGrant && actorId == targetUserId` | `self_grant_forbidden` 403 |
| 3 | `source == AdminGrant && target.role != user` | `grant_target_forbidden` 403 (an owner may grant **to** an admin, never to themselves — rule 2 already caught self) |
| 4 | `amount < 0 && balance + amount < 0` | `insufficient_credits` 402 |
| 5 | `MintedLast24h + amount > Credit:MintCapPerActorPer24h` | `NeedsRequest` → **202** + `credit_grant_requests` row |
| 6 | otherwise | `Allowed` → apply in the caller's transaction |

**One command = one transaction.** `UnitOfWorkBehavior` is the only `SaveChangesAsync` caller, so the handler performs, in this order, inside one transaction:

1. `SELECT user_id FROM credit_accounts WHERE user_id = @targetUserId FOR UPDATE` — the account row is created lazily on first grant (`INSERT … ON CONFLICT DO NOTHING`), because `credit_accounts` exists to be the lock (00 §6:319).
2. `SELECT pg_try_advisory_xact_lock(hashtext('nts:credit_mint:' || @actorId))` → `false` ⇒ return `grant_in_progress` (409, retryable) **before** any write. Transaction-scoped only: EF returns pooled connections per command, so a session-scoped `pg_advisory_lock` could be released on another physical connection (F02/BR2). Lock order is `credit_accounts` → `promo_codes` → `payments` → `credit_lots`.
3. `ISystemContext.For(targetUserId)` scope for the money writes (`credit_ledger`/`credit_lots`/`credit_accounts` are tenant-filtered; an unscoped global query loads 0 rows silently, F10/C11).
4. `MintingPolicy.EvaluateAsync(actorId, targetUserId, amount, MintingSource.AdminGrant, ct)` — the cap sum runs here, after the lock, in this transaction.
5. Insert the `credit_grant_requests` row (`target_user_id`, `amount`, `reason`, `source = 'admin_grant'`, `requested_by = actorId`; `status = 'approved'`, `decided_by = actorId`, `decision_note = 'within cap'` when allowed, else `status = 'pending'`, `activates_at = NULL`). **Every grant gets a row** so the ledger can carry `grant:adjust:{grantRequestId}` — the only admin-grant key D2 allows.
6. Allowed ⇒ `ICreditLedger.GrantAsync(targetUserId, CreditLotSource.Adjust, amount, now + 12 months, new CreditGrantReference(grantRequestId, actorId), ct)`; the lot is `source = 'adjust'` with the 12-month expiry of D6/D12 and the ledger row `kind = 'adjust'`, `created_by = actorId`, `reference_type = 'credit_grant'`, `reference_id = grantRequestId`, `idempotency_key = grant:adjust:{grantRequestId}` (`ON CONFLICT DO NOTHING` ⇒ replay is a no-op).
7. Negative amount (within rules 1–4) ⇒ consume in the pinned spend order (`ORDER BY expires_at ASC, source_rank ASC, id ASC`, skip expired/voided) through `ICreditLedger`, one `adjust` row **per lot** with its `lot_id`; never a direct `UPDATE credit_lots`.
8. `audit_logs` row: `category = 'billing'`, `actor_type = 'admin'|'owner'`, `subject_user_id = targetUserId`, `data = { grantRequestId, amount, reason, source: 'admin_grant', decision }`; `billing_credits_minted_total{actor}` += the applied positive amount; `billing_credit_grant_pending` += 1 on the pending path; owners get the security alert through 11.6.2-T1 + the owner e-mail of 08 §5.2 (never a second pipeline).

**Cap query** (index-bound, no N+1):

```sql
SELECT COALESCE(SUM(amount), 0)
FROM   credit_ledger
WHERE  created_by = @actorId AND amount > 0 AND kind IN ('grant','bonus','purchase','adjust')   -- BR18: minted/settled positives only
  AND  created_at >= now() - interval '24 hours';
```

Indexes this task's migration adds: `credit_grant_requests (status, requested_at)` (pinned by D17), and `credit_ledger (created_by, created_at) WHERE created_by IS NOT NULL` for the cap sum (**12 CR-13 — owned by this task**). `reserve`/`release`/`settle`/`refund` rows are never counted, so reserved credits never enter the cap (BR18). `IPromoExposureQuery` reads `promo_codes` (soft dependency: 12.7.1-T1's migration creates the table; it is only reached by the `PromoExposure` source, i.e. by 12.7.2-T2) and is implemented here so all three callers share one sum.

**HTTP surface.** `POST /admin/users/{id}/credits`, body `{ amount, reason }`, `AdminPolicy` (owners included), `Idempotency-Key` mandatory (09 D6; a retried POST must not mint twice — README §3.1 requires the header on checkout/redeem and this route is money-moving, so the requirement is pinned here). Success 200 with the balance-affecting result, or **202** `{ creditGrantRequestId }` on the approval path. `Application/Common/Errors/ErrorCodes.cs` + `Api/Http/ErrorCatalogue.cs` carry `self_grant_forbidden`/`grant_target_forbidden`/`grant_in_progress` (12 CR-7); **no** `grant_requires_approval` code is added — above the cap is a success (09 README:975). Config `Credit:MintCapPerActorPer24h` = 2000 is validated at boot (1…100 000) and is **not** an owner-editable setting in M2.

## Acceptance checks

- **AC-1** Given 1,500 credits already minted by actor A in the last 24 h, When A grants 500 to a `user` target, Then 200, one `credit_ledger` row (`kind = 'adjust'`, `created_by = A`, `idempotency_key = grant:adjust:{grantRequestId}`), one `credit_lots` row (`source = 'adjust'`, `expires_at = now + 12 months`), one `approved` request row, one `audit_logs` row, `billing_credits_minted_total{actor=A}` +500.
- **AC-2** Given the same state, When A grants 501, Then **202** `{ creditGrantRequestId }`, **no** ledger row and **no** lot, one `pending` request row, `billing_credit_grant_pending` +1, and an owner alert (11.6.2-T1 pipeline + owner e-mail).
- **AC-3** Given actor A targets their own account, When the command runs, Then 403 `self_grant_forbidden` with no request row, no lot and no audit row.
- **AC-4** Given an admin actor targets an `admin` or `owner` account, Then 403 `grant_target_forbidden`; Given an **owner** actor targets an `admin`, Then the grant applies (owners may grant to admins).
- **AC-5** Given a target whose balance is 300 and a `-500` adjustment, Then 402 `insufficient_credits`, nothing moves and the negative request is listed for the digest; Given `-200`, Then it applies, consuming lots in `expires_at ASC, source_rank ASC, id ASC` order with one `adjust` row per lot.
- **AC-6** Given another grant holds the minting advisory lock, When this command runs, Then 409 `grant_in_progress` and no state change; no session-scoped `pg_advisory_lock` appears anywhere in the implementation.
- **AC-7** Given 10 parallel `POST /admin/users/{id}/credits` of 500 by one actor (Testcontainers, real PostgreSQL), Then at most four apply and every further one becomes a `pending` request — the cap sum never exceeds 2,000 and the ledger is never left with two rows for one `grant:adjust:{…}` key.
- **AC-8** Given a replay of the same `Idempotency-Key` with the same body, Then the stored response is returned and no second movement happens; with a **different** body, Then the 09 D6 conflict code for a reused key is returned.
- **AC-9** Given the command succeeds, Then exactly one `SaveChangesAsync` ran (one transaction), the account row lock was taken on `credit_accounts` before any lot write, and the tenant scope was `ISystemContext.For(targetUserId)` (assert on the fakes/Testcontainers session).
- **AC-10** Given `Credit:MintCapPerActorPer24h = 0` or `> 100000` in configuration, Then the host fails to start with a startup validation error; `2000` starts.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Advisory lock busy | 409 `grant_in_progress`, no row, no audit; the client may retry (the admin UI treats it as a soft failure with retry) |
| Target user deleted/suspended mid-flight | The account row still resolves; a suspended target is refused by 09's admin hierarchy rule (404 `not_found` when the actor may not act on the target), never a silent grant |
| DB error after the ledger insert | The whole transaction rolls back — no lot without its ledger row and no ledger row without its lot |
| `amount == 0` | 400 `validation_failed` (rule 1) — never a zero-value audit row |
| `Reason` empty / > 500 chars | 400 `validation_failed` (09's admin action convention: every money action carries a reason) |
| Replayed `Idempotency-Key`, different body | The 09 D6 conflict code, no movement ⚠️ (the exact code is 09 D6's; do not invent one here) |
| Cap sum race with a resolve grant | Both writers hold the same per-actor advisory lock only if the actor is the same; different actors are independent by design (the cap is per actor) |
| Promo exposure query runs before `promo_codes` exists | Soft dependency on 12.7.1-T1's migration: the query is only reachable through `MintingSource.PromoExposure`, which 12.7.2-T2 introduces; the migration order in `12-payments-sandbox` keeps `promo_codes` ahead of it |
| Metric/alert send failure | The grant stays applied (the audit row is the source of truth); the alert retries through the 11.6.2-T1 pipeline and the digest lists it |
