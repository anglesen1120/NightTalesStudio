# 12.5.1-T2 — `credit_grant_requests`: owner decisions, 7-day expiry and `CreditsMintedDigestJob`

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

A grant above the minting cap must wait for a human who is not the requester, and the owner must be able to *see* what was minted without asking. Ship the `credit_grant_requests` queue (owner-only list + direct filing), the approve/reject decisions with a mandatory note and the different-person rule, the 7-day expiry of undecided requests, the activation pass for a request whose `activates_at` time-lock has elapsed, and `CreditsMintedDigestJob` (daily 08:00 server-local) that e-mails every owner the credits granted per actor, the resolves and promo redemptions, the top 10 recipients of the last 24 h and the pending/overdue queue — the digest is itself an anti-fraud control, so a silent failure is a security failure.

## Design

**Commands and routes.**

```
DecideCreditGrantRequestCommand(Guid GrantRequestId, bool Approve, string Note)                    [Audited]
ApplyCreditGrantRequestCommand(Guid GrantRequestId)                                                [Audited]   // time-lock pass, T2's job only
```

| Route | Verb | Body / query | Policy | Success | Failure |
|---|---|---|---|---|---|
| `/admin/credit-grant-requests` | GET | `?status=pending&cursor=&limit=` | `OwnerPolicy` | 200 `{ items: CreditGrantRequestDto[], nextCursor }` | 400 `validation_failed` (bad status/limit) |
| `/admin/credit-grant-requests` | POST | `{ targetUserId, amount, reason }` (source `admin_grant`) | `OwnerPolicy` | 201 `CreditGrantRequestDto` | 403, 400 |
| `/admin/credit-grant-requests/{id}/approve` | POST | `{ note }` | `OwnerPolicy` + `IReauthGuard.RequireRecentAsync(5 min)` | 200 `CreditGrantRequestDto` | 409 `grant_request_not_pending`, 409 `grant_in_progress`, 403 `forbidden` (self-approval) |
| `/admin/credit-grant-requests/{id}/reject` | POST | `{ note }` (mandatory) | `OwnerPolicy` + `IReauthGuard` | 200 `CreditGrantRequestDto` | 409 `grant_request_not_pending`, 400 `validation_failed`, 403 `forbidden` |

The approve handler re-reads the row **inside** the transaction, verifies `status = 'pending'`, calls `MintingPolicy.EvaluateAsync(deciderId, target_user_id, amount, MintingSource.AdminGrant, ct)` under the same per-actor advisory try-lock (a busy lock ⇒ 409 `grant_in_progress`), applies the grant through `ICreditLedger.GrantAsync(… CreditLotSource.Adjust …, grant:adjust:{grantRequestId})` in the target's `ISystemContext.For(targetUserId)` scope, sets `status = 'approved'`, `decided_by`, `decided_at`, `decision_note`, and queues the `grant_request_decided` e-mail through `IEmailSender.QueueAsync`. The decider must differ from `requested_by` when the requester is an owner (403 `forbidden`), the target of the request is not the decider's own account, and every transition writes one `audit_logs` row (`category = 'billing'`). An `admin` may **not** decide. Reject stores the note, sets `status = 'rejected'`, applies nothing and sends the same e-mail.

**Grant-request `source` values (BR33, 00 §6:314).** The check constraint allows `admin_grant` | `promo_code` only. A resolve-originated request persists `source = 'admin_grant'` + `target_payment_id` — **never** a literal `payment_resolve`; a promo request persists `source = 'promo_code'` + `promo_code_id`. The Domain enum `MintingSource` maps `AdminGrant`/`Resolve` ⇒ `admin_grant` and `PromoExposure` ⇒ `promo_code`; a new persisted value would violate the constraint and break the approve path at runtime.

**Above-cap answers (BR27).** The above-cap **promo save** answers **200** with the code saved `active = false` plus `creditGrantRequestId` (12.7.2-T2), while the grant route `POST /admin/users/{id}/credits` keeps **202** `{ creditGrantRequestId }` (12.5.1-T1). Both paths write one `credit_grant_requests` row per above-cap event, `status = 'pending'` until an owner decides or the time-lock fires.

**Digest job and the request lifecycle.**

```
[JobPolicy(Queue = JobQueue.Default, Retries = 1)] [DisableConcurrentExecution]
CreditsMintedDigestJob : IRecurringJob  → daily 08:00 server-local, no arguments
  1. expire: SELECT id FROM credit_grant_requests WHERE status = 'pending' AND requested_at < now() - 7 d AND (target_payment_id IS NULL OR target_payment_id NOT IN (SELECT id FROM payments WHERE status = 'pending_approval'))  (index (status, requested_at); 12 CR-29: a request backing a still-`pending_approval` payment never expires — expiring it would strand the payment with no approve/reject path, F22)
     → per row: ISender.Send(new ExpireCreditGrantRequestCommand(id))   // one command per row, one transaction each (BR9, 06 YR26)
  2. aggregate for the last 24 h: grants/adjusts per actor (SUM over credit_ledger signed positive, kind IN ('grant','adjust')),
     resolves by actor, promo redemptions by code, top 10 recipients (GROUP BY target_user_id ORDER BY SUM(amount) DESC LIMIT 10)
  3. pending + overdue (pending_approval payments > 7 d, F22) + expired-this-run list
  4. billing_credit_grant_pending = COUNT(pending); log credits_minted_digest_sent{ownerCount}; IEmailSender.QueueAsync(template 'credits_minted_digest', owners, vi/en)
```

```
[JobPolicy(Queue = JobQueue.Default, Retries = 1)] [DisableConcurrentExecution]
CreditGrantRequestApplyJob   // BR27/D7: owned by this task; every 15 min, retries 1
  every 15 min → SELECT id FROM credit_grant_requests WHERE status = 'pending' AND activates_at IS NOT NULL AND activates_at <= now()
  → per row: ISender.Send(new ApplyCreditGrantRequestCommand(id))
     · source = 'admin_grant'  → apply through the same path as approve (decided_by = 'system:time-lock')
     · source = 'promo_code'   → IPromoActivationWriter.ActivateAsync(promo_code_id, id, ct)  (implemented by 12.7.2-T2, which owns promo_codes.active)
     · row becomes approved with decision_note = 'time-lock'; a cancel link consumed the token earlier ⇒ row already expired ⇒ no-op
```

`IPromoActivationWriter { Task<ErrorOr<Success>> ActivateAsync(Guid promoCodeId, Guid grantRequestId, CancellationToken ct); }` is declared here and implemented in 12.7.2-T2 — [INFERENCE], an internal port the README does not fix.

**Cancel link.** For a promo request the owner receives an e-mail with a cancel link built on 09.10.8-T1's mechanism: `approval_cancel_tokens` per recipient, public `POST /security/cancel-links/{kind}/{id}` with `[AllowAnonymousRequest]`, rate policy `anon`, uniform 400 `cancel_token_invalid`, `expires_at = activates_at`; BR27 fixes the kind value: `kind = "credit_grant_request"`. The token is minted at send time by the per-template `IEmailTokenMinter` and never stored in a payload or `email_messages.params`. Consuming it sets `status = 'expired'` and dispatches nothing.

**Reads.** `credit_grant_requests` has no `user_id` column, so it is **not** `IUserOwned`; the queue/digest read it directly with keyset pagination `(requested_at, id)` and `limit ≤ 100`, while the money write runs under `ISystemContext.For(target_user_id)`. `ISystemWorkQuery.PendingAsyncT` is **not** used (its pinned shape is `(id, user_id)` user-owned work).

**i18n and copy.** `admin.billing.grantRequests.*` (`pending`, `approved`, `rejected`, `expired`, `overdue`, `approve`, `reject`, `noteRequired`) and the `grant_request_decided` / `credits_minted_digest` templates in vi + en, English fallback (D18).

## Steps

1. 5. Implement `CreditGrantRequestApplyJob` (every 15 min, `[JobPolicy(Queue = JobQueue.Default, Retries = 1)]`, `[DisableConcurrentExecution]`, one `ApplyCreditGrantRequestCommand` per row, `grant:adjust:{grantRequestId}` idempotency, a row already `expired` by a cancel link skipped) with the `IPromoActivationWriter` branch; register the port's implementation with 12.7.2-T2 (BR27/D7 own the job here).
6. Queue the `credits_minted_digest` and `grant_request_decided` e-mails through `IEmailSender.QueueAsync`; add the owner list lookup (owners only, verified at send time).
7. Set the `billing_credit_grant_pending` gauge after every transition and at the end of each digest run; counters/logs carry ids and counts only (no e-mail addresses, no promo code lists).
8. Add the i18n keys and the template copy in both locales.

## Acceptance checks

- **AC-1** Given a `pending` request and an owner who is not the requester, When they approve with a note, Then the grant is applied **once** in one transaction (`grant:adjust:{grantRequestId}`, an `adjust` lot, `created_by` = the decider), the row becomes `approved` with `decided_by`/`decided_at`/`decision_note`, one `audit_logs` row is written and a `grant_request_decided` e-mail is queued.
- **AC-2** Given the same request already `approved`, When approve runs again (retry or second owner), Then 409 `grant_request_not_pending` and no second movement.
- **AC-3** Given the requester is the only owner, When they call approve, Then 403 `forbidden` and the row stays `pending`; Given two owners exist, Then the other owner can approve and the requester still cannot.
- **AC-4** Given reject without a note, Then 400 `validation_failed`; with a note, Then `rejected`, no lot, `grant_request_decided` queued, `audit_logs` written.
- **AC-5** Given `GET /admin/credit-grant-requests?status=pending&limit=50`, Then only `pending` rows are returned, keyset-paginated with `nextCursor`, and an `AdminPolicy` caller gets 403.
- **AC-6** Given a `pending` request with `requested_at` 8 days ago, When `CreditsMintedDigestJob` runs, Then it becomes `expired`, one `ExpireCreditGrantRequestCommand` is dispatched per row, `billing_credit_grant_pending` drops by one and the row appears in the digest; a **second** run dispatches nothing.
- **AC-7** Given 08:00 server-local, When the digest runs with two owners, Then both receive one e-mail containing grants per actor (direct, resolves), promo redemptions, the top 10 recipients of the last 24 h and the pending/overdue list; no request row is mutated except the 7-day expiries.
- **AC-8** Given a promo request whose `activates_at` has passed and no cancel was used, When `CreditGrantRequestApplyJob` runs, Then `IPromoActivationWriter.ActivateAsync(promoCodeId, requestId, ct)` is called once and the row becomes `approved` with `decision_note = 'time-lock'`; a re-run is a no-op.
- **AC-9** Given a cancel link for a promo request is consumed before `activates_at`, Then the row is `expired`, the apply job never activates the code, and a reused/expired/foreign token returns the uniform 400 `cancel_token_invalid` (09.10.8-T1) with no status disclosure.
- **AC-10** Given the advisory lock for the decider is held by a parallel grant, Then approve returns 409 `grant_in_progress` and the row stays `pending` (retryable, no partial write).
- **AC-11** Given the digest runs, Then the job passes **no** arguments to Hangfire, is registered on `JobQueue.Default` with retries 1, and `[DisableConcurrentExecution]` prevents a second concurrent run (assert the attribute via the job metadata).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two owners approve concurrently | The row lock plus the status check make one win; the loser gets 409 `grant_request_not_pending` with no movement |
| Decision on an already expired row | 409 `grant_request_not_pending` (expiry is terminal) |
| Decider promoted/suspended after re-auth | `IReauthGuard` is checked again at execution; the owner-set rule of 09.10.4 applies unchanged |
| E-mail pipeline down | The decision still applies (e-mail rides the outbox and retries); the digest's failure raises an alert and the digest is re-run manually — the metric/gauge is set before the e-mail is queued |
| Digest crashes mid-expiry | Per-row commands: rows already expired stay expired, the rest are picked up by the next run (no transaction spanning the run) |
| Time-lock apply job crashes | `activates_at <= now()` is re-evaluated by the next 15-minute run; the row stays `pending` and the owner sees it in the digest as overdue |
| `promo_code_id` row deleted or inactive when activating | `IPromoActivationWriter` returns the `not_found`/state error; the request stays `pending` and is alerted, never a silent `approved` |
| Target user no longer exists at approve time | 404 `not_found`; the row stays `pending` for a manual decision (no auto-grant) |
| Digest list > 100 items | Keyset paging inside the aggregation; the e-mail summarises counts and links to the admin screen, never a 5,000-row mail |
