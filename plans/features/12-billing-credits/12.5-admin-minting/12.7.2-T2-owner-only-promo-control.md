# 12.7.2-T2 — Owner-only promo control and exposure counted in the minting cap

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.7.2-T2 | S (0.5) | BE + Security | 12.7.2-T1, 12.5.1-T1, 09.3.3-T1 | 10.9.2-T1 (10/08 CR-hand-off) | S · M2 |

## Goal

A promo code is a second minting door: `fixed_credits` codes create credits with no payment, so `value × max_redemptions` must count against the creator's rolling 24 h mint cap, and only an owner may open that door. Ship the owner-only authorization of `POST /admin/promo-codes` and `PATCH /admin/promo-codes/{id}` (an `admin` may only set `active = false`; every other field ⇒ 403 `forbidden`), the exposure arithmetic into `MintingPolicy` (`PromoExposure` source, **increases only** on PATCH), and the above-cap path: the code is saved `active = false` with a `credit_grant_requests` row (`source = 'promo_code'`, `activates_at = requested_at + Credit:PromoExposureApprovalHours`), a second owner approves it, or — with a single owner — the 24 h time-lock activates it unless someone used the e-mailed cancel link.

## Design

**Authorization matrix** (one endpoint pair, two policies — evaluated before the command, and re-checked inside the handler because the policy alone does not see field-level rules):

| Caller | `POST /admin/promo-codes` | `PATCH /admin/promo-codes/{id}` |
|---|---|---|
| `owner` | allowed (subject to the cap/time-lock path) | allowed |
| `admin` | 403 `forbidden` | allowed **only** when the body changes nothing but `active = false`; any other field ⇒ 403 `forbidden` |
| non-admin | 403 (route policy) | 403 |

`IMintingPolicy` call sites (BR32): exactly 12.5.1-T1, 12.3.5-T1/-T2 and this task — **12.7.2-T1 never calls it** (it owns `IPromoValidator`, the catalogue write and redemption only; the cap is this task's gate on the same `UpsertPromoCodeCommand`). The cap's ledger half sums the minted positives of BR18 only — never reserved credits — and the persisted `source` of the request row is `promo_code` here (BR33).

**Exposure arithmetic** (the only place promo credits are counted as minting):

```
activeExposure(actor) = Σ over promo_codes WHERE kind = 'fixed_credits' AND active AND created_by = actor
                        of value × max_redemptions                                   // counted once per code
increase(PATCH)       = max(0, value_new × max_redemptions_new − value_old × max_redemptions_old)
amount               = increase(POST) = value × max_redemptions
```

`bonus_percent` codes are never counted (they need a paid purchase, D14). 12 CR-15 adds `promo_codes.created_by` (BR27), so the exposure query keys on the code's creator exactly as the primary design assumed; the attribution fallback through `credit_grant_requests` + `audit_logs` is withdrawn and every code — auto-approved included — is visible to the cap.

**Write path (inside `UpsertPromoCodeCommand`, one transaction via `UnitOfWorkBehavior`).**

1. Validate `PromoCodeInput` (12.7.2-T1's validator: `kind`, `value` > 0, `valid_from < valid_to`, `max_redemptions` ≥ 1, `per_user_limit` ≥ 1, `min_package_id` exists ⇒ else 404 `package_not_found`) and enforce `If-Match: "pc-<xmin>"` on PATCH ⇒ mismatch 409 `concurrency_conflict`.
2. Take the `promo_codes` row lock for PATCH (`SELECT … FOR UPDATE`) in global lock order (`credit_accounts` → `promo_codes` → `payments` → `credit_lots`; the owner's `credit_accounts` row is locked only on the approve path that grants credits).
3. `pg_try_advisory_xact_lock(hashtext('nts:credit_mint:' || @actorId))` ⇒ `false` returns 409 `grant_in_progress` (transaction-scoped only; a session lock is forbidden, F02/BR2).
4. `MintingPolicy.EvaluateAsync(actorId, targetUserId: actorId, amount: increase, MintingSource.PromoExposure, ct)`:
   `Allowed` ⇒ save with the requested `active` and increment `billing_credits_minted_total{actor}` by the increase;
   `NeedsRequest` ⇒ save the code with `active = false`, insert one `credit_grant_requests` row (`source = 'promo_code'`, `promo_code_id`, `amount = increase`, `requested_by = actorId`, `status = 'pending'`, `reason` from the input or a generated one, `activates_at = now + Credit:PromoExposureApprovalHours`) and answer **200** with the code (`active = false`) plus `creditGrantRequestId` (BR27) — the caller sees the code exists but is not live (the README path: "the code is saved `active = false` with a `credit_grant_requests` row"); queue the owner alert + the cancel link e-mail;
   `Rejected` (rule 1/4 of `MintingPolicy`, e.g. a bad amount) ⇒ 400/402 and nothing is saved.
5. A **second owner** approves ⇒ `ApplyCreditGrantRequestCommand` (12.5.1-T2) calls this task's `IPromoActivationWriter.ActivateAsync(promoCodeId, grantRequestId, ct)` ⇒ `active = true`, one `audit_logs` row, `billing_credits_minted_total{actor = code creator}` += the counted increase, `grant_request_decided` e-mail.
6. **Single owner** ⇒ no second owner exists, so the time-lock applies: `CreditGrantRequestApplyJob` (12.5.1-T2) sees `activates_at <= now()` and activates through the same writer — unless the cancel link was consumed first (row `expired`, code stays `active = false`). The cancel link is built on 09.10.8-T1's public `POST /security/cancel-links/{kind}/{id}` (uniform 400 `cancel_token_invalid`, no status disclosure) with the BR27-fixed `kind = "credit_grant_request"`, the token minted at send time by the per-template `IEmailTokenMinter` through 09.3.3-T1's `IUserActionTokenService` and never stored in an outbox payload.
7. Every path writes one `audit_logs` row (`category = 'billing'`, `actor_type`, `data = { promoCodeId, code, increase, active, grantRequestId }`) and structured logs with ids and the `increment`, never the full code list.

`IPromoActivationWriter` is declared by 12.5.1-T2 and implemented here ([INFERENCE], internal port). No new error code is introduced: `forbidden`, `concurrency_conflict`, `grant_in_progress`, `package_not_found`, `validation_failed` are the existing ones (12 CR-7/C11).

## Steps

1. Add the owner-only policy split on the two admin promo endpoints (`OwnerPolicy`; for `PATCH`, accept `AdminPolicy` and enforce "only `active = false`" in the handler) and return 403 `forbidden` for every other admin field change.
2. Implement the field-diff check: compare `PromoCodeInput` against the loaded row; an admin body that differs in any field other than `active` ⇒ `forbidden`, no write.
3. Implement `IPromoExposureQuery` consumption for the increase (`increase()` above) and call `MintingPolicy.EvaluateAsync(…, MintingSource.PromoExposure, ct)` under the advisory try-lock inside the command transaction; never a second exposure source.
4. Add the above-cap branch: `active = false` + `credit_grant_requests` row + owner alert + cancel-link e-mail; return the code in its persisted (inactive) state.
5. Implement `IPromoActivationWriter.ActivateAsync` here (idempotent: `active = true` + `audit_logs` only when the row is still `active = false` and the request is being approved by the time-lock or a second owner).
6. Add `If-Match: "pc-<xmin>"` handling on PATCH and the 409 `concurrency_conflict` mapping.
7. Wire the metric increment on activation and the digest visibility (the minted digest lists promo redemptions and the pending request, 12.5.1-T2).
8. Add i18n keys `admin.billing.promo.*` (`ownerOnly`, `savedInactive`, `pendingApproval`, `timeLockNotice`, `cancelLinkSent`) in vi + en.

## Outputs

Owner-only authorization + admin-restricted `PATCH` on `/admin/promo-codes`; exposure arithmetic wired into `MintingPolicy`; the above-cap inactive + `credit_grant_requests` + time-lock/cancel path; `IPromoActivationWriter` implementation; ETag/409 handling; audit + metric wiring; i18n keys; tests.

## Acceptance checks

- **AC-1** Given an `admin` calls `POST /admin/promo-codes`, Then 403 `forbidden` and no row is written; Given an `owner` calls it with a valid `PromoCodeInput`, Then 201 with the persisted code.
- **AC-2** Given an `admin` PATCHes `active = false` on an existing code, Then 200 and the code is inactive; Given the same admin PATCHes `value`, `max_redemptions` or `active = true`, Then 403 `forbidden` with no write.
- **AC-3** Given an owner creates `kind = 'fixed_credits'`, `value = 50`, `max_redemptions = 100` with 0 credits already minted, Then exposure 5,000 is counted, the code is saved `active = false`, one `credit_grant_requests` row exists (`source = 'promo_code'`, `promo_code_id`, `amount = 5000`, `activates_at = requested_at + 24 h`) and the owners are alerted with a cancel link.
- **AC-4** Given a second owner approves that request, Then `active = true`, `billing_credits_minted_total{actor = creator}` += 5,000, one `audit_logs` row, `grant_request_decided` e-mail; a re-run does not increment twice.
- **AC-5** Given the **cancel link** is consumed before `activates_at`, Then the request is `expired`, the code stays `active = false`, and `CreditGrantRequestApplyJob` never activates it; a reused or foreign token returns 400 `cancel_token_invalid`.
- **AC-6** Given one owner and no cancel, When `activates_at` passes, Then the apply job activates the code once (`decision_note = 'time-lock'`), the audit row records the system actor and the metric increments once.
- **AC-7** Given an active `fixed_credits` code (50 × 100) and a PATCH raising `max_redemptions` to 120, Then only the **increase** (`50 × 20 = 1,000`) is counted against the actor's cap; Given a PATCH reducing it to 80, Then 0 is counted and the code stays active.
- **AC-8** Given a `bonus_percent` code is created or raised, Then **no** exposure is counted (it needs a paid purchase) and the cap is untouched.
- **AC-9** Given a PATCH with a stale `If-Match: "pc-<xmin>"`, Then 409 `concurrency_conflict` and no write; Given a matching ETag, Then 200 and a new ETag.
- **AC-10** Given another grant holds the per-actor minting advisory lock, Then create/PATCH returns 409 `grant_in_progress` with no partial write (no code row, no request row).
- **AC-11** Given `min_package_id` refers to a missing package, Then 404 `package_not_found`; Given `value = 0` or `max_redemptions = 0`, Then 400 `validation_failed`.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two owners approve the same promo request | Row lock + status check ⇒ one activation, the loser gets 409 `grant_request_not_pending`; the metric increments once |
| Owner PATCHes the code while its request is `pending` | The row lock serialises; the request's `activates_at` is re-evaluated against the **new** increase (a new request row is created, the old one expires) — pinned so a PATCH cannot smuggle extra exposure |
| Cancel link consumed at the same instant as the time-lock | The token consumption takes the row lock first; the loser sees `status != 'pending'` and returns without activating |
| `promo_codes.created_by` (12 CR-15) | Ruled in — the column exists (BR27/CR-15) and the exposure query keys on the creator; no fallback attribution path is implemented |
| Code saved `active = false` and never decided | The pending queue surfaces it (`billing_credit_grant_pending`, digest, F22-style overdue list); after 7 days it is `expired` and the code must be re-issued by an owner |
| `If-Match` missing on PATCH | 400 `validation_failed` (the D17 ETag contract requires it) |
| Deployment of the send-time cancel-link e-mail fails | The code stays inactive; the owner re-triggers from the admin screen, and the token is re-minted at resend (never reused from a payload) |
| Metrics/alerts unavailable | Create/PATCH still applies and the audit row is written; the alert retries through the 11.6.2-T1 pipeline |
