## Goal

Make credits *real objects*: every credit sits in a `credit_lots` row with a source, an amount, an expiry and a payment link, and every movement names the lot it touched. This task builds the lot engine — schema, Domain invariants, and the lot half of `CreditService` — so that (a) a reserve consumes lots in the pinned FR-12-11 order, (b) release/refund return credits to exactly the lots they came from, (c) a lot that expired or was voided while a job ran never becomes spendable again, and (d) `GET /credits/balance` can report total / free / purchased / next expiry from live lots. It is the prerequisite of every grant path in plan 12 (§5 sequencing step 3).

## Design

**Domain (`NightTales.Domain/Ledger/`).**

```csharp
public readonly record struct LotId(Guid Value);
public enum CreditLotSource { Trial, Bonus, Promo, Purchase, Adjust }        // wire/DB: trial/bonus/promo/purchase/adjust
public static class CreditLotSourceRanks { /* trial 0 · promo 1 · bonus 2 · adjust 3 · purchase 4 (README D6) */ }

public sealed class CreditLot : Entity, IUserOwned
{
    public LotId Id { get; private init; }
    public Guid UserId { get; private init; }
    public CreditLotSource Source { get; private init; }
    public long Amount { get; private init; }
    public long Remaining { get; private set; }
    public DateTimeOffset? ExpiresAt { get; private init; }   // NULL only for source = Adjust (negative adjustments create no lot)
    public Guid? PaymentId { get; private init; }
    public DateTimeOffset? VoidedAt { get; private set; }
    public string? VoidedReason { get; private set; }         // 12 CR-2b
    public DateTimeOffset CreatedAt { get; private init; }

    public bool IsLive(DateTimeOffset now);
    public void Consume(long amount);   // amount > 0, amount <= Remaining, IsLive(now)
    public void Return(long amount);    // amount > 0, Remaining + amount <= Amount
    public void Expire();               // Remaining = 0 (ledger row staged by the caller)
    public void Void(string reason, DateTimeOffset now);
}
public sealed record LotConsumption(LotId LotId, long Amount);                // README D2, verbatim
public static class CreditLotErrors { /* negative_amount, over_remaining, lot_not_live, lot_not_lot_owner, return_over_amount, lot_already_voided */ }
```

**Schema** (created by **12.2.1-T1's** `_12_CreditLots` migration — BR20; this task adds no migration for the table, only consumes it; plan §3.2 has the exact DDL): `credit_lots` with `ck_credit_lots_remaining_bounds CHECK (remaining >= 0 AND remaining <= amount)` (12 CR-2b), `ck_credit_lots_expiry_after_created` (F04), `ck_credit_lots_voided_pair`; `credit_ledger.lot_id → credit_lots(id)`; unique `ux_credit_ledger_idem` (owner spelling, 12.2.1-T1); the F20 indexes `ix_credit_lots_user_expiry (user_id, expires_at) WHERE voided_at IS NULL`, `ix_credit_lots_payment (payment_id)`, `ix_credit_ledger_user_created (user_id, created_at DESC, id DESC)`, `ix_credit_ledger_reference (reference_type, reference_id)`.

**Sign convention (BR18, mandatory, M1) — one convention, identical in 12.2, 12.4, 12.6 and 12.8.** `credit_ledger.amount` is signed **from the user's balance view**: `grant`/`bonus`/`purchase` **positive**; `reserve` = **−R** (the reserve); `settle` = **−C** (the charge, `C = min(R, max(floor, credits(actual)))`); `release` = **+R** (the whole hold, exactly, no rounding — written only together with `settle`, in the same transaction); `refund` = **+R** with **no** `settle` row; `expire` = **−remaining**; `adjust` = signed. Per reservation: `SUM(amount)` = **−R** while open, **−C** once settled, **0** once refunded. UI/DTO values are derived per reservation group, never per row: `quoted = Σ|reserve|`, `charged = Σ|settle|`, `returned = quoted − charged` (or `= quoted` when refunded).

**Consumption** (inside the caller's transaction, immediately after `SELECT … FROM credit_accounts WHERE user_id = @u FOR UPDATE` — BR2, lock order `credit_accounts → promo_codes → payments → credit_lots`): the pinned SQL of planner §3.3 (`ORDER BY expires_at ASC NULLS LAST, <source_rank CASE> ASC, id ASC`, `FOR UPDATE`, guards `remaining > 0 AND voided_at IS NULL AND (expires_at IS NULL OR expires_at > @now)`). Consumed lots produce **one `credit_ledger` row per lot** (`kind = 'reserve'`, `amount = -consumed`, `lot_id`, `reference_type = 'reservation'`, `reference_id`, `price_version` on reserve rows). Key suffix rule: multi-lot rows use `reserve:{referenceId}:{lotId}` (see Notes/R-1); the reservation's `Lots` list is **derived** from these rows (`GetOpenReservationAsync`, F8) — no new table.

**Return path** (`ReturnToLotsAsync(reservationId, amountToReturnPerLot, reason, ct)`), per lot `FOR UPDATE`, planner §3.4 table: live ⇒ `Return`; expired ⇒ `Return` + `Expire()` with `expire:{lotId}:{reservationId}`; voided ⇒ `Return` + immediate re-removal with `void:{paymentId}:{lotId}`. Settle uses kind `release` (`release:{reservationId}:{lotId}`), failure/cancel uses `refund` (`refund:{reservationId}:{lotId}`). A replay of either never moves credits twice (unique `idempotency_key`).

**Grant** (the `GrantAsync(userId, source, amount, expiresAt, reference, ct)` **member is 12.2.1-T1's** — declared and implemented there, BR29; this task supplies the lot row + ledger staging it calls, F8): under the account lock, create the lot (`remaining = amount`) and the ledger row with the reference's key (`grant:trial:{userId}`, `grant:adjust:{grantRequestId}`, `grant:promo:{promoRedemptionId}`, `purchase:{paymentId}`, `bonus:{paymentId}`); a conflicting key returns the existing `LotId` without a second lot.

**Void** (`VoidPaymentLotsAsync(paymentId, reason, ct)`): every lot with that `payment_id` (purchase + bonus + promo bonus) → `voided_at`, `voided_reason`, one `adjust` row `void:{paymentId}:{lotId}`; returns `(long VoidedCredits, long ShortfallCredits)` so 12.3.4-T1 can raise the platform-loss alert when the credits were already spent.

**Balance read** ([INFERENCE] `ICreditLotSnapshotQuery`, single member, pinned, never extended): `SnapshotAsync(userId, ct) → (long Total, long Free, long Purchased, long? NextExpiryAmount, DateTimeOffset? NextExpiryAt)` computed from live lots with one grouped query (`SUM` + `GROUP BY source` + `ORDER BY expires_at ASC NULLS LAST LIMIT 1`); `free` = `trial`+`bonus`+`promo`+`adjust`, `purchased` = `purchase` (12 CR-25: matches the frozen §3.1 CreditBalanceDto note — an admin adjustment is free credit, not a refundable purchase). 12.2.2-T1 projects the frozen `CreditBalanceDto` from it. 12.2.3-T1 uses the same shapes for `SUM(remaining) = SUM(amount)` checks.

**Performance.** Per-user live-lot rows are ≤ a few dozen; the spend-order scan is served by `ix_credit_lots_user_expiry` plus a small sort. No N+1: the snapshot is one query, voiding is one `SELECT … FOR UPDATE` + one `UPDATE`. Batch nothing here — this is a request/job path with a single user in scope.

**Observability.** No new metric (F21's list is closed, F13): log `CreditLotConsumed { userId, reservationId, lots, credits }`, `CreditLotVoided { paymentId, lots, voidedCredits, shortfallCredits }`, `CreditLotInvariantViolation` (Error) with the constraint name. The existing `billing_balance_liability_credits` and `billing_reservation_missing_total` metrics cover the aggregates.

## Acceptance checks

- **AC-1** Given lots trial 50 (expires in 20 d), bonus 100 (11 months), purchased 1,000 (11 months), When a reserve of 120 runs, Then exactly two `reserve` rows exist (−50 on the trial lot, −70 on the bonus lot) with `lot_id` set and `price_version` filled, and the trial lot's `remaining` is 0.
- **AC-2** Given live credits of 119 and a reserve of 120, When the command runs, Then the API returns 402 `insufficient_credits`, no `credit_ledger` row exists for that `referenceId`, and every lot's `remaining` is unchanged.
- **AC-3** Given a `promo` lot and a `bonus` lot with the same `expires_at`, When 10 credits are reserved, Then the `promo` lot is consumed first (`source_rank` 1 < 2), and given an `adjust` and a `purchase` lot with the same expiry, `adjust` (3) precedes `purchase` (4).
- **AC-4** Given a reserve that consumed two lots, When it is refunded, Then each lot's `remaining` equals its exact pre-reserve value and the ledger contains one `refund` row **per lot** with the matching `lot_id`.
- **AC-5** Given a lot that expired between reserve and refund, When the refund runs, Then the return is immediately re-removed by one `expire:{lotId}:{reservationId}` row of the same amount, and `SUM(credit_ledger.amount) == SUM(credit_lots.remaining)` for the user still holds.
- **AC-6** Given a lot voided between reserve and settle, When the settle releases credits, Then the released part is removed again with `void:{paymentId}:{lotId}` and no row exists with `voided_at IS NOT NULL AND remaining > 0`.
- **AC-7** Given a direct SQL insert of a lot with `remaining = amount + 1`, Then PostgreSQL rejects it with `ck_credit_lots_remaining_bounds`; with `expires_at <= created_at`, it rejects it with `ck_credit_lots_expiry_after_created`.
- **AC-8** Given trial 20 (expiring in 5 d) + 5 bonus (15 d) + 100 purchased (11 months), When `GET /credits/balance` runs, Then `total = 125`, `free = 25`, `purchased = 100`, `nextExpiry = { amount: 20, expiresAt: <the 5-day instant> }`.
- **AC-9** Given one 20-credit lot and 20 concurrent reserves of 1 credit, When all complete, Then 20 succeed, `remaining = 0`, no reserve row exceeds the lot's amount, and an extra concurrent reserve returns 402 instead of a negative `remaining`.
- **AC-10** Given the same `referenceId` reserved twice, When the second call runs, Then no additional reserve row or lot consumption is recorded (unique `idempotency_key`) and the same reservation id is returned.
- **AC-11** Given a payment with a purchase lot, a bonus lot and a promo bonus lot, When `VoidPaymentLotsAsync` runs, Then all three have `voided_at`/`voided_reason` set, three `adjust` rows `void:{paymentId}:{lotId}` exist, and a second call changes nothing.
- **AC-12** Given a void where part of the purchase lot was already spent, When it runs, Then the returned shortfall is > 0 and the lot ends at `remaining = 0` (never negative); 12.3.4-T1 turns that into the platform-loss alert.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Insufficient live credits (all lots expired/voided or too small) | 402 `insufficient_credits` (D2), whole command transaction rolls back, no partial consumption |
| Lot consumed concurrently by an expiry run | Account row lock serializes both; the loser re-reads `remaining` and either continues with the next lot or returns `insufficient_credits` — never a negative lot |
| Unique `idempotency_key` violation | Treated as a no-op (existing row wins), logged at Debug, the caller gets the previous result — never a second movement |
| Return into a lot whose `remaining` would exceed `amount` (double refund race) | The `Return` guard throws `return_over_amount` before SQL; the second caller's key conflict makes it a no-op instead |
| `payment_id` has no lots at void time (already voided / never granted) | Success no-op returning `(0, 0)`; the caller must not report a failure to the user |
| Void shortfall (bonus consumed, purchase spent) | `ShortfallCredits > 0` returned; 12.3.4-T1 writes `billing_provider_loss_total` + alert; the lot is still voided to 0 |
| A user with zero lots | Consumption short-circuits to `insufficient_credits` without SQL for lots; the snapshot returns `(0, 0, 0, null, null)` |
| Reserve spanning > 50 lots | Allowed but logged at Warning (`CreditLotConsumed` with `lots`) — signals a lot-splitting bug upstream |
| `expires_at = NULL` lot (`source = adjust`) | Live until voided; ordered last (`NULLS LAST`) so expiring lots are always spent first |
