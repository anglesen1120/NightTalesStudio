# 12.6.2-T1 — CreditExpiryJob and expiry notices

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|

## Goal

Liability must not grow forever and must match OpenAI's own one-year expiry (plan B8/B10): a daily job writes the `expire` ledger row for the `remaining` of every expired live lot, zeroes it, and mails the user **once per lot** when that lot enters its last 30 days. Nothing about a user's balance may become negative, and a replayed run must be a no-op.

## Design

**Job.** `CreditExpiryJob : IJob` (Hangfire), **no arguments** (ids-only; the sweep pages internally), `[JobPolicy(Queue = JobQueue.Default, Retries = 1)]`, `[DisableConcurrentExecution(timeoutInSeconds: 1800)]`, registered on a daily 03:00 server-local recurring schedule (12.6.1-T1's folder registers nothing; the registration lives here, unconditionally — `billing_enabled` gates money **routes** only, O-7, because beta credits are admin-granted and must still expire).

```csharp
public async Task RunAsync(CancellationToken ct)
{
    var now = clock.UtcNow;
    // Pass 1 — expire (keyset pages of 500, at most MaxPages = 100, then stop and log)
    for (LotId? after = null; ; )
    {
        var due = await expiringLots.DueAsync(now, take: 500, after, ct);          // 12.6.1-T1 port
        if (due.Count == 0) break;
        foreach (var row in due) await sender.Send(new ExpireCreditLotCommand(row.Id), ct);   // one command per lot
        after = due[^1].Id; pages++;
        if (pages >= MaxPages) { log.Warning("CreditExpiryJobPageCap {Pages}", pages); break; }
    }
    // Pass 2 — 30-day notices (same paging shape over DueSoonAsync(now, now.AddDays(30)))
    // foreach (row) await sender.Send(new SendCreditExpiringNoticeCommand(row.Id), ct);
}
```

Per-row commands are mandatory (BR9/06 YR26): one bad lot must never roll back the rest of the page.

**`ExpireCreditLotCommand(LotId LotId) : ICommand<Success>` — `[NotAudited]`** (system-driven; the `expire` ledger row is the audit). Handler `ExpireCreditLotCommandHandler`:

1. `IExpiringLotQuery.GetAsync(lotId, ct)` → `(Guid UserId, long Remaining, DateTimeOffset? ExpiresAt, DateTimeOffset? VoidedAt, long Total)`; not found ⇒ `CreditLotErrors.LotNotFound` → **no-op success** (the row may have been voided and hard-deleted by retention; there is no route, so no error code leaves the system — log at Debug).
2. `using var scope = systemContext.For(userId)` (09.2.3 — the job has no ambient user; `credit_lots` is `IUserOwned`).
3. Single transaction, one `SaveChangesAsync` (UnitOfWorkBehavior): `SELECT … FROM credit_accounts WHERE user_id = @u FOR UPDATE` (BR2 lock order), then re-read the lot `FOR UPDATE`. Skip as a no-op when `VoidedAt is not null`, `Remaining = 0`, or `ExpiresAt > clock.UtcNow` (the boundary is strict: a lot whose `expires_at == now` is **due**; `CreditLot.IsLive` uses the same strict comparison — one predicate, two call sites, kept identical).
4. Otherwise `ICreditLedger.ExpireAsync(lotId, ct)`: ledger row `(kind = 'expire', amount = -remaining, lot_id, reference_type = 'lot', reference_id = lotId, idempotency_key = 'expire:{lotId}')` — BR19's `expire:{lotId}:{reservationId?}` with the optional reservation part omitted — then `lot.Expire()` (`remaining = 0`). A duplicate key (a replay, or a release-time re-removal that already used `expire:{lotId}:{reservationId}`) is a no-op; the two keys never collide by construction.

**`SendCreditExpiringNoticeCommand(LotId LotId) : ICommand<Success>` — `[NotAudited]`, `[OutboxEvent(typeof(CreditExpiring))]`.** Handler `SendCreditExpiringNoticeCommandHandler`: same per-user scope; guard `Remaining > 0 AND VoidedAt is null AND ExpiresAt <= now + 30 d AND ExpiresAt > now`; then claim the notice so a replay and a second job instance cannot mail twice — `idempotency_keys (user_id, key = 'notice:expiring:{lotId}', request_hash = sha256(userId|lotId), response_type = 'credit_expiring_notice', expires_at = lot.ExpiresAt)` inserted with claim semantics ([INFERENCE] mechanism: D7/D17 fix the once-per-lot rule and the template, but name no key; R-4 in the report). The command emits `credit_expiring.v1 { userId, lotId, amount, expiresAt, uiLocale }`; the outbox handler `CreditExpiringNotificationHandler` calls `IEmailSender.QueueAsync(userId, "credit_expiring", model, locale, ct)` with the template bodies in vi and en (D18). No `IRealtimeNotifier` (ids-only, reserved for render progress); the in-app notice is `nextExpiry` on the frozen `CreditBalanceDto` (F16), rendered by 10.8.x.

**Sources and expiries** (set at grant time, planner §3.6 table, never recomputed here): `purchase`/`bonus` = `paid_at + Credit:PurchasedExpiryMonths`, `trial` = `now + Credit:TrialExpiryDays`, `promo` per code, `adjust` = 12 months.

**Performance.** M2 volume is small (hundreds of lots); the per-user index `ix_credit_lots_user_expiry (user_id, expires_at) WHERE voided_at IS NULL` serves 12.6.1-T1's spend scan but **not** this global `WHERE expires_at <= now` sweep, so **this task owns the global index `credit_lots (expires_at, id) WHERE voided_at IS NULL` (12 CR-13 / BR24)** and creates it in its own additive migration (the sweep is not per-user). The scan stays keyset-paged (`take = 500` × ≤ 100 pages per run), so a large table never produces an unbounded query.

**Observability.** No new metric — F21's list is closed (F13). Structured logs: `CreditExpiryJobRun { due, expired, creditsExpired, noticesQueued, pages, elapsedMs }` (Information), `CreditExpiryJobPageCap` (Warning), `CreditLotExpired { lotId, userId, credits }` (Information, ids only), `CreditExpiringNoticeQueued { lotId, userId }`. Failures surface through Hangfire's 1 retry and the existing 11.6.2-T1 job-failure alert (no second pipeline, D17).

## Acceptance checks

- **AC-1** Given a live lot with `expires_at = now − 1 h` and `remaining = 30`, When `ExpireCreditLotCommand` runs, Then exactly one `credit_ledger` row exists with `kind = 'expire'`, `amount = -30`, `lot_id` = that lot and `idempotency_key = 'expire:{lotId}'`, and the lot's `remaining` is 0.
- **AC-2** Given that same command replayed twice, When it runs again, Then no second ledger row and no second `remaining` change is recorded and the command succeeds.
- **AC-3** Given a lot with `expires_at = now + 5 min` and `remaining > 0`, When the job runs, Then no `expire` row is written and the lot is untouched (strict boundary: only `expires_at <= now` is due).
- **AC-4** Given a lot whose `expires_at` passed but which is `voided_at IS NOT NULL` (or already `remaining = 0`), When the job runs, Then it is skipped silently and no ledger row is written.
- **AC-5** Given three users each owning one expired lot, When `CreditExpiryJob.RunAsync` runs once, Then three `expire` rows exist (one per user, each under its own `ISystemContext.For` scope) and one failure for user B (simulated throw) does not prevent users A and C from expiring.
- **AC-6** Given a lot expiring in 20 days with `remaining = 40`, When the job runs, Then exactly one `outbox_messages` row of type `credit_expiring.v1` exists for that `(userId, lotId)` and the outbox handler called `IEmailSender.QueueAsync` once with the `credit_expiring` template.
- **AC-7** Given the same lot and a second job run two days later, Then no second notice row/e-mail is produced (the claim row `notice:expiring:{lotId}` blocks it), while a **different** lot of the same user still gets its own notice.
- **AC-8** Given a user whose lot expires in 45 days, When the job runs, Then no notice is produced at all.
- **AC-9** Given 600 due lots, When the job runs, Then it processes them in pages of 500 (two pages), and a run that hits the 100-page cap stops with a `CreditExpiryJobPageCap` warning without failing and without double-expiring anything already processed.
- **AC-10** Given the job runs with a `FakeClock` fixed at `T`, When it executes, Then every expiry decision uses `T` (no wall-clock read inside the handler) — asserted by advancing the fake and re-running.
- **AC-11** Given the migration of this task is applied, Then `pg_indexes` (or the EF model snapshot) shows the index `credit_lots (expires_at, id) WHERE voided_at IS NULL`, and the sweep's `DueAsync` plan uses it instead of a sequential scan (BR24).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Lot not found (retention deleted it) | No-op success, Debug log; never an error response (no route exists) |
| Lot voided between selection and the command | Skip (guard on `VoidedAt`) — the void path already removed the credits |
| Lot already expired by a concurrent worker | The `credit_accounts` row lock plus the unique `expire:{lotId}` key make the loser a no-op |
| Claim row already present for the notice | Skip without an e-mail; the lot still expires normally (notices are best-effort and must never roll back an expiry) |
| Outbox/e-mail delivery fails | The `expire` row is already committed; the outbox retries independently and lands in `outbox_messages.failed_at` after its own retries — expiry is never re-run for that |
| `expires_at` is `NULL` (`source = adjust`) | Never selected (`expires_at <= now` is false for `NULL`) — adjust lots do not expire |
| Job crashes mid-page | The next run re-selects the same rows; every already-processed lot is skipped by the guards + key, so a restart is idempotent |
| 100-page cap reached in one run | Warning log, clean exit; the remaining lots are processed by the next daily run (no backlog risk at M2 volumes) |
| Clock skew / DST | `IClock.UtcNow` only; comparisons are UTC (`timestamptz`), the 03:00 server-local schedule is Hangfire's concern |
