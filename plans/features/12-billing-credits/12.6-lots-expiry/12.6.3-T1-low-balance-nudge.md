## Goal

Tell a creator they are about to run out **before** their next episode is blocked: a daily job finds users whose live credit balance is below the price of one Standard render and sends the `credit_low_balance` e-mail **at most once per `Credit:LowBalanceEmailEveryDays` window** (opt-out honoured: `credit_accounts.low_balance_opt_out`, BR23). The dashboard banner itself is 10.8.x's UI; this task supplies the server-side trigger contract it consumes and adds **no** new wire field.

## Design

**Threshold.** `threshold = active price version's floors['render']['standard']` read through `IPriceCatalog` (soft read of 12.1.2-T1; **BR23** rules this threshold and adds no `Credit:LowBalance*` option). If the floor is absent/inactive, the job **skips the whole run** with `Warning LowBalanceNotifierJobSkippedNoFloor` — it never guesses a number (a wrong threshold would spam every user).

**Job.** `LowBalanceNotifierJob : IJob`, no arguments, `[JobPolicy(Queue = JobQueue.Default, Retries = 1)]`, `[DisableConcurrentExecution(timeoutInSeconds: 900)]`, daily recurring registration (unconditional — O-7/§7.2, the flag gates money routes only).

```csharp
public async Task RunAsync(CancellationToken ct)
{
    var now = clock.UtcNow;
    var threshold = await pricing.StandardRenderFloorAsync(ct);            // soft, 12.1.2-T1
    if (threshold is null) { log.Warning("LowBalanceNotifierJobSkippedNoFloor"); return; }
    var windowStart = WindowStart(now);                                    // floor(epochDay / Credit:LowBalanceEmailEveryDays)
    for (Guid? after = null; ; )
    {
        var page = await lowBalance.UsersBelowAsync(threshold.Value, take: 500, after, ct);   // (UserId, Total)
        if (page.Count == 0) break;
        foreach (var u in page) await sender.Send(new SendLowBalanceNoticeCommand(u.UserId, u.Total), ct);
        after = page[^1].UserId;
    }
}

public DateTimeOffset WindowStart(DateTimeOffset now)
    => DateTimeOffset.UnixEpoch.AddDays(Math.Floor((now - DateTimeOffset.UnixEpoch).TotalDays / options.LowBalanceEmailEveryDays) * options.LowBalanceEmailEveryDays);
```

**Selection** (`ILowBalanceQuery`, [INFERENCE] name; pinned single member, never extended — 09.2.3-T1 pattern): one set-based grouped read over **live** lots, keyset-paged by `user_id`:

```sql
SELECT user_id, SUM(remaining) AS total
FROM   credit_lots
WHERE  voided_at IS NULL AND remaining > 0 AND (expires_at IS NULL OR expires_at > @now)
GROUP  BY user_id
HAVING SUM(remaining) < @threshold
  AND  user_id > @after
ORDER  BY user_id
LIMIT  @take;
```

Deliberate consequence: a brand-new user with **no lots at all** never appears (no rows to group) — the nudge is for people who had credits and are running out, which is exactly the intent; no extra "has activity" filter is invented. A user at 0 credits **with** lots is included (they are blocked).

**`SendLowBalanceNoticeCommand(Guid UserId, long Total) : ICommand<Success>` — `[NotAudited]`, `[OutboxEvent(typeof(CreditLowBalance))]`.** Handler `SendLowBalanceNoticeCommandHandler`:

1. Opt-out: if `credit_accounts.low_balance_opt_out = true` (12 CR-15), skip (no claim, no event) — BR23; the flag is flipped only by this task's `PATCH /credits/preferences` (12 CR-16).
2. Rate limit: claim `idempotency_keys (user_id, key = 'notice:lowbalance:{userId}:{windowIndex}', request_hash = sha256(userId|windowIndex), response_type = 'credit_low_balance_notice', expires_at = windowStart + Credits:LowBalanceEmailEveryDays)`; insert conflict ⇒ skip silently. `windowIndex = floor(epochDay / Credit:LowBalanceEmailEveryDays)` ⇒ at most one e-mail per 7-day window even across job restarts, replicas or a clock jump inside the window (a jump forward ends the window early, which is the safe direction).
3. Emit `credit_low_balance.v1 { userId, total, thresholdCredits, uiLocale }`; the outbox handler `LowBalanceNotificationHandler` calls `IEmailSender.QueueAsync(userId, "credit_low_balance", model, locale, ct)` (template in vi + en, D18). No `IRealtimeNotifier` (ids-only, reserved for render progress).

**Preferences route (12 CR-16, owned by this task).** `PATCH /credits/preferences` takes body `{ lowBalanceOptOut }` and flips `credit_accounts.low_balance_opt_out` under the `credit_accounts` row lock (BR2) through `UpdateCreditPreferencesCommand` — always on, **never** behind `billing_enabled` (BR23). The column (`boolean NOT NULL DEFAULT false`, 12 CR-15) lands in 12.2.1-T1's `_12_CreditAccounts` migration (BR20); this task owns the route, the command and the read that skips an opted-out user.

**Banner (not built here).** 10.8.x renders "Buy credits" from the frozen `GET /credits/balance` (`total`, §3.1) compared with `GET /billing/quote?operation=render` `maxCredits` (12.1.3-T1) — **no new DTO field may be added** (F16/§3.1 frozen; 12 CR-9 fixes the field set 10 S consumes). Per the owner rule (2026-09-25) the banner/notice visual is designed in 10.8.x's own `<story>-T0 — UI design` task (states, 360/768/1280, vi+en, dark/light, focus order, D11 components); 12.6's canonical rows contain no UI task, so the dependency is recorded, not duplicated (report R-3).

**Performance.** One grouped scan per day over live lots (M2: thousands of rows, well under a second); the global sweep index `credit_lots (expires_at, id) WHERE voided_at IS NULL` (12 CR-13/BR24, owned by 12.6.2-T1) also accelerates this aggregate once the table grows. Paging is keyset (`user_id > @after`), 500 per page, no `OFFSET`.

**Observability.** No new metric (F21's list is closed, F13). Logs: `LowBalanceNotifierJobRun { thresholdCredits, candidates, sent, skippedOptOut, skippedAlreadyNudged, elapsedMs }` (Information), `LowBalanceNotifierJobSkippedNoFloor` (Warning), `LowBalanceNoticeQueued { userId, total, thresholdCredits }` (Information, ids only — never the e-mail address).

## Acceptance checks

- **AC-1** Given the active price version's `floors['render']['standard'] = 300` and a user whose live lots sum to 250, When `LowBalanceNotifierJob.RunAsync` runs, Then exactly one `outbox_messages` row of type `credit_low_balance.v1` exists for that user and one `IEmailSender.QueueAsync` call used the `credit_low_balance` template.
- **AC-2** Given the same user two days later (new balance still below the threshold), When the job runs again inside the same window, Then no second row/e-mail is produced (claim `notice:lowbalance:{userId}:{windowIndex}` exists).
- **AC-3** Given the same user 8 days later with a balance still below the threshold, When the job runs, Then a second e-mail **is** produced (new window).
- **AC-4** Given a user whose balance rose to 400 (≥ floor 300), When the job runs, Then no e-mail is produced.
- **AC-5** Given a user with `credit_accounts.low_balance_opt_out = true` (12 CR-15), When the job runs, Then no claim row, no outbox row and no e-mail are produced for them, while other users in the same run are still nudged; `PATCH /credits/preferences { lowBalanceOptOut: true }` (12 CR-16) flips the column, and `{ lowBalanceOptOut: false }` restores the nudge in the next window (BR23).
- **AC-6** Given no active price version with a Standard-render floor (or `floors` missing that entry), When the job runs, Then it exits with a `LowBalanceNotifierJobSkippedNoFloor` warning, sends nothing, and does not throw.
- **AC-7** Given a user with exactly one live lot of 0 `remaining` (all spent), When the job runs, Then the user is nudged (a blocked user is the target of this feature), and given a newly registered user with **no** `credit_lots` rows at all, Then they are not selected.
- **AC-8** Given 600 candidate users, When the job runs, Then it pages through all of them (500 + 100) with keyset paging and each candidate receives at most one command.
- **AC-9** Given one candidate whose command throws, When the job runs, Then the remaining candidates are still processed (one command per row through `ISender`) and the run's `sent` count reflects the successes.
- **AC-10** Given `Credit:LowBalanceEmailEveryDays = 7` and a `FakeClock`, When the job runs at window boundaries (`day 6 → day 7 → day 13 → day 14`), Then e-mails are produced on day 6, day 13 … exactly once per 7-day bucket (window arithmetic asserted with the fake clock, never with wall time).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Active price version has no Standard-render floor | Whole run skipped with a Warning (never guesses a threshold); no partial mail |
| Claim insert conflicts (another replica already nudged) | Skip silently; `skippedAlreadyNudged` counted in the run log |
| `credit_accounts.low_balance_opt_out` is true | Skip before claiming; the window is not consumed, so a later opt-in can still be nudged in that window |
| Candidate's lots all expired/voided between selection and command | The command re-checks nothing about balance (its payload is informational); the e-mail may still be sent — acceptable because the balance was true at selection and the window limit prevents spam. [INFERENCE, deliberate] |
| Outbox or SMTP failure | The claim row stays (no duplicate later in the window); the outbox retries independently and records `failed_at` after its own retries |
| User deleted/suspended between selection and send | `IEmailSender` skips suspended users (09); the claim row remains and costs one window — no crash |
| Clock jump forward past a window boundary | An extra e-mail at most once per window; a backward jump cannot re-send inside a consumed window (the claim key is the window index) |
| Threshold read fails (catalog exception) | The run throws, Hangfire retries once; no partial sends (the threshold is read before the loop) |
| Very large candidate set | Keyset paging, 500 per page, unbounded pages per run (daily cadence, no backlog risk); each page is one grouped query |
