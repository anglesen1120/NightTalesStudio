## Goal

Ship promo codes end to end: `promo_codes` + `promo_redemptions` (00 §6:298/299 ✅), the admin list/create/patch routes, `POST /billing/promo/redeem` for `fixed_credits`, the **implementation of `IPromoValidator`** that `12.3.2-T1` declares (BR6 ✅) for the checkout path (`bonus_percent`), and the promo half of the `payment_paid.v1` handler — bonus credits granted **only** once the payment is `paid`, as a `source = promo` lot bound to that `payment_id` (D14 ✅). Owner-only hardening, the `MintingPolicy` exposure arithmetic and the 24 h time-lock are `12.7.2-T2`'s (`../12.5-admin-minting/`, README §0 line 35 ✅) and are **not** re-implemented here.

## Design

**Domain.** `PromoCode(Id, Code, Kind, Value, ValidFrom, ValidTo, MaxRedemptions, PerUserLimit, MinPackageId?, Active)` with guards: `value 1..100` for `bonus_percent` and `1..100000` for `fixed_credits` (D14 ✅), `valid_from < valid_to`, `max_redemptions >= 1`, `1 <= per_user_limit <= max_redemptions`, `code` non-empty and unique case-insensitively (`citext` ✅); `PromoRedemption(Id, PromoCodeId, UserId, PaymentId?, CreditsGranted, RedeemedAt)`; `PromoKind` wire values `bonus_percent`/`fixed_credits` (✅ D14). Status is derived, never stored: `expired = now > valid_to`, `exhausted = redemption_count >= max_redemptions`.

**`PromoValidator` (Application, implements `12.3.2-T1`'s seam).** Read-only, no lock, no write — it answers the checkout question and returns the preview the checkout response needs:

```
ValidateAsync(string code, Guid userId, Guid packageId, long amountMinorUnits, CancellationToken ct)
  → ErrorOr<PromoValidation(Guid PromoCodeId, PromoKind Kind, long BonusCredits, long BonusPercent)>   // BR32-frozen
```

Order of checks (D14 ✅, the order is the contract): normalise `code` (`citext`) → not found or `!Active` ⇒ `promo_invalid` (400) → `now < valid_from || now > valid_to` ⇒ `promo_expired` (400) → `redemption_count >= max_redemptions` ⇒ `promo_exhausted` (409) → that user's row count `>= per_user_limit` ⇒ `promo_already_used` (409) → `min_package_id` set and `!= packageId` ⇒ `promo_invalid` (400). The counts here are **advisory** (the authoritative recount happens under the row locks at redeem/paid time — F16 ✅); the same predicate is used by both paths so the two can never disagree about *which* code fails.

**`RedeemPromoCodeCommand(string Code, string IdempotencyKey)` — the `fixed_credits` path.** One transaction, lock order `credit_accounts` → `promo_codes` (BR2 ✅):

```sql
SELECT ... FROM credit_accounts WHERE user_id = @userId FOR UPDATE;                 -- §3 invariant 1
SELECT ... FROM promo_codes     WHERE code = @code FOR UPDATE;                      -- max_redemptions guard
SELECT COUNT(*) FROM promo_redemptions WHERE promo_code_id = @id AND user_id = @userId;  -- per_user_limit, F20 index
SELECT COUNT(*) FROM promo_redemptions WHERE promo_code_id = @id;                   -- max_redemptions
INSERT INTO promo_redemptions (promo_code_id, user_id, payment_id, credits_granted, redeemed_at)
       VALUES (@id, @userId, NULL, @value, now());
-- then: ICreditLedger.GrantAsync(userId, source: Promo, amount: value,
--         expiresAt: promo_codes.valid_to, reference: new CreditGrantReference($"{redemptionId}"),
--         ct)  →  ledger row idempotency_key = grant:promo:{promoRedemptionId}   (D2 ✅)
-- one SaveChangesAsync (UnitOfWorkBehavior ✅)
```

`Idempotency-Key` is stored in `idempotency_keys` (request hash over body + user ✅ 12.3.2-T1's pattern): same key + same body ⇒ the stored response, no second lot; same key + different body ⇒ 409 `payment_invalid_state` (12.3.2-T1's frozen replay code ✅). `kind = bonus_percent` on this route ⇒ 400 `promo_invalid` (`fixed_credits` only ✅ §3.1). The route sits behind `billing_enabled` (BR17 ✅ "order creation") while this row does **not** carry the flag (see Notes).

**`UpsertPromoCodeCommand` (name verbatim from D13 ✅) — routes/validation/audit only.** Create/patch with `If-Match: "pc-<xmin>"` (412 on stale), the §3 invariant guards, and `audit_logs` (`category = 'billing'` ✅). **No cap arithmetic, no exposure multiplication and no advisory lock in this task**: D13 ✅ places the promo exposure sum (`value × max_redemptions`, increase-only on a PATCH) inside `MintingPolicy` (`12.5.1-T1`), and the owner-only guard, the ≥-cap request flow and the single-owner 24 h time-lock are `12.7.2-T2`'s (`../12.5-admin-minting/`, README §0 line 35 ✅). This task's row lists no `12.5.1-T1`/`09.3.3-T1` dependency (README:347 ✅) and BR32 fixes the `IMintingPolicy` call sites to 12.5.1-T1, 12.3.5-T1/-T2 and 12.7.2-T2 only — so this handler has **no `IMintingPolicy` call site at all** (`plan.md` §11 DoR-13 resolved). A `bonus_percent` code is **not** exposure (D14 ✅); a `fixed_credits` code is *counted by the policy*, not here. Admin create/patch must end as 403 `forbidden` (✅ §3.1) — implemented as the policy/attribute seam that `12.7.2-T2` finalises, with the `active = false` escape hatch (BR17-adjacent emergency stop, plan §12.7.2 ✅).

**`PromoRedemptionOnPaymentPaidHandler` — `[OutboxEvent("payment_paid.v1")]` (BR6 ✅).** Subscribing, not publishing: 12.3.3-T1 owns the event. For the payment's `promo_code_id` (a `bonus_percent` code, or a `fixed_credits` code added at checkout), one transaction: re-read the payment under `ISystemContext.For(payment.UserId)` (F10 ✅), verify `status = paid` (✅ D14 "only on `paid`"), insert `promo_redemptions(promo_code_id, user_id, payment_id, credits_granted, redeemed_at)` where `credits_granted = floor(payment.credits × value ÷ 100)` for `bonus_percent` (rounded **down**, matching the resolve rule ✅ plan §12.3.5) or `value` for `fixed_credits`, then `GrantAsync(userId, source: Promo, amount: credits_granted, expiresAt: per-code rule from `promo_codes.valid_to` ✅ D6, reference: the redemption id)` with `grant:promo:{promoRedemptionId}` (D2 ✅). The partial unique `(payment_id) WHERE payment_id IS NOT NULL` (D14 ✅) is the DB guard: a second redemption for the same payment is an `ON CONFLICT`-style no-op (detect by unique-violation → reload → return success, metric only — never a 5xx, because the outbox will retry). The handler never writes `purchase`/`bonus` rows or the lots they belong to — those are 12.3.3-T1's ✅.

**Read model.** `GetPromoCodesQuery` (admin) projects `PromoCodeDto` = `PromoCodeInput` fields + `{ id, redemptionCount, active }` (`[INFERENCE]` — only `PromoCodeInput` is frozen ✅); `AsNoTracking`, projected in SQL, ordered `active DESC, valid_to DESC`.

## Acceptance checks

- **Given** an active `fixed_credits` code with `value = 50`, `perUserLimit = 1` for a fresh user, **When** `POST /billing/promo/redeem { code }` with an `Idempotency-Key`, **Then** 200 `{ creditsGranted: 50, balance: <new> }`, exactly one `promo_redemptions` row with `payment_id = NULL`, exactly one `source = promo` lot expiring at `valid_to`, and a `CreditBalanceChanged` realtime message carrying only `userId`.
- **Given** the same key replayed with the same body, **Then** the stored response and **no** second lot (`grant:promo:{promoRedemptionId}` no-op ✅ D2); **Given** the same key with a different body, **Then** 409 `payment_invalid_state`.
- **Given** that user's `perUserLimit` already reached, **Then** 409 `promo_already_used`; **Given** the code's `maxRedemptions` reached, **Then** 409 `promo_exhausted`; **Given** an inactive/unknown code, **Then** 400 `promo_invalid`; **Given** `valid_to` in the past, **Then** 400 `promo_expired` — and for a code that is *both* exhausted and already used, the answer is `promo_exhausted` (order ✅ D14).
- **Given** a `bonus_percent` code at checkout, **When** `12.3.2-T1`'s `CheckoutCommand` calls `IPromoValidator.ValidateAsync`, **Then** a preview is returned and **no** redemption row exists after checkout.
- **Given** a payment with a `bonus_percent` code that becomes `paid`, **When** the `payment_paid.v1` event is handled, **Then** exactly one redemption with that `payment_id` and one `source = promo` lot bound to it, `credits_granted = floor(credits × value ÷ 100)`; **Given** the event is delivered twice, **Then** the second delivery is a no-op (no second lot, no error) — the outbox retry stays green.
- **Given** a code created or patched through `UpsertPromoCodeCommand`, **Then** it is validated, written and audit-logged, **no credits or ledger rows move**, and no exposure arithmetic and no `IMintingPolicy` call site exist in the handler (BR15/BR32 — call sites are 12.5.1-T1, 12.3.5-T1/-T2, 12.7.2-T2 only); the cap outcome — 202 `{ creditGrantRequestId }` above the cap, owner-only 403 `forbidden` for admins, the 24 h time-lock with one owner — is **`12.7.2-T2`**'s acceptance, and the minting advisory lock/409 `grant_in_progress` belong to `MintingPolicy` (`12.5.1-T1` ✅ D13), not to this route.
- **Given** `billing_enabled` false, **When** redeem is called, **Then** the route is refused as an order-creation path ✅ BR17; **Given** the flag, **Then** it works.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two parallel redeems of the same payment-less code by one user | `credit_accounts` lock serialises them; the in-transaction recount sees the first row ⇒ the second gets `promo_already_used`; **never** a pre-transaction check (F16 ✅) |
| Two parallel redeems by different users at `max_redemptions − 1` | `promo_codes` row lock serialises; the loser gets `promo_exhausted` |
| Duplicate `payment_paid.v1` / outbox retry | Unique violation on `(payment_id)` ⇒ reload ⇒ success, `billing_payments_needs_review_total` untouched, a debug log only ✅ F21 |
| `payment_id` row arrives for a payment later voided/refunded | The lot is created from the snapshot; 12.3.4-T1's voiding then removes it (its rule ✅) — this handler does not special-case it |
| Promo code with `min_package_id` for a package deactivated meanwhile | Validation uses the id, not activeness — the payment's snapshot governs ✅ 12.7.1-T1 |
| `promo_redemptions` insert succeeds but `GrantAsync` fails (ledger error) | Same transaction ⇒ full rollback; the API returns the ledger's error (`insufficient_credits` is impossible here) and no redemption leaks |
| `floor(credits × value ÷ 100) == 0` (tiny package, 1 % code) | The code is rejected at save time (`value` for `bonus_percent` must be ≥ 1 but the *result* can round to 0) ⇒ the handler skips granting and records the redemption with `credits_granted = 0` + an alert; documented, never a negative or zero lot |
| `Idempotency-Key` header missing | 400 (00 §8 requires it ✅) |
| Redeem with an expired `Idempotency-Key` record purged by retention | Treated as a fresh call; the lot guard (`grant:promo:{promoRedemptionId}`) cannot help because the redemption id is new ⇒ retention window must exceed the code's `valid_to` — DoR note |
