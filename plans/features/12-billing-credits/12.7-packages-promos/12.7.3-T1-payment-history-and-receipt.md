# 12.7.3-T1 — Payment history, payment detail and the HTML receipt

## Goal

Give the buyer their own money record: `GET /billing/payments` (cursor-paged `PaymentDto` rows), `GET /billing/payments/{id}` (`PaymentDetailDto`) and `GET /billing/payments/{id}/receipt` returning **`text/html; charset=utf-8` with `Content-Disposition: inline`** — print-styled, in the user's `ui_locale`, with VND/USD and locale date formatting and the business details from settings (README §3.1 ✅, D18 ✅, O-8/BR12 ✅, 12 CR-2 ✅). **No server-side PDF library is added** (F19 ✅): the user prints to PDF from the browser. This task adds no table or row of its own (the receipt is rendered on demand; the only side effect is the `payment_receipt` e-mail of BR32) and carries **no** `billing_enabled` cell (§8.1 line 349 ✅ / BR17 ✅).

## Design

**Read model + tenancy.** `GetPaymentsQuery(Guid UserId, string? Cursor, int Limit)` and `GetPaymentQuery(Guid UserId, Guid PaymentId)`. `payments` is `IUserOwned` (09.2.3 ✅): the query runs under the ambient user's tenant filter, so a foreign id is **404**, never 403 (no existence leak). `Limit` clamped to **1..100** (default 20, ✅ §3.1 "max 100"). Ordering `created_at DESC, id DESC` (the F20 index `payments (status, created_at)`; the cursor is an opaque base64 of `(created_at, id)`, so paging is stable while new rows land above — no `OFFSET`). Projection is done in SQL (`AsNoTracking`, `Select`) straight into `PaymentDto`; `packageCode` comes from the `credit_packages` snapshot join (`payments.package_id` → `code`), and for a package that was since deactivated/renamed, `PaymentDto.packageCode` still resolves — the id is stable, the code may change; the **name** shown in the receipt is the payment's own snapshot ([INFERENCE]: only `credits`/`bonus_credits`/`price_version` are on `payments` ✅ 00 §6:300, so the receipt renders the code plus the amounts).

**`receiptAvailable`** ✅: `true` when `status ∈ { paid, partially_refunded, refunded }` (a receipt exists once money was taken) and the row has a business-config snapshot; `false` for `pending`/`failed`. `[INFERENCE]` — the field is frozen, the predicate is this task's, recorded for DoR.

**`PaymentDetailDto`.** `orderCode`, `providerPaymentId`, `invoiceInfo` (verbatim `jsonb` → `{ companyName, taxCode, address }` when present ✅ §3.1's checkout body), and `refundRequest` projected from `refund_requests` (`status` verbatim ✅ 00 §6:302) selecting the **latest** row by `created_at DESC, id DESC`, `null` when none. `refundableCredits`/`refundEligible` are **12.7.5-T1's** (`IRefundEligibility`, BR32 ✅) computed over `credit_lots` where `payment_id = @id`; `refundEligible = status ∈ { paid, partially_refunded } && paid_at + 14 d >= now && account not flagged && refundableCredits > 0` — the **authoritative** check is 12.7.5-T1's route (`refund_not_eligible` 409 / `account_under_review` 403 ✅); this projection must never be the only guard (the button it drives is a hint, the server re-checks). The exact predicate is 12.7.5-T1's to own (BR32; DoR-7 resolved) — this task renders it through the soft edge and never re-declares it.

**Receipt rendering.** `IReceiptRenderer.Render(PaymentDetailDto, ReceiptContext) → string` in Application; a Razor-free implementation (`StringBuilder` + a small HTML template with a `RenderedReceipt` DTO) — **no** view engine dependency in the Worker/API is added by this task ([INFERENCE] on the renderer mechanism; the *contract* is fixed: HTML, inline, print-styled). The document contains:

- Business block: `Billing:BusinessName`, tax code and address from settings (09.10 ✅); ⚠️ the exact setting keys are 09.10's and must be read at DoR-5/D18's business-details rule.
- Buyer block: the buyer's own email/name only — **no** other user's PII (D18 ✅); `payments.invoice_info` when present.
- Money block: package code, `amount` + `currency`, `method`, `status`, `credits`, `bonusCredits`, `orderCode`, `createdAt`, `paidAt`, `price_version`; formatted `vi-VN`/`en-US` (VND integer grouping, USD 2 decimals) and dates in the user's `ui_locale` (`en-US` fallback ✅ D18).
- Print styling: one `<style>` block with `@media print` (no external CSS — CSP-safe), page A4, no interactive controls.
- Legal footer: the credit-expiry and refund-window statements the terms carry (13.1.2-T1 ✅ CR-6), sourced from the same i18n keys as the pricing page so the UI and the receipt cannot drift (F17 ✅).

**HTTP hardening (the folder's one XSS sink).** Every dynamic value is HTML-encoded — notably `invoiceInfo.companyName`/`taxCode`/`address`, which are user-supplied. Response headers: `Content-Type: text/html; charset=utf-8`, `Content-Disposition: inline` (✅ frozen) with a filename hint only for a later download path; `X-Content-Type-Options: nosniff`; `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; img-src data:`; `Cache-Control: private, no-store`; `Referrer-Policy: no-referrer`. `IEmailSender`'s `payment_receipt` template is **sent by this task** through **09.2.6-T3** (BR32 ✅ — the paid path does not send it): exactly one send per paid payment, idempotent on `paymentId`, never triggered by a receipt GET.

## Steps

1. `GetPaymentsQuery` + `GetPaymentQuery` + handlers (`[NotAudited]`, `IUserOwned`), cursor encode/decode helper, limit clamp.
2. `PaymentDto`/`PaymentDetailDto` projections in SQL; `packageCode` join; `receiptAvailable` predicate; `refundRequest` latest-row projection.
3. Consume 12.7.5-T1's `IRefundEligibility` (BR32 ✅ — its `RefundArithmetic` sits behind that port) for `refundableCredits`; render `refundEligible` — never re-declare either.
4. `IReceiptRenderer` + HTML template + `ReceiptContext(locale, settings, now)`; all values encoded; `@media print` styles.
5. Routes `GET /billing/payments`, `GET /billing/payments/{id}`, `GET /billing/payments/{id}/receipt` — authenticated, **never** flag-gated (BR17 ✅), 404 for foreign ids, `ETag "pm-<xmin>"` on the detail route (`If-None-Match` ⇒ 304).
6. Send the `payment_receipt` e-mail once per paid payment through 09.2.6-T3 (BR32 ✅) — the same `ReceiptModel` as the HTML route, `IEmailSender` template, idempotent on `paymentId`.
7. i18n `billing.history.*`, `billing.payments.*`, `billing.receipt.*`, `billing.errors.*` for both locales + English fallback; the receipt's strings are server-side from the same files ✅ D18.

## Outputs

`GetPaymentsQuery`/`GetPaymentQuery` + handlers; the three routes; SQL projections for `PaymentDto`/`PaymentDetailDto`; `IReceiptRenderer` + the print-styled HTML template + `ReceiptContext`; the `payment_receipt` e-mail send through 09.2.6-T3 (BR32); the `refundEligible`/`refundableCredits` rendering of 12.7.5-T1's `IRefundEligibility` (soft edge, BR32); the response-header set; i18n keys; tests below.

## Acceptance checks

- **Given** a user with 30 payments, **When** `GET /billing/payments?limit=100`, **Then** all 30 newest-first with an opaque `nextCursor` only when more remain; **Given** a new payment lands between two pages, **Then** the second page still returns no duplicate and no skipped older row (keyset paging on `(created_at, id)`).
- **Given** two users, **When** user B requests user A's payment id, **Then** 404 on all three routes and no field of A's row appears in the body or the logs.
- **Given** a `paid` payment with `paid_at`, **When** `GET /billing/payments/{id}`, **Then** `receiptAvailable = true`, `orderCode`, `providerPaymentId`, `invoiceInfo` and `refundRequest` match the rows, and `refundEligible`/`refundableCredits` equal the `RefundArithmetic` result.
- **Given** a payment that becomes `paid`, **Then** exactly one `payment_receipt` e-mail is sent through 09.2.6-T3 (BR32) in the buyer's `ui_locale`, and a duplicate event or retry sends no second mail.
- **Given** a receipt request in `vi`, **Then** amounts group VND-style with `vi-VN` dates; **Given** `en`, **Then** `en-US` formats — and both documents contain the business name/tax code/address and the expiry + refund-window footer (D18 ✅).
- **Given** `invoiceInfo.companyName = "<script>alert(1)</script>"`, **When** the receipt is rendered, **Then** the value appears HTML-escaped and the body contains no executable `script` element.
- **Given** `billing_enabled` false, **When** any of the three routes is called, **Then** it works (BR17 ✅ — unwinding/reading money is never blocked).
- **Given** an unchanged payment and the `ETag` from a previous detail call, **When** the detail is re-requested with `If-None-Match`, **Then** 304 and an empty body.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Cursor malformed/forged | 400 `ValidationProblemDetails` on the `cursor` field; the cursor is opaque base64url of `(created_at, id)` and is validated, never interpolated into SQL |
| `limit <= 0` / `> 100` | clamped (1/100) — never an error |
| Payment row exists but belongs to another tenant | 404 (tenant filter ✅ F10-style rule) |
| `package_id` points at a deactivated package | `packageCode` still resolves (id stable); no 500, no empty string |
| Receipt requested for `pending`/`failed` | 404 with 09's standard not-found ProblemDetails (the frozen §3.1 code set has no dedicated code for this); `receiptAvailable = false` is the UI hint, and a receipt is never rendered for money not taken |
| Receipt for a `refunded`/`partially_refunded` payment | rendered with `status` verbatim and a `refund` line — a receipt is a record, not a guarantee |
| `ui_locale` unknown/absent | `en-US` fallback (D18 ✅), never a 500 |
| Business settings missing (fresh install) | the block renders with the settings' empty values and the boot validation (09.10 ✅) is the guard — no hard-coded vendor string |
| Very old payment whose `credit_packages` row was hard-deleted | impossible: this folder never deletes (`active = false` only, §3 invariant 10) — the join is `LEFT JOIN` for safety |
| Concurrent status change between detail and receipt | each request is its own read (`AsNoTracking`); no cross-request consistency promise is made |
