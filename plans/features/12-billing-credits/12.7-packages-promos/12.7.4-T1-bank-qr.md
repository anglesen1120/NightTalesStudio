## Goal

Make bank-transfer QR a correct, buyer-visible order path for Vietnamese users **without re-implementing any landed sibling seam**: the `method = bank_qr` branch of checkout produced with the **exact** amount and the row's unique `order_code` in the transfer note, the provider capability wiring (`Capabilities.BankQr`), the expiry the buyer's countdown and the `/billing/return` polling depend on (BR11 ✅), the payload-handling rules (never logged, and **never** persisted in `payments.raw` — derived from `order_code` + the provider account config, BR32), and the QA of the `needs_review` handoff for 10.8.4. Resolution by reference, the amount/currency gate and the unmatched-event outcome are **`12.3.3-T1`'s** (its steps 3–4, acceptance 5 and 8 ✅); the `bankQr`/`checkoutUrl` projection and the capability fallback are **`12.3.2-T1`'s** (its steps 6–7, acceptance 4 ✅). Delivered behind `billing_enabled` (this row carries the flag ✅ README §8.1 line 350 + line 319 ✅).

## Design

**Capability wiring (12.3.1-T1's recorded facts → behaviour).**

```
Capabilities.BankQr == true   ⇒ ProviderMethod.BankQr is offered; QR details come back per D8
Capabilities.BankQr == false  ⇒ 400 payment_method_unavailable (fail-closed — BR32/CR-7);
                                never a silent card/page fallback
Capabilities.BankQr == false everywhere (no provider supports it ⚠️ DoR-6)
                              ⇒ the story is dropped: the QR step is not offered in 10.8.4 and
                                no manual bank-statement matching is added (plan §12.7.4 ✅)
Capabilities.StatusApi == false ⇒ the pending QR row is settled only by the webhook; it expires at
                                expires_at (BR11 ✅) and a later transfer ⇒ needs_review (F13 ✅)
```

**Ruled by BR32 (DoR-11 resolved).** `Capabilities.BankQr == false` ⇒ **400 `payment_method_unavailable`**, fail-closed — "never a silent card fallback". `12.3.2-T1`'s acceptance-4 page fallback is superseded and that folder's task applies the change to its own file; one behaviour, one owner.

**QR invariants (the only guards this task adds).**

1. `bankQr.amount` must equal `payments.amount` (already integer VND ✅ D8) — the buyer must transfer the exact figure, so a provider-side rounding of the display amount is a **502 `payment_provider_error`**, not a silent `needs_review` (a wrong amount in the QR is unpayable, not merely odd).
2. `bankQr.orderCode` must equal `payments.order_code` (unique ✅ F20) — the transfer note the buyer copies must match the row 12.3.3-T1 looks up; a mismatch is 502. This is an **equality assertion on our own row**, not a second lookup implementation.
3. `bankQr.qrPayload` is validated (non-empty, ≤ 4096 chars, `[A-Za-z0-9+/=:.%-]`), **never** logged and **never** persisted in `payments.raw` (00 §6:300 has `raw jsonb` ✅) — it is derived on read from `order_code` + the provider account config (**BR32**; DoR-8 resolved).
4. `expiresAt` in the response is the row's `payments.expires_at` (checkout + `Payment:CheckoutExpiryMinutes` = 30 min ✅ BR11). A provider-supplied `CheckoutSession.ExpiresAt` **shorter** than ours is adopted; a longer one is clamped. One source of truth for the countdown and for the expiry job.
5. The response is exactly the frozen field set — a test asserts no `redirectUrl` member exists ✅ (12 CR-9).

**Status surface for 10.8.4** (the UI contract this folder owes): the step renders `pending` (QR + amount + order code + countdown + "keep the code in the note"), then polls `GET /billing/payments/{id}` (12.7.3-T1 ✅) until `paid` / `failed` / `needs_review` / `pending_approval`, or stops at `expiresAt`; `needs_review` shows the "We are checking your transfer" copy (`plans/10-web-ui.md:216-219` ✅ 10.8.4-T1). Underpaid/overpaid amounts are shown to the admin, not to the buyer. `processingPaused` copy is 12.8.3's and unrelated to this route.

**Aliases and self-approval.** None: the resolve queue requires an admin other than a self-dealing actor (12.3.5-T1/-T2 ✅), and this task writes no status.

## Steps

1. Wire the capability matrix from `Payment:Providers` into checkout: register the QR branch only when at least one provider reports `BankQr`; with a fake provider (`BankQr = false`) assert the BR32 fail-closed answer — **400 `payment_method_unavailable`**, no fallback, no card/page substitution.
2. Add the five QR invariants above at the `BankQrDetails` → `CheckoutSessionDto` boundary (single small mapper; no matcher, no classifier) + their unit tests.
3. Assert `expiresAt` mapping/clamping against `payments.expires_at` and the countdown contract (BR11 ✅).
4. Assert no logging and no persistence of `qrPayload` or the transfer note (log capture + a `payments.raw` assertion) — BR32 makes "never persisted" a hard rule, not a sibling's choice.
5. Contract-test the review handoff: a `needs_review` QR row appears in `GET /admin/payments?status=needs_review` with the `AdminPaymentDto` fields 12.3.5-T1 consumes ✅ (no new projection is written by this task — the assertion pins the shape).
6. i18n `billing.checkout.*` (QR copy: exact amount, "include the code in the transfer note", countdown, expiry) + `billing.errors.*` (`payment_provider_error`, `payment_expired`), vi + en with English fallback ✅ D18.
7. Arch test: the delivery contains no order-code matcher, no settlement classifier and no grant path (the withdrawal is permanent — DoR-12).

The QR branch wiring + capability matrix (Application, on 12.3.2-T1's seam); the `BankQrDetails` → `CheckoutSessionDto` mapper with the five invariants; the expiry mapping/clamping; the no-log/no-persist guarantees; the review-handoff contract assertions; the i18n keys; tests below. No port, no row, no lookup query, no classifier, no job.

## Acceptance checks

- **Given** `Capabilities.BankQr` true and a fresh checkout with `method = bank_qr`, **Then** `bankQr.{ qrPayload, bankName, accountNumber, accountName, amount, orderCode }` is present, `amount` equals the row's integer VND amount, `orderCode` equals `payments.order_code`, `expiresAt` equals `payments.expires_at` (= checkout + 30 min), and the payload has no `redirectUrl` field.
- **Given** a provider that answers with a hosted page instead of QR details, **Then** `checkoutUrl` is set and `bankQr` is null (D8 precedence ✅); **Given** `Capabilities.BankQr` false, **Then** **400 `payment_method_unavailable`** (fail-closed, BR32/CR-7), the row is not settled as a card payment and no `needs_review` row is created.
- **Given** the provider returns an `orderCode` that differs from `payments.order_code`, or a `BankQrDetails.AmountMinorUnits` that differs from `payments.amount`, **Then** 502 `payment_provider_error` and the row is `failed` — the buyer never receives a QR that cannot be matched.
- **Given** a QR order that ends `needs_review` (whatever the cause: underpaid, overpaid, re-fetch disagreement — decided by 12.3.3-T1 ✅), **Then** the row appears in `GET /admin/payments?status=needs_review` with `expectedAmount`, `receivedAmount`, `orderCode`, `providerEvents`, `expiresAt` and `resolveRequestedBy`, and this task has added no row, no lot and no status transition.
- **Given** a pending QR order with no webhook, **When** `expires_at` passes, **Then** `PaymentStatusSyncJob` (12.3.3-T2 ✅) expires it; **Given** a webhook for that order afterwards, **Then** 12.3.3-T1's late-event rule applies (`needs_review` ✅ BR11).
- **Given** the whole flow end to end with `FakePaymentProvider`, **Then** exactly one grant path runs (12.3.3-T1's) and the ledger shows `purchase:{paymentId}`/`bonus:{paymentId}` once ✅ — this task adds no grant.
- **Given** a `qrPayload` and a transfer-note value, **Then** neither appears in any log line, span or metric label (capture assertion).
- **Given** `billing_enabled` false, **Then** checkout creates no order ✅ BR17 while the webhook, the payment reads/receipt and the jobs keep running.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `Capabilities.BankQr` false (single provider, stale client/cached page) | **400 `payment_method_unavailable`** — fail-closed, never a silent card/page fallback (**BR32**/CR-7); only one behaviour is implemented |
| No configured provider reports `BankQr` at all ⚠️ DoR-6 | story dropped: the QR step is absent from 10.8.4, nothing else changes, no statement matching (plan §12.7.4 ✅) |
| Provider rounds the QR amount | 502 `payment_provider_error`, row `failed` — an unpayable QR must never reach the buyer |
| Provider's `orderCode` differs from ours | 502, row `failed` — matching is by `payments.order_code`, and the QR must carry it |
| Provider returns neither `CheckoutUrl` nor `BankQr` | 502, row `failed` (12.3.2-T1 rule ✅) |
| `CheckoutSession.ExpiresAt` longer than the row's | clamped to `payments.expires_at` (BR11 ✅); shorter is adopted |
| Bank app cannot scan the payload ⚠️ | onboarding-time fact for 12.3.1-T1 (BR16 ✅); the payload is passed through verbatim, never reshaped |
| Buyer transfers without the note / with a typo | no match ⇒ 12.3.3-T1's `payment_not_found` log + alert + 200, no new row (its acceptance 8 ✅) |
| Buyer transfers a different amount | 12.3.3-T1's amount gate ⇒ `needs_review` + alert; admin resolves via 12.3.5-T1 |
| Webhook arrives after `expires_at` | `needs_review` (BR11 ✅), never an automatic grant |
| `StatusApi` unavailable | webhook-only settlement; the row still expires at `expires_at` (F13 ✅) |
