# 12.8.1-T1 — Funding overview query, balance snapshots and runway input

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

Answer "how long does the OpenAI balance last" from data we already have, with two admin routes and one frozen DTO: `GET /admin/funding` → `FundingOverviewDto` and `POST /admin/funding/balance-snapshots` (body `BalanceSnapshotInput { balanceUsd, note }`). The view is the **only** place the owner sees last/estimated balance, 7-day burn, `runwayDays`, outstanding credit liability and its cost to serve, 7/30-day revenue, fixed monthly cost, the effective FX rate with its source, and the auto-reload monthly limit. Nothing is dispatched, reserved or charged here: this task is a read model plus one append-only admin write (README D11, D15; high-level plan §12.8.1).

## Design

```csharp
// Application/Features/Funding/FundingOverviewDto.cs
public sealed record FundingOverviewDto(
    decimal? LastBalanceUsd, DateTimeOffset? LastBalanceAt, decimal EstimatedBalanceUsd,
    decimal Burn7dUsd, decimal? RunwayDays, long OutstandingCredits, decimal OutstandingCostUsd,
    decimal Revenue7dUsd, decimal Revenue30dUsd, decimal FixedMonthlyCostUsd,
    decimal FxUsdVnd, string FxRateSource, DateTimeOffset? FxRateDate, decimal? AutoReloadMonthlyLimitUsd);

// Application/Features/Funding/GetFundingOverviewQuery.cs
public sealed record GetFundingOverviewQuery : IRequest<ErrorOr<FundingOverviewDto>>;   // [NotAudited]

// Application/Features/Funding/RecordBalanceSnapshotCommand.cs
public sealed record RecordBalanceSnapshotCommand(decimal BalanceUsd, string? Note)
    : IRequest<ErrorOr<FundingOverviewDto>>;                                            // [Audited(Category.Billing, Visibility.Internal)]
```

- Field names and order are D11's verbatim list as amended by **BR31** (14 fields: the wire names `lastBalanceUsd`, `lastBalanceAt`, `estimatedBalanceUsd`, `burn7dUsd`, `runwayDays`, `outstandingCredits`, `outstandingCostUsd`, `revenue7dUsd`, `revenue30dUsd`, `fixedMonthlyCostUsd`, `fxUsdVnd`, `fxRateSource`, `fxRateDate`, `autoReloadMonthlyLimitUsd`); `LastBalanceUsd`/`LastBalanceAt`/`RunwayDays`/`FxRateDate`/`AutoReloadMonthlyLimitUsd` are nullable because the platform can legitimately have no snapshot, zero burn, no top-up or no recorded limit. No extra field is added.
- `recorded_by` comes from `IUserContext.UserId`, never the body; `note` is trimmed and capped at 500 chars.
- **Queries (one read-only transaction, ≤ 6 statements, no per-row loop, F20):**

```sql
-- 1 last snapshot
SELECT balance_usd, recorded_at FROM provider_balance_snapshots
 WHERE provider = 'openai' ORDER BY recorded_at DESC LIMIT 1;                    -- ix_provider_snapshots (provider, recorded_at DESC)
-- 2 cost recorded since that snapshot (bounded to 90 days, see Failure handling)
SELECT COALESCE(SUM(cost_usd), 0) FROM usage_records
 WHERE created_at > @lastBalanceAt AND created_at > now() - interval '90 days';
-- 3 top-ups since that snapshot
SELECT COALESCE(SUM(amount_usd), 0) FROM provider_topups WHERE paid_at > @lastBalanceAt;
-- 4 outstanding liability (live lots only, D6)
SELECT COALESCE(SUM(remaining), 0) FROM credit_lots
 WHERE voided_at IS NULL AND expires_at > now();                                 -- credit_lots (user_id, expires_at) WHERE voided_at IS NULL (F20)
-- 5 active price parameters
SELECT credit_usd, margin FROM price_versions WHERE active_from <= now() ORDER BY active_from DESC LIMIT 1;
-- 6 burn + revenue: 12.5.2-T1's per-day query over a 30-day window (one grouped query, no N+1)
```

- `estimatedBalanceUsd = lastBalanceUsd − costSince + topUpsSince`; when no snapshot exists the view returns `LastBalanceUsd = null`, `EstimatedBalanceUsd = 0` and `RunwayDays = null` (it never invents a balance).
- `burn7dUsd` = mean daily cost over the last 7 complete UTC days from 12.5.2-T1's rows; `runwayDays = burn7dUsd == 0 ? null : estimatedBalanceUsd / burn7dUsd` — **never** a divide-by-zero and never `∞` (JSON cannot carry it).
- `outstandingCostUsd = outstandingCredits × credit_usd × (1 − margin)` of the active version — the cost to serve the credits already sold (README's "estimated cost to serve").
- `fxUsdVnd`/`fxRateSource`/`fxRateDate` come from `IFxRateProvider.CurrentAsync()`. The port is **declared by 12.1.2-T1** (options-backed) and its **DB-backed implementation belongs to 12.8.2-T1** (BR31) — this task only consumes it, so no soft adapter is needed. `fxRateSource` ∈ `topup`\|`fallback`; `fxRateDate` = the winning top-up's `paid_at`, null with the fallback (BR31).
- **Indexes and migration ownership (BR20 — one text per area, not per task):** the migration text **`_12_ProviderFunding`** is owned by this task **alone** and is the **only** migration for both funding tables — it creates `provider_balance_snapshots`, `provider_topups`, `ix_provider_snapshots (provider, recorded_at DESC)` (CR-13), `ix_provider_topups_paid_at (paid_at DESC)` (F20) **and** `ux_provider_topups (provider, reference)` (CR-13); CR-13's "(12.8.2-T1)" tag on that last index names which task's *feature* needs it, not a second migration text — 12.8.2-T1 adds no migration of its own (coordinated with this task before either lands). The burn windows rely on the pinned `usage_records (user_id, operation, created_at)` and CR-13's `usage_records (created_at, operation)` (12.5.2-T1's).
- Both funding tables are **not** `IUserOwned`: their entity configurations are registered outside the tenant filter with an explicit comment (`// admin-scope, F10: no tenant filter`) and a test asserts a user-scoped query cannot see them.
- Read path uses `AsNoTracking()` + `SqlQueryRaw<decimal>` projections for statements 2–5 (aggregates over tables the funding feature does not own); no `ExecuteSql`, no writes, no lock. The only write is `provider_balance_snapshots` via the standard unit-of-work (one `SaveChangesAsync`, F-E).

## Acceptance checks

1. **Given** an admin and no snapshot, **When** `GET /admin/funding`, **Then** `lastBalanceUsd = null`, `lastBalanceAt = null`, `estimatedBalanceUsd = 0`, `runwayDays = null`, `burn7dUsd = 0`, and `outstandingCredits` still reflects the live lots.
2. **Given** a snapshot of `$50.00` at `T0`, cost of `$4.00` recorded since `T0` and a top-up of `$20.00` with `paid_at` after `T0`, **When** the owner reads the view, **Then** `estimatedBalanceUsd = 66.00` and `lastBalanceUsd = 50.00`.
3. **Given** `burn7dUsd = 2.00` and `estimatedBalanceUsd = 14.00`, **When** the view is read, **Then** `runwayDays = 7.00`.
4. **Given** zero burn (no `usage_records` cost in 7 days), **When** the view is read, **Then** `runwayDays = null` and the response is HTTP 200 (no divide-by-zero, no `Infinity` in JSON).
5. **Given** `outstandingCredits = 1_000` with the active version `credit_usd = 0.01` and `margin = 0.6`, **When** the view is read, **Then** `outstandingCostUsd = 4.00`.
6. **Given** one paid payment of 200,000 VND recorded with `payments.fx_usd_vnd = 25,000` (CR-15) and no refunds, **When** the view is read, **Then** `revenue7dUsd`/`revenue30dUsd` are 8.00 and the value is the collected amount converted at that payment's **own stored** rate (never the current rate, never `credits × price` — BR8/BR31).
7. **Given** a top-up row with `fx_rate = 26_100` and `paid_at = 2026-09-20`, **When** the view is read, **Then** `fxUsdVnd = 26100`, `fxRateSource = "topup"`, `fxRateDate = 2026-09-20`.
8. **Given** no top-up row and `Credit:FxUsdVndFallback = 25_500`, **When** the view is read, **Then** `fxUsdVnd = 25500`, `fxRateSource = "fallback"`, `fxRateDate = null`.
9. **Given** `POST /admin/funding/balance-snapshots { balanceUsd: 50, note: "Sept top-up" }`, **When** the command completes, **Then** one `provider_balance_snapshots` row exists with `recorded_by` = the acting admin and `recorded_at` = now, an `audit_logs` row with category `billing` exists, and the response is the recomputed `FundingOverviewDto`.
10. **Given** `balanceUsd = -1` or `note` longer than 500 chars, **When** the command is sent, **Then** 400 `validation_failed` and no row is written.
11. **Given** a non-admin session, **When** either route is called, **Then** 404 (never 403 — 09 D5) and no data leaks.
12. **Given** a snapshot taken, storage disabled, a legacy row set has been seeded, **When** the request is repeated, **Then** the second `provider_balance_snapshots` row is a plain duplicate, not an update (append-only; no cached balance column exists anywhere).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| No snapshot row at all | `lastBalanceUsd/lastBalanceAt/runwayDays = null`, `estimatedBalanceUsd = 0`; the response is still 200 and the view is still useful (liability + revenue); `RunwayAlertStage` treats "no snapshot" as "cannot compute runway" and alerts once per day at warn level rather than opening anything |
| Snapshot older than 30 days | cost since is bounded to 90 days (statement 2), `runwayDays = null` and a log warning + a warn alert through 11.6.2-T1; a stale snapshot must never produce a confident-looking runway |
| `burn7dUsd = 0` | `runwayDays = null` (see check 4) |
| `TotalAvailableCredits` sum overflow | `remaining` is `bigint`; `SUM` is taken in SQL as `numeric` and narrowed; a value above `decimal` range is impossible, but the mapping is explicit, not a silent cast |
| DB timeout on the burn/revenue window | the query is bounded (7/30 days, indexed); on failure the handler returns `ErrorCodes.ServiceUnavailable`-class failure → 503 per the ErrorCatalogue, no partial DTO |
| Concurrent snapshot writes | both inserts are allowed (append-only observations); the view always reads the latest by `recorded_at`; no lock is taken (reads never block the owner) |
