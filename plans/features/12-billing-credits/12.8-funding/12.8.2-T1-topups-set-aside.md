# 12.8.2-T1 — Top-up records, the weekly set-aside report and the FX source

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.8.2-T1 | S (0.5) | BE | 12.8.1-T1 | 12.8.4-T1, 10.9.2-T1 (10/08 CR-hand-off) | S · M2 |

## Goal

Record what was actually paid to the provider and answer "how much of each sale must be set aside for the API". Two verbs on `/admin/funding/topups`: `POST` records a `TopUpInput { provider, amountUsd, amountVnd, fxRate, paidAt, reference }` row and returns the recomputed report; `GET` returns the report alone. The report is `{ revenue, setAside, actualCost, actualTopUps, gap }` over the last `FundingOptions.SetAsideTopUpDays` (14) days, with `setAside = revenue × (1 − margin)` from the *same* margin 12.5.2-T1 produces (BR8) — the `gap` is what the owner tops up next. Recording a top-up is also what makes `provider_topups.fx_rate` the effective FX rate (D16/F14), so the write evicts the cached rate in the same request.

## Design

```csharp
public sealed record TopUpInput(string Provider, decimal AmountUsd, decimal AmountVnd, decimal FxRate,
                                DateTimeOffset PaidAt, string? Reference);            // §3.1, verbatim field names
public sealed record SetAsideReportDto(decimal Revenue, decimal SetAside, decimal ActualCost,
                                       decimal ActualTopUps, decimal Gap);            // D11's five names, verbatim

public sealed record RecordTopUpCommand(TopUpInput Input) : IRequest<ErrorOr<SetAsideReportDto>>;   // [Audited(Category.Billing, Visibility.Internal)]
public sealed record GetSetAsideReportQuery(DateTimeOffset? From, DateTimeOffset? To) : IRequest<ErrorOr<SetAsideReportDto>>; // [NotAudited]

// DB-backed IFxRateProvider (BR31): the port is declared by 12.1.2-T1 (options-backed fallback implementation);
// this task supplies the decorator that prefers the latest provider_topups row.
public sealed class TopUpBackedFxRateProvider(IFxRateProvider fallback, IMemoryCache cache, IReadDb db) : IFxRateProvider
{ public Task<FxRateSnapshot> CurrentAsync(CancellationToken ct); }
```

- `provider` is validated against the allowed value `openai` (00 §6:303's provider); a payment provider name is never accepted here (`PaymentOptions.ActiveProvider` is a different concept).
- **Idempotent by reference.** `ux_provider_topups (provider, reference)` (CR-13) — a repeated `reference` (the bank transfer number) inserts nothing, returns the existing row's report as a no-op and logs `funding.topup_duplicate_total`. This mirrors BR1's claim-first posture without a ledger movement (this task moves no credits).
- **The write is the FX update.** After the insert commits, the handler asks the FX provider to drop its cached snapshot (TTL 60 s as a backstop) so the next `CurrentAsync()` reads the new `fx_rate` — no config write, no job (D16, F14). Order matters: insert → commit → evict; evicting before the commit can re-read the old row.
- **Report SQL (one statement per input, ≤ 3 total, no per-row loop):**

```sql
-- revenue over the window: NOT written here — 12.5.2-T1's query result is summed. CR-15 adds `payments.fx_usd_vnd`
-- (the rate actually paid, BR8/BR31), so 12.5.2-T1 converts each payment at its OWN stored rate, never the current one.
-- actual provider cost over the window: usage_records.cost_usd + the GPU share (12.5.2-T1 owns this shape)
SELECT COALESCE(SUM(cost_usd), 0) FROM usage_records WHERE created_at >= @from AND created_at < @to;
-- actual top-ups over the window
SELECT COALESCE(SUM(amount_usd), 0) FROM provider_topups WHERE paid_at >= @from AND paid_at < @to;   -- ix_provider_topups_paid_at
```

  The revenue leg is taken from 12.5.2-T1's query result rather than re-written here (per-payment conversion at `payments.fx_usd_vnd`, CR-15/BR31, net of refunds — BR8). If 12.5.2-T1's query returns the window in day buckets, this task sums those buckets; it never re-derives revenue from credits or package prices.
- `margin` = the active/realised margin from the same source as the report; `setAside = revenue × (1 − margin)`; `gap = actualCost − actualTopUps` (positive ⇒ the owner is behind on set-aside; the `gap` drives the next top-up, D11/D15).
- **`MaxPrefundBurnDays` guard.** `POST` accepts any valid top-up (the money is already spent — refusing the record would hide reality), but it returns the report plus a log/alert when `estimatedBalanceUsd` (12.8.1-T1's estimate) would exceed `MaxPrefundBurnDays × burn7dUsd`: pre-funding beyond ~60 days wastes credits that expire after 1 year (O-5/B8). No error code is invented for this; it is a warning.
- Default window: `SetAsideTopUpDays` (14) days back to now; an explicit `?from=&to=` is honoured up to 180 days (`validation_failed` beyond that). `To` defaults to now, `From` to `To − SetAsideTopUpDays`.

## Steps

1. **No migration owned here** (BR20: `_12_ProviderFunding`, including `ux_provider_topups (provider, reference)` per CR-13, is 12.8.1-T1's single text) — confirm the entity configuration is registered **not** `IUserOwned` (F10) if 12.8.1-T1 has not already done so.
2. `TopUpInput`, `SetAsideReportDto`, `RecordTopUpCommand` + handler: validate, dedupe by reference, insert with `recorded_by` from `IUserContext`, evict the FX cache, compute and return the report.
3. `GetSetAsideReportQuery` + handler: window validation, the three aggregates, `setAside`/`gap` math.
4. Endpoints `GET|POST /admin/funding/topups` in the 09.9.1 admin group; both added to the admin route table 09.2.3-T2 enumerates.
5. Emit the pre-fund warning path (log + metric) when the post-top-up estimate exceeds `MaxPrefundBurnDays` of burn; no new error code.
6. Register `TopUpBackedFxRateProvider` as the DB-backed `IFxRateProvider` implementation (decorating 12.1.2-T1's options-backed fallback, BR31); unit tests for the math and the dedupe; integration tests for the wire shape and the FX refresh.

## Outputs

- `provider_topups` rows writable through the audited route (append-only; no update/delete path exists).
- `GET|POST /admin/funding/topups` returning `SetAsideReportDto { revenue, setAside, actualCost, actualTopUps, gap }`.
- The effective FX rate (D16) changes as a consequence of a top-up record, with no config write and no job.
- `TopUpBackedFxRateProvider` registered as the DB-backed `IFxRateProvider` implementation (BR31).
- `ux_provider_topups (provider, reference)` and `ix_provider_topups_paid_at (paid_at DESC)` exist, both created by 12.8.1-T1's `_12_ProviderFunding` migration (BR20/CR-13) — this task owns neither index's DDL, only its consumer behaviour (dedupe, FX read).

## Acceptance checks

1. **Given** `POST /admin/funding/topups { provider: "openai", amountUsd: 20, amountVnd: 522000, fxRate: 26100, paidAt: 2026-09-20, reference: "FT-123" }`, **When** it completes, **Then** one `provider_topups` row exists with all five values and `recorded_by` = the acting admin, an `audit_logs` row (category `billing`) exists, and the response is `SetAsideReportDto`.
2. **Given** a second `POST` with the same `reference` and `provider`, **When** it completes, **Then** no second row is inserted, the response equals the first response, and `funding.topup_duplicate_total` is incremented.
3. **Given** a top-up of 26,100 VND/USD recorded at `paid_at` today and an older row at 25,500, **When** `IFxRateProvider.CurrentAsync()` is called next, **Then** it returns `UsdVnd = 26100`, `Source = TopUp`, `AsOf = today`, without a host restart or a config change (D16/BR31).
4. **Given** revenue 1,000 USD in the window and margin 0.60, **When** the report is read, **Then** `setAside = 400.00` and `revenue = 1000.00`.
5. **Given** `actualCost = 450` and `actualTopUps = 300` in the window, **When** the report is read, **Then** `gap = 150.00` and the sign convention is positive-when-behind.
6. **Given** a `bonus_percent` promo and bonus credits granted on a paid purchase, **When** the report is computed, **Then** `revenue` equals the collected payment amount only — bonus/promo credits never appear as revenue (BR8).
7. **Given** `amountUsd = 0`, `fxRate = 0`, `amountVnd < 0`, `paidAt` more than 1 day in the future, or `provider != "openai"`, **When** the command is sent, **Then** 400 `validation_failed` and no row is written.
8. **Given** `?from=` 200 days ago, **When** `GET /admin/funding/topups`, **Then** 400 `validation_failed`; with no query string the window is the last `SetAsideTopUpDays` days.
9. **Given** an estimated balance that would exceed `MaxPrefundBurnDays × burn7dUsd` after the recorded top-up, **When** the command completes, **Then** it returns 200 with the report, writes no error code, and raises the pre-fund warning log/metric once.
10. **Given** storage/DB failure mid-command, **When** `POST` runs, **Then** no `provider_topups` row exists (single transaction, `UnitOfWorkBehavior`), the FX cache is **not** evicted and a 5xx from the catalogue is returned.
11. **Given** two concurrent `POST`s with different references, **When** both complete, **Then** both rows exist and the second report includes both top-ups.
12. **Given** a non-admin, **When** either verb is called, **Then** 404 and no write.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Duplicate `reference` | no-op: the existing row is returned (partial unique index is the guard, not a read-then-write check — the read-then-write form races two concurrent admin submitters) |
| `reference` null (bank statement not yet available) | allowed; the row is inserted and the dedupe index is not applied (`WHERE reference IS NOT NULL`); the owner is expected to record a reference later via a new row — never an update |
| FX row with `fx_rate = 0` (bad data entered before validation existed) | the SQL uses `NULLIF(...,0)` for conversions and the boot validator rejects the option, but a zero rate already in the table would make the FX provider return 0 → the provider **ignores** rows with `fx_rate <= 0` and falls back (fail-safe, logged) |
| Top-up recorded with a `paid_at` older than the last snapshot | the estimate adds it (top-ups since the snapshot); no negative intermediate is shown to the owner |
| Report window with no payments | `revenue = 0`, `setAside = 0`, `gap = −actualTopUps` (over-funded window is visible, not hidden) |
| Concurrent report reads while a top-up commits | read-committed snapshot per statement; the report may miss the newest row by milliseconds — accepted, the numbers are advisory and the audit row is the source of truth |

## Notes

- The FX-column gap is **resolved**: CR-15 adds `payments.fx_usd_vnd` (numeric(12,6), the rate actually paid), so 12.5.2-T1 converts each payment at its own stored rate (BR8/BR31) — no open item remains here.
- Consumed by the set-aside/top-up form (10.9.1-T0-gated admin UI, BR22/§7 `12-ui-gate`). No UI ships from this folder.
- Related to 12.5.1-T2's owner digest and 12.5.2-T1's margin screen: all three must read the same revenue definition; this task never adds a second one (BR8).
- The `gap` drives the next top-up amount, and the `12-funding-ops` gate compares the report with the bank statement — hence `amountVnd`/`fxRate`/`paid_at`/`reference` are all recorded rather than derived.
