## Goal

Make the platform warn the owner **before** the provider balance runs out, pause trial grants automatically when it is nearly out, pay back the deferred trial grants when it recovers, and own the `POST /admin/funding/resume` route that closes the `provider_funds_exhausted` latch. The route requires an owner with a recent re-auth and **two independent probes** — a 1-token text probe and a 1-image probe through one healthy render node. Funds are declared healthy only when both spend real money successfully: a text-only pass keeps the latch open with the reason `node_image_project_unfunded` (D15). This task also registers the hourly `FundingRunwayJob` and defines the stage seam the other three tasks plug into, so no later task has to modify this one.

### Runway, thresholds and the trial pause

- Runway comes from 12.8.1-T1's query (`runwayDays`, `burn7dUsd`, `estimatedBalanceUsd`); `runwayDays = null` (no snapshot / zero burn) means "cannot compute" → warn-level notice at most once per day, **no** flag change.
- Bands: `runwayDays < WarnRunwayDays` (7) → warn; `< CriticalRunwayDays` (3) → critical; the metric `billing_openai_runway_days` is written every run regardless of band.
- Alert on **band transition**, detected by comparing the new band with the band computed in the previous run (process-local snapshot). A Worker restart may re-send one alert — accepted, the durable signal is the metric. ⚠️ A durable band state would need a store the contract does not define ([OPEN], see Notes).
- Below critical, trial grants pause: `IFeatureFlagWriter.SetAsync("trial_grants_paused", true, ct)`; at or above critical, `false`. The flag is the **durable** pause state, readable by 12.4.2-T1 through `IFeatureFlags.IsEnabledAsync` (a 30 s cache means a grant may slip through in the first 30 s after the threshold — accepted, and the deferred path recovers it).
- Sales never stop (O-5): nothing in this stage touches checkout, packages or payments.
- `runwayDays` also drives the pre-fund ceiling: when `estimatedBalanceUsd > MaxPrefundBurnDays × burn7dUsd`, the stage logs a warn notice (credits expire after 1 year and are non-refundable — B8/O-5). `MaxPrefundBurnDays` itself is the 60-day guard owned with 12.8.2-T1's warning.
- The rate's source/date and `autoReloadMonthlyLimitUsd` are surfaced by 12.8.1-T1's view; auto-reload is a **documented** owner decision, not an API call (D15, O-5) — this stage only reports the configured limit.

### Deferred trial grants

- **Deferred path (normal case): the outbox consumer for `trial_grant_requested.v1 { userId }`.** The handler reads the current `trial_grants_paused` flag; if it is **still on**, the handler does **not** call `ISender` at all and returns a retryable failure so 09's outbox dispatcher (`outbox_messages.next_attempt_at`/`failed_at`, 09 D6) redelivers it later on its own backoff — this task never manually "re-drives" a message; the dispatcher's normal retry loop is the mechanism. **This "no send while paused" rule is load-bearing, not cosmetic:** if the subscriber instead called `GrantTrialCreditsCommand` unconditionally, 12.4.2-T1's handler would evaluate `TrialEligibility`, see the pause, return `Defer`, and publish **another** `trial_grant_requested.v1` — subscriber → command → defer → publish → subscriber is an unbounded outbox loop (the same class of bug as the 06 upload hold→event→enqueue trap). If the flag is **off**, the handler dispatches `GrantTrialCreditsCommand(userId, Deferred)` through `ISender` (12.4.2-T1's handler: amount = `registration.trial.credits`, expiry = `TrialExpiryDays`, idempotency `grant:trial:{userId}` — a duplicate is a no-op, BR4).
- **Recovery sweep (safety net): `ITrialGrantCandidateQuery.PendingAsync(ct) → IReadOnlyList<Guid>`** — the pinned, one-member query 12.4.2-T1 declares and owns, returning the full candidate list directly (no `(id, user_id)` tuple shape, no separate pagination port — this is a plain list, not `ISystemWorkQuery.PendingAsyncT`'s shape), defined as "verified users with no `grant:trial:{userId}` row **and** no open `trial_grant_requested.v1`". "Open" means the outbox row is still retryable (`failed_at IS NULL`, 09 D6); once the dispatcher exhausts its retries and marks the row `failed_at` (dead-lettered — a genuine delivery failure, not a business skip), that user is no longer "open" and becomes a `PendingAsync` candidate. `RunwayAlertStage` calls `PendingAsync` every run (regardless of the pause flag — this catches lost commands, not paused ones) and dispatches `GrantTrialCreditsCommand(userId, RecoverySweep)` for each row returned, one command per user under its own `ISystemContext.For(userId)` scope (F10).
- **Explicit hole (recorded, not silently accepted):** while a `trial_grant_requested.v1` message is still "open" (within the dispatcher's retry window), `PendingAsync` correctly excludes that user — the outbox consumer above is the only path expected to grant them, and it will, once `trial_grants_paused` clears, on the dispatcher's own schedule (bounded by 09's configured max retry window). If that window is shorter than a real funding outage, a user could fall through both paths for the gap between "outbox gives up" and "the next `RunwayAlertStage` run" — bounded by the job's hourly cadence, so at most ~1 hour, and closed by the next run's sweep. This is recorded as [OPEN] for the TL: the exact 09 dispatcher max-retry-window value is not in this README and should be confirmed ≥ the plausible funding-outage duration, or `PendingAsync`'s "open" definition tightened.
- No new event, table or idempotency key: `trial_grant_requested.v1` + `grant:trial:{userId}` + `ITrialGrantCandidateQuery.PendingAsync` are all frozen by 12.4.2-T1.

### `POST /admin/funding/resume`

```csharp
public sealed record ResumeFundingCommand : IRequest<ErrorOr<ResumeProbeResult>>;   // [Audited(Category.Billing, Visibility.Internal)]
public sealed record ResumeProbeResult(string Flag, string TextProbe, string ImageProbe, string? Reason);
```

1. Owner-only policy + `IReauthGuard.RequireRecentAsync(5 min)` (401 `reauth_required` when stale; 403 `forbidden` for a non-owner).
2. If `provider_funds_exhausted` is already off → 200 no-op: `{ flag: "open", textProbe: "skipped", imageProbe: "skipped" }`, nothing dispatched (a double click must not dispatch twice).
3. Text probe (1 token through `OpenAiTextClient`) → fails: keep the latch open, `reason = "provider_funds_exhausted"`, `imageProbe = "skipped"`, P1-level alert, **200** (a failed probe is a result, never an error — plan 12 §5.3).
4. Text passes → image probe through `IProviderFundsProbe.ProbeImageAsync` (12.8.3-T3, one healthy node) → fails: keep the latch open, `reason = "node_image_project_unfunded"`, alert the admins (the node's own project/key is funded separately — 11.3.2/11.3.3), **200**.
5. Both pass → `IFeatureFlagWriter.SetAsync("provider_funds_exhausted", false, ct)`; emit `provider_funds_resumed.v1 { resumedAt, dispatched }`; then dispatch the held rows **in order** (`queued_at`, then `id`) and count them into `dispatched`.
6. Ordered dispatch re-checks each reservation: `ICreditLedger.GetOpenReservationAsync(referenceId, ct)`; a missing reservation cancels the job instead of dispatching it (the free-spend guard, F08/BR5). The ids come from the pinned system query and each dispatch runs in its own command under `ISystemContext.For(userId)` (one `SaveChangesAsync` per command).

## Steps

1. Declare `IFundingRunwayStage`, `IProviderFundsProbe`, `ProbeOutcome`; register `FundingRunwayJob` (hourly recurring, `JobQueue.Default`, no new queue) with DI-registered stages.

3. Implement the `trial_grant_requested.v1` outbox consumer (checks `trial_grants_paused`, dispatches or returns retryable) and the `ITrialGrantCandidateQuery.PendingAsync` recovery sweep in `RunwayAlertStage`, both using `grant:trial:{userId}`.
4. Implement the text probe over `OpenAiTextClient`; declare `ProbeImageAsync` in `IProviderFundsProbe` for 12.8.3-T3 (interface declared here, implementation there — the soft edge of §8.1).
5. Implement `ResumeFundingCommand` + handler + the endpoint, with the ordered dispatch loop and the reservation re-check.
6. Wire the flag keys' creation into the ops runbook (CLI), not into code paths.

## Outputs

- `FundingRunwayJob` registered and running hourly with at least `RunwayAlertStage`; `billing_openai_runway_days` published each run.
- `trial_grants_paused` toggled at the critical threshold; deferred grants applied once each after recovery (`grant:trial:{userId}`).
- `POST /admin/funding/resume` returning `{ flag, textProbe, imageProbe, reason? }`, with exactly two reasons possible: `provider_funds_exhausted` and `node_image_project_unfunded`.
- `provider_funds_resumed.v1 { resumedAt, dispatched }` emitted on a successful resume; ordered dispatch of held rows with a per-row reservation re-check.

## Acceptance checks

1. **Given** `runwayDays = 5`, **When** the stage runs, **Then** a warn alert is emitted once through 11.6.2-T1, `billing_openai_runway_days = 5`, `trial_grants_paused` stays off, and nothing is paused on the product surface.
2. **Given** `runwayDays = 2.5`, **When** the stage runs, **Then** a critical alert + the `funding_runway_critical` e-mail to owners are emitted and `trial_grants_paused` is written `true` (exactly one `feature_flags_changed.v1 { Key, Enabled, OccurredAt }`).
3. **Given** `trial_grants_paused = true` and a user verifying their e-mail, **When** 12.4.2-T1 runs, **Then** `trial_grant_requested.v1 { userId }` is published, no lot is created, and no ledger row exists.
4. **Given** a pending `trial_grant_requested.v1 { userId: U }` and runway recovering to 4 days, **When** the stage runs, **Then** one trial grant is applied to U (expiry `TrialExpiryDays`), the stage reports it, and a second run applies nothing (idempotent `grant:trial:U`).
5. **Given** `runwayDays = null` (no snapshot), **When** the stage runs, **Then** no flag change and no threshold alert occurs; at most one "cannot compute runway" notice per day is logged.
6. **Given** the latch `provider_funds_exhausted` is on and an owner with a re-auth 2 minutes old calls the route, **When** both probes pass, **Then** the flag is written `false`, `provider_funds_resumed.v1 { resumedAt, dispatched }` is emitted, held rows are dispatched in `queued_at` order, and each dispatch re-checked its reservation.
7. **Given** the text probe passes and the image probe fails, **When** the route completes, **Then** the response is **200** with `flag = "provider_funds_exhausted"`, `textProbe = "passed"`, `imageProbe = "failed"`, `reason = "node_image_project_unfunded"`, the latch stays on and admins are alerted.
8. **Given** the text probe fails, **When** the route completes, **Then** `imageProbe = "skipped"`, `reason = "provider_funds_exhausted"`, no image spend happens.
9. **Given** the latch is already off, **When** the route is called again, **Then** 200 with both probes `skipped` and `dispatched = 0` (no double dispatch).
10. **Given** a re-auth older than 5 minutes, **When** the route is called, **Then** 401 `reauth_required` and **no** probe is executed (money is not spent on an unauthorized call); a non-owner gets 403 `forbidden`.
11. **Given** a held row whose reservation was already refunded, **When** resume dispatches, **Then** `GetOpenReservationAsync` returns nothing and the job is cancelled instead of dispatched (no free provider spend).
12. **Given** the whole stage, **When** a run happens, **Then** every alert went through 11.6.2-T1 and no second sink/metric family was created (D17).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Two concurrent resumes | both may dispatch; dispatch is idempotent per job/reservation and the second call sees the flag already off → the ordered loop runs once in practice; a duplicated `provider_funds_resumed.v1` is harmless (consumers are idempotent by `resumedAt`) |
| Probe provider is down (network/5xx) | probe outcome is `failed` with an error code; the latch stays **open** (fail-closed) and the response is 200 — never a 5xx that would leave the caller unsure whether money was spent |
| Text probe times out mid-request | the command aborts before the flag write (single unit of work), the latch stays on, and the alert records the transport failure |
| No healthy node for the image probe | `ProbeImageAsync` returns `Unavailable` → `reason = "node_image_project_unfunded"` is **not** used; the reason is the flag while the alert says "no healthy node" — the two causes are distinguishable in the alert, never by inventing a third reason value ⚠️ (the contract fixes exactly one non-text reason, see Notes) |
| `trial_grants_paused` flag row missing (never created by the CLI) | `IFeatureFlags` returns false (not enabled); the stage logs an operator error once and continues — a missing row must not block granting |
| Deferred grant applied twice | no-op by `grant:trial:{userId}` (`ON CONFLICT DO NOTHING`), never a second lot |
| Runway oscillating around 3 days | the flag write is idempotent and the alert fires on transition only; a flapping threshold produces at most one e-mail per band entry |
