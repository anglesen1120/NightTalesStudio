# 12.8.3-T3 — 1-image probe through one healthy render node (`node_image_project_unfunded`)

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.8.3-T3 | XS (0.25) | BE | 12.8.3-T1 (soft), 11.3.3-T1, 05.4.1-T2 | — | S · M2 |

## Goal

Implement the **image** half of the resume probe: `IProviderFundsProbe.ProbeImageAsync` (the port declared by 12.8.3-T1) must prove that the render node's *own* OpenAI project/key — which is funded separately from the API's project and is never visible to us — can still pay for an image. A text probe alone is a false green: it proves the API's key has funds while the node's project may be empty, in which case every render fails after the user was told processing resumed. **Neither existing adapter route can serve this today** (⚠️ [OPEN], Notes item 1): `render-node.v1`'s only submit route, `POST /v1/renders`, needs the full D3 `mpt` key set and produces a multi-minute GPU render, not "spend exactly one image"; and the node's **image relay** (`images.v1`, 03 D5/D6) binds `127.0.0.1:8091` **inside** the adapter process — it is MPT's private channel to the relay and is not reachable from outside the node at all (11 README:179 — only the adapter's HTTPS listener on port 8090 faces the network). So this task requires a **CR to 05.4.1-T2 + 11.3.5-T1** adding a new externally-reachable probe route on the adapter's public HTTPS interface (port 8090) that internally drives one relay-backed image call without a render. This task's design targets that new route; until the CR lands, the implementation returns `unavailable` (fail-closed, §Failure handling).

## Design

```csharp
// Infrastructure/Nodes/NodeImageFundsProbe.cs — implements the port declared by 12.8.3-T1
public sealed class NodeImageFundsProbe(
    IReadDb db,                                // no-tracking read over worker_nodes (09.2.1-T1's published read port; admin-scope, no tenant filter needed)
    RenderNodeConnectionFactory connectionFactory,
    IClock clock, ILogger<NodeImageFundsProbe> log) : IProviderFundsProbe
{
    public Task<ProbeOutcome> ProbeTextAsync(CancellationToken ct) => throw new NotSupportedException(); // owned by 12.8.3-T1
    public async Task<ProbeOutcome> ProbeImageAsync(CancellationToken ct);
}
```

- **Node selection (one node, or none):**

```sql
SELECT id, base_url FROM worker_nodes
 WHERE state = 'active' AND last_heartbeat_at >= now() - interval '2 minutes'
 ORDER BY (SELECT count(*) FROM render_jobs r
            WHERE r.worker_node_id = worker_nodes.id AND r.status IN ('submitted','running')) ASC,
          name ASC
 LIMIT 1;                                        -- active tasks are derived, never stored (11 rule)
```

  No row ⇒ `ProbeOutcome(false, "node_unavailable")`: the resume handler keeps the latch open and does **not** use `node_image_project_unfunded` (that reason means "the node answered and its project could not pay"); the alert says "no healthy node" instead (12.8.3-T1's failure table).
- **The probe request depends on an adapter route that does not exist yet (⚠️ [OPEN], Notes item 1).** The design targets a new `POST /v1/probe-image` on the adapter's public HTTPS interface (`Adapter:Port` 8090, reached through `RenderNodeConnectionFactory` — pinned TLS + node key header, never a bare `HttpClient`), proposed by a CR to 05.4.1-T2 + 11.3.5-T1: the adapter accepts the call, internally drives exactly one image through its own relay-backed path (`images.v1`, 03 D5/D6, at the adapter's discretion — the caller never talks to `127.0.0.1:8091` directly, since that listener is not reachable from outside the node) and returns a terminal result synchronously or via one status poll. No `render_jobs` row, no `story_version_id`, no user id, no credits reserved, no render — this is a pure probe. **Until the CR lands and the route exists, `NodeImageFundsProbe.ProbeImageAsync` returns `ProbeOutcome(false, "probe_route_unavailable")`** (fail-closed — never a fabricated pass) and this is asserted by a test.
- **Outcome mapping (four cases, no ambiguity):**

| Adapter result | `ProbeOutcome` | Resume consequence (12.8.3-T1) |
|---|---|---|
| probe route not implemented yet (pre-CR) | `Passed = false`, `ErrorCode = "probe_route_unavailable"` | latch stays open, `reason` **not** set (distinct from both frozen reasons), alerted as a build gap, not a funding fact |
| task finishes (image produced) | `Passed = true` | with a passing text probe ⇒ latch closes, dispatch resumes |
| task fails with an error code/text (including the node's project being unable to pay) | `Passed = false`, `ErrorCode` = the adapter's code, e.g. `credit_balance_exhausted` | latch stays open, `reason = node_image_project_unfunded`, admins alerted |
| transport/TLS/timeout/no healthy node | `Passed = false`, `ErrorCode = "node_unavailable"` | latch stays open, alert "no healthy node", reason **not** set |

- No retry, no caching, no reuse: a cached "pass" would green-light real user spending. One attempt, bounded by the adapter's own timeout; the probe is deliberately excluded from any Polly policy that could retry it for minutes.
- The probe never writes `credit_ledger`, `render_jobs`, `credit_lots` or `episodes`. Its (tiny) provider cost is platform cost: it is attributed to the `platform_loss`/unpriced bucket of 12.5.2-T1's report once that bucket exists — ⚠️ [OPEN], see Notes item (2).
- Logging: ids only (`nodeId`, `errorCode`, `durationMs`); the adapter's raw body is never logged (it can carry a provider payload).

## Acceptance checks

1. **Given** two nodes, one `active` with a 10-second-old heartbeat and one `down`, **When** the probe runs, **Then** exactly one node is contacted (the active one) and the transport used is `RenderNodeConnectionFactory` (pinned TLS asserted in the test).
2. **Given** one `active` node whose last heartbeat is 5 minutes old (the poller marks it `down` within 2 min), **When** the probe runs, **Then** the outcome is `unavailable` with no request sent.
3. **Given** two `active` nodes with 3 and 0 active tasks, **When** the probe runs, **Then** the node with 0 derived active tasks is chosen.
4. **Given** the CR to 05.4.1-T2/11.3.5-T1 has **not** landed, **When** the probe reaches the point of calling the adapter, **Then** it returns `ProbeOutcome(false, "probe_route_unavailable")` and the resume route reports `imageProbe = "failed"` with **no** `node_image_project_unfunded` reason (a build gap is never mistaken for a funding fact).
5. **Given** the CR has landed and the adapter finishes the probe task, **When** the probe runs, **Then** `Passed = true`, `ErrorCode = null`, and **no** `render_jobs`, `credit_ledger`, `credit_lots` or `episodes` row was written.
6. **Given** the adapter fails the task with `credit_balance_exhausted`, **When** the probe runs, **Then** `Passed = false` with that code, and the resume route (12.8.3-T1) returns `reason = node_image_project_unfunded` with the latch still open.
7. **Given** a TLS/certificate mismatch or a 30 s timeout, **When** the probe runs, **Then** `ErrorCode = "node_unavailable"` and the resume reason is **not** `node_image_project_unfunded`.
8. **Given** a passing image probe on Monday and a probe call on Tuesday after the node's project was emptied, **When** the second call runs, **Then** it performs a fresh request (no cached `Passed`).
9. **Given** a failing probe, **When** the resume route returns, **Then** the response is 200 with `imageProbe = "failed"` (never 5xx) and the alert was raised through 11.6.2-T1 only.
10. **Given** the probe's own provider cost, **When** the report runs, **Then** it appears in the platform-cost buckets and never in a user's `usage_records`-driven charge or in `revenueUsd`.
11. **Given** the probe is executed with a stale owner re-auth, **When** the route is called, **Then** no node is contacted and no image is spent (the probe runs only after the auth check, 12.8.3-T1's step order).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Node becomes `down` between selection and the request | transport failure ⇒ `unavailable`; the latch stays open; the next attempt picks another node |
| Node is `draining` | never selected (only `state = 'active'`) |
| Two owners resume simultaneously | both probes may run (two image calls, cents); the latch write and the ordered dispatch are idempotent (12.8.3-T1) — the probe is explicitly **not** the concurrency guard |
| Adapter returns an unexpected 5xx | `unavailable`, alerted; never `node_image_project_unfunded` (a node fault is not a funding fact) |
| Image probe passes but a later render still fails on funds | the third trip detector (12.8.3-T2, image-failure storm) re-opens the latch; the probe is a snapshot, not a guarantee |
| Probe run while the node is mid-render at capacity | the probe uses the adapter's cheapest path and does not take the scheduler's slot (`INodeSelector` is not used); if the adapter still rejects for capacity, the outcome is `unavailable` and the resume is retried by the owner |

## Notes

- [OPEN] items carried to the TL: (1) **hard prerequisite** — a CR to 05.4.1-T2 + 11.3.5-T1 must add a probe-only route (`POST /v1/probe-image`, proposed name) on the adapter's public interface; neither `render-node.v1`'s render submit nor the node-internal image relay (`127.0.0.1:8091`, unreachable from outside the node) can serve as today's probe target, and 11.1.2-T1's mock-mpt needs the matching mode; until the CR lands this task ships the fail-closed `probe_route_unavailable` path only. (2) the attribution of the probe's own tiny provider cost (no user scope exists for a `usage_records` row) — 12.5.2-T1's `platform_loss` bucket must define it, otherwise the probe cost is invisible in the margin report.
- Deliberate non-use of `INodeSelector` (11.3.3-T2): the probe must not compete with user renders for a dispatch slot, and its result must not depend on the scheduler's fairness rule.
- The probe exists only because the node's OpenAI project is funded separately and is invisible to our configuration (11.3.2: the image key is node-managed, never stored here); if that ever changes, this task is the first candidate for deletion.
