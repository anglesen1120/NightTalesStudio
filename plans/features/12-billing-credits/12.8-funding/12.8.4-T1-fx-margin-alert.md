# 12.8.4-T1 — Effective FX rate and the 7-day price-review alert

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 12.8.4-T1 | S (0.5) | BE | 12.1.1-T1 (soft), 12.5.2-T1, 12.8.1-T1, 12.8.2-T1 | — | S · M2 |

## Goal

One FX rate, one source, no config write: the effective `USD→VND` rate is the latest recorded top-up (`provider_topups.fx_rate` by `paid_at DESC, created_at DESC LIMIT 1`), with `Credit:FxUsdVndFallback` (validated at boot) only when no top-up exists — and everything that prices in VND reads it through the single port `IFxRateProvider.CurrentAsync()`, **declared by 12.1.2-T1** (options-backed fallback implementation) with its **DB-backed implementation owned by 12.8.2-T1** (BR31 — no new edge; this task neither declares nor implements the port). On top of that, warn the owner before margin erosion becomes permanent: when any package's margin stays below 50 % for 7 days, raise the ratified `billing_price_review_required` alert (D16/CR-8) naming the package, the observed margin and the effective rate. This task ships `PriceReviewStage`, asserts the port's boot validation with a test (rather than re-declaring it) and invents no metric and no second pipeline.

## Design

```csharp
// Application/Abstractions/Funding/IFxRateProvider.cs — already declared by 12.1.2-T1 (BR31); shown here only as the
// shape this task consumes and asserts. This task neither declares nor implements the port.
public sealed record FxRateSnapshot(decimal UsdVnd, FxRateSource Source, DateTimeOffset? AsOf);
public enum FxRateSource { TopUp, Fallback }        // wire values frozen by BR31: fxRateSource = "topup" | "fallback"
public interface IFxRateProvider
{
    Task<FxRateSnapshot> CurrentAsync(CancellationToken ct);
}
```

- **Resolution order (F14 verbatim):** latest `provider_topups` row → `fx_rate`; none → `Credit:FxUsdVndFallback`. Query: `ORDER BY paid_at DESC, created_at DESC LIMIT 1` on `ix_provider_topups_paid_at`. Deterministic tie-break on `created_at` (two top-ups recorded with the same `paid_at`).
- **Data hygiene:** a row with `fx_rate <= 0` is skipped (logged once); if no usable row exists the fallback is used. A bad historical row must never zero the price of the whole catalogue.
- **Boot validation:** the option type binding `CreditOptions` fails startup (`ValidateOnStart`) when `FxUsdVndFallback` is outside `[15_000, 40_000]` — a plausible VND/USD band; the point is that a placeholder `0` or `1` can never reach production pricing.
- **Cache:** `IMemoryCache` entry keyed by a constant, TTL 60 s, `CurrentAsync` returns the cached snapshot; `RecordTopUpCommand` (12.8.2-T1) calls the eviction member **after** commit so the very next pricing call sees the new rate (D16: implicit update, no config write, no task) — this task asserts that contract with a test rather than implementing it.
- **Consumers (BR7):** the margin report (12.5.2-T1), the funding view (12.8.1-T1, via `fxUsdVnd` + `fxRateSource`) and `package_below_cost` (12.7.1-T1). No consumer may read `provider_topups` or the option directly; a test asserts the only reader of the option is this provider.
- **`fx_buffer` is untouched here** — it stays a `price_versions` parameter (BR7).

### `PriceReviewStage` (contributed to `FundingRunwayJob`)

```csharp
public sealed class PriceReviewStage(IPriceCatalog prices, IFxRateProvider fx, /* cost source: 12.5.2-T1's query */ IAlertSink alerts, IClock clock)
    : IFundingRunwayStage { public Task RunAsync(CancellationToken ct); }
```

- Window: the **last 7 complete UTC days** (from `IClock`).
- For each active `credit_packages` row and each day, the FX effective on that day is the latest top-up with `paid_at <= end of that day` (fallback when none) — the rate is a step function, so a per-day rate is exact and needs no stored daily snapshot.
- Package margin for a day:

```text
priceUsdPerCredit = (priceVnd / credits) / fxUsdVnd(day)
costUsdPerCredit  = credit_usd × (1 − margin)          // price_versions: price per credit × planned cost share
marginPct(package, day) = 1 − costUsdPerCredit / priceUsdPerCredit
```

  `bonus_credits` are not added to `credits` here: the bonus is a promotion cost and is already visible in the realised report (12.5.2-T1) — using them twice would understate margin twice.
- Alert condition: `marginPct(package, day) < 0.50` on **all 7** days for at least one active package → one alert per package per 7-day window, naming the package code, the worst day's margin and the rate used. A single day above 50 % resets the streak (that is the whole point of "for 7 days").
- Alerts go through 11.6.2-T1 only (D17) under the ratified rule key `billing_price_review_required` (CR-8: any package below 50 % margin for 7 days) — no new metric family is created; the alert carries its numbers in its payload.
- The realised margin from 12.5.2-T1 is included in the alert payload as context (it is the number the owner already trusts, BR8) but the alert decision uses the per-package formula above — a portfolio-level margin can be healthy while one package is being sold below cost.
- No writes: the stage never updates `credit_packages` or `price_versions` (pricing changes are an owner decision through the existing admin routes, 12.7.1-T1/12.1.2-T1); it only alerts.

## Acceptance checks

1. **Given** top-ups with `paid_at` 2026-09-10 (rate 25,100) and 2026-09-20 (rate 26,100), **When** `CurrentAsync()` is called, **Then** it returns 26100 with `Source = TopUp` and `AsOf = 2026-09-20`.
2. **Given** two top-ups with identical `paid_at` but different `created_at`, **When** `CurrentAsync()` is called, **Then** the later `created_at` wins (deterministic tie-break).
3. **Given** no top-up rows and `Credit:FxUsdVndFallback = 25_500`, **When** `CurrentAsync()` is called, **Then** `UsdVnd = 25500`, `Source = Fallback`, `AsOf = null`.
4. **Given** `Credit:FxUsdVndFallback = 0` (or 1), **When** the host starts, **Then** startup fails with the validator message (no silent 0-rate pricing).
5. **Given** a stored top-up with `fx_rate = 0`, **When** `CurrentAsync()` is called, **Then** that row is skipped and the fallback/last usable row is used, with one log line.
6. **Given** a cached snapshot and a new top-up committed, **When** the next `CurrentAsync()` is called, **Then** it returns the new rate (eviction after commit, not before).
7. **Given** no eviction happened (e.g. a direct DB insert by an operator), **When** 61 seconds pass, **Then** the next call re-reads the DB (TTL backstop).
8. **Given** the funding view, **When** it is read, **Then** `fxUsdVnd`/`fxRateSource` equal the port's value in the same request (one call, no second source of truth).
9. **Given** package P with `priceVnd = 250_000`, `credits = 1_000`, active `credit_usd = 0.01`, `margin = 0.60` and an FX of 25,000 for all 7 days, **When** the stage runs, **Then** the computed margin is 40 % and an alert is raised naming P, the worst day and the rate (this is the FX-erosion case: the VND price no longer covers the planned cost share).
10. **Given** the same package but with a 20 % margin on one of the 7 days (FX recovered for a day), **When** the stage runs, **Then** **no** alert is raised (the streak is broken).
11. **Given** only 6 days of history since the first package was created, **When** the stage runs, **Then** no alert is raised (7 complete days are required) and nothing is logged as an error.
12. **Given** a below-50 % margin on two packages, **When** the stage runs, **Then** one alert per package is emitted, all through 11.6.2-T1, and a second run in the same window re-alerts at most once per 24 h.
13. **Given** any pricing consumer, **When** the architecture test scans the solution, **Then** only `FxRateProvider` reads `CreditOptions.FxUsdVndFallback` and no consumer queries `provider_topups` directly.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| No top-up and an invalid fallback | host fails at startup (check 4) — the only safe outcome, because every VND price depends on it |
| All top-up rows non-positive (bad legacy data) | fallback used + one log/alert; the funding view's `fxRateSource` says `fallback` so the owner can see the data problem |
| FX step mid-window | each day is evaluated with the rate effective **on that day**; an intraday top-up does not retroactively change the previous day's margin |
| Package `active = false` | excluded (a discontinued offer needs no price review) |
| `credits = 0` on a package row | division guard: the package is skipped and logged (data error, and the admin save path already rejects it) |
| Alert storm risk | the stage dedupes per package per 7-day window with at most one alert per 24 h; a re-alert is expected while the erosion persists |
| The realised margin (12.5.2-T1) and the per-package formula disagree | both numbers are in the alert payload; the decision uses the per-package formula (a portfolio average can hide a below-cost package) |

- The per-package margin formula is [INFERENCE]: D16 names the threshold and the window (50 %, 7 days) and F14/D10 freeze the inputs (`priceVnd`, `credits`, `credit_usd`, `margin`, `fx_rate`), but no formula is written down; the chosen one is the FX-erosion reading of "VND prices stay above cost when the exchange rate moves" (high-level §12.8.4).
- `PriceReviewStage` deliberately does not mutate prices: raising a price is an owner action through the existing package/price-version routes, and an automated price change would be a silent commercial decision.
- Soft dependency on 12.1.1-T1: the cost model's measured `credit_usd`/`margin` values make the 50 % threshold meaningful; against placeholder values the stage still runs but its alerts are advisory only.
