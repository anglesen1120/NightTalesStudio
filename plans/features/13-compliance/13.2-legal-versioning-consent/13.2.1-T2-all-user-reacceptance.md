# 13.2.1-T2 — All-user blocking re-acceptance at login

| Story | Size | Area | Depends on | Blocks | Phase / flag |
|---|---|---|---|---|---|
| 13.2.1 | XS (0.25) | BE/FE | 13.2.1-T1, 13.2.2-T1, 10.2.2-T1 | 10.3.2-T1 | S · M2 |

## Goal

Make a material policy change block every existing user at the next login: the success responses of `POST /auth/login`, `POST /auth/refresh` and `GET /me/legal` carry `pendingAcceptance` — the list of documents whose current version the user has not accepted — so the SPA (10.3.2-T1) can raise the blocking dialog before routing (D7/F2). No new error code, no forced re-authentication, tokens stay valid, and a version scheduled for the future (`effective_at > now()`) is never reported before its instant.

**Locale.** `pendingAcceptance` resolves versions in the user's `UiLocale` (`vi` | `en`; register takes it, A6) with `vi` as the fallback when unset [DECISION] — the two locales may legitimately carry different versions (D6 is per (kind, locale)), and the user must be shown the version of the text they will actually read.

**Document set (in scope of the scan).** `tos` and `privacy`, always in that order — the same order as `LegalAcceptanceDto.Documents` (A2). `age_18` is deliberately excluded (registration-time attestation; `POST /me/legal/accept`'s body is P-signed `{tos, privacy}` and must not change — plan O-4).

**Zero side effects.** No write, no audit, no e-mail, no outbox event, no SignalR message (the P slice recorded the same rule for acceptance); the only added cost is one indexed `user_consents` projection plus one indexed resolver lookup per document per login/refresh/`GET /me/legal`.

## Steps

1. Add `GetPendingAsync` to `ILegalAcceptance` and `PendingAcceptanceDto`/`PendingDocumentDto`.
2. Implement `PendingAcceptanceReader` (single `DISTINCT ON` query + resolver comparisons) and use it from `LegalAcceptanceService`/the `GetLegalAcceptanceQuery` handler so the gate and the DTO cannot disagree (one reader, one truth).
3. Append `PendingAcceptance` to `LegalAcceptanceDto` and assert the P test double (`LegalAcceptanceDto` equality helpers) is updated — the `documents` array must be byte-identical to before.
4. Attach `pendingAcceptance` to the login and refresh success responses (O-1 edit request); never on failure paths (401/403/429).
5. Run the locale rule through the reader (user `UiLocale`, fallback `vi`) and add the `vi`/`en` test cases.
6. Tests + the staging capture for the `13-S-legal` gate (a synthetic non-owner login before/after accepting).

## Outputs

- `ILegalAcceptance.GetPendingAsync` + `PendingAcceptanceReader` (one query, no N+1).
- `LegalAcceptanceDto.PendingAcceptance` and `pendingAcceptance` on login/refresh 200 bodies.
- The JSON contract 10.3.2-T1 consumes, frozen by tests; no new route, no new code, no new copy.

## Acceptance checks

- Given a user who accepted `privacy 1.0.0` while the current version is `1.1.0`, When `POST /auth/login` succeeds, Then the 200 body contains `pendingAcceptance: { documents: [{ document: "privacy", currentVersion: "1.1.0" }] }` and an access token is issued (no 409, no `reauth_required`).
- Given the same user, When `POST /auth/refresh` succeeds, Then the same object is present on the refresh response.
- Given the same user, When `GET /me/legal` returns, Then `documents` is unchanged (both documents, order `tos`, `privacy`, same fields) **and** `pendingAcceptance` is present with the single pending document.
- Given a user up to date on both documents, Then `pendingAcceptance.documents` is `[]` on all three responses — never `null`, never absent.
- Given the accepted version equals the current one, Then that document does not appear (accepting the current version satisfies it until the next material change).
- Given a scheduler-published `tos 1.2.0` with `effective_at = now() + 14 days`, Then it appears in no `pendingAcceptance` before the instant (`FakeClock` before/after).
- Given a user whose `UiLocale = 'en'` and whose `en` current version differs from `vi`, Then the reported `currentVersion` is the `en` one (and the fallback is `vi` when unset).
- Given any of the three responses, Then no `user_consents` row, no audit row, no outbox row and no e-mail is produced.
- Given the P acceptance tests, Then they pass unmodified (stale accept → 409 `legal_version_outdated`, sorted `errors.documents`, nothing written).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| `user_consents` empty (never accepted) | Both documents are pending; the dialog is shown; `GET /me/legal` still reports `acceptedVersion: null`. |
| A consent row exists for a version no longer in the registry (history) | It is simply not equal to the current version → pending; no query on `legal_documents` history and no error. |
| Resolver/config unavailable (DB error) | Login/refresh must not fail because of the pending read: `pendingAcceptance` is advisory UX only, so the handler logs `legal.pending.failed` (warning) and returns `pendingAcceptance: { documents: [] }` — no 500, no new config flag (ruled T23, README §B10) — login/refresh always succeed on their own merits. The **enforcing** gate is unchanged P `EnsureCurrentAsync` → 409 `legal_acceptance_required` (`…/13.2.1-T1-…md:171`), which still fails closed; a resolver outage there is a separate 09.3.1-T1 concern, not this task's. |
| User locale is neither `vi` nor `en` (or unknown) | Fall back to `vi` (the register-time default) — never 400. |
| The same document accepted twice (history rows) | `DISTINCT ON (document) … ORDER BY accepted_at DESC, id DESC` picks the newest row; ties broken by `id` so the result is deterministic. |
| A user with `tos` current but `privacy` stale | Only `privacy` is reported; acceptance remains all-or-nothing in the POST (P contract). |
| `age_18` missing while `tos`/`privacy` are current | Nothing is reported (plan O-4): the age attestation is registration-time; revisit only if 13.6.1-T1's memo demands re-attestation. |
| Very large `user_consents` history per user | One indexed projection with `DISTINCT ON`; no per-row load, no `AsEnumerable`. |

## Notes

- **T7 discipline.** The only edit inside the P files is additive (`LegalAcceptanceDto` gains a property; the query handler calls the new reader). If a reviewer sees `EnsureCurrentAsync`'s signature, its `documents` ordering, or `POST /me/legal/accept`'s body change here, that is a defect.
- **Trap (pinned by a test).** `pendingAcceptance.documents` is ordered `tos`, `privacy` (projection order) while the gate's `errors.documents` is alphabetical (`["privacy","tos"]`). Do **not** "unify" them: 06/02 and the P tests assert the alphabetical gate order.
- Resolved: **O-1** — D7's field on the P-signed `LoginResult` (`09.3.2-T1:146`) and the `RefreshResult` wrapper (`:148`, keeping `IssuedAccessToken` a pure token record, `:29`) are now covered by **13 CR-28** (README §B4). Implement `GET /me/legal` and both response extensions; do not introduce a parallel login response type.
- **No new codes, no copy.** D7 fixes "no new error code"; the dialog's wording is 10's (`errors.legal_acceptance_required` etc. stay P's).
- **Consumer.** `10.3.2-T1` (CR-13) — it needs this exact JSON and the design gate (owner rule 2026-09-25) comes before any of its UI work.
- **Observability.** `legal.pending.failed` (warning, no e-mail/IP/user id in the payload; only the `traceId` and document kinds). No metric is added.
