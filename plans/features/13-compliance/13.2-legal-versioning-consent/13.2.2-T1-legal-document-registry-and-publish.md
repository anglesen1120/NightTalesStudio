## Goal

Create `legal_documents` and make it the **runtime source of the current legal version** per (kind, locale), so a published policy change no longer needs a code change: the resolver behind the P contracts (`ILegalAcceptance`, `IConsentWriter`'s version source) reads the max row with `effective_at <= now()`, with the `LegalDocuments:Current:*` config as the first-boot seed only (D6/F6/F10). Ship the operator verb `nts-worker legal publish` that refuses a version whose served file is not deployed (409 `legal_content_missing`, T6), take ownership of `tools/ci/check-legal-versions.py` (CR-12) and add the fail-fast startup equality assertion.

**Publish handler flow (single transaction, no lock).**
1. Validate (validator) → 400 `validation_failed` on a malformed version/kind/locale/content-url prefix.
2. Read the **published** current version for (kind, locale) with `TryGetPublishedVersionAsync` (**no** seed fallback — the verb must never treat the config value as a published row); if a row exists and `LegalVersionComparer.Compare(new, current) <= 0` → `Error.Validation("legal_version_not_increasing", …)` [INFERENCE code — 09's catalogue is the registry; if the TL prefers, reuse `validation_failed` and keep the CLI message].
3. `IStaticContentProbe.HeadAsync(contentUrl)`: not `Exists` → `Error.Conflict(ErrorCodes.LegalContentMissing, "The served legal text for this version was not found.")` (UC2); probe exception → same error, logged as `legal.publish.refused`.
4. Fetch the bytes once (bounded 1 MiB), `checksum = "sha256:" + Convert.ToHexString(SHA256.HashData(bytes)).ToLowerInvariant()`.
5. Insert in one command: read the existing (kind, locale, version) row — if present with an equal `checksum` → return the existing row (idempotent, UC7); if present with a different `checksum` → `Error.Conflict("legal_version_conflict", …)` and write nothing. Otherwise `Add` the row with `PublishedBy = ICurrentUser.Id` and return it. The unique index is the only serialization point; no advisory lock is taken [DECISION — `ux_…` makes a concurrent double publish fail with one unique violation, which the handler retries once as the idempotent read path].
6. The audit row is written by `AuditBehavior` inside the same transaction; `SaveChangesAsync` is called only by `UnitOfWorkBehavior` (09.2.1-T1) — the handler never calls it.

## Acceptance checks

- Given a deployed `privacy 1.1.0` file, When the verb runs for `vi`, Then one `legal_documents` row exists with `kind='privacy'`, `version='1.1.0'`, `locale='vi'`, `effective_at` as passed, `content_url` as passed, `published_by` = the operator id, `checksum` a `sha256:` of the served bytes, one `legal.document_published` audit row with `visibility = internal` and no text/path in `data`, and the exit code is 0.
- Given the same command again with identical served bytes, Then exit 0, still one row and one audit row (idempotent).
- Given the served bytes changed, Then exit 2, `code=legal_version_conflict` on stdout, and no new/changed row.
- Given a version lower than or equal to the current one, Then the command fails with a validation error and writes nothing.
- Given `/content/legal/privacy.1.2.0.vi.md` → 404 or an unreachable origin, Then exit 3, `code=legal_content_missing`, no row, no audit row.
- Given `LegalDocuments:Current:Privacy = 1.0.0` while the current `privacy` row (`effective_at <= now()`) is `1.1.0`, When the API starts, Then startup throws the mismatch message and no request is served.
- Given a `privacy 1.2.0` row with `effective_at = now() + 14 d` alongside the current `1.1.0`, When the API starts, Then startup **succeeds** — the future-dated scheduled row is not the current row (I5, 13 CR-33).
- Given an empty `legal_documents` table, Then startup succeeds and the resolver returns the config value (seed path); `GET /me/legal` still returns the same `LegalAcceptanceDto` shape as before this change (A2) — the P contract tests pass unmodified.
- Given `--db` pointed at a database whose current row (max `version` with `effective_at <= now()`) differs from `manifest.json`, When `tools/ci/check-legal-versions.py` runs, Then it exits 1 with a `file: line: message` line naming the kind, locale and both versions.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Served file missing (404) | 409 `legal_content_missing`, exit 3, **no** row, **no** audit row (fail closed). |
| Static origin unreachable / TLS error / timeout | Same as missing: fail closed, exit 4 in the CLI, warning log `legal.publish.refused reason=probe_unreachable`. |
| File larger than 1 MiB or not a text type | Refuse (`legal_content_missing` family, CLI exit 3) — the legal texts are small; a huge payload means the path is wrong. |
| Concurrent identical publishes | One insert wins; the loser maps the unique violation to the idempotent read and returns the same row (one audit row from the winner). |
| Concurrent publishes of two different versions for the same pair | Both rows are written (append-only is not a conflict); the resolver picks the greater `effective_at <= now()` (deterministic by `LegalVersionComparer` on a tie), and the startup check requires the config to equal that **current** row — a mismatch fails the next deploy (13 CR-33). |
| Config says a version that has no row and the table has rows for that pair | Startup fails fast (UC4). |
| Config missing or > 32 chars | Existing `ValidateOnStart()` behaviour (A4) — untouched. |
| Migration run against a database that already has a `legal_documents` table (manual hotfix) | EF migration fails loudly; no `IF NOT EXISTS` and no destructive `Down` in production — the operator rolls forward with a new migration [DECISION]. |
| `LegalDocuments:Current:Age18` absent | The resolver returns the seed from the config only for the pairs it is asked about; `Age18` is only requested after 13.2.3-T1 (soft dependency) — the key is added there (CR-11), not here. |
| A DB error inside the resolver | Propagates: `GET /me/legal` → 500 with `traceId`; the gate fails closed (the action does not proceed), matching P's rule (`…/13.2.1-T1-…md:171`). |

## Notes

- **P contracts untouched (T7).** No signature, DTO, route, audit action or option type of `13.2.1-T1` changes; only the version *source* moves behind them. A reviewer should diff `LegalAcceptanceService`/`LegalAcceptanceReader` against the P task file and find only the resolver call swapped in.
- **Reuse (D18).** One audit path (`[Audited]`/`IAuditWriter`), one CLI host, one blob/public-origin configuration — no new HTTP client family, no new e-mail, no new flag, no new table besides the contracted one.
- **Transaction/lock.** Exactly one write command; `SaveChangesAsync` stays `UnitOfWorkBehavior`'s; the unique index is the only lock (no `pg_advisory_lock`, no table lock). Audit and row commit atomically — an audit row without its version row (or vice versa) is impossible.
- **Performance.** One indexed lookup per (document, locale) per request; the verb's single 1 MiB-bounded download; no query touches `user_consents`.
- **Observability/i18n.** Log/metric names are pinned in §7 of the plan; the CLI prints codes (English), never user-facing copy, so no vi/en strings are added by this task beyond the attestation text owned by 13.2.3-T1.
- Resolved: O-2 (`age_gate` added via **13 CR-26**) and O-1 (`LoginResult`/`RefreshResult` via **13 CR-28**, owned by 13.2.1-T2). The audit pair is D6's (`support`, `internal`), both already present in the contract (`00-overview.md` §6:307) — no new category is introduced.
- **Out of scope.** Publishing to the *page* (web deploy), the lawyer review, `age_18`, `pendingAcceptance`, deletion/export/report work, and any admin UI (O6).
