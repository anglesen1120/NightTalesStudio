## Goal

Satisfy the 18+ rule of 13 §5.1/§5.2 with a mandatory **self-attestation** recorded as evidence: an `age_18` row in `user_consents` written through the existing `IConsentWriter`, the attestation text published and versioned like every other legal document, the enum member + config key added by CR-11, and registration rejecting an unchecked box with 400 `age_attestation_required` (CR-10). No identity verification in S (D8, O5).

**Validation and record flow.** `POST /auth/register` body unchanged (`Consents` may now carry the third entry). Order: (1) existing validation; (2) `IAgeAttestationGuard.Require(consents, options.Age18)` → on failure 400 `age_attestation_required` with `errors: { age18: [...] }` [DECISION — the FE needs a field to attach the message to; the register command's own field is the `Consents` list]; (3) the existing per-entry `IConsentWriter.RecordAsync(userId, document, version, ip, ct)` loop records `age_18` exactly like `tos`/`privacy`; (4) everything commits in the one registration transaction (`UnitOfWorkBehavior`), so a user row without its attestation is impossible.

**Version source.** `options.Age18` is the seed like every other pair (D6); once 13.2.2-T1's registry has an `age_gate` row with `effective_at <= now()`, that row is the current version (the guard compares against the same resolver value the recording uses, so `user_consents.version` cannot diverge from the served text). The `age_gate` value in `legal_documents.kind` is an extension of K8's three-value list — see O-2.

## Acceptance checks

- Given a registration submitted without an `age_18` entry in `Consents`, Then the response is 400 with `code = age_attestation_required`, `errors.age18` present, and **no** `users` row and **no** `user_consents` row exists afterwards.
- Given an `age_18` entry whose version differs from `LegalDocuments:Current:Age18`, Then 400 `age_attestation_required` (the version is stale) and nothing is written.
- Given a registration with `tos` + `privacy` + `age_18` at the current versions, Then **202** (the status `09.3.1-T3:112` fixes for `POST /auth/register`) and raw SQL shows one `users` row plus three `user_consents` rows for the new user, one with `document = 'age_18'`, `version = '1.0.0'` and a non-null `ip`; the `document` column stores snake_case.
- Given the app boots without `LegalDocuments:Current:Age18`, Then startup fails through the existing `ValidateOnStart()` (fail fast, no `1.0.0` default) — the key ships together with the content, never later.
- Given the `manifest.json` has no `age_gate` entry while the config key is set, When `tools/ci/check-legal-versions.py` runs, Then it exits 1 naming the missing entry (the check is extended in 13.2.2-T1).
- Given the served attestation text for the current version is missing, When an operator tries to publish that version, Then 409 `legal_content_missing` (13.2.2-T1's verb) and the acceptance path keeps working against the previous current version.
- Given an existing user (the owner, registered in P) who has no `age_18` row, Then nothing blocks their existing session and the gate's `errors.documents` stays `["privacy","tos"]` (plan O-4; P untouched, T7).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Checkbox unticked (no `age_18` entry) | 400 `age_attestation_required` before any write; the user row is not created (the guard runs before `UserManager`'s create in the flow). |
| `age_18` version stale (page cached before a bump) | 400 with the same code; the form reloads the current version — no partial write. |
| Duplicate `age_18` entries in the payload | Rejected (exactly one required) — guards against a client sending both `vi` and `en` attestations. |
| `user_consents` insert fails (FK violation: user deleted mid-flight) | The whole registration transaction rolls back (existing behaviour, A5/I6) — never a user without the attestation. |
| Config key missing/oversized | Startup failure (existing `ValidateOnStart()`), so the feature can never be "half on". |
| PDPL memo (13.6.1-T1) later requires verifiable age assurance | Out of scope: D8/O5 fix self-attestation for S; the memo creates a backlog story and, if the attestation text changes materially, a version bump through 13.2.2-T1's publish path. |
| A user attests 18+ falsely | The record proves *what* was attested and when (version + time + IP); no identity verification exists in S (D8 [DECISION]) — the ToS/Privacy text states the rule; this limitation is recorded, not hidden. |
| Attestation text not deployed while the config key is already set | The publish verb refuses (409 `legal_content_missing`) and the CI check fails; the acceptance path still resolves the previous version, so registration never blocks on a text the user cannot read. |
