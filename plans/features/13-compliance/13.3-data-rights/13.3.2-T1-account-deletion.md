## Goal

Give the `account` scope of the P deletion engine (`../13.3.1-deletion-engine/`) an owner, so a user (or 09.10.5-T1's admin path) can ask for account deletion and the platform can prove it happened inside the 7-day window. `POST /me/delete` re-authenticates, revokes every refresh family and trusted device, opens exactly one `data_deletion_requests (scope=account, reason=account_delete)` row with `due_at = requested_at + 7 d` and sets `users.status = 'suspended'`; `AccountDeletionScopeHandler` then composes the existing owners (06 channels/publications, 02 series/episodes, 09 sessions/storage, this folder's exports) into per-table batched set-based deletes, removes the user's storage prefixes and anonymises `users` — keeping only the pseudonymised ledger, audit rows and the deletion row itself. `GET /me/deletion-requests` and `GET /admin/deletion-requests?status=` make the state visible (F14); the retry verb stays 13.3.1-T1's `nts-worker deletions` (D18: no second deletion path).

## Design

**Command/query surface** (`src/NightTales.Application/Compliance/Deletion/`, one file triple each, `[Audited]`/`[NotAudited]` exactly once):

```csharp
[Audited] public sealed record DeleteMyAccountCommand(string CurrentPassword) : ICommand<DeleteMyAccountResult>, IIdempotentCommand;
public sealed record DeleteMyAccountResult(Guid RequestId, DateTimeOffset DueAt);

[NotAudited] public sealed record GetMyDeletionRequestsQuery(string? Status) : IQuery<IReadOnlyList<DeletionRequestDto>>;
public sealed record DeletionRequestDto(Guid Id, string Scope, string Reason,
    DateTimeOffset RequestedAt, DateTimeOffset DueAt, DateTimeOffset? CompletedAt, string Status);   // D10 shape, verbatim

[NotAudited] public sealed record GetAdminDeletionRequestsQuery(string? Status, string? Cursor)
    : IQuery<AdminPageDto<AdminDeletionRequestDto>>;                 // 09's envelope, ≤ 100/page, keyset on (requested_at DESC, id DESC)
public sealed record AdminDeletionRequestDto(Guid Id, Guid UserId, string Scope, string Reason,
    DateTimeOffset RequestedAt, DateTimeOffset DueAt, string Status, int Attempts);
```

`DeleteMyAccountCommandHandler`: verify `CurrentPassword` against the Identity store (a stale step-up window is 401 `reauth_required`, a wrong password is 401 `invalid_credentials`, both before any state change) → revoke every refresh family and trusted device through the 09.3.x ports → `IDeletionRequests.CreateAsync(userId, DeletionScope.Account, null, DeletionReason.AccountDelete, ct)` (the upsert on `(user_id, scope, target_id, reason) WHERE completed_at IS NULL` makes a repeat call return the **same** open row, YR13) → `users.status = 'suspended'` (T2: no new status value; the open row is the reason of record) → stop every running job/queue item for the user (autopilot/renders are 02/06/09 owners' pause paths — fail the attempt with `account_busy` instead of deleting underneath a live writer). Handler ≤ 80 lines: the state change is the command, the row work is the handler below.

**Scope handler** (`src/NightTales.Infrastructure/Compliance/Deletion/Handlers/AccountDeletionScopeHandler.cs`):

```csharp
public sealed class AccountDeletionScopeHandler : IDeletionScopeHandler
{
    public DeletionScope Scope => DeletionScope.Account;
    public async Task<ErrorOr<DeletionResult>> ExecuteAsync(DeletionRequest request, CancellationToken ct);
}
```

Registered in the Worker composition root next to the P `EpisodeDeletionScopeHandler`, and `DataDeletion:DeferredScopes` becomes `[]` **in the same change** (otherwise the P validator fails Worker boot — the intended guard).

Order of work, each step idempotent and safe to repeat:

1. **Children first, parents last** — one batched `DELETE` per table per transaction (≤ 5 000 rows, `user_id = @id`, loop until 0 rows):
   `render_jobs`, `publications`, `channel_connections`, `story_versions`, `story_sources`, `fact_sheets`, `generation_runs`, `fetch_tasks`, `source_candidates`, `episodes`, `series`, `assets`, `data_export_requests`, `user_action_tokens`, `email_messages` (the user's own; [INFERENCE] — not on D10's/T22's keep-list, and a deleted account's send log is not needed for accounting). Every name is a `00-overview.md` §6 table ✅. **`user_consents` is NOT in this list** — T22 rules it survives deletion (tos/privacy/age_18 rows, version/time/ip, no contact data). The wallet/credit-ledger and `payments` tables are also **not** in this list (keep-list, step 5). The exact list is the proposal; the **assertion** is the architecture test below, not this literal list.
2. **Storage prefixes** — `media/{userId}/`, `research/{userId}/`, `exports/{userId}/` under `nt-media-<env>` via `IBlobStore` (prefix member from `13.3.1-T1` CR-1; until it lands, delete the DB-enumerable keys only and log `research_prefix_sweep_pending`, exactly like the episode handler).
3. **Publication/agent hand-offs** — publications in `awaiting_consent|scheduled` go through 06.2.6-T1's cancel rules; an `uploaded` publication is **not** cancelable (409 `publication_invalid_state`, user copy `publication.cancel.uploaded_use_studio`, `06.2.6-T1:30`) → unlink/hide instead, and the handler records which branch ran per row (CR-23). Channel side reuses 06.4.1-T1/06.4.3-T1 through `IDeletionScopeHandlerRegistry.Resolve(DeletionScope.Channel)` — no second channel path (D18).
4. **Anonymise** (single statement, after the child tables are empty):
```sql
UPDATE users SET email = 'deleted+' || left(encode(sha256(id::text::bytea), 'hex'), 16) || '@invalid',
                 display_name = 'deleted user', status = 'deleted',
                 mfa_secret = NULL, recovery_codes = NULL, updated_at = now()
WHERE id = @id;
```
   plus the normalized-address column Identity requires (⚠️ exact column name confirmed against 09.3.1-T1 at implementation) so the unique index stays satisfiable.
5. **Keep** (D10/T21/T22, ⚠️ 12's ledger keep-window pending): `payments` + credit ledger rows get a **random pseudonym UUID** written into `user_id` (T21: `user_id = gen_random_uuid()`, no mapping retained anywhere — amounts/dates/order codes stay, and the row is no longer joinable to `audit_logs` or the deleted user), `audit_logs` (subject/actor id kept, e-mail/IP redacted in `data`), `data_deletion_requests` (evidence), `user_consents` (T22: kept as-is — `document`/`version`/`accepted_at`/`ip`, no contact data). `usage_records` must survive (13 §5.4, `13.3.1-T1:82`).
6. **Complete**: `request.Complete(now)` → `completed_at`, audit `account.data_deleted` (`support`, `internal`, `ActorLabel = "system:operator"`), same transaction as step 4. Metrics are the P job's metric phase (`deletion_requests_open`, `deletion_request_overdue_total`) — nothing extra here.

**Admin read** (`AdminDeletionRequestReader`, the only other bypass site, CR-20): `IgnoreQueryFilters(["tenant"])` + keyset `(requested_at DESC, id DESC)` + `?status=open|overdue` where `overdue` = `completed_at IS NULL AND due_at < now()`. **The route is not ours:** `GET /admin/deletion-requests?status=&cursor=` is a row of the single `/api/v1/admin` group registered by **09.9.1-T1** under `AdminPolicy` (`09-backend-api/README.md:1053`, 09 D20:1032), returning `AdminPageDto<AdminDeletionRequestDto>{ items, nextCursor }` with ≤ 100/page, and wrong role/unauthenticated → **404 `not_found`** (never 403). This task supplies the handler, DTO, engine and audit behaviour; reading stays read-only (no PATCH/POST/DELETE here).

**Operator CLI** (CR-25, this task): `Cli/DeletionsRetryCommand.cs` — `nts-worker deletions retry <requestId>` re-enqueues an open row for immediate processing by clearing `claimed_at`/backing off `attempts` so the next `DataDeletionJob` tick picks it up; `Cli/DeletionsCancelCommand.cs` — `nts-worker deletions cancel <requestId>` (T11: the only undo path — no user-facing route) deletes the row **while `completed_at IS NULL`**, sets `users.status` back to `active`, and writes audit `account.deletion_cancelled`. Both verbs are additions to the P `DeletionsCommand` CLI group (`13.3.1-T1`'s `export`/`reapply`), registered by this task.

**i18n** (D17): `account.deletion.*` in `web/src/assets/i18n/account/{vi,en}.json` (confirm/type-to-confirm/due date/completed/expired/failed copy, the 30-day backup sentence, the 7-day promise wording) — the keys are handed to 10.8.2-T1; no page is built here.

## Acceptance checks

- **Given** a signed-in user inside the step-up window, **When** `POST /me/delete` with `Idempotency-Key`, **Then** 202 `{ requestId, dueAt }`, `due_at = requested_at + 7 d`, `users.status = 'suspended'`, every refresh family and trusted device revoked, one `data_deletion_requests` row (`account`, `target_id IS NULL`, `account_delete`).
- **Given** that open row, **When** the same call is repeated with the same key, **Then** the same body; **When** it is repeated with a fresh key, **Then** the same `requestId` (one open row, YR13) — never a second row and never a 409.
- **Given** a stale step-up window, **Then** 401 `reauth_required` and no state change; **Given** a wrong password, **Then** 401 `invalid_credentials` and no state change; **Given** no `Idempotency-Key`, **Then** 400 `idempotency_key_required`.
- **Given** the due row, **When** `DataDeletionJob` runs, **Then** every child table for that user is empty, the three storage prefixes are empty, `users` is anonymised (`deleted+<16 hex>@invalid`, `display_name = 'deleted user'`, `status = 'deleted'`), `completed_at` is set, one `account.data_deleted` audit row exists, and `usage_records` / `payments` / credit rows / `audit_logs` / the deletion row still exist.
- **Given** a second run of the job on the completed row, **Then** it does nothing (idempotent, no audit row, no error).
- **Given** a batch failure mid-way, **Then** the row stays open with `status='failed'` + `last_error_code`, `attempts` incremented, and the next hourly run resumes from the first table that still has rows.
- **Given** an admin/owner, **When** `GET /admin/deletion-requests?status=overdue`, **Then** ≤ 100 rows/page, keyset cursor works, read-only (no PATCH/POST here); **Given** an unauthenticated caller or a non-admin (wrong role), **Then** 404 `not_found` (`AdminPolicy` semantics on 09's group, never 403).
- **Given** a user with no deletion rows, **When** `GET /me/deletion-requests`, **Then** 200 `[]`; **Given** another user's id, **Then** the row is invisible (tenant filter, no admin path reachable).

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Batch `DELETE` fails (lock timeout, FK) | transaction rolls back for that batch; row → `failed`, `last_error_code`, `attempts + 1`; hourly retry; after `MaxAttempts` (5) the row stays open and overdue → P alert rule fires |
| A still-running writer re-inserts rows after step 1 | the loop re-runs each table up to twice; rows still present after the second pass fail the attempt (never a "complete" with rows left behind) |
| Storage unavailable / prefix member missing (CR-1) | DB rows are deleted; objects are retried next attempt; `research_prefix_sweep_pending` logged; completion is **not** blocked (documented residual: orphan objects, same as the P episode scope) |
| User has an in-flight render / autopilot run | `account_busy` fail; the running owner's pause path must stop it first (02/06/09); retry next hour |
| Admin-initiated delete (09.10.5-T1) | same command + same row (CR-18); the row's `reason` is still `account_delete`, the actor is captured in the audit row |
| Password re-auth during an active deletion | the account is `suspended`; login is refused, so the second half of the flow cannot be interrupted by the user |
| `users.email` collision after the rename | impossible by construction (`deleted+<16 hex of the id>@invalid`), asserted by a test with two deleted users |
| `deletions cancel` on a row already completed | refused (no-op / error) — cancellation only while `completed_at IS NULL` (T11) |
| `deletions retry` on a row with `attempts >= MaxAttempts` | still re-enqueued (operator override); the P job's own `MaxAttempts` gate is for automatic retries, not the operator verb |
| Restore from backup | out of scope here: 13.3.2-T2 proves the runbook re-applies completed rows (11.6.1-T1) |
