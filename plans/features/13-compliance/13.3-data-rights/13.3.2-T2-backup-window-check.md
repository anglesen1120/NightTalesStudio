# 13.3.2-T2 — Backup-window check: retention config = 30 days, restore runbook re-applies completed deletions, e-mail and policy text match

## Goal

Prove that the promise made to the user — "your data leaves the live system within 7 days and ages out of backups within 30 days" (13 §4 13.3.2, `00-overview.md:420`, [DECISION] 30 days) — matches what the platform is actually configured to do, and that a restore cannot resurrect a deleted account. This is a **check** task, not a new feature: it pins the backup retention value, forces the restore runbook to re-apply completed deletions **before** the service reopens, and makes the confirmation e-mail and the Privacy Policy quote the same number. Deliverable is a failing test when any of the three drifts, plus one evidence line for 13.5.1-T1's pack.

## Design

No new runtime code path. Three artefacts and one test:

1. **Retention assertion.** One `BackupRetentionMatchesPromiseTests` (Application.UnitTests) binding the backup-retention options object used by 11.6.1-T1's tooling and asserting **30 days**; a comment names the two files that must change together with the number (`plans/11-*` runbook + the policy source). Failure message quotes the policy sentence so the fix is obvious.
2. **Copy alignment.** `BackupWindowCopyTests` greps the Privacy Policy source (`web/src/content/legal/privacy.1.0.0.{vi,en}.md`, later the version 13.1.1-T2 publishes) and the deletion-confirmation e-mail template for the retention number and fails when either text says something else (no "immediately", no "permanently within 7 days" for backups). Both languages are checked; the vi and en sentences must both contain the number.
3. **Runbook step.** A CR to 11.6.1-T1 (CR-21) making `restore-drill.sh` run, in order: `deletions export --since <target-time> --out <file>` **before** the restore, restore, `deletions reapply --since <target-time> --file <file>` **after** and **before** the service reopens; a non-zero exit from either must fail the drill (the P engine's exit codes are the contract). The drill is run on staging against a synthetic tenant and its result line is handed to 13.5.1-T1's evidence index (O7: binaries outside the repo).

**What is explicitly not done:** no new table/column/migration; no change to the deletion engine; no calendar row written here (K13); no promise on the user-facing deletion page about backups (T9: the copy is the policy + e-mail, not the status page).

## Acceptance checks

- **Given** the backup retention configuration, **When** the test runs, **Then** it asserts exactly 30 days and fails with the policy sentence in the message when the number changes.
- **Given** the Privacy Policy source (vi + en) and the deletion-confirmation e-mail template, **When** the copy test runs, **Then** both languages contain the 30-day backup sentence and do **not** claim immediate backup removal.
- **Given** a staging restore drill after a completed account deletion, **When** the runbook executes, **Then** `deletions export --since` runs before the restore, `deletions reapply --since --file` runs after it and before the store reopens, and the restored-and-re-applied database contains no rows for that user.
- **Given** the reapply exits non-zero, **Then** the drill exits non-zero and the runbook marks the restore as failed (never "reopened anyway").
- **Given** a second drill run on the same target time, **Then** it is a no-op and still exits 0 (YR12 idempotency).
- **Given** `GET /me/deletion-requests`, **Then** it shows `completed` for the synthetic user before the drill and still `completed` after it.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| Retention key not found / not configurable | the finding is reported (contract gap) and the assertion is written against the P options object; the drill still runs |
| Policy text says "deleted immediately" | copy test red → the text is fixed by 13.1.1-T2's next version (D6 publish path), not by editing here |
| Drill cannot run (no backup target on the dev machine) | the check is recorded as `not run on this host` in the evidence line — never recorded as passed |
| Restore reopens the service before the reapply | runbook order is the assertion; a violated order fails the drill and is treated as a release blocker for the restore step |
| Reapply partially fails (one row) | exit 1; the drill fails; the row stays open and the hourly job retries (P behaviour) |
| Clock/timezone ambiguity at `--target-time` | the target time is passed as an explicit ISO instant (UTC), never a local date (P contract) |
