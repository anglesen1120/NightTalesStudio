## Goal

One aggregate, one table and one hourly job own every deletion duty the platform owes under a legal deadline (III.D.2 7/30 days, III.E.4 30-day refresh, 13 §5.4). `IDeletionRequests.CreateAsync` is the single entry point every feature calls to start the clock; `IDeletionScopeHandler` lets each scope's owner plug in its delete logic without the engine knowing their internals (13 README D4, F3); `DataDeletionJob` executes due rows, exports the due-soon metric that 11.6.2-T1's alert rule reads, and never silently "completes" a scope nobody registered a handler for (F4: `account` stays deferred in P, a *required* scope with no handler fails the Worker at start). A CLI pair (`export` + `reapply --since`) lets 11.6.1-T1's restore drill prove that a restored backup re-applies every deletion completed after the backup point — and every still-open duty whose rows the restore erased — before the service reopens (D4, K5, YR12).

## Design

**Domain** (`src/NightTales.Domain/Compliance/Deletion/`):
```csharp
public enum DeletionScope { Account, Channel, Episode }
public enum DeletionReason { UserRequest, InAppRevoke, GoogleRevoke, AccountDelete }
public enum DeletionStatus { Pending, InProgress, Completed, Failed }

public sealed class DeletionRequest : AggregateRoot, IUserOwned   // tenant filter protects UC1's re-read + 13.3.2
{
    public Guid UserId { get; }
    public DeletionScope Scope { get; }
    public Guid? TargetId { get; }
    public DeletionReason Reason { get; }
    public DeletionStatus Status { get; private set; }
    public DateTimeOffset RequestedAt { get; }
    public DateTimeOffset DueAt { get; }
    public DateTimeOffset? ClaimedAt { get; private set; }
    public int Attempts { get; private set; }
    public string? LastErrorCode { get; private set; }
    public DateTimeOffset? LastErrorAt { get; private set; }
    public DateTimeOffset? CompletedAt { get; private set; }
    public DateTimeOffset? ReappliedAt { get; private set; }

    public static ErrorOr<DeletionRequest> Create(Guid userId, DeletionScope scope, Guid? targetId,
        DeletionReason reason, DateTimeOffset now);          // validates the scope/targetId/reason matrix, computes DueAt
    public ErrorOr<Success> Complete(DateTimeOffset now);     // -> Completed + CompletedAt
    public ErrorOr<Success> Fail(DateTimeOffset now, string errorCode, int maxAttempts);
    public ErrorOr<Success> Reapply(DateTimeOffset now);      // Completed -> InProgress (ReappliedAt set) -> Completed
}

public interface IDeletionScopeHandler
{
    DeletionScope Scope { get; }
    Task<ErrorOr<DeletionResult>> ExecuteAsync(DeletionRequest request, CancellationToken ct);
}
public sealed record DeletionResult(int ObjectsDeleted, int RowsAffected);   // YR7: shape kept, 06.4.3-T1 adapts
```
Invariants (unit-tested): `DueAt == RequestedAt + (Reason is GoogleRevoke ? 30d : 7d)`; `TargetId is null` iff `Scope == Account`; `CompletedAt is not null` iff `Status == Completed`; `Completed → InProgress` only via `Reapply`. **No `AlertedAt` field**: the due-soon alert is a monitoring rule over a metric (06.4 R6), so the engine keeps no dedupe state.

**Application** (`src/NightTales.Application/Compliance/Deletion/`):
```csharp
public interface IDeletionRequests
{
    Task<ErrorOr<DeletionRequest>> CreateAsync(Guid userId, DeletionScope scope, Guid? targetId,
        DeletionReason reason, CancellationToken ct);
}
public interface IDeletionScopeHandlerRegistry { IDeletionScopeHandler? Resolve(DeletionScope scope); }
```
`CreateAsync`: validates the scope/targetId/reason combination (domain + FluentValidation), asserts `targetId` belongs to `userId` for `Channel`/`Episode` (→ `Error.NotFound` on mismatch, never a 403-shaped leak), then `INSERT … ON CONFLICT (user_id, scope, target_id, reason) WHERE completed_at IS NULL DO NOTHING` and re-reads **by the same four columns inside the caller's tenant scope** (YR13). Joins the caller's ambient `IUnitOfWork` (no explicit `SaveChanges` — the Behaviors pipeline commits, same pattern as `EmailSender.QueueAsync`).

**Infrastructure** (`src/NightTales.Infrastructure/Compliance/Deletion/`):
- `DataDeletionRequestRepository.cs` — EF writes used **inside a tenant/system scope** only (`Create`, status transitions, the CLI's upsert); it must **not** call `IgnoreQueryFilters` (09.1.2-T1:43).
- `DeletionScopeHandlerRegistry.cs` — resolves handlers by scope; `DeletionScopeHandlerRegistryValidator` (startup) fails boot for a required scope with no handler (see Steps 7).
- `Handlers/EpisodeDeletionScopeHandler.cs` — the `episode` scope: read the episode's `assets` keys + `story_sources.extracted_text_key` rows → `IBlobStore.DeleteAsync` per key (idempotent) → **remove the episode aggregate so `story_versions`/`fact_sheets`/… cascade** (02 CR-22) → return `DeletionResult`. `usage_records` must survive (13 §5.4); if a child FK blocks the cascade the handler deletes that child explicitly — the integration test pins which case applies. Never writes `assets.deleted_at` (09.7.3-T1's column).
- `Configuration/DeletionRequestConfiguration.cs` — `IEntityTypeConfiguration<DeletionRequest>`, table `data_deletion_requests`, `HasCheckConstraint` for `scope`/`reason`/`status`, the three indexes below.
- `Migrations/<yyyyMMddHHmm>_13_DataDeletionRequests.cs` — expand-only:
```sql
CREATE TABLE data_deletion_requests (
  id uuid PRIMARY KEY, user_id uuid NOT NULL, scope text NOT NULL, target_id uuid NULL, reason text NOT NULL,
  status text NOT NULL DEFAULT 'pending', requested_at timestamptz NOT NULL, due_at timestamptz NOT NULL,

```

## Failure handling and edge cases

- **No handler for a deferred scope** (`account` in P): row stays `Pending`, `deletion_requests_unhandled_total{scope}` increments, one `Warning` per run (not per row); never `Completed`.
- **No handler for a required scope**: the Worker refuses to start (K21) — the failure surfaces at deploy, not as a silently missed legal deadline.
- **`IBlobStore.DeleteAsync` fails** (503/timeout): row → `Failed`, `last_error_code = service_unavailable`, retried next tick until `MaxAttempts`; ≥ 3 rows failing the same code in one run signals the [OPEN] incident path (CR-4) — until then metric + log only.
- **Object already missing**: `DeleteAsync` treats a missing key as success (09.7.2-T1:61), so a partial prior run never blocks completion.
- **CR-1 not yet landed**: only enumerable keys are deleted (from `assets` + `story_sources.extracted_text_key`); orphan objects under `research/…` with no DB row (02.5.2-T2:219) are **not** deleted until the port gains a prefix operation — logged as `research_prefix_sweep_pending`, a tracked gap, never silently claimed as complete.
- **Crash between object delete and `Complete()`**: the lease expires, the next tick re-claims and re-runs the idempotent handler.
- **Two workers, same rows**: only one `UPDATE` matches; the loser's read-back is empty and it skips — no double execution, no advisory lock needed.
- **Restore erases rows created after the target time**: this is why `export` also takes still-open rows and why the drill captures the list from the live DB before restoring (YR12, 11.6.1-T1 plan:62) — a re-apply that silently applied nothing exits non-zero.
- **Restore re-apply on a live/production host**: refused by the scratch-host guard (config flag, mirrors 11.6.1-T1's own check); never trusts `--force` alone.
- **`data_deletion` job disabled mid-incident**: rows keep accruing and the due-soon metric stops being exported, so operators must re-enable before the next deadline; documented, not auto-mitigated (a duty that can be missed silently needs a human, mirroring 11.6.1-T1's no-Hangfire-for-restores stance).
- **Alert backend down**: the metric phase only logs; the engine's actual deletions are unaffected (UC3 separation).

The due-soon **rule text is 06 CR-10** (TL applies), so no rule file is authored here.
- **YR7**: `DeletionResult(int ObjectsDeleted, int RowsAffected)` and `ErrorOr` failures are kept; 06.4.3-T1 adapts to this shape.
- **YR12**: `reapply` replays completed **and** still-open requests, ordered by `completed_at NULLS FIRST, id`, and fails loudly rather than reporting a false success.
- **YR13**: the partial unique index carries `user_id` — without it, two users' open `(account, NULL, account_delete)` rows would collide and `ON CONFLICT DO NOTHING` would swallow the second user's request.
- The job reads cross-user rows only through its **allow-listed** `IgnoreQueryFilters(["tenant"])` call site declared in `DataDeletionJob` (09.1.2-T1:43); per-row work uses a fresh `IServiceScopeFactory` scope with a single `ISystemContext.For(userId)` because a second `For` (or a `For` after a DbContext) throws (09.2.3-T1:24,68).
- No e-mail, no SMTP, no template, no `alerted_at`: the due-soon alert is 11.6.2-T1's rule over our metric (06.4 R6).
- Rollback: the migration is additive; disabling `DataDeletion:Enabled` stops the job without losing rows; no data is destroyed by disabling.
- **Deviation — default `DeferredScopes` (QA-1, orchestrator ruling).** The shipped default is `["account", "channel"]`, not plan §7.1's `["account"]`: no `channel` handler exists until 06.4.3-T1 and the Worker must boot. The acceptance check "a Worker started without a `Channel` handler fails to start" therefore holds only once `channel` is removed from the default; the tests prove it with `DataDeletion:DeferredScopes:0=account`. **06.4.3-T1 must remove `channel` from `DataDeletionOptions.DefaultDeferredScopes` when it registers the handler** (also noted in `plan.md` §10.1).
- **Deviation — unknown/foreign episode target (QA-2, orchestrator ruling).** `CreateAsync` already returns `NotFound` for a target the caller does not own, so an episode request for a missing/foreign target cannot normally exist; if one does (the episode was removed after the request), the episode handler completes it idempotently (0 deletes, audit row) instead of plan §7.3's `Error.NotFound` → `Failed`. Reason: a deletion duty whose target is already gone is fulfilled, and retrying to `MaxAttempts` would only raise false failures.
- **Claim and scan plan (QA-3).** The claim is a per-row conditional `UPDATE … WHERE id = @id AND (status/lease predicate)` by primary key, so two workers match a row once; the due scan uses `ix_deletion_requests_due`. Recorded `EXPLAIN (ANALYZE, BUFFERS)` on a 10k-row table: scan = Index Scan on `ix_deletion_requests_due`, 0.04 ms; the open/overdue counts = Index Only Scan. This closes the manual EXPLAIN acceptance check.
- **`CreateAsync` actor guard (SEC-1).** The insert is raw SQL and bypasses the tenant filter, so `DeletionRequests` takes `ICurrentUser`: an `ActorType.User` caller whose id differs from `userId` gets `NotFound` and no row is written. `Admin` (the staff delete surface) and `System` (pinned job scopes) actors, and an unpinned scope, keep the unchanged behaviour — their authorization stands with the caller (plan UC1).
- **Duplicate handlers (QA-5).** `DeletionScopeHandlerRegistryValidator` fails Worker start-up when two `IDeletionScopeHandler`s share a scope, naming the scope; the registry never has to choose.
- **Config docs (QA-4).** `docs/dev-setup.md` has no section listing optional Worker keys (its tables list only required keys and boot contexts), so the `DataDeletion:*` keys stay documented in plan §7.1 and `DataDeletionOptions` only.
