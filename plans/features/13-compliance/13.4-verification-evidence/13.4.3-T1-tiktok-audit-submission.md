File the TikTok Content Sharing audit (R2) so the 07 posting path may publish publicly: argue the intended use — **public creators sharing their own content, not an internal tool** ✅ — and show **every** UX item the platform requires, each one mapped to a shipped screen and a captured artefact from the 13.5.1-T1 evidence pack.

This is the last task of the S slice (W4, §B5 :313) and the only R2 item in this folder (O8 :401 — its 0.5 d is inside the S slice's 8.5, not additive).

## Design

**Repo artifact (text only).**

```
docs/compliance/tiktok-audit-<yyyy-mm-dd>.md     # <yyyy-mm-dd> = filing date, ISO
```
The README fixes no path for this filing (it fixes `google-oauth-verification-<date>.md` and `pdpd-memo-<date>.md`), so this name follows D12/D16's convention **[INFERENCE]**; ruled **T17** (README §B10): `docs/compliance/tiktok-audit-<yyyy-mm-dd>.md` stays this task's single filing copy, and `07.4.1-T1` links to it rather than keeping its own.

**Sections.**

```
  ## 0. Header
  ## 1. Intended use
  ## 2. Required-UX matrix
  ## 3. AI disclosure
  ## 4. Consent / revoke
  ## 5. Content policy
  ## 6. Calendar rows
  ## 7. Follow-up log
```

| § | Contents |
|---|---|
| §0 | filing date · app id (redacted label + external artefact id) · `07.4.1` revision · pack date/path · sign-off |
| §1 | intended use — public creators sharing their own content, multi-user, **not** an internal tool — plus the operator consent model (per-post consent + series authorization) |
| §2 | `\| # \| Required UX item (verbatim from 07.4.1) \| Where in the product \| Owning task id \| Evidence artefact id \| Verdict \|` |
| §3 | `is_aigc = true` · the code path that sets it (07) · any user-visible disclosure, described as it actually ships |
| §4 | grant · per-post consent · disconnect · deletion request — each with an artefact id |
| §5 | prohibited/restricted sections + the report route (`/vi/report`, `/en/report`) as the takedown path |
| §6 | filing date · expected reply (range/unknown ⚠️) · re-file cadence · appeal path |
| §7 | appended per exchange (info requested, granted, denied + reason); earlier sections are never rewritten |

**Matrix rules.** One row per required UX item, in 07's order; `Verdict ∈ {proven, provisional, gap}` where `provisional` = the evidence is staging-only or the screen is not shipped (10 wave 2 **[OPEN]**), and a single `gap` **blocks the filing** — the same rule 13.4.2-T1 uses for the YouTube audit. No row may have an empty `Evidence artefact id` or an empty `Owning task id`.

**Content rules (D14).** Synthetic tenant `demo+<n>@invalid`; no real e-mail, IP, token, API key or real user's story text in any artefact; demo video/screencast (if the portal requires one) is recorded with its location + visibility in the artefact index, and the binary lives in `~/.nts/compliance/…`, never the repo.

## Steps

1. Wait for `07.4.1-T1`'s required-UX-item list (hard); copy the items **verbatim** into §2, in its order. If 07 lists a different set than the portal shows at filing time, record both and flag the difference in §7 — do not silently reword 07.
2. Fill §1 from 07's contract: intended use for public creators, per-post consent and series authorization, multi-user behaviour — no capability the product does not have.
3. For each §2 row, find the shipped screen and its owning task (e.g. 10.7.3's posting screen, the per-post consent UI, the disconnect/revoke screen, the deletion-request screen, the report page) and an artefact id from the pack; mark `provisional` where only staging evidence exists and name the blocking task.
4. Fill §3: `is_aigc = true`, the code path from 07, and where the user sees the disclosure; if the platform shows no label, say so plainly (the duty is on the user per FR-13-7) — never claim a label that does not exist.
5. Fill §4/§5 from the shipped flows: grant, per-post consent, disconnect, deletion request, and the takedown route (`/vi/report`, `/en/report`, 10 CR-24 — the reason list comes from the Content Policy's prohibited/restricted sections, D11).
6. Capture the portal's questions verbatim; answer each within the matrix/artefact evidence; keep answers short and traceable.
7. File the submission; record `sent at` + ticket reference in §0/§7.
8. Produce the calendar values (filing date, expected reply as a range/unknown ⚠️, re-file cadence, appeal path if the portal states one) and hand them to `13.5.2-T1`; record the pack date in §0 so a re-file reuses the same artefacts.
9. Every exchange (info requested, approved, rejected) appends to §7 and updates the calendar status; a re-file appends a new revision section rather than rewriting the previous one.

## Acceptance checks

- Given `07.4.1-T1`'s required-UX list, When §2 is read, Then every item appears as a row in 07's order with a non-empty owning task id and evidence artefact id, and no item was reworded or dropped.
- Given the artefact index, When §2/§3/§4 rows are resolved, Then every referenced artefact exists, has a matching sha256, and is redaction-checked (D14); no binary is tracked in the repo.
- Given the filing is about to be sent, When the verdicts are read, Then there is **no** `gap` row; every `provisional` row names the blocking task id and the reason (staging-only or screen not shipped).
- Given the portal form, Then the submitted answers use only claims traceable to a §2 row or an artefact id, and the questions are recorded verbatim.
- Given the filing date, Then `docs/compliance-calendar.md` (via 13.5.2-T1) has the TikTok audit row with status `filed`, the expected reply recorded as a range/unknown, and the re-file cadence.
- Given a rejection or "needs more information", Then §7 records the request, the remediation or the gap that cannot be remediated, and the status stays honest in the calendar — the audit is **not** re-filed with the same gaps.
- Given §3, Then `is_aigc = true` is stated with the code path from 07 and any user-visible disclosure is described as it actually ships (or the absence is stated).

## Failure handling and edge cases

| Case | Handling |
|---|---|
| A required UX item is not shipped at filing time | Row verdict = `gap` → **do not file**; record the blocking task id and wait (the R2 wording means this task runs after 07's slice). |
| 07's list and the portal's list differ | Copy both; file against the portal's list while showing 07's mapping; §7 records the difference and 07 is told (a CR, not a silent fix). |
| Evidence is staging-only | `provisional`, labelled; never present staging as production. |
| Portal requires a screencast | Capture per D14 (synthetic tenant, redaction, hash, binary outside the repo); record id/visibility. |
| Rejection | §7 + calendar status; `07.4.1-T1` owns any product change the rejection implies — this task does not patch 07. |
| TikTok throttles or the portal is unreachable | Record the attempt date/time in §7; the calendar row stays `not_filed`; retry cadence recorded. |
| Reply time unknown (⚠️) | Calendar stores "expected: unknown, check every <n> weeks" — never a fabricated date. |
| The artifact path conflicts with 07.4.1-T1's output | Resolve by keeping one filing copy: if 07 owns it, this task's §0 links to that path and the local file holds only the mapping tables **ruled T17** — `docs/compliance/tiktok-audit-<yyyy-mm-dd>.md` stays this task's single filing copy; `07.4.1-T1` links to it. |
