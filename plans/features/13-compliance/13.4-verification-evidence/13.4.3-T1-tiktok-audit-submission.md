# 13.4.3-T1 — TikTok Content Sharing audit submission (R2)

| Story | Size | Area | Depends on | Blocks | Phase / flag |

## Goal

File the TikTok Content Sharing audit (R2) so the 07 posting path may publish publicly from the owner's own TikTok account: argue the intended use — **a personal creator publishing their own videos, not an internal tool** ✅ — and show **every** UX item the platform requires, each one mapped to a shipped screen and a captured artefact from the `07.4.1-T1` evidence pack.

Deliverable = a filing document plus its calendar row; **no code, no route, no DTO, no table/column/index, no migration, no job, no CLI verb, no `tools/` script, no config key**. This is the only phase-R2 item in plan 13 and the last task of the folder (DEC 10.14 dropped the rest of the former S slice).

## Inputs

- **Contract:** this file, `plan.md` §1–§11, and 07's audit contract (`../07-tiktok-posting/README.md` §1.3 U1–U13, §3 D4/D8/D10/D11, §4 CR-7/CR-8/CR-9/CR-10, §7 gates, §8.1); `plans/13-compliance.md` §4 `13.4.3`, §6 row `13.4.3-T1` (BA, R2), §8 risk "audit delays".
- **Hard dependency — `07.4.1-T1`:** the evidence pack `docs/compliance/evidence-<yyyy-mm-dd>/index.md` (+ binaries in `~/.nts/compliance/evidence-<yyyy-mm-dd>/`), which carries the U1–U13 checklist, the screencast, the consent texts, the intended-use and volume notes and the error/limit log. 13 never re-captures 07's evidence and never restates its UX requirements in its own words.
- **Hard dependency — `10.7.3-T1`:** the posting screen (`/episodes/:id/publish/tiktok`) the screencast shows; its design task `10.7.3-T0` must be approved against 07 README §1.3 before capture.
- **AI-disclosure evidence:** TikTok posts carry `is_aigc = true` ✅ (07; FR-13-7) — the filing states the field and the code path that sets it, from 07's contract, not from a guess.
- **Personal scope (DEC 10.14):** the product serves the owner's own channel. The filing says exactly that: one owner account, one TikTok connection, no public sign-up, no other users, no charges. Do **not** claim multi-tenant or third-party-user capability.
- **External:** the TikTok developer portal's audit form and its required fields are not published in the plans → captured verbatim at filing time **[OPEN]**, and no reply deadline is promised (⚠️).

## Design

**Repo artifact (text only).**

```
docs/compliance/tiktok-audit-<yyyy-mm-dd>.md     # <yyyy-mm-dd> = filing date, ISO
```
**T17 (kept):** `docs/compliance/tiktok-audit-<yyyy-mm-dd>.md` is this task's single filing copy; `07.4.1-T1` links to it rather than keeping its own.

**Sections.**

```
  ## 0. Header
  ## 1. Intended use
  ## 2. Required-UX matrix
  ## 3. AI disclosure
  ## 4. Consent / revoke
  ## 5. Data handling and content rules
  ## 6. Calendar rows

```

| § | Contents |
|---|---|
| §0 | filing date · app id (redacted label + external artefact id) · `07.4.1-T1` pack date/path · sign-off |
| §1 | intended use — one personal creator publishing their own videos, single owner account, no other users — plus the consent model (per-post consent + series authorization) |
| §2 | `\| # \| Required UX item (verbatim from 07.4.1-T1) \| Where in the product \| Owning task id \| Evidence artefact id \| Verdict \|` |
| §3 | `is_aigc = true` · the code path that sets it (07) · any user-visible disclosure, described as it actually ships |
| §4 | grant · per-post consent · disconnect · token revoke — each with an artefact id |
| §5 | stored TikTok fields and their retention · deletion path (disconnect + the `13.3.1-T1` channel-scope deletion request) · prohibited/restricted content rules the owner follows; takedown of published videos uses TikTok's own in-app report — the product adds no public report route (DEC 10.14) |
| §6 | filing date · expected reply (range/unknown ⚠️) · re-file cadence · appeal path |
| §7 | appended per exchange (info requested, granted, denied + reason); earlier sections are never rewritten |

**Matrix rules.** One row per required UX item, in `07.4.1-T1`'s order; `Verdict ∈ {proven, provisional, gap}` where `provisional` = the evidence is staging-only or the screen is not shipped, and a single `gap` **blocks the filing** — the same rule `13.4.2-T1` uses for the YouTube audit. No row may have an empty `Evidence artefact id` or an empty `Owning task id`.

**Content rules.** Artefacts follow the evidence-pack convention in `../README.md` §B0a (synthetic tenant `demo+<n>@invalid`, no real e-mail/IP/token/API key/story text, binaries in `~/.nts/compliance/…`, sha256 in the index, ≥ 24-month retention).

## Steps

1. Wait for `07.4.1-T1`'s pack and required-UX list (hard); copy the items **verbatim** into §2, in its order. If 07 lists a different set than the portal shows at filing time, record both and flag the difference in §7 — do not silently reword 07.
2. Fill §1 from 07's contract and the personal scope: one owner account, per-post consent and series authorization — no capability the product does not have.
3. For each §2 row, find the shipped screen and its owning task (the `10.7.3-T1` posting screen, the per-post consent UI, the disconnect/revoke screen) and an artefact id from the pack; mark `provisional` where only staging evidence exists and name the blocking task.
4. Fill §3: `is_aigc = true`, the code path from 07, and where the user sees the disclosure; if the platform shows no label, say so plainly (the duty is on the user per FR-13-7) — never claim a label that does not exist.
5. Fill §4/§5 from the shipped flows: grant, per-post consent, disconnect/token revoke, the deletion path (`13.3.1-T1`'s channel-scope request) and the stored-field/retention table; state that takedown of a published video is TikTok's own report flow.
6. Capture the portal's questions verbatim; answer each within the matrix/artefact evidence; keep answers short and traceable.
7. File the submission; record `sent at` + ticket reference in §0/§7.
8. Produce the calendar values (filing date, expected reply as a range/unknown ⚠️, re-file cadence, appeal path if the portal states one) **inline in §6** (no `docs/compliance-calendar.md`: that file belonged to a dropped task, DEC 10.14); record the pack date in §0 so a re-file reuses the same artefacts.
9. Every exchange (info requested, approved, rejected) appends to §7 and updates the §6 status; a re-file appends a new revision section rather than rewriting the previous one.

## Acceptance checks

- Given `07.4.1-T1`'s required-UX list, When §2 is read, Then every item appears as a row in 07's order with a non-empty owning task id and evidence artefact id, and no item was reworded or dropped.
- Given the artefact index, When §2/§3/§4 rows are resolved, Then every referenced artefact exists, has a matching sha256, and is redaction-checked; no binary is tracked in the repo.
- Given the filing is about to be sent, When the verdicts are read, Then there is **no** `gap` row; every `provisional` row names the blocking task id and the reason (staging-only or screen not shipped).
- Given the portal form, Then the submitted answers use only claims traceable to a §2 row or an artefact id, and the questions are recorded verbatim.
- Given the filing date, Then §6 has the filing row with status `filed`, the expected reply recorded as a range/unknown, and the re-file cadence.
- Given a rejection or "needs more information", Then §7 records the request, the remediation or the gap that cannot be remediated, and the §6 status stays honest — the audit is **not** re-filed with the same gaps.
- Given §1, Then the intended use claims a **single owner account publishing its own videos** and no capability the personal product does not have (DEC 10.14).
- Given §3, Then `is_aigc = true` is stated with the code path from 07 and any user-visible disclosure is described as it actually ships (or the absence is stated).

## Tests

No test file is added (documents only). Evidence run:

- **Matrix completeness:** read §2 end-to-end; grep the artefact column for empty cells and any row lacking a task id (`plan.md` §9 TS-6).
- **Redaction:** the `VP7_RedactionClean` grep over `docs/compliance/**`; confirm no media tracked (`git status --porcelain docs/compliance`).
- **Hash consistency:** `shasum -a 256 ~/.nts/compliance/evidence-<date>/*` against the pack's `index.md` column (`plan.md` §9 TS-3).
- **R2 gate:** the audit is filed with 07's required UX items **and** the evidence pack — both must be present and cited before the gate closes (`plan.md` §7).
- **Manual portal check:** the form's field set captured verbatim, with a timestamp, in §0/§7.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| A required UX item is not shipped at filing time | Row verdict = `gap` → **do not file**; record the blocking task id and wait (R2 means this task runs after 07's slice). |
| 07's list and the portal's list differ | Copy both; file against the portal's list while showing 07's mapping; §7 records the difference and 07 is told (a CR, not a silent fix). |
| Evidence is staging-only | `provisional`, labelled; never present staging as production. |
| Portal requires a screencast | Capture per the evidence-pack convention (synthetic tenant, redaction, hash, binary outside the repo); record id/visibility. |
| Rejection | §7 + §6 status; `07.4.1-T1` owns any product change the rejection implies — this task does not patch 07. |
| TikTok throttles or the portal is unreachable | Record the attempt date/time in §7; the §6 row stays `not_filed`; retry cadence recorded. |
| Reply time unknown (⚠️) | §6 stores "expected: unknown, check every <n> weeks" — never a fabricated date. |
| The artifact path conflicts with 07.4.1-T1's output | Resolve by keeping one filing copy: `docs/compliance/tiktok-audit-<yyyy-mm-dd>.md` stays this task's single filing copy; `07.4.1-T1` links to it. |
