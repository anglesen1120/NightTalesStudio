## Goal

Create `docs/compliance-calendar.md` — **this folder's file** (K13 :162) — as the single place where every recurring compliance deadline is written down with an owner, a cadence and a next-due date, plus a **Log** section carrying the monthly deletion-SLA/DSAR report read from the 08.1 monitoring stack (D15 :252–254). The calendar turns NFR-13-1's "100 % of deletion requests before `due_at`" and FR-13-5's 72-hour report target into measured numbers instead of memory, and it names the flag from D12 so the OAuth launch gate cannot be forgotten.

Deliverable = one markdown file plus the metric values and three alert rules handed to their owners. **No code, no route, no DTO, no table/column/index, no migration, no job, no CLI verb, no `tools/` script, no config key** (D18 :262) — the metrics already exist (or are declared by 13.3.3-T1/13.3.4-T1, see §Failure handling).

## Design

**Repo artifact (text only).**

```
docs/compliance-calendar.md
  # Compliance calendar
  > header: purpose · owner · how a row is closed · where the metrics come from (08.1) · legend ⚠️/[DECISION]

  ## Deadlines
  | # | Item | Owner | Cadence | Next due | Last done | Evidence link | Status |

  ## Log
  ### <YYYY-MM> monthly report
  | Metric | Value | Target / threshold | Notes |
  ### <YYYY-MM> incidents / misses
  | Date | Row | What lapsed | Impact | Action | Closed at |

  ## Alert rules handed over (11.6.2-T1)
  | Rule | Condition | Severity | Owner |
```

**Deadlines rows (D15 :252, one row per item kind — names kept verbatim):**

| Item | Cadence | Notes |
|---|---|---|
| OAuth verification (D12) | one-off + re-check while `not_filed` | carries the flag key `saas_registration` and the appeal path `https://support.google.com/youtube/contact/yt_api_appeals` |
| YouTube re-audit cadence | **⚠️ unknown** (13.4.2 plan's inline row; do not invent a number) | next due reads `pending — Google cadence unpublished` + a check cadence |

| Key rotation | 11's ops cadence | link the rotation record, not the key |
| Monthly deletion-SLA + DSAR report | monthly | the Log block below; this row is the trigger |

**Monthly report block (D15 :254, metric names verbatim):** `deletion_requests_open`, `deletion_request_overdue_total` (P/K18), `dsar_export_failed_total`, `reports_open_total`, and the **oldest open report age** (hours) with the 72-hour target column. Read from the 08.1 stack at month close; the block also records the worst miss of the month.

**Honesty rules (this is the point of the file).**
- A metric that has no emitter yet is written `n/a — emitting task <id>`, never `0`. Emitters are ruled (T13, README §B10): `dsar_export_failed_total` ← `13.3.3-T1`, `reports_open_total`/oldest-open-report ← `13.3.4-T1`; `n/a` still applies whenever this task reads a metric before that folder has shipped.
- A deadline whose date is not published (⚠️) reads `pending — <who> publishes it` with a check cadence; never a fabricated date.
- A month that missed the 24-hour alert or the 72-hour target says so in the Log; the file is an operating record, not a marketing page (T9).
- No user data in the file: no e-mail, IP, tenant id or report text — counts, ages and row references only (D17 baseline).

**Metadata per row:** `Next due` (ISO date or `pending`), `Last done` (ISO date), `Evidence link` (a repo path, an artefact id from the 13.5.1-T1 pack, or a dashboard name — never a secret).

## Steps

1. Create `docs/compliance-calendar.md` with the header, the `## Deadlines` table and the empty `## Log` and `## Alert rules handed over` sections.
2. Fill the seven D15 item kinds; copy the YouTube-audit row **verbatim** from `13.4.2-audit-filing/plan.md:192`/`:225` (K13) and keep the `⚠️` on the re-audit cadence.
3. Fill the OAuth-verification row from 13.4.1-T1's values, including the flag key `saas_registration`, the current status (`not_filed|filed|info_requested|granted|denied`) and the appeal path.
4. Add the TikTok-audit row skeleton (R2, values land when 13.4.3-T1 files) and the restore-drill/key-rotation rows pointing at 11.6.1-T1's evidence.
5. At the first month close: read the five metric values + the oldest open report age from the 08.1 stack (or record `n/a — emitting task <id>`), append the `### <YYYY-MM> monthly report` block, and record any `due_at` miss in the incidents block.
6. Hand 11.6.2-T1 the three alert rules (deletion overdue `due_at − now < 24 h` — already P; export failed twice for the same request; oldest open report > 72 h, D15 :254) and record the handover in the `## Alert rules handed over` section with the receiving task id.
7. Keep `Last done`/`Next due` updated as rows close; on a policy-version bump, add the follow-on rows (re-publish via 13.2.2-T1, re-acceptance via 13.2.1-T2) rather than editing the historical log.

## Failure handling and edge cases

| Case | Handling |
|---|---|
| A metric has no emitter yet | Write `n/a — emitting task <id>` and raise a CR to that task (13.3.3-T1 for `dsar_export_failed_total`, 13.3.4-T1 for `reports_open_total` / oldest-open-report age); never invent a series and never write `0`. |
| Deadline unknown (⚠️ e.g. YouTube re-audit cadence) | `Next due = pending — <who> publishes it` + a check cadence; no fabricated date (K16-style caution). |
| A month is missed entirely | Append the month block with the values you can read and an explicit "month not reviewed on time" note; the incidents block stays empty only if nothing lapsed. |
| 08.1 stack unavailable at month close | Record the date/time of the attempt and the reason; carry the value forward as `n/a — dashboard unreachable`, and re-read later the same month when it returns. |
| A deletion request exceeded `due_at` | The P alert (`due_at − now < 24 h`) should have fired first; if it did not, record that the alert failed as an incident — that is 11.6.2-T1's rule to fix, this task records the miss. |
| Policy text changes (new version) | Add follow-on rows (13.2.2-T1 publish, 13.2.1-T2 re-acceptance) with their own `Next due`; do not rewrite past log entries. |
| OAuth granted / denied | Update the row's status and the flag key note; the flip itself happens in 13.4.1-T1 (O9), never here. |
| A key rotation row tempts someone to paste a key | Evidence links point at the rotation *record*, never the key (K18/no-secret rule). |
| Calendar grows into a second source of truth for legal text versions | It stores only dates and pointers; the version source of record stays `legal_documents` + `manifest.json` (D6/CR-12). |
