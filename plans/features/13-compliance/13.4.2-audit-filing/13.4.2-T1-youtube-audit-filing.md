## Design

**Repo artifact (text only).**

```
docs/compliance/youtube-audit-<yyyy-mm-dd>.md      # <yyyy-mm-dd> = filing date, ISO
  ## 0. Header            filing date · production API project (the audited one) + owner channel
                          (redacted label + external-artefact id) · pack path/date · form URL · sign-off lines
  ## 1. Walkthrough result
  ## 2. Form answers
  ## 3. Quota justification
  ## 4. Links
  ## 5. Pack index
  ## 6. Calendar             # filing-date + re-audit reminder ONLY, inside this doc — handoff row for 13.5.2-T1, see boundary note below
  ## 7. Appeal path
  ## 8. Follow-up log
  ## 9. Revision <n> — <date>      # appended on a re-file; sections 0–8 of the earlier revision are never rewritten
```

**External (recorded, never committed):** the submitted form copy + Google confirmation/ticket reference, screenshots taken at filing time, the support/appeal thread — location and SHA-256 go into the pack's `06-artefacts.md` (`06.5.1-T1-audit-evidence-pack.md:89`).

**§ 1 schema** — one row per step, `| Step | Action | Observable | Evidence (pack artefact id / timestamp) | Clause ids | Verdict | Verifier |`. $\text{Verdict} \in \{proven, provisional, gap\}$; `provisional` = staging-only or screen-not-yet-shipped evidence, explicitly labelled; **`gap` blocks the filing**.

**§ 2 schema** — `| Form question (verbatim as presented) | Answer | Pack artefact / clause-row refs | Redaction |`. The form's field set is not published in the plans and may change, so the questions are captured verbatim from the live form at filing time [OPEN]; answers are ≤ 3 sentences each, every one traceable to a pack artefact (A1–A16) or a clause-map row; no claim outside the pack.

**§ 3 quota justification (the arithmetic).** One unit per `videos.insert` (G1:31). The three figures are separate: **(1) observed** = `max(units_used)` over the audit window from `platform_quota_usage` — evidence, satisfying `units_used ≤ units_limit` (= `YouTube:Quota:UnitsPerDay`); **(2) scheduled need** = what the owner's settings will actually ask for — the planner admits at most `daily_cap` publications for a **channel** on a local day (`02.8.3-cadence-publishing/plan.md:88`), so per audited channel `need(channel) = min(daily_cap, uploads the channel's enabled series schedule on the busiest local day)` and `scheduled_need = Σ over audited channels` (one channel in P) — **not** the sum of the `daily_cap` values of series sharing a channel (the cross-series cap precedence is [OPEN] in 02.8.3; this document uses the cap as the upper bound); **(3) requested extension** = the ask, sized for the intended use: `ask ≥ scheduled_need`, `ask ≥ observed`, and scaled at M2 by `uploads/user/day × beta users` (`plans/13-compliance.md:85`). An extension exists only while `ask > 100`; if the justified need is ≤ 100, § 3 states **"no extension needed at M1 — keep `YouTube:Quota:UnitsPerDay` = 100"** and asks for none. The M1 filing's role (`plans/13-compliance.md:84-85`) is to **justify** quota from the owner's cadence and daily cap; the extension figure itself is requested at the M2 re-filing from beta data (`uploads/user/day × users`). The request is never capped at observed usage: observed history is what the 100-call bucket allowed, not what the cadence needs. Expressed in `videos.insert` calls/day against the **100-call Video Uploads bucket**; `videos.list`/`channels.list` draw on the separate **shared 10,000-unit** bucket (`videos.list` = 1 unit, batched by 50 — 06 README D16), stated separately. No fabricated volume numbers: every figure is read at filing time and cited.

**Redaction rule (repo copy).** Forbidden in the document: client secret (`GOCSPX…`), OAuth access tokens (`ya29.…`), refresh tokens (`1//…`) and `refresh_token`/`access_token` values, upload session URI, `code`/`state` values including the `?code=`/`?state=` query strings, consent/cancel tokens, cookies, `Authorization` headers, e-mail addresses, **IPv4 and IPv6 addresses**, channel names/titles, **YouTube video ids** (their publication forms `youtu.be/<id>`, `youtube.com/watch?v=<id>`, `studio.youtube.com/video/<id>`), raw API payloads. Allowed: the secret **name**, the OAuth **client id**, redacted labels (`channel #1`, `video #1`), row-existence statements. The submission copy kept outside the repo may carry the owner's contact e-mail and the client id — the minimum Google needs (`../README.md:50`). The check (VF5 command block, § Tests) runs over **both** `docs/compliance/youtube-audit-*.md` and `docs/compliance/audit-pack/` in two parts: **A** value-shaped (must print nothing), **B** field names the pack's tables may legitimately mention (every hit explained in the § 2 redaction column). Known A noise: four-part version strings (`1.76.0.4262`); clock times do not match the IPv6 alternative (≥ 3 colon groups).

**Verdict vocabulary / invariants (in-document gates).** I1 no `gap` for III.A.1, III.A.2, III.C.3, III.D.2, III.E.4; I2 every answer traceable; I3 quoted versions = `manifest.json` = `LegalDocuments:Current:*`; I4 § 3 separates observed usage (`units_used ≤ units_limit` = `YouTube:Quota:UnitsPerDay`) from the justified future request, computes the scheduled need under the **per-channel** `daily_cap` rule (not a sum over series sharing a channel), requires `ask ≥ scheduled need` and `ask ≥ observed`, and treats it as a request only when `ask > 100`; I5 redaction clean (two people); I6 walkthrough ran on the production API project, staging rows labelled; I7 no policy sentence quoted unless re-read that day.

**Boundaries.** Do not edit the pack (`06.5.1-T1-audit-evidence-pack.md:136`), the legal texts (13.1.1-T1 / 13.1.2-T1), the acceptance endpoint/dialog (13.2.1-T1), the deletion engine (13.3.1-T1), or `YouTube:AuditStatus` (owner/ops, 06 README:126). No new export route, e-mail template, feature flag, audit writer or CLI — every evidence item comes from an existing table, route or screen (no second mechanism; 06 README D1/D17). **Calendar boundary:** `docs/compliance-calendar.md` is 13.5.2-T1's deliverable (Must · XS, S — after Gate 2, `plans/13-compliance.md:95-96`), not this task's; § 6 of this document only *records* the filing date, the re-audit reminder and the ⚠️ cadence assumption inline, worded as a ready-to-copy row, and this task never creates or appends `docs/compliance-calendar.md`.

**Performance.** No runtime path: batching/streaming/N+1 do not apply; the document is a few hundred KB of text at most; the pack's read-only SQL runs on existing indexes (`platform_quota_usage` PK `(platform, quota_day)`) and is not re-invented here.

**Security and privacy.** Secrets/tokens are never read or written (names only; tokens live encrypted in `channel_connections.*_enc`); no personal data in the repo; the second-person redaction pass is mandatory; no new `[Audited]` action and no product log line is added; the repo document contains no personal data and is therefore outside 13.3.1-T1's deletion scope (13 README:27 K5). Tenant-404 / CSRF / idempotency / ETag are **not applicable** (no endpoint, no state change) — stated so a reviewer does not look for them. Idempotency in this task means: one document per filing date, re-files append `## 9. Revision <n>` instead of editing history.

## Steps

1. Confirm the entry gate: pack present with its index + clause map and gate **06-audit-ready** stated (`plans/features/06-youtube-posting/README.md:187`); 13 P slice live. Freeze the filing date `<yyyy-mm-dd>` and record the pack id/date.
2. Create `docs/compliance/youtube-audit-<yyyy-mm-dd>.md` and write § 0 (filing date, audited production API project, owner channel as a redacted label with its external-artefact id, pack path/date, form URL, sign-off lines for author + reviewer).
3. Re-run the 13 walkthrough steps against the **production** API project and the owner's channel, in the order of the pack's `01-walkthrough-checklist.md`: (1) legal acceptance dialog → (2) connect (re-auth + consent) → (3) channels page shows the connection → (4) publish form filled (title/description/tags/privacy/schedule) → (5) per-video consent (`pc.v1` shown + version recorded) → (6) upload → private → (7) processing → published → (8) disconnect (Google revoke + 7-day request) → (9) autopilot on (series authorization text + version) → (10) veto-window notice with edit/cancel/approve-now → (11) consent row written by the scheduler/authorization → (12) upload of the autopilot publication → (13) quota wait + ETA when the day is full. Fill § 1 with per-step verdicts, timestamps and evidence refs; label staging-only rows `provisional`.
4. Verify I1 against `docs/compliance/audit-pack/<date>/02-policy-clause-map.md`: any `gap` row for a mandatory clause stops the filing — hand the gap back to `06.5.1-T1`'s owner instead of writing an answer around it.
5. Open the audit form once; copy every question verbatim into § 2 (field set [OPEN]).
6. Answer each question from the pack only (artefact/clause refs in the third column); state the redaction applied per row.
7. Write § 3 with the three figures using the values read at filing time (`daily_cap`, cadence, `YouTube:Quota:UnitsPerDay`): the observed `units_used` peak from the cited `platform_quota_usage` rows, the scheduled need computed under the per-channel cap, and the requested extension sized for the M2 projection (`uploads/user/day × users`) — or the explicit "no extension needed at M1" statement when the justified need is ≤ 100.
8. Write § 4: privacy policy URL, ToS URL (both live at the filed versions), the revoke link, the Google Privacy Policy link, the contact line.
9. Write § 5 (pack path/date + artefact ids + clause-map reference), § 6 (M2 re-file entry; re-audit re-check date — cadence ⚠️ [OPEN]; re-verification of the answers after any policy change), § 7 (appeal URL + triggers: rejection, silent rejection, quota denial; what is re-submitted), § 8 (follow-up date, since no Google SLA is published ⚠️).
10. Run the scripted checks and fix until clean: `python3 tools/ci/check-legal-versions.py` (VF3, must exit 0) and the redaction grep (VF5, must print nothing).
11. Hand the document to the second person (UC6): they re-check three § 2 rows against the pack, repeat VF5, and sign § 0; the author fixes anything they flag and re-runs step 10.
12. Owner signs § 0, submits the form; record the submitted copy + confirmation/ticket reference outside the repo and add its location + SHA-256 to the pack's `06-artefacts.md`.
13. Write the outcome into § 8; state the gate evidence for `13-P-ready` ("filing done", `../README.md:64`) in text handed to the 13 and 06 plan owners. **No file outside `docs/compliance/` is edited by this task.**
14. On a Google question: repeat 6 + 10 + 11 for the new row; if the answer needs behaviour evidence the pack does not carry, hand back to `06.5.1-T1` and pause the filing rather than answering unproven.

## Failure handling and edge cases

| Case | Behaviour |
|---|---|
| A mandatory clause row is `gap` in the pack | filing stops at step 4; the gap goes back to `06.5.1-T1` with the blocking artefact id; no answer is improvised around it |
| Audit not decided for months ⚠️ | § 8 stays open; the studio continues in pre-audit mode (`AuditStatus = pending`, uploads `private`, no `publishAt`, outcome `published_private_locked`) — public growth waits; this is the recorded residual risk (`plans/06-youtube-posting.md:209`; 02.8.3-T3:63-68) |
| Audit rejected | § 7 appeal submitted the same day; § 8 records the reason; fixes go to the owning task; a corrected revision is re-filed; the channel stays private meanwhile (`plans/13-compliance.md:168`) |
| The quota extension is denied or deferred | keep `YouTube:Quota:UnitsPerDay = 100` and the 1/day personal cap (`plans/00-overview.md:27`); re-request at M2 with beta data (`plans/13-compliance.md:85`) |
| The form asks something the pack does not answer | add the § 2 row + the pack's clause-map row; if behaviour-backed evidence is missing, `06.5.1-T1` extends the pack first and the filing pauses |
| A policy sentence changed since pack collection | that sentence's rows are re-collected and re-verdict before submitting (I7); the changed rows are re-checked by the reviewer |
| Version drift (`manifest.json` vs `LegalDocuments:Current:*`) | `VP4/VF3` fails → fix the drift first (13.2.2-T1 owns the CI check, 13 CR-30, `../README.md:42`); the filing waits |
| Production vs staging project confusion | § 1 rows name the environment; a staging-only row is `provisional` and cannot satisfy a mandatory clause (I6) |
| Answers stale because the owner changed the cadence mid-review | re-read `daily_cap`/cadence at submission time and rewrite § 3 (the ask must match the settings snapshot being filed) |
| A follow-up reveals a behaviour that does not match the policy | treat as a gap: fix the behaviour (owning task) or amend the policy text (13.1.x) before answering — never answer around it |
| The audit is approved | owner flips `AuditStatus` to `approved` (06 README:126); the authorization text loses `{{pre_audit_note}}` → the covered-field diff revokes the series authorization and the owner re-accepts before the first public upload (02.8.3-T2:69-71, :170) — recorded in § 6 as the follow-up action, not performed here |
| A secret or personal datum is found in the repo copy | rotate the affected credential (`nts/<env>/api/YOUTUBE_CLIENT_SECRET`, 06 README:102), redo the redaction pass, correct the copy before submission |
| No answer within the expected window | § 6 follow-up date; no published Google SLA ⚠️, so a check date is recorded instead of a deadline [OPEN] |
| Rollback | none needed (documents only); a defective filing is corrected by a revision + re-submission — the submitted form cannot be recalled [DECISION] |
