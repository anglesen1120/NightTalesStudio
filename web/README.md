# web

Angular workspace of the NightTales Web UI (plan 10). This file only documents what a developer must not get wrong; the contract is `plans/features/10-web-ui/README.md`.

## Generated API client (`src/app/shared/api/**`)

The client is generated by `ng-openapi-gen` (pinned in `package.json`) from the vendored backend document `openapi.json`, which is the `openapi` artifact of `backend.yml` (09.1.5-T1). `tools/web/openapi.lock.json` records its source, `info.version`, SHA-256 and `sourceCommit` (the backend commit it was built from); `tools/web/openapi-contract.test.mjs` recomputes the hash.

- **Never edit `src/app/shared/api/**` or `openapi.json` by hand.** Both are generated/vendored, are excluded from lint, and a hand edit fails `npm run api:gen:check` with the file and line.
- `npm run api:gen` regenerates the tree from the committed `openapi.json` (second run: no diff).
- `npm run api:gen:check` (alias `api:check`, run by `web.yml`) regenerates into a temp directory and fails on any drift, on an absolute `http(s)://` literal in generated code (the SPA is same-origin) and when `index.ts` stops exporting `ProblemDetails`. It also rejects an `api-gen.config.json` option the pinned generator does not support.
- **Adopting a new backend document:** produce `src/NightTales.Api/openapi.json` with the backend build (`docs/dev-setup.md`, "build-time OpenAPI generation") or download the `openapi` artifact, then run `npm run api:gen:local -- <path>`. It generates into a temp directory first and only on success regenerates the tree, replaces `openapi.json` and rewrites the lock; a failed generation exits non-zero with the generator error and leaves all three untouched. Commit the three together and review the generated diff (`ProblemDetails` and the DTOs the screens map) in the same PR.
- Only `features/*/data-access/**` and `core/**/data-access/**` may import `@shared/api` (spec files excepted); everything else goes through the domain port.
- `excludeTags` in `api-gen.config.json` lists tags the generator cannot import (a dotted tag such as `NightTales.Api`, which ASP.NET gives lambda handlers). Operations under an excluded tag have no generated client; the fix is an explicit `WithTags` on the backend endpoint, after which the entry is removed.

## Content Security Policy and Trusted Types (README D4, WR2, WR12, WR13)

The policy is a **response header**, never a `<meta>` tag and never patched from JavaScript.

- `npm run build && npm run csp:gen` writes exactly one file, `dist/nginx/csp-headers.conf`, outside the served
  `dist/web/browser` tree. It holds one `add_header Content-Security-Policy "..." always;` line. Nothing generated is
  committed. The web `Dockerfile` builder stage runs both commands, so the image cannot ship without the policy;
  `web.yml` runs them again for validation only.
- `tools/web/gen-csp.mjs` SHA-256-hashes every executable inline `<script>` of the built HTML into `script-src`
  (JSON / import-map data blocks are not hashed). It **fails the build**, naming file and line, on an inline `on*=`
  handler, a `javascript:` URL, a `<script src>` that is not same-origin, a policy over 8 000 characters, or a
  produced file that breaks the D4 contract. There is no bypass flag.
- A new inline script is hashed by the build automatically. Never whitelist it with `'unsafe-inline'` or a CDN origin;
  prefer an external, self-hosted file. `optimization.styles.inlineCritical` must stay `false` (its injected `onload`
  handler would fail `csp:gen`).
- The production document has no `<base>` (`base-uri 'none'`): `angular.json` sets `deployUrl: "/"` so assets are
  root-relative and `app.config.ts` provides `APP_BASE_HREF`. `ng serve` does not honour `deployUrl`, so the
  `development` build configuration sets `baseHref: "/"` instead (dev sends no CSP, so a `<base>` is harmless there);
  `e2e/deep-link.spec.ts` reloads a nested route on both targets. Because the production document has no `<base>`,
  every runtime fetch (Transloco loader included) must use a root-relative URL (`/assets/...`), never `assets/...`.
- Media origins: the file keeps `${NTS_CSP_MEDIA_ORIGINS}` literal in `img-src 'self' data:${...}` and
  `media-src 'self'${...}` (no space before the placeholder); the image's envsubst fills it at container start from
  `NTS_CSP_MEDIA_ORIGINS` (space-separated `http(s)://host[:port]` origins, empty by default).
  `docker-entrypoint.d/16-nts-media-origins.envsh` gives each validated origin a leading space, so an empty list
  leaves exactly `img-src 'self' data:` / `media-src 'self'`. The container's entrypoint rejects a malformed value.
  To add an origin, set that variable; never widen `img-src` / `media-src` to `*`.
- Trusted Types: the header allow-lists exactly `angular`, `angular#bundler` and `nts-sanitizer`.
  `core/security/nts-sanitizer.ts` is the only module that may create a policy (and the only file exempt from the
  `bypassSecurityTrust*` lint ban); `shared/util/download-blob.ts` + `safe-filename.ts` are the only download path.
- `ng serve` sends no CSP. The runtime proof is the container run: `NTS_E2E_TARGET=container npm run e2e` against the
  image (`e2e/security/*`); every spec imports `test` from `e2e/fixtures/csp.fixture.ts`, which fails on any CSP or
  Trusted Types violation.

## Translations (README D10)

- One **scope** per feature: `web/src/assets/i18n/<scope>/{vi,en}.json`. Both files are mandatory; `vi` is the default.
- `core` is Transloco's root translation (keys are used as written, e.g. `common.close`, `core.ui.pageHeader.back`).
  Every other scope is declared on its lazy route with `provideTranslocoScope('<scope>')`; its file keys are prefixed
  with the scope name in code: `quality/vi.json` `{ "hook_missing": … }` is used as `quality.hook_missing`.
- Key style `scope.area.item`, camelCase leaves, no sentence fragments outside a scope. Keys handed over by other plans
  are used verbatim (`series.style.<name>.label/.hint`, `series.style.trueCrimeNotice`, `voices.tag.<tag>`,
  `quality.*`, `render.*`).
- Dates, numbers, relative times and schedule times go through `LocaleService`; no screen calls `Intl` directly.
  `LocaleService.activate(locale, { persist })` is the only way to change the language.
- `npm run i18n:check` (CI) fails on a key present in one language only, a duplicate or non-string leaf, a missing
  language file, a missing handed-over key, and a key used in code that no file defines. `npm run i18n:find` lists
  used and unused keys against the files (dev aid, not a CI step).
